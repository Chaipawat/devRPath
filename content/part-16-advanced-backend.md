## 1. Big Picture

Chapter ก่อนหน้านี้สอนให้คุณ "เขียนระบบให้ทำงานได้"
Chapter นี้สอนให้คุณ **"เขียนระบบให้ยังทำงานได้ตอนคนใช้เยอะ และตอนชิ้นส่วนบางตัวพัง"**

นี่คือเส้นแบ่งจริง ๆ ระหว่าง Mid กับ Senior ในห้องสัมภาษณ์

Junior ถูกถามว่า: *"เขียน API นี้ยังไง"*
Mid ถูกถามว่า: *"API นี้ช้า แก้ยังไง"*
Senior ถูกถามว่า: *"ถ้า database ล่ม 30 วินาที ระบบคุณจะเกิดอะไรขึ้น และผู้ใช้จะเห็นอะไร"*

### ทุกอย่างใน chapter นี้แก้แค่ 3 ปัญหา

ฟังดูเยอะ 30 กว่าคำ แต่จริง ๆ มันตอบแค่ 3 คำถาม:

เพราะพอเขาถามเรื่องอะไรก็ตาม คุณถามตัวเองก่อนว่า *"เขากำลังพูดถึงปัญหากลุ่มไหน"*

### กฎทองของบทนี้ — ทุกอย่างมีราคา

> **ทุกเทคนิคใน chapter นี้ไม่ได้ "ทำให้ระบบดีขึ้น" — มันแค่ "ย้ายปัญหาไปที่อื่น"**

- Cache → เร็วขึ้น แต่ได้ปัญหา **ข้อมูลเก่า** มาแทน
- Queue → ทนโหลดได้ดีขึ้น แต่ได้ปัญหา **ผู้ใช้ไม่รู้ว่างานเสร็จหรือยัง** มาแทน
- Microservices → ทีมโตได้ แต่ได้ปัญหา **network ระหว่าง service** มาแทน
- Retry → ทนของพังได้ แต่ได้ปัญหา **ข้อมูลซ้ำ** มาแทน

คนสัมภาษณ์ระดับ Senior ไม่ได้รอฟังว่าคุณรู้จัก Redis
เขารอฟังว่า **คุณรู้ว่าใส่ Redis แล้วคุณเพิ่งซื้อปัญหาอะไรเข้ามา**

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Caching** | เก็บของไว้ใกล้มือ | เก็บผลลัพธ์ที่คำนวณ/ดึงมาแล้ว ไว้ใช้ซ้ำ ไม่ต้องทำใหม่ |
| **Redis** | ตู้เก็บของความเร็วสูง | in-memory data store ใช้เป็น cache / session / queue / lock |
| **Cache Aside** | "ถามตู้ก่อน ไม่มีค่อยไปหลังร้าน" | pattern: อ่าน cache ก่อน miss แล้วค่อยอ่าน DB แล้วเขียนกลับ cache |
| **Cache Hit / Miss** | เจอ / ไม่เจอ | เจอของใน cache = hit, ไม่เจอ = miss ต้องไป DB |
| **Cache Invalidation** | ลบของเก่าทิ้ง | การทำให้ cache ที่ล้าสมัยหายไปเมื่อข้อมูลจริงเปลี่ยน |
| **TTL** | วันหมดอายุ | Time To Live — เวลาที่ cache อยู่ได้ก่อนถูกลบอัตโนมัติ |
| **Stale Data** | ข้อมูลค้าง | ข้อมูลใน cache ที่ไม่ตรงกับความจริงแล้ว |
| **Queue** | คิวใบสั่งงาน | ที่พักงานที่ยังไม่ได้ทำ ให้ worker มาหยิบไปทำทีหลัง |
| **Message Broker** | บุรุษไปรษณีย์ | ตัวกลางที่รับ message แล้วส่งต่อให้ผู้รับที่ถูกต้อง |
| **RabbitMQ** | ไปรษณีย์ส่งพัสดุรายชิ้น | message broker เน้นส่งงานให้ worker ทำทีละชิ้น |
| **Kafka** | สมุดบันทึกเหตุการณ์ | event log ที่เก็บเหตุการณ์ไว้ตามลำดับ ให้หลายคนมาอ่านซ้ำได้ |
| **Producer / Consumer** | คนส่ง / คนรับ | ฝั่งที่ยิงงานเข้า queue และฝั่งที่ดึงงานไปทำ |
| **Worker** | คนงานหลังร้าน | process แยกที่คอยหยิบงานจาก queue ไปทำ |
| **Background Job** | งานที่ทำทีหลัง | งานที่ไม่ต้องรอผลทันที เช่น ส่ง email, gen PDF |
| **WebSocket** | สายโทรศัพท์ที่เปิดค้าง | การเชื่อมต่อสองทางค้างไว้ ให้ server ส่งข้อมูลหาเราได้เอง |
| **Polling** | ถามซ้ำ ๆ ทุก 5 วิ | client ยิงถาม server เป็นระยะว่า "มีของใหม่ยัง" |
| **Long Polling** | ถามแล้วรอจนกว่าจะมี | client ยิงถามแล้ว server ค้างไว้จนมีข้อมูลค่อยตอบ |
| **Load Balancer** | คนโบกให้ไปช่องว่าง | กระจาย request ไปหลาย server ไม่ให้ตัวใดตัวหนึ่งตาย |
| **Reverse Proxy** | หน้าด่านที่รับแทน | ตัวรับ request แทน server จริง แล้วส่งต่อข้างใน |
| **API Gateway** | ประตูหน้าที่มียาม | จุดเข้าเดียวของทุก API ทำ auth / rate limit / routing |
| **CDN** | สาขาใกล้บ้าน | เครือข่าย server ทั่วโลกที่เก็บไฟล์ static ไว้ใกล้ผู้ใช้ |
| **Horizontal Scaling** | เพิ่มจำนวนเครื่อง | scale out — เพิ่ม server หลายตัว |
| **Vertical Scaling** | เพิ่มพลังเครื่องเดิม | scale up — เพิ่ม CPU/RAM ให้เครื่องเดียว |
| **Stateless** | ไม่จำอะไรระหว่าง request | server ไม่เก็บข้อมูลผู้ใช้ไว้ในตัวเอง |
| **Stateful** | จำไว้ในตัว | server เก็บ state ของผู้ใช้ไว้ใน memory ตัวเอง |
| **Sticky Session** | ผูกลูกค้าไว้กับโต๊ะเดิม | LB บังคับให้ผู้ใช้คนเดิมไปเครื่องเดิมเสมอ |
| **Monolith** | ตึกเดียวจบ | ทั้งระบบเป็น codebase / deploy เดียว |
| **Modular Monolith** | ตึกเดียว แต่แบ่งห้องชัด | monolith ที่แบ่ง module มีขอบเขตชัดเจน |
| **Microservices** | หลายตึกแยกกัน | แยกระบบเป็นหลาย service deploy แยก ทีมแยก |
| **Distributed System** | ระบบที่กระจายหลายเครื่อง | ระบบที่ชิ้นส่วนคุยกันผ่าน network |
| **Idempotency** | ทำซ้ำได้ ผลเท่าเดิม | เรียกซ้ำกี่ครั้ง ผลลัพธ์เหมือนเรียกครั้งเดียว |
| **Retry** | ลองใหม่ | ยิงซ้ำเมื่อเรียกครั้งแรกล้มเหลว |
| **Timeout** | หมดเวลารอ | กำหนดว่ารอนานสุดเท่าไร ไม่งั้นถือว่าพัง |
| **Exponential Backoff** | รอนานขึ้นเรื่อย ๆ | retry แบบเว้นช่วงเพิ่มขึ้นทวีคูณ 1s → 2s → 4s |
| **Jitter** | สุ่มเวลาเล็กน้อย | เพิ่มค่าสุ่มใน backoff ไม่ให้ทุกคน retry พร้อมกัน |
| **Circuit Breaker** | เบรกเกอร์ไฟ | ตัดการเรียกไปยังปลายทางที่พัง ชั่วคราว |
| **Rate Limiting** | จำกัดโควต้า | จำกัดจำนวน request ต่อหน่วยเวลา |
| **Event Driven** | ทำงานตามเหตุการณ์ | ระบบสื่อสารกันด้วย "เหตุการณ์ที่เกิดขึ้นแล้ว" |
| **Eventual Consistency** | เดี๋ยวก็ตรงกัน | ข้อมูลอาจไม่ตรงกันชั่วคราว แต่สุดท้ายจะตรง |
| **Backpressure** | สัญญาณ "รับไม่ไหวแล้ว" | กลไกบอกต้นทางให้ส่งช้าลง |
| **Dead Letter Queue** | ถังงานที่ทำไม่สำเร็จ | ที่เก็บ message ที่ล้มเหลวซ้ำ ๆ ไว้ตรวจทีหลัง |

## 3. Mental Model

### Model 1 — ทุกเรื่องคือการ "แลก"

เวลาเจอคำถาม advanced backend อย่าเพิ่งตอบว่าควรใช้อะไร
ให้เติมประโยคนี้ในหัวก่อนเสมอ:

> **"เทคนิคนี้ทำให้ ____ ดีขึ้น โดยแลกกับ ____ ที่แย่ลง"**

| เทคนิค | ได้อะไร | เสียอะไร |
|---|---|---|
| Cache | Latency ต่ำลง, DB โหลดลด | ข้อมูลอาจเก่า, ต้องจัดการ invalidation |
| Queue | รับโหลดพีคได้, API ตอบเร็ว | ผลลัพธ์ไม่ทันที, ต้องมีที่แจ้งสถานะ |
| Horizontal Scale | รองรับคนเยอะ | ต้อง stateless, จัดการ session ยากขึ้น |
| Microservices | ทีมแยกกันทำได้ | network failure, deploy ซับซ้อน, debug ยาก |
| Retry | ทนความล้มเหลวชั่วคราว | เสี่ยงข้อมูลซ้ำ, เสี่ยงถล่มระบบที่กำลังป่วย |
| Event Driven | ระบบหลวม ต่อขยายง่าย | ตามรอยยาก, eventual consistency |

### Model 2 — "ระยะทางคือเวลา"

เหตุผลเดียวที่ cache กับ CDN มีอยู่ คือ **ยิ่งข้อมูลอยู่ไกล ยิ่งช้า**

```
CPU Register     เร็วสุด
     ↓
RAM (in-process memory)
     ↓
Redis (คนละ process แต่ใน network เดียวกัน)
     ↓
Database (ต้องอ่าน disk + parse query)
     ↓
API ข้าง ๆ (ข้าม network)
     ↓
API ข้ามทวีป     ช้าสุด
```

> **ให้มองภาพนี้ว่า** "การ optimize backend ส่วนใหญ่ คือการพยายามย้ายข้อมูลขึ้นไปอยู่ชั้นบนของบันไดนี้ให้มากที่สุดเท่าที่ยอมให้มันเก่าได้"

### Model 3 — "Network เชื่อถือไม่ได้"

ทันทีที่ระบบคุณข้าม network ไปหาของอย่างอื่น (DB, Redis, API เพื่อน) คุณต้องยอมรับความจริง 4 ข้อ:

1. มันอาจ **ช้า** (ต้องมี Timeout)
2. มันอาจ **ล้มชั่วคราว** (ต้องมี Retry + Backoff)
3. มันอาจ **สำเร็จแล้วแต่คุณไม่รู้** (ต้องมี Idempotency)
4. มันอาจ **ล้มยาว ๆ** (ต้องมี Circuit Breaker)

นี่คือที่มาของ **Resilience 5 อย่าง** ที่จะพูดยาว ๆ ใน section ถัดไป

### Model 4 — "Stateless คือกุญแจของทุกการ scale"

จำประโยคนี้ไว้ประโยคเดียวพอ:

> **ถ้า server ของคุณจำอะไรไว้ในตัวเอง คุณจะเพิ่มเครื่องไม่ได้**

ทุกเรื่อง scaling วนกลับมาที่ประโยคนี้เสมอ

## 4. ภาพจำ

```
🧠 ภาพจำ #1 — Cache = ตู้เย็นหน้าบ้าน
อยากกินน้ำ → เปิดตู้เย็น (เร็ว)
ตู้เย็นไม่มี → ไปซื้อที่ร้าน (ช้า) → ซื้อมาแช่ตู้ไว้ด้วย

Request
   ↓
Cache (มี? → ตอบเลย)
   ↓ ไม่มี
Database
   ↓
เขียนกลับเข้า Cache
```

ปัญหาของตู้เย็นคืออะไร? **ของค้างตู้** — นั่นแหละคือ stale data และเป็นที่มาของ TTL

```
🧠 ภาพจำ #2 — Queue = ใบสั่งอาหารเสียบที่ครัว
ลูกค้าสั่ง → พนักงานเสียบใบสั่ง → ลูกค้ากลับไปนั่งได้เลย
ครัว (Worker) หยิบใบสั่งไปทำตามลำดับ

Client → API → [Queue] → Worker → Database
                  ↑
            คิวยาวได้ ไม่พัง
```

```
🧠 ภาพจำ #3 — Load Balancer = พนักงานโบกช่องเช็คเอาต์
"ช่อง 3 ว่าง เชิญครับ"
ถ้าช่องไหนปิดไฟ (health check ไม่ผ่าน) ก็ไม่โบกไปช่องนั้น

Request → LB ─┬→ Server A
              ├→ Server B
              └→ Server C (ป่วย → ข้าม)
```

```
🧠 ภาพจำ #4 — Circuit Breaker = เบรกเกอร์ไฟในบ้าน
ไฟช็อตซ้ำ ๆ → เบรกเกอร์ตัด → ไม่ให้เสียบซ้ำจนไฟไหม้ทั้งบ้าน
รอสักพัก → ลองสับขึ้นดู 1 ครั้ง → ถ้าปกติค่อยเปิดเต็ม

CLOSED (ปกติ) → เจอ error เยอะ → OPEN (ตัดทันที)
                                      ↓ รอครบเวลา
                                 HALF-OPEN (ลองแค่นิดเดียว)
```

```
🧠 ภาพจำ #5 — Idempotency = กดปุ่มลิฟต์
กด 1 ครั้งหรือ 10 ครั้ง ลิฟต์ก็มาคันเดียว
ต่างจาก "กดสั่งพิซซ่า" ที่กด 10 ครั้ง = พิซซ่า 10 ถาด

กดซ้ำ → ระบบเช็คว่า "คำสั่งนี้เคยทำแล้ว" → ตอบผลเดิมกลับ
```

```
🧠 ภาพจำ #6 — Microservices = แยกบ้านออกจากพ่อแม่
อิสระ ทำอะไรก็ได้ ✓
แต่ต้องจ่ายค่าน้ำค่าไฟ ทำกับข้าวเอง ซ่อมของเอง ✗
ถ้ายังไม่พร้อม อยู่บ้านเดิมแล้วแบ่งห้องให้ชัด (Modular Monolith) ดีกว่า
```

## 5. How It Works

### 5.1 Caching — Cache Aside Pattern

**Cache Aside** (หรือ Lazy Loading) คือ pattern ที่ใช้บ่อยที่สุด 90% ของงานจริง

```
[READ PATH]

Request
   ↓
อ่าน Cache ด้วย key
   ↓
มีข้อมูล? ──── YES ──→ ตอบกลับทันที (CACHE HIT)
   ↓ NO
อ่าน Database (CACHE MISS)
   ↓
เขียนผลลง Cache + ตั้ง TTL
   ↓
ตอบกลับ
```

> **ให้มองภาพนี้ว่า** "แอปไม่ได้เชื่อ cache ว่ามีของเสมอ มันแค่แวะถามก่อนทุกครั้ง ถ้าไม่มีค่อยไปเอาของจริงมาแล้วฝากตู้ไว้ให้คนถัดไป"

```
[WRITE PATH]

Update Database
   ↓
ลบ key ใน Cache ทิ้ง (DELETE ไม่ใช่ UPDATE)
   ↓
คนถัดไปที่อ่าน = miss → โหลดของใหม่เอง
```

**ทำไมต้อง "ลบ" ไม่ใช่ "เขียนทับ"?**
เพราะถ้ามี 2 request แก้พร้อมกัน การเขียนทับอาจสลับลำดับกันแล้ว cache ค้างค่าเก่าถาวร
การลบทิ้งแย่ที่สุดแค่ทำให้เกิด miss 1 ครั้ง ซึ่งปลอดภัยกว่ามาก

**TTL — ตาข่ายนิรภัยชั้นสุดท้าย**

TTL ไม่ใช่กลยุทธ์หลักของ invalidation แต่เป็น **ประกันว่าถ้าเราลืมลบ cache ที่ไหนสักแห่ง ข้อมูลเก่าจะไม่ค้างตลอดกาล**

| ประเภทข้อมูล | TTL ที่เหมาะสม | เหตุผล |
|---|---|---|
| รายการสินค้าหน้าแรก | 1–5 นาที | เปลี่ยนไม่บ่อย ยอมให้เก่าได้ |
| ราคาสินค้า | 10–60 วินาที | เก่าแล้วลูกค้าโวย |
| จำนวน stock คงเหลือ | ไม่ควร cache | ผิดแล้วขายเกิน |
| ข้อมูล profile ตัวเอง | ลบตอน update | ผู้ใช้ต้องเห็นผลทันที |
| Config / Feature flag | 30–300 วินาที | ยอมให้ช้าได้นิดหน่อย |

**ราคาที่ต้องจ่ายของ Cache**

| ราคา | อธิบาย |
|---|---|
| Stale data | ผู้ใช้อาจเห็นข้อมูลเก่า ต้องตกลงกับ business ว่ายอมได้กี่วินาที |
| Complexity | ต้องคิดทุกจุดที่เขียนข้อมูลว่าต้องลบ cache ตัวไหนบ้าง |
| Cache Stampede | ตอน key หมดอายุพร้อมกัน ทุก request วิ่งชน DB พร้อมกัน |
| Memory cost | Redis กิน RAM และ RAM แพงกว่า disk |

### 5.2 Redis — ไม่ได้มีไว้ cache อย่างเดียว

Redis เก็บข้อมูลไว้ใน memory เป็นหลัก เลยเร็วมาก และเป็น single-threaded สำหรับคำสั่งหลัก ทำให้แต่ละคำสั่งเป็น atomic โดยธรรมชาติ

| ใช้ Redis ทำอะไร | ทำไมเหมาะ |
|---|---|
| **Cache** | เร็ว มี TTL ในตัว |
| **Session store** | ทำให้ app stateless ได้ (session ไม่อยู่ในเครื่องใดเครื่องหนึ่ง) |
| **Rate limiter** | นับเลขแบบ atomic ได้ ไม่ต้องกลัว race |
| **Distributed lock** | กันไม่ให้ worker หลายตัวทำงานเดียวกันซ้ำ |
| **Queue เบา ๆ** | มี list / stream ให้ใช้ แต่ไม่ครบเท่า broker จริง |
| **Leaderboard / counter** | sorted set กับ atomic increment เร็วมาก |

**สิ่งที่ต้องรู้ก่อนใช้ Redis ใน production**

- ข้อมูลอยู่ใน memory → **Redis ล่ม = ข้อมูลใน cache หายหมด** ระบบต้องยังทำงานได้ (แค่ช้าลง)
- ถ้าจะเก็บของที่หายไม่ได้ (เช่น order) **อย่าเก็บใน Redis อย่างเดียว**
- ต้องตั้ง memory policy ว่าเมื่อเต็มจะลบอะไรก่อน (เช่น ลบตัวที่ไม่ได้ใช้นานสุด)

### 5.3 Queue, Message Broker, Worker

**ปัญหาที่ Queue แก้:** งานบางอย่างช้าและผู้ใช้ไม่จำเป็นต้องรอ

```
[แบบไม่มี Queue — Synchronous]

User กด "สั่งซื้อ"
   ↓
บันทึก order            (50ms)
   ↓
ส่ง email ยืนยัน         (2,000ms)   ← ผู้ใช้ยืนหมุนอยู่ตรงนี้
   ↓
gen PDF ใบเสร็จ         (3,000ms)
   ↓
ยิง API ระบบบัญชี        (1,500ms)
   ↓
ตอบกลับ                  รวม 6.5 วินาที 😱
```

```
[แบบมี Queue — Asynchronous]

User กด "สั่งซื้อ"
   ↓
บันทึก order            (50ms)
   ↓
โยน 3 งานเข้า Queue      (5ms)
   ↓
ตอบกลับ "รับคำสั่งแล้ว"    รวม ~60ms ✓

            [QUEUE]
               ↓
   ┌───────────┼───────────┐
[Worker 1]  [Worker 2]  [Worker 3]
  email        PDF        บัญชี
```

> **ให้มองภาพนี้ว่า** "Queue คือการเปลี่ยนจาก 'ลูกค้ายืนรอจนครัวทำเสร็จ' เป็น 'รับใบสั่งแล้วให้กลับไปนั่งก่อน' — งานไม่ได้หายไปไหน แค่ย้ายออกจากเส้นทางที่ผู้ใช้ต้องรอ"

**เมื่อไรควรใช้ Queue**

| ควรใช้ | ไม่ควรใช้ |
|---|---|
| ส่ง email / SMS / push notification | ผู้ใช้ต้องเห็นผลลัพธ์ทันทีบนหน้าจอ |
| สร้างรายงาน / PDF / export ไฟล์ใหญ่ | งานที่เร็วอยู่แล้ว (< 100ms) |
| ประมวลผลรูป / วิดีโอ | งานที่ผลลัพธ์ต้องใช้ตัดสินใจใน request ถัดไปทันที |
| ซิงค์ข้อมูลไประบบอื่น | ระบบยังไม่มีทางแจ้งสถานะให้ผู้ใช้รู้ |
| งานที่มีโหลดพีคเป็นช่วง (flash sale) | ทีมยังไม่มีคน monitor queue |

**ราคาที่ต้องจ่ายของ Queue**

1. **ผู้ใช้ไม่รู้ว่าเสร็จหรือยัง** → ต้องมีหน้า status / WebSocket / email แจ้ง
2. **งานอาจล้มเหลวเงียบ ๆ** → ต้องมี retry + Dead Letter Queue + alert
3. **งานอาจถูกทำซ้ำ** → broker ส่วนใหญ่รับประกันแค่ "ส่งอย่างน้อย 1 ครั้ง" ไม่ใช่ "พอดี 1 ครั้ง" → **worker ต้อง idempotent**
4. **ต้องดูแล infra เพิ่ม** → broker ล่มคืออีกจุดที่พังได้

### 5.4 RabbitMQ vs Kafka — ต่างกันที่ "วิธีคิด" ไม่ใช่แค่ performance

```
[RabbitMQ — Message Queue: ส่งงานให้คนทำ]

Producer → [Queue] → Consumer A หยิบ msg#1 → ทำเสร็จ → msg#1 หายไป
                   → Consumer B หยิบ msg#2
                   → Consumer C หยิบ msg#3

หลักคิด: "งาน 1 ชิ้น มีคนทำ 1 คน ทำเสร็จแล้วทิ้ง"
```

```
[Kafka — Event Log: บันทึกเหตุการณ์ให้ทุกคนมาอ่าน]

Producer → [Topic: order-created]
            [0][1][2][3][4][5]...      ← เก็บไว้ตามลำดับ ไม่ลบทันที
                 ↑         ↑
         Billing อ่านถึง 2   Analytics อ่านถึง 5

หลักคิด: "เหตุการณ์ถูกบันทึกไว้ ใครสนใจก็มาอ่าน อ่านย้อนได้"
```

> **ให้มองภาพนี้ว่า** "RabbitMQ เหมือนใบสั่งงานที่ทำเสร็จแล้วฉีกทิ้ง ส่วน Kafka เหมือนสมุดบันทึกประวัติศาสตร์ที่ใครจะเปิดอ่านย้อนหลังกี่รอบก็ได้"

| ประเด็น | RabbitMQ (Task Queue) | Kafka (Event Log) |
|---|---|---|
| หน่วยข้อมูล | Task / คำสั่งให้ทำ | Event / สิ่งที่เกิดขึ้นแล้ว |
| หลังอ่าน | message หายจาก queue | event ยังอยู่ตาม retention |
| ผู้รับหลายคน | ต้อง config exchange/fanout | เป็นธรรมชาติของมัน ใครมาอ่านก็ได้ |
| อ่านย้อนหลัง | ทำไม่ได้ | ทำได้ (rewind offset) |
| Ordering | จัดการยากเมื่อมีหลาย consumer | รับประกันลำดับภายใน partition |
| Throughput | สูง | สูงมาก (ออกแบบมาเพื่อ stream) |
| เหมาะกับ | ส่ง email, gen PDF, งานเบื้องหลัง | event streaming, audit log, data pipeline |
| ความซับซ้อนในการดูแล | ปานกลาง | สูง (ต้องเข้าใจ partition, consumer group) |

**ประโยคที่พูดได้ในห้องสัมภาษณ์**

> "ถ้าโจทย์คือ 'มีงานต้องทำ อยากให้มีคนหยิบไปทำ' ผมมอง RabbitMQ ก่อน
> ถ้าโจทย์คือ 'มีเหตุการณ์เกิดขึ้น หลายระบบอยากรู้ และอาจอยากอ่านย้อนหลัง' ผมมอง Kafka
> แต่ถ้าระบบยังเล็ก ผมจะเริ่มจาก queue ที่ทีมดูแลไหวก่อน เพราะ Kafka มีต้นทุนการดูแลสูง"

### 5.5 Realtime — Polling vs Long Polling vs WebSocket

```
[POLLING]
Client: มีของใหม่ยัง? → Server: ยัง
   (รอ 5 วิ)
Client: มีของใหม่ยัง? → Server: ยัง
   (รอ 5 วิ)
Client: มีของใหม่ยัง? → Server: มี! นี่ไง
```

```
[LONG POLLING]
Client: มีของใหม่ยัง? → Server: (ค้างสายไว้ 30 วิ...)
                                 มี! นี่ไง → ตอบ
Client: ถามใหม่ทันที  → Server: (ค้างสายอีก...)
```

```
[WEBSOCKET]
Client ⇄ Server  (เปิดสายค้างไว้ สองทาง)
              ← Server ส่งมาเองได้ทุกเมื่อ
              → Client ส่งไปได้ทุกเมื่อ
```

> **ให้มองภาพนี้ว่า** "Polling คือโทรถามทุก 5 นาทีว่าของถึงยัง, Long Polling คือโทรแล้วไม่วางจนกว่าจะมีคำตอบ, WebSocket คือเปิดสายคุยค้างไว้เลยแล้วอีกฝ่ายพูดขึ้นมาเมื่อไรก็ได้"

| | Polling | Long Polling | WebSocket |
|---|---|---|---|
| ความซับซ้อน | ต่ำสุด | กลาง | สูงสุด |
| Latency | เท่ากับช่วงเวลาถาม | ต่ำ | ต่ำสุด (ทันที) |
| โหลด server | สูง (ถามทิ้งเยอะ) | กลาง (ถือ connection ค้าง) | ต่ำต่อข้อความ แต่ถือ connection เยอะ |
| ผ่าน proxy/firewall | ง่ายสุด | ง่าย | บางที่บล็อก ต้อง config เพิ่ม |
| Scale ยากไหม | ง่าย (stateless) | กลาง | ยาก (connection มี state) |
| เหมาะกับ | สถานะที่อัปเดตช้า เช่น "job เสร็จยัง" | แจ้งเตือน ที่อยากได้เร็วแต่ไม่อยากทำ WS | chat, collaborative editing, ราคาหุ้น, เกม |

**ราคาที่ต้องจ่ายของ WebSocket**

- Connection มี **state** → พอ scale ออกหลายเครื่อง ผู้ใช้ A กับ B อาจอยู่คนละเครื่อง ต้องมี **Pub/Sub (เช่น Redis)** เป็นตัวกลางส่งข้อความข้ามเครื่อง
- ต้องจัดการ reconnect เอง (เน็ตหลุด, มือถือสลับ WiFi/4G)
- Load balancer ต้องรองรับ และมักต้องใช้ sticky session
- ถ้าโจทย์แค่ "รู้ว่างานเสร็จยัง" → **polling ง่ายกว่ามากและมักจะพอ**

### 5.6 Load Balancer, Reverse Proxy, API Gateway, CDN

ทั้ง 4 ตัวนี้อยู่ "หน้าบ้าน" เหมือนกัน คนจึงสับสนบ่อยที่สุด

```
[USER]
   ↓
[CDN]              ← เสิร์ฟ static ใกล้ผู้ใช้ (รูป, JS, CSS)
   ↓ (ถ้าเป็น API)
[API GATEWAY]      ← ตรวจ token, rate limit, routing ตาม path
   ↓
[LOAD BALANCER]    ← เลือกว่าจะส่งไปเครื่องไหนที่ยังสุขภาพดี
   ↓  ↓  ↓
[APP][APP][APP]
```

> **ให้มองภาพนี้ว่า** "CDN คือสาขาใกล้บ้านที่มีของพร้อมหยิบ, API Gateway คือ รปภ. หน้าตึกที่ตรวจบัตรและกำหนดโควต้า, Load Balancer คือพนักงานข้างในที่โบกให้ไปเคาน์เตอร์ที่ว่าง"

| | ทำอะไร | คำถามที่มันตอบ |
|---|---|---|
| **Reverse Proxy** | รับ request แทน server จริง แล้วส่งต่อข้างใน | "ใครควรเป็นหน้าด่าน แทนที่จะให้ client ยิงถึง app ตรง ๆ" |
| **Load Balancer** | กระจาย request ไปหลาย instance + health check | "ส่งไปเครื่องไหนดี" |
| **API Gateway** | auth, rate limit, routing, logging, transform | "คนนี้มีสิทธิ์ไหม ใช้เกินโควต้าหรือยัง ควรไป service ไหน" |
| **CDN** | cache ไฟล์ static ไว้หลาย ๆ จุดทั่วโลก | "ทำยังไงให้ไฟล์อยู่ใกล้ผู้ใช้ที่สุด" |

หมายเหตุสำคัญ: **Load Balancer เป็น Reverse Proxy ชนิดหนึ่ง** และ Nginx ตัวเดียวก็ทำได้ทั้ง reverse proxy และ load balancer พร้อมกัน — อย่าท่องว่ามันคือคนละสิ่งเสมอ

**CDN ทำอะไรได้บ้าง**

- Cache static asset (รูป, JS, CSS, font, video) ไว้ที่ edge ใกล้ผู้ใช้
- ลด latency เพราะระยะทางสั้นลง
- ลดโหลด origin server อย่างมหาศาล
- ราคาที่ต้องจ่าย: **ต้องจัดการ cache invalidation** → วิธีมาตรฐานคือ **ใส่ hash ในชื่อไฟล์** (`app.9f3a2c.js`) แล้วไฟล์ใหม่ = ชื่อใหม่ = ไม่ต้อง purge

### 5.7 Scaling & State

```
[VERTICAL SCALING]                [HORIZONTAL SCALING]

  ┌─────┐                          ┌──┐ ┌──┐ ┌──┐ ┌──┐
  │     │  →  ┌───────┐            │  │ │  │ │  │ │  │
  │ 2CPU│     │ 32CPU │            └──┘ └──┘ └──┘ └──┘
  └─────┘     │       │            เพิ่มจำนวนเครื่อง
              └───────┘
   เพิ่มพลังเครื่องเดิม
```

> **ให้มองภาพนี้ว่า** "Vertical คือจ้างพนักงานเก่งขึ้นคนเดิม 1 คน ส่วน Horizontal คือจ้างพนักงานธรรมดาเพิ่มอีก 10 คน — คนเก่งคนเดียวลาป่วยแล้วร้านปิด"

| | Vertical Scaling | Horizontal Scaling |
|---|---|---|
| วิธี | เพิ่ม CPU / RAM / SSD ให้เครื่องเดิม | เพิ่มจำนวนเครื่อง |
| แก้ code ไหม | ไม่ต้อง | ต้อง (ต้อง stateless) |
| เพดาน | มี — ใหญ่สุดของ cloud ก็มีลิมิต | แทบไม่มี |
| Single point of failure | มี (เครื่องเดียวล่ม = จบ) | ไม่มี (ตายตัวหนึ่ง ตัวอื่นรับต่อ) |
| ค่าใช้จ่าย | เพิ่มแบบไม่เป็นเชิงเส้น (แพงขึ้นเร็ว) | เพิ่มแบบเป็นเชิงเส้นกว่า |
| ต้อง downtime ไหม | มักต้อง restart | ไม่ต้อง (rolling) |
| เหมาะกับ | Database, ระบบเล็ก, แก้ปัญหาเฉพาะหน้า | App server, ระบบที่ traffic โตไม่หยุด |

**Stateless vs Stateful — หัวใจของ Horizontal Scaling**

```
[STATEFUL — scale ไม่ได้]

User A login → Server 1 (เก็บ session ไว้ใน RAM ตัวเอง)
User A ยิงครั้งต่อไป → LB ส่งไป Server 2 → "คุณเป็นใคร?" → 401 ❌
```

```
[STATELESS — scale ได้]

User A login → Server 1 → เก็บ session ไว้ที่ [REDIS] / ใช้ JWT
User A ยิงครั้งต่อไป → Server 2 → อ่าน Redis / verify JWT → ผ่าน ✓

   [APP 1] ─┐
   [APP 2] ─┼→ [REDIS: session]
   [APP 3] ─┘
```

> **ให้มองภาพนี้ว่า** "Stateless คือการย้ายความทรงจำออกจากตัวพนักงาน ไปไว้ในแฟ้มกลางที่ทุกคนเปิดได้ — พนักงานคนไหนรับเรื่องก็ทำงานต่อได้เหมือนกัน"

สิ่งที่ห้ามเก็บไว้ในตัว app ถ้าจะ scale:
- Session ใน memory → ย้ายไป Redis หรือใช้ JWT
- ไฟล์ที่ผู้ใช้อัปโหลดลง local disk → ย้ายไป object storage (S3)
- Cache ใน process ที่ต้อง consistent → ย้ายไป Redis
- Cron/scheduler ที่รันในทุก instance → ต้องมี distributed lock ไม่งั้นทำงานซ้ำ N ครั้ง

**Sticky Session — ทางออกที่ต้องรู้ว่าเป็นยาแก้ปวด ไม่ใช่ยารักษา**
LB ผูกผู้ใช้ไว้กับเครื่องเดิม ทำให้ stateful app พอ scale ได้
ราคาที่จ่าย: โหลดกระจายไม่เท่ากัน, เครื่องล่ม = ผู้ใช้กลุ่มนั้นหลุดหมด, deploy ยาก

### 5.8 Monolith → Modular Monolith → Microservices

```
[MONOLITH]                        [MICROSERVICES]

┌──────────────────┐              ┌──────┐ ┌──────┐ ┌──────┐
│ Auth  Order      │              │ Auth │ │Order │ │ Pay  │
│ Payment  Report  │              └──┬───┘ └──┬───┘ └──┬───┘
│                  │                 │        │        │
│   [ONE DB]       │              [DB A]   [DB B]   [DB C]
└──────────────────┘
 deploy ครั้งเดียว                  deploy แยก / ทีมแยก / พังแยก
```

> **ให้มองภาพนี้ว่า** "Monolith คือบ้านหลังใหญ่ที่ทุกคนอยู่ด้วยกัน ส่วน Microservices คือหมู่บ้านที่ทุกคนมีบ้านของตัวเอง — สะดวกขึ้นก็จริง แต่เดินไปคุยกันต้องออกนอกบ้านทุกครั้ง"

**ความจริงที่ต้องพูดตรง ๆ: Microservices ไม่ใช่คำตอบเริ่มต้น**

> **Microservices ไม่ได้แก้ปัญหา technical เป็นหลัก มันแก้ปัญหา "องค์กร" — คือปัญหาที่ทีมหลายทีมเหยียบเท้ากันใน codebase เดียว**

ถ้าคุณมีทีม 5–15 คน และยังไม่ได้เจอปัญหาที่ deploy ของทีมหนึ่งบล็อกอีกทีม **คุณยังไม่ต้องการ microservices**

**ต้นทุนจริงของ Microservices (สิ่งที่คนไม่ค่อยบอก)**

| ต้นทุน | เกิดอะไรขึ้นจริง |
|---|---|
| **Network เข้ามาแทนที่ function call** | เดิมเรียก function พังไม่ได้ ตอนนี้เรียกข้าม network → ช้าได้ ล่มได้ timeout ได้ |
| **Transaction ข้าม service ไม่มี** | เดิม `BEGIN...COMMIT` จบ ตอนนี้ต้องทำ Saga + compensation เอง |
| **Debug ยากขึ้นหลายเท่า** | 1 request วิ่งผ่าน 6 service → ต้องมี distributed tracing ถึงจะตามรอยได้ |
| **ต้องมี infra ทีม / DevOps** | CI/CD หลาย pipeline, service discovery, monitoring, log รวม |
| **Data consistency** | ข้อมูลซ้ำระหว่าง service → ต้องยอมรับ eventual consistency |
| **Local development ยาก** | จะรันทั้งระบบบนเครื่องตัวเองยังไง |
| **Versioning ของ API ระหว่าง service** | เปลี่ยน contract ทีเดียว พังหลายที่ |

**เส้นทางที่ Senior ส่วนใหญ่แนะนำ**

```
เริ่มที่ Monolith
      ↓  (โค้ดเริ่มพันกัน)
Modular Monolith          ← แบ่ง module ขอบเขตชัด ห้ามเรียกข้ามกันมั่ว
      ↓  (module ไหนโตจน scale/deploy แยกจำเป็นจริง ๆ)
แยกเฉพาะ module นั้นออกเป็น service
      ↓
Microservices (เท่าที่จำเป็น)
```

> **ให้มองภาพนี้ว่า** "อย่ารีบย้ายออกจากบ้าน ให้แบ่งห้องให้ชัดก่อน แล้วค่อยย้ายเฉพาะคนที่จำเป็นต้องย้ายจริง ๆ"

**Modular Monolith — ทางเลือกที่ถูกประเมินต่ำ**

- ยัง deploy ครั้งเดียว ยังใช้ transaction เดียวได้ ยัง debug ง่าย
- แต่แบ่ง module ชัด: `order/`, `payment/`, `user/` แต่ละ module มี public interface ของตัวเอง
- **ห้ามเรียกข้าม module ไปแตะ table ของกันและกันตรง ๆ**
- ผลลัพธ์: ถ้าวันหนึ่งต้องแยกจริง คุณแค่ตัดตรงรอยที่แบ่งไว้แล้ว ซึ่งง่ายกว่าแยกจากโค้ดพันกันมาก

**เมื่อไรถึงค่อยพิจารณา Microservices จริง ๆ**

- [ ] มีหลายทีม และ deploy ของทีมหนึ่งบล็อกอีกทีมเป็นประจำ
- [ ] มีบาง module ที่โหลดต่างจากส่วนอื่นมาก จน scale แยกคุ้มกว่า
- [ ] ทีมมีคน/เครื่องมือดูแล CI/CD, monitoring, tracing ได้จริง
- [ ] ขอบเขต domain ชัดพอที่จะบอกได้ว่าเส้นแบ่งอยู่ตรงไหน

ถ้าติ๊กไม่ครบ → คำตอบคือ Modular Monolith

## 6. Example — สถานการณ์จากงานจริง

### Example 1: หน้าแรกช้า 3 วินาที ทุก request

**อาการ:** หน้า homepage ดึงรายการสินค้าแนะนำ 20 ชิ้น query ซับซ้อน join 4 ตาราง ใช้เวลา 2.8 วินาที และเพจนี้มีคนเข้า 80% ของ traffic

**การคิดแบบ Senior:**

1. ข้อมูลนี้เปลี่ยนบ่อยแค่ไหน? → ทีม marketing อัปเดตวันละ 2–3 ครั้ง
2. ยอมให้เก่าได้กี่นาที? → คุยกับ PM ได้ข้อสรุป "5 นาทีรับได้"
3. → **ใส่ Cache Aside + TTL 5 นาที**

**ผลลัพธ์:** 2.8s → ~15ms สำหรับ cache hit และโหลด DB ลดฮวบ

**แต่ยังไม่จบ — ปัญหาที่ตามมา:**
- ตอน TTL หมดพร้อมกัน 500 request วิ่งชน DB พร้อมกัน (**Cache Stampede**)
- แก้ด้วย: ให้ request แรกที่ miss ถือ lock ไว้ ที่เหลือรอผลหรือใช้ค่าเก่าไปก่อน

### Example 2: Flash Sale ทำระบบล่ม

**อาการ:** ตอนเปิดขาย 20:00 น. มี request พุ่งจาก 50/วินาที เป็น 8,000/วินาที ระบบล่ม 4 นาที

**สิ่งที่ต้องมีทั้งชุด ไม่ใช่ตัวเดียว:**

```
[USER]
   ↓
[CDN]                  → หน้า landing เป็น static ไม่แตะ backend เลย
   ↓
[RATE LIMITING]        → 1 user ยิงได้ไม่เกิน N ครั้ง/วินาที
   ↓
[LOAD BALANCER]
   ↓
[APP x 20]             → scale out ล่วงหน้าก่อนเวลา
   ↓
[REDIS]                → เช็ค stock ที่ Redis (atomic) ไม่ใช่ DB
   ↓
[QUEUE]                → order ที่ผ่านแล้วเข้า queue
   ↓
[WORKER]               → ค่อย ๆ เขียนลง DB ตามอัตราที่ DB รับไหว
```

> **ให้มองภาพนี้ว่า** "Flash sale คือน้ำหลาก คุณไม่ได้ขยายท่อให้ใหญ่พอรับน้ำทั้งหมด แต่สร้างอ่างเก็บน้ำ (queue) ไว้ปล่อยลงท่อทีละนิด"

### Example 3: ลูกค้าถูกตัดเงิน 2 ครั้ง

**อาการ:** ลูกค้า 1 คนถูกเรียกเก็บเงิน 2 รอบ วันละ ~3 เคส

**สาเหตุจริง:**

```
App → Payment Gateway  (ตัดเงินสำเร็จ ✓)
           ↓
    แต่ response หายระหว่างทาง / timeout
           ↓
App คิดว่าพัง → Retry
           ↓
Payment Gateway ตัดเงินอีกครั้ง ❌
```

**บทเรียน:** **Retry โดยไม่มี Idempotency = เครื่องผลิตข้อมูลซ้ำ**

**วิธีแก้:**
1. Client สร้าง `Idempotency-Key` (UUID) ต่อ 1 ความตั้งใจจ่ายเงิน
2. ส่ง key เดิมทุกครั้งที่ retry
3. ฝั่งรับเช็คก่อนว่า key นี้เคยประมวลผลแล้วหรือยัง
4. ถ้าเคย → **คืนผลลัพธ์เดิม** ไม่ทำงานใหม่

```
Request + Idempotency-Key: abc-123
   ↓
เคยเห็น key นี้ไหม?
   ├─ เคย → ตอบผลลัพธ์เดิมที่เก็บไว้ (ไม่ตัดเงินซ้ำ)
   └─ ไม่เคย → ทำงานจริง → บันทึกผลคู่กับ key → ตอบกลับ
```

### Example 4: Service เพื่อนล่ม แล้วลากระบบเราตายด้วย

**อาการ:** Recommendation Service ล่ม → หน้า product page ทั้งหมดค้าง 30 วินาทีแล้ว timeout → ทั้งเว็บใช้ไม่ได้ ทั้งที่ recommendation เป็นแค่กล่องเล็ก ๆ มุมขวา

**สาเหตุ:** ไม่มี timeout สั้น ๆ ไม่มี circuit breaker → thread ของ app ทุกตัวไปติดรอ service ที่ตายอยู่ (**Cascading Failure**)

**วิธีแก้:**

```
เรียก Recommendation Service
   ↓
Timeout 500ms                  ← ไม่รอเกินนี้เด็ดขาด
   ↓ ล้มเหลวติดกันเกิน threshold
Circuit Breaker → OPEN         ← หยุดเรียกไปเลย 30 วินาที
   ↓
Fallback: แสดง "สินค้ายอดนิยม" จาก cache แทน
   ↓
หน้าเว็บยังใช้งานได้ปกติ ✓
```

> **ให้มองภาพนี้ว่า** "ฟีเจอร์เสริมไม่ควรมีอำนาจฆ่าฟีเจอร์หลัก — งานของ circuit breaker คือการตัดแขนขาที่ติดเชื้อ เพื่อรักษาชีวิตทั้งร่าง"

### Example 5: ระบบแจ้งเตือน — ควรใช้ WebSocket ไหม?

**โจทย์:** ผู้ใช้กด "สร้างรายงาน" ใช้เวลา 30–90 วินาที อยากให้รู้ตอนเสร็จ

**คำตอบที่ Junior มักตอบ:** "ใช้ WebSocket ครับ realtime ดีกว่า"

**คำตอบที่ดีกว่า:**

> "ผมจะเริ่มจาก polling ทุก 3 วินาทีที่ endpoint `/jobs/:id/status` ก่อนครับ
> เพราะงานนี้ผู้ใช้รออยู่บนหน้าจออยู่แล้ว ไม่ได้ต้องการความเร็วระดับมิลลิวินาที
> และ polling ทำงานบน stateless server ได้เลย ไม่ต้องแก้ infra
> ถ้าวันหนึ่งเราต้องส่งแจ้งเตือนหลายแบบพร้อมกัน หรือต้อง push ตอนผู้ใช้ไม่ได้เปิดหน้านั้น
> ผมค่อยพิจารณา WebSocket พร้อม Redis Pub/Sub เพื่อให้ push ข้ามเครื่องได้ครับ"

นี่คือคำตอบระดับ Senior — **เริ่มจากของที่ง่ายที่สุดที่แก้ปัญหาได้ แล้วบอกเงื่อนไขที่จะยกระดับ**

## 7. Compare — ตารางเปรียบเทียบสิ่งที่มักสับสน

### 7.1 Cache Aside vs Write Through vs Write Behind

| | Cache Aside | Write Through | Write Behind |
|---|---|---|---|
| ตอนเขียน | เขียน DB แล้วลบ cache | เขียน cache + DB พร้อมกัน | เขียน cache ก่อน ค่อยลง DB ทีหลัง |
| Consistency | ดี (ยอม miss 1 ครั้ง) | ดีมาก | เสี่ยงข้อมูลหายถ้า cache ล่ม |
| Write latency | ต่ำ | สูงขึ้น | ต่ำสุด |
| ความซับซ้อน | ต่ำ | กลาง | สูง |
| ใช้เมื่อ | 90% ของงานทั่วไป | อ่านทันทีหลังเขียนบ่อย | write เยอะมากและยอมเสี่ยงได้ |

### 7.2 Queue vs Event Stream vs Pub/Sub

| | Queue (RabbitMQ) | Event Stream (Kafka) | Pub/Sub (Redis) |
|---|---|---|---|
| หลักคิด | งานที่ต้องมีคนทำ | เหตุการณ์ที่บันทึกไว้ | ประกาศให้คนที่ฟังอยู่ |
| ถ้าไม่มีใครฟังตอนนั้น | รออยู่ในคิว | ยังอยู่ อ่านทีหลังได้ | **หายเลย** |
| อ่านย้อนหลัง | ไม่ได้ | ได้ | ไม่ได้ |
| เหมาะกับ | background job | data pipeline / event sourcing | broadcast ภายใน เช่น ส่ง WS ข้ามเครื่อง |

### 7.3 Load Balancer vs API Gateway

| | Load Balancer | API Gateway |
|---|---|---|
| ระดับการทำงาน | Network / HTTP | Application / Business |
| รู้จัก business ไหม | ไม่รู้ แค่กระจาย | รู้ — รู้จัก route, user, plan |
| ทำ auth ไหม | ปกติไม่ | ใช่ |
| ทำ rate limit ไหม | ทำได้เบื้องต้น | ใช่ ละเอียดกว่า (ต่อ user / ต่อ API key) |
| จำเป็นตอนไหน | ทันทีที่มีมากกว่า 1 instance | ตอนมีหลาย service / หลาย client |

### 7.4 Monolith vs Modular Monolith vs Microservices

| | Monolith | Modular Monolith | Microservices |
|---|---|---|---|
| จำนวน deploy | 1 | 1 | N |
| ขอบเขต module | คลุมเครือ | ชัดเจน (บังคับด้วย convention/lint) | ชัดเจน (บังคับด้วย network) |
| Transaction | ง่าย | ง่าย | ยาก (ต้อง Saga) |
| Debug | ง่ายสุด | ง่าย | ยากสุด (ต้อง tracing) |
| Scale แยกส่วน | ไม่ได้ | ไม่ได้ | ได้ |
| ทีมที่เหมาะ | 1–8 คน | 5–30 คน | หลายทีม แต่ละทีมเป็นเจ้าของ service |
| ต้นทุน infra | ต่ำ | ต่ำ | สูง |

### 7.5 Strong vs Eventual Consistency

| | Strong Consistency | Eventual Consistency |
|---|---|---|
| ความหมาย | อ่านแล้วได้ค่าล่าสุดเสมอ | อาจได้ค่าเก่า แต่สุดท้ายจะตรงกัน |
| ราคา | ช้ากว่า, scale ยากกว่า | เร็วกว่า, scale ง่ายกว่า |
| ต้องใช้กับ | ยอดเงิน, stock ที่ขายเกินไม่ได้, สิทธิ์เข้าถึง | ยอด view, จำนวน like, feed, search index |
| ผู้ใช้เห็นอะไร | ถูกต้องเสมอ | "เดี๋ยวก็มา" เช่น like ขึ้นช้า 2 วิ |

## 8. Common Mistakes

| # | สิ่งที่ Junior มักเข้าใจผิด | ความจริง |
|---|---|---|
| 1 | "ใส่ Redis แล้วระบบเร็วขึ้นเสมอ" | ถ้า query เร็วอยู่แล้ว การข้าม network ไป Redis อาจช้ากว่า และคุณเพิ่งซื้อปัญหา stale data มาฟรี ๆ |
| 2 | "Cache ไว้นาน ๆ ดีกว่า" | TTL ยาว = ผู้ใช้เห็นข้อมูลผิดนานขึ้น TTL ต้องมาจากคำถาม business ว่า "ยอมให้เก่าได้กี่วินาที" |
| 3 | "Update cache ตอนแก้ข้อมูล" | ควร **ลบ** ไม่ใช่เขียนทับ เพราะ race condition ทำให้ค่าเก่าค้างถาวรได้ |
| 4 | "ใส่ retry ไว้ก่อน ปลอดภัยดี" | retry ที่ไม่มี idempotency = สร้างข้อมูลซ้ำ และ retry ที่ไม่มี backoff = ถล่มระบบที่กำลังป่วยให้ตายเร็วขึ้น |
| 5 | "Timeout ตั้งเยอะ ๆ ไว้ก่อน จะได้ไม่พลาด" | timeout ยาว = thread ค้างเยอะ = ระบบคุณตายตาม service ที่พัง (cascading failure) |
| 6 | "Microservices ทันสมัยกว่า" | Microservices แก้ปัญหาองค์กร ไม่ใช่ปัญหา performance และมีต้นทุนสูงมาก ทีมเล็กใช้แล้วช้าลงแทบทุกครั้ง |
| 7 | "แยกเป็น microservices แล้วแชร์ database เดียวกัน" | นี่คือ **distributed monolith** — ได้ข้อเสียครบทุกข้อ แต่ไม่ได้ข้อดีสักข้อ |
| 8 | "Realtime ต้องใช้ WebSocket เท่านั้น" | polling ทุก 3 วิ พอสำหรับงานส่วนใหญ่ WebSocket มีต้นทุน scale ที่ต้องจ่ายจริง |
| 9 | "เก็บ session ใน memory ก็ได้ ตอนนี้มีเครื่องเดียว" | วันที่เพิ่มเครื่องที่สอง ผู้ใช้จะหลุด login แบบสุ่ม และเป็น bug ที่หาสาเหตุยากมาก |
| 10 | "Load Balancer แปลว่ามี high availability แล้ว" | ถ้า LB ไม่ทำ health check หรือ app ไม่ stateless หรือ DB ยังมีตัวเดียว → ยังล่มได้อยู่ |
| 11 | "Queue รับประกันว่างานจะทำครั้งเดียว" | ส่วนใหญ่รับประกันแค่ at-least-once → **worker ต้อง idempotent เสมอ** |
| 12 | "Eventual consistency คือ bug" | มันคือ **การตัดสินใจ** ที่แลกความถูกต้องทันที กับความเร็วและ scale — ต้องเลือกให้ตรงกับ business |
| 13 | "Rate limit เอาไว้กัน hacker" | หน้าที่หลักคือกันระบบตัวเองล่มจากการใช้งานผิดปกติ (รวมถึง bug ในฝั่ง client ของเราเอง) |
| 14 | "Event Driven = ระบบดีกว่า" | มันทำให้ระบบหลวมและต่อขยายง่าย แต่แลกกับการที่ "ไม่มีใครรู้ทั้งภาพ" และตามรอย bug ยากมาก |
| 15 | "Scale ไม่พอก็เพิ่มเครื่อง" | ถ้า bottleneck อยู่ที่ DB การเพิ่ม app server คือการเพิ่มจำนวนคนที่มายืนรอหน้าประตูเดิม |

## 9. Debugging — ไล่ตามลำดับ

### 9.1 "ระบบช้า" — ไล่แบบนี้

```
1. ช้าที่ไหน?  → ดู APM / trace แยกเวลาเป็นช่วง
       ↓
2. ช้าทุกคน หรือบางคน?  → ถ้าบางคน = ข้อมูลบางชุดใหญ่ผิดปกติ
       ↓
3. ช้าที่ Network / App / DB / External API?
       ↓
   ├── DB ช้า      → EXPLAIN query, ดู index, ดู N+1
   ├── External ช้า → มี timeout ไหม? มี circuit breaker ไหม?
   ├── App ช้า      → CPU เต็ม? event loop block? GC?
   └── ช้าตอน peak → scale ไม่พอ / connection pool หมด
```

**เช็คลิสต์เร็ว ๆ**
- [ ] Cache hit ratio เท่าไร? ถ้าต่ำกว่า 70% แปลว่า key strategy ผิดหรือ TTL สั้นเกิน
- [ ] Connection pool ของ DB เต็มหรือเปล่า (อาการ: ช้าพร้อมกันหมดทุก endpoint)
- [ ] มี query ที่ไม่มี index โผล่มาตอน data โตหรือเปล่า

### 9.2 "Cache มีปัญหา"

```
ผู้ใช้เห็นข้อมูลเก่า
   ↓
1. ตอน update ข้อมูล มีการลบ cache ไหม?
   ↓
2. ลบ key ถูกตัวไหม? (key pattern ตรงกันจริงหรือเปล่า)
   ↓
3. มี cache ซ้อนกันหลายชั้นไหม? (browser → CDN → app → Redis)
   ↓  ชั้นไหนที่ยังค้าง?
4. TTL ยาวเกินไปหรือเปล่า
   ↓
5. มีหลาย instance ที่ cache ใน memory ตัวเองอยู่ด้วยไหม
```

> **ให้มองภาพนี้ว่า** "ข้อมูลเก่าที่หลุดออกมา มักไม่ได้มาจาก cache ชั้นที่คุณกำลังเพ่งมองอยู่ ให้ไล่ทุกชั้นตั้งแต่ browser ลงมา"

### 9.3 "งานใน Queue ไม่ถูกทำ / ทำซ้ำ"

```
1. Worker ยังรันอยู่ไหม? (process ตาย เงียบ ๆ เป็นเรื่องปกติมาก)
   ↓
2. Queue มี message ค้างกี่ตัว? (queue depth เพิ่มขึ้นเรื่อย ๆ = consume ไม่ทัน)
   ↓
3. มี message ใน Dead Letter Queue ไหม? → อ่าน error ที่นั่น
   ↓
4. Worker ทำงานนานเกิน visibility timeout ไหม?
   → ถ้าเกิน broker จะคิดว่าตาย แล้วส่งให้ตัวอื่นทำซ้ำ (นี่คือสาเหตุ "ทำซ้ำ" อันดับ 1)
   ↓
5. Worker idempotent หรือยัง? ถ้ายัง → ทำซ้ำ = ข้อมูลเสีย
```

### 9.4 "Error 5xx เป็นช่วง ๆ"

```
1. เกิดเฉพาะบาง instance ไหม? → เครื่องนั้นป่วย / memory leak
   ↓
2. เกิดตอน deploy ไหม? → health check ไม่ตรง / connection ยังไม่พร้อม
   ↓
3. เกิดตามรอบเวลาไหม? → cron / batch job แย่ง resource
   ↓
4. Dependency ตัวไหน error ก่อน? → ดู trace ย้อนต้นทาง
   ↓
5. มี circuit breaker ที่ OPEN อยู่ไหม? → ถ้ามี ปัญหาอยู่ปลายทาง ไม่ใช่เรา
```

### 9.5 "WebSocket หลุดบ่อย / ข้อความไม่ถึงบางคน"

```
1. หลุดบ่อย → idle timeout ที่ LB / proxy ตัดหรือเปล่า (ต้องมี heartbeat/ping)
   ↓
2. ข้อความไม่ถึงบางคน + มีหลาย instance
   → ผู้ส่งกับผู้รับอยู่คนละเครื่อง และไม่มี Pub/Sub กลาง ✓ นี่คือสาเหตุ
   ↓
3. Client reconnect แล้วข้อความช่วงที่หลุดหายไหม
   → ต้องมีกลไกดึงย้อนหลัง (ไม่ใช่พึ่ง WS อย่างเดียว)
```

### ตัวอย่าง: "อธิบาย Resilience ให้ฟังหน่อย"

> **Retry** เพราะความล้มเหลวส่วนใหญ่บนเน็ตเวิร์กเป็นเรื่องชั่วคราว

>
> เรียงความสำคัญ ถ้าให้เลือกใส่ทีละอย่าง ผมใส่ Timeout ก่อน แล้ว Idempotency แล้วค่อย Retry
> เพราะใส่ Retry ก่อน Idempotency คือการสร้างปัญหาที่ร้ายกว่าปัญหาเดิม"

## 12. One-Minute Review

**ทุกอย่างในบทนี้แก้แค่ 3 ปัญหา:** ช้าเกินไป / คนเยอะเกินไป / ของพังบางส่วน

**กลุ่ม "ช้า"**
- **Cache Aside**: อ่าน cache ก่อน miss ค่อยไป DB แล้วเขียนกลับ / เขียนข้อมูล = **ลบ** cache ไม่ใช่ทับ
- **TTL**: ตาข่ายนิรภัยกันข้อมูลค้างถาวร ตั้งจากคำถาม "ยอมให้เก่าได้กี่วินาที"
- **Redis**: cache / session / rate limit / lock — แต่ล่มแล้วข้อมูลหาย ห้ามเก็บของสำคัญไว้ที่เดียว
- **CDN**: static asset ใกล้ผู้ใช้ / invalidate ด้วยการใส่ hash ในชื่อไฟล์
- **Queue + Worker**: ย้ายงานหนักออกจากเส้นทางที่ผู้ใช้ต้องรอ — แลกกับ "ผู้ใช้ไม่รู้ว่าเสร็จยัง"

**กลุ่ม "คนเยอะ"**
- **Vertical** = เพิ่มพลังเครื่องเดิม มีเพดาน / **Horizontal** = เพิ่มเครื่อง ต้อง stateless
- **Stateless คือกุญแจ**: session → Redis/JWT, ไฟล์ → object storage
- **Load Balancer** กระจาย + health check / **API Gateway** auth + rate limit + routing
- **Rate Limiting** หน้าที่หลักคือกันระบบตัวเองตาย ไม่ใช่แค่กัน hacker

**กลุ่ม "ของพัง" — Resilience 5 อย่าง (ต้องมาเป็นชุด)**

```
Timeout → Retry → Exponential Backoff → Idempotency → Circuit Breaker
  รอ       ลอง      เว้นช่วงถี่ห่างขึ้น     ซ้ำได้ไม่เสียหาย   ตัดเมื่อพังจริง
```

- ไม่มี Timeout → ค้างรอ service ที่ตาย แล้วตายตาม (cascading failure)
- Retry ไม่มี Backoff → ซ้ำเติมระบบที่ป่วย
- **Retry ไม่มี Idempotency → สร้างข้อมูลซ้ำ (ตัดเงิน 2 รอบ)**
- ไม่มี Circuit Breaker → retry ไปเรื่อยกับของที่พังยาว

**สถาปัตยกรรม**
- **Microservices ไม่ใช่คำตอบเริ่มต้น** มันแก้ปัญหาองค์กร ไม่ใช่ปัญหา performance
- เส้นทาง: Monolith → **Modular Monolith** → แยกเฉพาะที่จำเป็น
- **Distributed Monolith** (แยก service แต่แชร์ DB) = ได้ข้อเสียครบ ไม่ได้ข้อดีเลย
- **Event Driven**: ระบบหลวม ต่อขยายง่าย แลกกับตามรอยยาก + eventual consistency
- **Eventual Consistency** ไม่ใช่ bug แต่เป็นการตัดสินใจ — ใช้กับ like/view ได้ ใช้กับยอดเงินไม่ได้

## 13. Memory Card

### จำ 5 อย่าง

1. **ทุกเทคนิคในบทนี้ไม่ได้ทำให้ระบบดีขึ้น — มันย้ายปัญหาไปที่อื่น** ตอบสัมภาษณ์ต้องพูดราคาที่จ่ายเสมอ
2. **Cache = ตู้เย็น** เร็วขึ้นแต่ของค้างตู้ได้ → เขียนข้อมูล = **ลบ cache** และมี **TTL** เป็นตาข่ายนิรภัย
3. **Stateless คือกุญแจของทุกการ scale** — ถ้า server จำอะไรไว้ในตัวเอง คุณเพิ่มเครื่องไม่ได้
4. **Resilience มาเป็นชุด 5** Timeout → Retry → Backoff → **Idempotency** → Circuit Breaker และ **retry โดยไม่มี idempotency = เครื่องผลิตข้อมูลซ้ำ**
5. **Microservices ไม่ใช่จุดเริ่มต้น** เริ่มที่ Modular Monolith แล้วแยกเฉพาะที่จำเป็นจริง

### Keyword Map

**Cache** → เก็บของไว้ใกล้มือ · **Cache Aside** → ถามตู้ก่อน ไม่มีค่อยไปหลังร้าน · **Cache Invalidation** → ลบของเก่าทิ้ง ยากที่สุด · **TTL** → วันหมดอายุ · **Redis** → ตู้เก็บของความเร็วสูง ล่มแล้วของหาย

**Queue** → ใบสั่งเสียบครัว · **Message Broker** → บุรุษไปรษณีย์ · **RabbitMQ** → งาน 1 ชิ้น คนทำ 1 คน ทำเสร็จแล้วทิ้ง · **Kafka** → สมุดบันทึกเหตุการณ์ อ่านย้อนได้ · **Worker** → คนงานหลังร้าน · **Background Job** → งานที่ไม่ต้องให้ผู้ใช้ยืนรอ · **Dead Letter Queue** → ถังงานที่ทำไม่สำเร็จ

**Polling** → ถามซ้ำทุก N วิ · **Long Polling** → ถามแล้วไม่วางสาย · **WebSocket** → เปิดสายค้าง สองทาง แต่ scale ยาก ต้องมี Pub/Sub กลาง

**Load Balancer** → คนโบกช่องว่าง · **Reverse Proxy** → หน้าด่านรับแทน · **API Gateway** → รปภ. ตรวจบัตร + โควต้า · **CDN** → สาขาใกล้บ้าน

**Vertical Scaling** → เพิ่มพลังเครื่องเดิม มีเพดาน · **Horizontal Scaling** → เพิ่มจำนวนเครื่อง ต้อง stateless · **Stateless** → ไม่จำอะไรในตัว · **Stateful** → จำไว้ในตัว scale ยาก · **Sticky Session** → ยาแก้ปวด ไม่ใช่ยารักษา

**Monolith** → ตึกเดียวจบ · **Modular Monolith** → ตึกเดียวแต่แบ่งห้องชัด (ทางเลือกที่ถูกประเมินต่ำ) · **Microservices** → แยกบ้าน อิสระแต่ต้องจ่ายค่าน้ำค่าไฟเอง · **Distributed System** → ทุกอย่างคุยกันผ่าน network ที่เชื่อถือไม่ได้

**Timeout** → หมดเวลารอ ใส่เป็นอย่างแรก · **Retry** → ลองใหม่ · **Exponential Backoff** → รอนานขึ้นเรื่อย ๆ + jitter · **Idempotency** → กดปุ่มลิฟต์ ซ้ำกี่ครั้งก็ผลเดิม · **Circuit Breaker** → เบรกเกอร์ไฟ ตัดก่อนไฟไหม้ทั้งบ้าน · **Rate Limiting** → จำกัดโควต้า กันระบบตัวเองตาย

**Event Driven** → ทำงานตามเหตุการณ์ หลวมแต่ตามรอยยาก · **Eventual Consistency** → เดี๋ยวก็ตรงกัน ใช้กับ like ได้ ใช้กับเงินไม่ได้ · **Backpressure** → สัญญาณ "รับไม่ไหวแล้ว"
