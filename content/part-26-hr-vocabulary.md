# PART 26 — HR TECHNICAL VOCABULARY

> ตำแหน่งในภาพใหญ่: Communication Layer — ภาษากลางที่ HR, Technical Interviewer, หัวหน้า และทีม product ใช้คุยเรื่องระบบกัน ไม่ว่าคุณจะทำ Frontend, Backend หรือ Infra

---

## 1. Big Picture

ในห้องสัมภาษณ์ คุณจะได้ยินประโยคแบบนี้บ่อยมาก:

- "ระบบที่คุณทำ **scalable** แค่ไหน?"
- "เคยเจอ **production issue** ไหม แล้วหา **root cause** ยังไง?"
- "ถ้าต้อง **trade-off** ระหว่างส่งงานเร็วกับ **technical debt** คุณเลือกยังไง?"
- "ทีมคุณทำ **postmortem** หลัง **incident** หรือเปล่า?"

คำพวกนี้ไม่ใช่ศัพท์ที่อยู่ใน syntax ของภาษาไหนเลย แต่เป็น **ภาษาของ engineering culture** — มันบอกคนฟังว่าคุณเคยอยู่ในทีมที่ทำระบบจริง มีคนใช้จริง มีปัญหาจริง

ปัญหาของ junior ส่วนใหญ่ไม่ใช่ "ไม่รู้จักคำ" แต่คือ:

1. **ใช้คำใหญ่เกินสิ่งที่ทำจริง** เช่น บอกว่า app todo list ของตัวเอง "highly available"
2. **ใช้คำผิดความหมาย** เช่น พูดว่า "ระบบ scalable เพราะโหลดเร็ว" (เร็วคือ latency ต่ำ ไม่ใช่ scalable)
3. **พูดคำได้แต่อธิบายต่อไม่ได้** พอโดนถามกลับว่า "race condition ที่เจอเกิดจากอะไร" แล้วเงียบ

คนสัมภาษณ์ที่มีประสบการณ์จะ **ถามเจาะทุกคำใหญ่ที่คุณพูด** ดังนั้นกฎทองของ PART นี้คือ:

> **อย่าพูดคำที่คุณอธิบายต่ออีก 2 ประโยคไม่ได้**

PART นี้จึงรวบรวมศัพท์ ~50 คำ แบ่งเป็น 4 หมวด แต่ละคำมี:

- คำแปลตรงตัว
- ความหมายจริงในงาน (ที่มักต่างจากคำแปลตรงตัว)
- ประโยคตัวอย่างที่ **คุณพูดเองได้จริงในห้องสัมภาษณ์** ไม่ใช่ประโยคในตำรา

วิธีใช้: อ่านคอลัมน์ Keyword แล้วลองพูดความหมายเองก่อน 1 ประโยค แล้วค่อยเช็คกับคอลัมน์ "ความหมายจริงในงาน"

## 2. Keywords

ตารางใน PART นี้ใช้ 4 ช่อง: **Keyword | คำแปล | ความหมายจริงในงาน | ตัวอย่างประโยคในการสัมภาษณ์**

ประโยคตัวอย่างเขียนเป็นภาษาไทยผสม keyword แบบที่ dev ไทยพูดกันจริง ถ้าสัมภาษณ์เป็นภาษาอังกฤษ ให้ใช้โครงเดียวกันแล้วแปลเป็นประโยคง่าย ๆ

### 2.1 หมวดคุณภาพระบบ (System Quality)

คำกลุ่มนี้ตอบคำถามว่า "ระบบนี้ **ดี** ในแง่ไหน" — ไม่ใช่แค่ทำงานได้ แต่ทำงานได้ดีแค่ไหนเมื่อเวลาผ่านไป คนเยอะขึ้น หรือมีอะไรพัง

| Keyword | คำแปล | ความหมายจริงในงาน | ตัวอย่างประโยคในการสัมภาษณ์ |
|---|---|---|---|
| Scalable | ขยายได้ | รับโหลดเพิ่มได้โดย **เพิ่ม resource** (เครื่อง/instance) แล้วระบบรองรับได้ตามสัดส่วน ไม่ต้องเขียนใหม่ | "ตอนออกแบบ API ผมทำให้ stateless เพื่อให้ scale แบบเพิ่ม instance หลัง load balancer ได้ ช่วง campaign เราเพิ่มจาก 2 เป็น 6 pod โดยไม่แก้ code" |
| Maintainable | ดูแลต่อได้ง่าย | คนอื่น (หรือตัวเราในอีก 6 เดือน) อ่าน แก้ เพิ่ม feature ได้โดยไม่กลัวพัง มี structure ชัด มี test | "ผมแยก business logic ออกจาก component ไปไว้ใน hook กับ service ทำให้ maintainable ขึ้น คนใหม่ในทีมแก้ logic ส่วนลดได้โดยไม่ต้องไปแตะ UI" |
| Reusable | นำกลับมาใช้ซ้ำได้ | ชิ้นส่วนที่เอาไปใช้ในหลายที่ได้โดยไม่ต้อง copy-paste และไม่ผูกกับ context เดิม | "ผมทำ `<DataTable>` เป็น reusable component รับ column config เป็น props ตอนนี้ใช้อยู่ 7 หน้าใน admin panel" |
| Reliable | เชื่อถือได้ | ทำงาน **ถูกต้องสม่ำเสมอ** ตามที่คาดหวัง ไม่ใช่แค่ไม่ล่ม แต่ผลลัพธ์ต้องถูกด้วย | "ผมเพิ่ม retry กับ validation ที่ payment callback เพราะเมื่อก่อนบางครั้ง order ไม่ถูก update ทำให้ระบบ reliable ขึ้น ticket เรื่องนี้หายไปเกือบหมด" |
| Fault Tolerant | ทนต่อความผิดพลาด | เมื่อบางส่วนพัง ระบบยังทำงานต่อได้ (อาจลดความสามารถลง) ไม่ล่มทั้งระบบ | "ถ้า recommendation service ล่ม หน้า product ยังขึ้นได้ปกติ แค่ส่วนแนะนำสินค้าจะซ่อนไป เราออกแบบให้ fault tolerant ด้วย timeout กับ fallback" |
| Highly Available | พร้อมใช้งานสูง | ระบบ **เปิดให้ใช้ได้** เกือบตลอดเวลา มักวัดเป็น % uptime ทำได้ด้วย redundancy ไม่มี single point of failure | "Database เราเป็น primary กับ replica คนละ zone ถ้า primary ล่มจะ failover อัตโนมัติ เป็นส่วนที่ทำให้ระบบ highly available" |
| Loosely Coupled | ผูกกันหลวม ๆ | ส่วนต่าง ๆ ของระบบพึ่งกันผ่าน interface/contract เปลี่ยนข้างในส่วนหนึ่งแล้วอีกส่วนไม่ต้องแก้ | "Order service ส่ง event ไป queue แทนการเรียก email service ตรง ๆ ทำให้ loosely coupled ถ้า email service ช้าหรือล่ม order ก็ยังสร้างได้" |
| Stateless | ไม่เก็บสถานะ | server ไม่จำอะไรของ client ไว้ใน memory ระหว่าง request ทุก request มีข้อมูลที่ต้องใช้ครบ (เช่น token) | "API ของเรา stateless เพราะเก็บ session ไว้ใน Redis ไม่ใช่ใน memory ของ server request ไหนวิ่งไป instance ไหนก็ได้" |
| Idempotent | เรียกซ้ำผลเท่าเดิม | ทำ operation เดิมกี่ครั้งก็ได้ **ผลลัพธ์สุดท้ายเหมือนทำครั้งเดียว** สำคัญมากกับ retry และ payment | "Endpoint ตัดเงินเราต้องส่ง idempotency key มาด้วย ถ้า client retry เพราะ timeout ระบบจะไม่ตัดเงินซ้ำ" |
| Backward Compatible | เข้ากันได้กับของเก่า | ของเวอร์ชันใหม่ยังใช้กับ client/ข้อมูลเวอร์ชันเก่าได้ ไม่ทำให้ของที่มีอยู่พัง | "ตอนเพิ่ม field ใหม่ใน API ผมทำเป็น optional เพื่อให้ backward compatible mobile app เวอร์ชันเก่าที่ user ยังไม่อัปเดตก็ยังใช้ได้" |
| Uptime | เวลาที่ระบบใช้ได้ | สัดส่วนเวลาที่ระบบใช้งานได้ เช่น 99.9% ต่อเดือน (เท่ากับล่มได้ประมาณ 43 นาทีต่อเดือน) | "ทีมเราตั้งเป้า uptime 99.9% ต่อเดือน เลยต้องมี health check และ alert ที่แจ้งเตือนภายในไม่กี่นาที" |
| Downtime | เวลาที่ระบบล่ม | ช่วงที่ user ใช้ไม่ได้ มีทั้ง planned (ประกาศล่วงหน้า เช่น maintenance) และ unplanned (ล่มเอง) | "Migration ครั้งนั้นเราทำแบบ zero-downtime คือเพิ่ม column ก่อน deploy code ใหม่ แล้วค่อยลบ column เก่าทีหลัง user ไม่รู้สึกเลย" |
| SLA | ข้อตกลงระดับบริการ | **Service Level Agreement** → สัญญากับลูกค้า/ภายนอก ถ้าทำไม่ได้มีผลทางธุรกิจ (เช่น คืนเงิน) | "SLA กับลูกค้า enterprise คือ 99.5% ถ้าหลุดต้องชดเชย credit ทีมเลยตั้ง SLO ภายในไว้สูงกว่านั้นเพื่อมี buffer" |
| SLO | เป้าหมายระดับบริการ | **Service Level Objective** → เป้าหมายภายในทีม เช่น "95% ของ request ตอบภายใน 300ms" ใช้ตัดสินใจว่าจะเร่ง feature หรือหยุดแก้ reliability | "เรามี SLO ว่า p95 latency ของ checkout ต้องต่ำกว่า 500ms พอ dashboard แดงติดกัน ทีมก็จะหยุดทำ feature แล้วมาแก้ performance ก่อน" |

### 2.2 หมวดประสิทธิภาพ (Performance)

คำกลุ่มนี้ตอบคำถามว่า "ระบบ **เร็ว** แค่ไหน และ **รับได้เยอะ** แค่ไหน" — สองเรื่องนี้ไม่ใช่เรื่องเดียวกัน

| Keyword | คำแปล | ความหมายจริงในงาน | ตัวอย่างประโยคในการสัมภาษณ์ |
|---|---|---|---|
| Latency | ความหน่วง | เวลาที่ **หนึ่ง request** ใช้ตั้งแต่ส่งจนได้คำตอบ วัดเป็น ms มักดูที่ p95/p99 ไม่ใช่ค่าเฉลี่ย | "API search เดิม p95 latency ประมาณ 2 วินาที ผมเพิ่ม index ที่ column ที่ใช้ filter ลดเหลือราว 200ms" |
| Throughput | ปริมาณงานต่อหน่วยเวลา | จำนวนงานที่ระบบทำได้ต่อวินาที เช่น requests/sec, jobs/min | "Worker เดิมประมวลผลได้ประมาณ 50 jobs ต่อนาที พอเปลี่ยนเป็น batch insert throughput เพิ่มขึ้นหลายเท่า queue ไม่ค้างอีก" |
| Concurrency | การทำงานพร้อมกัน | ระบบจัดการหลายงานที่ **อยู่ในช่วงเวลาเดียวกัน** ได้ (อาจสลับกันทำ ไม่จำเป็นต้องรันพร้อมกันจริง) | "Node.js จัดการ concurrency ด้วย event loop พอเรียก DB แล้วรอ มันไปรับ request อื่นต่อได้ ผมเลยระวังไม่ให้มี CPU-heavy code ไป block loop" |
| Bottleneck | คอขวด | จุดที่ช้าที่สุดใน flow ซึ่งจำกัดความเร็วของทั้งระบบ แก้ที่อื่นก็ไม่ช่วย | "ตอนแรกทีมคิดว่า server ช้า เลยเพิ่ม instance แต่ไม่ช่วย ผมไปดู trace แล้วเจอว่า bottleneck คือ query ที่ไม่มี index ใน DB" |

### 2.3 หมวดปัญหา & การแก้ (Problems & Fixes)

คำกลุ่มนี้คือคำที่ถูกถามบ่อยที่สุดในรอบ behavioral + technical เพราะคนสัมภาษณ์อยากรู้ว่า **ตอนระบบมีปัญหา คุณทำตัวยังไง**

| Keyword | คำแปล | ความหมายจริงในงาน | ตัวอย่างประโยคในการสัมภาษณ์ |
|---|---|---|---|
| Race Condition | สภาวะแข่งกัน | ผลลัพธ์ผิดเพราะ **ลำดับเวลา** ของงานสองงานที่แตะข้อมูลเดียวกันไม่แน่นอน | "เราเคยขายของเกิน stock เพราะสอง request อ่าน stock=1 พร้อมกันแล้วต่างคนต่างลด ผมแก้ด้วย atomic update ที่เช็ค stock > 0 ใน query เดียว" |
| Memory Leak | หน่วยความจำรั่ว | memory ที่ใช้แล้วไม่ถูกคืน ค่อย ๆ โตขึ้นจน app ช้าหรือ crash | "หน้า dashboard ใช้ memory เพิ่มขึ้นเรื่อย ๆ ผมเจอว่า `setInterval` ใน `useEffect` ไม่มี cleanup พอเพิ่ม return clear interval ก็หาย" |
| Technical Debt | หนี้ทางเทคนิค | ทางลัดที่เลือกเพื่อส่งเร็ว ซึ่งต้อง "จ่ายดอกเบี้ย" ทีหลังเป็นเวลาแก้ bug/เพิ่ม feature ที่ยากขึ้น | "ตอน MVP เรา hardcode config ไว้เพื่อให้ทัน launch ผมบันทึกเป็น tech debt ใน backlog แล้วกลับมาแยกเป็น env config ใน sprint ถัดไป" |
| Legacy Code | code เก่า | code ที่ยังใช้งานจริงแต่เก่า ไม่มี test เข้าใจยาก คนเขียนอาจไม่อยู่แล้ว **ไม่ได้แปลว่า code แย่** | "ผมต้องแก้ legacy module ที่ไม่มี test เลยเขียน test ครอบพฤติกรรมเดิมก่อน แล้วค่อยแก้ เพื่อให้มั่นใจว่าไม่ทำของเดิมพัง" |
| Refactoring | ปรับโครงสร้าง code | เปลี่ยนโครงสร้างภายในให้ดีขึ้น **โดยพฤติกรรมภายนอกเหมือนเดิม** ไม่ใช่การเพิ่ม feature | "ผม refactor function 300 บรรทัดให้แยกเป็นฟังก์ชันย่อย โดยรัน test เดิมให้ผ่านทุกขั้น behavior ไม่เปลี่ยน แต่อ่านง่ายขึ้นมาก" |
| Regression | การถดถอย | ของที่ **เคยทำงานได้ พังเพราะการแก้ใหม่** | "หลังแก้ bug ฟอร์ม login ปุ่ม reset password กลับพัง เป็น regression ผมเลยเพิ่ม E2E test ของ flow นี้ไว้ใน CI" |
| Root Cause | ต้นเหตุ | สาเหตุที่แท้จริง ไม่ใช่อาการ ถ้าแก้ที่ root cause ปัญหาจะไม่กลับมา | "อาการคือ API timeout แต่ root cause คือ connection pool เต็ม เพราะมีจุดหนึ่งไม่ release connection ตอนเกิด error" |
| Hotfix | แก้ด่วน | การแก้และ deploy เร่งด่วนนอกรอบ release ปกติ เพื่อหยุดปัญหาบน production | "เราทำ hotfix ปิด feature flag ภายใน 10 นาที แล้วค่อยแก้ root cause จริงแบบมี review และ test ในวันถัดไป" |
| Rollback | ถอยกลับ | เอาเวอร์ชันก่อนหน้าที่ใช้ได้กลับมา deploy แทนเวอร์ชันที่มีปัญหา | "หลัง deploy error rate พุ่ง ผมไม่รีบแก้บน production แต่ rollback กลับเวอร์ชันก่อนก่อน เพราะเร็วและปลอดภัยกว่า แล้วค่อยหาสาเหตุ" |
| Production Issue | ปัญหาบนระบบจริง | ปัญหาที่เกิดกับ environment ที่ user ใช้จริง มีผลต่อคนจริง/เงินจริง | "Production issue ที่จำได้คือ user บางกลุ่ม login ไม่ได้ ผมเริ่มจากดู log ของช่วงเวลานั้นแล้วเทียบกับ deploy ล่าสุด" |
| Incident | เหตุการณ์ผิดปกติ | ปัญหาที่ **กระทบ user หรือธุรกิจ** และทีมต้องเข้าไปจัดการแบบมีขั้นตอน มักมีระดับความรุนแรง (severity) | "ทีมเราประกาศ incident เมื่อ checkout error เกิน threshold จะมีคนนำ incident คนสื่อสาร และคนแก้ แยกบทบาทกันชัด" |
| Postmortem | สรุปหลังเหตุการณ์ | เอกสารวิเคราะห์หลัง incident: เกิดอะไร เพราะอะไร แก้ยังไง ป้องกันยังไง แบบ **blameless** (ไม่หาคนผิด) | "หลัง incident ผมเขียน postmortem ระบุ timeline, root cause และ action item เช่นเพิ่ม alert กับ test เน้นว่าระบบเปิดช่องให้พลาดตรงไหน ไม่ใช่ใครพลาด" |
| Blocker | สิ่งที่ขวางงาน | สิ่งที่ทำให้งานเดินต่อไม่ได้จนกว่าจะแก้ เช่น รอ API, รอสิทธิ์, รอ decision | "ใน standup ผมแจ้ง blocker ว่ารอ API spec จากทีม backend พร้อมบอกว่าระหว่างนี้จะ mock data ทำ UI ไปก่อน" |

### 2.4 หมวดกระบวนการทำงาน (Workflow & Process)

คำกลุ่มนี้บอกว่า **คุณทำงานเป็นทีมเป็นไหม** — HR และหัวหน้าทีมใช้คำพวกนี้เยอะกว่า technical interviewer

#### 2.4.1 ทีมและการวางแผน

| Keyword | คำแปล | ความหมายจริงในงาน | ตัวอย่างประโยคในการสัมภาษณ์ |
|---|---|---|---|
| Backlog | รายการงานค้าง | รายการงานทั้งหมดที่ยังไม่ทำ เรียงตาม priority รวม feature, bug, tech debt | "ผมช่วย PO จัด backlog โดยแยก bug ที่กระทบ user ขึ้นก่อน และบอก effort คร่าว ๆ ให้เขาตัดสินใจ priority ได้" |
| Sprint | รอบการทำงาน | ช่วงเวลาสั้น ๆ คงที่ (มักเป็น 1–2 สัปดาห์) ที่ทีมตกลงว่าจะส่งงานชุดหนึ่งให้เสร็จ | "ทีมเราทำ sprint ละ 2 สัปดาห์ มี planning ต้น sprint และ retro ท้าย sprint ผมชอบ retro เพราะได้ปรับวิธีทำงานจริง" |
| Story Point | แต้มความยากของงาน | หน่วยประมาณ **ความซับซ้อน/ความไม่แน่นอน** ของงานแบบเทียบกัน ไม่ใช่จำนวนชั่วโมง | "Story point ของทีมเราเทียบกับงาน reference เช่นฟอร์มธรรมดาคือ 2 ถ้างานไหนมีส่วนที่ไม่รู้เยอะ ผมจะให้แต้มสูงและเสนอแยก spike ออกมา" |
| Code Review | ตรวจ code | ให้คนอื่นอ่าน code ก่อน merge เพื่อหา bug แชร์ความรู้ และรักษามาตรฐาน | "ตอน code review ผมพยายามคอมเมนต์ที่เหตุผล เช่น 'ตรงนี้ถ้า API คืน null จะ crash' มากกว่า 'แก้ตรงนี้' และแยกว่าอันไหนต้องแก้ อันไหนแค่เสนอ" |
| Pair Programming | เขียน code เป็นคู่ | สองคนทำงานเดียวกันพร้อมกัน คนหนึ่งพิมพ์ (driver) อีกคนคิด/ตรวจ (navigator) | "ตอนเข้าทีมใหม่ ผม pair programming กับ senior 2–3 วัน ทำให้เข้าใจ codebase เร็วกว่าอ่านเองมาก" |
| MVP | ผลิตภัณฑ์ขั้นต่ำที่ใช้ได้ | **Minimum Viable Product** → เวอร์ชันเล็กที่สุดที่ยังให้คุณค่ากับ user ได้จริง เพื่อทดสอบสมมติฐานเร็ว | "ใน MVP เราตัด filter ขั้นสูงออก เหลือ search อย่างเดียว เพราะอยากรู้ก่อนว่า user ใช้ search จริงไหม ค่อยเพิ่มตาม data" |
| Scope Creep | ขอบเขตงานบวม | requirement ค่อย ๆ เพิ่มระหว่างทางโดยไม่ปรับเวลา/คน ทำให้งานเลื่อน | "พอมีคำขอเพิ่มกลาง sprint ผมไม่ปฏิเสธเลย แต่บอก PO ว่าถ้าเพิ่มอันนี้ ต้องเลื่อนอะไรออก เพื่อกัน scope creep" |
| Cross-functional | ข้ามสายงาน | ทีมหรืองานที่รวมหลายบทบาท เช่น dev, design, QA, PO อยู่ด้วยกัน | "ทีมผมเป็น cross-functional มี designer กับ QA ในทีม ผมเลยคุยเรื่อง edge case กับ QA ตั้งแต่ตอนเริ่ม ไม่ใช่รอตอนส่งเทส" |
| Stakeholder | ผู้มีส่วนได้ส่วนเสีย | คนที่ได้รับผลหรือมีอำนาจตัดสินใจเรื่องนั้น เช่น PO, หัวหน้า, ทีมอื่น, ลูกค้า | "ก่อนเปลี่ยน API ผมลิสต์ stakeholder ที่ใช้ API นี้ แล้วแจ้งล่วงหน้าพร้อม timeline ไม่ให้ใครโดนเซอร์ไพรส์" |
| Trade-off | การแลกเปลี่ยน | ได้อย่างต้องเสียอย่าง ไม่มีทางเลือกที่ดีทุกด้าน ต้องเลือกตาม context | "เราเลือก SSR เพื่อ SEO แต่ trade-off คือ server load เพิ่ม เลยใส่ cache หน้า product ไว้ช่วย" |
| Proof of Concept | ต้นแบบพิสูจน์แนวคิด | **PoC** → ทำชิ้นเล็ก ๆ เพื่อพิสูจน์ว่า "ทำได้ไหม" ก่อนลงแรงจริง มักไม่ได้เอาขึ้น production | "ก่อนตัดสินใจใช้ WebSocket ผมทำ proof of concept 2 วัน ทดสอบกับ load balancer ของบริษัทว่าต่อ connection ค้างไว้ได้จริง" |
| Handover | ส่งมอบงาน | การส่งต่องาน/ความรู้ให้อีกคนหรืออีกทีม มีเอกสาร สิทธิ์ และคำอธิบายครบ | "ก่อนลาออกจากที่เก่า ผมทำ handover document มี architecture, วิธี deploy, จุดที่เปราะ และนัด walkthrough กับคนรับงาน" |
| On-call | เวรเฝ้าระบบ | ช่วงเวลาที่เราเป็นคนแรกที่ต้องรับ alert และตอบสนองเมื่อ production มีปัญหา | "ทีมผลัดกัน on-call สัปดาห์ละคน ผมเคยโดนปลุกตีสองเพราะ disk เต็ม หลังจากนั้นผมเพิ่ม alert ล่วงหน้าที่ 80% แทน" |

#### 2.4.2 Release และการเปลี่ยนแปลงระบบ

| Keyword | คำแปล | ความหมายจริงในงาน | ตัวอย่างประโยคในการสัมภาษณ์ |
|---|---|---|---|
| Deployment | การนำขึ้นระบบ | เอา code เวอร์ชันใหม่ไปรันบน environment (staging/production) **deploy ≠ release** เสมอไป (อาจ deploy แต่ซ่อนด้วย feature flag) | "Deployment ของเราผ่าน CI/CD ทั้งหมด merge เข้า main แล้ว pipeline build, test, deploy ไป staging อัตโนมัติ production ต้องกด approve" |
| Migration | การย้าย/เปลี่ยนโครงสร้าง | การเปลี่ยนจากของเดิมไปของใหม่ เช่น schema DB, ย้าย framework, ย้าย cloud ต้องมีแผนย้ายข้อมูลและ rollback | "Database migration ที่เปลี่ยนชื่อ column ผมแยกเป็นหลายขั้น: เพิ่ม column ใหม่, เขียนทั้งสองที่, ย้ายข้อมูล, แล้วค่อยลบของเก่า" |
| Deprecated | เลิกสนับสนุน (กำลังจะเลิก) | ยังใช้ได้อยู่ แต่ **ประกาศว่าจะเอาออกในอนาคต** ควรย้ายไปใช้ของใหม่ | "Library ที่เราใช้ประกาศ deprecated method หนึ่ง ผมเลยค่อย ๆ ย้ายไปใช้ตัวใหม่ก่อนอัปเกรด major version จะได้ไม่พังทีเดียว" |
| Breaking Change | การเปลี่ยนที่ทำของเดิมพัง | การเปลี่ยนที่ทำให้ผู้ใช้เดิม (client, code อื่น) ต้องแก้ตาม ไม่อย่างนั้นพัง เช่น ลบ field, เปลี่ยนชื่อ, เปลี่ยน type | "การเปลี่ยน `price` จาก string เป็น number เป็น breaking change เราเลยออกเป็น API v2 และให้ v1 ใช้ได้ต่ออีก 3 เดือน" |

## 3. Mental Model

ให้มองศัพท์ทั้งหมดใน PART นี้เป็น **คำถาม 4 ข้อที่องค์กรถามเกี่ยวกับระบบ**

```
                 ┌── คุณภาพระบบ   → "ระบบนี้ไว้ใจได้แค่ไหน เมื่อเวลาผ่านไป?"
                 │
ศัพท์ในห้องสัมภาษณ์ ├── ประสิทธิภาพ   → "เร็วแค่ไหน รับได้เยอะแค่ไหน?"
                 │
                 ├── ปัญหา & การแก้ → "พังแล้วทำยังไง และไม่ให้พังซ้ำยังไง?"
                 │
                 └── กระบวนการทำงาน → "ทำงานเป็นทีมกับคนอื่นได้ไหม?"
```

ให้มองภาพนี้ว่า ทุกคำศัพท์ที่ HR หรือ interviewer พูด จริง ๆ แล้วคือการถาม 1 ใน 4 คำถามนี้ ถ้าคุณรู้ว่าเขาถามหมวดไหน คุณจะรู้ว่าต้องตอบด้วยหลักฐานแบบไหน

| หมวดที่ถูกถาม | เขาอยากได้หลักฐานแบบไหน |
|---|---|
| คุณภาพระบบ | การตัดสินใจเชิง design และเหตุผล (ทำไมออกแบบแบบนี้) |
| ประสิทธิภาพ | ตัวเลขก่อน/หลัง และวิธีวัด |
| ปัญหา & การแก้ | เรื่องเล่าที่มีลำดับ: อาการ → สืบ → root cause → แก้ → ป้องกัน |
| กระบวนการทำงาน | พฤติกรรมกับคน: สื่อสาร ตกลง ส่งต่อ |

อีก mental model ที่สำคัญ: **ศัพท์ใหญ่ต้องมี "ตัวเลข" หรือ "กลไก" ตามมาเสมอ**

```
คำใหญ่ (Scalable)
      ↓
กลไก (stateless + เพิ่ม instance หลัง load balancer)
      ↓
หลักฐาน (ช่วง campaign เพิ่มจาก 2 เป็น 6 pod ไม่ต้องแก้ code)
```

ให้มองภาพนี้ว่า คำศัพท์เป็นแค่ "หัวข้อ" ส่วนกลไกและหลักฐานคือ "เนื้อ" ถ้ามีแต่หัวข้อ คนฟังจะไม่เชื่อ

## 4. ภาพจำ

```
🧠 ภาพจำ:
ศัพท์ technical = ศัพท์หมอ
คนไข้พูดว่า "ปวดท้อง" (อาการ)
หมอพูดว่า "ไส้ติ่งอักเสบ" (root cause)
หมอที่ดีอธิบายได้ว่า ทำไมถึงคิดว่าเป็นไส้ติ่ง

อาการ (Production Issue)
      ↓
ตรวจ (Log / Metric / Trace)
      ↓
วินิจฉัย (Root Cause)
      ↓
รักษา (Hotfix / Rollback)
      ↓
ป้องกัน (Postmortem → Action Item)
```

ให้มองภาพนี้ว่า ศัพท์ทุกคำคือ "ขั้นหนึ่งในการรักษา" ถ้าพูดได้ว่ามันอยู่ขั้นไหน คนฟังจะรู้ทันทีว่าคุณเข้าใจกระบวนการทั้งหมด

ภาพจำรายคู่ที่ช่วยไม่ให้สับสน:

```
🧠 Latency vs Throughput = ทางด่วน
Latency   = รถคันหนึ่งใช้เวลาวิ่งจากต้นทางถึงปลายทางกี่นาที
Throughput = ทางด่วนปล่อยรถผ่านได้กี่คันต่อชั่วโมง
เพิ่มเลน → throughput เพิ่ม แต่รถแต่ละคันไม่ได้วิ่งเร็วขึ้น
```

ให้มองภาพนี้ว่า latency คือประสบการณ์ของ "รถหนึ่งคัน" ส่วน throughput คือความจุของ "ทั้งถนน" สองตัวนี้แก้คนละวิธี

```
🧠 Scalable = ร้านอาหารที่เพิ่มพ่อครัวได้
ลูกค้าเพิ่ม → เพิ่มพ่อครัว → ออกอาหารได้มากขึ้นตามสัดส่วน
ถ้าสูตรอยู่ในหัวพ่อครัวคนเดียว (stateful) → เพิ่มคนก็ไม่ช่วย
```

ให้มองภาพนี้ว่า ระบบจะ scale ได้ก็ต่อเมื่อความรู้ (state) ไม่ได้ติดอยู่กับเครื่องใดเครื่องหนึ่ง

```
🧠 Idempotent = ปุ่มเรียกลิฟต์
กดครั้งเดียว หรือกด 10 ครั้ง → ลิฟต์ก็มาครั้งเดียว
ไม่ใช่ idempotent = กดปุ่มโอนเงิน 10 ครั้ง → โอน 10 ครั้ง
```

ให้มองภาพนี้ว่า idempotent คือการออกแบบให้ "การกดซ้ำ" ไม่มีผลเสีย ซึ่งสำคัญมากเพราะใน network จริง client retry เสมอ

```
🧠 Technical Debt = บัตรเครดิต
รูดก่อน (ส่งงานเร็ว) → ได้ของทันที
ไม่จ่ายคืน → ดอกเบี้ยทบ (ทุก feature ใหม่ช้าลงเรื่อย ๆ)
หนี้ไม่ผิด ถ้ารู้ตัวว่าก่อ และมีแผนจ่าย
```

ให้มองภาพนี้ว่า technical debt ไม่ใช่ความผิด แต่เป็นการตัดสินใจทางธุรกิจที่ต้องมีแผนจ่ายคืน

```
🧠 Fault Tolerant vs Highly Available = เครื่องบิน 2 เครื่องยนต์
Fault Tolerant   = เครื่องยนต์ดับไป 1 ตัว ยังบินต่อได้
Highly Available = สายการบินมีเครื่องสำรองพร้อมบิน เที่ยวบินแทบไม่ถูกยกเลิก
```

ให้มองภาพนี้ว่า fault tolerant พูดถึง "ตอนพังบางส่วน" ส่วน highly available พูดถึง "สัดส่วนเวลาที่ใช้งานได้" ซึ่งเกี่ยวกันแต่ไม่ใช่เรื่องเดียวกัน

```
🧠 Deprecated vs Breaking Change = ป้ายถนน
Deprecated     = ป้าย "ถนนนี้จะปิดเดือนหน้า กรุณาใช้เส้นทางใหม่"
Breaking Change = วันที่ถนนปิดจริง ใครยังขับมาทางนี้ไปต่อไม่ได้
```

ให้มองภาพนี้ว่า deprecated คือ "คำเตือนล่วงหน้า" ส่วน breaking change คือ "วันที่มีผลจริง" ทีมที่ดีจะมีช่วงเวลาระหว่างสองอย่างนี้เสมอ

## 5. How It Works

ศัพท์ส่วนใหญ่ใน PART นี้ไม่ได้อยู่แยกกัน แต่ **เกิดต่อเนื่องกันเป็นวงจรชีวิตของงาน** ถ้าเล่าเป็น flow ได้ คุณจะใช้คำได้ถูกที่ถูกเวลาโดยอัตโนมัติ

### 5.1 วงจรการส่งงาน (Workflow)

```
[Stakeholder มี requirement]
          ↓
[PoC ถ้ายังไม่แน่ใจว่าทำได้]
          ↓
[Backlog → จัด priority]
          ↓
[Sprint Planning → ให้ Story Point]
          ↓
[Develop (อาจ Pair Programming)]
          ↓
[Code Review]
          ↓
[Deployment → Staging → Production]
          ↓
[MVP ถึงมือ user → เก็บ feedback → กลับไป Backlog]
```

ให้มองภาพนี้ว่า งานหนึ่งชิ้นเดินจาก "ความต้องการของคน" ไปเป็น "ของที่ user ใช้จริง" และวนกลับมาเป็นความต้องการใหม่เสมอ ศัพท์แต่ละคำคือชื่อของแต่ละสถานี

### 5.2 วงจรเมื่อระบบมีปัญหา (Incident Lifecycle)

```
[Alert ดัง / User แจ้ง]
          ↓
[On-call รับเรื่อง]
          ↓
[ประกาศ Incident + ประเมินความรุนแรง]
          ↓
[หยุดเลือดก่อน: Rollback หรือ Hotfix หรือปิด feature flag]
          ↓
[ระบบกลับมา → นับ Downtime → เทียบกับ SLO/SLA]
          ↓
[หา Root Cause]
          ↓
[Postmortem แบบ blameless]
          ↓
[Action Item: test กัน Regression, alert ใหม่, จ่าย Technical Debt]
```

ให้มองภาพนี้ว่า เวลาระบบพัง ลำดับที่ถูกคือ "หยุดความเสียหายก่อน แล้วค่อยหาสาเหตุ แล้วค่อยป้องกัน" — คนที่ข้ามไปหา root cause ขณะที่ user ยังใช้ไม่ได้ คือคนที่ยังไม่เคยอยู่ใน incident จริง

### 5.3 วงจรการเปลี่ยนแปลงระบบ (Change Lifecycle)

```
[ของเดิมใช้งานอยู่ (อาจเป็น Legacy Code)]
          ↓
[ออกของใหม่แบบ Backward Compatible]
          ↓
[ประกาศของเดิมเป็น Deprecated + ให้เวลาย้าย]
          ↓
[Migration: ผู้ใช้/ข้อมูลย้ายไปของใหม่]
          ↓
[เอาของเดิมออก = Breaking Change (ทำตอนไม่มีใครใช้แล้ว)]
```

ให้มองภาพนี้ว่า การเปลี่ยนระบบที่ดีคือการ "สร้างสะพานใหม่ข้างสะพานเก่า ให้คนเดินข้ามจนหมดก่อน แล้วค่อยรื้อสะพานเก่า" ไม่ใช่รื้อก่อนแล้วค่อยสร้าง

### 5.4 คำด้านประสิทธิภาพเชื่อมกันยังไง

```
Request เข้ามาเยอะขึ้น (Concurrency สูงขึ้น)
          ↓
ถ้าไม่มี Bottleneck → Throughput เพิ่ม, Latency คงที่
ถ้ามี Bottleneck    → Throughput ตัน, Latency พุ่ง
          ↓
แก้ Bottleneck / Scale ออก
          ↓
ถ้าหลาย request แตะข้อมูลเดียวกันพร้อมกัน → ระวัง Race Condition
```

ให้มองภาพนี้ว่า "เร็ว" กับ "รับได้เยอะ" จะไปด้วยกันจนกว่าจะเจอคอขวด และทันทีที่มีงานพร้อมกันเยอะ ปัญหาเรื่องลำดับเวลาจะตามมาเสมอ

## 6. Example

### Scenario A — ตอบคำถาม "เล่า production issue ที่เคยเจอ"

**ตอบแบบใช้ศัพท์เยอะแต่ไม่มีเนื้อ (อย่าทำ):**

> "ผมเคยเจอ production issue ครับ เป็น race condition ทำให้ระบบไม่ reliable ผมก็หา root cause แล้วทำ hotfix ครับ ตอนนี้ระบบ scalable แล้ว"

ปัญหา: มีคำใหญ่ 5 คำ แต่ไม่มีข้อมูลเลยว่าเกิดอะไร และ "scalable" ไม่เกี่ยวกับเรื่องนี้

**ตอบแบบใช้ศัพท์เป็น (ทำแบบนี้):**

> "มีครั้งหนึ่งที่ระบบ e-commerce ขายสินค้าเกิน stock ช่วง flash sale ครับ
> อาการคือ stock ติดลบ ผมดู log แล้วเจอสอง order สร้างห่างกันไม่กี่ ms
> root cause คือ race condition: code อ่าน stock ก่อน แล้วค่อยลดในอีก query เลยมีช่องที่สอง request อ่านค่าเดิมพร้อมกัน
> hotfix วันนั้นคือเปลี่ยนเป็น update แบบมีเงื่อนไข stock > 0 ใน query เดียว
> หลังจากนั้นเขียน postmortem และเพิ่ม test ที่ยิง request พร้อมกันไว้ใน CI เพื่อกัน regression"

ทำไมดี: ศัพท์ทุกคำมีเนื้อหารองรับ และเรียงตามวงจร incident

### Scenario B — HR ถาม "คุณจัดการกับ scope creep ยังไง"

HR ไม่ได้อยากได้คำตอบ technical เขาอยากรู้ว่า **คุณสื่อสารเป็นไหม**

> "ผมไม่ปฏิเสธคำขอทันทีครับ แต่จะแปลงให้เป็น trade-off ที่ stakeholder ตัดสินใจได้ เช่น 'ถ้าเพิ่ม export PDF ใน sprint นี้ งาน filter จะเลื่อนไป sprint หน้า เลือกอันไหนดีครับ' แล้วบันทึกไว้ใน backlog ให้ทุกคนเห็นตรงกัน"

### Scenario C — Technical interviewer ถาม "API ของคุณ idempotent ไหม"

> "GET, PUT, DELETE ผมออกแบบให้ idempotent ตาม HTTP semantics ครับ ส่วน POST ที่สร้าง order ตัวมันเองไม่ idempotent เลยให้ client ส่ง idempotency key มา server เก็บ key ไว้ ถ้าเจอ key ซ้ำจะคืนผลเดิมแทนการสร้างใหม่ ป้องกันกรณี mobile network หลุดแล้ว retry"

### Scenario D — หัวหน้าถาม "ทำไมงานนี้ใช้ 8 story point"

> "งาน UI เองไม่ยากครับ ประมาณ 3 แต่ผมให้ 8 เพราะต้องแตะ legacy module ที่ไม่มี test และยังไม่รู้ว่า API รองรับ pagination ไหม ถ้าอยากลดความเสี่ยง ผมเสนอแยก spike 1 วันไปเช็ค API ก่อน แล้วค่อยประมาณใหม่"

ทำไมดี: แสดงว่าเข้าใจว่า story point วัด **ความไม่แน่นอน** ด้วย ไม่ใช่แค่ปริมาณงาน

## 7. Compare

คู่ศัพท์ที่คนสับสนบ่อยที่สุด

### 7.1 SLA vs SLO vs Uptime

| มิติ | SLA | SLO | Uptime |
|---|---|---|---|
| คืออะไร | สัญญากับลูกค้า | เป้าหมายภายในทีม | ตัวเลขที่วัดได้จริง |
| ใครกำหนด | ธุรกิจ + ลูกค้า | ทีม engineering | ระบบ monitoring วัด |
| ถ้าไม่ถึง | มีผลทางสัญญา/เงิน | ทีมปรับ priority มาแก้ reliability | เป็นแค่ข้อมูล |
| ตั้งค่าเทียบกัน | ต่ำสุด | สูงกว่า SLA (มี buffer) | ควรสูงกว่า SLO |

### 7.2 Bug vs Production Issue vs Incident

| มิติ | Bug | Production Issue | Incident |
|---|---|---|---|
| คืออะไร | code ทำงานผิดจากที่ตั้งใจ | ปัญหาบนระบบจริง (อาจไม่ใช่ bug เช่น disk เต็ม) | ปัญหาที่กระทบ user/ธุรกิจจนต้องจัดการแบบเร่งด่วน |
| เกิดที่ไหน | ได้ทุก environment | production เท่านั้น | production |
| ความเร่งด่วน | ตาม priority ใน backlog | แล้วแต่ผลกระทบ | สูง มีขั้นตอน incident |
| ผลลัพธ์ | ticket + fix | fix / config change | recovery + postmortem |

จำ: **bug ทุกตัวไม่ใช่ incident** (ปุ่มเบี้ยวในหน้า settings คือ bug) และ **incident ไม่จำเป็นต้องมาจาก bug** (cloud provider ล่มก็เป็น incident ได้)

### 7.3 Hotfix vs Rollback

| มิติ | Hotfix | Rollback |
|---|---|---|
| ทำอะไร | เขียนแก้ใหม่แล้ว deploy ด่วน | กลับไปใช้เวอร์ชันก่อนหน้า |
| ความเร็ว | ขึ้นกับว่าแก้ง่ายแค่ไหน | มักเร็วกว่า เพราะของเก่าเคยใช้ได้แล้ว |
| ความเสี่ยง | code ใหม่ที่ test น้อย อาจสร้างปัญหาใหม่ | ถ้ามี DB migration ไปแล้ว อาจ rollback ไม่ได้ตรง ๆ |
| ใช้เมื่อ | rollback ไม่ได้ หรือปัญหาไม่ได้มาจาก deploy ล่าสุด | ปัญหาเริ่มหลัง deploy ล่าสุดชัดเจน |

### 7.4 Latency vs Throughput

| มิติ | Latency | Throughput |
|---|---|---|
| ถามว่า | หนึ่งงานใช้เวลาเท่าไร | ต่อวินาทีทำได้กี่งาน |
| หน่วย | ms, วินาที | req/s, jobs/min |
| user รู้สึกเป็น | "เว็บช้า" | "ช่วงคนเยอะแล้วล่ม/ค้าง" |
| แก้ด้วย | cache, index, ลด network hop | scale ออก, batch, queue |

### 7.5 Concurrency vs Parallelism

| มิติ | Concurrency | Parallelism |
|---|---|---|
| ความหมาย | จัดการหลายงานในช่วงเวลาเดียวกัน (สลับกันได้) | ทำหลายงาน **ในเวลาเดียวกันจริง** บนหลาย core |
| ต้องมีหลาย core ไหม | ไม่จำเป็น | จำเป็น |
| ตัวอย่าง | Node.js event loop รับหลาย request | Java thread pool บน CPU หลาย core, Worker Threads |

### 7.6 Fault Tolerant vs Highly Available vs Reliable

| มิติ | Fault Tolerant | Highly Available | Reliable |
|---|---|---|---|
| คำถาม | ส่วนหนึ่งพังแล้วยังทำงานไหม | เปิดให้ใช้ได้กี่ % ของเวลา | ทำงานถูกต้องสม่ำเสมอไหม |
| วิธีทำ | timeout, fallback, circuit breaker, retry | redundancy, failover, multi-zone | validation, test, idempotency, monitoring |
| ตัวอย่างที่ขาด | ระบบ recommend ล่ม → ทั้งหน้าล่ม | DB มีตัวเดียว ล่มแล้วรอคนมา restart | ระบบเปิดได้ แต่คิดเงินผิด |

### 7.7 Refactoring vs Rewrite vs Migration

| มิติ | Refactoring | Rewrite | Migration |
|---|---|---|---|
| เปลี่ยนอะไร | โครงสร้างภายใน | เขียนใหม่ทั้งหมด | ย้ายจากของเดิมไปของใหม่ (tech/schema/platform) |
| behavior ภายนอก | ต้องเหมือนเดิม | ตั้งใจให้เหมือน แต่เสี่ยงต่าง | อาจเปลี่ยนหรือไม่ก็ได้ |
| ขนาด | เล็ก ทำทีละนิดได้ | ใหญ่ เสี่ยงสูง | กลาง-ใหญ่ ต้องมีแผน |

### 7.8 MVP vs PoC

| มิติ | MVP | Proof of Concept |
|---|---|---|
| ตอบคำถาม | "user อยากได้ไหม" | "technical ทำได้ไหม" |
| ใครใช้ | user จริง | ทีมภายใน |
| ขึ้น production | ใช่ | มักไม่ใช่ (มักทิ้งหลังพิสูจน์) |

### 7.9 Deprecated vs Breaking Change vs Backward Compatible

| มิติ | Deprecated | Breaking Change | Backward Compatible |
|---|---|---|---|
| ของเดิมยังใช้ได้ไหม | ได้ (ตอนนี้) | ไม่ได้ | ได้ |
| สื่อสารว่า | "เตรียมย้ายนะ" | "ต้องแก้ตาม" | "ไม่ต้องทำอะไร" |
| ตัวอย่าง | method เก่ามี warning | ลบ field ออกจาก API | เพิ่ม optional field |

## 8. Common Mistakes

### 8.1 คำที่ใช้ผิดบ่อย

| คำที่พูด | ใช้ผิดแบบนี้ | ความจริง | พูดใหม่ให้ถูก |
|---|---|---|---|
| Scalable | "ระบบผม scalable เพราะโหลดเร็ว" | เร็ว = latency ต่ำ ส่วน scalable = รับโหลดเพิ่มได้เมื่อเพิ่ม resource ระบบที่เร็วตอนมี 10 คน อาจล่มตอนมี 10,000 คน | "หน้านี้ latency ต่ำเพราะ cache ส่วนเรื่อง scale เราทำ API ให้ stateless เพื่อเพิ่ม instance ได้" |
| Bug vs Incident | "เมื่อวานมี incident ปุ่มสีผิด" | ปุ่มสีผิดคือ bug ไม่กระทบ user จนต้องระดมทีม | "เจอ bug เรื่อง UI ผมเปิด ticket ไว้ ส่วน incident คือตอน checkout ใช้ไม่ได้ 20 นาที" |
| Race Condition | เรียกทุก bug ที่ "บางทีเกิดบางทีไม่เกิด" ว่า race condition | race condition ต้องมี **2 งานขึ้นไปแตะ state เดียวกัน และผลขึ้นกับลำดับเวลา** ถ้าอธิบายไม่ได้ว่าใครแข่งกับใคร อย่าใช้คำนี้ | "ผมสงสัยว่าเป็น race condition ระหว่าง request ที่ fetch ช้ากับที่ fetch เร็ว เพราะ response เก่ามาทับ state ใหม่" |
| Memory Leak | "app ใช้ RAM เยอะ = memory leak" | ใช้เยอะแต่คงที่ อาจเป็นแค่ใช้เยอะ leak คือ **โตขึ้นเรื่อย ๆ และไม่ลดลง** | "memory โตขึ้นทุกครั้งที่เปิด-ปิด modal และไม่ลดลงหลัง GC ผมเลยสงสัยว่ามี listener ไม่ถูก remove" |
| Refactoring | "ผม refactor เพิ่ม feature ใหม่" | refactor = behavior เหมือนเดิม ถ้าเพิ่ม feature คือ feature work | "ผม refactor ก่อนให้ code พร้อม แล้วค่อยเพิ่ม feature ใน PR แยก" |
| Legacy Code | ใช้ในความหมาย "code ขยะ" และตำหนิคนเขียนเดิม | legacy code มักเป็น code ที่ **ทำเงินให้บริษัทมานาน** การพูดดูถูกทำให้ดูทำงานกับคนอื่นยาก | "เป็น legacy module ที่ไม่มี test ผมเลยเริ่มจากเขียน characterization test ก่อนแก้" |
| Highly Available | อ้างว่า side project "highly available" | HA ต้องมี redundancy + failover จริง และมักมีตัวเลข uptime | "project นี้ deploy ตัวเดียว ยังไม่ได้ทำ HA แต่ถ้าจะทำ ผมจะเริ่มจากเพิ่ม instance และ DB replica" |
| Idempotent | "idempotent = ไม่มี side effect" | GET ไม่ควรมี side effect ส่วน DELETE มี side effect แต่ยัง idempotent (ลบซ้ำผลสุดท้ายเหมือนเดิม) | "DELETE เป็น idempotent เพราะเรียกซ้ำ resource ก็ยังถูกลบอยู่ แม้ response ครั้งที่สองอาจเป็น 404" |
| Stateless | "React component ไม่มี useState = stateless ระบบเลย stateless" | คำว่า stateless ในบริบท backend หมายถึง server ไม่เก็บ session ของ client ใน memory — คนละเรื่องกับ component | ระบุบริบทเสมอ: "API stateless" หรือ "component ที่ไม่มี local state" |
| Technical Debt | ใช้เป็นข้ออ้างของทุกอย่างที่ไม่ชอบ | tech debt คือทางลัดที่มี **ต้นทุนต่อเนื่อง** วัดได้ เช่นทำให้ทุก feature ช้าลง | "ส่วนนี้เป็น tech debt เพราะทุกครั้งที่เพิ่ม payment method ต้องแก้ 5 ไฟล์ ถ้ารวมเป็น strategy จะเหลือไฟล์เดียว" |
| Rollback | "rollback DB ได้ทุกเมื่อ" | code rollback ง่าย แต่ data/schema ที่เปลี่ยนไปแล้วอาจ rollback ไม่ได้ | "ผมทำ migration แบบ backward compatible ไว้ เพื่อให้ rollback code ได้โดยไม่ต้อง rollback schema" |
| Story Point | "1 point = 1 วัน" | point คือ relative size รวมความซับซ้อนและความไม่แน่นอน แต่ละทีมมี scale ของตัวเอง | "ทีมเราใช้ point เทียบกับงาน reference ไม่ได้แปลงเป็นชั่วโมงตรง ๆ" |
| Deployment | "deploy แล้ว = user เห็นแล้ว" | deploy ≠ release ถ้าใช้ feature flag, canary หรือ staged rollout | "deploy ขึ้น production แล้วแต่เปิด flag ให้ 10% ของ user ก่อน" |
| Trade-off | พูดคำว่า trade-off แต่บอกแค่ข้อดี | trade-off ต้องบอก **สิ่งที่เสีย** และเหตุผลที่ยอมเสีย | "เราได้ SEO จาก SSR แต่เสีย server cost เพิ่ม ยอมได้เพราะ traffic ส่วนใหญ่มาจาก search" |

### 8.2 ความผิดพลาดเชิงพฤติกรรม

- **พูดคำใหญ่ติดกันหลายคำในประโยคเดียว** — "ระบบเรา scalable, reliable, fault tolerant, highly available" ฟังเหมือนท่อง brochure คนสัมภาษณ์จะเลือกเจาะคำที่คุณอ่อนที่สุด
- **พูด "เรา" ตลอด** — ในเรื่อง incident/postmortem ให้แยกว่า "ทีมทำอะไร" และ "ผมทำส่วนไหน"
- **ใช้ศัพท์ภาษาอังกฤษกับ HR ที่ไม่ใช่ dev แบบไม่แปล** — ถ้าคนฟังเป็น HR ให้แปลเป็นผลกระทบทางธุรกิจ เช่น "downtime 20 นาที ลูกค้าจ่ายเงินไม่ได้"
- **โทษคนใน postmortem** — "เพราะ QA ไม่ test" ทำให้ดูไม่เข้าใจ blameless culture ให้พูดว่า "process เราไม่มีจุดที่จับเคสนี้ได้"
- **อ้างตัวเลขที่จำไม่ได้จริง** — ถ้าไม่แน่ใจให้พูดเป็นช่วงหรือบอกว่า "ประมาณ" ดีกว่าโดนถามต่อแล้วตัวเลขไม่ตรงกัน

## 9. Debugging

ในบริบทของ PART นี้ "debugging" คือ **การแก้ตอนคุณใช้ศัพท์แล้วคำตอบเริ่มพัง** หรือตอนได้ยินคำที่ไม่รู้จัก

### 9.1 เมื่อได้ยินศัพท์ที่ไม่แน่ใจ

```
ได้ยินคำที่ไม่แน่ใจ
      ↓
อย่าเดา → ถามกลับเพื่อ clarify
      ↓
"หมายถึง ... ในบริบทของ ... ใช่ไหมครับ"
      ↓
ถ้ายังไม่รู้ → บอกตรง ๆ + โยงกับสิ่งที่รู้
```

ให้มองภาพนี้ว่า การถามกลับไม่ได้ทำให้ดูอ่อน แต่การตอบผิดความหมายทั้งคำตอบทำให้ดูอ่อนกว่ามาก

ประโยคที่ใช้ได้:

- "ขอ clarify นิดหนึ่งครับ คำว่า consistency ตรงนี้หมายถึงแบบ database transaction หรือความสม่ำเสมอของ UI ครับ"
- "คำนี้ผมไม่เคยใช้ในงานจริงครับ แต่ถ้าหมายถึง ... ผมเคยทำสิ่งที่ใกล้เคียงคือ ..."

### 9.2 เมื่อพูดคำใหญ่ไปแล้วโดนเจาะ

ไล่ตามลำดับ:

1. **กลไก** — "มันเกิดขึ้นได้เพราะ ..." (อธิบาย mechanism)
2. **ตัวอย่าง** — "ในงานที่ทำ มันเกิดตอน ..."
3. **หลักฐาน** — "เรารู้เพราะ log/metric แสดงว่า ..."
4. **ขอบเขต** — "ส่วนที่ผมไม่ได้ทำเองคือ ... ทีม infra เป็นคนดูแล"

ถ้าตอบข้อ 1 ไม่ได้ ให้ถอยทันที: "ขอแก้คำนิดครับ จริง ๆ ที่ผมทำคือ ... ยังไม่ถึงขั้น ..." — การแก้คำพูดตัวเองอย่างซื่อตรงเป็นสัญญาณที่ดีในสายตา senior

### 9.3 เช็คลิสต์ก่อนสัมภาษณ์

| เช็ค | ทำอย่างไร |
|---|---|
| คำใหญ่ใน resume | ขีดเส้นใต้ทุกคำอย่าง scalable, high-performance, reliable แล้วเตรียมกลไก+หลักฐานของแต่ละคำ |
| เรื่องเล่า incident | เตรียม 1–2 เรื่อง เล่าตามวงจร: อาการ → หยุดเลือด → root cause → ป้องกัน |
| ตัวเลข | เขียนตัวเลขที่มั่นใจไว้ (ก่อน/หลัง latency, จำนวน user, ขนาดทีม) |
| คำคู่ที่สับสน | ท่อง Compare ในหัวข้อ 7 ให้แยกได้ทันที |
| ปรับภาษาตามคนฟัง | ซ้อมเล่าเรื่องเดียวกัน 2 เวอร์ชัน: ให้ dev ฟัง กับให้ HR ฟัง |

### 9.4 แปลศัพท์ให้ HR (ไม่ใช่ dev) ฟัง

| ศัพท์ | แปลเป็นภาษาธุรกิจ |
|---|---|
| Latency ลดลง | "หน้าเว็บตอบสนองเร็วขึ้น ลูกค้ารอน้อยลง" |
| Downtime | "ช่วงที่ลูกค้าใช้บริการไม่ได้" |
| Technical Debt | "ทางลัดที่ทำให้งานในอนาคตช้าลง ถ้าไม่เคลียร์" |
| Regression | "ของที่เคยใช้ได้ กลับพังหลังการอัปเดต" |
| Scalable | "รองรับลูกค้าที่เพิ่มขึ้นได้โดยไม่ต้องสร้างใหม่" |
| Postmortem | "การสรุปบทเรียนหลังเกิดปัญหา เพื่อไม่ให้เกิดซ้ำ" |

## 10. Interview Questions

### 🟢 Junior

1. Latency กับ throughput ต่างกันอย่างไร
2. Refactoring คืออะไร ต่างจากการแก้ bug อย่างไร
3. Regression คืออะไร ป้องกันได้อย่างไร
4. Code review มีไว้ทำไม คุณเคยได้ feedback อะไรที่จำได้
5. Technical debt คืออะไร ยกตัวอย่างที่เคยเจอ
6. ถ้าคุณติด blocker คุณจะทำอย่างไร
7. MVP คืออะไร

### 🟡 Mid

1. อธิบาย idempotent พร้อมตัวอย่าง API ที่ต้องระวัง
2. Race condition ที่เคยเจอหรือนึกออกในงาน frontend/backend มีอะไรบ้าง แก้อย่างไร
3. Hotfix กับ rollback ต่างกันอย่างไร เลือกอันไหนเมื่อไร
4. SLA กับ SLO ต่างกันอย่างไร ทำไมต้องตั้ง SLO สูงกว่า SLA
5. เล่า production issue ที่เคยเจอ ตั้งแต่อาการจนถึงป้องกัน
6. คุณจะทำ breaking change ใน API ที่มี client ใช้อยู่อย่างไร
7. คุณประเมิน story point อย่างไร ถ้าประเมินพลาดทำอย่างไร
8. Scope creep เกิดขึ้นกลาง sprint คุณจัดการอย่างไร

### 🔴 Senior

1. ออกแบบระบบให้ fault tolerant และ highly available ต่างกันอย่างไรในแง่การลงทุน
2. จะโน้มน้าว stakeholder ให้ให้เวลาจ่าย technical debt อย่างไร
3. Postmortem ที่ดีมีองค์ประกอบอะไร ทำไมต้อง blameless
4. จะวาง migration ที่ zero-downtime สำหรับการเปลี่ยน schema ที่ใช้อยู่จริงอย่างไร
5. ถ้าทีมเกิด incident ซ้ำเรื่องเดิมบ่อย ๆ คุณจะมองหาปัญหาที่ไหน
6. เคยตัดสินใจ trade-off ครั้งไหนที่ผลออกมาผิด เรียนรู้อะไร

## 11. Answer Like a Developer

### โครงตอบคำถามที่มีศัพท์ (Define → Why → Example → Trade-off)

```
1. Define   : นิยาม 1 ประโยคแบบภาษาคน
      ↓
2. Why      : ทำไมสำคัญในงานจริง
      ↓
3. Example  : ตอนไหนที่เคยเจอ/ทำ (มีตัวเลขยิ่งดี)
      ↓
4. Trade-off: ราคาที่ต้องจ่าย หรือข้อจำกัด
```

ให้มองภาพนี้ว่า ทุกคำตอบต้องเริ่มจากสิ่งที่คนฟังเข้าใจได้ทันที แล้วค่อยลงลึกถึงประสบการณ์ และจบด้วยการแสดงว่าคุณรู้ว่ามันไม่ฟรี

ตัวอย่าง: **"อธิบาย idempotent"**

- Define: "ทำซ้ำกี่ครั้ง ผลสุดท้ายเหมือนทำครั้งเดียว"
- Why: "เพราะ network ไม่เสถียร client จะ retry เสมอ ถ้าไม่ idempotent ก็เสี่ยงข้อมูลซ้ำ"
- Example: "endpoint ชำระเงินผมรับ idempotency key และเก็บผลของ key นั้นไว้"
- Trade-off: "ต้องเก็บ key และกำหนดอายุ เพิ่ม storage และความซับซ้อนนิดหน่อย"

### โครงเล่าเรื่องปัญหา (อาการ → หยุดเลือด → Root Cause → ป้องกัน)

| ขั้น | ต้องมีอะไร | ศัพท์ที่ใช้ได้ |
|---|---|---|
| อาการ | ใครกระทบ เท่าไร นานแค่ไหน | production issue, incident, downtime, latency |
| หยุดเลือด | ทำอะไรให้ user ใช้ได้ก่อน | rollback, hotfix, feature flag |
| Root Cause | สาเหตุจริงและหลักฐาน | root cause, race condition, memory leak, bottleneck |
| ป้องกัน | ทำอะไรไม่ให้เกิดซ้ำ | postmortem, regression test, alert, tech debt |

### โครงตอบคำถาม process จาก HR (สถานการณ์ → สิ่งที่ทำ → ผลลัพธ์กับคน)

- สถานการณ์: "มี requirement เพิ่มกลาง sprint"
- สิ่งที่ทำ: "ผมทำให้เห็น trade-off และให้ stakeholder เลือก"
- ผลลัพธ์กับคน: "ทีมไม่ต้อง OT และ PO รู้ล่วงหน้าว่าอะไรจะเลื่อน"

## 12. One-Minute Review

- ศัพท์ในห้องสัมภาษณ์มี 4 หมวด: **คุณภาพระบบ / ประสิทธิภาพ / ปัญหา & การแก้ / กระบวนการทำงาน**
- **Scalable ≠ เร็ว** — scalable คือรับโหลดเพิ่มได้เมื่อเพิ่ม resource, เร็วคือ latency ต่ำ
- **Latency** = งานเดียวใช้เวลาเท่าไร, **Throughput** = ต่อวินาทีทำได้กี่งาน
- **Idempotent** = ทำซ้ำผลเท่าเดิม สำคัญกับ retry และ payment
- **Race condition** ต้องอธิบายได้ว่าใครแข่งกับใคร แตะข้อมูลอะไร
- **Bug ≠ Incident** — incident คือกระทบ user/ธุรกิจจนต้องจัดการแบบเร่งด่วน
- Incident: **หยุดเลือดก่อน (rollback/hotfix) → root cause → postmortem แบบ blameless**
- **SLA** สัญญากับลูกค้า, **SLO** เป้าภายในที่ตั้งสูงกว่า, **Uptime** ตัวเลขที่วัดจริง
- เปลี่ยน API: **backward compatible → deprecated → migration → ค่อยทำ breaking change**
- **MVP** ถามว่า user อยากได้ไหม, **PoC** ถามว่าทำได้ไหม
- กฎทอง: **อย่าพูดคำที่อธิบายต่ออีก 2 ประโยคไม่ได้**

## 13. Memory Card

**จำ 5 อย่าง**

1. ทุกคำใหญ่ต้องตามด้วย **กลไก + หลักฐาน** ไม่อย่างนั้นอย่าพูด
2. **เร็ว (latency) ≠ รับได้เยอะ (throughput) ≠ ขยายได้ (scalable)**
3. ระบบพัง: **หยุดเลือด → หาสาเหตุ → ป้องกัน** ตามลำดับนี้เสมอ
4. เปลี่ยนของที่คนใช้อยู่: **สร้างสะพานใหม่ก่อน แล้วค่อยรื้อสะพานเก่า**
5. คุยกับ HR ให้ **แปลศัพท์เป็นผลกระทบต่อ user และธุรกิจ**

**Keyword:**

- Scalable → เพิ่ม resource แล้วรับโหลดเพิ่มได้
- Idempotent → ทำซ้ำผลเท่าเดิม
- Race Condition → ผลผิดเพราะลำดับเวลา
- Root Cause → สาเหตุจริง ไม่ใช่อาการ
- Rollback → กลับไปเวอร์ชันที่เคยใช้ได้
- Postmortem → สรุปบทเรียนแบบไม่หาคนผิด
- SLO → เป้าภายในที่ทำให้ทีมรู้ว่าเมื่อไรต้องหยุดทำ feature มาแก้ระบบ
- Trade-off → ได้อย่างเสียอย่าง ต้องบอกทั้งสองฝั่ง
- Breaking Change → ของเดิมพังถ้าไม่แก้ตาม
