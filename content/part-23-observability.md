# PART 23 — OBSERVABILITY

> ตำแหน่งในภาพใหญ่: Cross-Cutting Layer — ชั้นที่ทำให้เรา "มองเห็น" ว่าระบบที่รันอยู่จริงในโลกภายนอกกำลังทำอะไรอยู่

---

## 1. Big Picture

ลองนึกภาพนี้

สามทุ่มครึ่ง โทรศัพท์ดัง ลูกค้าบอกว่า **"จ่ายเงินไม่ได้"**

คุณเปิดคอมขึ้นมา เปิดเว็บตัวเอง กดสั่งของ → ผ่านปกติ
เปิด server ดู → CPU 30% ปกติดี
ลอง deploy ใหม่ → ก็ยังไม่รู้ว่าแก้อะไรไปบ้าง

**ปัญหาไม่ใช่ว่าระบบพัง ปัญหาคือเรามองไม่เห็นว่ามันพังตรงไหน**

ระบบที่รันอยู่ production มันเหมือน **กล่องทึบ** — ข้างในมีคำขอวิ่งเข้าออกวินาทีละหลายร้อยครั้ง
เราไม่ได้นั่งอยู่ในนั้น เราเห็นได้แค่ **สิ่งที่ระบบยอมพ่นออกมาให้เราเห็น**

```
[ผู้ใช้จริงหลายพันคน]
         ↓
   [ระบบของเรา]  ← กล่องทึบ เราไม่ได้นั่งดูอยู่ข้างใน
         ↓
   พ่นสัญญาณออกมา 3 อย่าง
         ↓
  ┌──────┬──────────┬────────┐
  │ LOGS │ METRICS  │ TRACES │
  └──────┴──────────┴────────┘
         ↓
   [DASHBOARD / ALERT]
         ↓
      [คนเรา]
         ↓
   ตัดสินใจว่าจะทำอะไรต่อ
```

> **ให้มองภาพนี้ว่า** "เรามองระบบไม่เห็นด้วยตาเปล่า เราเห็นได้เฉพาะร่องรอยที่ระบบตั้งใจทิ้งไว้ให้ ดังนั้นถ้าไม่ได้วางร่องรอยไว้ตั้งแต่ตอนเขียน ตอนพังก็จะไม่มีอะไรให้ดู"

**Observability → ความสามารถในการมองเห็นสภาพภายในของระบบจากสัญญาณที่มันส่งออกมา → มีไว้เพื่อให้เราตอบคำถามที่ "ยังไม่เคยเตรียมคำตอบไว้" ได้ ตอนระบบมีปัญหาจริง**

และประโยคที่ต้องจำไปห้องสัมภาษณ์:

> **"ระบบที่ debug ไม่ได้ ไม่ใช่ระบบที่เขียนเสร็จ"**

Junior มักคิดว่า observability คือ "งานหลังบ้านของ DevOps"
จริง ๆ แล้วมันคือ **ส่วนหนึ่งของ feature** — feature ที่ไม่มี log ที่มีประโยชน์ = feature ที่ยังไม่พร้อมขึ้น production

### ทำไมเรื่องนี้ถึงเป็นคำถามสัมภาษณ์ที่แยกระดับคนได้ชัด

| ระดับ | ตอบว่า |
|---|---|
| Junior | "ใส่ `console.log` ครับ" |
| Mid | "ใส่ structured log + request id แล้วดู error rate จาก dashboard" |
| Senior | "ผมดู golden signals ก่อนเพื่อยืนยันว่าผู้ใช้เจอจริง แล้วค่อยไล่ trace หา service ที่ช้า แล้วค่อยเปิด log ตาม trace id — และสิ่งที่สำคัญกว่าคือ alert เราผูกกับอาการของผู้ใช้หรือผูกกับ CPU" |

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| Observability | มองเห็นข้างในได้ | ความสามารถตอบคำถามใหม่จากสัญญาณที่ระบบพ่นออกมา |
| Monitoring | เฝ้าของที่รู้อยู่แล้ว | เฝ้าค่าที่เราตั้งไว้ล่วงหน้า แล้วเตือนเมื่อเกิน |
| Log | บันทึกเหตุการณ์ | ข้อความบอกว่า "ณ เวลานั้นเกิดอะไรขึ้น" |
| Structured Log | log เป็น JSON | log ที่ค้น/กรอง/นับได้ ไม่ใช่ข้อความเปล่า |
| Log Level | ระดับความสำคัญ | DEBUG / INFO / WARN / ERROR / FATAL |
| Metric | ตัวเลขตามเวลา | ค่าที่วัดซ้ำ ๆ เก็บเป็นกราฟ เช่น req/s, error rate |
| Counter | นับเพิ่มอย่างเดียว | จำนวนครั้งที่เกิดเหตุการณ์ เช่น จำนวน error |
| Gauge | ค่าขึ้นลงได้ | ค่าปัจจุบัน เช่น memory ที่ใช้ตอนนี้ |
| Histogram | กระจายของค่า | ใช้คำนวณ p50/p95/p99 ของ latency |
| Cardinality | จำนวนค่าที่เป็นไปได้ของ label | ถ้าสูงเกิน (เช่นใส่ user id) ระบบ metric จะระเบิด |
| Trace | เส้นทางของ 1 request | ภาพรวมว่า request เดินผ่าน service ไหนบ้าง ใช้เวลาเท่าไร |
| Span | 1 ช่วงงานใน trace | เช่น "query DB" 1 span, "เรียก payment" 1 span |
| Trace ID | เลขประจำ request ข้ามระบบ | ใช้ร้อย log ของทุก service เข้าด้วยกัน |
| Request ID / Correlation ID | เลขประจำคำขอ | เลขอ้างอิงที่ส่งกลับให้ผู้ใช้/support ใช้ตามเรื่อง |
| Context Propagation | ส่งต่อ id ไปกับ request | แนบ trace id ไปกับ header ทุก hop |
| APM | เครื่องมือรวมศูนย์ | Application Performance Monitoring — รวม metric+trace+error ในที่เดียว |
| Golden Signals | 4 สัญญาณหลัก | Latency, Traffic, Errors, Saturation |
| Latency | ช้าต่อคน | เวลาที่ 1 request ใช้ ดูเป็น percentile |
| Throughput / Traffic | รับได้กี่คน | จำนวน request ต่อวินาที |
| Error Rate | สัดส่วนพัง | error ÷ request ทั้งหมด (ดูเป็น % ไม่ใช่จำนวน) |
| Saturation | ความแน่น | ทรัพยากรเต็มแค่ไหน เช่น CPU, pool, queue depth |
| SLI | ตัวชี้วัดจริง | ค่าที่วัดได้จริง เช่น % ของ request ที่เร็วกว่า 1s |
| SLO | เป้าที่เราตั้งเอง | เช่น "99.9% ของ request ต้องเร็วกว่า 1s" |
| SLA | สัญญากับลูกค้า | ข้อตกลงที่มีบทลงโทษถ้าไม่ถึง |
| Error Budget | โควตาพังที่ยอมได้ | 100% − SLO เช่น SLO 99.9% → พังได้ 0.1% |
| Health Check | เช็กว่ายังไหวไหม | endpoint ที่บอกว่า instance นี้รับงานได้หรือยัง |
| Liveness | ยังไม่ตายใช่ไหม | ถ้าไม่ผ่าน → รีสตาร์ท |
| Readiness | พร้อมรับงานหรือยัง | ถ้าไม่ผ่าน → เอาออกจาก load balancer ชั่วคราว |
| Alert | สัญญาณเตือน | เงื่อนไขที่เมื่อเข้าเกณฑ์แล้วปลุกคน |
| Alert Fatigue | เตือนจนชิน | เตือนบ่อยเกินจนคนเลิกสนใจ = ไม่มี alert เลย |
| Incident | เหตุการณ์ที่กระทบผู้ใช้ | ไม่ใช่ทุก bug คือ incident — ต้องกระทบจริง |
| Severity (SEV) | ระดับความรุนแรง | SEV1 พังทั้งระบบ … SEV3 กระทบเล็กน้อย |
| MTTD / MTTR | เวลาตรวจเจอ / เวลาแก้จบ | ตัวชี้วัดคุณภาพของ observability และกระบวนการ |
| Postmortem | สรุปหลังเหตุการณ์ | เอกสารบันทึก timeline, impact, root cause, action item |
| Blameless | ไม่โทษคน | โทษระบบและกระบวนการที่ปล่อยให้คนพลาดได้ |
| Root Cause | ต้นเหตุจริง | สาเหตุที่ถ้าแก้แล้วเหตุนี้จะไม่เกิดซ้ำ |
| Action Item | สิ่งที่ต้องทำต่อ | มีเจ้าของ + มีกำหนดเวลา ไม่ใช่ "จะระวังมากขึ้น" |
| Sampling | เก็บบางส่วน | เก็บ trace/log แค่บางเปอร์เซ็นต์เพื่อลดค่าใช้จ่าย |
| Retention | เก็บนานแค่ไหน | log เก็บ 7 วัน / 30 วัน — เก็บนาน = จ่ายแพง |
| PII | ข้อมูลระบุตัวบุคคล | ชื่อ เบอร์ บัตรประชาชน อีเมล — **ห้ามลง log** |

## 3. Mental Model

### Mental Model #1 — สามเสาตอบคำถามคนละคำถาม

นี่คือแก่นของ chapter นี้ทั้งบท ถ้าจำได้อย่างเดียวให้จำอันนี้

| เสา | ตอบคำถามว่า | ลักษณะ | ราคา |
|---|---|---|---|
| **Metric** | "มีปัญหาไหม และเริ่มเมื่อไร" | ตัวเลขรวม กราฟ ดูย้อนหลังยาวได้ | ถูกที่สุด |
| **Trace** | "ปัญหาอยู่ตรงไหนของเส้นทาง" | เดินตาม request 1 ตัวข้าม service | ปานกลาง |
| **Log** | "แล้วทำไมมันถึงเป็นแบบนั้น" | รายละเอียดดิบ ณ จุดนั้น | แพงที่สุด |

```
[METRIC]  "error rate ของ /checkout พุ่งจาก 0.2% → 4% ตอน 20:14"
    ↓  รู้ว่ามีปัญหา + รู้ว่าเริ่มเมื่อไร แต่ยังไม่รู้ว่าที่ไหน
[TRACE]   "trace ที่ error ทุกตัวไปตายที่ span เรียก payment-service"
    ↓  รู้ว่าอยู่ตรงไหน แต่ยังไม่รู้ว่าเพราะอะไร
[LOG]     "payment-service log ว่า connection pool exhausted"
    ↓  รู้แล้วว่าทำไม
[ROOT CAUSE]
```

> **ให้มองภาพนี้ว่า** "Metric คือคนบอกว่ามีคนเจ็บ Trace คือคนบอกว่าเจ็บตรงไหนของร่างกาย และ Log คือผลตรวจที่บอกว่าเจ็บเพราะอะไร — ต้องใช้เรียงกันแบบนี้ ไม่ใช่กระโดดไปอ่าน log ตั้งแต่แรก"

**ทำไมห้ามเริ่มจาก log?** เพราะ log คือข้อมูลที่เยอะที่สุด ถ้าเปิดอ่านโดยไม่รู้ว่าจะหาอะไร คุณจะเจอข้อความหลายแสนบรรทัดที่ไม่เกี่ยวข้องเลย — การไล่จาก metric ลงมาคือการ **หดขอบเขตการค้นหา** ทีละชั้น

### Mental Model #2 — Monitoring คือคำถามที่เตรียมไว้ Observability คือคำถามที่ยังไม่เคยคิด

```
MONITORING     = "CPU เกิน 80% หรือยัง"        ← รู้คำถามล่วงหน้า (known unknowns)
OBSERVABILITY  = "ทำไมเฉพาะลูกค้าที่ใช้ iOS
                  ในไทยตอน 20:00 ถึง checkout ไม่ผ่าน"  ← คำถามที่ไม่มีใครเตรียมไว้
```

> **ให้มองภาพนี้ว่า** "Monitoring คือเครื่องวัดที่ติดตั้งไว้ล่วงหน้าตามจุดที่เราเดาว่าจะมีปัญหา ส่วน Observability คือการที่ข้อมูลของเราละเอียดพอจะตอบคำถามใหม่ที่เราไม่ได้เดาไว้ล่วงหน้า"

Monitoring ไม่ใช่ของเก่าที่ต้องเลิกใช้ — **Monitoring คือส่วนหนึ่งของ Observability** ถ้าระบบมี observability ดี คุณจะตั้ง monitoring ได้ตรงจุดมากขึ้น

### Mental Model #3 — Golden Signals: วัด 4 อย่างนี้ก่อนวัดอย่างอื่น

| สัญญาณ | คำถาม | ตัวอย่าง metric |
|---|---|---|
| **Latency** | ช้าไหม | p50 / p95 / p99 ของ response time (แยก success กับ error) |
| **Traffic** | คนเข้าเยอะไหม | req/s, active users, order/min |
| **Errors** | พังกี่ % | 5xx rate, exception rate, failed payment rate |
| **Saturation** | เต็มหรือยัง | CPU, memory, connection pool ที่ใช้, queue depth |

```
        ┌─ Latency     → ผู้ใช้รอนานไหม
Service ├─ Traffic     → มีงานเข้ามาเท่าไร
        ├─ Errors      → ล้มเหลวกี่ %
        └─ Saturation  → ทรัพยากรใกล้เต็มหรือยัง
```

> **ให้มองภาพนี้ว่า** "4 ตัวนี้คือสัญญาณชีพของระบบ เหมือนหมอวัดชีพจร ความดัน อุณหภูมิ และการหายใจก่อนจะสั่งตรวจอย่างอื่น"

**เคล็ดที่ Senior ใช้จริง:** เวลาดู latency ให้แยกกราฟของ request ที่สำเร็จออกจาก request ที่ error เสมอ เพราะ error ที่ตอบกลับเร็วมาก (เช่น 400 ทันที) จะไปดึงค่าเฉลี่ยลง ทำให้กราฟดู "ดีขึ้น" ตอนระบบพัง ซึ่งหลอกมาก

### Mental Model #4 — SLI → SLO → Error Budget → Alert

```
SLI  (วัดได้จริง)     "99.95% ของ request เร็วกว่า 1 วินาที"
  ↓
SLO  (เป้าที่ตั้ง)     "ต้อง ≥ 99.9%"
  ↓
Error Budget         "พังได้ 0.1% ของเดือน ≈ 43 นาที"
  ↓
Alert                "ถ้าเผา budget เร็วผิดปกติ → ปลุกคน"
```

> **ให้มองภาพนี้ว่า** "เราไม่ได้ตั้งเป้าให้ระบบไม่พังเลย เพราะทำไม่ได้และแพงเกินไป เราตั้งงบว่าพังได้เท่าไร แล้วเตือนเมื่อจะใช้งบหมดเร็วผิดปกติ"

นี่คือเหตุผลที่ระดับ Senior ตอบคำถาม "alert ที่ดีคืออะไร" ได้ต่างจาก Junior — Junior ตอบว่า "CPU > 80%" ส่วน Senior ตอบว่า **"เมื่อผู้ใช้กำลังเจ็บ และเจ็บเร็วพอที่จะกินงบที่เราตกลงไว้"**

### Mental Model #5 — Observability เริ่มที่ตอนเขียน ไม่ใช่ตอนพัง

```
ตอนเขียน code      → ตัดสินใจว่าจะทิ้งร่องรอยอะไรไว้
        ↓
ตอนขึ้น production → ระบบพ่นร่องรอยออกมา
        ↓
ตอนพัง             → เราอ่านได้เฉพาะร่องรอยที่เคยทิ้งไว้เท่านั้น
```

> **ให้มองภาพนี้ว่า** "ตอนพังคือตอนอ่านผลสอบ ไม่ใช่ตอนเตรียมตัวสอบ — สิ่งที่คุณไม่ได้ log ไว้ ตอนนั้นย้อนกลับไปเอาไม่ได้แล้ว"

## 4. ภาพจำ

```
🧠 ภาพจำหลัก: ระบบ = คนไข้ / เรา = หมอ

METRIC = สัญญาณชีพ (ชีพจร ความดัน)  → "มีอะไรผิดปกติไหม"
TRACE  = ใบส่งตัวข้ามแผนก             → "ไปช้าอยู่แผนกไหน"
LOG    = บันทึกของแพทย์                → "เกิดอะไรขึ้นจริง ๆ"

Metric → Trace → Log
(กว้าง → แคบ → ละเอียด)
```

```
🧠 ภาพจำ Trace ID:

Trace ID = เลขพัสดุ

พัสดุ 1 ชิ้นเดินทางผ่าน
[ศูนย์คัดแยก] → [รถขนส่ง] → [ศูนย์ปลายทาง] → [คนส่ง]

ทุกจุดสแกนเลขเดียวกัน
เลยตามได้ว่า "ตกค้างอยู่จุดไหน"

ถ้าไม่มีเลขพัสดุ = ต้องไปถามทุกศูนย์ว่าเห็นกล่องสีน้ำตาลไหม
```

> **ให้มองภาพนี้ว่า** "Trace ID คือสิ่งที่เปลี่ยนคำถาม 'ใครเห็น request นี้บ้าง' ให้กลายเป็นการค้นครั้งเดียวจบ"

```
🧠 ภาพจำ Log Level:

DEBUG = โน้ตในสมุดตัวเอง       (เยอะมาก เปิดเฉพาะตอนสืบ)
INFO  = บันทึกประจำวันของร้าน   (เหตุการณ์สำคัญของ business)
WARN  = ไฟเหลือง               (ยังไม่พัง แต่ผิดปกติ)
ERROR = ไฟแดง                  (งานนี้ล้มเหลว มีคนเจ็บ)
FATAL = ไฟไหม้โรงงาน           (ทั้ง process ไปต่อไม่ได้)
```

```
🧠 ภาพจำ Alert ที่ดี vs Alert ที่แย่:

แย่ : "CPU 85%"         → แล้วไง? ลูกค้าเดือดร้อนหรือยัง
ดี  : "checkout ล้มเหลว 5% ติดต่อกัน 5 นาที" → มีคนซื้อของไม่ได้จริง

กฎ: Alert ที่อาการ (symptom) ไม่ใช่ที่สาเหตุ (cause)
```

```
🧠 ภาพจำ Health Check:

Liveness  = "ยังหายใจอยู่ไหม"     → ไม่ผ่าน = เรียกรถพยาบาล (restart)
Readiness = "พร้อมลงสนามหรือยัง"  → ไม่ผ่าน = นั่งข้างสนามก่อน (เอาออกจาก LB)
```

> **ให้มองภาพนี้ว่า** "Liveness ตอบว่าควรฆ่าทิ้งแล้วเกิดใหม่ไหม ส่วน Readiness ตอบว่าควรส่งงานให้ตอนนี้ไหม — สองคำถามนี้คนละคำถาม เลยต้องเป็นคนละ endpoint"

```
🧠 ภาพจำ Postmortem แบบ Blameless:

ไม่ใช่: "ใครกด deploy"
แต่คือ: "ทำไมระบบเราปล่อยให้การกดครั้งเดียวทำให้ทั้งระบบล่มได้"

คน = ตัวชี้ให้เห็นรูของระบบ
ไม่ใช่ = สาเหตุของรู
```

## 5. How It Works

### 5.1 ภาพรวม Pipeline ของสัญญาณทั้ง 3 เสา

```
                    [APPLICATION CODE]
                            ↓
        ┌───────────────────┼───────────────────┐
        ↓                   ↓                   ↓
   log.info(...)      counter++/timer      span.start/end
        ↓                   ↓                   ↓
   [stdout/agent]     [metric endpoint]    [trace exporter]
        ↓                   ↓                   ↓
   [Log Collector]    [Metric Scraper]     [Trace Collector]
        ↓                   ↓                   ↓
   [Log Storage]      [Time-Series DB]     [Trace Storage]
        ↓                   ↓                   ↓
   ค้นด้วย query       กราฟ + Alert         ดู waterfall
        └───────────────────┴───────────────────┘
                            ↓
                    [DASHBOARD / APM]
                            ↓
                         [คนเรา]
```

> **ให้มองภาพนี้ว่า** "แอปแค่พ่นข้อมูลออกมาอย่างเดียว ไม่ได้เก็บเอง — มีระบบข้างนอกคอยเก็บ จัดเรียง และทำให้ค้นได้ ดังนั้นสิ่งที่แอปพ่นต้องอยู่ในรูปที่เครื่องอ่านต่อได้"

**ทำไม app ไม่ควรเขียน log ลงไฟล์เองใน production ยุค container?** เพราะ container มีอายุสั้น ตายแล้วไฟล์หายไปพร้อมกัน — วิธีมาตรฐานคือพ่นออก stdout แล้วให้ตัวเก็บ log นอก container รับไปเก็บที่ปลอดภัย

### 5.2 Logs — จาก `console.log` ไปเป็น Structured Log

**ปัญหาของ log แบบข้อความเปล่า:**

```
Error: payment failed
Error: payment failed
User not found
timeout
```

อ่านแล้วตอบไม่ได้เลยว่า ของใคร ตอนไหน order ไหน เกิดที่ service ไหน และนับไม่ได้ว่าเกิดกี่ครั้ง

**Structured Log = log ที่เป็น key-value (ปกติคือ JSON)**

```
{"ts":"...","level":"error","msg":"payment_failed",
 "trace_id":"a1b2c3","order_id":"ORD-889","user_ref":"u_1042",
 "provider":"omise","duration_ms":3021,"reason":"upstream_timeout"}
```

> **ให้มองภาพนี้ว่า** "Structured log คือการเปลี่ยน log จากเรื่องเล่าที่มนุษย์อ่าน ให้กลายเป็นข้อมูลที่เครื่องกรองและนับได้ เช่น 'ขอ error ทั้งหมดของ provider=omise ในช่วง 20 นาทีนี้'"

**ของที่ควรมีในทุกบรรทัด log (จำเป็น checklist นี้ไปสัมภาษณ์ได้เลย):**

| ฟิลด์ | ทำไมต้องมี |
|---|---|
| `timestamp` | เรียงลำดับเหตุการณ์ข้าม service ได้ (ควรเป็น UTC) |
| `level` | กรองเฉพาะ error ตอนไฟไหม้ |
| `service` / `env` | รู้ว่ามาจากตัวไหน และเป็น prod หรือ staging |
| `trace_id` / `request_id` | ร้อยเรื่องเดียวกันข้ามหลาย service |
| `event name` แบบคงที่ | `payment_failed` นับได้ ส่วน "จ่ายเงินไม่ผ่านของคุณสมชาย" นับไม่ได้ |
| `duration_ms` | บอกว่าขั้นตอนนี้กินเวลาเท่าไร |
| `reason` / `error_code` | บอกสาเหตุแบบที่จัดกลุ่มได้ |

**Log Level ใช้ยังไงให้ถูก**

| Level | ใช้เมื่อ | ตัวอย่าง | ควรมี alert ไหม |
|---|---|---|---|
| DEBUG | ตอนสืบปัญหาเท่านั้น | ค่าตัวแปรระหว่างทาง | ไม่ |
| INFO | เหตุการณ์สำคัญของธุรกิจ | `order_created`, `user_logged_in` | ไม่ |
| WARN | ผิดปกติแต่ยังไปต่อได้ | retry ครั้งที่ 2 สำเร็จ | อาจดูแนวโน้ม |
| ERROR | งานนี้ล้มเหลว มีคนได้รับผลกระทบ | จ่ายเงินไม่สำเร็จ | ใช่ (ดูเป็น rate) |
| FATAL | process ไปต่อไม่ได้ | ต่อ DB ไม่ได้ตอน start | ใช่ ทันที |

> ⚠️ **กฎเหล็กของ log level:** ถ้าทุกอย่างเป็น ERROR แปลว่าไม่มีอะไรเป็น ERROR — ทีมจะเลิกดู

### 5.3 🔴 คำเตือนที่สำคัญที่สุดของ chapter นี้ — ห้าม log ของพวกนี้

```
❌ ห้ามลง log เด็ดขาด
   ├── รหัสผ่าน (password ทั้งแบบดิบและแบบ hash)
   ├── Token / JWT / API Key / Secret / Refresh Token
   ├── Cookie / Session ID / Authorization header เต็ม ๆ
   ├── เลขบัตรเครดิต / CVV / เลขบัญชี
   ├── เลขบัตรประชาชน / passport
   ├── ชื่อ-นามสกุล เบอร์โทร อีเมล ที่อยู่ (PII)
   └── request body / response body ทั้งก้อนแบบไม่กรอง
```

> **ให้มองภาพนี้ว่า** "log คือข้อมูลที่ถูกส่งออกนอกระบบ ถูกเก็บไว้หลายวัน และมีคนเข้าถึงได้มากกว่าฐานข้อมูลเสมอ — อะไรที่ลง log แล้วเท่ากับหลุดออกจากกำแพงความปลอดภัยชั้นในไปแล้ว"

**เหตุผลที่ต้องเข้มขนาดนี้ (พูดในห้องสัมภาษณ์ได้):**

1. log ถูกเก็บในระบบกลาง ทีม support / analytics / vendor ก็เห็นได้
2. log ถูก backup และเก็บนานกว่าที่คิด ลบยาก
3. token ที่หลุดใน log = ล็อกอินแทนผู้ใช้ได้จริงจนกว่าจะหมดอายุ
4. PII ที่หลุด = เรื่องกฎหมาย (เช่น PDPA / GDPR) ไม่ใช่แค่เรื่องเทคนิค

**วิธีที่ถูกต้อง — log "ตัวอ้างอิง" ไม่ใช่ "ตัวข้อมูล"**

| แทนที่จะ log | ให้ log แบบนี้ |
|---|---|
| `email: somchai@mail.com` | `user_id: u_1042` |
| `card: 4111 1111 1111 1111` | `card_last4: 1111`, `card_brand: visa` |
| `Authorization: Bearer eyJ...` | `auth: present`, `token_exp: ...` |
| `password: 123456` | ไม่ต้อง log อะไรเลยเกี่ยวกับ field นี้ |
| body ทั้งก้อน | เฉพาะ field ที่จำเป็น + ผ่าน redact list |

**pseudocode สั้น ๆ ของ redaction (แนวคิด ไม่ใช่ syntax ที่ต้องท่อง):**

```
REDACT = ["password","token","authorization","card","citizen_id"]
log(obj) → แทนค่าทุก key ที่อยู่ใน REDACT ด้วย "[REDACTED]" ก่อนเขียนออก
```

อธิบาย: ทำที่ชั้น logger กลางที่เดียว ไม่ใช่ไปไล่แก้ทุกจุดที่เรียก log เพราะจุดที่ลืมคือจุดที่หลุด

### 5.4 Metrics — ตัวเลขตามเวลา

**Log บอกเหตุการณ์เดี่ยว Metric บอกภาพรวม**

```
1 request ที่ error   → LOG   (รายละเอียดครบ แต่เห็นแค่ 1 ตัว)
error 4% ของทั้งหมด   → METRIC (ไม่มีรายละเอียด แต่เห็นทั้งระบบ)
```

**3 ชนิดของ metric ที่ต้องแยกให้ออก**

| ชนิด | พฤติกรรม | ตัวอย่าง | คำถามที่ตอบได้ |
|---|---|---|---|
| Counter | ขึ้นอย่างเดียว | `http_requests_total` | "เกิดไปทั้งหมดกี่ครั้ง / ต่อวินาทีเท่าไร" |
| Gauge | ขึ้นลงได้ | `memory_used_bytes`, `queue_depth` | "ตอนนี้เท่าไร" |
| Histogram | เก็บการกระจาย | `request_duration_ms` | "p95 เท่าไร" |

> ⚠️ **Latency ต้องเป็น Histogram เท่านั้น** ถ้าเก็บเป็น gauge แบบ "ค่าเฉลี่ย" คุณจะคำนวณ p95/p99 ย้อนหลังไม่ได้เลย และค่าเฉลี่ยก็หลอกอยู่แล้ว (ดู PART 22)

**Cardinality — กับดักที่ทำ metric ระบบล่มได้จริง**

```
ดี  : http_requests_total{route="/orders/:id", status="500"}
       → ค่าที่เป็นไปได้ไม่กี่สิบ

พัง : http_requests_total{url="/orders/88213", user_id="u_1042"}
       → ค่าที่เป็นไปได้ = จำนวน order × จำนวน user = ล้าน ๆ series
```

> **ให้มองภาพนี้ว่า** "label ของ metric คือช่องในตู้เก็บเอกสาร ถ้าใส่ user id เป็นชื่อช่อง คุณกำลังสร้างตู้ที่มีลิ้นชักเป็นล้านช่อง — ระบบเก็บ metric จะพังก่อนระบบจริงของคุณ"

**กฎง่าย ๆ:** id ของแต่ละคน/แต่ละรายการ → ใส่ใน **log** หรือ **trace** ไม่ใช่ **metric label**

### 5.5 Tracing — ตามรอย 1 request ข้ามหลาย service

ในระบบ service เดียว การอ่าน log ตามเวลายังพอไหว
แต่พอมี 5 service คำถามง่าย ๆ ว่า "คำสั่งซื้อนี้ไปตายตรงไหน" จะกลายเป็นฝันร้ายทันที ถ้าไม่มี trace

```
[Client]
   │  X-Request-Id: req-77  (ถ้าไม่มี gateway จะสร้างให้)
   ↓
[API Gateway]      trace_id = T-9f3  span A (120ms)
   ↓  ส่ง trace_id ไปกับ header
[Order Service]                      span B (95ms)
   ↓
[Payment Service]                    span C (3021ms) ← ช้าตรงนี้
   ↓
[Bank API (external)]                span D (3000ms) ← ต้นตอจริง
```

> **ให้มองภาพนี้ว่า** "Trace คือการติดกล้องไว้กับ request หนึ่งตัว แล้วดูภาพย้อนหลังว่ามันไปยืนรออยู่หน้าประตูบานไหนนานที่สุด"

**Trace Waterfall — สิ่งที่คุณเห็นจริงใน APM**

```
T-9f3 (total 3260ms)
├── gateway.handle          ▇                        120ms
├── order.create            ▇▇                        95ms
│   └── db.insert           ▇                         14ms
├── payment.charge          ▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇     3021ms  ← span ที่กินเวลา
│   └── http.bank_api       ▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇      3000ms
└── notify.push             ▇                         24ms
```

> **ให้มองภาพนี้ว่า** "แถบยาวที่สุดคือที่ที่เวลาหายไป — trace เปลี่ยนคำถาม 'ทำไมช้า' ให้เหลือแค่การมองหาแถบยาวที่สุดในภาพ"

**Context Propagation — หัวใจที่ทำให้ trace ทำงานได้**

```
Service A  ──[header: traceparent / X-Trace-Id]──▶  Service B
Service B  ──[ส่งต่อ header เดิม]──▶  Service C
```

> **ให้มองภาพนี้ว่า** "trace id เหมือนสายรัดข้อมือคนไข้ ทุกแผนกที่รับตัวไปต้องไม่ถอดออก — service ไหนลืมส่งต่อ header เส้นทางจะขาดตรงนั้นทันที"

**จุดที่ trace มักขาดในงานจริง (ข้อนี้ตอบได้ = ดูมีประสบการณ์มาก):**

- ผ่าน **message queue** แล้วไม่ได้ใส่ trace id ลงใน message header
- งาน **background job / cron** ที่ไม่ได้เริ่ม trace ใหม่และไม่ผูกกับ trace เดิม
- เรียก third-party แล้วไม่ได้สร้าง span ครอบ → เห็นแค่ "ช้า" แต่ไม่รู้ว่าช้าที่ปลายทาง
- ฝั่ง frontend ไม่ได้ส่ง request id มา → ตามจาก user ย้อนเข้าไปไม่ได้

### 5.6 Request ID กับ Trace ID ต่างกันยังไง (คำถามสัมภาษณ์บ่อย)

```
Request ID  = เลขของ "คำขอ 1 ครั้งที่ระบบเรารับ"   (เอาไว้คุยกับลูกค้า/support)
Trace ID    = เลขของ "เส้นทางทั้งหมดที่คำขอนั้นเดิน" (เอาไว้ร้อย service)
Span ID     = เลขของ "ช่วงงานย่อย 1 ช่วงใน trace"   (เอาไว้ชี้จุดในเส้นทาง)
```

ในงานจริงหลายทีมทำให้ request id = trace id ไปเลยเพื่อความง่าย และส่งค่านี้กลับไปในหน้า error ให้ผู้ใช้เห็น

```
หน้าจอผู้ใช้:  "เกิดข้อผิดพลาด กรุณาแจ้งรหัสนี้: T-9f3a21"
        ↓ ลูกค้าแจ้ง support
Support ค้น trace id เดียว → เห็นทั้งเส้นทาง + log ทุก service ของ request นั้น
```

> **ให้มองภาพนี้ว่า** "การโชว์ trace id บนหน้าจอ error คือการเปลี่ยนคำบ่นลอย ๆ ของลูกค้าให้กลายเป็นหลักฐานที่ค้นได้ในระบบภายใน 10 วินาที"

### 5.7 Health Check — Liveness vs Readiness

```
[Load Balancer / Kubernetes]
        │
        ├── GET /health/live   → "process ยังไม่ค้างใช่ไหม"   → fail = restart pod
        └── GET /health/ready  → "ต่อ DB/cache ได้ พร้อมรับงาน" → fail = ถอดออกจาก LB
```

> **ให้มองภาพนี้ว่า** "Liveness ตอบว่าควรฆ่าทิ้งไหม Readiness ตอบว่าควรส่งงานให้ตอนนี้ไหม — ถ้าเอาสองอันนี้รวมกัน พอ DB สะดุดแป๊บเดียวระบบจะรีสตาร์ททุก pod พร้อมกันจนล่มทั้งระบบ"

**กับดักที่เจอจริง:**

| ทำแบบนี้ | เกิดอะไรขึ้น |
|---|---|
| `/health` ตอบ 200 เสมอ ไม่เช็กอะไร | LB ส่งงานให้เครื่องที่ต่อ DB ไม่ได้ → ผู้ใช้เจอ error แต่ dashboard เขียว |
| Liveness ไปเช็ก DB ด้วย | DB ช้า 30 วินาที → pod ทุกตัวถูก restart พร้อมกัน → ล่มหนักกว่าเดิม |
| Readiness หนักเกิน (ยิง query จริง) | health check เองกลายเป็นภาระของ DB |

---

### 5.8 Alert — เตือนที่อาการ ไม่ใช่ที่สาเหตุ

```
❌ Alert แบบ cause-based
   CPU > 80%  → ปลุกตี 3 → ไปดู → เป็น batch job ปกติ → ไม่มีใครเดือดร้อน

✅ Alert แบบ symptom-based
   checkout error rate > 2% นาน 5 นาที → มีคนซื้อของไม่ได้จริง
```

> **ให้มองภาพนี้ว่า** "อย่าปลุกคนเพราะเครื่องร้อน ให้ปลุกเพราะลูกค้ากำลังเจ็บ — CPU สูงเป็นข้อมูลไว้สืบหลังจากถูกปลุก ไม่ใช่เหตุผลที่จะปลุก"

**เกณฑ์ alert ที่ดี 5 ข้อ**

| เกณฑ์ | ความหมาย |
|---|---|
| ผูกกับผู้ใช้ | ถ้าไม่มีใครเดือดร้อน ไม่ควรปลุกคน |
| ทำอะไรต่อได้ | alert ต้องมี action ไม่ใช่แค่แจ้งให้รู้ |
| มี runbook | บอกว่าตื่นมาแล้วให้ดูอะไรก่อน |
| ไม่เด้งบ่อยเกิน | เด้งวันละสิบครั้งจนชิน = เท่ากับไม่มี alert (alert fatigue) |
| มีระยะเวลา (for 5m) | กัน spike ชั่วขณะที่หายเองไม่ต้องปลุกใคร |

**ตารางแยกว่าอะไรควร "ปลุก" อะไรควร "แค่แจ้ง"**

| สถานการณ์ | ระดับ |
|---|---|
| ระบบชำระเงินล้มเหลว > 2% | 📟 ปลุกทันที (page) |
| ทั้งเว็บตอบ 5xx | 📟 ปลุกทันที |
| p95 latency เกิน SLO ต่อเนื่อง 15 นาที | 📟 ปลุก |
| disk เหลือ 15% | 💬 แจ้งใน channel (ยังมีเวลา) |
| error rate ของ feature ที่ยังไม่เปิดใช้ | 💬 แจ้ง |
| CPU 85% แต่ latency ปกติ | 📊 ดูเป็นกราฟ ไม่ต้อง alert |

### 5.9 Incident Flow — ตั้งแต่เด้งจนถึงปิดเคส

```
[DETECT]     alert เด้ง / ลูกค้าแจ้ง
   ↓
[TRIAGE]     กระทบใคร กี่ % รุนแรงแค่ไหน (SEV?)
   ↓
[COMMS]      ตั้งห้องคุย + แจ้งผู้เกี่ยวข้อง + ตั้ง incident commander
   ↓
[MITIGATE]   หยุดเลือดก่อน (rollback / ปิด feature flag / ลด traffic)
   ↓
[FIX]        แก้ที่ต้นเหตุ
   ↓
[VERIFY]     ยืนยันจาก metric ว่าผู้ใช้กลับมาปกติจริง
   ↓
[POSTMORTEM] เขียนสรุปแบบ blameless ภายใน 1–3 วัน
```

> **ให้มองภาพนี้ว่า** "ตอนเกิดเหตุ หน้าที่แรกคือหยุดเลือด ไม่ใช่หาสาเหตุ — การหาสาเหตุทำทีหลังได้ แต่ผู้ใช้ที่ใช้งานไม่ได้อยู่ตอนนี้รอไม่ได้"

**สิ่งที่ Junior มักทำผิดตอน incident:** พยายามหา root cause ให้เจอก่อนแล้วค่อยแก้ ทั้งที่ควร **rollback ก่อน** แล้วค่อยนั่งหาสาเหตุอย่างสบายใจจาก log ที่เก็บไว้

---

### 5.10 Postmortem แบบ Blameless — โครงที่ใช้ได้จริง

```
1. TITLE + วันที่ + ระดับความรุนแรง
2. IMPACT      ใครเจ็บ กี่คน กี่นาที เสียอะไรไปบ้าง (ตัวเลข ไม่ใช่ความรู้สึก)
3. TIMELINE    เวลา → เกิดอะไร → ใครทำอะไร (ตามจริง ไม่ตัดสิน)
4. DETECTION   รู้ได้ยังไง ใช้เวลานานแค่ไหนกว่าจะรู้ (MTTD)
5. ROOT CAUSE  สาเหตุจริง (ถาม "ทำไม" ต่ออีกชั้นเสมอ)
6. WHAT WENT WELL     อะไรช่วยให้รอด
7. WHAT WENT WRONG    อะไรทำให้ช้า/แย่ลง
8. ACTION ITEMS       ทำอะไร / ใครรับผิดชอบ / ภายในเมื่อไร
```

> **ให้มองภาพนี้ว่า** "Postmortem ไม่ใช่ศาล แต่เป็นแผนที่ว่าระบบเรามีรูตรงไหน — ถ้าใครกลัวโดนลงโทษ เขาจะไม่เล่าความจริง แล้วเราจะไม่มีวันเห็นรูนั้น"

**Blameless แปลว่าอะไรกันแน่**

| ❌ แบบโทษคน | ✅ แบบ blameless |
|---|---|
| "สมชาย deploy วันศุกร์ตอนเย็น" | "เราไม่มี guard ที่ห้าม deploy นอกเวลาทำการ" |
| "ลืมใส่ index" | "เราไม่มีขั้นตอน review query plan ก่อนขึ้น prod" |
| "น้องใหม่ลบข้อมูลผิด" | "คำสั่งลบบน prod ทำได้โดยไม่ต้องมีคนที่สองยืนยัน" |
| Action: "จะระวังมากขึ้น" | Action: "เพิ่ม dry-run + confirmation ภายใน 2 สัปดาห์ (เจ้าของ: ทีม platform)" |

> **จำประโยคนี้:** "คนไม่ใช่ root cause — คนคือจุดที่ทำให้เราเห็นว่าระบบยอมให้ความผิดพลาดนั้นเกิดขึ้นได้"

**เกณฑ์ตรวจว่า action item ใช้ได้จริงไหม:** ต้องมี **เจ้าของ + กำหนดเวลา + วัดผลได้** ถ้าเขียนว่า "จะระมัดระวังขึ้น" หรือ "จะสื่อสารให้ดีขึ้น" นั่นไม่ใช่ action item แต่เป็นความรู้สึก

## 6. Example

### Example 1 — Error rate ของ /checkout พุ่งตอนสองทุ่ม

**สถานการณ์:** ระบบสั่งอาหาร alert เด้งว่า `checkout_error_rate > 2% for 5m` ตอน 20:14

**สิ่งที่ทำ ไล่ตาม 3 เสา**

```
[1] METRIC — เปิด dashboard
    error rate: 0.2% → 4.1% ตอน 20:14 (ขึ้นแบบหักศอก)
    traffic: ปกติ ไม่มี spike
    latency p95: 900ms → 3.4s
    → สรุป: ไม่ใช่คนเยอะ แต่มีอะไรช้าและพัง
```

```
[2] เช็ก "เปลี่ยนอะไรไป"
    deploy ล่าสุด 19:50  ← ใกล้เคียงเวลามาก แต่ยังไม่ฟันธง
    feature flag: ไม่มีการเปิดใหม่
```

```
[3] TRACE — กรอง trace ที่ status=error ช่วง 20:14–20:20
    ทุก trace ไปตายที่ span เดียวกัน: payment.charge → http.bank_api
    span นั้นใช้เวลา ~3000ms แล้วจบด้วย timeout
```

```
[4] LOG — ค้นด้วย trace id ของ trace ตัวอย่าง
    {"level":"error","msg":"payment_failed","reason":"upstream_timeout",
     "provider":"bank_x","duration_ms":3002,"trace_id":"T-9f3"}
    และพบ log อีกชุด: "retry attempt 3" ถี่มาก
```

```
[5] ROOT CAUSE
    ธนาคารปลายทางช้าลง (ไม่ใช่ความผิดเรา)
    + deploy 19:50 เปลี่ยน retry จาก 1 ครั้ง เป็น 3 ครั้งแบบไม่มี backoff
    → เรายิงซ้ำใส่ระบบที่ช้าอยู่แล้ว ทำให้ตัวเองแย่ลงและ pool เต็ม
```

```
[6] MITIGATE ก่อน FIX
    20:31 rollback retry config → error rate ลงเหลือ 0.6% ใน 4 นาที
    (ยังไม่ปกติ 100% เพราะธนาคารยังช้า แต่ผู้ใช้ส่วนใหญ่ผ่านแล้ว)
```

> **ให้มองภาพนี้ว่า** "การไล่จาก metric → trace → log ทำให้เราหดพื้นที่ค้นหาจาก 'ทั้งระบบ' เหลือ 'บรรทัดเดียว' ภายในไม่กี่นาที โดยไม่ต้องเดาเลยสักครั้ง"

**ตัวอย่าง Postmortem ที่เขียนจากเคสนี้ (ย่อ)**

| หัวข้อ | เนื้อหา |
|---|---|
| Impact | ผู้ใช้ 3,100 คนชำระเงินไม่สำเร็จ เป็นเวลา 17 นาที ยอดขายหาย ~X บาท |
| Detection | alert symptom-based เด้งใน 1 นาทีหลังเริ่ม (MTTD 1 นาที) |
| Timeline | 20:14 เริ่ม / 20:15 alert / 20:22 ระบุ span / 20:31 rollback / 20:35 ปกติ |
| Root Cause | retry 3 ครั้งแบบไม่มี backoff ทำให้ภาระซ้ำเติม upstream ที่ช้าอยู่แล้ว |
| What went well | มี trace ครบทุก hop จึงชี้จุดได้ใน 8 นาที |
| What went wrong | ไม่มี circuit breaker, retry ไม่มี jitter, ไม่มี alert ที่ dependency ภายนอก |
| Action Items | 1) ใส่ exponential backoff + jitter (ทีม payment, 1 สัปดาห์) 2) เพิ่ม circuit breaker (2 สัปดาห์) 3) เพิ่ม dashboard latency ของ provider ภายนอก (3 วัน) |

**ข้อสังเกตสำคัญ:** ไม่มีบรรทัดไหนเขียนว่า "ใครเป็นคน deploy" — เพราะไม่เกี่ยว สิ่งที่เกี่ยวคือ **ระบบยอมให้ config แบบนี้ขึ้น prod ได้โดยไม่มีใครเห็นผลกระทบ**

### Example 2 — ลูกค้าคนเดียวบอกว่า "โอนเงินแล้วยอดไม่ขึ้น"

เคสนี้ยากกว่าเคสแรก เพราะ **metric ปกติหมด** (มีคนเจ็บแค่ 1 คนจากหลายหมื่น)

```
[1] ขอ "รหัสอ้างอิง" จากหน้าจอ error ที่ลูกค้าเห็น → T-4b81
[2] ค้น trace id นั้นตัวเดียว → เห็นครบว่า request เดินผ่าน 4 service
[3] พบว่า wallet-service ตอบ 200 แต่ span "update_balance" ไม่มีใน trace
[4] เปิด log ของ wallet-service ด้วย trace id เดิม
    → "event published to queue" แต่ไม่มี log ฝั่ง worker เลย
[5] ดู queue → message ค้างใน dead-letter queue เพราะ schema เปลี่ยน
```

> **ให้มองภาพนี้ว่า** "ปัญหาที่กระทบคนเดียวจะมองไม่เห็นจาก metric เลย และนี่คือเหตุผลที่ต้องมี trace id ที่ตามจากตัวผู้ใช้เข้ามาถึงข้างในระบบได้"

**บทเรียนจากเคสนี้ (ชอบถูกถามต่อในสัมภาษณ์):** งานที่วิ่งแบบ async ผ่าน queue ต้องส่ง trace id ไปกับ message ด้วย ไม่งั้น trace จะขาดตรงรอยต่อ และ dead-letter queue ต้องมี metric + alert ของตัวเอง เพราะมันเงียบมาก

### Example 3 — Dashboard เขียวทั้งกระดาน แต่ลูกค้าบ่นเต็ม social

```
Dashboard:  CPU ปกติ / Memory ปกติ / 5xx = 0 / uptime 100%
ความจริง :  หน้าเว็บโหลดไม่ขึ้นเพราะ JS bundle จาก CDN โหลดไม่ได้ในบางภูมิภาค
```

> **ให้มองภาพนี้ว่า** "เราวัดแต่สิ่งที่อยู่ในบ้านเรา แต่ผู้ใช้ยืนอยู่นอกบ้าน — ถ้าไม่วัดจากฝั่งผู้ใช้ เราจะเห็นเขียวตลอดแม้ในวันที่ไม่มีใครใช้งานได้"

**สิ่งที่ขาด:** Real User Monitoring (วัดจาก browser จริง), synthetic check จากหลายภูมิภาค, และ SLI ที่นิยามจาก "ผู้ใช้ทำงานสำเร็จ" ไม่ใช่ "server ตอบ 200"

## 7. Compare

### Monitoring vs Observability

| | Monitoring | Observability |
|---|---|---|
| ตอบคำถาม | ที่เตรียมไว้ล่วงหน้า | ที่เพิ่งคิดออกตอนนี้ |
| ประเภทปัญหา | known unknowns | unknown unknowns |
| วิธีทำ | ตั้ง threshold + alert | เก็บข้อมูลละเอียดพอให้ตัดมุมมองได้ |
| ตัวอย่าง | "CPU เกิน 80% ไหม" | "ทำไมเฉพาะ user บน iOS ในไทยถึงพัง" |
| ความสัมพันธ์ | เป็น **ส่วนหนึ่ง** ของ observability | ครอบ monitoring อีกที |

### Log vs Metric vs Trace

| | Log | Metric | Trace |
|---|---|---|---|
| หน่วยข้อมูล | เหตุการณ์เดี่ยว | ตัวเลขรวมตามเวลา | เส้นทางของ 1 request |
| ตอบคำถาม | ทำไม | มีปัญหาไหม / เมื่อไร | ที่ไหน |
| ขนาดข้อมูล | ใหญ่มาก | เล็กมาก | ปานกลาง |
| เก็บย้อนหลัง | สั้น (แพง) | ยาวได้เป็นปี | ปานกลาง + sampling |
| ใช้ทำ alert | ได้แต่ไม่เหมาะ (ควรแปลงเป็น metric ก่อน) | เหมาะที่สุด | ไม่ค่อยใช้ |
| จุดอ่อน | เยอะจนหาไม่เจอถ้าไม่มี id | ไม่มีรายละเอียด | ต้องมี propagation ครบทุก hop |

### Request ID vs Trace ID vs Span ID vs Correlation ID

| | ขอบเขต | ใช้ตอน |
|---|---|---|
| Request ID | 1 คำขอที่เข้าระบบเรา | คุยกับ support / แสดงบนหน้า error |
| Trace ID | ทั้งเส้นทางข้ามทุก service | ร้อย log ทุก service เข้าด้วยกัน |
| Span ID | 1 ช่วงงานย่อยใน trace | ชี้ว่าช้าที่ขั้นตอนไหน |
| Correlation ID | ร้อยหลาย request ที่เป็นเรื่องเดียวกัน | flow ที่มีหลายคำขอ เช่น checkout หลายขั้น |

### Structured Log vs Plain Text Log

| | Plain Text | Structured (JSON) |
|---|---|---|
| คนอ่านตอน dev | อ่านง่าย | อ่านยากกว่าเล็กน้อย |
| ค้นหา/กรอง | ทำได้จำกัด ต้องพึ่ง regex | กรองตาม field ได้ตรง ๆ |
| นับเป็น metric | แทบทำไม่ได้ | ทำได้ |
| เหมาะกับ | local dev | production |

> **Trade-off:** หลายทีมเลยตั้งค่าให้ local เป็น pretty text และ production เป็น JSON ซึ่งเป็นคำตอบที่ฟังดูมีประสบการณ์ในห้องสัมภาษณ์

### Health Check vs Monitoring vs Alert

| | ใครถาม | ความถี่ | ผลลัพธ์ |
|---|---|---|---|
| Health Check | LB / Kubernetes | ทุกไม่กี่วินาที | ส่งงานให้ / ไม่ส่ง / restart |
| Monitoring | ระบบเก็บ metric | ตลอดเวลา | กราฟไว้ดู |
| Alert | กฎที่ตั้งไว้บน metric | เมื่อเข้าเงื่อนไข | ปลุกคน |

### SLI vs SLO vs SLA

| | คืออะไร | ตัวอย่าง | ผิดแล้วไง |
|---|---|---|---|
| SLI | ค่าที่วัดได้จริง | 99.95% ของ request < 1s | เป็นแค่ตัวเลข |
| SLO | เป้าภายในทีม | ต้อง ≥ 99.9% | ต้องหยุด feature มาแก้ระบบ |
| SLA | สัญญากับลูกค้า | ≥ 99.5% ไม่งั้นคืนเงิน | มีผลทางธุรกิจ/กฎหมาย |

### Alert ที่ Cause vs ที่ Symptom

| | Cause-based | Symptom-based |
|---|---|---|
| ตัวอย่าง | CPU > 80%, memory > 90% | checkout error > 2%, p95 > SLO |
| ปลุกคนตอน | ทรัพยากรตึง (อาจไม่มีใครเจ็บ) | ผู้ใช้เจ็บจริง |
| False positive | สูงมาก | ต่ำ |
| ควรใช้เป็น | ข้อมูลประกอบตอนสืบ | ตัวปลุกคน |

### MTTD vs MTTR

| | ย่อมาจาก | วัดอะไร | ปรับดีขึ้นด้วย |
|---|---|---|---|
| MTTD | Mean Time To Detect | นานแค่ไหนกว่าจะรู้ว่าพัง | alert ที่ผูกกับอาการผู้ใช้ |
| MTTR | Mean Time To Recovery | นานแค่ไหนกว่าจะกลับมาปกติ | rollback ที่เร็ว + runbook + trace ที่ชี้จุดได้ไว |

## 8. Common Mistakes

| ❌ ความเข้าใจผิด | ความจริง |
|---|---|
| "มี `console.log` ก็พอแล้ว" | log ที่ไม่มี level/field/trace id หาอะไรไม่เจอตอนมี traffic จริง |
| "log ให้เยอะไว้ก่อน ดีกว่าไม่มี" | log เยอะเกินทำให้ค่าใช้จ่ายพุ่งและหาของไม่เจอ ต้องเลือก event ที่มีความหมาย |
| "log request body ทั้งก้อนไว้ก่อน เผื่อได้ใช้" | ⚠️ นี่คือวิธีทำ password/token/PII หลุดที่พบบ่อยที่สุด |
| "มี dashboard สวย ๆ = มี observability" | dashboard ตอบเฉพาะคำถามที่คนทำเดาไว้ ตอน incident จริงมักถามคำถามที่ไม่มีในกระดาน |
| "uptime 100% = ระบบดี" | server ตอบ 200 ได้ทั้งที่ผู้ใช้ทำงานไม่สำเร็จ ต้องวัดจากมุมผู้ใช้ |
| "alert เยอะ = ปลอดภัย" | alert fatigue ทำให้คนปิดการแจ้งเตือนจริง ๆ ทิ้ง = อันตรายกว่าไม่มี alert |
| "CPU สูงต้องรีบแก้" | CPU สูงแต่ latency ปกติ = ใช้ทรัพยากรคุ้ม ไม่ใช่ปัญหา |
| "ใส่ user_id เป็น label ของ metric จะได้ดูรายคน" | cardinality ระเบิด ระบบ metric ล่ม — รายคนต้องอยู่ใน log/trace |
| "Trace ทำให้ระบบช้า เลยไม่ใส่" | ใช้ sampling ได้ และตอน incident การไม่มี trace แพงกว่ามาก |
| "`/health` ตอบ 200 ตลอดก็พอ" | เท่ากับหลอก LB ว่าเครื่องพร้อมทั้งที่ต่อ DB ไม่ได้ |
| "Liveness เช็ก DB ด้วยสิ ครบดี" | DB สะดุด → pod ถูก restart ยกชุด → ระบบล่มหนักกว่าเดิม |
| "incident จบแล้วก็จบ ไม่ต้องเขียนอะไร" | เหตุเดิมจะกลับมาอีก เพราะไม่มีใครแก้ต้นเหตุเชิงระบบ |
| "postmortem = หาว่าใครผิด" | ถ้าโทษคน คนจะซ่อนข้อมูล แล้วครั้งหน้าจะยิ่งหา root cause ไม่เจอ |
| "root cause คือ 'คนลืมใส่ index'" | นั่นคืออาการ root cause คือ "ไม่มีกระบวนการตรวจ query plan ก่อนขึ้น prod" |
| "ดูค่าเฉลี่ย latency ก็พอ" | ค่าเฉลี่ยซ่อน tail — ต้องดู p95/p99 (เชื่อมกับ PART 22) |
| "monitoring เป็นงานของ DevOps" | คนเขียน feature คือคนเดียวที่รู้ว่าอะไรควร log และ SLI ควรวัดอะไร |

## 9. Debugging

### ลำดับการไล่เมื่อ "ระบบมีปัญหา" (ใช้ได้ทั้งตอน incident จริงและตอบสัมภาษณ์)

```
[1] ยืนยันว่ามีคนเจ็บจริงไหม
      ดู SLI/golden signals ไม่ใช่ดู CPU
      ↓
[2] กำหนดขอบเขต
      ทุกคนหรือบางคน / ทุก endpoint หรือเส้นเดียว / ทุก region หรือบางที่
      ↓
[3] ถามว่า "เปลี่ยนอะไรไปเมื่อเร็ว ๆ นี้"
      deploy / config / feature flag / migration / ของข้างนอกที่เราพึ่งพา
      ↓
[4] ดู golden signals ทีละตัว
      traffic ขึ้นผิดปกติ? errors พุ่ง? latency พุ่ง? saturation เต็ม?
      ↓
[5] เปิด trace ของ request ที่ error/ช้า
      หา span ที่กินเวลา หรือ span ที่หายไป
      ↓
[6] เปิด log ด้วย trace id นั้น
      อ่าน reason/error_code ไม่ใช่เดา
      ↓
[7] ดู dependency
      DB, cache, queue, third-party — ของข้างนอกก็พังเป็น
      ↓
[8] MITIGATE ก่อน (rollback / flag off) แล้วค่อยหา root cause
      ↓
[9] เก็บหลักฐาน (กราฟ, trace id, log) ไว้เขียน postmortem
```

> **ให้มองภาพนี้ว่า** "ลำดับนี้คือการหดพื้นที่ค้นหาลงทีละครึ่ง เหมือน binary search บนระบบ ไม่ใช่การเปิด log แล้วอ่านไล่จากบนลงล่าง"

### ตาราง: อาการ → ดูอะไรก่อน → เครื่องมือ

| อาการ | สงสัยอะไร | ดูอะไรก่อน |
|---|---|---|
| Error rate พุ่งแบบหักศอก | deploy/config เพิ่งเปลี่ยน | deploy timeline เทียบกับกราฟ |
| Error rate ค่อย ๆ ไต่ขึ้น | ทรัพยากรค่อย ๆ หมด (leak, pool, disk) | กราฟ saturation ย้อนหลังหลายชั่วโมง |
| p99 แย่ p50 ปกติ | tail latency: GC, lock, cache miss, บาง instance ป่วย | histogram + แยกกราฟราย instance |
| ช้าทุก request เท่า ๆ กัน | dependency กลาง (DB/3rd party) ช้า | trace ดู span ที่ยาวที่สุด |
| Dashboard เขียวแต่ลูกค้าบ่น | เราวัดผิดจุด (ไม่ได้วัดจากฝั่งผู้ใช้) | RUM / synthetic check / log ฝั่ง client |
| ลูกค้าคนเดียวมีปัญหา | ข้อมูลเฉพาะราย / message ค้าง | ค้นด้วย trace id หรือ user ref |
| กราฟ metric หายไปเฉย ๆ | collector/agent ตาย ไม่ใช่ traffic หาย | health ของ agent + เทียบกับ log |
| งาน async ไม่เกิดผล | consumer ตาย / message เข้า DLQ | queue depth, DLQ count, consumer lag |
| Pod restart วน | liveness ตั้งผิด หรือ OOM | restart count + exit code + memory graph |
| Alert เด้งแต่ทุกอย่างปกติ | alert ผูกกับ cause ไม่ใช่ symptom | ทบทวนเกณฑ์ alert |

### กฎเหล็กตอน debug ด้วย observability

1. **อย่าเดาว่าส่วนไหนพัง** ให้ถามว่า "ข้อมูลอะไรจะยืนยัน/ตัดสมมติฐานนี้ทิ้งได้"
2. **เทียบกับ baseline เสมอ** — 3.4 วินาทีแย่ไหม ขึ้นกับว่าเมื่อวานเป็นเท่าไร
3. **correlation ไม่ใช่ causation** — สองกราฟขึ้นพร้อมกันไม่ได้แปลว่าอันหนึ่งทำอีกอันเสมอ
4. **ถ้ามองไม่เห็น ให้ยอมรับว่ามองไม่เห็น** แล้วเพิ่ม instrument ชั่วคราว ดีกว่าเดาไปเรื่อย
5. **ตัวเครื่องมือเองก็พังได้** — dashboard ว่างเปล่าอาจแปลว่า agent ตาย ไม่ใช่ไม่มีคนใช้งาน

## 11. Answer Like a Developer

### โครงตอบ: "Log, Metric, Trace ต่างกันยังไง"

1. บอกว่าแต่ละอันตอบคำถามคนละคำถาม (มีปัญหาไหม / อยู่ตรงไหน / เพราะอะไร)
2. ให้ภาพจำ: สัญญาณชีพ / ใบส่งตัว / บันทึกแพทย์
3. บอกลำดับใช้จริง: metric → trace → log
4. บอก trade-off: log ละเอียดสุดแต่แพงสุดและเก็บได้สั้นสุด
5. ปิดด้วยการใช้งานจริง: "ตอน incident ผมไม่เปิด log เป็นอย่างแรก เพราะยังไม่รู้ว่าจะหาอะไร"

### โครงตอบ: "ระบบมีปัญหา คุณจะทำยังไง"

```
[1] ยืนยันผลกระทบ  "ขอดูก่อนว่ากระทบผู้ใช้กี่ % และ endpoint ไหน"
      ↓
[2] ตีขอบเขต       "ทุกคนหรือบางกลุ่ม ทุกที่หรือบาง region"
      ↓
[3] ถามว่าเปลี่ยนอะไร "deploy/config/flag ล่าสุดเมื่อไร"
      ↓
[4] ไล่ 3 เสา       "metric → trace → log"
      ↓
[5] หยุดเลือดก่อน   "rollback / flag off แล้วค่อยหา root cause"
      ↓
[6] ปิดด้วย postmortem + action item
```

**ตัวอย่างการพูดจริง:**

> "อย่างแรกผมจะยืนยันก่อนครับว่ามีผู้ใช้เจ็บจริงไหม โดยดูจาก error rate และ p95 ของ endpoint ที่สำคัญ ไม่ใช่ดู CPU เพราะ CPU สูงอาจไม่กระทบใครเลย
>
> จากนั้นผมจะตีขอบเขตว่ากระทบทุกคนหรือบางกลุ่ม แล้วถามทีมว่ามี deploy หรือเปลี่ยน config อะไรก่อนหน้านั้นไหม เพราะเหตุส่วนใหญ่เกิดหลังมีการเปลี่ยนแปลง
>
> พอรู้ว่าเสียตรงไหน ผมจะเปิด trace ของ request ที่ error เพื่อดูว่าไปช้าหรือพังที่ span ไหน แล้วค่อยเอา trace id นั้นไปเปิด log ของ service นั้นเพื่อดูสาเหตุจริง
>
> ระหว่างนั้นถ้ามีทางหยุดเลือดได้เร็ว เช่น rollback หรือปิด feature flag ผมจะทำก่อนครับ เพราะการหาสาเหตุทำทีหลังได้ แต่ผู้ใช้รอไม่ได้
>
> หลังจบผมจะเขียน postmortem แบบ blameless พร้อม action item ที่มีเจ้าของและกำหนดเวลา เพื่อให้เหตุเดิมไม่กลับมาอีก"

### โครงตอบ: "Alert ที่ดีคืออะไร"

1. เริ่มด้วยหลัก: alert ที่อาการของผู้ใช้ ไม่ใช่ที่ทรัพยากร
2. ยกตัวอย่างแย่/ดี: "CPU 80%" vs "checkout error > 2% นาน 5 นาที"
3. เพิ่มเกณฑ์: ต้อง actionable + มี runbook + มีช่วงเวลา
4. พูดถึง alert fatigue: "เตือนบ่อยจนคนชิน = เท่ากับไม่มี alert"
5. ปิดด้วย SLO: "ผมชอบผูก alert กับการเผา error budget มากกว่าผูกกับ threshold ดิบ"

### โครงตอบ: "เล่า incident ที่เคยเจอ"

ใช้โครงเดียวกับ postmortem จะเล่าไม่หลงทาง

| ขั้น | พูดอะไร |
|---|---|
| Impact | กระทบใคร กี่คน กี่นาที (ตัวเลข) |
| Detection | รู้จาก alert หรือลูกค้าแจ้ง (ตอบตามจริง) |
| Action | หยุดเลือดยังไง ใช้เวลาเท่าไร |
| Root cause | สาเหตุเชิงระบบ ไม่ใช่ชื่อคน |
| Learning | เปลี่ยนอะไรหลังจากนั้น และวัดผลได้ไหม |

### สิ่งที่ทำให้คะแนนตก

| อย่าพูด | พูดแบบนี้แทน |
|---|---|
| "ผมใส่ `console.log` แล้วดูใน terminal" | "ผมใช้ structured log ที่มี trace id เพื่อค้นข้าม service ได้" |
| "เราตั้ง alert ตอน CPU เกิน 80%" | "เราตั้ง alert ที่ error rate และ latency ของ flow ที่ผู้ใช้ใช้จริง" |
| "log ไว้เยอะ ๆ เผื่อได้ใช้" | "เราเลือก event ที่มีความหมาย และมี redaction กันข้อมูลอ่อนไหวหลุด" |
| "incident นั้นเกิดเพราะน้องคนนั้น deploy ผิด" | "ระบบเราตอนนั้นยังไม่มี guard ที่กันการ deploy แบบนั้น เลยเพิ่ม check ทีหลัง" |
| "uptime เรา 100%" | "SLI ที่เราวัดคือสัดส่วนคำสั่งซื้อที่สำเร็จ ซึ่งสะท้อนผู้ใช้มากกว่า uptime ของ server" |
| "เราไม่ได้ทำ tracing เพราะระบบเล็ก" | "ตอนนี้ยังใช้ log กับ request id ได้อยู่ แต่พอเริ่มมี service ที่สอง ผมจะเพิ่ม trace ทันที" |

## 12. One-Minute Review

- **Observability = ความสามารถตอบคำถามใหม่จากสัญญาณที่ระบบพ่นออกมา** ส่วน Monitoring = เฝ้าคำถามที่เตรียมไว้แล้ว
- **3 เสา ตอบคนละคำถาม:** Metric = มีปัญหาไหม/เมื่อไร, Trace = อยู่ตรงไหน, Log = เพราะอะไร → ใช้เรียงกันแบบนี้
- **Golden Signals 4 ตัว:** Latency, Traffic, Errors, Saturation — วัด 4 อันนี้ก่อนวัดอย่างอื่น
- **Structured log** (JSON + level + trace id + event name คงที่) คือสิ่งที่ทำให้ log ค้นได้และนับได้
- ⚠️ **ห้าม log รหัสผ่าน token cookie เลขบัตร หรือ PII เด็ดขาด** — log ออกนอกกำแพงความปลอดภัย ให้ log ตัวอ้างอิงแทน เช่น `user_id`, `card_last4` และทำ redaction ที่ logger กลาง
- **Trace ID ทำให้ debug ระบบหลาย service เป็นไปได้** เพราะร้อย log ของทุก hop เข้าด้วยกัน — ต้องส่งต่อผ่าน header และผ่าน queue ด้วย
- **Latency ต้องเป็น histogram** เพื่อคำนวณ p95/p99 ย้อนหลังได้ และ **ห้ามใส่ id รายคนเป็น metric label** (cardinality ระเบิด)
- **Liveness = ควร restart ไหม / Readiness = ควรส่งงานให้ไหม** คนละคำถาม คนละ endpoint
- **Alert ที่ดีผูกกับอาการที่ผู้ใช้เจอ ไม่ใช่ CPU สูง** และต้อง actionable มี runbook ไม่งั้นเกิด alert fatigue
- **ตอน incident: หยุดเลือดก่อน (rollback/flag off) แล้วค่อยหา root cause**
- **Postmortem แบบ blameless:** Impact → Timeline → Detection → Root Cause → What went well/wrong → Action Items ที่มีเจ้าของและกำหนดเวลา
- **โทษระบบ ไม่โทษคน** — คนคือจุดที่ทำให้เห็นรูของระบบ ไม่ใช่ตัวรู
- **เครื่องมือเองก็พังได้** กราฟหายอาจแปลว่า collector ตาย ไม่ใช่ traffic หาย

## 13. Memory Card

### จำ 5 อย่าง

1. **3 เสาตอบคนละคำถาม** — Metric (มีปัญหาไหม) → Trace (ตรงไหน) → Log (ทำไม) ใช้เรียงกันเสมอ
2. **Trace ID คือกุญแจของระบบหลาย service** — ไม่มีมัน = ต้องไปไล่ถามทุก service ทีละตัว
3. **Alert ที่อาการของผู้ใช้ ไม่ใช่ที่ CPU** — ถ้าไม่มีใครเจ็บ ไม่ควรปลุกคน
4. ⚠️ **ห้าม log password / token / PII** — log ออกนอกกำแพงความปลอดภัยและลบยาก ให้ log id อ้างอิงแทน
5. **Postmortem โทษระบบ ไม่โทษคน** — จบด้วย action item ที่มีเจ้าของและกำหนดเวลา ไม่ใช่ "จะระวังมากขึ้น"

### Keyword Card

- **Observability** → มองเห็นข้างใน → ตอบคำถามที่ไม่ได้เตรียมไว้
- **Monitoring** → เฝ้าค่าที่ตั้งไว้ → เป็นส่วนย่อยของ observability
- **Log** → บันทึกเหตุการณ์ → ตอบว่า "ทำไม" ละเอียดสุด แพงสุด
- **Structured Log** → log เป็น JSON → ค้นได้ กรองได้ นับได้
- **Log Level** → DEBUG/INFO/WARN/ERROR/FATAL → ถ้าทุกอย่างเป็น ERROR = ไม่มีอะไรเป็น ERROR
- **Metric** → ตัวเลขตามเวลา → ตอบว่า "มีปัญหาไหม เริ่มเมื่อไร"
- **Counter / Gauge / Histogram** → นับสะสม / ค่าปัจจุบัน / การกระจาย → latency ต้องเป็น histogram
- **Cardinality** → จำนวนค่าของ label → ใส่ user id = ระบบ metric ระเบิด
- **Trace / Span** → เส้นทาง 1 request / ช่วงงานย่อย → หาแถบยาวที่สุดใน waterfall
- **Trace ID / Request ID** → เลขร้อยข้าม service / เลขอ้างอิงให้ลูกค้า → ต้อง propagate ทุก hop รวมถึง queue
- **Context Propagation** → ส่ง id ไปกับ header → ขาดที่ hop ไหน trace ตายตรงนั้น
- **APM** → รวม metric+trace+error ที่เดียว → ลดเวลาเชื่อมภาพตอน incident
- **Golden Signals** → Latency, Traffic, Errors, Saturation → วัด 4 อันนี้ก่อน
- **SLI / SLO / SLA** → วัดได้จริง / เป้าในทีม / สัญญากับลูกค้า → ใช้ตัดสินว่าพอหรือยัง
- **Error Budget** → โควตาพังที่ยอมได้ → เผาเร็วผิดปกติเมื่อไร ค่อยปลุกคน
- **Health Check** → live (ควร restart ไหม) / ready (ควรส่งงานไหม) → แยก endpoint เสมอ
- **Alert Fatigue** → เตือนจนชิน → เท่ากับไม่มี alert
- **Incident / Severity** → เหตุที่กระทบผู้ใช้ / ระดับความรุนแรง → ไม่ใช่ทุก bug คือ incident
- **MTTD / MTTR** → นานแค่ไหนกว่าจะรู้ / กว่าจะกลับมาปกติ → ตัวชี้วัดคุณภาพ observability
- **Postmortem / Blameless** → สรุปหลังเหตุ / ไม่โทษคน → คนคือจุดที่เผยรูของระบบ
- **Action Item** → สิ่งที่ต้องทำต่อ → ต้องมีเจ้าของ + กำหนดเวลา + วัดผลได้
- **Sampling / Retention** → เก็บบางส่วน / เก็บนานแค่ไหน → คือปุ่มควบคุมค่าใช้จ่ายของ observability
- **PII** → ข้อมูลระบุตัวบุคคล → ห้ามลง log เด็ดขาด ให้ใช้ id อ้างอิงแทน
