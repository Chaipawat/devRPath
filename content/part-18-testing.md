# PART 18 — TESTING

> ตำแหน่งในภาพใหญ่: Quality Layer — ชั้นที่คอยยืนยันว่าโค้ดที่เขียนไปยังทำงานถูกอยู่ ก่อนที่ผู้ใช้จริงจะเป็นคนเจอปัญหาแทนเรา

---

## 1. Big Picture

เวลาคนเพิ่งเริ่มเขียนโปรแกรม เขาทดสอบโค้ดด้วยการ "เปิดเว็บแล้วกดดู"
กดสมัครสมาชิก → เห็นว่าสมัครได้ → จบ ถือว่าโค้ดใช้ได้

วิธีนี้ **ไม่ผิด** มันคือการทดสอบแบบหนึ่ง เรียกว่า manual test
ปัญหาคือมันไม่ scale:

- วันนี้มี 5 หน้า กดครบใน 10 นาที
- อีก 1 ปี มี 60 หน้า กดครบใช้เวลา 2 วัน
- และทุกครั้งที่แก้โค้ด 1 บรรทัด ก็ต้องกดใหม่ทั้ง 60 หน้าเพื่อให้มั่นใจ

**Automated Test คือการเอา "การกดดู" นั้นมาเขียนเป็นโค้ด เพื่อให้เครื่องกดแทนเราได้ทุกวัน วันละร้อยรอบ โดยไม่บ่นและไม่ลืม**

พูดแบบ HR ฟังรู้เรื่อง:

> "Test คือโค้ดอีกชุดหนึ่งที่มีหน้าที่เดียวคือคอยถามโค้ดหลักว่า 'แกยังทำงานถูกอยู่ไหม' ถ้าไม่ถูก มันจะร้องให้เรารู้ตั้งแต่ยังอยู่บนเครื่องเรา ไม่ใช่ให้ลูกค้าเป็นคนบอก"

### Test มีไว้เพื่ออะไรจริง ๆ

นี่คือจุดที่ junior ส่วนใหญ่ตอบผิดในห้องสัมภาษณ์
คำตอบที่คนมักตอบคือ "เพื่อหาบั๊ก" — ซึ่งถูกไม่ถึงครึ่ง

เหตุผลจริงเรียงตามน้ำหนัก:

| เหตุผล | อธิบาย |
|---|---|
| **กล้าแก้โค้ด (confidence to change)** | เหตุผลอันดับ 1 — มี test แล้วเรากล้า refactor เพราะถ้าพังมันจะบอก |
| **กันของเก่าพัง (regression)** | ฟีเจอร์ที่เคยทำงานได้ ต้องไม่พังเพราะฟีเจอร์ใหม่ |
| **เป็นเอกสารที่ไม่มีวันล้าสมัย** | อ่าน test แล้วรู้ว่าฟังก์ชันนี้ควรทำอะไรบ้าง และ test โกหกไม่ได้เพราะมันรัน |
| **บังคับให้ออกแบบโค้ดดีขึ้น** | โค้ดที่เทสยาก มักเป็นโค้ดที่ผูกกันแน่นเกินไป — test คือสัญญาณเตือน design |
| **หาบั๊ก** | มีจริง แต่เป็นผลพลอยได้ ไม่ใช่เป้าหมายหลัก |

ประโยคที่ควรพูดได้ในห้องสัมภาษณ์:

> "เทสต์ไม่ได้มีไว้พิสูจน์ว่าโค้ดถูก มันมีไว้ให้เรากล้าเปลี่ยนโค้ด"

### ภาพรวมของทั้ง chapter

```
[DEVELOPER เขียนโค้ด]
        ↓
[UNIT TEST]        ← เร็วมาก เทสชิ้นเล็ก ๆ ทีละชิ้น
        ↓
[INTEGRATION TEST] ← ช้าขึ้น เทสว่าหลายชิ้นต่อกันแล้วยังทำงาน
        ↓
[E2E TEST]         ← ช้าสุด เทสเหมือนผู้ใช้จริงกดทั้งระบบ
        ↓
[CI PIPELINE]      ← รันทุกอย่างอัตโนมัติทุกครั้งที่ push
        ↓
[DEPLOY]
        ↓
[SMOKE TEST บน production]  ← เช็กลมหายใจหลัง deploy
```

> **ให้มองภาพนี้ว่า** "Test แต่ละชั้นคือด่านกรองที่ตาข่ายถี่ต่างกัน ชั้นล่างถี่และเร็วเพื่อกรองของเสียส่วนใหญ่ ชั้นบนหยาบและช้าแต่จับปัญหาที่เกิดตอนของทุกชิ้นมาต่อกันจริง"

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Testing Pyramid** | ล่างเยอะ บนน้อย | หลักการจัดสัดส่วนเทสต์: unit เยอะสุด, e2e น้อยสุด |
| **Unit Test** | เทสชิ้นเดียว | ทดสอบฟังก์ชัน/คลาสเดียวโดยตัดของรอบข้างออก เร็วระดับมิลลิวินาที |
| **Integration Test** | เทสรอยต่อ | ทดสอบว่าหลายชิ้นต่อกันแล้วยังทำงาน เช่น service + database จริง |
| **E2E Test** | เทสเหมือนผู้ใช้ | เปิด browser จริง กดจริง ตั้งแต่หน้าแรกจนจบ flow |
| **Test Case** | 1 เคส 1 คำถาม | หน่วยเทสต์หนึ่งชุด: input แบบนี้ → คาดหวังผลแบบนี้ |
| **Assertion** | บรรทัดที่ตัดสิน | บรรทัดที่บอกว่า "ผลต้องเท่ากับสิ่งนี้" ถ้าไม่ตรง test fail |
| **Arrange-Act-Assert** | เตรียม-ทำ-ตรวจ | โครงมาตรฐานของ test case ที่อ่านง่าย |
| **Mock** | ของปลอมที่จำได้ว่าถูกเรียก | ของแทนที่เราตรวจได้ว่าถูกเรียกกี่ครั้ง ด้วยอะไร |
| **Stub** | ของปลอมที่ตอบค่าตายตัว | ของแทนที่แค่คืนค่าที่เรากำหนดไว้ ไม่สนใจว่าถูกเรียกยังไง |
| **Spy** | ของจริงที่มีคนแอบดู | ห่อของจริงไว้ ยังทำงานจริง แต่บันทึกว่าถูกเรียกอย่างไร |
| **Fake** | ของปลอมที่ทำงานได้จริง | implementation แบบง่าย เช่น in-memory database |
| **Test Double** | คำรวมของปลอมทั้งหมด | คำแม่ของ mock / stub / spy / fake |
| **Happy Path** | ทางที่ทุกอย่างถูก | เคสที่ผู้ใช้ทำถูกทุกอย่างและระบบทำงานปกติ |
| **Edge Case** | ขอบของที่รับได้ | ค่าตรงขอบเขต: 0, ค่าว่าง, ตัวสุดท้าย, ตัวมากสุด |
| **Negative Case** | เคสที่ต้องพัง | ใส่ของผิดเข้าไปแล้วระบบต้องปฏิเสธอย่างถูกวิธี |
| **Regression Test** | กันของเก่าพัง | เทสต์ที่มีไว้ยืนยันว่าสิ่งที่เคยทำงานได้ยังทำงานได้ |
| **Smoke Test** | เช็กลมหายใจ | เทสต์สั้น ๆ ไม่กี่เคสหลัง deploy ว่าระบบยังไม่ตายทั้งก้อน |
| **Load Test** | ทดสอบภาระปกติ | ยิงโหลดระดับที่คาดว่าจะเจอจริง ดูว่ายังไหวไหม |
| **Stress Test** | ทดสอบจุดแตก | ยิงเกินขีดจนพัง เพื่อรู้ว่าพังตรงไหนและพังยังไง |
| **Coverage** | % โค้ดที่ถูกรัน | สัดส่วนบรรทัด/branch ที่มีเทสต์วิ่งผ่าน (ย้ำ: แค่ "วิ่งผ่าน") |
| **Flaky Test** | เทสต์ตัวแปรปรวน | เทสต์ที่บางรอบผ่านบางรอบไม่ผ่าน ทั้งที่โค้ดไม่เปลี่ยน |
| **Fixture / Seed** | ข้อมูลตั้งต้น | ข้อมูลที่เตรียมไว้ให้เทสต์ใช้ |
| **Test Runner** | คนคุมการรัน | เครื่องมือที่ไปหาไฟล์เทสต์มารันและรายงานผล |
| **CI** | เครื่องรันเทสต์ให้อัตโนมัติ | ระบบที่รันเทสต์ทุกครั้งที่ push / เปิด PR |
| **QA** | คนตรวจคุณภาพมุมผู้ใช้ | บทบาทที่ทดสอบจากมุมธุรกิจและผู้ใช้ ไม่ใช่มุมโค้ด |

## 3. Mental Model

### โมเดลที่ 1: Test คือ "สัญญา" ไม่ใช่ "การพิสูจน์"

Test ไม่เคยพิสูจน์ว่าโค้ดถูกทั้งหมด มันพิสูจน์ได้แค่ว่า
**"สำหรับ input ชุดที่ฉันคิดถึง โค้ดให้ผลอย่างที่ฉันคาด"**

สิ่งที่เราไม่ได้คิดถึง เทสต์ไม่มีทางจับได้ นี่คือเหตุผลว่าทำไม coverage 100% ยังมีบั๊ก

### โมเดลที่ 2: เทสต์คือการตั้งคำถาม 3 ชั้น

ทุก test case ตอบ 3 อย่างนี้:

```
[ARRANGE]  เตรียมโลกให้อยู่ในสภาพที่ต้องการ
     ↓
[ACT]      ทำสิ่งเดียวที่อยากทดสอบ
     ↓
[ASSERT]   ตรวจว่าผลตรงกับที่คาด
```

> **ให้มองภาพนี้ว่า** "เทสต์หนึ่งตัวคือการทดลองวิทยาศาสตร์หนึ่งครั้ง — จัดฉากให้ครบ ทำหนึ่งอย่าง แล้ววัดผลหนึ่งอย่าง"

ถ้า test case หนึ่งตัวมี Act หลายครั้ง แปลว่ามันควรถูกแยกเป็นหลายเคส

### โมเดลที่ 3: "ทดสอบพฤติกรรม ไม่ใช่ทดสอบวิธีทำ"

นี่คือเส้นแบ่ง junior กับ mid ที่ชัดที่สุด

| ทดสอบพฤติกรรม (ดี) | ทดสอบวิธีทำ (เปราะ) |
|---|---|
| "ใส่ของลงตะกร้าแล้ว ยอดรวมต้องเป็น 300" | "ต้องเรียกฟังก์ชัน `calcSum()` 1 ครั้ง" |
| "กรอกรหัสผิด 5 ครั้งแล้วบัญชีต้องถูกล็อก" | "ต้อง set ตัวแปร `failCount` เป็น 5" |
| ถ้า refactor ข้างในแล้วผลเหมือนเดิม → test ยังเขียว | ถ้า refactor ข้างใน → test แดงทั้งที่ระบบไม่พัง |

เทสต์ที่ผูกกับวิธีทำ (implementation detail) จะกลายเป็น **โซ่ถ่วง** ทันทีที่ต้อง refactor
สังเกตง่าย ๆ: ถ้าแก้โค้ดโดยไม่เปลี่ยนพฤติกรรมแล้วเทสต์แดง — เทสต์ตัวนั้นเขียนผิดชั้น

### โมเดลที่ 4: Testing Pyramid = เรื่องของ "ต้นทุนต่อความมั่นใจ"

```
                    ╱╲
                   ╱E2E╲          ← ช้า แพง เปราะ แต่ให้ความมั่นใจสูงสุดต่อ 1 เทส
                  ╱──────╲
                 ╱Integration╲    ← กลาง ๆ ทุกด้าน จับบั๊กรอยต่อ
                ╱────────────╲
               ╱  Unit Test   ╲   ← เร็ว ถูก เสถียร แต่ไม่รู้ว่าต่อกันแล้วรอด
              ╱────────────────╲
```

> **ให้มองภาพนี้ว่า** "ยิ่งขึ้นสูง ยิ่งเหมือนผู้ใช้จริงมากขึ้น แต่ยิ่งช้าและยิ่งพังง่ายโดยไม่ใช่ความผิดของโค้ด เราจึงเอาชั้นล่างเยอะ ๆ ไว้กรองของเสีย และเก็บชั้นบนไว้แค่เส้นทางที่เสียไม่ได้"

ตัวเลขสัดส่วนที่คนชอบท่อง (70/20/10) **ไม่ใช่กฎ** — มันคือสัญลักษณ์ของ trade-off
สิ่งที่ต้องตอบให้ได้คือ **"ทำไมชั้นล่างต้องเยอะกว่า"** ไม่ใช่ "กี่เปอร์เซ็นต์"

คำตอบ: เพราะ feedback loop
unit test รู้ผลใน 2 วินาที → แก้ได้ทันที
e2e รู้ผลใน 15 นาที → กว่าจะรู้ว่าพัง เราลืมบริบทไปแล้ว

## 4. ภาพจำ

```
🧠 ภาพจำที่ 1 — Testing Pyramid = โรงงานตรวจสินค้า

Unit Test        = ตรวจน็อตทีละตัว          (เร็วมาก ตรวจได้เป็นพัน)
Integration Test = ตรวจว่าเครื่องยนต์ประกอบแล้วติด
E2E Test         = ขับรถออกถนนจริงหนึ่งรอบ  (ช้า แต่รู้จริงว่าใช้ได้)

น็อต → เครื่องยนต์ → ขับจริง
```

```
🧠 ภาพจำที่ 2 — Mock / Stub / Spy = นักแสดงในกองถ่าย

Stub = นักแสดงที่พูดบทเดิมทุกครั้ง  ("คุณมีเงิน 100 บาท")
Mock = นักแสดงที่จดว่าใครสั่งอะไรบ้าง แล้วเอาไปฟ้องตอนจบ
Spy  = ของจริง แต่มีกล้องแอบถ่ายไว้ว่าถูกใช้กี่ครั้ง
Fake = ของปลอมที่ใช้งานได้จริง (database จำลองในหน่วยความจำ)

ของจริง → ของปลอม → ตรวจว่าทำถูกไหม
```

```
🧠 ภาพจำที่ 3 — Coverage = ไฟฉายส่องห้อง

ส่องถึงมุมไหน = โค้ดบรรทัดนั้นถูก "รัน"
แต่ส่องเห็น ไม่ได้แปลว่า "ตรวจแล้ว"
coverage 100% = ส่องทั่วห้อง แต่ไม่ได้แปลว่าไม่มีขโมยในห้อง

รันผ่าน ≠ ตรวจสอบ
```

```
🧠 ภาพจำที่ 4 — Flaky Test = นาฬิกาปลุกที่บางวันไม่ดัง

ไม่ดังบ้าง = คุณเลิกเชื่อมันภายใน 3 วัน
พอเลิกเชื่อ = ตอนมันดังจริงเพราะไฟไหม้ คุณก็กดปิด

เทสต์ที่ไม่น่าเชื่อถือ แย่กว่าไม่มีเทสต์
```

```
🧠 ภาพจำที่ 5 — Smoke Test = เป่าลมเข้าท่อน้ำ

ช่างประปาสมัยก่อนเป่าควันเข้าท่อ ถ้าเห็นควันรั่วออกมา = ท่อแตก
เราไม่ได้ตรวจทั้งระบบ เราแค่ถามว่า "ยังหายใจอยู่ไหม"

Deploy → Smoke Test → ถ้าไม่ผ่าน rollback ทันที
```

## 5. How It Works

### 5.1 ชีวิตของเทสต์หนึ่งตัวใน CI

```
[DEV เขียนโค้ด + เขียนเทสต์]
        ↓
[git push]
        ↓
[CI PIPELINE เริ่มทำงาน]
        ↓
[Lint / Type Check]         ← เร็วสุด ล้มก่อนเปลืองเวลา
        ↓
[Unit Test]                 ← วินาที
        ↓
[Integration Test]          ← นาที (ยก database ชั่วคราวขึ้นมา)
        ↓
[Build]
        ↓
[Deploy → Staging]
        ↓
[E2E Test]                  ← สิบนาที
        ↓
[Deploy → Production]
        ↓
[Smoke Test บน production]
        ↓
[Monitoring / Alert]
```

> **ให้มองภาพนี้ว่า** "Pipeline คือด่านตรวจเรียงจากถูกและเร็วไปหาแพงและช้า เพื่อให้ของเสียส่วนใหญ่ตกตั้งแต่ด่านแรก ๆ ที่ยังไม่เปลืองเวลาใคร"

### 5.2 Unit Test ทำงานยังไง

```
โค้ดจริง:  OrderService → PaymentGateway → ธนาคารจริง
                              ↓
ตอนเทสต์:  OrderService → [STUB PaymentGateway] → คืนค่า "สำเร็จ" ทันที
```

> **ให้มองภาพนี้ว่า** "Unit test คือการตัดสายไฟรอบ ๆ ชิ้นที่เราสนใจออก แล้วเสียบของปลอมแทน เพื่อให้เหลือตัวแปรเดียวคือโค้ดที่เราอยากตรวจ"

เหตุผลที่ต้องตัด:

- **เร็ว** — ไม่ต้องรอ network / database
- **แน่นอน** — ธนาคารล่มก็ไม่กระทบเทสต์เรา
- **ควบคุมเคสยากได้** — เช่น "ถ้าธนาคารตอบ timeout จะเกิดอะไร" ของจริงสั่งให้ timeout ไม่ได้ แต่ stub สั่งได้

### 5.3 Integration Test ทำงานยังไง

```
[TEST]
   ↓
[SERVICE จริง]
   ↓
[REPOSITORY จริง]
   ↓
[DATABASE จริง (แต่เป็นตัวชั่วคราวสำหรับเทสต์)]
```

> **ให้มองภาพนี้ว่า** "Integration test คือการปล่อยให้ของจริงคุยกันจริง โดยเปลี่ยนแค่ 'ปลายทางที่จะเสียหายถ้าพัง' ให้เป็นของชั่วคราว"

บั๊กประเภทที่มีแต่ integration test เท่านั้นที่จับได้:

- SQL เขียนผิด syntax (unit test ที่ mock repository จะไม่มีวันรู้)
- ชื่อคอลัมน์ไม่ตรง schema
- transaction ไม่ rollback จริง
- ORM สร้าง query ที่ไม่ใช่อย่างที่คิด (N+1)
- serialization ของ date/decimal เพี้ยนตอนข้ามชั้น

### 5.4 E2E Test ทำงานยังไง

```
[TEST RUNNER]
      ↓ สั่ง browser จริง
[BROWSER]
      ↓ คลิก / พิมพ์ / รอ element
[FRONTEND]
      ↓ HTTP
[BACKEND]
      ↓
[DATABASE]
      ↓ ผลกลับขึ้นมา
[BROWSER แสดงผล]
      ↓
[ASSERT: ผู้ใช้ต้องเห็นข้อความ "สั่งซื้อสำเร็จ"]
```

> **ให้มองภาพนี้ว่า** "E2E คือการจ้างหุ่นยนต์มานั่งเป็นผู้ใช้จริง กดจริงทุกปุ่ม แล้วถามว่าสุดท้ายเห็นสิ่งที่ควรเห็นไหม"

### 5.5 Load Test กับ Stress Test ทำงานยังไง

```
จำนวนผู้ใช้จำลอง
      │
      │                          ╱─ STRESS TEST: ไต่ขึ้นเรื่อย ๆ จนระบบพัง
      │                     ╱────
      │      ┌──────────────┐    ← LOAD TEST: คงที่ที่ระดับ "ปกติวันพีค"
      │     ╱                ╲
      │    ╱                  ╲
      └────────────────────────────── เวลา
```

> **ให้มองภาพนี้ว่า** "Load test ถามว่า 'วันที่คนเยอะที่สุดเรายังยิ้มได้ไหม' ส่วน Stress test ถามว่า 'ถ้าเกินกว่านั้น เราจะพังแบบสุภาพหรือพังแบบระเบิด'"

สิ่งที่ต้องดูตอนทำ ไม่ใช่แค่ "ผ่าน/ไม่ผ่าน" แต่คือ:

| ตัวชี้วัด | ถามว่าอะไร |
|---|---|
| **Latency p95 / p99** | ผู้ใช้ที่ช้าที่สุด 5% / 1% ต้องรอนานแค่ไหน |
| **Throughput** | ระบบรับได้กี่ request ต่อวินาที |
| **Error rate** | พอโหลดสูงขึ้น เริ่มตอบ 5xx ที่จุดไหน |
| **Saturation** | อะไรเต็มก่อน — CPU, memory, connection pool, disk |
| **จุดแตก** | พังแล้วฟื้นเองได้ไหม หรือค้างยาว |

จุดที่ mid-level ต้องพูดได้: **ค่าเฉลี่ย (average) โกหกเสมอ** ให้ดู p95/p99 เพราะผู้ใช้ที่โกรธคือคนที่อยู่หางกราฟ

## 6. Example

### สถานการณ์จริง: ฟีเจอร์ "ใช้คูปองส่วนลด" ในเว็บอีคอมเมิร์ซ

กฎธุรกิจ:

- คูปองลด 10% แต่ลดได้ไม่เกิน 200 บาท
- ใช้ได้เมื่อยอดรวม ≥ 500 บาท
- คูปองหมดอายุแล้วใช้ไม่ได้
- 1 ผู้ใช้ใช้คูปองใบเดิมได้ครั้งเดียว

**ชั้น Unit Test — ทดสอบตรรกะการคำนวณล้วน ๆ**

| ประเภท | Test Case | คาดหวัง |
|---|---|---|
| Happy Path | ยอด 1,000 + คูปอง 10% | ลด 100 → จ่าย 900 |
| Edge Case | ยอด 500 พอดี | ใช้ได้ ลด 50 |
| Edge Case | ยอด 499 | ใช้ไม่ได้ |
| Edge Case | ยอด 5,000 (10% = 500) | ลดแค่ 200 ตามเพดาน |
| Edge Case | คูปองหมดอายุวันนี้ 23:59 | ยังใช้ได้ |
| Negative | คูปองไม่มีในระบบ | โยน error `COUPON_NOT_FOUND` |
| Negative | ยอดติดลบ | โยน error ไม่ใช่คำนวณต่อ |

pseudocode สั้น ๆ (แค่ให้เห็นโครง ไม่ใช่ syntax ที่ต้องจำ):

```
// Arrange: ยอด 5000 + คูปอง 10% เพดาน 200
// Act:     calcDiscount(5000, coupon)
// Assert:  ผลต้องเป็น 200 ไม่ใช่ 500
```

จุดสำคัญ: เคส "10% = 500 แต่เพดาน 200" คือ **edge case ที่คนลืมบ่อยที่สุด** และเป็นเคสที่เคยทำให้บริษัทจริงขาดทุนมาแล้ว

**ชั้น Integration Test — ทดสอบว่าคูปองถูกบันทึกว่าใช้แล้วจริง**

```
[TEST]
  ↓ เรียก POST /orders พร้อมคูปอง
[ORDER SERVICE จริง]
  ↓
[DATABASE จริง (ชั่วคราว)]
  ↓
ตรวจ: แถวใน coupon_usage ต้องเพิ่ม 1 แถว
ตรวจ: ยิงซ้ำด้วยคูปองเดิม ต้องได้ 409 Conflict
```

> **ให้มองภาพนี้ว่า** "เคสนี้ mock ไม่ได้ เพราะสิ่งที่เรากลัวคือ database จริงจะยอมให้ใช้คูปองซ้ำหรือเปล่า ซึ่งขึ้นกับ unique constraint จริงในตาราง"

**ชั้น E2E Test — เส้นทางที่เสียไม่ได้**

เลือกแค่ 1 เส้น: เข้าเว็บ → เลือกสินค้า → ใส่ตะกร้า → กรอกคูปอง → เห็นยอดลด → จ่ายเงิน → เห็นหน้า "สั่งซื้อสำเร็จ"

ไม่ต้องทำ e2e ให้ครบทุกเคสคูปอง เพราะ:

- เคสคำนวณ unit test คุมครบแล้วในเวลา 20 มิลลิวินาที
- e2e เคสละ 40 วินาที ทำครบ 7 เคสคือเสียเวลา 5 นาทีเพื่อข้อมูลที่รู้อยู่แล้ว

**นี่คือคำตอบของ "จัดสัดส่วน pyramid ยังไง" ที่ใช้ตอบสัมภาษณ์ได้จริง**

### สถานการณ์ที่สอง: Frontend Testing ของหน้าฟอร์มคูปอง

Frontend มักมี 3 ชั้นย่อย:

| ชั้น | ทดสอบอะไร | ตัวอย่าง |
|---|---|---|
| **Logic / Hook test** | ฟังก์ชันคำนวณ, custom hook, reducer | `formatPrice(1000)` → `"฿1,000"` |
| **Component test** | render แล้วผู้ใช้เห็น/กดได้ตามที่ควร | กรอกคูปองผิด → ต้องเห็นข้อความแดง |
| **E2E** | ทั้ง flow ผ่าน browser จริง | ตามข้างบน |

หลักสำคัญของ component test:

> **query จากสิ่งที่ผู้ใช้เห็น (ข้อความ, label, role) ไม่ใช่จาก class name หรือโครงสร้าง DOM**

เพราะถ้าเทสต์ผูกกับ `div > div > span:nth-child(2)` แล้วนักออกแบบขยับ layout — เทสต์แดงทั้งที่ผู้ใช้ไม่เดือดร้อนเลย นั่นคือเทสต์ที่ทดสอบ "วิธีทำ" ไม่ใช่ "พฤติกรรม"

### สถานการณ์ที่สาม: API Testing

API test อยู่กลาง ๆ ระหว่าง integration กับ e2e — มันยิง HTTP จริงเข้า endpoint จริง แต่ไม่เปิด browser

สิ่งที่ API test ต้องตรวจ (ไม่ใช่แค่ status 200):

| ตรวจอะไร | ทำไม |
|---|---|
| **Status code** | 200/201/400/401/403/404/409 ต้องตรงความหมาย |
| **Response schema** | field ครบ ชนิดข้อมูลถูก ไม่มี field ที่ไม่ควรหลุด |
| **ข้อมูลลับต้องไม่หลุด** | `password_hash`, `internal_note` ต้องไม่อยู่ใน response |
| **Auth** | ไม่ส่ง token → 401, token ของคนอื่น → 403 |
| **Validation** | ส่ง body ผิดรูป → 400 พร้อมข้อความที่ใช้ได้ |
| **Idempotency** | ยิง POST ซ้ำด้วย key เดิม → ไม่สร้างซ้ำ |
| **Pagination** | หน้าสุดท้าย, หน้าเกิน, limit ใหญ่เกิน |

> เคสที่คนลืมมากที่สุดใน API test คือ **"ผู้ใช้ A ขอดูข้อมูลของผู้ใช้ B"** — นี่คือช่องโหว่ IDOR ที่หลุดขึ้น production บ่อยที่สุดในโลก และเป็นเคสที่เขียนเทสต์ได้ง่ายมาก

## 7. Compare

### 7.1 Unit vs Integration vs E2E

| หัวข้อ | Unit | Integration | E2E |
|---|---|---|---|
| ขอบเขต | ฟังก์ชัน/คลาสเดียว | หลายชิ้นต่อกัน | ทั้งระบบผ่าน UI |
| ของรอบข้าง | ปลอมหมด | ของจริงบางส่วน (เช่น DB) | ของจริงเกือบหมด |
| ความเร็ว | มิลลิวินาที | วินาที | สิบวินาที–นาที |
| ความเสถียร | สูงมาก | กลาง | ต่ำ (flaky ง่ายสุด) |
| ชี้จุดพังได้แม่นแค่ไหน | แม่นมาก (รู้บรรทัดเลย) | ปานกลาง | หยาบ ("มันพังสักที่") |
| จับบั๊กแบบไหน | ตรรกะผิด | รอยต่อ/สัญญาไม่ตรงกัน | flow พังในสายตาผู้ใช้ |
| ควรมีเท่าไร | เยอะ | กลาง | น้อยแต่สำคัญ |

### 7.2 Mock vs Stub vs Spy vs Fake

| | ทำอะไร | ตรวจอะไร | ใช้เมื่อ |
|---|---|---|---|
| **Stub** | คืนค่าที่กำหนดไว้ | ตรวจผลลัพธ์ปลายทาง | อยากควบคุม input ที่มาจากภายนอก |
| **Mock** | คืนค่าได้ + จำว่าถูกเรียกยังไง | ตรวจว่า "ถูกเรียก" ถูกต้อง | อยากยืนยันว่า side effect เกิดขึ้น เช่น "ต้องส่งอีเมล 1 ครั้ง" |
| **Spy** | ห่อของจริง ยังทำงานจริง | ตรวจการเรียกโดยไม่เปลี่ยนพฤติกรรม | อยากดูว่าถูกเรียกไหม แต่ยังอยากได้ผลจริง |
| **Fake** | implementation ง่าย ๆ ที่ใช้ได้จริง | ตรวจผลลัพธ์ | อยากได้ของจริงแต่เร็ว เช่น in-memory repo |

เส้นแบ่งที่ใช้ตอบสัมภาษณ์:

> **"Stub ตอบคำถามว่า 'ถ้าข้างนอกตอบแบบนี้ ระบบเราทำอะไร' ส่วน Mock ตอบคำถามว่า 'ระบบเราสั่งข้างนอกถูกหรือเปล่า' — ต่างกันที่สิ่งที่เรา assert"**

และคำเตือน: **mock เยอะเกินไปคือกลิ่นของ design ที่ผูกกันแน่นเกินไป** ถ้าเทสต์หนึ่งตัวต้อง mock 8 อย่างถึงจะรันได้ ปัญหาไม่ได้อยู่ที่เทสต์ แต่อยู่ที่คลาสนั้นทำงานเยอะเกินไป

### 7.3 Happy Path vs Edge Case vs Negative Case

| | คืออะไร | ตัวอย่าง (ระบบโอนเงิน) |
|---|---|---|
| **Happy Path** | ทุกอย่างถูกต้อง ระบบทำงานปกติ | โอน 500 จากบัญชีที่มี 1,000 → สำเร็จ |
| **Edge Case** | ค่าอยู่ตรงขอบของสิ่งที่รับได้ | โอน 1,000 จากบัญชีที่มี 1,000 พอดี |
| **Negative Case** | input ผิด/สิทธิ์ไม่พอ ต้องถูกปฏิเสธอย่างสุภาพ | โอน -100 / โอนจากบัญชีคนอื่น |

จำง่าย ๆ: **Happy = ตั้งใจให้ผ่าน / Edge = ตรงเส้น / Negative = ตั้งใจให้ไม่ผ่าน แต่ต้องไม่ระเบิด**

junior เขียนแต่ happy path → ระบบผ่านเทสต์ 100% แล้วพังใน production ทันทีที่เจอผู้ใช้จริง เพราะผู้ใช้จริงกดผิดตลอดเวลา

### 7.4 Regression vs Smoke

| | Regression Test | Smoke Test |
|---|---|---|
| ถามว่า | "ของเก่ายังทำงานครบไหม" | "ระบบยังหายใจอยู่ไหม" |
| จำนวนเคส | เยอะ (สะสมขึ้นเรื่อย ๆ) | น้อยมาก (5–15 เคส) |
| รันเมื่อไร | ทุกครั้งที่แก้โค้ด (ใน CI) | ทันทีหลัง deploy |
| ใช้เวลา | นาที–สิบนาที | ไม่กี่สิบวินาที |
| ถ้าไม่ผ่าน | ห้าม merge | rollback ทันที |

### 7.5 Load vs Stress vs Soak

| | เป้าหมาย | คำถามที่ตอบ |
|---|---|---|
| **Load Test** | โหลดระดับที่คาดว่าจะเจอ | "วันพีคเรารอดไหม" |
| **Stress Test** | ดันจนพัง | "พังที่เท่าไร และพังยังไง" |
| **Soak Test** | โหลดปานกลาง แต่นานหลายชั่วโมง | "มี memory leak / connection leak ไหม" |
| **Spike Test** | โหลดพุ่งฉับพลัน | "โปรนาทีทองมาแล้วเราตายไหม" |

### 7.6 QA vs Developer Testing

นี่คือคำถามสัมภาษณ์ที่คนตอบผิดมากที่สุดข้อหนึ่ง เพราะคนชอบตอบว่า "QA คือคนกดเว็บ" ซึ่งดูถูกวิชาชีพและตอบไม่ตรง

| | Developer Testing | QA |
|---|---|---|
| มุมมอง | มุมโค้ด — "โค้ดฉันทำงานตามที่ฉันตั้งใจไหม" | มุมผู้ใช้/ธุรกิจ — "ของที่ทำมา ตอบโจทย์จริงไหม" |
| รู้ข้างในไหม | รู้ (white box) | มักไม่รู้ (black box) โดยตั้งใจ |
| จับอะไรได้ดี | ตรรกะผิด, regression, edge case ของฟังก์ชัน | requirement เข้าใจผิด, UX พัง, flow ที่ไม่มีใครคิดถึง |
| จุดบอด | "ฉันเขียนถูกตามที่ฉันเข้าใจ — แต่ฉันเข้าใจโจทย์ผิด" | ไม่เห็นว่าข้างในเสี่ยงตรงไหน |
| เวลาที่ทำ | ระหว่างเขียน (shift left) | ก่อน release / ระหว่าง sprint |

ประโยคที่ควรพูด:

> "Developer test พิสูจน์ว่า **เราสร้างของถูกวิธี (build the thing right)** ส่วน QA พิสูจน์ว่า **เราสร้างของที่ถูกต้อง (build the right thing)** — มันไม่แทนกัน และมี QA ไม่ได้แปลว่า developer เลิกเขียนเทสต์"

## 8. Common Mistakes

### 8.1 คิดว่า Coverage สูง = ปลอดภัย ← ข้อใหญ่ที่สุด

นี่คือความเข้าใจผิดที่แพงที่สุดในเรื่อง testing

**Coverage วัดว่า "บรรทัดนี้ถูกรันระหว่างเทสต์" ไม่ได้วัดว่า "บรรทัดนี้ถูกตรวจสอบ"**

ตัวอย่างที่เห็นภาพชัด:

```
// เทสต์ที่ให้ coverage 100% แต่ไร้ค่า
calcDiscount(1000, coupon)   // เรียกฟังก์ชัน
// ...แล้วจบ ไม่มี assert สักบรรทัด
```

ฟังก์ชันถูกรันครบทุกบรรทัด → coverage รายงาน 100%
แต่ถ้าฟังก์ชันคืนค่าผิดทั้งหมด เทสต์ก็ยังเขียว เพราะไม่มีใครถามว่าผลถูกไหม

```
[โค้ดถูกรัน]  ──→ coverage นับให้
[ผลถูกตรวจ]  ──→ coverage ไม่รู้เรื่องเลย
```

> **ให้มองภาพนี้ว่า** "Coverage เหมือนบันทึกว่ามีคนเดินผ่านทุกห้องในตึกครบแล้ว แต่ไม่ได้บอกว่ามีใครเปิดตู้ดูข้างในสักตู้"

สิ่งที่ coverage มองไม่เห็นเลย:

| มองไม่เห็น | ตัวอย่าง |
|---|---|
| **Assertion ที่หายไป** | รันแล้วไม่ตรวจผล |
| **เคสที่ไม่ได้คิดถึง** | โค้ดไม่มีเงื่อนไขรองรับ "จำนวนติดลบ" — ไม่มีบรรทัดให้ cover ตั้งแต่แรก |
| **Combination ของ input** | `if (a && b)` cover ครบได้โดยไม่เคยลอง a=true, b=false |
| **Requirement ที่เข้าใจผิด** | โค้ดทำตามที่เขียนทุกอย่าง แต่ธุรกิจต้องการอีกแบบ |
| **ปัญหา concurrency / race** | รันทีละเคสไม่เจอ |
| **Performance** | ถูกต้องแต่ช้า 40 วินาที |

**วิธีใช้ coverage ให้ถูกต้อง:**

- ใช้เป็น **เข็มทิศชี้จุดที่ยังไม่เคยแตะ** (ไฟล์ payment coverage 0% = สัญญาณอันตรายจริง)
- **ห้ามใช้เป็น KPI** ที่ให้คนไล่ตามตัวเลข เพราะทีมจะเขียนเทสต์ขยะเพื่อดันตัวเลข
- ดู **branch coverage** มากกว่า line coverage เพราะมันบังคับให้ลองทั้งสองทางของ if
- 60% ที่เทสต์ตรงจุดสำคัญ ดีกว่า 95% ที่เทสต์ getter/setter

ประโยคตอบสัมภาษณ์:

> "Coverage ต่ำบอกอะไรเราได้แน่นอนว่ามีจุดที่ไม่มีใครดูแล แต่ coverage สูงไม่ได้บอกอะไรเลยว่าปลอดภัย — มันเป็น necessary แต่ไม่ใช่ sufficient"

### 8.2 Flaky Test — ปล่อยไว้แล้วเทสต์ทั้งชุดจะตายทั้งระบบ

**Flaky test = เทสต์ที่บางรอบผ่าน บางรอบไม่ผ่าน ทั้งที่โค้ดและ input ไม่เปลี่ยน**

ทำไมมันร้ายแรงกว่าที่คิด:

```
[เทสต์แดงโดยไม่มีเหตุผล]
        ↓
[ทีมเริ่มกด "rerun" เป็นนิสัย]
        ↓
[ทีมเลิกเชื่อสีแดง]
        ↓
[วันที่มันแดงเพราะบั๊กจริง ก็โดนกด rerun เหมือนกัน]
        ↓
[บั๊กขึ้น production]
```

> **ให้มองภาพนี้ว่า** "Flaky test ไม่ได้ทำให้เทสต์ตัวนั้นไร้ค่า มันทำให้ทีมเลิกเชื่อเทสต์ทุกตัวในระบบ"

**สาเหตุหลักของ flaky test:**

| สาเหตุ | อาการ | วิธีแก้ |
|---|---|---|
| **Timing / รอไม่พอ** | e2e กดเร็วกว่า element โผล่ | รอแบบมีเงื่อนไข (รอจนเห็น element) ห้าม `sleep(2000)` ตายตัว |
| **ลำดับเทสต์ผูกกัน** | รันเดี่ยวผ่าน รันรวมแดง | แต่ละเทสต์ต้องเตรียมข้อมูลของตัวเองและล้างเอง |
| **State ค้างจากเทสต์ก่อน** | รอบสองแดงเพราะข้อมูลซ้ำ | reset database / clear cache ระหว่างเคส |
| **เวลา / timezone / วันที่** | แดงเฉพาะตอนข้ามเดือน หรือ 23:59 | freeze เวลาในเทสต์ อย่าใช้ `now()` ตรง ๆ |
| **ค่าสุ่ม / UUID** | แดงเป็นบางรอบแบบไร้แพตเทิร์น | ใส่ seed ให้ random |
| **รันขนานแย่งทรัพยากร** | แดงเฉพาะตอน CI รัน 8 job พร้อมกัน | แยก database/schema ต่อ worker |
| **พึ่ง network ภายนอกจริง** | แดงตอน API ปลายทางช้า | mock ที่ขอบระบบ |
| **Async ไม่ได้รอให้จบ** | บางรอบ assert ก่อนงานเสร็จ | await ให้ครบ อย่าพึ่ง timing |

**วิธีจัดการเมื่อเจอ flaky test (ลำดับที่ควรทำ):**

```
[พบเทสต์ flaky]
        ↓
1. บันทึกไว้ทันที (ห้ามแค่กด rerun แล้วเงียบ)
        ↓
2. แยกมันออกจาก pipeline หลัก (quarantine) เพื่อไม่ให้ทีมเลิกเชื่อสีแดง
        ↓
3. รันซ้ำ 50-100 รอบ หาแพตเทิร์นว่าแดงเมื่อไร
        ↓
4. หาสาเหตุจริงจากตารางข้างบน แล้วแก้ที่ต้นเหตุ
        ↓
5. ถ้าแก้ไม่ได้ใน 2 สัปดาห์ → ลบทิ้ง
```

> **ให้มองภาพนี้ว่า** "การกักตัวเทสต์ที่ป่วยไว้ก่อน ดีกว่าปล่อยให้มันทำให้ทั้งทีมเลิกไว้ใจระบบเตือนภัย"

ข้อควรระวัง: **auto-retry คือยาแก้ปวด ไม่ใช่การรักษา** ใส่ retry ได้ชั่วคราวเพื่อไม่ให้ทีมติดขัด แต่ต้องมี ticket ตามแก้เสมอ ไม่งั้นมันจะซ่อนบั๊ก race condition จริง ๆ ไว้

### 8.3 เขียนแต่ Happy Path

เทสต์ 40 ตัว แต่ทุกตัวคือ "ทุกอย่างถูก → สำเร็จ"
ผู้ใช้จริงกดผิด ส่งค่าว่าง เน็ตหลุดกลางทาง กดปุ่มรัว 5 ครั้ง — ไม่มีเทสต์ตัวไหนครอบคลุมเลย

**กฎง่าย ๆ: ทุก happy path ควรมีอย่างน้อย 1 negative และ 1 edge คู่กัน**

### 8.4 Mock ทุกอย่างจนเทสต์ไม่ได้ทดสอบอะไรเลย

ถ้า mock ทุกชิ้นที่โค้ดเรียกใช้ สิ่งที่เหลือให้เทสต์คือ "โค้ดของเราเรียก mock ตามลำดับที่เราเขียนไว้" — ซึ่งเป็นการเทสต์ว่าเราเขียนโค้ดเหมือนที่เราเขียน

**กฎ: mock เฉพาะ "ขอบของระบบ" — network ภายนอก, การส่งอีเมล, การตัดบัตร, เวลา, การสุ่ม**
ส่วนตรรกะของเราเอง ให้ใช้ของจริง

### 8.5 เทสต์ผูกกับโครงสร้างภายใน

เทสต์ที่ assert ว่า "ต้องเรียก method ชื่อนี้" หรือ query จาก CSS class
พอ refactor แล้วแดงทั้งกระดาน ทั้งที่ผู้ใช้ไม่รู้สึกอะไรเลย → คนก็จะโทษว่า "เทสต์กวนเวลา" แล้วเลิกเขียน

### 8.6 เทสต์ช้าจนไม่มีใครรัน

unit test ที่กิน 8 นาที = ไม่มีใครรันก่อน commit = เทสต์ตายตั้งแต่ยังไม่เกิด
มัก มีสาเหตุจาก unit test ที่แอบต่อ database หรือ network จริง

### 8.7 ลบเทสต์ที่แดงเพื่อให้ pipeline เขียว

เห็นบ่อยมากใน codebase จริง และเป็นเหตุผลหลักที่บั๊กเดิมกลับมาซ้ำ ๆ
ถ้าต้องปิดเทสต์ชั่วคราว ต้องมี ticket + วันหมดอายุเสมอ

### 8.8 คิดว่า "มี QA แล้ว dev ไม่ต้องเขียนเทสต์"

QA จับบั๊กตอนของเสร็จแล้ว → แพงกว่าจับตอนเขียนหลายเท่า
ยิ่งบั๊กถูกเจอช้าเท่าไร ค่าแก้ยิ่งแพงขึ้นเรื่อย ๆ:

```
เจอตอนเขียนโค้ด     → ค่าใช้จ่าย 1x
เจอตอน code review  → 3x
เจอตอน QA           → 10x
เจอตอน production   → 50x+ (มีค่าเสียหายทางธุรกิจด้วย)
```

> **ให้มองภาพนี้ว่า** "บั๊กเหมือนรอยรั่วบนเรือ — อุดตอนยังอยู่อู่ต่อเรือใช้เทปหนึ่งม้วน อุดตอนอยู่กลางทะเลใช้ทั้งลูกเรือ"

### 8.9 อะไรที่ **ไม่ควร** เขียนเทสต์

ข้อนี้สำคัญพอ ๆ กับ "ควรเทสต์อะไร" และเป็นคำถามที่แยก mid ออกจาก junior ได้ทันที
เพราะเทสต์ทุกตัวมี **ต้นทุนการดูแล** — ไม่ใช่ของฟรี

| ไม่ควรเทสต์ | เหตุผล |
|---|---|
| **Getter / Setter ที่ไม่มีตรรกะ** | ทดสอบว่าภาษาโปรแกรมทำงานได้ ไม่ใช่ทดสอบโค้ดเรา |
| **Library / Framework ของคนอื่น** | React, Spring, ORM มีเทสต์ของเขาเองแล้ว หน้าที่เราคือเทสต์ว่า *เราใช้มันถูกไหม* |
| **Third-party API จริงใน unit/CI** | ช้า, flaky, มีค่าใช้จ่าย, ล่มแล้วเราแดงฟรี — ให้ mock แล้วทำ contract test แยก |
| **โค้ดสร้างอัตโนมัติ (generated code)** | ไม่ได้เขียนเอง เปลี่ยนตาม generator |
| **Config / constant ล้วน ๆ** | `const TAX = 0.07` ไม่ต้องมีเทสต์ยืนยันว่ามันเท่ากับ 0.07 |
| **CSS / สีปุ่ม / ระยะห่าง pixel** | เปลี่ยนบ่อยมาก เทสต์จะแดงทุกสัปดาห์ (ใช้ visual review แทน) |
| **Implementation detail ภายใน (private method)** | ทดสอบผ่าน public behavior แทน ไม่งั้น refactor ไม่ได้ |
| **โค้ด prototype / spike ที่จะทิ้งใน 2 สัปดาห์** | ต้นทุนดูแลสูงกว่าประโยชน์ |
| **UI ที่ยังเปลี่ยนทุกวันในช่วงออกแบบ** | รอให้นิ่งก่อนแล้วค่อยลง e2e |
| **เคส combination ทุกแบบแบบ brute force** | เทสต์ 500 เคสที่ต่างกันนิดเดียว = ช้าและไม่มีใครดูแล — ใช้ boundary + equivalence class แทน |

**หลักตัดสินใจ 1 ประโยค:**

> "เขียนเทสต์เมื่อ **มันพังแล้วเจ็บ** และ **มันมีโอกาสพังจริง** — ถ้าพังแล้วไม่มีใครเดือดร้อน หรือมันพังไม่ได้อยู่แล้ว อย่าเสียเวลาดูแลมัน"

จัดลำดับความสำคัญของสิ่งที่ควรเทสต์ก่อน:

```
1. ตรรกะเกี่ยวกับเงิน / สิทธิ์ / ข้อมูลส่วนตัว   ← เทสต์ให้แน่นที่สุด
2. ตรรกะธุรกิจที่มีเงื่อนไขซับซ้อน
3. บั๊กที่เคยเกิดขึ้นแล้ว (regression)
4. จุดที่แก้บ่อย
5. flow หลักที่ผู้ใช้ใช้ทุกวัน (e2e แค่ไม่กี่เส้น)
—— เส้นแบ่ง ——
6. อย่างอื่น (เขียนเมื่อว่างหรือเมื่อเจอปัญหา)
```

## 9. Debugging

### 9.1 เทสต์แดง — ไล่ตามลำดับนี้

```
[TEST แดง]
     ↓
1. แดงเพราะโค้ดพังจริง หรือเพราะเทสต์เขียนผิด?
     ↓  (อ่าน assertion กับ error message ก่อนเสมอ — อย่าเพิ่งแก้โค้ด)
2. รันเฉพาะเทสต์ตัวนั้นเดี่ยว ๆ ยังแดงไหม?
     ↓  ถ้าเดี่ยวผ่าน แต่รวมแดง → ปัญหา state ค้าง / ลำดับเทสต์
3. มันแดงตั้งแต่ commit ไหน?  (git bisect)
     ↓
4. ดูว่า input จริงที่เข้าไปคืออะไร (log ค่าตอน arrange)
     ↓
5. แก้ที่ต้นเหตุ → เขียนเทสต์เพิ่มถ้าพบว่าเคสนี้เคยหลุด
```

> **ให้มองภาพนี้ว่า** "เทสต์แดงคือพยาน ไม่ใช่จำเลย — งานแรกคือฟังว่ามันเห็นอะไร ไม่ใช่รีบทำให้มันเงียบ"

### 9.2 เทสต์เขียวหมดแต่ production พัง — ไล่ดูอะไร

| ตรวจอะไร | คำถาม |
|---|---|
| **ข้อมูลจริงต่างจากข้อมูลเทสต์ไหม** | production มีค่า null, ตัวอักษรไทย, ค่าที่เก่ากว่า schema ปัจจุบัน |
| **Config / env ต่างกันไหม** | timezone, encoding, feature flag, limit ต่าง |
| **Concurrency** | เทสต์รันทีละคน production มี 500 คนพร้อมกัน |
| **ปริมาณ** | เทสต์มี 10 แถว production มี 10 ล้านแถว → timeout |
| **Integration จริง** | เรา mock เขาไว้ แต่ของจริงตอบอีกรูปแบบ (contract drift) |
| **เคสที่ไม่มีใครคิดถึง** | ผู้ใช้ทำสิ่งที่เราไม่เคยจินตนาการ |

> ถ้าตอบข้อนี้ในสัมภาษณ์ได้ดี คุณจะดูเป็นคนที่เคยดูแล production จริง

### 9.3 เจอบั๊กบน production → ต้องทำตามลำดับนี้ (หลักการสำคัญ)

นี่คือหลักการที่ทีมที่ดีทุกทีมใช้ และเป็นคำตอบที่ interviewer รอฟัง:

```
[เจอบั๊กบน production]
        ↓
1. หยุดเลือดก่อน (rollback / feature flag ปิด) — ผู้ใช้สำคัญกว่าความสวยของกระบวนการ
        ↓
2. เขียนเทสต์ที่ "fail ซ้ำอาการนั้น" ให้ได้ก่อน   ← ขั้นตอนที่ห้ามข้าม
        ↓
3. ยืนยันว่าเทสต์ตัวนั้น "แดง" ด้วยเหตุผลเดียวกับที่ production พัง
        ↓
4. ค่อยแก้โค้ด
        ↓
5. เทสต์เปลี่ยนเป็นเขียว = พิสูจน์แล้วว่าแก้ตรงจุดจริง
        ↓
6. เทสต์ตัวนี้อยู่ใน repo ตลอดไป = regression test ที่กันบั๊กเดิมกลับมา
```

> **ให้มองภาพนี้ว่า** "การเขียนเทสต์ที่พังก่อนแก้ คือการบังคับตัวเองให้พิสูจน์ว่าเราเข้าใจสาเหตุจริง ไม่ใช่แค่ไปขยับโค้ดจนอาการหาย"

ทำไมขั้นที่ 2 สำคัญมาก:

| ถ้าข้ามขั้นนี้ | จะเกิดอะไร |
|---|---|
| ไม่มีหลักฐานว่าเข้าใจสาเหตุ | อาจแก้ที่ปลายเหตุ อาการหายเพราะบังเอิญ |
| ไม่รู้ว่าแก้แล้วหายจริงไหม | ต้องไปกดลอง production เอง ซึ่งเสี่ยง |
| ไม่มีอะไรกันบั๊กเดิมกลับมา | อีก 6 เดือนมีคน refactor แล้วบั๊กเดิมโผล่อีก |
| ไม่รู้ว่ามันเกิดได้ในเงื่อนไขไหน | เขียนเทสต์บังคับให้ระบุเงื่อนไขชัดเจน |

ประโยคที่ควรพูดในห้องสัมภาษณ์:

> "ผมจะไม่แก้บั๊กที่ยังไม่มีเทสต์ที่ reproduce ได้ เพราะถ้า reproduce ไม่ได้ ผมก็ไม่รู้ว่าผมแก้ถูกหรือแค่ทำให้มันหายไปชั่วคราว"

ข้อยกเว้นที่ต้องพูดคู่กันเสมอ: **ถ้าระบบกำลังล่มและเงินกำลังไหลออก ให้หยุดเลือดก่อน (ขั้น 1) แล้วค่อยกลับมาทำขั้น 2-6 หลังสถานการณ์นิ่ง** — การยึดกระบวนการตอนไฟไหม้คือความผิดพลาดอีกแบบ

### 9.4 เทสต์ช้า — ไล่ดูตามนี้

```
[TEST SUITE ช้า]
     ↓
1. ดูว่าเทสต์ตัวไหนกินเวลาสูงสุด (runner บอกได้)
     ↓
2. unit test ตัวนั้นแอบต่อ database / network จริงหรือเปล่า
     ↓
3. มี sleep แบบตายตัวไหม (แปลงเป็น wait แบบมีเงื่อนไข)
     ↓
4. setup ซ้ำทุกเคสหรือเปล่า (บางอย่าง setup ครั้งเดียวต่อไฟล์ได้)
     ↓
5. รันขนานได้ไหม (ต้องแยกข้อมูลต่อ worker ก่อน)
     ↓
6. e2e เยอะเกินสัดส่วนไหม → ย้ายเคสลงชั้นล่าง
```

> **ให้มองภาพนี้ว่า** "เทสต์ที่ช้าจะค่อย ๆ ถูกคนเลี่ยงไม่รัน จนสุดท้ายมันเท่ากับไม่มี — ความเร็วคือฟีเจอร์ของชุดเทสต์"

## 10. Interview Questions

### 🟢 Junior

1. Unit test กับ Integration test ต่างกันยังไง ยกตัวอย่างจากงานที่เคยทำ
2. Testing Pyramid คืออะไร ทำไมชั้นล่างต้องเยอะกว่าชั้นบน
3. Mock กับ Stub ต่างกันยังไง
4. Happy path / Edge case / Negative case ต่างกันยังไง ยกตัวอย่างฟอร์มสมัครสมาชิก
5. Test coverage คืออะไร และ 100% แปลว่าไม่มีบั๊กหรือเปล่า
6. ทำไมต้องเขียน automated test ทั้งที่กดทดสอบเองก็ได้
7. Regression test คืออะไร
8. E2E test คืออะไร ทำไมถึงไม่ทำทุกเคสด้วย e2e

### 🟡 Mid

1. ถ้าให้คุณเข้าโปรเจกต์ที่ไม่มีเทสต์เลยและมีโค้ด 3 ปี คุณจะเริ่มเขียนเทสต์จากตรงไหน เพราะอะไร
2. เทสต์อะไรที่คุณ **ไม่** เขียน และเพราะอะไร
3. คุณจัดการ flaky test ยังไง และทำไมมันอันตรายกว่าที่คนคิด
4. Mock มากเกินไปมีปัญหาอะไร รู้ได้ยังไงว่ามากเกินไป
5. เจอบั๊กบน production คุณทำอะไรเป็นอันดับแรก และเขียนเทสต์ตอนไหน
6. ทีมตั้ง KPI ว่า coverage ต้อง 90% คุณเห็นด้วยไหม เพราะอะไร
7. Load test กับ Stress test ต่างกันยังไง และคุณจะดูตัวเลขอะไรบ้าง
8. API test ควรตรวจอะไรบ้างนอกจาก status code
9. Frontend component test ควร query element จากอะไร และทำไมไม่ควร query จาก class name
10. QA กับ developer testing แบ่งหน้าที่กันยังไง มี QA แล้วทำไม dev ยังต้องเขียนเทสต์

### 🔴 Senior

1. ทีมมี e2e 600 เคส รัน 90 นาที และแดงสุ่ม ๆ สัปดาห์ละ 3 ครั้ง คุณจะวางแผนแก้ยังไงใน 1 ไตรมาส
2. คุณจะออกแบบ test strategy สำหรับระบบ microservice ที่มี 12 service ยังไง ใครเทสต์รอยต่อ
3. Contract test แก้ปัญหาอะไรที่ integration test ทั่วไปแก้ไม่ได้
4. เราควรรัน integration test กับ database จริงหรือ in-memory database trade-off คืออะไร
5. ถ้า business กดดันให้ปล่อยฟีเจอร์ภายใน 2 วันและไม่มีเวลาเขียนเทสต์ คุณจะตัดสินใจยังไง และจะสื่อสารความเสี่ยงยังไง
6. ระบบ payment ของคุณต้องการความมั่นใจระดับไหน และคุณจะวัด "ความมั่นใจ" ยังไงนอกจาก coverage
7. เทสต์ในระบบเก่าผูกกับ implementation หนักมาก จะ refactor โค้ดโดยไม่ทำให้เทสต์ทั้งกระดานแดงได้ยังไง
8. คุณจะตัดสินใจ rollback หรือ fix forward ตอน production พังจากอะไรบ้าง

## 11. Answer Like a Developer

### โครงการตอบ 4 ขั้น (ใช้ได้กับเกือบทุกคำถามเรื่องเทสต์)

```
1. บอกหลักการสั้น ๆ 1 ประโยค
       ↓
2. บอกว่าใช้จริงตอนไหน + ยกตัวอย่างจากงานที่เคยทำ
       ↓
3. บอก trade-off / ข้อจำกัด (ตรงนี้ทำให้ดู senior)
       ↓
4. ปิดด้วยวิธีตัดสินใจของตัวเอง
```

> **ให้มองภาพนี้ว่า** "คนสัมภาษณ์ไม่ได้อยากรู้ว่าคุณท่องนิยามได้ เขาอยากรู้ว่าตอนต้องเลือกจริงคุณคิดยังไง"

### ตัวอย่างการตอบ: "Coverage 100% ปลอดภัยไหม"

❌ แบบท่องจำ: "ไม่ปลอดภัย เพราะ coverage ไม่ใช่ทุกอย่าง"

✅ แบบ developer:

> "ไม่ครับ เพราะ coverage วัดแค่ว่าบรรทัดนั้น *ถูกรัน* ระหว่างเทสต์ ไม่ได้วัดว่ามันถูก *ตรวจสอบ*
> ผมเคยเจอเทสต์ที่เรียกฟังก์ชันแล้วไม่มี assert เลย — coverage ยังขึ้น 100%
> แล้วมันก็มองไม่เห็นเคสที่เราไม่ได้คิดถึงตั้งแต่แรก เพราะถ้าโค้ดไม่มีเงื่อนไขรองรับค่าติดลบ ก็ไม่มีบรรทัดให้ cover
> ผมเลยใช้ coverage เป็นเข็มทิศหาจุดที่ไม่มีใครดูแล เช่นถ้าโมดูล payment อยู่ที่ 0% นั่นคือสัญญาณจริง
> แต่ผมไม่ตั้งมันเป็น KPI เพราะพอเป็น KPI คนจะเขียนเทสต์ getter เพื่อดันตัวเลข ซึ่งเพิ่มต้นทุนดูแลโดยไม่เพิ่มความปลอดภัย"

### ตัวอย่างการตอบ: "เจอบั๊กบน production ทำยังไง"

✅

> "ลำดับของผมคือ หยุดเลือดก่อนเสมอ — rollback หรือปิด feature flag ให้ผู้ใช้กลับมาใช้ได้
> จากนั้นก่อนแก้โค้ดใด ๆ ผมจะเขียนเทสต์ที่ reproduce อาการนั้นให้ fail ให้ได้ก่อน
> เพราะถ้า reproduce ไม่ได้ แปลว่าผมยังไม่เข้าใจสาเหตุ แก้ไปก็แค่เดา
> พอเทสต์แดงด้วยเหตุผลเดียวกับ production แล้วค่อยแก้ พอมันเขียวคือมีหลักฐานว่าแก้ตรงจุด
> และเทสต์ตัวนั้นจะอยู่ต่อเป็น regression test กันบั๊กเดิมกลับมา
> ปิดท้ายด้วย postmortem แบบไม่โทษคน ว่าทำไมด่านก่อนหน้าไม่จับ แล้วเพิ่มด่านตรงนั้น"

### ตัวอย่างการตอบ: "เทสต์อะไรที่คุณไม่เขียน"

✅

> "ผมไม่เขียนเทสต์ให้ getter/setter ที่ไม่มีตรรกะ ไม่เขียนเทสต์ทดสอบ framework ของคนอื่น
> และไม่เอา third-party API จริงเข้ามาใน CI เพราะมันช้าและทำให้เทสต์ flaky โดยที่โค้ดเราไม่ได้ผิด
> หลักของผมคือเทสต์ทุกตัวมีต้นทุนดูแล ผมเลยถามสองข้อ: พังแล้วเจ็บไหม และมีโอกาสพังจริงไหม
> ถ้าทั้งสองข้อเป็นใช่ ผมเทสต์แน่นมาก โดยเฉพาะเรื่องเงิน สิทธิ์ และข้อมูลส่วนตัว
> ถ้าไม่ ผมเอาเวลาไปเทสต์ตรงที่เสี่ยงกว่า"

### สิ่งที่ห้ามพูด

| ❌ ห้าม | ทำไม |
|---|---|
| "เทสต์เยอะ ๆ ไว้ก่อน ดีกว่า" | ไม่คิดเรื่องต้นทุนการดูแล |
| "ผมไม่ค่อยเขียนเทสต์ เพราะมี QA" | สื่อว่าผลักความรับผิดชอบ |
| "E2E ดีที่สุดเพราะเหมือนผู้ใช้จริง" | ไม่เห็น trade-off เรื่องความช้าและ flaky |
| "coverage 100% = คุณภาพดี" | เข้าใจเครื่องมือผิด |
| "flaky test ก็แค่กด rerun" | สัญญาณอันตรายสำหรับทีม |

## 12. One-Minute Review

อ่านรอบเดียวก่อนเข้าห้องสัมภาษณ์:

- **Test มีไว้ให้กล้าเปลี่ยนโค้ด** ไม่ใช่แค่หาบั๊ก — นี่คือเหตุผลอันดับ 1
- **Testing Pyramid**: unit เยอะ (เร็ว ถูก แม่น) → integration กลาง (จับรอยต่อ) → e2e น้อย (ช้า เปราะ แต่เหมือนผู้ใช้จริง)
- **โครงเทสต์ = Arrange → Act → Assert** หนึ่งเคสควรมี Act เดียว
- **ทดสอบพฤติกรรม ไม่ใช่วิธีทำ** — refactor แล้วเทสต์ต้องไม่แดง
- **Stub = ป้อนค่าเข้า / Mock = ตรวจว่าเราสั่งออกถูก / Spy = ของจริงที่ถูกจับตา / Fake = ของปลอมที่ใช้ได้จริง**
- **Mock แค่ขอบระบบ** (network, email, payment, เวลา, random) — mock เยอะ = design ผูกกันแน่นเกินไป
- **Happy / Edge / Negative ต้องมาเป็นชุด** — เขียนแต่ happy path คือกับดักของ junior
- **Coverage วัดว่าโค้ดถูก "รัน" ไม่ได้วัดว่าถูก "ตรวจ"** — ไม่มี assert ก็ยังได้ 100%
  ใช้เป็นเข็มทิศหาจุดที่ไม่มีใครดูแล ห้ามใช้เป็น KPI
- **Flaky test อันตรายกว่าที่คิด** เพราะมันทำให้ทีมเลิกเชื่อเทสต์ทั้งระบบ
  สาเหตุหลัก: timing, state ค้าง, ลำดับเทสต์, เวลา/timezone, ค่าสุ่ม, รันขนาน, network จริง
  วิธีจัดการ: บันทึก → quarantine → รันซ้ำหาแพตเทิร์น → แก้ต้นเหตุ → แก้ไม่ได้ก็ลบ (retry คือยาแก้ปวด)
- **เจอบั๊ก production: หยุดเลือด → เขียนเทสต์ให้ fail ซ้ำอาการ → แก้ → เขียว → เก็บไว้เป็น regression → postmortem**
- **Smoke test = เช็กลมหายใจหลัง deploy** ไม่กี่เคส ถ้าแดงคือ rollback
- **Load = ไหวไหมที่โหลดปกติ / Stress = พังที่เท่าไรและพังยังไง** ดู p95/p99 ไม่ใช่ค่าเฉลี่ย
- **API test ต้องตรวจ schema, สิทธิ์ (ผู้ใช้ A ดูของ B ไม่ได้), ข้อมูลลับไม่หลุด** ไม่ใช่แค่ 200
- **Frontend test ให้ query จากสิ่งที่ผู้ใช้เห็น** ไม่ใช่ class name
- **ไม่ควรเทสต์**: getter/setter, framework คนอื่น, third-party API จริงใน CI, generated code, CSS/pixel, private method, โค้ดที่จะทิ้ง
- **QA = build the right thing / Dev test = build the thing right** ไม่แทนกัน
- ยิ่งเจอบั๊กช้า ยิ่งแพง — เจอตอนเขียน 1x เจอบน production 50x

## 13. Memory Card

### จำ 5 อย่างนี้พอ

1. **Pyramid = ตาข่ายซ้อนชั้น** — ล่างถี่และเร็วเยอะ ๆ บนหยาบและช้าแต่เหมือนผู้ใช้จริง เก็บไว้เฉพาะเส้นที่เสียไม่ได้
2. **Coverage = ไฟฉายส่องห้อง** — ส่องถึงไม่ได้แปลว่าตรวจแล้ว ไม่มี assert ก็ 100% ได้
3. **Flaky = นาฬิกาปลุกที่บางวันไม่ดัง** — ปล่อยไว้แล้วทีมจะเลิกเชื่อสัญญาณเตือนทั้งหมด กักตัวแล้วแก้ต้นเหตุ
4. **บั๊ก production = เขียนเทสต์ให้แดงก่อน แล้วค่อยแก้** — หยุดเลือดก่อน → reproduce ด้วยเทสต์ → แก้ → เทสต์อยู่ต่อเป็นยาม
5. **เทสต์ทุกตัวมีค่าดูแลรายเดือน** — เขียนเมื่อ "พังแล้วเจ็บ" และ "พังได้จริง" เท่านั้น

### Keyword สั้น

**Testing Pyramid** → ล่างเยอะ บนน้อย
**Unit Test** → เทสชิ้นเดียว ตัดของรอบข้างออก
**Integration Test** → เทสรอยต่อด้วยของจริง
**E2E Test** → หุ่นยนต์กดแทนผู้ใช้
**Test Case** → 1 เคส 1 คำถาม
**Arrange-Act-Assert** → เตรียม ทำ ตรวจ
**Mock** → ของปลอมที่จดว่าถูกเรียกยังไง
**Stub** → ของปลอมที่ตอบค่าตายตัว
**Spy** → ของจริงที่มีกล้องจับ
**Fake** → ของปลอมที่ใช้งานได้จริง
**Happy Path** → ทางที่ทุกอย่างถูก
**Edge Case** → ค่าตรงขอบ
**Negative Case** → ต้องถูกปฏิเสธอย่างสุภาพ
**Regression Test** → ยามกันบั๊กเดิมกลับมา
**Smoke Test** → เช็กลมหายใจหลัง deploy
**Load Test** → วันพีครอดไหม
**Stress Test** → พังที่เท่าไร พังยังไง
**Coverage** → % โค้ดที่ถูกรัน ไม่ใช่ถูกตรวจ
**Flaky Test** → แดงสุ่ม ทำลายความเชื่อใจ
**API Test** → ตรวจ schema + สิทธิ์ ไม่ใช่แค่ 200
**QA** → build the right thing
**Developer Testing** → build the thing right

### Flow ที่ต้องวาดได้จากความจำ

```
เขียนโค้ด
   ↓
Unit Test (วินาที)
   ↓
Integration Test (นาที)
   ↓
Build → Staging
   ↓
E2E Test (สิบนาที)
   ↓
Deploy Production
   ↓
Smoke Test
   ↓
Monitoring
```

> **ให้มองภาพนี้ว่า** "ทั้ง pipeline คือด่านเรียงจากถูกและเร็วไปหาแพงและช้า เพื่อให้ของเสียตกตั้งแต่ด่านแรก"

```
เจอบั๊กบน production
        ↓
หยุดเลือด (rollback / ปิด flag)
        ↓
เขียนเทสต์ที่ fail ซ้ำอาการ
        ↓
แก้โค้ด
        ↓
เทสต์เขียว = พิสูจน์แล้วว่าแก้ตรงจุด
        ↓
เก็บไว้เป็น regression test
        ↓
Postmortem: ทำไมด่านก่อนหน้าไม่จับ
```

> **ให้มองภาพนี้ว่า** "การแก้บั๊กที่ดีจบด้วยยามเพิ่มหนึ่งคนเสมอ ไม่ใช่แค่อาการหาย"
