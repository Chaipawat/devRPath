# PART 20 — DEBUGGING

> ตำแหน่งในภาพใหญ่: Cross-Layer Skill — ทักษะที่วิ่งทะลุทุกชั้นตั้งแต่ Browser → Frontend → API → Service → Database → Infrastructure และเป็นทักษะที่แยก junior ออกจาก senior ชัดที่สุดในห้องสัมภาษณ์

## 1. Big Picture

ลองนึกภาพนี้: เวลา 21:40 น. มีข้อความเด้งเข้ากลุ่ม

> "ลูกค้าบอกว่า login ไม่ได้ครับ"

Developer สองคนได้ข้อความเดียวกัน แต่ทำคนละอย่าง

**คนที่ 1 (junior)** เปิดโค้ดหน้า login ทันที ไล่อ่านจากบรรทัดแรก เจอจุดที่ดูน่าสงสัย แก้ไปหนึ่งจุด deploy ขึ้นไป แล้วถามกลับว่า "ลองใหม่ได้ยัง" — ผ่านไป 40 นาที แก้ไป 3 รอบ ลูกค้ายัง login ไม่ได้ และตอนนี้มีบั๊กใหม่เพิ่มมาอีกหนึ่งตัวจากการแก้มั่ว

**คนที่ 2 (senior)** ถามกลับ 4 คำถามก่อน: "ลูกค้าคนเดียวหรือหลายคน", "เริ่มตอนกี่โมง", "ขึ้น error ว่าอะไร", "เพิ่ง deploy อะไรไปก่อนหน้านั้น" — แล้วเปิด log ดู 2 นาที เห็นว่า request ไปถึง API จริง แต่ได้ 401 ทุกตัวหลังเวลา 21:05 ซึ่งตรงกับเวลาที่ deploy service auth ขึ้นไป — ย้อนกลับ (rollback) ใน 5 นาที ระบบกลับมาใช้ได้ แล้วค่อยนั่งหาสาเหตุจริงตอนเช้า

**ความต่างไม่ใช่ความเก่งเรื่อง syntax แต่คือ "ลำดับความคิด"**

Debugging คือการสืบสวน ไม่ใช่การเดา
และการสืบสวนมีขั้นตอนตายตัวเหมือนกันทุกครั้ง ไม่ว่าปัญหาจะอยู่ที่ React หรือที่ Kubernetes

พูดแบบให้ HR ฟังรู้เรื่อง:

> "Debugging คือการหาว่าทำไมสิ่งที่เกิดขึ้นจริงถึงไม่ตรงกับสิ่งที่เราคิดว่าควรจะเกิด โดยใช้หลักฐานเป็นตัวตัดสิน ไม่ใช่ใช้ความรู้สึก"

### ทำไมเรื่องนี้เป็นหัวใจของหนังสือเล่มนี้

เพราะมันคือทักษะเดียวที่:

| เหตุผล | อธิบาย |
|---|---|
| **ใช้ได้ทุกภาษา ทุก framework** | React, Spring Boot, Django, Kubernetes ใช้ลำดับความคิดเดียวกันหมด |
| **ไม่มีวันล้าสมัย** | framework เปลี่ยนทุก 3 ปี แต่วิธีสืบสวนไม่เคยเปลี่ยน |
| **เป็นสิ่งที่สัมภาษณ์วัดจริง** | คำถาม "ถ้า API ช้าจะทำยังไง" ไม่ได้วัดคำตอบ แต่วัดลำดับการคิด |
| **แยก level คนได้ทันทีใน 2 นาที** | junior เริ่มจาก "แก้ยังไง" senior เริ่มจาก "ตอนนี้เรารู้อะไรแล้วบ้าง" |

### ประโยคที่ควรติดหัวไว้ตลอดทั้ง chapter นี้

> **"ห้ามแก้สิ่งที่ยังพิสูจน์ไม่ได้ว่าเป็นสาเหตุ"**

การแก้โดยยังไม่รู้สาเหตุ ไม่เรียกว่าแก้บั๊ก เรียกว่า **เดาแล้วเปลี่ยนโค้ด** ซึ่งมีผลข้างเคียง 3 อย่างเสมอ:

1. บางทีอาการหายเพราะบังเอิญ → สาเหตุจริงยังอยู่ กลับมาอีกแน่
2. เพิ่มโค้ดที่ไม่มีใครรู้ว่ามีไว้ทำไม → หนี้ทางเทคนิค
3. เสียหลักฐาน → พอเปลี่ยนโค้ดไปแล้ว บั๊กเดิมอาจเกิดซ้ำไม่ได้อีก สืบต่อไม่ได้เลย

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Bug** | พฤติกรรมที่ไม่ตรงคาด | ความต่างระหว่างสิ่งที่ระบบทำจริง กับสิ่งที่ควรทำ |
| **Reproduce** | ทำให้เกิดซ้ำได้ตามสั่ง | ขั้นตอนที่ทำให้บั๊กโผล่มาแน่นอน — หัวใจของทุกการ debug |
| **Repro Steps** | สูตรทำให้พัง | ลำดับการกดที่เขียนไว้ให้คนอื่นทำตามแล้วเจออาการเดียวกัน |
| **Expected** | สิ่งที่ควรเกิด | พฤติกรรมที่ถูกต้องตาม requirement |
| **Actual** | สิ่งที่เกิดจริง | พฤติกรรมที่สังเกตเห็นจริง ต้องอธิบายเป็นข้อเท็จจริง ไม่ใช่ความเห็น |
| **Symptom** | อาการ | สิ่งที่ผู้ใช้เห็น เช่น "หน้าขาว" — ไม่ใช่สาเหตุ |
| **Root Cause** | ต้นตอจริง | สาเหตุที่ถ้าแก้แล้วอาการจะไม่กลับมาอีก |
| **Hypothesis** | สมมติฐาน | ข้อเดาที่ "พิสูจน์ผิดได้" เช่น "token หมดอายุก่อนเวลา" |
| **Falsifiable** | พิสูจน์ผิดได้ | สมมติฐานที่ดีต้องมีวิธีทำให้มันตกได้ ไม่ใช่เดาลอย ๆ |
| **Bisect** | ตัดครึ่ง | วิธีจำกัดวงโดยตัดพื้นที่ค้นหาลงครึ่งหนึ่งทุกรอบ |
| **git bisect** | ตัดครึ่งไทม์ไลน์ | คำสั่งหา commit แรกที่ทำให้พัง โดยไล่แบบ binary search |
| **Log** | บันทึกเหตุการณ์ | ข้อความที่ระบบเขียนไว้ว่าเกิดอะไรขึ้นตอนไหน |
| **Structured Log** | log ที่เครื่องอ่านได้ | log รูปแบบ key-value / JSON ที่ค้นหาและกรองได้ |
| **Correlation ID / Trace ID** | เลขติดตามพัสดุ | id เดียวที่ติดไปกับ request ทุก service ทำให้ต่อภาพได้ |
| **Stack Trace** | รอยเท้าตอนล้ม | ลำดับฟังก์ชันที่ถูกเรียกก่อนเกิด error |
| **Breakpoint** | จุดหยุดเวลา | จุดที่สั่งให้โปรแกรมหยุดเพื่อดูค่าตัวแปรตอนนั้น |
| **Step Over / Into** | เดินทีละก้าว | การสั่งให้ debugger เดินข้ามบรรทัด / มุดเข้าไปในฟังก์ชัน |
| **Metric** | ตัวเลขตามเวลา | ค่าที่วัดต่อเนื่อง เช่น latency, error rate, CPU |
| **Trace** | เส้นทางของ request | ภาพที่บอกว่า request ใช้เวลาไปที่ไหนเท่าไร |
| **Observability** | ระบบเล่าเรื่องตัวเองได้ | ความสามารถในการตอบคำถามใหม่ ๆ เกี่ยวกับระบบโดยไม่ต้อง deploy เพิ่ม |
| **Three Pillars** | log + metric + trace | สามเสาหลักของ observability |
| **Heisenbug** | บั๊กขี้อาย | บั๊กที่หายไปเมื่อเราพยายามสังเกตมัน (เช่นพอใส่ log แล้ว timing เปลี่ยน) |
| **Flaky** | เดี๋ยวได้เดี๋ยวไม่ได้ | พฤติกรรมที่ไม่คงที่ มักมาจาก race condition / เวลา / ข้อมูลไม่สะอาด |
| **Race Condition** | ใครถึงก่อนชนะ | บั๊กที่ผลลัพธ์ขึ้นกับลำดับเวลาของสองอย่างที่ทำงานพร้อมกัน |
| **Regression** | ของเก่าพัง | สิ่งที่เคยทำงานได้ กลับพังหลังมีการเปลี่ยนแปลง |
| **Regression Test** | ยามเฝ้าไม่ให้พังซ้ำ | เทสต์ที่เขียนไว้หลังแก้บั๊ก เพื่อกันบั๊กเดิมกลับมา |
| **Rollback** | ถอยกลับเวอร์ชันเดิม | การย้อน deploy กลับไปเวอร์ชันที่ยังดี เพื่อหยุดเลือดก่อน |
| **Blast Radius** | รัศมีความเสียหาย | ขอบเขตว่าปัญหากระทบใครบ้าง กี่คน กี่ระบบ |
| **MTTR** | เวลาเฉลี่ยกว่าจะกลับมาใช้ได้ | Mean Time To Recovery — ตัวชี้วัดคุณภาพการ debug ของทีม |
| **Postmortem** | สรุปหลังเหตุการณ์ | เอกสารสรุปว่าเกิดอะไร ทำไม และจะกันซ้ำยังไง (ไม่โทษคน) |
| **Rubber Duck** | อธิบายให้เป็ดฟัง | เทคนิคอธิบายปัญหาออกเสียงจนเจอจุดผิดด้วยตัวเอง |

## 3. Mental Model

### โมเดลที่ 1: Debugging = การลดพื้นที่ค้นหา ไม่ใช่การเดาคำตอบ

ตอนเริ่มต้น บั๊กอาจอยู่ที่ไหนก็ได้ใน 10 ที่
งานของเราไม่ใช่ "ทายให้ถูกว่าอยู่ที่ไหน" แต่คือ **ตัดออกทีละครึ่งจนเหลือที่เดียว**

```
พื้นที่ค้นหา 100%
      ↓  (พิสูจน์ว่า request ออกจาก browser จริง)
เหลือ 60%  → ตัด frontend ออกได้
      ↓  (พิสูจน์ว่า API ตอบ 200 พร้อมข้อมูลถูก)
เหลือ 30%  → ตัด backend ออกได้
      ↓  (พิสูจน์ว่าข้อมูลใน database ถูก)
เหลือ 10%  → เหลือแค่ชั้น render
      ↓
จุดเดียว = Root Cause
```

> **ให้มองภาพนี้ว่า** "การ debug คือการเล่นเกมทายตัวเลขที่เราถามคำถามแบบมากกว่า/น้อยกว่า ไม่ใช่เกมทายตัวเลขแบบสุ่มไปเรื่อย ๆ"

### โมเดลที่ 2: ระบบคือชั้น ๆ — บั๊กอยู่ได้แค่ชั้นเดียว (หรือรอยต่อระหว่างชั้น)

```
[USER / BROWSER]        ← กดอะไร เห็นอะไร
       ↓
[FRONTEND CODE]         ← state, render, event
       ↓
[NETWORK]               ← DNS, CORS, TLS, timeout
       ↓
[GATEWAY / PROXY]       ← nginx, load balancer, rate limit
       ↓
[BACKEND SERVICE]       ← business logic, auth
       ↓
[DATABASE / CACHE]      ← query, index, lock
       ↓
[INFRASTRUCTURE]        ← container, memory, disk, node
```

> **ให้มองภาพนี้ว่า** "ระบบคือตึกหลายชั้น และงานแรกของนักสืบไม่ใช่การหาตัวคนร้าย แต่คือการรู้ก่อนว่าคนร้ายอยู่ชั้นไหน"

**เทคนิคสำคัญ:** ทุกครั้งที่เจอปัญหา ให้ถามว่า "ปัญหานี้หยุดที่ชั้นไหน" แล้วเดินจากชั้นนอกสุด (ผู้ใช้) เข้าไปหาชั้นใน ไม่ใช่เริ่มจากตรงกลางเพราะ "รู้สึกว่าน่าจะอยู่ตรงนี้"

### โมเดลที่ 3: บั๊กทุกตัวคือช่องว่างระหว่าง "สิ่งที่เราคิดว่าโค้ดทำ" กับ "สิ่งที่โค้ดทำจริง"

โค้ดไม่เคยผิด มันทำตามที่เขียนเป๊ะ ๆ เสมอ
สิ่งที่ผิดคือ **ความเข้าใจของเราเกี่ยวกับโค้ด**

```
ความเชื่อของเรา        ความจริงของระบบ
      │                       │
      └────── ช่องว่าง ────────┘
                 ↑
            บั๊กอยู่ตรงนี้
```

> **ให้มองภาพนี้ว่า** "การ debug คือการหาว่าเราเชื่อผิดตรงไหน ไม่ใช่การหาว่าคอมพิวเตอร์ทำงานผิดตรงไหน"

ผลที่ตามมาคือ ถ้าเรามั่นใจ 100% ว่า "ตรงนี้ถูกแน่นอน ไม่ต้องดู" — บั๊กมักซ่อนอยู่ตรงนั้นแหละ

### โมเดลที่ 4: แยก "หยุดเลือด" ออกจาก "รักษาโรค"

บน production สองอย่างนี้คนละงาน และลำดับสำคัญมาก

| เป้าหมาย | ชื่อทางเทคนิค | ทำเมื่อไร | ตัวอย่าง |
|---|---|---|---|
| ให้ผู้ใช้กลับมาใช้งานได้เร็วสุด | Mitigation | ทำก่อนเสมอเมื่อกระทบผู้ใช้ | rollback, ปิด feature flag, สลับ traffic |
| หาสาเหตุจริงและแก้ถาวร | Remediation | ทำหลังเลือดหยุดแล้ว | แก้โค้ด เพิ่ม index เพิ่ม test |

> **ประโยคสัมภาษณ์:** "ตอนเกิดเหตุบน production เป้าหมายแรกคือทำให้ระบบกลับมาใช้ได้ ไม่ใช่การเข้าใจว่าเกิดอะไรขึ้น การเข้าใจเป็นงานลำดับถัดไป"

## 4. ภาพจำ

```
🧠 ภาพจำหลัก:
Debugging = นักสืบที่จุดเกิดเหตุ ไม่ใช่หมอที่จ่ายยา

หมอมั่ว   : ฟังอาการ 5 วิ → จ่ายยาเลย → ไม่หายก็เปลี่ยนยา
นักสืบ    : เก็บหลักฐาน → ตั้งผู้ต้องสงสัย → ตัดออกทีละคน → จับคนร้าย
```

```
แจ้งเหตุ (อาการ)
      ↓
รักษาที่เกิดเหตุ (อย่าเพิ่งแก้โค้ด)
      ↓
เก็บหลักฐาน (log / metric / network)
      ↓
ตั้งผู้ต้องสงสัย 3 คน (hypothesis)
      ↓
สอบสวนทีละคน (test)
      ↓
เจอคนร้าย (root cause)
      ↓
จับกุม (fix)
      ↓
ตั้งกล้องวงจรปิดไว้ (regression test + monitor)
```

> **ให้มองภาพนี้ว่า** "การแก้บั๊กที่ดีจบด้วยการติดกล้องเพิ่มหนึ่งตัวเสมอ ไม่ใช่แค่จับคนร้ายได้"

```
🧠 ภาพจำรอง:
Log = กล้องวงจรปิด    → เห็นว่าเกิดอะไรตอนไหน
Metric = เครื่องวัดชีพจร → เห็นว่าผิดปกติตั้งแต่เมื่อไร
Trace = GPS ติดรถ      → เห็นว่าเวลาหายไปตรงช่วงไหน
```

```
🧠 ภาพจำเรื่อง "อาการ ≠ สาเหตุ":
ไฟแดงบนแผงหน้าปัดรถ = อาการ
น้ำมันเครื่องแห้ง     = สาเหตุ

เอาเทปปิดไฟแดง = แก้อาการ (รถยังพังอยู่)
เติมน้ำมันเครื่อง = แก้สาเหตุ
```

## 5. How It Works

### 🔑 DEBUGGING FRAMEWORK หลักของหนังสือเล่มนี้

นี่คือกรอบความคิดที่จะใช้ตลอดทั้งเล่ม จำให้ขึ้นใจ:

```
REPRODUCE → EXPECTED → ACTUAL → LOCATE → EVIDENCE → HYPOTHESIS
   → TEST → ROOT CAUSE → FIX → REGRESSION TEST → MONITOR
```

แบ่งเป็น 4 ช่วงใหญ่เพื่อให้จำง่าย:

```
ช่วงที่ 1: ตั้งโจทย์ให้ชัด
   REPRODUCE → EXPECTED → ACTUAL
        ↓
ช่วงที่ 2: จำกัดวงและเก็บหลักฐาน
   LOCATE → EVIDENCE
        ↓
ช่วงที่ 3: สืบสวน
   HYPOTHESIS → TEST → ROOT CAUSE
        ↓
ช่วงที่ 4: ปิดงานให้ไม่กลับมาอีก
   FIX → REGRESSION TEST → MONITOR
```

> **ให้มองภาพนี้ว่า** "สามช่วงแรกคือการทำให้ปัญหาที่คลุมเครือกลายเป็นข้อเท็จจริงชิ้นเดียว ส่วนช่วงสุดท้ายคือการทำให้ข้อเท็จจริงชิ้นนั้นไม่มีวันกลับมาหลอกเราอีก"

**กฎเหล็ก: ห้ามข้ามขั้น และห้ามกระโดดไป FIX ก่อนถึง ROOT CAUSE**

ถ้าคุณพบว่าตัวเองกำลังพิมพ์แก้โค้ดอยู่ ให้หยุดแล้วถามตัวเองว่า "ตอนนี้ฉันอยู่ step ไหน" — ถ้าตอบไม่ได้ แปลว่ากำลังเดา

---

### STEP 1 — REPRODUCE (ทำให้เกิดซ้ำได้ตามสั่ง)

**ทำอะไร:** หาลำดับการกระทำที่ทำให้บั๊กโผล่มาแน่นอน แล้วเขียนเป็นขั้นตอนที่คนอื่นทำตามได้

ขั้นตอนนี้สำคัญที่สุดและถูกข้ามบ่อยที่สุด เพราะถ้าเกิดซ้ำไม่ได้ เราจะไม่มีวันรู้ว่าแก้แล้วหายจริงหรือแค่บังเอิญ

**คำถามที่ต้องถามตัวเอง:**

- เกิดกับ user ทุกคน หรือบางคน? (บางคน → ข้อมูล / role / device ต่างกัน)
- เกิดทุกครั้ง หรือบางครั้ง? (บางครั้ง → เวลา / ลำดับ / cache / race)
- เกิดทุก environment หรือเฉพาะ production? (เฉพาะ prod → config / data / scale)
- เริ่มเกิดตั้งแต่เมื่อไร? และ **ก่อนหน้านั้นมีอะไรเปลี่ยน**? (deploy, config, ข้อมูล, dependency, certificate)
- ต้องกดอะไรบ้างเป็นลำดับ ถึงจะเจอ?
- ต้องอยู่ในสภาพไหนถึงเจอ? (login ค้างไว้นาน, ข้อมูลเยอะ, เน็ตช้า, มือถือรุ่นเก่า)

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- ยังพูดว่า "บางทีก็เกิด บางทีก็ไม่เกิด" โดยยังไม่รู้ว่า "บางที" คือเงื่อนไขอะไร
- ยังไม่มีขั้นตอนที่เขียนเป็นข้อ ๆ ให้เพื่อนทำตามแล้วเจอเหมือนกัน
- ยังไม่รู้ว่าเกิดกับ user คนเดียวหรือทุกคน
- ยังบอกไม่ได้ว่า "ถ้าแก้เสร็จแล้วจะรู้ได้ยังไงว่าหาย"

> ถ้าบั๊กเกิดซ้ำไม่ได้จริง ๆ ให้เปลี่ยนเป้าหมายชั่วคราวจาก "แก้บั๊ก" เป็น "เพิ่มหลักฐานให้พอจนเกิดครั้งหน้าจะจับได้" — นั่นคือใส่ log / trace id / error tracking เพิ่ม แล้วรอ

---

### STEP 2 — EXPECTED (ระบุสิ่งที่ควรเกิด)

**ทำอะไร:** เขียนให้ชัดว่า "ถ้าระบบทำงานถูกต้อง ผลควรเป็นอะไร" เป็นประโยคที่วัดได้

ฟังดูเหมือนเรื่องเล็ก แต่หลายครั้ง "บั๊ก" กลับกลายเป็นว่าไม่มีใครเห็นตรงกันว่าอะไรคือพฤติกรรมที่ถูก

**คำถามที่ต้องถามตัวเอง:**

- ผลที่ถูกต้องคืออะไร ในระดับที่วัดได้ (ตัวเลข ข้อความ สถานะ HTTP)?
- ใครเป็นคนบอกว่านี่คือสิ่งที่ถูก — requirement, design, หรือความเข้าใจส่วนตัวของเรา?
- เคยทำงานถูกต้องมาก่อนไหม? ถ้าเคย ตอนนั้นผลเป็นยังไง?
- กรณีขอบ (empty, 0, ผู้ใช้ไม่มีสิทธิ์) ผลที่ถูกควรเป็นอะไร?

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- อธิบายสิ่งที่ควรเกิดได้แค่ว่า "มันควรทำงานได้"
- สองคนในทีมอธิบายพฤติกรรมที่ถูกต้องไม่เหมือนกัน
- ยังไม่รู้ว่านี่คือบั๊ก หรือเป็น feature ที่ออกแบบไว้แบบนั้นแต่ไม่มีใครชอบ

---

### STEP 3 — ACTUAL (ระบุสิ่งที่เกิดจริง)

**ทำอะไร:** เขียนสิ่งที่สังเกตเห็นจริง เป็น **ข้อเท็จจริง** ไม่ใช่การตีความ

| เขียนแบบตีความ (ไม่ดี) | เขียนแบบข้อเท็จจริง (ดี) |
|---|---|
| "API พัง" | "POST /api/login ตอบ 500 ทุกครั้ง body คือ `{"error":"internal"}`" |
| "หน้าเว็บโหลดไม่ขึ้น" | "หน้าขาว console ขึ้น TypeError: cannot read property 'name' of undefined" |
| "database ช้า" | "query รายการ order ใช้เวลา 4.2 วินาที ตอน 09:00-09:30 เท่านั้น" |

**คำถามที่ต้องถามตัวเอง:**

- error message เต็ม ๆ เขียนว่าอะไร (ไม่ใช่สรุปย่อ)?
- HTTP status เท่าไร? body คืออะไร?
- เกิดตอนไหนเป๊ะ ๆ (timestamp)?
- ผู้ใช้เห็นอะไร กับ log เขียนอะไร — ตรงกันไหม?

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- ยังไม่ได้เห็น error message ตัวจริงกับตา (เห็นแต่คนเล่าต่อมา)
- ยังใช้คำว่า "มันพัง" "มันช้า" โดยไม่มีตัวเลขหรือข้อความประกอบ
- อธิบายให้คนอื่นฟังแล้วเขาต้องถามกลับว่า "พังยังไง"

> **เคล็ดลับ:** วาง EXPECTED กับ ACTUAL ไว้ข้างกันเสมอ ความต่างระหว่างสองบรรทัดนี้คือ "นิยามของบั๊ก" และมันมักชี้ layer ให้เราทันที

---

### STEP 4 — LOCATE (จำกัดวงว่าปัญหาอยู่ชั้นไหน)

**ทำอะไร:** ตัดชั้นที่ไม่ใช่ออกทีละชั้น จนเหลือช่วงแคบที่สุดที่ปัญหาต้องอยู่ในนั้น

วิธีที่ใช้ได้เสมอคือ **เดินตามเส้นทางของข้อมูล แล้วหาจุดที่ข้อมูลเปลี่ยนจากถูกเป็นผิด**

```
[Browser]  ข้อมูลถูกไหม? ──ถูก──┐
                                ↓
[Network]  request ออกไปไหม? ──ออก──┐
                                    ↓
[API]      รับค่าอะไร? ──ถูก──┐
                              ↓
[Service]  คำนวณถูกไหม? ──ผิดตรงนี้! ← จุดที่ต้องขุดต่อ
                              ↓
[Database] ข้อมูลถูกไหม? ──ถูก──┘
```

> **ให้มองภาพนี้ว่า** "เหมือนท่อน้ำรั่ว เราไม่ทุบผนังทุกจุด แต่เดินเช็กทีละข้อต่อจนเจอข้อที่น้ำเริ่มไม่ออก"

**คำถามที่ต้องถามตัวเอง:**

- ข้อมูลยังถูกต้องอยู่ถึงจุดไหน และเริ่มผิดที่จุดไหน?
- ถ้าตัดชั้นนี้ออก (เรียก API ตรงด้วย curl / query database ตรง) ปัญหายังอยู่ไหม?
- เกิดที่ environment ไหนบ้าง — local, staging, production?
- ถ้าเป็นเรื่องช้า เวลาหายไปช่วงไหน (network / server / database / render)?

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- ยังตอบไม่ได้ว่าปัญหาอยู่ฝั่ง frontend หรือ backend
- กำลังเปิดโค้ดหลายไฟล์พร้อมกันโดยไม่รู้ว่ากำลังหาอะไร
- ยังบอกไม่ได้ว่า "ถ้าปัญหาอยู่ชั้นนี้จริง เราจะเห็นหลักฐานอะไร"

---

### STEP 5 — EVIDENCE (เก็บหลักฐาน — ดูอะไร ที่ไหน)

**ทำอะไร:** ไปเอาข้อมูลจริงจากระบบมาดู ไม่ใช่นั่งนึกเอา

แหล่งหลักฐานมาตรฐานเรียงตามชั้น:

| ชั้น | ดูที่ไหน | ดูอะไร |
|---|---|---|
| Browser | DevTools Console | error, warning, stack trace |
| Browser | DevTools Network | status code, request/response body, header, เวลาแต่ละช่วง |
| Browser | Application tab | cookie, localStorage, token หมดอายุหรือยัง |
| Frontend | React DevTools / Profiler | state, props, จำนวนครั้งที่ re-render |
| Network | Gateway / proxy log | request เข้าถึงจริงไหม ถูกบล็อกไหม |
| Backend | Application log | ข้อความ error เต็ม + stack trace + trace id |
| Backend | APM / Trace | เวลาแต่ละ span, จำนวน query ต่อ request |
| Database | Slow query log / EXPLAIN | query ไหนช้า ใช้ index ไหม อ่านกี่แถว |
| Database | Lock / connection view | มี lock ค้างไหม connection เต็มไหม |
| Infra | Container log / kubectl logs | process ตายด้วยเหตุผลอะไร |
| Infra | Metric dashboard | CPU, memory, restart count, error rate |

**คำถามที่ต้องถามตัวเอง:**

- หลักฐานนี้บอกอะไรที่เรายังไม่รู้ หรือแค่ยืนยันสิ่งที่เดาไว้แล้ว?
- ช่วงเวลาที่ปัญหาเริ่ม ตรงกับเหตุการณ์อะไรบ้างบน timeline (deploy / traffic พุ่ง / job รัน)?
- ถ้าไม่มี log ตรงจุดนี้ ต้องเพิ่มอะไรถึงจะเห็น?
- มี trace id ไหม — ถ้ามี ตาม request เดียวข้ามทุก service ได้เลย

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- ยังไม่ได้เปิด log หรือ Network tab เลยสักครั้ง
- กำลังพูดว่า "น่าจะเป็นเพราะ..." โดยไม่มีข้อมูลรองรับ
- หลักฐานที่มีอยู่ตรงกับสมมติฐานได้หลายข้อพอ ๆ กัน (แปลว่ายังต้องเก็บเพิ่ม)

---

### STEP 6 — HYPOTHESIS (ตั้งสมมติฐาน อย่างน้อย 3 ข้อ)

**ทำอะไร:** เขียนคำอธิบายที่เป็นไปได้ออกมาหลายข้อ โดยแต่ละข้อต้อง **พิสูจน์ผิดได้**

ทำไมต้อง 3 ข้อขึ้นไป? เพราะถ้าตั้งข้อเดียว สมองจะหาหลักฐานมาสนับสนุนข้อนั้นโดยอัตโนมัติ (confirmation bias) แล้วเราจะเสียเวลาเป็นชั่วโมงกับคำตอบที่ผิด

| สมมติฐานที่ไม่ดี | สมมติฐานที่ดี |
|---|---|
| "น่าจะเป็นที่ backend" | "token ถูกสร้างด้วย secret คนละตัวหลัง deploy → ทำให้ verify ไม่ผ่านทุกคน" |
| "cache มีปัญหา" | "cache เก็บ response ของ user คนแรกไว้แล้วส่งให้ทุกคน เพราะ key ไม่มี user id" |
| "database ช้า" | "query นี้ไม่มี index บนคอลัมน์ created_at เลยต้อง scan ทั้งตาราง" |

**คำถามที่ต้องถามตัวเอง:**

- ถ้าสมมติฐานนี้จริง **เราต้องเห็นอะไรอีก** ที่ตอนนี้ยังไม่ได้ดู?
- ถ้าสมมติฐานนี้เท็จ **อะไรคือหลักฐานที่จะทำให้มันตก**?
- สมมติฐานไหนอธิบายได้ครบทุกอาการ (ไม่ใช่แค่บางอาการ)?
- ข้อไหนทดสอบได้เร็วสุดและถูกสุด → ทำก่อน

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- มีสมมติฐานอยู่ข้อเดียวแล้วเริ่มแก้โค้ดแล้ว
- สมมติฐานที่มีอยู่พิสูจน์ผิดไม่ได้เลย (เช่น "มันแปลก ๆ")
- ยังไม่มีสมมติฐานไหนอธิบายว่า "ทำไมเพิ่งเกิดวันนี้ ไม่เกิดเมื่อวาน"

> **เคล็ดลับเรียงลำดับ:** เรียงสมมติฐานด้วย (ความน่าจะเป็น × ความง่ายในการทดสอบ) ไม่ใช่ด้วยความน่าสนใจทางเทคนิค — เช็ก "เพิ่ง deploy อะไรไป" ก่อนเสมอ เพราะถูกและได้ผลบ่อย

---

### STEP 7 — TEST (พิสูจน์ / ตัดออกทีละข้อ)

**ทำอะไร:** ออกแบบการทดลองที่ผลลัพธ์จะ **ตัดสินสมมติฐานได้จริง** แล้วทำทีละอย่าง

**กฎเหล็กของขั้นนี้: เปลี่ยนทีละอย่างเท่านั้น**
ถ้าเปลี่ยน 3 อย่างพร้อมกันแล้วอาการหาย เราจะไม่มีวันรู้ว่าอันไหนคือตัวจริง

**คำถามที่ต้องถามตัวเอง:**

- การทดลองนี้ ถ้าได้ผล A แปลว่าอะไร ถ้าได้ผล B แปลว่าอะไร — ตอบก่อนทำ
- การทดลองนี้ทำบน production ปลอดภัยไหม หรือควรทำบน staging?
- มีวิธีทดสอบที่ตัดสมมติฐานได้ทีละหลายข้อพร้อมกันไหม (แบ่งครึ่ง)?
- ถ้าผลออกมาไม่ตรงทั้ง A และ B แปลว่าความเข้าใจพื้นฐานของเราผิดตรงไหน?

วิธีทดสอบที่ใช้บ่อย:

| วิธี | ใช้ตอนไหน |
|---|---|
| ยิง API ตรงด้วย curl / Postman | ตัด frontend ออกจากสมการ |
| รัน query ตรงบน database | ตัด backend logic ออก |
| ย้อน commit / git bisect | รู้ว่า "เพิ่งเกิด" แต่ไม่รู้ว่าเพราะอะไร |
| ปิด feature flag | สงสัยว่าเป็นฟีเจอร์ใหม่ |
| เทียบ environment | เกิดเฉพาะ prod → ต่างกันที่ config หรือ data |
| ลดข้อมูลลงครึ่งหนึ่ง | สงสัยเรื่องขนาดข้อมูล |
| เปลี่ยน user / account | สงสัยเรื่อง permission หรือข้อมูลเฉพาะคน |

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- อาการหายแล้วแต่ยังตอบไม่ได้ว่าเพราะการเปลี่ยนแปลงตัวไหน
- ยังไม่มีการทดลองไหนที่ทำให้สมมติฐานข้อใดตกได้เลย
- กำลังบอกว่า "ลองแก้แบบนี้ดูก่อน เผื่อหาย"

---

### STEP 8 — ROOT CAUSE (ไปให้ถึงต้นตอจริง)

**ทำอะไร:** ถามต่อว่า "แล้วทำไมถึงเป็นแบบนั้น" จนถึงจุดที่แก้แล้วอาการไม่กลับมาอีก

เทคนิคมาตรฐานคือ **5 Whys** — ถามทำไมซ้ำประมาณ 5 ครั้ง

```
อาการ: หน้า dashboard ขาว
  ↓ ทำไม?
เพราะ JS error: cannot read property 'name' of undefined
  ↓ ทำไม?
เพราะ API ส่ง user มาเป็น null
  ↓ ทำไม?
เพราะ token หมดอายุ API เลยตอบ 401 พร้อม body ว่าง
  ↓ ทำไม?
เพราะ frontend ไม่ได้เช็ก status ก่อนอ่านข้อมูล
  ↓ ทำไม?
เพราะไม่มีตัวจัดการ error กลางของชั้น API client   ← ROOT CAUSE
```

> **ให้มองภาพนี้ว่า** "ถ้าหยุดถามที่ชั้นบนสุด เราจะได้แค่พลาสเตอร์ปิดแผล แต่ถ้าถามลงไปจนสุด เราจะได้ระบบที่บั๊กแบบเดียวกันเกิดไม่ได้อีกเลยทั้งหมวด"

**คำถามที่ต้องถามตัวเอง:**

- ถ้าแก้ตรงนี้ บั๊ก **ประเภทเดียวกัน** ในที่อื่นจะหายด้วยไหม หรือหายแค่จุดเดียว?
- อธิบายได้ครบไหมว่าทำไมมันเพิ่งเกิดตอนนี้ ไม่เกิดเมื่อสัปดาห์ที่แล้ว?
- อธิบายได้ไหมว่าทำไมเกิดกับ user กลุ่มนี้ ไม่เกิดกับกลุ่มอื่น?
- ทำไมด่านก่อนหน้า (type check / code review / test / staging) ถึงไม่จับ?

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- อธิบายสาเหตุได้แค่ "ข้อมูลมันเป็น null" (นั่นคืออาการชั้นที่สอง ไม่ใช่สาเหตุ)
- ยังตอบไม่ได้ว่าทำไมเพิ่งเกิดวันนี้
- การแก้ที่คิดไว้คือ "ใส่ if เช็ก null เพิ่ม" โดยไม่รู้ว่าทำไมถึงมี null

---

### STEP 9 — FIX (แก้ที่ต้นตอ)

**ทำอะไร:** แก้ให้ตรงกับ root cause ด้วยการเปลี่ยนแปลงที่เล็กที่สุดเท่าที่จำเป็น

**คำถามที่ต้องถามตัวเอง:**

- การแก้นี้แก้ที่สาเหตุ หรือแก้ที่อาการ?
- การแก้นี้มี blast radius แค่ไหน — กระทบส่วนอื่นไหม?
- ถ้าแก้แล้วพัง จะ rollback ยังไง และใช้เวลากี่นาที?
- ควรแก้ตอนนี้เลย หรือควรหยุดเลือดก่อน (rollback / flag) แล้วค่อยแก้ให้ดีตอนเช้า?
- มีที่อื่นในโค้ดที่มีปัญหาแบบเดียวกันอีกไหม (grep หาแพตเทิร์นเดียวกัน)?

**หลักการเลือกวิธีแก้บน production:**

```
กระทบผู้ใช้อยู่ตอนนี้?
   ├── ใช่ → หยุดเลือดก่อน (rollback / feature flag / scale)
   │         แล้วค่อยแก้ root cause ทีหลังอย่างใจเย็น
   └── ไม่ → แก้ root cause ให้ถูกต้องตั้งแต่แรก ไม่ต้องรีบ
```

> **ให้มองภาพนี้ว่า** "ความเร็วที่ต้องการตอนไฟไหม้คือความเร็วในการดับไฟ ไม่ใช่ความเร็วในการสร้างตึกใหม่"

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- แก้แล้วแต่ยังอธิบายให้เพื่อนฟังไม่ได้ว่าทำไมมันถึงหาย
- การแก้ประกอบด้วยหลายอย่างปนกัน จน review ไม่ออกว่าอันไหนแก้บั๊ก
- ยังไม่ได้คิดว่าถ้าแก้แล้วมีอะไรอาจพังตามมา

---

### STEP 10 — REGRESSION TEST (เขียนเทสต์กันบั๊กเดิมกลับมา)

**ทำอะไร:** เขียนเทสต์ที่ **fail ก่อนแก้ และ pass หลังแก้**

ลำดับที่ถูกต้องคือ:

```
เขียนเทสต์ตามอาการ  →  รันแล้วต้อง "แดง"  ← พิสูจน์ว่าเทสต์จับบั๊กนี้ได้จริง
        ↓
แก้โค้ด
        ↓
รันอีกครั้ง ต้อง "เขียว"  ← พิสูจน์ว่าการแก้ได้ผลจริง
```

> **ให้มองภาพนี้ว่า** "เทสต์ที่ไม่เคยแดงมาก่อน คือยามที่เราไม่เคยรู้เลยว่าเขาตื่นอยู่หรือหลับอยู่"

**คำถามที่ต้องถามตัวเอง:**

- เทสต์นี้ fail จริงไหมถ้าเอาการแก้ออก?
- เทสต์นี้ทดสอบที่ระดับไหน — unit (ถูก/เร็ว) หรือ integration (สมจริงกว่า)?
- ถ้าบั๊กนี้เกิดจากข้อมูลรูปแบบแปลก ๆ ได้ใส่ข้อมูลรูปแบบนั้นไว้ในเทสต์หรือยัง?
- ปัญหาแบบนี้ควรถูกจับที่ชั้นไหนจึงจะถูกที่สุด (type, lint, test, review, monitor)?

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- แก้เสร็จแล้วแต่ไม่มีอะไรกันไม่ให้คนถัดไปทำพังแบบเดิม
- เทสต์ที่เขียนผ่านตั้งแต่ยังไม่แก้โค้ด
- บั๊กนี้เคยเกิดมาแล้วรอบก่อน (นั่นแปลว่ารอบก่อนข้ามขั้นนี้ไป)

---

### STEP 11 — MONITOR (เฝ้าดูหลังปล่อยจริง)

**ทำอะไร:** หลัง deploy ต้องมีตัวชี้วัดที่บอกได้ว่า "หายจริง" และมีตัวเตือนถ้ากลับมาอีก

**คำถามที่ต้องถามตัวเอง:**

- ตัวเลขไหนที่ควรเปลี่ยนไปในทางที่ดีขึ้นหลัง deploy (error rate, latency, จำนวนเคสร้องเรียน)?
- ถ้าบั๊กนี้กลับมา เราจะรู้ภายในกี่นาที และรู้จากอะไร?
- ควรมี alert ไหม และ alert ที่ตั้งจะทำให้คนตื่นตอนตีสามโดยไม่จำเป็นหรือเปล่า?
- มีข้อมูลอะไรที่ถ้ามีตั้งแต่แรกจะทำให้ debug ครั้งนี้เร็วขึ้น 10 เท่า? → ใส่เพิ่มเลยตอนนี้

**สัญญาณว่ายังข้ามขั้นนี้ไม่ได้:**

- ยืนยันว่าหายด้วยการ "ลองกดเองแล้วโอเค" อย่างเดียว
- ไม่มีใครรู้เลยว่าถ้ามันกลับมาพรุ่งนี้จะมีใครรู้บ้างไหม
- ยังไม่ได้เขียน postmortem หรืออย่างน้อยบันทึกสั้น ๆ ว่าเกิดอะไรขึ้น

---

### ภาพรวมทั้ง framework พร้อมของที่ได้ในแต่ละขั้น

```
REPRODUCE      → ได้: สูตรทำให้พังซ้ำได้
EXPECTED       → ได้: เส้นมาตรฐานว่าอะไรคือถูก
ACTUAL         → ได้: ข้อเท็จจริงว่าเกิดอะไรจริง
LOCATE         → ได้: ชั้นที่ปัญหาอยู่
EVIDENCE       → ได้: ข้อมูลจริงจากระบบ
HYPOTHESIS     → ได้: ผู้ต้องสงสัย 3 คนขึ้นไป
TEST           → ได้: ผู้ต้องสงสัยเหลือคนเดียว
ROOT CAUSE     → ได้: คำอธิบายที่ครบทุกอาการ
FIX            → ได้: การเปลี่ยนแปลงที่เล็กและตรงจุด
REGRESSION TEST→ ได้: ยามเฝ้าถาวร
MONITOR        → ได้: ความมั่นใจว่าหายจริงและจะรู้ถ้ากลับมา
```

> **ให้มองภาพนี้ว่า** "ทุกขั้นตอนต้องส่งมอบของชิ้นหนึ่งให้ขั้นถัดไป ถ้าขั้นไหนยังไม่มีของส่งต่อ แปลว่ายังไปต่อไม่ได้"

## 6. Example

ต่อไปนี้คือ scenario จริง 10 ข้อ ที่เจอบ่อยที่สุดในงานและในห้องสัมภาษณ์

**กฎเหล็กของทุก scenario: ห้ามกระโดดไปตอบวิธีแก้ทันที** ทุกข้อจะเดินตามลำดับนี้เสมอ

```
Observation → Possible Layers → Evidence → Hypothesis (≥3)
   → Test → Root Cause → Fix (+ ป้องกันไม่ให้เกิดซ้ำ)
```

---

### 🔧 Scenario 1 — "Login ไม่ได้"

**Observation (สิ่งที่ได้ยิน / เห็นจริง)**

- ผู้ใช้กดปุ่ม Login แล้วหน้าค้างที่หน้าเดิม ไม่มีข้อความ error
- แจ้งเข้ามา 3 คน ตั้งแต่ประมาณ 09:10
- ทีมงานลองเองบนเครื่องตัวเอง เข้าได้ปกติ

สิ่งที่ยังไม่รู้ (สำคัญพอ ๆ กับสิ่งที่รู้): เป็นทุกคนไหม, เป็นทุกอุปกรณ์ไหม, request ออกจาก browser หรือเปล่า

**Possible Layers**

```
[Browser]   ปุ่มไม่ทำงาน / JS error ก่อนยิง request
     ↓
[Network]   request ไม่ออก / โดน CORS / timeout
     ↓
[API]       ตอบ 4xx (รหัสผิด / บัญชีถูกล็อก) หรือ 5xx
     ↓
[Auth]      token สร้างไม่ได้ / verify ไม่ผ่าน / clock ไม่ตรง
     ↓
[Database]  หา user ไม่เจอ / connection เต็ม
     ↓
[Client]    login สำเร็จแต่ cookie ไม่ถูกเก็บ → เด้งกลับหน้าเดิม
```

> **ให้มองภาพนี้ว่า** "คำว่า login ไม่ได้ ครอบคลุมได้ตั้งแต่ปุ่มกดไม่ติด ไปจนถึงเข้าได้แต่ถูกเตะออกทันที เราจึงห้ามเดาจากคำเล่า ต้องดูให้เห็นว่าหยุดที่ชั้นไหน"

**Evidence (ดูอะไร ที่ไหน)**

| ดูที่ไหน | ดูอะไร |
|---|---|
| DevTools → Network | มี request `POST /api/login` ไหม, status เท่าไร, response body ว่าอะไร |
| DevTools → Console | มี JS error ก่อนกดไหม |
| DevTools → Application | หลัง login มี cookie / token ถูกเซ็ตไหม, `Secure`/`SameSite` เป็นอะไร |
| Backend log | มี log ของ request นี้ไหม, error อะไร, trace id อะไร |
| Timeline การ deploy | มี deploy หรือเปลี่ยน config ก่อน 09:10 ไหม |

สมมติหลักฐานที่ได้จริง: request ออกไปถึง API และตอบ **200** พร้อม token แต่กดแล้วเด้งกลับหน้า login ทันที และใน Application tab **ไม่มี cookie** ถูกเก็บ

**Hypothesis (อย่างน้อย 3 ข้อ)**

1. Cookie ถูกส่งกลับมาพร้อม `Secure` แต่ผู้ใช้เข้าผ่าน http (หรือผ่าน domain ที่ไม่ตรง) → browser ทิ้ง cookie
2. Cookie ตั้ง `SameSite=Strict/None` ไม่ตรงกับสถานการณ์ข้าม domain → browser ไม่เก็บ
3. Frontend เก็บ token ไว้ใน memory อย่างเดียว พอ redirect แล้ว state หาย → เด้งกลับ
4. เวลาบนเครื่อง server ไม่ตรง ทำให้ token หมดอายุทันทีที่สร้าง

**Test (พิสูจน์ / ตัดออกยังไง)**

| ทดสอบอะไร | ถ้าผลเป็นแบบนี้แปลว่า |
|---|---|
| ดู response header `Set-Cookie` ตัวเต็ม | เห็น attribute จริงว่าเป็น Secure / SameSite อะไร |
| เข้าผ่าน https บน domain เดียวกัน แล้วลองใหม่ | ถ้าเข้าได้ → ข้อ 1 เป็นจริง |
| ยิง API ตรงด้วย curl แล้วดู header | ตัด frontend ออกจากสมการทั้งหมด |
| ถอด token ออกมาดู `exp` เทียบเวลาปัจจุบัน | ตัดข้อ 4 ออกหรือยืนยัน |
| ถามผู้ใช้ 3 คนว่าเข้าเว็บด้วย URL อะไร | มักเจอว่าเข้าคนละ domain กับทีม |

สมมติผลคือ: ผู้ใช้ทั้ง 3 คน bookmark URL เก่าที่เป็น http และ cookie ถูกตั้งเป็น `Secure` หลัง deploy เมื่อเช้า

**Root Cause**

การ deploy เช้านี้เปลี่ยน cookie ให้มี flag `Secure` (ถูกต้องตามหลัก security) แต่ระบบยังเปิดให้เข้าทาง http ได้อยู่ และไม่มีการ redirect http → https บังคับ ผู้ใช้ที่ bookmark URL เก่าจึง login สำเร็จที่ฝั่ง server แต่ browser ทิ้ง cookie ทุกครั้ง

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| หยุดเลือด | เปิด redirect บังคับจาก http → https ที่ชั้น gateway |
| แก้ root cause | ปิดไม่ให้รับ http เลย + ตั้ง HSTS |
| ป้องกันซ้ำ | เพิ่ม integration test ที่ตรวจ header `Set-Cookie` ว่ามี Secure/HttpOnly/SameSite ตามที่ตั้งใจ |
| ป้องกันซ้ำ | เพิ่ม e2e test ที่ login แล้วต้องเห็น cookie ถูกเก็บจริง |
| ป้องกันซ้ำ | เพิ่ม metric: อัตรา login สำเร็จรายชั่วโมง + alert ถ้าตกเกิน 20% |
| ป้องกันซ้ำ | frontend แสดงข้อความชัดเจนเมื่อ login สำเร็จแต่ session หาย (แทนที่จะเงียบ) |

**บทเรียนที่เอาไปพูดในห้องสัมภาษณ์ได้:** "คำว่า login ไม่ได้ ผมจะไม่เดาก่อน ผมจะดูก่อนว่ามัน fail ที่ชั้นไหน — ไม่ยิง request, ยิงแล้วได้ 4xx, หรือได้ 200 แต่ session ไม่ติด เพราะสามกรณีนี้สาเหตุคนละเรื่องกันหมด"

---

### 🔧 Scenario 2 — "API ช้า"

**Observation**

- หน้า order list โหลดนาน ผู้ใช้บ่นว่า "หมุนนาน"
- วัดจาก DevTools: `GET /api/orders` ใช้เวลา 4.5-6 วินาที
- endpoint อื่นในระบบเดียวกันเร็วปกติ (< 300ms)
- เพิ่งเริ่มช้าประมาณ 2 สัปดาห์ที่แล้ว ค่อย ๆ แย่ลง ไม่ใช่พังทันที

**Possible Layers**

```
[Browser]      ต้องรอ resource อื่นก่อน / render ช้า ไม่ใช่ API ช้า
     ↓
[Network]      DNS / TLS / ระยะทาง / ขนาด payload ใหญ่
     ↓
[Gateway]      รอคิว / rate limit / connection pool ไม่พอ
     ↓
[Service]      logic ช้า / เรียก external API ต่อ / N+1 query
     ↓
[Database]     query ไม่มี index / ตาราง lock / ข้อมูลโตขึ้น
     ↓
[Infra]        CPU เต็ม / memory ไม่พอ / disk I/O ช้า
```

> **ให้มองภาพนี้ว่า** "คำว่าช้า คือเวลารวมของหลายช่วงต่อกัน หน้าที่แรกคือหาว่าเวลาหายไปช่วงไหน ไม่ใช่เดาว่าใครช้า"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| DevTools → Network → Timing | แยก DNS / Connect / TTFB / Content Download |
| APM / Trace | span ไหนกินเวลา, มีกี่ query ต่อ 1 request |
| Slow query log | query ไหนเกิน threshold, ใช้เวลาเท่าไร |
| `EXPLAIN` ของ query นั้น | ใช้ index ไหม, อ่านกี่แถว |
| Metric ย้อนหลัง 30 วัน | latency ค่อย ๆ ขึ้น หรือกระโดดวันเดียว |
| ขนาด response | ส่งกลับมากี่ KB, กี่ record |

สมมติหลักฐาน: TTFB = 4.3 วินาที (แปลว่า server ใช้เวลาคิดนาน ไม่ใช่เน็ตช้า) และ trace บอกว่ามี database query 212 ครั้งใน 1 request

**Hypothesis**

1. **N+1 query** — ดึง order 100 รายการ แล้ววนลูปดึงข้อมูลลูกค้าทีละรายการ
2. **ไม่มี index** — query หลักต้อง scan ทั้งตารางที่โตขึ้นเรื่อย ๆ (ตรงกับอาการ "ค่อย ๆ ช้า")
3. **ดึงข้อมูลมามากเกินจำเป็น** — ไม่มี pagination เลยดึงทั้งหมดทุกครั้ง
4. **เรียก external service** ในลูป เช่น ขอสถานะขนส่งทีละ order

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| นับจำนวน query ต่อ 1 request จาก trace | 212 ครั้ง → ยืนยันข้อ 1 ทันที, ตัดข้อ 2 ออกจากการเป็นสาเหตุหลัก |
| รัน query หลักตรงบน database แล้วจับเวลา | ถ้าเร็ว → ปัญหาไม่ได้อยู่ที่ query เดี่ยว แต่อยู่ที่จำนวนครั้ง |
| ลองเรียก endpoint ด้วย limit=10 | ถ้าเร็วขึ้นเป็นสัดส่วนตรง ๆ → ยืนยันว่าเวลาแปรตามจำนวนแถว |
| ดู `EXPLAIN` | ถ้าเห็น full scan → ข้อ 2 เป็นปัญหาร่วม |
| ปิดการเรียก external ชั่วคราวบน staging | ตัดข้อ 4 |

**Root Cause**

โค้ดดึง order มา 100 รายการ แล้ววนลูปเรียก `getCustomer(order.customerId)` ทีละตัว = 1 + 100 query และอีก 111 query จากการโหลดรายการสินค้าในแต่ละ order ทั้งหมดนี้ไม่มีใครเห็นตอน review เพราะ ORM ซ่อน query ไว้ใต้ property access

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| แก้ root cause | ดึงข้อมูลที่เกี่ยวข้องมาในครั้งเดียว (join หรือ batch load ด้วย id ชุดเดียว) |
| แก้เสริม | ใส่ pagination บังคับ (default limit) ไม่ให้ดึงทั้งตาราง |
| แก้เสริม | เพิ่ม index บนคอลัมน์ที่ใช้กรอง/เรียง ถ้า EXPLAIN บอกว่ายัง scan |
| ป้องกันซ้ำ | เพิ่ม test ที่ assert ว่า endpoint นี้ใช้ query ไม่เกิน N ครั้ง |
| ป้องกันซ้ำ | ตั้ง alert เมื่อ p95 latency ของ endpoint เกิน threshold |
| ป้องกันซ้ำ | เพิ่ม log จำนวน query ต่อ request ใน environment dev ให้เห็นตั้งแต่ตอนเขียน |

**หลักคิดที่ต้องจำ:** ปัญหาเรื่องช้าให้ถามเสมอว่า **"ช้าเพราะทำงานหนึ่งอย่างช้า หรือช้าเพราะทำงานเล็ก ๆ หลายร้อยครั้ง"** — วิธีแก้คนละทางกันโดยสิ้นเชิง

### 🔧 Scenario 3 — "React render ซ้ำ"

**Observation**

- หน้าค้นหาสินค้า พิมพ์ในช่องค้นหาแล้วรู้สึกหน่วง ตัวอักษรขึ้นช้ากว่าที่พิมพ์
- React Profiler แสดงว่าพิมพ์ 1 ตัวอักษร → component ลูกทั้งหน้า render ใหม่ประมาณ 400 ตัว
- บนเครื่อง dev ที่แรงไม่ค่อยรู้สึก แต่บนมือถือลูกค้าช้าชัดเจน

**Possible Layers**

```
[State]        state อยู่สูงเกินไป → เปลี่ยนทีเดียวลามทั้งต้นไม้
     ↓
[Props]        ส่ง object / array / function ใหม่ทุกรอบ → ลูกคิดว่าเปลี่ยน
     ↓
[Context]      value ของ context เป็น object ใหม่ทุก render
     ↓
[Rendering]    list ยาวไม่มี virtualization
     ↓
[Effect]       useEffect ตั้ง state ต่อ → render ซ้อน render
     ↓
[Browser]      งานหนักอยู่บน main thread ทำให้ input ตอบช้า
```

> **ให้มองภาพนี้ว่า** "React จะ re-render ลูกทั้งกิ่งเมื่อพ่อ render ใหม่ ปัญหาจึงมักไม่ได้อยู่ที่ลูกที่ช้า แต่อยู่ที่ว่าเราวาง state ไว้สูงเกินความจำเป็น"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| React DevTools → Profiler | component ไหน render กี่ครั้ง ใช้เวลาเท่าไร |
| Profiler → "Why did this render?" | เปลี่ยนเพราะ props / state / parent / context |
| Highlight updates | เห็นกรอบกระพริบว่าอะไร render บ้างตอนพิมพ์ |
| Performance tab | งานบน main thread ยาวเกิน 50ms ตรงไหน |
| โค้ด: ตำแหน่งของ state | `searchText` ถูกประกาศไว้ที่ component ไหน |

สมมติหลักฐาน: Profiler บอกว่า `<ProductList>` (400 items) re-render ทุกครั้งที่พิมพ์ และเหตุผลคือ "parent re-rendered"

**Hypothesis**

1. `searchText` state อยู่ที่ component พ่อสุด ทำให้ทุกอย่างใต้มัน render ใหม่ทุกตัวอักษร
2. ส่ง prop เป็น inline object / arrow function ใหม่ทุกรอบ ทำให้ memo ไม่ช่วยอะไร
3. ใช้ Context ตัวเดียวเก็บทุกอย่าง และสร้าง value object ใหม่ทุก render
4. รายการยาว 400 รายการวาดจริงทั้งหมดในครั้งเดียว โดยไม่มี virtualization
5. ไม่มี debounce ทำให้ยิงค้นหาทุกตัวอักษร

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| ย้าย state ลงไปไว้ที่ component ช่องค้นหาเท่านั้น (ทดลองชั่วคราว) | ถ้าหน่วงหาย → ข้อ 1 คือสาเหตุหลัก |
| ห่อ `<ProductList>` ด้วย memo แล้ววัดใหม่ | ถ้ายัง render → มี prop ที่เปลี่ยน reference ทุกรอบ (ข้อ 2) |
| ดู Profiler ว่า prop ไหนเปลี่ยน | ชี้ตัวจริงว่า function หรือ object ตัวไหน |
| ลด list เหลือ 20 รายการ | ถ้าเร็วขึ้นมาก → ข้อ 4 มีส่วน |
| เพิ่ม delay ก่อนยิง search | ถ้าหน่วงต่างจากเดิม → ข้อ 5 มีส่วน |

**Root Cause**

`searchText` ถูกเก็บไว้ที่ component หน้าใหญ่สุด และ `<ProductList>` รับ prop เป็น `filters={{...}}` ที่สร้างใหม่ทุก render ผลคือทุกการกดแป้นทำให้ทั้งหน้า reconcile ใหม่ และรายการ 400 ตัวถูกเทียบใหม่ทั้งหมดบน main thread

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| แก้หลัก | ย้าย state ลงให้ใกล้จุดที่ใช้ที่สุด (colocate state) |
| แก้หลัก | ทำให้ prop ที่ส่งลงไปมี reference คงที่เมื่อค่าไม่เปลี่ยน |
| แก้เสริม | แยก component ที่เปลี่ยนบ่อยออกจาก component ที่นิ่ง |
| แก้เสริม | ใช้ virtualization กับ list ยาว และ debounce การค้นหา |
| ป้องกันซ้ำ | ใส่ Profiler check ในขั้นตอน review หน้าที่มี list ใหญ่ |
| ป้องกันซ้ำ | ตั้งกติกาทีม: state ใหม่ต้องเริ่มจากล่างสุดก่อน ค่อยยกขึ้นเมื่อจำเป็นจริง |
| ป้องกันซ้ำ | วัด interaction latency บนเครื่องจริงของผู้ใช้ ไม่ใช่เครื่อง dev |

**หลักคิดที่ต้องจำ:** ก่อนจะโปรยคำสั่ง memo ทั่วไฟล์ ให้ถามก่อนว่า **"ทำไมพ่อถึง render"** เพราะ 80% ของปัญหานี้แก้ได้ด้วยการย้าย state ไม่ใช่การเพิ่ม memo

### 🔧 Scenario 4 — "Database ช้า"

**Observation**

- ทุกเช้าวันจันทร์ 09:00-09:40 ระบบช้าทั้งเว็บ ไม่ใช่เฉพาะหน้าเดียว
- Metric: latency ของแทบทุก endpoint ขึ้นพร้อมกัน
- CPU ของ database sustained 90%+ ในช่วงนั้น เวลาอื่นอยู่ที่ 20%
- ไม่ได้ deploy อะไรใหม่เลยในสัปดาห์นั้น

**Possible Layers**

```
[Application]  N+1 / เปิด connection ไม่ปิด / retry ถล่ม
     ↓
[Connection]   pool เต็ม → request ต้องรอคิว
     ↓
[Query]        query หนักตัวเดียวกิน CPU / ไม่มี index
     ↓
[Lock]         transaction ยาวจับ lock ค้าง คนอื่นรอ
     ↓
[Data Volume]  ตารางโตจนแผนการค้นหาเปลี่ยน
     ↓
[Infra]        job / backup / report รันชนกับเวลาใช้งานจริง
```

> **ให้มองภาพนี้ว่า** "ถ้าทุกหน้าช้าพร้อมกัน แปลว่ามีทรัพยากรกลางบางอย่างเต็ม ไม่ใช่โค้ดหน้าใดหน้าหนึ่งเขียนไม่ดี"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| Metric ของ database | CPU, active connection, lock wait, cache hit ratio |
| Slow query log ช่วงเวลานั้น | query ไหนโผล่บ่อยและกินเวลานาน |
| รายการ session/process ที่กำลังรัน | ใครถือ lock อยู่ ใครรออยู่ |
| ตารางงานที่ตั้งเวลาไว้ (cron / batch) | มี job รายงานประจำสัปดาห์รันตอน 09:00 ไหม |
| Connection pool metric ฝั่ง app | เต็มไหม, เวลารอคิวเท่าไร |
| ขนาดตารางย้อนหลัง | ตารางไหนโตเร็วผิดปกติ |

สมมติหลักฐาน: มี query รายงานยอดขายรายสัปดาห์ที่รันตอน 09:00 ทุกวันจันทร์ สแกนตาราง order ทั้งหมดและทำงานบน database ตัวเดียวกับระบบหลัก

**Hypothesis**

1. Batch report รันชนเวลาใช้งาน กิน CPU และ I/O จนงานปกติแย่งไม่ทัน
2. Transaction ของ report ถือ lock ยาว ทำให้ write ของระบบหลักรอ
3. Connection pool ถูก report กินจนเหลือให้ระบบหลักน้อย
4. ข้อมูลโตจนแผนการค้นหา (query plan) ของ query หลักเปลี่ยนไปใช้ full scan
5. เช้าวันจันทร์ traffic ผู้ใช้สูงกว่าปกติอยู่แล้ว (ปัจจัยร่วม ไม่ใช่สาเหตุเดียว)

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| เลื่อน job ไปรันตี 3 สัปดาห์ถัดไป | ถ้าจันทร์ถัดไปไม่ช้า → ยืนยันข้อ 1 |
| ดู lock wait ระหว่างช่วงนั้น | ถ้าสูง → ข้อ 2 มีส่วน; ถ้าเกือบศูนย์ → ตัดข้อ 2 |
| ดูกราฟ connection ที่ใช้ vs ขนาด pool | ตัดหรือยืนยันข้อ 3 |
| `EXPLAIN` query หลักตอนนี้ เทียบกับที่เคยเป็น | ตัดหรือยืนยันข้อ 4 |
| เทียบ traffic ผู้ใช้จันทร์กับวันอื่น | รู้ว่าเป็นปัจจัยร่วมมากแค่ไหน |

**Root Cause**

รายงานรายสัปดาห์รันบน database หลักในเวลาที่คนใช้งานสูงสุด สแกนข้อมูลย้อนหลังทั้งหมด ทำให้ buffer cache ถูกไล่ออก (cache ของข้อมูลที่ระบบหลักใช้บ่อยหายไป) และ CPU เต็ม ระบบหลักจึงช้าทั้งกระดาน

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| หยุดเลือด | เลื่อนเวลา job ไปช่วงที่คนใช้น้อย |
| แก้ root cause | ย้าย workload รายงานไปที่ read replica แยกจากตัวหลัก |
| แก้เสริม | ทำรายงานแบบสะสมล่วงหน้า แทนการสแกนย้อนหลังทุกครั้ง |
| แก้เสริม | จำกัดเวลาทำงานสูงสุดของ query (statement timeout) ไม่ให้ตัวเดียวถล่มทั้งระบบ |
| ป้องกันซ้ำ | แยก connection pool ของงาน batch ออกจากงาน online |
| ป้องกันซ้ำ | เพิ่ม alert เมื่อ CPU database เกิน 70% ต่อเนื่อง 5 นาที |
| ป้องกันซ้ำ | ทำ dashboard ที่ซ้อนกราฟ "งานที่ตั้งเวลาไว้" ทับกับ "latency" ให้เห็นความสัมพันธ์ทันที |

### 🔧 Scenario 5 — "Production error (แต่ local ไม่เป็น)"

**Observation**

- Error tracking แจ้งว่ามี exception ใหม่ 1,200 ครั้งใน 20 นาที
- ข้อความ: `NullPointerException` (หรือ `TypeError: cannot read property of undefined`) ที่ฟังก์ชันคำนวณส่วนลด
- ทีมลองบน local และ staging ตามขั้นตอนเดียวกัน ไม่เกิดเลย
- เพิ่ง deploy ไป 25 นาทีที่แล้ว

**Possible Layers**

```
[Data]        ข้อมูลจริงมีรูปแบบที่ dev ไม่เคยเจอ
     ↓
[Config]      env variable ต่างกันระหว่าง prod กับ local
     ↓
[Version]     dependency / build ไม่เหมือนกัน
     ↓
[Scale]       เกิดเฉพาะตอนมี concurrency สูง (race condition)
     ↓
[Integration] external service ตอบต่างจาก mock ที่ใช้ตอน dev
     ↓
[Cache]       ข้อมูลเก่าใน cache มีโครงสร้างคนละแบบกับโค้ดใหม่
```

> **ให้มองภาพนี้ว่า** "บั๊กที่เกิดเฉพาะ production แปลว่ามีตัวแปรบางอย่างที่ production มีแต่เครื่องเราไม่มี และตัวแปรนั้นมักคือข้อมูลจริงหรือ config"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| Error tracking | stack trace เต็ม + จำนวนครั้ง + เริ่มเวลาไหน + กระทบกี่ user |
| Error tracking → context | user id, request payload, version ของ release |
| Deploy timeline | เริ่ม error ตรงกับ deploy พอดีไหม |
| Log ของ request ที่พัง | ค่า input จริงที่เข้ามาคืออะไร |
| เทียบ config prod กับ staging | ตัวแปรไหนต่าง |
| สัดส่วน error | เกิดกับทุก request หรือแค่บาง % (ชี้ว่าขึ้นกับข้อมูล) |

สมมติหลักฐาน: error เกิดกับ ~4% ของ request และทุกเคสมี `coupon` เป็น `null` ในข้อมูล order

**Hypothesis**

1. โค้ดใหม่อ่าน field ของ coupon โดยไม่เช็ก null และข้อมูลจริงมี order เก่าที่ไม่มี coupon
2. Config ของ prod ชี้ไปที่ service ส่วนลดคนละตัว ซึ่งตอบโครงสร้างต่างกัน
3. ข้อมูลใน cache ที่ค้างจากเวอร์ชันก่อน มีโครงสร้างไม่ตรงกับโค้ดใหม่
4. Race condition ที่เกิดเฉพาะตอนมีผู้ใช้พร้อมกันมาก

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| เอา payload จริงจาก log มารันบน local | ถ้าพังทันที → ยืนยันข้อ 1 และตัดข้อ 4 |
| นับสัดส่วน error เทียบกับสัดส่วน order ที่ไม่มี coupon | ถ้าตรงกัน → หลักฐานหนักแน่นมาก |
| diff config prod vs staging | ตัดหรือยืนยันข้อ 2 |
| ล้าง cache บางส่วนแล้วดูว่า error ลดไหม | ตัดหรือยืนยันข้อ 3 |
| ดูว่า error กระจายทุกช่วงเวลาไหม หรือกระจุกตอน peak | ถ้ากระจายสม่ำเสมอ → ไม่ใช่ race condition |

**Root Cause**

โค้ดใหม่สมมติว่า order ทุกใบต้องมี coupon object เสมอ (เพราะ data ที่ dev ใช้ทดสอบถูก seed มาให้มี coupon ครบทุกใบ) แต่ข้อมูลจริงมี order เก่าก่อนระบบ coupon ถูกสร้าง ซึ่ง field นั้นเป็น null

ชั้นที่ลึกกว่านั้น: ไม่มีการตรวจสอบรูปร่างข้อมูลที่ขอบระบบ (validation at boundary) และข้อมูลทดสอบไม่สะท้อนข้อมูลจริง

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| หยุดเลือด | rollback ไปเวอร์ชันก่อนหน้าทันที (เลือดหยุดใน 5 นาที) |
| แก้ root cause | จัดการกรณีไม่มี coupon อย่างชัดเจน และกำหนดค่าปริยายที่ถูกต้องทางธุรกิจ |
| แก้เสริม | ตรวจสอบและแปลงข้อมูลที่ขอบระบบให้อยู่ในรูปที่โค้ดภายในเชื่อถือได้ |
| ป้องกันซ้ำ | เพิ่ม test ที่ใช้ข้อมูลรูปแบบเก่า (legacy shape) เป็น fixture |
| ป้องกันซ้ำ | ทำข้อมูล staging ให้สะท้อนความหลากหลายของข้อมูลจริง (ลบข้อมูลส่วนบุคคลออก) |
| ป้องกันซ้ำ | ใช้ canary release ปล่อยให้ traffic 5% ก่อน แล้วดู error rate ก่อนปล่อยเต็ม |
| ป้องกันซ้ำ | ตั้ง alert error rate ให้เด้งภายใน 2 นาทีหลัง deploy |

**ประโยคสัมภาษณ์ที่ใช้ได้:** "ถ้าเกิดเฉพาะ production ผมจะสงสัยสามอย่างก่อนเสมอ คือข้อมูลจริง, config และขนาด/ความพร้อมกัน แล้วเอา payload จริงจาก log มารันบนเครื่องตัวเองเพื่อย่อปัญหาให้เล็กที่สุด"

### 🔧 Scenario 6 — "Docker container start ไม่ได้"

**Observation**

- รัน container แล้วสถานะขึ้น `Exited (1)` ภายใน 2 วินาที
- บนเครื่อง dev คนหนึ่งรันได้ อีกคนรันไม่ได้ ทั้งที่ใช้ image เดียวกัน
- ไม่มี log ยาว ๆ มีแค่ไม่กี่บรรทัดแล้วหยุด

**Possible Layers**

```
[Image]        build ไม่สำเร็จ / ไฟล์ที่ต้องใช้ไม่ได้ถูก copy เข้า image
     ↓
[Entrypoint]   คำสั่งเริ่มต้นผิด / ไฟล์ไม่มีสิทธิ์รัน
     ↓
[Config/Env]   ตัวแปรที่จำเป็นไม่ถูกส่งเข้าไป → app ตายตอน start
     ↓
[Dependency]   ต่อ database / service อื่นไม่ได้ตั้งแต่ตอน boot
     ↓
[Port/Volume]  port ชนกับของเดิม / mount path ไม่มีจริง
     ↓
[Platform]     สถาปัตยกรรม CPU ไม่ตรงกับ image ที่ build ไว้
```

> **ให้มองภาพนี้ว่า** "container คือกล่องที่รันคำสั่งเดียว ถ้าคำสั่งนั้นจบ กล่องก็ปิด — งานของเราคือหาว่าคำสั่งนั้นจบเพราะทำงานเสร็จ หรือจบเพราะตาย"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| `docker logs <container>` | บรรทัดสุดท้ายก่อนตาย — มักบอกทุกอย่าง |
| exit code | 0 = จบปกติ, 1 = error ใน app, 137 = ถูกฆ่า (OOM/kill), 127 = ไม่เจอคำสั่ง |
| `docker inspect` | entrypoint/cmd จริงที่ถูกใช้, env, mount |
| `docker run ... sh` แทน entrypoint | เข้าไปดูข้างในว่าไฟล์ครบไหม |
| `docker history` / Dockerfile | ขั้นตอน build ตัวไหนที่อาจ copy ไม่ครบ |
| เทียบเครื่องที่รันได้ vs ไม่ได้ | env file ต่างกันไหม, สถาปัตยกรรม CPU ต่างกันไหม |

สมมติหลักฐาน: log บรรทัดสุดท้ายคือ `Error: DATABASE_URL is required` และ exit code = 1

**Hypothesis**

1. ไฟล์ env ไม่ถูกส่งเข้า container บนเครื่องคนที่รันไม่ได้ (เครื่องที่รันได้มี `.env` อยู่ในโฟลเดอร์)
2. ชื่อตัวแปรสะกดไม่ตรงกันระหว่าง compose file กับโค้ด
3. Secret ถูกฉีดเข้ามาจาก tool ภายนอกที่คนหนึ่งลงไว้ อีกคนไม่ได้ลง
4. Image ที่สองเครื่องใช้จริง ๆ เป็นคนละ tag (คนหนึ่งใช้ cache เก่า)

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| รัน container แล้วสั่ง `env` ดูตัวแปรทั้งหมด | เห็นชัดว่ามี DATABASE_URL จริงไหม |
| เทียบ digest ของ image สองเครื่อง | ตัดหรือยืนยันข้อ 4 |
| ส่ง env ตรงจาก command line แล้วรันใหม่ | ถ้ารันได้ → ยืนยันว่าเป็นเรื่องการส่ง env |
| grep ชื่อตัวแปรในโค้ดกับใน compose | ตัดหรือยืนยันข้อ 2 |
| รัน container โดย override entrypoint เป็น shell | ตรวจว่าไฟล์และสิทธิ์ครบไหม |

**Root Cause**

ไฟล์ `.env` อยู่ใน `.gitignore` (ถูกต้องแล้ว) แต่ไม่มีไฟล์ `.env.example` และไม่มีเอกสารบอกว่าต้องมีตัวแปรอะไรบ้าง คนใหม่ในทีมจึงรันแล้วตายทันที และ error message เดิมก็ไม่ได้บอกว่าขาดตัวไหนบ้างในครั้งเดียว

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| แก้เฉพาะหน้า | ส่งตัวแปรที่ขาดเข้าไป แล้วรันใหม่ |
| แก้ root cause | เพิ่มขั้นตอนตรวจ config ตอน app เริ่ม: ถ้าขาดให้บอก **ทุกตัวที่ขาดพร้อมกัน** แล้วจบด้วยข้อความที่อ่านรู้เรื่อง |
| ป้องกันซ้ำ | เพิ่ม `.env.example` ที่มีคีย์ครบ (ไม่มีค่าจริง) และเขียนไว้ใน README |
| ป้องกันซ้ำ | ใส่ healthcheck ใน compose/Dockerfile เพื่อแยก "ยังไม่พร้อม" ออกจาก "ตายแล้ว" |
| ป้องกันซ้ำ | ทำสคริปต์ setup ที่รันครั้งเดียวแล้วเครื่องใหม่พร้อมใช้งาน |
| ป้องกันซ้ำ | ระบุ platform ของ image ให้ชัด เพื่อกันปัญหา CPU ต่างสถาปัตยกรรม |

**เคล็ดลับที่ใช้ได้เสมอ:** ถ้า container ตายเร็วมาก ให้ดู **exit code ก่อน log** เพราะตัวเลขนั้นบอกหมวดของสาเหตุได้ทันที (แอปตายเอง vs ถูกระบบฆ่า vs หาคำสั่งไม่เจอ)

### 🔧 Scenario 7 — "Kubernetes pod restart ตลอด"

**Observation**

- `kubectl get pods` แสดง `CrashLoopBackOff` และ RESTARTS = 27
- เกิดกับ pod ของ service เดียว pod อื่นปกติ
- เริ่มหลัง deploy เวอร์ชันใหม่เมื่อ 1 ชั่วโมงก่อน
- ผู้ใช้บางส่วนยังใช้งานได้ บางส่วนเจอ error เป็นช่วง ๆ

**Possible Layers**

```
[Application]  แอปตายเองเพราะ exception ตอน start
     ↓
[Probe]        liveness probe ตรวจผิดจุด → k8s ฆ่าทั้งที่แอปยังดี
     ↓
[Resource]     memory limit ต่ำเกิน → ถูกฆ่าด้วย OOMKilled
     ↓
[Config]       ConfigMap / Secret ไม่มี key ที่ต้องใช้
     ↓
[Dependency]   ต่อ database ไม่ได้ตอน start → ตายทันที
     ↓
[Image]        pull image ไม่ได้ / tag ผิด
```

> **ให้มองภาพนี้ว่า** "Kubernetes ไม่ได้ทำให้แอปพัง มันแค่ทำตามที่เราสั่งว่า ถ้าแอปไม่ผ่านเกณฑ์สุขภาพให้ฆ่าแล้วเปิดใหม่ — หน้าที่เราคือหาว่าเกณฑ์ผิด หรือแอปผิด"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| `kubectl describe pod` | เหตุผลการ restart: OOMKilled / Error / probe failed |
| `kubectl logs <pod> --previous` | log ของ container รอบที่ตายไปแล้ว (สำคัญมาก) |
| ส่วน Events ใน describe | ลำดับเหตุการณ์: pull image, start, probe fail, kill |
| resource requests/limits | memory limit เท่าไร เทียบกับที่แอปใช้จริง |
| ค่า probe | path, initialDelaySeconds, timeout, threshold |
| Metric memory ของ pod | กราฟขึ้นแล้วตกเป็นฟันเลื่อยไหม (ชี้ OOM) |

สมมติหลักฐาน: `describe` บอก `Last State: Terminated, Reason: OOMKilled` และกราฟ memory ขึ้นถึง limit ภายใน 3 นาทีทุกครั้ง

**Hypothesis**

1. เวอร์ชันใหม่ใช้ memory มากขึ้นจริง (โหลดข้อมูลเข้า memory มากขึ้น) แต่ limit ยังเท่าเดิม
2. มี memory leak ในโค้ดใหม่ ทำให้โตเรื่อย ๆ จนชน limit
3. Limit ถูกตั้งไว้ต่ำผิดตั้งแต่แรก และเวอร์ชันก่อนหน้าก็เฉียดอยู่แล้ว
4. Runtime ไม่รู้ว่าตัวเองอยู่ใน container ที่มี limit เลยจอง heap เกินขนาดที่ container อนุญาต
5. liveness probe ตั้ง timeout สั้นเกิน ทำให้ถูกฆ่าซ้อนตอนแอปกำลังทำงานหนัก (ปัจจัยร่วม)

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| ดูรูปทรงกราฟ memory | ขึ้นแล้วคงที่ = ข้อ 1/3; ขึ้นเรื่อย ๆ ไม่ลง = ข้อ 2 (leak) |
| เทียบ memory ที่ใช้ระหว่างเวอร์ชันเก่า/ใหม่บน staging | ยืนยันว่าเวอร์ชันใหม่กินมากขึ้นจริงไหม |
| เพิ่ม limit ชั่วคราวแล้วดูว่าหยุด restart ไหม | แยก "ไม่พอ" ออกจาก "รั่ว" — ถ้ารั่วจะแค่ตายช้าลง ไม่หาย |
| ดูค่าที่ runtime จองจริงตอน start | ตัดหรือยืนยันข้อ 4 |
| ดู event ว่ามี probe failed ก่อน OOM ไหม | ตัดหรือยืนยันข้อ 5 |

**Root Cause**

เวอร์ชันใหม่เพิ่มการ cache ข้อมูล master ไว้ใน memory ของแต่ละ pod โดยไม่มีขอบเขตสูงสุด เมื่อข้อมูลโตขึ้น memory จึงชน limit ที่ตั้งไว้เท่าเดิม → Kubernetes ฆ่า pod → เปิดใหม่ → โหลด cache ใหม่ → ชน limit อีก เป็นวงจร

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| หยุดเลือด | rollback ไปเวอร์ชันก่อนหน้า หรือเพิ่ม limit ชั่วคราวเพื่อให้บริการกลับมา |
| แก้ root cause | จำกัดขนาด cache สูงสุด + มีนโยบายไล่ของเก่าออก |
| แก้เสริม | ย้าย cache ที่ใช้ร่วมกันไปไว้ที่ cache กลาง แทนที่จะเก็บซ้ำในทุก pod |
| แก้เสริม | ตั้ง requests/limits ให้สอดคล้องกับที่วัดได้จริง และให้ runtime รับรู้ limit ของ container |
| ป้องกันซ้ำ | เพิ่ม alert เมื่อ memory ใช้เกิน 80% ของ limit |
| ป้องกันซ้ำ | เพิ่ม alert เมื่อ restart count เพิ่มขึ้นในช่วงสั้น |
| ป้องกันซ้ำ | แยก liveness (ยังมีชีวิตไหม) ออกจาก readiness (พร้อมรับ traffic ไหม) ให้ชัด เพื่อไม่ให้แอปที่แค่ช้าถูกฆ่าทิ้ง |

### 🔧 Scenario 8 — "Memory usage สูงขึ้นเรื่อย ๆ"

**Observation**

- กราฟ memory ของ service หนึ่งไต่ขึ้นเรื่อย ๆ ตลอดสัปดาห์ ไม่เคยลง
- ทุกครั้งที่ deploy (= restart) กราฟตกลงมาที่ฐานเดิมแล้วเริ่มไต่ใหม่
- ยังไม่มีใครบ่น แต่ถ้าปล่อยไว้จะชน limit ในอีก 3 วัน

**Possible Layers**

```
[Code]        เก็บของไว้ใน collection ระดับ global แล้วไม่เคยลบ
     ↓
[Cache]       cache ไม่มีขนาดสูงสุด / ไม่มีวันหมดอายุ
     ↓
[Listener]    ลงทะเบียน event/subscription แล้วไม่ยกเลิก
     ↓
[Connection]  เปิด connection / stream / file แล้วไม่ปิด
     ↓
[Runtime]     ตั้ง heap ใหญ่เกินจริง ทำให้ดูเหมือนรั่วทั้งที่ยังไม่ใช่
     ↓
[Traffic]     โหลดโตขึ้นตามธรรมชาติ (ไม่ใช่รั่ว แค่ต้องขยาย)
```

> **ให้มองภาพนี้ว่า** "memory leak คืออ่างน้ำที่เปิดก๊อกไว้แต่จุกไม่ปิดสนิท ระดับน้ำจึงขึ้นเรื่อย ๆ และการ restart คือการดึงจุกออกชั่วคราว ไม่ใช่การซ่อมจุก"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| กราฟ memory ระยะยาว | ขึ้นเป็นเส้นตรงตามเวลา หรือขึ้นตาม traffic |
| กราฟ memory เทียบกับจำนวน request สะสม | ถ้าสัมพันธ์กับจำนวน request สะสม → leak ต่อ request |
| Heap snapshot 2 จุดเวลา แล้วเทียบกัน | object ชนิดไหนเพิ่มขึ้นมากที่สุด |
| จำนวน object / listener / connection ที่ยังเปิดอยู่ | ตัวเลขนี้โตขึ้นเรื่อย ๆ ไหม |
| GC metric | เก็บกวาดบ่อยขึ้นแต่คืน memory ได้น้อยลงไหม |
| Diff ของ commit ช่วงที่กราฟเริ่มเปลี่ยนชัน | มีอะไรเปลี่ยนตรงนั้น |

สมมติหลักฐาน: heap snapshot บอกว่า object ชนิดเดียวเพิ่มขึ้น 400,000 ตัวใน 2 ชั่วโมง และมันถูกอ้างถึงจาก Map ตัวหนึ่งที่เป็นตัวแปรระดับ module

**Hypothesis**

1. มี Map/Dictionary ระดับ global ที่ใส่ข้อมูลต่อ request เข้าไปแล้วไม่เคยลบ
2. Cache ไม่มี TTL และไม่มีขนาดสูงสุด
3. มีการลงทะเบียน event listener ทุกครั้งที่มี request แต่ไม่ยกเลิก
4. Memory ขึ้นเพราะ traffic โตจริง ไม่ใช่รั่ว (ต้องตัดออกให้ได้ก่อน)

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| หยุดส่ง traffic ไปที่ instance หนึ่งแล้วดูว่า memory ลดไหม | ถ้าไม่ลดเลย → ของค้างจริง (ไม่ใช่แค่ traffic) |
| ยิง load test แบบเดิมซ้ำ ๆ แล้วดูว่า memory กลับมาที่ฐานเดิมไหม | กลับ = ไม่รั่ว, ไม่กลับ = รั่ว |
| เทียบ heap snapshot ก่อน/หลังยิง 10,000 request | เห็นชัดว่าอะไรค้าง และใครถืออยู่ |
| ดู reference chain ของ object ที่ค้าง | ชี้บรรทัดจริงในโค้ด |
| ปิดฟีเจอร์ที่สงสัยด้วย flag บน instance เดียว | เปรียบเทียบกับ instance อื่นแบบควบคุมตัวแปร |

**Root Cause**

โค้ดเก็บสถานะของแต่ละ request ไว้ใน Map ระดับ module เพื่อใช้ตอน callback กลับมา แต่ในกรณีที่ request ล้มเหลวหรือ timeout จะไม่มีใครลบ key นั้นออก ผลคือ entry ค้างสะสมไปเรื่อย ๆ ตามจำนวน request ที่ล้มเหลว

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| หยุดเลือด | ตั้ง restart ตามกำหนดชั่วคราว เพื่อกันชน limit ระหว่างรอแก้ (วิธีชั่วคราวเท่านั้น) |
| แก้ root cause | ลบ entry ในทุกเส้นทางการจบงาน ทั้งสำเร็จ ล้มเหลว และ timeout |
| แก้เสริม | เปลี่ยนไปใช้โครงสร้างที่มีขนาดสูงสุดและมีอายุหมดในตัว |
| ป้องกันซ้ำ | เพิ่ม metric ที่วัดขนาดของ collection นั้นโดยตรง แล้วตั้ง alert |
| ป้องกันซ้ำ | เพิ่ม soak test (ยิงโหลดต่อเนื่องหลายชั่วโมง) ใน pipeline ก่อน release ใหญ่ |
| ป้องกันซ้ำ | ตั้งกติกาทีม: ทุกที่ที่ "เพิ่มของเข้า collection" ต้องตอบได้ว่า "ใครลบ และเมื่อไร" |

**หลักคิดที่ต้องจำ:** ก่อนจะสรุปว่า leak ต้องตัดคำอธิบายที่ง่ายกว่าทิ้งก่อนเสมอ — traffic โต, cache อุ่นเครื่อง, runtime ยังไม่ได้เก็บกวาด สามอย่างนี้หน้าตาเหมือน leak ในกราฟช่วงสั้น

### 🔧 Scenario 9 — "API ได้ 401 Unauthorized"

**Observation**

- ผู้ใช้ที่เปิดเว็บทิ้งไว้ตั้งแต่เช้า พอกดปุ่มบันทึกตอนบ่ายได้ 401 และถูกเด้งออก
- ผู้ใช้ที่เพิ่ง login ใหม่ใช้งานได้ปกติ
- เกิดกับทุกคนที่ทิ้งหน้าไว้นานเกินประมาณ 1 ชั่วโมง

**Possible Layers**

```
[Client]     ไม่ได้แนบ token ไปกับ request / แนบผิดที่
     ↓
[Token]      หมดอายุ / ถูกเพิกถอน / ผิด audience
     ↓
[Refresh]    ไม่มีกลไกต่ออายุ หรือมีแต่ทำงานไม่ครบทุกกรณี
     ↓
[Server]     secret / key เปลี่ยน → verify ไม่ผ่านทุกใบ
     ↓
[Clock]      เวลาเครื่อง server เพี้ยน → มองว่าใบยังไม่ถึงเวลาใช้ หรือหมดอายุแล้ว
     ↓
[Gateway]    proxy ตัด header Authorization ทิ้ง
```

> **ให้มองภาพนี้ว่า** "401 แปลว่าระบบไม่รู้ว่าคุณเป็นใคร ส่วน 403 แปลว่ารู้ว่าคุณเป็นใครแต่ห้ามทำ — สองอันนี้ทำให้เราไปคนละทิศในการสืบ"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| DevTools → Network → Request Headers | มี `Authorization` ติดไปจริงไหม |
| ถอด payload ของ token (ส่วนที่ไม่ลับ) | `exp`, `iat`, `iss`, `aud` เทียบกับเวลาปัจจุบัน |
| Response body ของ 401 | server บอกเหตุผลอะไร (หมดอายุ / ลายเซ็นผิด / ไม่มี token) |
| Backend log ของ request นั้น | เหตุผลการปฏิเสธฝั่ง server |
| ดูว่าเกิดกับทุกคนหรือเฉพาะคนที่ทิ้งไว้นาน | ชี้ไปที่เรื่องอายุ token มากกว่าเรื่อง key |
| Gateway config | มีการกรอง header ไหม |

สมมติหลักฐาน: token มีอายุ 60 นาที, request ที่ 401 ทุกใบมี `exp` ที่ผ่านมาแล้ว, และ frontend ไม่เคยเรียก endpoint refresh เลย

**Hypothesis**

1. Access token หมดอายุ และ frontend ไม่มีกลไก refresh
2. มี refresh แต่ทำงานเฉพาะตอนโหลดหน้าใหม่ ไม่ทำงานตอนหน้าเปิดค้างไว้
3. Refresh token เองก็หมดอายุ เพราะตั้งอายุสั้นเกินไป
4. Server เปลี่ยน signing key ทำให้ token เก่าใช้ไม่ได้ (แต่ข้อนี้ควรกระทบทุกคน ไม่ใช่เฉพาะคนที่ทิ้งไว้นาน)

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| เปิดหน้าไว้ 61 นาที แล้วกดปุ่ม | ถ้าได้ 401 ตรงเวลา → ยืนยันเรื่องอายุ token |
| ดูว่ามี request ไป endpoint refresh ไหมใน Network | ตัดหรือยืนยันข้อ 1/2 |
| ยิง API ด้วย token ที่เพิ่งออกใหม่ ผ่าน curl | ถ้าผ่าน → key ฝั่ง server ปกติ ตัดข้อ 4 |
| โหลดหน้าใหม่แล้วกดทันที | ถ้าได้ → ยืนยันว่า refresh ทำงานเฉพาะตอนโหลดหน้า (ข้อ 2) |
| เทียบเวลาเครื่อง server กับเวลาจริง | ตัดเรื่อง clock |

**Root Cause**

Frontend อ่าน token จาก storage ตอนโหลดหน้าเว็บครั้งเดียว แล้วเก็บไว้ในหน่วยความจำจนกว่าจะรีเฟรชหน้า ไม่มีการดักจับ 401 เพื่อขอ token ใหม่แล้วยิงซ้ำ ผู้ใช้ที่ทิ้งหน้าไว้เกินอายุ token จึงเจอ 401 ทุกครั้ง และที่แย่กว่าคือระบบเด้งออกโดยไม่บอกว่าเกิดอะไรขึ้น

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| แก้ root cause | ทำตัวจัดการกลางของ API client: เจอ 401 → ขอ token ใหม่ → ยิง request เดิมซ้ำอัตโนมัติหนึ่งครั้ง |
| แก้เสริม | กันการขอ refresh พร้อมกันหลายใบ (หลาย request 401 พร้อมกัน) ให้เหลือครั้งเดียวแล้วรอผลร่วมกัน |
| แก้เสริม | ถ้า refresh ไม่ผ่านจริง ให้แสดงข้อความชัดเจนว่า "เซสชันหมดอายุ กรุณาเข้าสู่ระบบใหม่" แทนการเด้งเงียบ ๆ |
| ป้องกันซ้ำ | เพิ่ม integration test ที่จำลอง token หมดอายุระหว่างใช้งาน |
| ป้องกันซ้ำ | เพิ่ม metric อัตรา 401 แยกตามสาเหตุ (หมดอายุ / ไม่มี token / ลายเซ็นผิด) |
| ป้องกันซ้ำ | ให้ server ตอบเหตุผลที่แยกแยะได้ในระดับที่ไม่เปิดเผยข้อมูลอ่อนไหว เพื่อให้ debug ได้เร็ว |

**จำไว้:** 401 = ไม่รู้ว่าคุณเป็นใคร, 403 = รู้แล้วแต่ไม่ให้ทำ — การแยกสองอันนี้ออกจากกันทำให้ประหยัดเวลาการสืบไปได้ครึ่งชั่วโมงทุกครั้ง

### 🔧 Scenario 10 — "API ได้ 500 Internal Server Error"

**Observation**

- ปุ่ม "ยืนยันคำสั่งซื้อ" ตอบ 500 กับผู้ใช้บางส่วน
- response body เป็นข้อความกลาง ๆ ว่า `{"message":"Internal server error"}` ไม่มีรายละเอียด
- เกิดประมาณ 8% ของ request ตั้งแต่เที่ยงวัน
- ไม่มี deploy ในวันนี้

**Possible Layers**

```
[Input]        ข้อมูลบางรูปแบบทำให้โค้ดพัง (ตัวอักษรพิเศษ, ค่าว่าง, ค่าใหญ่มาก)
     ↓
[Code]         exception ที่ไม่ได้จัดการ
     ↓
[Dependency]   external API ตอบช้า/ตอบผิดรูปแบบ → โค้ดเราพังต่อ
     ↓
[Database]     connection เต็ม / timeout / ข้อมูลผิดข้อจำกัด
     ↓
[Resource]     memory หรือ file descriptor หมด
     ↓
[Infra]        pod บางตัวป่วย แต่ load balancer ยังส่ง traffic ไป
```

> **ให้มองภาพนี้ว่า** "500 ไม่ใช่สาเหตุ มันคือคำว่า ฉันพังแต่ไม่อยากบอกเหตุผลต่อหน้าผู้ใช้ — เหตุผลจริงอยู่ใน log ฝั่ง server เสมอ"

**Evidence**

| ดูที่ไหน | ดูอะไร |
|---|---|
| Backend log / error tracking | stack trace เต็มของ request ที่ 500 |
| Trace id | ตามรอย request เดียวข้ามทุก service |
| สัดส่วน error แยกตาม pod/instance | ถ้ากระจุกที่ instance เดียว → ปัญหาอยู่ที่เครื่องนั้น |
| สัดส่วน error แยกตาม input | มี pattern ร่วมอะไรใน payload ที่พัง |
| Metric ของ dependency | external service ตอบช้าขึ้นตอนเที่ยงไหม |
| Database metric | connection ที่ใช้ vs สูงสุด, error ของ timeout |

สมมติหลักฐาน: stack trace ชี้ไปที่การเรียก service คำนวณค่าส่ง และข้อความคือ read timeout; และ 8% นั้นตรงกับช่วงที่ service คำนวณค่าส่งมี latency สูงเกิน timeout ที่เราตั้งไว้

**Hypothesis**

1. External service ช้าลงตอนเที่ยง เกิน timeout ที่เราตั้ง → เรา throw ออกมาเป็น 500
2. เรา retry ซ้ำแรงเกินไป จนยิ่งถล่ม service ปลายทางให้ช้าขึ้นอีก (วงจรป้อนกลับ)
3. Connection pool ไปยัง service นั้นเล็กเกิน → request ต้องรอคิวจนหมดเวลา
4. มี instance บางตัวของฝั่งเราป่วย (เช่น DNS cache ค้าง) ทำให้เฉพาะ traffic ที่ไปตัวนั้นพัง

**Test**

| ทดสอบอะไร | ตัดสินอะไร |
|---|---|
| ดูกราฟ latency ของ external service เทียบกับ error ของเรา | ถ้ารูปทรงตรงกัน → ยืนยันข้อ 1 |
| แยก error rate ตาม instance | กระจายทุกตัว → ตัดข้อ 4 |
| ดูจำนวน request ที่เรายิงไป external ช่วงนั้น | ถ้าพุ่งเกินปกติมาก → ข้อ 2 มีส่วน |
| ดู metric การรอคิวของ connection pool | ตัดหรือยืนยันข้อ 3 |
| ยิงทดสอบไป external โดยตรงจากเครื่อง server | วัดว่าช้าจริงจากฝั่งเขา ไม่ใช่เน็ตเรา |

**Root Cause**

Service คำนวณค่าส่งของผู้ให้บริการภายนอกช้าลงในช่วงเที่ยง (เวลาที่คนสั่งเยอะ) ระบบเราตั้ง timeout ไว้และเมื่อ timeout ก็โยน exception ออกมาเป็น 500 โดยไม่มีทางหนี และยังมีการ retry ทันที 3 ครั้งแบบไม่มีการหน่วง ทำให้ปริมาณ request ไปที่ปลายทางเพิ่มขึ้นเป็นสามเท่าในช่วงที่มันกำลังป่วย — ซ้ำเติมปัญหาให้ยาวขึ้น

**Fix + ป้องกันไม่ให้เกิดซ้ำ**

| ระยะ | ทำอะไร |
|---|---|
| หยุดเลือด | ลดจำนวน retry และเพิ่มการหน่วงแบบเพิ่มขึ้นเรื่อย ๆ พร้อมสุ่มเวลา |
| แก้ root cause | ออกแบบ fallback: ถ้าคำนวณค่าส่งไม่ได้ ให้ใช้ค่าประมาณตามโซนแล้วทำเครื่องหมายไว้ ไม่ใช่ทำให้ทั้งคำสั่งซื้อพัง |
| แก้เสริม | ใส่ circuit breaker: ถ้าปลายทางป่วย ให้หยุดยิงชั่วคราวแล้วค่อยลองใหม่ |
| แก้เสริม | แยกให้ชัดว่า error ของ dependency ควรกลายเป็น 503 + Retry-After มากกว่า 500 |
| ป้องกันซ้ำ | ใส่ trace id ใน response ที่ผู้ใช้เห็น เพื่อให้ support แจ้งกลับมาแล้วเราค้นได้ทันที |
| ป้องกันซ้ำ | ตั้ง alert ที่ error rate ไม่ใช่ที่จำนวน error (ป้องกันการมองไม่เห็นตอน traffic น้อย) |
| ป้องกันซ้ำ | เพิ่ม test ที่จำลองว่า dependency ช้า/ล่ม แล้วดูว่าระบบยังทำงานในระดับที่ยอมรับได้ |

**หลักคิดที่ต้องจำ:** เวลาเจอ 500 ให้ถามเสมอว่า **"เราพังเอง หรือเราพังเพราะคนอื่นพังแล้วเราไม่มีแผนสำรอง"** — สองอย่างนี้แก้คนละแบบ

## 7. Compare

### ตารางที่ 1 — คำที่มักใช้ปนกัน

| คำ | หมายถึงอะไร | ตัวอย่าง | ถ้าสับสนจะเกิดอะไร |
|---|---|---|---|
| **Symptom (อาการ)** | สิ่งที่สังเกตเห็น | "หน้าขาว" | แก้ที่อาการ อาการกลับมาอีก |
| **Cause (สาเหตุใกล้)** | สิ่งที่ทำให้อาการเกิดโดยตรง | "อ่าน property ของ undefined" | แก้แล้วบั๊กคล้ายกันยังเกิดที่อื่น |
| **Root Cause (ต้นตอ)** | จุดที่แก้แล้วบั๊กหมวดนี้หายไป | "ไม่มีการจัดการ error กลางของ API client" | ถ้าถึงจุดนี้ ถึงจะจบจริง |
| **Trigger (ตัวจุดชนวน)** | เหตุการณ์ที่ทำให้ปัญหาโผล่วันนี้ | "deploy เมื่อ 09:00" | สับสนว่า trigger คือ root cause บ่อยมาก |

### ตารางที่ 2 — เครื่องมือสามเสาของ observability

| เครื่องมือ | ตอบคำถามว่า | เก่งเรื่อง | ไม่เก่งเรื่อง |
|---|---|---|---|
| **Log** | "เกิดอะไรขึ้นกับ request นี้" | รายละเอียดเชิงเหตุการณ์ | มองภาพรวมตามเวลา, แพงถ้าเก็บทุกอย่าง |
| **Metric** | "ผิดปกติตั้งแต่เมื่อไร และแรงแค่ไหน" | เห็นแนวโน้ม ตั้ง alert ได้ | บอกไม่ได้ว่า request ไหนพังเพราะอะไร |
| **Trace** | "เวลาหายไปตรงไหนของเส้นทาง" | ระบบหลาย service, ปัญหาความช้า | ไม่ได้บอกรายละเอียดภายในโค้ด |

> **กฎการเลือก:** เริ่มจาก metric (รู้ว่าเมื่อไรและแรงแค่ไหน) → trace (รู้ว่าตรงไหน) → log (รู้ว่าทำไม)

### ตารางที่ 3 — วิธีค้นหาตำแหน่งบั๊ก

| วิธี | ใช้เมื่อไร | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **อ่านโค้ด** | บั๊กอยู่ในขอบเขตแคบและเรารู้ที่แล้ว | ไม่ต้องรันอะไร | ตาลายง่าย เสียเวลามากถ้าขอบเขตกว้าง |
| **ใส่ log เพิ่ม** | ต้องรู้ค่าจริงตอนรัน | เห็นข้อมูลจริง ใช้ได้บน production | ต้อง deploy ใหม่ ถ้าใส่เยอะจะรก |
| **Breakpoint / debugger** | ต้องดูหลายตัวแปรพร้อมกัน | เห็นสถานะครบ เดินทีละก้าวได้ | ใช้กับ production ยาก, ไม่เหมาะกับปัญหา timing |
| **Bisect (ตัดครึ่ง)** | รู้ว่า "เคยดี ตอนนี้พัง" | หา commit ต้นเหตุได้เร็วมาก | ต้องมีวิธีทดสอบอัตโนมัติว่าพังหรือไม่ |
| **ตัดชิ้นส่วนออก** | สงสัยว่า component ไหนเป็นตัวปัญหา | พิสูจน์ได้ชัดเจน | ต้องแก้ชั่วคราว ระวังลืมคืนสภาพ |
| **เปรียบเทียบ environment** | เกิดที่เดียวไม่เกิดที่อื่น | ชี้ตัวแปรที่ต่างได้ตรง ๆ | ต้องมีรายการ config ที่เทียบได้ |

### ตารางที่ 4 — Debug บน local vs บน production

| หัวข้อ | Local | Production |
|---|---|---|
| เป้าหมายแรก | เข้าใจสาเหตุ | ทำให้ผู้ใช้กลับมาใช้ได้ |
| เครื่องมือหลัก | debugger, breakpoint, log ละเอียด | metric, trace, error tracking, log ที่มีอยู่ |
| ความเสี่ยงของการทดลอง | ต่ำ ลองได้เรื่อย ๆ | สูง ทุกการทดลองกระทบผู้ใช้จริง |
| ข้อจำกัด | ข้อมูลไม่เหมือนจริง | เข้าถึงข้อมูลได้จำกัดด้วยเหตุผลความเป็นส่วนตัว |
| วิธีที่ควรใช้ | ทดลองเร็ว วนหลายรอบ | เปลี่ยนน้อยครั้ง คิดให้รอบคอบก่อนทุกครั้ง |

### ตารางที่ 5 — HTTP status ที่บอกทิศทางการสืบ

| Status | แปลว่า | เริ่มดูที่ไหนก่อน |
|---|---|---|
| **400** | เราส่งข้อมูลผิดรูปแบบ | payload ที่ frontend ส่ง, validation ฝั่ง server |
| **401** | ระบบไม่รู้ว่าคุณเป็นใคร | token, header, การ refresh |
| **403** | รู้ว่าเป็นใครแต่ไม่ให้ทำ | role / permission / policy |
| **404** | หาไม่เจอ | path, id, routing, การ deploy ไม่ครบ |
| **409** | ชนกับสถานะปัจจุบัน | ข้อมูลซ้ำ, การแก้พร้อมกัน |
| **429** | ยิงถี่เกิน | rate limit, retry ที่แรงเกิน |
| **500** | ฝั่งเราพัง | stack trace ใน log ของเรา |
| **502 / 503 / 504** | ตัวกลางหรือปลายทางมีปัญหา | upstream service, timeout, pod ไม่พร้อม |

## 8. Common Mistakes

| ความเข้าใจผิด | ทำไมถึงผิด | ทำแบบนี้แทน |
|---|---|---|
| **แก้ก่อน เข้าใจทีหลัง** | ถ้าหายโดยไม่รู้สาเหตุ แปลว่ามันจะกลับมาแน่นอน | เดินตาม framework จนถึง root cause ก่อนพิมพ์แก้ |
| **เปลี่ยนหลายอย่างพร้อมกัน** | หายแล้วก็ไม่รู้ว่าเพราะอะไร | เปลี่ยนทีละอย่าง วัดผลทีละครั้ง |
| **เชื่อคำเล่ามากกว่าหลักฐาน** | "ไม่ได้แก้อะไรเลย" มักไม่จริงเสมอ | ดู log, deploy history, diff ด้วยตาตัวเอง |
| **ข้ามขั้น Reproduce** | จะไม่มีวันรู้ว่าแก้แล้วหายจริงไหม | ลงทุนเวลาทำให้เกิดซ้ำก่อน มันคุ้มเสมอ |
| **ตั้งสมมติฐานข้อเดียว** | สมองจะหาหลักฐานมาสนับสนุนข้อนั้นอย่างเดียว | บังคับตัวเองให้เขียน 3 ข้อขึ้นไป |
| **คิดว่า trigger คือ root cause** | "deploy ทำให้พัง" ไม่ได้บอกว่าพังเพราะอะไร | ถามต่อว่า deploy นั้นเปลี่ยนอะไร และทำไมสิ่งนั้นทำให้พัง |
| **ใส่ try-catch กลบ error** | อาการหาย แต่ข้อมูลอาจผิดเงียบ ๆ ซึ่งแย่กว่าพังดัง ๆ | จับ error เฉพาะกรณีที่รู้ว่าจะทำอะไรต่อ และต้อง log ไว้เสมอ |
| **เชื่อว่า "โค้ดฉันถูกแน่นอน"** | บั๊กชอบซ่อนในจุดที่เรามั่นใจที่สุด | ตรวจสมมติฐานพื้นฐานด้วยการพิมพ์ค่าออกมาดูจริง |
| **debug ด้วยการ restart แล้วจบ** | restart คือการซ่อนอาการ ไม่ใช่การแก้ | restart ได้เพื่อหยุดเลือด แต่ต้องมีงานตามต่อเสมอ |
| **ไม่จดว่าลองอะไรไปแล้วบ้าง** | พอเวลาผ่านไป 2 ชั่วโมงจะเริ่มลองซ้ำของเดิม | จดไทม์ไลน์สั้น ๆ: เวลา + ทำอะไร + ผลเป็นยังไง |
| **debug คนเดียวเกิน 45 นาทีโดยไม่คืบ** | ติดในกรอบความคิดเดิม | อธิบายให้เพื่อนฟัง (rubber duck) — มักเจอเองระหว่างพูด |
| **ลบ log ทิ้งหลังแก้เสร็จ** | ครั้งหน้าจะเริ่มจากศูนย์ใหม่ | เก็บ log ที่มีประโยชน์ไว้ ทำให้เป็นของถาวร |
| **ไม่เขียน regression test เพราะ "แก้นิดเดียว"** | บั๊กที่เคยเกิดมักเกิดซ้ำได้ง่ายที่สุด | เขียนเทสต์ให้บั๊กทุกตัวที่หลุดถึงผู้ใช้ |
| **คิดว่าไม่มี error ใน console = ไม่มีปัญหาฝั่ง frontend** | error หลายอย่างถูกกลืนใน promise ที่ไม่มี catch | ดู Network tab และ error tracking ประกอบเสมอ |
| **ตีความ coincidence เป็น causation** | สองอย่างเกิดพร้อมกันไม่ได้แปลว่าอันหนึ่งทำให้อีกอันเกิด | ต้องมีกลไกอธิบายได้ว่าทำไม A ทำให้ B |

## 9. Debugging

หัวข้อนี้คือ "debug ตัวกระบวนการ debug เอง" — เมื่อไล่มาแล้วแต่ยังไม่คืบ ให้ไล่ตามลำดับนี้

### เมื่อรู้สึกว่าตัน ให้ถาม 6 คำถามนี้ตามลำดับ

```
1. ฉันกำลังอยู่ step ไหนของ framework?
        ↓ (ตอบไม่ได้ = กำลังเดา ให้กลับไป step 1)
2. ข้อเท็จจริงที่ "พิสูจน์แล้ว" มีอะไรบ้าง? เขียนออกมาเป็นข้อ ๆ
        ↓
3. สิ่งที่ฉัน "สมมติว่าจริง" แต่ยังไม่ได้พิสูจน์ มีอะไรบ้าง?
        ↓ (คำตอบของบั๊กมักซ่อนอยู่ในรายการนี้)
4. ถ้าข้อสมมติที่มั่นใจที่สุดกลับเป็นเท็จ อะไรจะอธิบายทุกอาการได้พอดี?
        ↓
5. มีใครในทีมเคยเจออาการแบบนี้ไหม? มีในระบบ ticket ไหม?
        ↓
6. ถ้าต้องอธิบายเรื่องนี้ให้คนนอกฟังใน 3 ประโยค ฉันจะพูดว่าอะไร?
```

> **ให้มองภาพนี้ว่า** "เวลาที่ตัน ปัญหาไม่ได้อยู่ที่ข้อมูลไม่พอ แต่อยู่ที่มีข้อสมมติบางข้อที่เราไม่เคยคิดจะตรวจ"

### ตารางอาการของกระบวนการ debug ที่ผิดทาง

| อาการ | แปลว่า | ทำอะไรต่อ |
|---|---|---|
| ลองแก้ไปแล้ว 5 อย่าง ยังไม่หาย | กำลังเดา ไม่ได้สืบ | หยุด กลับไป EVIDENCE เก็บหลักฐานใหม่ |
| อธิบายให้เพื่อนฟังไม่ได้ว่าปัญหาคืออะไร | ยังผ่าน ACTUAL/EXPECTED ไม่จริง | เขียน expected กับ actual ลงกระดาษ |
| อาการหายเองโดยไม่ได้ทำอะไร | ปัญหาขึ้นกับเวลา/โหลด/สถานะภายนอก | เก็บหลักฐานทันทีตอนเกิด ไม่ใช่ตอนหาย |
| ทุกสมมติฐานถูกตัดหมดแล้ว | สมมติฐานพื้นฐานบางข้อผิด | ตรวจสิ่งที่ "แน่นอนอยู่แล้ว" เช่น ยิงถูก environment ไหม, ดู log ถูก service ไหม |
| แก้บน dev หาย แต่ prod ยังเป็น | ตัวแปรที่ต่างยังไม่ถูกระบุ | ทำตาราง diff: version, config, data, scale |
| มีคนบอกว่า "เมื่อวานยังดีอยู่" | มีอะไรเปลี่ยนระหว่างนั้นแน่นอน | ไล่ timeline: deploy, config, ข้อมูล, certificate, dependency, quota |

### ลำดับการไล่ปัญหาแบบเร็วสำหรับ production incident

```
1. กระทบผู้ใช้กี่คน อะไรบ้าง (blast radius)
        ↓
2. เริ่มเมื่อไร และตอนนั้นมีอะไรเปลี่ยน
        ↓
3. หยุดเลือดได้ไหม (rollback / flag / scale / ปิดฟีเจอร์)
        ↓
4. สื่อสารให้ทีมและผู้เกี่ยวข้องรู้สถานะ
        ↓
5. เก็บหลักฐานไว้ให้ครบ ก่อนที่มันจะหายไปตาม retention
        ↓
6. สืบหาสาเหตุจริงเมื่อเลือดหยุดแล้ว
        ↓
7. Postmortem: ทำไมด่านก่อนหน้าไม่จับ และจะเพิ่มด่านตรงไหน
```

> **ให้มองภาพนี้ว่า** "ตอนไฟไหม้ ลำดับคือพาคนออกก่อน ดับไฟ แล้วค่อยสอบสวนหาต้นเพลิง ไม่ใช่ยืนสอบสวนตั้งแต่ไฟยังลุก"

## 10. Interview Questions

### 🟢 Junior

1. **"เล่าวิธี debug ของคุณเวลาเจอบั๊ก"**
   สิ่งที่เขาฟัง: คุณมีลำดับในหัวไหม หรือทำแบบสุ่ม
2. **"เจอ `undefined is not a function` จะเริ่มจากตรงไหน"**
   สิ่งที่เขาฟัง: รู้จักอ่าน stack trace และรู้ว่าต้องหาว่าค่าที่คาดว่าจะมีนั้นหายไปตั้งแต่ตรงไหน
3. **"401 กับ 403 ต่างกันยังไง"**
   สิ่งที่เขาฟัง: เข้าใจว่าอันหนึ่งคือไม่รู้ว่าเป็นใคร อีกอันคือรู้แล้วแต่ห้าม
4. **"console.log กับ debugger ใช้ต่างกันตอนไหน"**
   สิ่งที่เขาฟัง: รู้ว่าอันไหนเหมาะกับสถานการณ์ไหน ไม่ใช่ท่องว่าอันไหนดีกว่า
5. **"ถ้าบั๊กเกิดซ้ำไม่ได้ จะทำยังไง"**
   สิ่งที่เขาฟัง: รู้ว่าต้องเพิ่มหลักฐาน ไม่ใช่เดาแล้วแก้ไปก่อน
6. **"หน้าเว็บขาว ไม่ขึ้นอะไรเลย ดูอะไรก่อน"**
   สิ่งที่เขาฟัง: เปิด console และ network เป็นอันดับแรก

### 🟡 Mid

1. **"API ช้า จะไล่ยังไงตั้งแต่ต้น"**
   สิ่งที่เขาฟัง: แยกเวลาออกเป็นช่วง ๆ ก่อน ไม่กระโดดไปเดาว่า database ช้า
2. **"เกิดเฉพาะบน production ไม่เกิดบน local จะทำยังไง"**
   สิ่งที่เขาฟัง: รู้ว่าตัวแปรที่ต่างคือข้อมูล, config, scale และรู้วิธีย่อปัญหาให้เล็กลง
3. **"อธิบาย N+1 query และวิธีจับได้"**
   สิ่งที่เขาฟัง: รู้ว่าดูจำนวน query ต่อ request ไม่ใช่แค่พูดคำว่า N+1 ได้
4. **"pod CrashLoopBackOff จะไล่ยังไง"**
   สิ่งที่เขาฟัง: รู้จัก `describe`, `logs --previous` และแยกสาเหตุ OOM / probe / config
5. **"เจอ flaky test จะจัดการยังไง"**
   สิ่งที่เขาฟัง: รู้ว่ามักมาจากเวลา ลำดับ หรือสถานะที่แชร์กัน และรู้ว่าปิดทิ้งไม่ใช่คำตอบ
6. **"จะรู้ได้ยังไงว่าแก้บั๊กถูกจุดจริง"**
   สิ่งที่เขาฟัง: มีเทสต์ที่แดงก่อนแก้ และมีตัวเลขยืนยันหลัง deploy
7. **"เห็น memory ขึ้นเรื่อย ๆ จะสรุปว่ารั่วเลยไหม"**
   สิ่งที่เขาฟัง: รู้ว่าต้องตัดคำอธิบายที่ง่ายกว่าออกก่อน

### 🔴 Senior

1. **"ระบบล่มตอนตีสอง คุณเป็นคนแรกที่รับสาย เล่าลำดับสิ่งที่ทำ"**
   สิ่งที่เขาฟัง: หยุดเลือดก่อนหาสาเหตุ, ประเมิน blast radius, สื่อสาร, เก็บหลักฐาน
2. **"ทีมคุณ MTTR สูง จะลดยังไง"**
   สิ่งที่เขาฟัง: มองเป็นปัญหาระบบ (observability, runbook, alert คุณภาพ, การซ้อม) ไม่ใช่โทษคน
3. **"จะออกแบบระบบให้ debug ง่ายตั้งแต่แรกยังไง"**
   สิ่งที่เขาฟัง: correlation id, structured log, ระดับ log ที่เหมาะ, error ที่มีบริบท, feature flag
4. **"บั๊กเกิดเดือนละครั้ง หาไม่เจอ จะทำยังไง"**
   สิ่งที่เขาฟัง: ยอมรับว่าต้องลงทุนกับหลักฐานก่อน แล้วรอให้มันเกิดอีกครั้งพร้อมกล้องที่ตั้งไว้แล้ว
5. **"เลือกยังไงระหว่าง rollback กับ fix forward"**
   สิ่งที่เขาฟัง: พิจารณาความเสี่ยง เวลา migration ของข้อมูล และผลกระทบต่อผู้ใช้ ไม่ใช่มีคำตอบตายตัว
6. **"postmortem ที่ดีมีอะไรบ้าง และทำไมต้องไม่โทษคน"**
   สิ่งที่เขาฟัง: เข้าใจว่าการโทษคนทำให้คนซ่อนข้อมูล และข้อมูลที่ซ่อนคือสิ่งที่ทำให้เกิดซ้ำ
7. **"ถ้า dependency ภายนอกช้า ระบบคุณควรมีพฤติกรรมยังไง"**
   สิ่งที่เขาฟัง: timeout, retry ที่มีการหน่วง, circuit breaker, fallback, การลดระดับบริการอย่างสง่างาม

## 11. Answer Like a Developer

### โครงการตอบคำถาม debug ทุกข้อ (ใช้ได้กับทุกคำถามในหัวข้อ 10)

```
1. ถามกลับก่อน 2-3 คำถาม เพื่อจำกัดขอบเขต
        ↓
2. บอกว่าจะตัดชั้นไหนออกก่อน และดูหลักฐานอะไร
        ↓
3. ยกสมมติฐาน 3 ข้อ พร้อมบอกว่าจะพิสูจน์แต่ละข้อยังไง
        ↓
4. บอกว่าเมื่อเจอ root cause แล้วจะแก้แบบไหน และทำไม
        ↓
5. ปิดท้ายด้วยการป้องกันไม่ให้เกิดซ้ำ (test + monitor)
```

> **ให้มองภาพนี้ว่า** "ผู้สัมภาษณ์ไม่ได้อยากได้คำตอบที่ถูก เขาอยากดูว่าถ้าเอาปัญหาที่เขาไม่เคยบอกคุณมาวางตรงหน้า คุณจะเดินยังไง"

### ประโยคเปิดที่ใช้ได้เสมอ (ท่องแค่โครง ไม่ต้องท่องคำ)

> "ก่อนตอบ ขอถามสามข้อครับ — เกิดกับผู้ใช้ทุกคนหรือบางคน, เริ่มตั้งแต่เมื่อไร, และช่วงนั้นมี deploy หรือเปลี่ยน config อะไรไหม เพราะสามข้อนี้จะตัดสาเหตุออกไปได้ครึ่งหนึ่งแล้ว"

### ตัวอย่างคำตอบแบบเต็ม (คำถาม: "API ช้า จะทำยังไง")

โครงที่ควรพูด:

1. **จำกัดขอบเขต** — "ช้าทุก endpoint หรือเฉพาะตัวนี้ ช้าตลอดหรือช้าบางช่วง เริ่มช้าตั้งแต่เมื่อไร"
2. **แยกเวลาก่อน** — "ผมจะดูก่อนว่าเวลาหายไปช่วงไหน ระหว่างเน็ต, เวลาที่ server ใช้คิด, หรือเวลาที่ browser ใช้วาด โดยดูจาก TTFB กับ trace"
3. **สมมติฐาน** — "ถ้า server เป็นตัวช้า ผมจะสงสัยสามอย่าง: จำนวน query ต่อ request, query ตัวเดียวที่ช้าเพราะไม่มี index, หรือรอ external service"
4. **วิธีพิสูจน์** — "ดูจำนวน query จาก trace, ดู EXPLAIN ของ query หลัก, และดู latency ของ dependency ในช่วงเดียวกัน"
5. **การแก้ตามสาเหตุ** — "ถ้าเป็น N+1 แก้ด้วยการดึงทีเดียว ถ้าเป็น index ก็เพิ่ม index แต่ต้องดูผลต่อ write ด้วย ถ้าเป็น dependency ต้องคุยเรื่อง timeout และ fallback"
6. **ป้องกันซ้ำ** — "สุดท้ายผมจะเพิ่ม alert ที่ p95 latency และเพิ่ม test ที่ล็อกจำนวน query ไว้ ไม่ให้ใครเผลอทำให้กลับไปเป็น N+1 อีก"

### สิ่งที่ห้ามพูด

| ห้ามพูด | เพราะอะไร | พูดแบบนี้แทน |
|---|---|---|
| "ผมจะลอง restart ดูก่อน" | ฟังดูเหมือนไม่มีกระบวนการ | "ถ้ากระทบผู้ใช้อยู่ ผมจะหยุดเลือดก่อนด้วย rollback แล้วค่อยสืบ" |
| "ผมจะ google หาคำตอบ" | ทุกคนทำ แต่มันไม่ใช่กระบวนการ | "ผมจะเก็บหลักฐานให้พอก่อน แล้วค่อยค้นด้วยข้อความ error ที่แน่นอน" |
| "น่าจะเป็นที่ backend" | เดาโดยไม่มีหลักฐาน | "ผมจะยิง API ตรงด้วย curl เพื่อตัด frontend ออกก่อน" |
| "ผมไม่เคยเจอเคสนี้" | ปิดบทสนทนา | "ผมยังไม่เคยเจอเคสนี้ตรง ๆ แต่ผมจะไล่แบบนี้..." แล้วเดินตาม framework |

## 12. One-Minute Review

**Debugging คืออะไร:** การหาว่าทำไมสิ่งที่เกิดจริงไม่ตรงกับสิ่งที่ควรเกิด โดยใช้หลักฐานเป็นตัวตัดสิน ไม่ใช่ความรู้สึก

**Framework หลักของเล่มนี้:**

```
REPRODUCE → EXPECTED → ACTUAL → LOCATE → EVIDENCE → HYPOTHESIS
   → TEST → ROOT CAUSE → FIX → REGRESSION TEST → MONITOR
```

**กฎที่ห้ามละเมิด 5 ข้อ:**

1. ห้ามแก้ก่อนรู้สาเหตุ
2. ห้ามเปลี่ยนหลายอย่างพร้อมกัน
3. ห้ามมีสมมติฐานข้อเดียว
4. ห้ามเชื่อคำเล่าโดยไม่ดูหลักฐานเอง
5. ห้ามปิดงานโดยไม่มี regression test

**ลำดับบน production:** หยุดเลือด → สื่อสาร → เก็บหลักฐาน → สืบสาเหตุ → แก้ถาวร → postmortem

**ถ้าตัน:** เขียนรายการ "สิ่งที่พิสูจน์แล้ว" กับ "สิ่งที่สมมติว่าจริง" — คำตอบมักอยู่ในรายการที่สอง

**สิ่งที่ผู้สัมภาษณ์วัดจริง:** ไม่ใช่คำตอบ แต่คือลำดับการคิด และการถามกลับเพื่อจำกัดขอบเขตก่อนตอบ

## 13. Memory Card

### จำ 5 อย่าง

1. **Debugging = ลดพื้นที่ค้นหา ไม่ใช่เดาคำตอบ** — ตัดชั้นออกทีละครึ่งจนเหลือจุดเดียว
2. **ไม่มี Reproduce = ไม่มีทางรู้ว่าแก้หาย** — ขั้นแรกสำคัญที่สุดและถูกข้ามบ่อยที่สุด
3. **สมมติฐานต้องมีอย่างน้อย 3 ข้อ และต้องพิสูจน์ผิดได้** — ข้อเดียวคือกับดักของสมอง
4. **อาการ ≠ สาเหตุ** — ถามทำไมต่ออีก 5 ครั้ง จนถึงจุดที่แก้แล้วบั๊กหมวดนี้หายทั้งหมวด
5. **จบงานที่ regression test + monitor เสมอ** — แก้แล้วต้องมียามเฝ้าเพิ่มหนึ่งคน

### Keyword

**Keyword:**
**Reproduce** → ทำให้พังซ้ำได้ตามสั่ง ถ้าทำไม่ได้ให้ไปลงทุนเพิ่มหลักฐานแทน
**Expected / Actual** → สองบรรทัดที่วางคู่กันแล้วกลายเป็นนิยามของบั๊ก
**Locate** → หาว่าปัญหาหยุดอยู่ชั้นไหนของระบบ ก่อนเปิดโค้ดไฟล์แรก
**Evidence** → log (ทำไม) + metric (เมื่อไร) + trace (ตรงไหน)
**Hypothesis** → ข้อเดาที่พิสูจน์ผิดได้ ต้องมี ≥ 3 ข้อเสมอ
**Test** → เปลี่ยนทีละอย่าง และตอบให้ได้ก่อนทำว่าผลแต่ละแบบแปลว่าอะไร
**Root Cause** → จุดที่แก้แล้วอาการไม่กลับมา และอธิบายได้ว่าทำไมเพิ่งเกิดวันนี้
**Fix** → บน production ให้หยุดเลือดก่อน แล้วค่อยแก้ให้ถูกต้อง
**Regression Test** → เทสต์ที่ต้องแดงก่อนแก้ ถึงจะเชื่อถือได้
**Monitor** → ถ้ามันกลับมา เราต้องรู้ก่อนผู้ใช้เสมอ
**5 Whys** → เครื่องมือขุดจากอาการลงไปถึงต้นตอ
**Blast Radius** → กระทบใครบ้าง กี่คน — ตัวตัดสินว่าจะรีบแค่ไหน
**MTTR** → ตัวชี้วัดว่าทีมเรา debug เก่งขึ้นจริงหรือไม่
**Postmortem** → สรุปเหตุการณ์แบบไม่โทษคน เพื่อให้คนกล้าบอกความจริง
