# PART 24 — SYSTEM DESIGN FUNDAMENTALS

> ตำแหน่งในภาพใหญ่: Whole-System Layer — มองทุกชั้นที่เรียนมา (Frontend → Backend → Database → Infrastructure) พร้อมกัน แล้วตัดสินใจว่าจะประกอบมันเข้าด้วยกันอย่างไร

---

## 1. Big Picture

รอบ System Design คือรอบที่คนสัมภาษณ์พูดประโยคเดียว เช่น **"ลองออกแบบ URL shortener แบบ bit.ly ให้หน่อย"** แล้วก็เงียบ ปล่อยให้คุณพูดต่ออีก 45 นาที

junior ส่วนใหญ่จะรีบลุกไปที่ whiteboard แล้ววาดกล่องให้มากที่สุดในทันที ทั้ง Load Balancer, Kafka, Redis, Microservices, Kubernetes เพราะคิดว่ายิ่งกล่องเยอะยิ่งดูเก่ง **นั่นคือวิธีที่เสียคะแนนเร็วที่สุด**

สิ่งที่คนสัมภาษณ์อยากเห็นจริง ๆ ไม่ใช่ architecture ที่จำมา แต่เป็น **วิธีคิด** ของคุณ

- คุณ **ถามข้อกำหนดก่อน** หรือเปล่า (ระบบนี้ต้องทำอะไร ใช้กี่คน)
- คุณ **ประเมินขนาด** ได้ไหม (ต้องรับกี่ request ต่อวินาที เก็บข้อมูลกี่ GB)
- คุณ **เริ่มจากสิ่งง่ายที่สุดที่ใช้งานได้** แล้วค่อยเพิ่มชิ้นส่วนเมื่อมีเหตุผลหรือเปล่า
- คุณ **อธิบาย trade-off** ได้ไหม (เลือก A เพราะอะไร แลกกับอะไร)

พูดง่าย ๆ ว่า System Design ไม่มีคำตอบถูกข้อเดียว มีแต่ **คำตอบที่มีเหตุผลรองรับ** กับ **คำตอบที่ไม่มีเหตุผลรองรับ** ส่วนภาพพื้นฐานที่ทุกระบบบนเว็บมีเหมือนกันคือแบบนี้

```
[USER]
   ↓
[FRONTEND]        ← React / Next.js / Mobile App
   ↓
[LOAD BALANCER]   ← กระจาย request ไปหลายเครื่อง
   ↓
[BACKEND]         ← Node / Spring Boot / Python
   ↓
[CACHE]           ← Redis: ของที่อ่านบ่อย
   ↓
[DATABASE]        ← PostgreSQL / MySQL / MongoDB
```

ให้มองภาพนี้ว่า "ร้านอาหารหนึ่งร้าน ลูกค้าสั่งผ่านหน้าร้าน พนักงานต้อนรับพาไปโต๊ะที่ว่าง พ่อครัวทำอาหาร ของที่ขายดีเตรียมไว้ก่อน และวัตถุดิบทั้งหมดอยู่ในห้องเก็บของ"

ทุกอย่างที่เพิ่มเข้าไปหลังจากนี้ ทั้ง CDN, API Gateway, Queue, Worker, Object Storage, WebSocket **ล้วนเพิ่มเพราะเจอปัญหาจริงสักข้อ** ไม่ได้เพิ่มเพราะมันฟังดูเท่ บทนี้จะสอนให้คุณเพิ่มทีละชั้นพร้อมบอกเหตุผลได้ทุกครั้ง

> เนื้อหาเชิงลึกของแต่ละชิ้นส่วนอยู่ในบทอื่นแล้ว: Queue / Cache / Rate Limit / Idempotency ดู **PART 16 (Advanced Backend)** ส่วน Logs / Metrics / Traces / Alert ดู **PART 23 (Observability)** บทนี้เน้น "ประกอบร่าง" และ "วิธีพูดในห้องสัมภาษณ์"

## 2. Keywords

| Keyword | จำสั้นๆ | ความหมาย |
|---|---|---|
| System Design | ออกแบบทั้งระบบ | การเลือกและเชื่อมชิ้นส่วน (server, DB, cache, queue) ให้ระบบตอบโจทย์ทั้งเรื่องฟังก์ชันและขนาด |
| Functional Requirement | ระบบต้องทำอะไร | ฟีเจอร์ เช่น "ย่อ URL ได้", "กดลิงก์แล้วพาไปหน้าเดิมได้" |
| Non-Functional Requirement (NFR) | ระบบต้องดีแค่ไหน | คุณภาพ เช่น เร็วแค่ไหน ล่มได้ไหม รองรับกี่คน ปลอดภัยแค่ไหน |
| DAU | ผู้ใช้ต่อวัน | Daily Active Users → จำนวนคนที่ใช้งานใน 1 วัน → จุดเริ่มคำนวณ traffic |
| QPS / RPS | request ต่อวินาที | Queries / Requests Per Second → วัดภาระที่ server ต้องรับ |
| Peak Traffic | ช่วงคนแน่นที่สุด | traffic ช่วงพีค มักประเมินเป็น 2–5 เท่าของค่าเฉลี่ย |
| Back-of-Envelope | คำนวณหลังซองจดหมาย | การประมาณตัวเลขคร่าว ๆ เพื่อรู้ "ขนาดของปัญหา" ไม่ต้องแม่นเป๊ะ |
| Read-heavy / Write-heavy | อ่านเยอะ / เขียนเยอะ | อัตราส่วนอ่าน:เขียน เป็นตัวกำหนดว่าจะเน้น cache หรือเน้น DB ที่เขียนเร็ว |
| Latency | ความหน่วง | เวลาที่ 1 request ใช้ตั้งแต่ส่งจนได้คำตอบ |
| Throughput | ปริมาณงานต่อเวลา | จำนวนงานที่ระบบทำได้ในหนึ่งหน่วยเวลา |
| Availability | ความพร้อมใช้งาน | สัดส่วนเวลาที่ระบบใช้ได้ เช่น 99.9% ≈ ล่มได้ราว 8–9 ชั่วโมงต่อปี |
| Consistency | ข้อมูลตรงกัน | ทุกคนอ่านแล้วเห็นข้อมูลล่าสุดเหมือนกันหรือไม่ |
| Horizontal Scaling | เพิ่มจำนวนเครื่อง | scale out → เพิ่ม server หลายเครื่องแล้วให้ LB กระจายงาน |
| Vertical Scaling | เพิ่มสเปคเครื่อง | scale up → เพิ่ม CPU/RAM ในเครื่องเดิม ง่ายแต่มีเพดาน |
| Stateless | server ไม่จำอะไร | server ไม่เก็บ session ในตัว ทำให้ request ไหนไปเครื่องไหนก็ได้ |
| Load Balancer | พนักงานจัดคิว | ตัวกระจาย request ไปยัง server หลายเครื่อง และตัดเครื่องที่พังออก |
| CDN | โกดังสาขาใกล้บ้าน | Content Delivery Network → เก็บไฟล์ static ไว้ใกล้ผู้ใช้ทั่วโลก → ลด latency |
| API Gateway | ประตูหน้าตึก | จุดเข้าเดียวของ API ทำ auth, rate limit, routing ไปหลาย service |
| Cache | ของที่หยิบบ่อยวางใกล้มือ | เก็บผลลัพธ์ที่อ่านบ่อยไว้ในหน่วยความจำเร็ว (เช่น Redis) → ลดภาระ DB |
| Message Queue | ตะกร้าใบสั่งงาน | ที่พักงานระหว่างคนสั่งกับคนทำ → ทำงานช้าแบบ async ได้โดยไม่ให้ผู้ใช้รอ |
| Worker | พนักงานหลังร้าน | process ที่ดึงงานจาก queue มาทำเบื้องหลัง เช่น ส่งอีเมล ย่อรูป |
| Object Storage | ห้องเก็บไฟล์ใหญ่ | ที่เก็บไฟล์ เช่น รูป วิดีโอ PDF (เช่น S3) แยกจาก database |
| WebSocket | สายโทรศัพท์ที่ค้างไว้ | การเชื่อมต่อสองทางที่เปิดค้าง → server ส่งข้อมูลหา client ได้ทันที |
| Replication | สำเนาข้อมูล | ก๊อป DB ไปหลายเครื่อง (primary + replica) → อ่านได้เร็วขึ้น ทนพังขึ้น |
| Sharding / Partitioning | แบ่งข้อมูลเป็นชิ้น | กระจายข้อมูลคนละส่วนไปคนละ DB เมื่อข้อมูลใหญ่เกินเครื่องเดียว |
| Single Point of Failure (SPOF) | จุดตายจุดเดียว | ชิ้นส่วนที่ถ้าพังแล้วทั้งระบบพังตาม |
| Trade-off | ได้อย่างเสียอย่าง | การเลือกที่ได้ข้อดีหนึ่งโดยแลกกับข้อเสียอีกด้าน |
| Bottleneck | คอขวด | จุดที่ช้าที่สุดซึ่งเป็นตัวจำกัดความเร็วของทั้งระบบ |

## 3. Mental Model

### 3.1 System Design = "แก้ปัญหาทีละข้อ" ไม่ใช่ "วาดภาพที่จำมา"

ให้คิดว่าทุกชิ้นส่วนในระบบคือ **ยาแก้โรคหนึ่งโรค**

- Cache แก้โรค "DB อ่านหนักเกินไป"
- Queue แก้โรค "งานช้าทำให้ผู้ใช้ต้องรอ" และ "traffic พุ่งกะทันหัน"
- CDN แก้โรค "ไฟล์ static โหลดช้าเพราะอยู่ไกล"

ถ้าคุณจ่ายยาโดยที่คนไข้ไม่ได้ป่วย ก็คือ **over-engineering** ซึ่งคนสัมภาษณ์หักคะแนน

```
เจออาการ (ปัญหา) → วินิจฉัย (คอขวดตรงไหน) → จ่ายยา (เพิ่มชิ้นส่วน) → บอกผลข้างเคียง (trade-off)
```

ให้มองภาพนี้ว่า "หมอที่ดีจะไม่จ่ายยาทุกตัวในตู้ แต่จ่ายเฉพาะตัวที่ตรงกับอาการ และบอกผลข้างเคียงทุกครั้ง"

### 3.2 วิธีคิด 12 ขั้น

นี่คือกรอบที่ใช้เดินในห้องสัมภาษณ์ทุกโจทย์ ไม่จำเป็นต้องพูดครบทุกขั้นเท่ากัน แต่ **ห้ามข้ามขั้น 1–4** เพราะเป็นฐานของทุกการตัดสินใจหลังจากนั้น

| ขั้น | ชื่อ | คำถามในหัว | ใช้เวลาประมาณ (จาก 45 นาที) |
|---|---|---|---|
| 1 | Requirement | ระบบต้องทำอะไร / ไม่ต้องทำอะไร | 3–5 นาที |
| 2 | Users | ใครใช้ ใช้จากไหน ใช้แบบไหน | 1–2 นาที |
| 3 | Traffic | กี่ request/วินาที อ่านหรือเขียนเยอะกว่ากัน | 3 นาที |
| 4 | Data | เก็บอะไร ขนาดเท่าไร โตปีละเท่าไร | 3 นาที |
| 5 | API | endpoint หลักมีอะไรบ้าง | 3–4 นาที |
| 6 | Database | SQL หรือ NoSQL, schema หลัก | 4–5 นาที |
| 7 | Cache | cache อะไร ที่ไหน หมดอายุเมื่อไร | 3 นาที |
| 8 | Scaling | ถ้า traffic โต 10 เท่า อะไรพังก่อน | 5 นาที |
| 9 | Reliability | ถ้าชิ้นไหนพัง ระบบยังอยู่ไหม | 3 นาที |
| 10 | Security | auth, rate limit, abuse | 2–3 นาที |
| 11 | Monitoring | จะรู้ได้ยังไงว่าระบบป่วย | 2 นาที |
| 12 | Trade-offs | สรุปสิ่งที่เลือกและสิ่งที่ยอมเสีย | 3 นาที |

```
1 Requirement → 2 Users → 3 Traffic → 4 Data
                          ↓
            (รู้ "ขนาดของปัญหา" แล้ว)
                          ↓
5 API → 6 Database → 7 Cache
                          ↓
            (มี design ที่ใช้งานได้แล้ว)
                          ↓
8 Scaling → 9 Reliability → 10 Security → 11 Monitoring
                          ↓
            (design รับของจริงได้แล้ว)
                          ↓
                   12 Trade-offs
```

ให้มองภาพนี้ว่า "สามช่วง: ช่วงแรกทำความเข้าใจโจทย์ ช่วงสองสร้างของที่ใช้ได้ ช่วงสามทำให้ทนทาน แล้วปิดด้วยการสรุปว่ายอมแลกอะไรไป"

### 3.3 คนสัมภาษณ์ให้คะแนนอะไรจริง ๆ

| สิ่งที่ได้คะแนน | สิ่งที่เสียคะแนน |
|---|---|
| ถามข้อกำหนดก่อนวาด | วาดทันทีที่ได้ยินโจทย์ |
| ประเมินตัวเลขคร่าว ๆ แล้วใช้ตัวเลขนั้นตัดสินใจ | ใส่ Kafka / sharding โดยไม่รู้ว่ามี traffic เท่าไร |
| เริ่มจาก design ง่ายที่ใช้งานได้ | เริ่มจาก microservices 12 ตัว |
| บอกว่า "เลือก X เพราะ... แลกกับ..." | บอกว่า "X ดีกว่า Y" แบบไม่มีบริบท |
| ชี้คอขวดของ design ตัวเองได้ | ปกป้อง design ตัวเองว่าไม่มีจุดอ่อน |
| คุยสองทาง เช็คกับคนสัมภาษณ์ระหว่างทาง | พูดคนเดียวยาว 20 นาทีไม่หยุด |

**จำไว้ประโยคเดียว:** คนสัมภาษณ์ไม่ได้ดูว่าคุณ "รู้ architecture ของ Netflix" แต่ดูว่า **ถ้าให้คุณไปออกแบบระบบจริงในทีม คุณจะตัดสินใจอย่างมีเหตุผลไหม**

## 4. ภาพจำ

```
🧠 ภาพจำ:
System Design = ขยายร้านก๋วยเตี๋ยว

วันแรก: ร้านเล็ก เจ้าของทำเองทุกอย่าง (1 server + 1 DB)
      ↓
คนเยอะ: จ้างพ่อครัวเพิ่ม + พนักงานจัดคิว (หลาย server + Load Balancer)
      ↓
ลูกค้าสั่งเมนูเดิมซ้ำ ๆ: ต้มน้ำซุปรอไว้ก่อน (Cache)
      ↓
ลูกค้าต่างจังหวัด: เปิดสาขา / จุดรับของใกล้บ้าน (CDN)
      ↓
ออเดอร์เดลิเวอรี่ล้น: รับใบสั่งใส่ตะกร้า ให้ทีมหลังร้านทยอยทำ (Queue + Worker)
      ↓
ลูกค้าอยากรู้ว่าอาหารถึงไหน: โทรแจ้งสถานะเรื่อย ๆ (WebSocket)
```

ให้มองภาพนี้ว่า "ไม่มีร้านไหนเปิดวันแรกพร้อมสิบสาขา ทุกการขยายเกิดขึ้นเพราะเจอปัญหาจริงก่อนเสมอ"

```
🧠 ภาพจำ:
Trade-off = ผ้าห่มสั้น
ดึงขึ้นคลุมไหล่ → เท้าโผล่
ดึงลงคลุมเท้า → ไหล่หนาว

เร็วขึ้น (Cache) → ข้อมูลอาจเก่า (Stale Data)
```

ให้มองภาพนี้ว่า "ทุกการตัดสินใจคือการเลือกว่าจะยอมให้ส่วนไหนหนาว คนเก่งคือคนที่บอกได้ว่าส่วนไหนหนาวและทำไมยอมรับได้"

```
🧠 ภาพจำ:
Back-of-Envelope = ประเมินว่าต้องใช้รถกี่คันขนของย้ายบ้าน
ไม่ต้องรู้น้ำหนักทุกกล่อง
รู้แค่ว่า "กระบะคันเดียวพอ" หรือ "ต้องใช้รถสิบล้อ"

ตัวเลขคร่าว ๆ → ขนาดของปัญหา → เลือกเครื่องมือให้เหมาะกับขนาด
```

ให้มองภาพนี้ว่า "การคำนวณคร่าว ๆ ไม่ได้มีไว้ให้ได้เลขเป๊ะ แต่มีไว้บอกว่าเราอยู่ในโลกของปัญหาขนาดไหน"

## 5. How It Works

หัวข้อนี้จะสร้างระบบ **ทีละชั้น** แต่ละชั้นบอกว่า "เจอปัญหาอะไร → เพิ่มอะไร → แลกกับอะไร"

### ชั้น 0 — เริ่มจากเล็กที่สุด

```
[USER]
   ↓
[FRONTEND]
   ↓
[BACKEND (1 เครื่อง)]
   ↓
[DATABASE (1 เครื่อง)]
```

ให้มองภาพนี้ว่า "ร้านเปิดใหม่ เจ้าของคนเดียวทำทุกอย่าง ซึ่งเพียงพอสำหรับผู้ใช้หลักร้อยถึงหลักพันคน"

- **เหมาะเมื่อ:** MVP, ผู้ใช้น้อย, ทีมเล็ก
- **ปัญหาที่จะเจอ:** backend เครื่องเดียวคือ SPOF ถ้าพังคือล่มทั้งระบบ และ CPU เต็มเมื่อผู้ใช้เยอะ

### ชั้น 1 — เพิ่ม Load Balancer + หลาย Backend

**ปัญหา:** backend เครื่องเดียวรับไม่ไหว / ถ้าพังระบบล่มทั้งหมด

```
[USER] → [FRONTEND] → [LOAD BALANCER]
                           ├──→ [BACKEND 1]
                           ├──→ [BACKEND 2]   ──→ [DATABASE]
                           └──→ [BACKEND 3]
```

ให้มองภาพนี้ว่า "จ้างพ่อครัวเพิ่มเป็นสามคน มีพนักงานหน้าร้านคอยส่งออเดอร์ให้คนที่ว่าง และถ้าพ่อครัวคนไหนป่วยก็ไม่ส่งงานให้คนนั้น"

- **สิ่งที่ต้องทำก่อน:** backend ต้องเป็น **stateless** คือไม่เก็บ session ใน memory ของเครื่อง (ย้ายไปเก็บที่ Redis หรือใช้ token) ไม่งั้น user login ที่เครื่อง 1 แล้ว request ถัดไปไปตกเครื่อง 2 จะหลุด
- **Health check:** LB ยิงเช็คเป็นระยะ เครื่องไหนไม่ตอบก็เลิกส่ง traffic ไปหา
- **Trade-off:** ระบบซับซ้อนขึ้น deploy ต้องคิดเรื่องหลายเครื่อง และคอขวดจะย้ายไปอยู่ที่ database แทน

### ชั้น 2 — เพิ่ม Cache

**ปัญหา:** database ช้า เพราะทุก request ยิง query เดิมซ้ำ ๆ (เช่น หน้าแรก เมนูร้าน โปรไฟล์)

```
[BACKEND]
   ↓
[CACHE (Redis)] ── เจอ (hit) ──→ ตอบกลับทันที
   ↓ ไม่เจอ (miss)
[DATABASE]
   ↓
เก็บผลลง CACHE แล้วตอบกลับ
```

ให้มองภาพนี้ว่า "ก่อนเดินไปห้องเก็บของหลังร้าน ให้ดูที่ชั้นวางข้างมือก่อน ถ้ามีก็หยิบเลย ถ้าไม่มีค่อยเดินไปเอาแล้ววางไว้บนชั้นเผื่อครั้งหน้า"

- รูปแบบนี้เรียกว่า **Cache-Aside** ซึ่งพบบ่อยที่สุด (รายละเอียดรูปแบบอื่นดู PART 16)
- **Trade-off:** ได้ความเร็ว แลกกับ **ข้อมูลอาจเก่า** ต้องตัดสินใจเรื่อง TTL และการลบ cache เมื่อข้อมูลเปลี่ยน
- **ถามตัวเองทุกครั้ง:** ข้อมูลนี้ถ้าเก่าไป 30 วินาที ผู้ใช้เดือดร้อนไหม (เมนูร้าน → ไม่เป็นไร / ยอดเงินในบัญชี → เป็นเรื่องใหญ่)

### ชั้น 3 — เพิ่ม Database Replica

**ปัญหา:** มี cache แล้วแต่ DB ยังหนัก เพราะ query อ่านหลากหลายจน cache ไม่ครอบคลุม

```
             ┌── เขียน ──→ [PRIMARY DB]
[BACKEND] ───┤                  │ replicate
             └── อ่าน ──→ [REPLICA 1] [REPLICA 2]
```

ให้มองภาพนี้ว่า "มีสมุดบัญชีตัวจริงเล่มเดียวที่แก้ได้ และมีสำเนาหลายเล่มให้คนมาเปิดอ่าน"

- **Trade-off:** replica ตามหลัง primary เล็กน้อย (**replication lag**) ถ้า user เพิ่งแก้โปรไฟล์แล้ว refresh อาจเห็นค่าเก่า วิธีแก้ที่พบบ่อยคืออ่านจาก primary สำหรับข้อมูลที่เพิ่งเขียน
- **ถ้าข้อมูลใหญ่เกินเครื่องเดียว** ค่อยคิดเรื่อง **sharding** ซึ่งซับซ้อนมาก (join ข้าม shard ยาก เปลี่ยน shard key ยาก) เลยควรเป็นทางเลือกหลัง ๆ

### ชั้น 4 — เพิ่ม CDN

**ปัญหา:** ผู้ใช้ไกลจาก server โหลดรูป JS CSS ช้า และ server เปลืองแบนด์วิดท์ไปกับไฟล์ static

```
[USER ที่เชียงใหม่]
   ↓
[CDN EDGE ใกล้ผู้ใช้] ── มีไฟล์ ──→ ส่งกลับทันที
   ↓ ไม่มี
[ORIGIN SERVER / OBJECT STORAGE]
```

ให้มองภาพนี้ว่า "แทนที่ลูกค้าทุกคนต้องมารับของที่โกดังกลางกรุงเทพ ก็ไปวางของขายดีไว้ที่สาขาใกล้บ้านเขา"

- **เหมาะกับ:** ไฟล์ static (JS, CSS, รูป, วิดีโอ) และหน้าเว็บที่ทุกคนเห็นเหมือนกัน
- **Trade-off:** ต้องจัดการ **cache invalidation** เวลา deploy ไฟล์ใหม่ (นิยมใส่ hash ในชื่อไฟล์) และไม่เหมาะกับข้อมูลส่วนตัวของแต่ละคน

### ชั้น 5 — เพิ่ม API Gateway

**ปัญหา:** ระบบแตกเป็นหลาย service (user, order, payment) แล้วทุก service ต้องเขียน auth, rate limit, logging ซ้ำกัน และ frontend ต้องรู้ที่อยู่ทุก service

```
[CLIENT]
   ↓
[API GATEWAY]  ← auth / rate limit / routing / logging
   ├──→ [USER SERVICE]
   ├──→ [ORDER SERVICE]
   └──→ [PAYMENT SERVICE]
```

ให้มองภาพนี้ว่า "ตึกสำนักงานที่มี รปภ. หน้าประตูบานเดียว ตรวจบัตรครั้งเดียวแล้วบอกทางว่าแผนกไหนอยู่ชั้นไหน"

- **ต่างจาก Load Balancer:** LB กระจายงานไปเครื่องที่ทำงาน **เหมือนกัน** ส่วน Gateway ส่งงานไป service ที่ทำงาน **ต่างกัน** ตาม path และทำงานเชิง policy ด้วย
- **Trade-off:** เพิ่ม hop ทำให้ latency เพิ่มนิดหน่อย และตัว gateway เองต้องไม่เป็น SPOF (ต้องรันหลายตัว)
- **ถ้าระบบยังเป็น monolith ตัวเดียว** มักยังไม่ต้องมี gateway แยก

### ชั้น 6 — เพิ่ม Queue + Worker

**ปัญหา:** งานบางอย่างช้า (ส่งอีเมล, ย่อรูป, สร้าง PDF, แจ้งเตือน) ถ้าทำใน request ผู้ใช้ต้องรอ หรือ traffic พุ่งทีเดียวจนระบบล่ม

```
[BACKEND] ── ใส่งานลง ──→ [QUEUE] ──→ [WORKER 1]
    ↓                             ──→ [WORKER 2]
ตอบผู้ใช้ทันที                          ↓
"รับออเดอร์แล้ว"                  ส่งอีเมล / ย่อรูป / แจ้งร้าน
```

ให้มองภาพนี้ว่า "แคชเชียร์รับใบสั่งแล้วเสียบไว้ที่ราว ลูกค้าไปนั่งรอได้เลย ส่วนครัวหลังร้านก็ทยอยหยิบใบสั่งไปทำตามกำลัง"

- **ได้อะไร:** ผู้ใช้ไม่ต้องรอ, รับ traffic พุ่งได้ (queue เป็น buffer), scale worker แยกจาก backend ได้
- **Trade-off:** กลายเป็น **eventual** คือผลลัพธ์ไม่ได้เกิดทันที ต้องคิดเรื่อง retry, งานซ้ำ (worker ต้อง **idempotent**), งานที่ล้มเหลวซ้ำ ๆ (Dead Letter Queue) รายละเอียดทั้งหมดอยู่ใน PART 16

### ชั้น 7 — เพิ่ม Object Storage

**ปัญหา:** ผู้ใช้อัปโหลดรูป วิดีโอ ไฟล์ ถ้าเก็บลง database หรือดิสก์ของ backend จะทำให้ DB บวม backup ช้า และ backend หลายเครื่องมองเห็นไฟล์ไม่ตรงกัน

```
[CLIENT]
   ↓ 1. ขอ URL สำหรับอัปโหลด
[BACKEND] ── ออก pre-signed URL (มีอายุสั้น)
   ↓ 2. อัปโหลดตรงไปที่
[OBJECT STORAGE (S3)]
   ↓ 3. แจ้ง backend ว่าอัปเสร็จ
[DATABASE] ← เก็บแค่ "ที่อยู่ไฟล์" + metadata
```

ให้มองภาพนี้ว่า "database เก็บแค่ป้ายบอกว่าของอยู่ชั้นไหน ส่วนของจริงที่ใหญ่ ๆ เอาไปไว้ในโกดังที่ออกแบบมาเก็บของใหญ่โดยเฉพาะ"

- **Pre-signed URL** → ลิงก์ชั่วคราวที่อนุญาตให้อัปโหลด/ดาวน์โหลดไฟล์เดียว → ไฟล์ใหญ่ไม่ต้องไหลผ่าน backend
- มักใช้คู่กับ **CDN** เพื่อให้ดาวน์โหลดเร็ว และใช้คู่กับ **Queue + Worker** เพื่อย่อรูปหรือแปลงวิดีโอหลังอัปโหลด
- **Trade-off:** ต้องจัดการสิทธิ์การเข้าถึงไฟล์ให้ดี (bucket ที่เปิด public ผิดพลาดเป็นสาเหตุข้อมูลรั่วที่พบบ่อย)

### ชั้น 8 — เพิ่ม WebSocket

**ปัญหา:** ต้องการ real-time เช่น แชท สถานะไรเดอร์ แจ้งเตือนสด ถ้าให้ client ถามซ้ำทุก 2 วินาที (**polling**) จะเปลือง request มากและยังช้ากว่าที่ควร

```
[CLIENT] ⇄ (เปิดค้างไว้) ⇄ [WEBSOCKET SERVER]
                                ↑
                         [PUB/SUB เช่น Redis]
                                ↑
[WORKER / BACKEND] ── "ไรเดอร์รับอาหารแล้ว" ──┘
```

ให้มองภาพนี้ว่า "แทนที่ลูกค้าจะโทรถามร้านทุกสองนาทีว่าอาหารเสร็จหรือยัง ก็เปิดสายค้างไว้แล้วให้ร้านเป็นฝ่ายบอกเองเมื่อมีข่าว"

- **Trade-off:** server ต้องถือ connection ค้างจำนวนมาก การ scale ยากกว่า HTTP ปกติ เพราะ user A อาจต่ออยู่กับเครื่อง 1 แต่ event เกิดที่เครื่อง 3 จึงต้องมี **pub/sub** ตรงกลางคอยกระจาย
- **ทางเลือกที่ง่ายกว่า:** ถ้าต้องการแค่ server → client ทางเดียว อาจใช้ **SSE (Server-Sent Events)** หรือถ้าไม่ต้องเร็วมากก็ใช้ polling ทุก 10–30 วินาทีได้

### ภาพรวมหลังเพิ่มครบทุกชั้น

```
                  [USER]
                     ↓
      ┌──────────────┴──────────────┐
   [CDN] ← static/รูป          [API GATEWAY]
      ↓                              ↓
[OBJECT STORAGE]             [LOAD BALANCER]
                                     ↓
                     [BACKEND x N] ⇄ [WEBSOCKET SERVER]
                       ↓        ↓            ↑
                   [CACHE]   [QUEUE] → [WORKER x N]
                       ↓
             [PRIMARY DB] → [REPLICA DB]
```

ให้มองภาพนี้ว่า "ร้านที่ขยายมาหลายปี ทุกชิ้นที่เห็นมีเรื่องเล่าว่าเพิ่มเข้ามาเพราะเคยเจอปัญหาอะไร" และ **ห้ามวาดภาพนี้ตั้งแต่นาทีแรกของการสัมภาษณ์**

### ตารางสรุป "เพิ่มเมื่อเจอปัญหาอะไร"

| ชิ้นส่วน | เพิ่มเมื่อเจอ | แลกกับ |
|---|---|---|
| Load Balancer + หลาย backend | server เดียวรับไม่ไหว / เป็น SPOF | ต้องทำ stateless, deploy ซับซ้อนขึ้น |
| Cache | DB โดน query อ่านซ้ำ ๆ จนช้า | ข้อมูลอาจเก่า, ต้องจัดการ invalidation |
| DB Replica | อ่านเยอะเกินที่ cache ช่วยได้ | replication lag |
| Sharding | ข้อมูล/การเขียนใหญ่เกินเครื่องเดียว | ความซับซ้อนสูงมาก, join ข้าม shard ยาก |
| CDN | ไฟล์ static โหลดช้า / ผู้ใช้กระจายหลายพื้นที่ | cache invalidation ตอน deploy |
| API Gateway | มีหลาย service ต้องทำ auth/rate limit ซ้ำ | hop เพิ่ม, ต้องทำให้ไม่เป็น SPOF |
| Queue + Worker | งานช้าทำให้ user รอ / traffic พุ่ง | eventual, ต้องจัดการ retry และงานซ้ำ |
| Object Storage | ต้องเก็บไฟล์ใหญ่ | ต้องคุมสิทธิ์การเข้าถึงไฟล์ |
| WebSocket | ต้องการ real-time สองทาง | connection ค้างเยอะ, scale ยากขึ้น |

## 6. Example

### โจทย์: "ออกแบบ URL Shortener (แบบ bit.ly)"

ด้านล่างคือการเดินครบ 12 ขั้น โดยแสดงให้เห็นว่า **พูดอะไรจริง ๆ ในห้อง** (ข้อความใน "..." คือสิ่งที่พูดออกมา)

#### ขั้นที่ 1 — Requirement

อย่าเพิ่งวาดอะไร ให้ **ถามกลับก่อน** เช่นเปิดด้วย "ก่อนจะเริ่มวาด ขอถามให้ชัดก่อนนะครับ ว่าเราต้องทำฟีเจอร์ไหนบ้าง" แล้วตามด้วยคำถามเหล่านี้

| คำถาม | ทำไมต้องถาม |
|---|---|
| "ผู้ใช้ตั้งชื่อลิงก์เอง (custom alias) ได้ไหมครับ" | เปลี่ยนวิธีสร้าง short code และต้องเช็คชื่อซ้ำ |
| "ลิงก์มีวันหมดอายุไหม" | กระทบการเก็บข้อมูลและการลบ |
| "ต้องมี analytics เช่นนับจำนวนคลิกไหม" | ถ้ามี จะมีการเขียนทุกครั้งที่คลิก ซึ่งเปลี่ยนภาระของระบบมาก |
| "ต้อง login ก่อนสร้างลิงก์ไหม" | กระทบ auth และการกัน spam |
| "แก้ไขหรือลบลิงก์หลังสร้างได้ไหม" | กระทบการ cache (ถ้าแก้ได้ต้องลบ cache) |

สมมติคนสัมภาษณ์ตอบว่า: ย่อลิงก์ได้, redirect ได้, custom alias เป็น optional, มีวันหมดอายุ, นับคลิกแบบคร่าว ๆ พอ แล้ว **สรุปกลับ** เพื่อให้ตรงกัน

> "สรุปนะครับ Functional: 1) ส่ง URL ยาวมาได้ short URL กลับไป 2) เปิด short URL แล้ว redirect ไป URL เดิม 3) นับคลิกคร่าว ๆ
> Non-functional: redirect ต้องเร็วมาก เพราะคนกดลิงก์ไม่อยากรอ, ระบบต้องไม่ล่มง่ายเพราะถ้าล่มลิงก์ทั่วอินเทอร์เน็ตจะเสียหมด, short code ต้องเดายาก
> Out of scope: ระบบจัดการแคมเปญ dashboard สวย ๆ ขอไม่ทำในรอบนี้นะครับ"

**จุดที่ได้คะแนน:** การบอก out of scope แสดงว่าคุณคุม scope เป็น

#### ขั้นที่ 2 — Users

> "ผู้ใช้มีสองกลุ่มครับ กลุ่มแรกคือคนสร้างลิงก์ ซึ่งมีน้อยกว่า กลุ่มสองคือคนกดลิงก์ ซึ่งมีมากกว่าหลายสิบเท่า และส่วนใหญ่ไม่ได้ login เลย เข้ามาจาก social media ผ่านมือถือ"

สิ่งที่ได้จากขั้นนี้: **ระบบนี้อ่าน (redirect) เยอะกว่าเขียน (สร้างลิงก์) มาก** ซึ่งจะกำหนดการออกแบบทั้งหมด

#### ขั้นที่ 3 — Traffic (back-of-envelope)

เปิดด้วย "ขอสมมติตัวเลขนะครับ ถ้าผิดช่วยแก้ได้เลย" แล้วคำนวณให้เห็น **ตัวช่วยจำ:** 1 วัน = 86,400 วินาที **ปัดเป็น ≈ 100,000 (10⁵) วินาที** ได้เลย คิดในหัวง่ายและยังอยู่ในขนาดที่ถูกต้อง

```
สมมติ DAU (คนสร้างลิงก์)      = 1,000,000 คน/วัน
แต่ละคนสร้างเฉลี่ย             = 1 ลิงก์/วัน
                ↓
ลิงก์ใหม่ต่อวัน                = 1,000,000 ลิงก์
                ↓ ÷ 100,000 วินาที
Write QPS เฉลี่ย               ≈ 10 ครั้ง/วินาที
                ↓ อัตราส่วน อ่าน:เขียน = 100:1
Read QPS เฉลี่ย                ≈ 1,000 ครั้ง/วินาที
                ↓ × 3 (peak)
Read QPS ช่วงพีค               ≈ 3,000 ครั้ง/วินาที
```

ให้มองภาพนี้ว่า "เริ่มจากจำนวนคนต่อวัน หารด้วยจำนวนวินาทีในวัน ก็ได้ภาระต่อวินาที แล้วคูณเผื่อช่วงคนแน่น"

> "ตัวเลขนี้บอกผมว่า การเขียน 10 ครั้งต่อวินาที database ตัวเดียวรับสบาย แต่การอ่าน 3,000 ครั้งต่อวินาทีช่วงพีคเป็นจุดที่ต้องใส่ใจ ผมเลยจะโฟกัสที่ฝั่ง read path ครับ"

**จุดที่ได้คะแนน:** ไม่ได้คำนวณแล้วทิ้ง แต่ **เอาตัวเลขไปตัดสินใจต่อ**

#### ขั้นที่ 4 — Data

```
ลิงก์ 1 แถวเก็บ: short_code, long_url, user_id, created_at, expires_at
ขนาดโดยประมาณ                 ≈ 500 bytes/แถว (URL ยาวเผื่อไว้)
                ↓
ลิงก์ใหม่ต่อปี = 1,000,000 × 365 ≈ 365 ล้านแถว (ปัด ≈ 400 ล้าน)
                ↓ × 500 bytes
ข้อมูลต่อปี                    ≈ 200 GB/ปี
                ↓ × 5 ปี
ข้อมูล 5 ปี                    ≈ 1 TB
```

ให้มองภาพนี้ว่า "จำนวนแถวต่อวัน คูณวันในปี คูณขนาดต่อแถว ก็รู้ว่าต้องเตรียมที่เก็บเท่าไร"

> "ปีละราว 200 GB ห้าปีราว 1 TB ซึ่ง database ตัวเดียวที่มี replica ยังรับได้ในช่วงแรก ยังไม่จำเป็นต้อง shard ตั้งแต่วันแรกครับ แต่ผมจะเลือก key ให้ shard ได้ง่ายถ้าวันหนึ่งต้องทำ"

**ความยาว short code:** ใช้ตัวอักษร **base62** (a–z, A–Z, 0–9 = 62 ตัว)

| ความยาว | จำนวนแบบที่เป็นไปได้ (ประมาณ) | พอไหม |
|---|---|---|
| 6 ตัว | 62⁶ ≈ 5.7 หมื่นล้าน | พอสำหรับหลายสิบปีที่ 400 ล้าน/ปี |
| 7 ตัว | 62⁷ ≈ 3.5 ล้านล้าน | เหลือเฟือ และเดายากขึ้น |

> "ผมเลือก 7 ตัวครับ เผื่อโตและทำให้เดาลิงก์คนอื่นยากขึ้น"

| สูตรที่ต้องจำ | วิธีคิด |
|---|---|
| QPS เฉลี่ย | (DAU × action ต่อคนต่อวัน) ÷ 100,000 |
| QPS ช่วงพีค | QPS เฉลี่ย × 2 ถึง 5 |
| ข้อมูลต่อปี | จำนวนแถวต่อวัน × 365 × ขนาดต่อแถว |
| หน่วยจำง่าย | 1 KB = 10³ bytes, 1 MB = 10⁶, 1 GB = 10⁹, 1 TB = 10¹² |

#### ขั้นที่ 5 — API

| Method | Path | ทำอะไร | ตอบกลับ |
|---|---|---|---|
| POST | `/api/links` | body: long_url, alias (optional), expires_at | 201 + short_url |
| GET | `/{code}` | redirect ไป URL เดิม | 301 หรือ 302 + header Location |

> "ตรง redirect มี trade-off ครับ ถ้าใช้ **301 (Permanent)** browser จะจำไว้แล้วไม่กลับมาถามเราอีก ประหยัด server แต่เราจะนับคลิกไม่ได้ ถ้าใช้ **302 (Temporary)** ทุกคลิกจะผ่านเรา นับคลิกได้แต่ภาระมากกว่า เนื่องจากโจทย์ต้องนับคลิก ผมเลือก 302 ครับ"

**จุดที่ได้คะแนน:** เรื่องเล็กแค่ status code ก็ยังเชื่อมกลับไปหา requirement ได้

#### ขั้นที่ 6 — Database

> "ข้อมูลเป็นแบบ key-value ชัดเจน คือเอา short_code ไปหา long_url ไม่มี join ซับซ้อน"

| ทางเลือก | เหมาะเมื่อ | แลกกับ |
|---|---|---|
| PostgreSQL / MySQL | ทีมคุ้นเคย, ต้องการ unique constraint ป้องกัน code ซ้ำ, ข้อมูลระดับ TB ต้น ๆ | ถ้าโตมากต้อง shard เอง |
| Key-Value / NoSQL (เช่น DynamoDB, Cassandra) | ข้อมูลโตมหาศาล, ต้องการ scale การเขียนกระจายหลายเครื่อง | query ยืดหยุ่นน้อยกว่า, ทีมต้องเรียนรู้ |

> "ด้วยขนาด 200 GB ต่อปี ผมเริ่มที่ PostgreSQL ก่อนครับ เพราะ unique index บน short_code ช่วยกันชนได้ง่าย และทีมส่วนใหญ่ใช้เป็น ถ้าวันหนึ่งโตจนเครื่องเดียวไม่พอ short_code เป็น shard key ที่ดีเพราะกระจายตัวสม่ำเสมอ"

**วิธีสร้าง short code (trade-off ที่คนสัมภาษณ์ชอบถาม)**

| วิธี | ทำงานอย่างไร | ข้อดี | ข้อเสีย |
|---|---|---|---|
| Hash URL แล้วตัด 7 ตัว | hash(long_url) → base62 → ตัด | URL เดิมได้ code เดิม | ชนกันได้ ต้องเช็คและสุ่มใหม่ |
| Counter + base62 | เลขลำดับ 1, 2, 3 → แปลงเป็น base62 | ไม่ชนแน่นอน | เดาลำดับได้, counter กลางเป็นจุดคอขวด |
| สุ่ม 7 ตัว + เช็คซ้ำ | random → insert ถ้าชนก็สุ่มใหม่ | เดายาก, ง่าย | ต้องพึ่ง unique constraint ใน DB |

> "ผมเลือกสุ่มแล้วให้ unique constraint ใน DB เป็นตัวจับชนครับ เพราะที่ 7 ตัว โอกาสชนต่ำมาก และลิงก์เดายาก ถ้าต้องการประสิทธิภาพสูงขึ้นค่อยเปลี่ยนเป็นให้แต่ละ server จองช่วงเลข counter ไว้ล่วงหน้า"

#### ขั้นที่ 7 — Cache

> "เพราะอ่านมากกว่าเขียน 100 เท่า และลิงก์ส่วนน้อยที่ viral มักถูกกดเป็นส่วนใหญ่ ผมจะใส่ Redis ไว้หน้า DB ด้วย cache-aside ครับ"

```
GET /aB3xK9p → [BACKEND] → [REDIS] ── hit ──→ 302 redirect
                        ↓ miss
                   [POSTGRES] → เก็บลง REDIS (TTL 24 ชม.) → 302 redirect
```

ให้มองภาพนี้ว่า "ลิงก์ที่คนกดบ่อยวางไว้บนโต๊ะ ลิงก์ที่นาน ๆ ถูกกดทีค่อยไปค้นในตู้"

> "ถ้าลบหรือแก้ลิงก์ ผมจะลบ key ใน Redis ด้วย และตั้ง TTL เผื่อกรณีลบไม่สำเร็จ ข้อมูลจะได้ไม่เก่าค้างตลอดไปครับ"

**ประมาณขนาด cache:** ถ้าเก็บลิงก์ที่ถูกกดบ่อยสัก 20% ของลิงก์ที่ใช้ในแต่ละวัน ขนาดระดับไม่กี่ GB ก็อยู่ใน RAM ของ Redis ได้สบาย

#### ขั้นที่ 8 — Scaling

> "ถ้า traffic โต 10 เท่า ผมไล่ดูว่าอะไรพังก่อนครับ"

| ชั้น | วิธี scale | หมายเหตุ |
|---|---|---|
| Backend | stateless → เพิ่มเครื่องหลัง Load Balancer | ง่ายที่สุด |
| Cache | Redis cluster / เพิ่ม node | รับ read path ส่วนใหญ่ |
| DB อ่าน | เพิ่ม read replica | ยอมรับ lag ได้ เพราะลิงก์ไม่ค่อยเปลี่ยน |
| DB เขียน | shard ด้วย short_code | ทำเมื่อจำเป็นจริงเท่านั้น |
| Click analytics | ไม่เขียน DB ตรงทุกคลิก ส่ง event เข้า **Queue** แล้วให้ **Worker** รวมยอดเป็นชุด | ยอดคลิกช้าไปไม่กี่วินาทีถึงนาที ยอมรับได้ตาม requirement |

```
GET /{code} → [BACKEND] ── redirect ทันที ──→ ผู้ใช้
                   ↓ (ไม่รอ)
          [QUEUE: click events] → [WORKER] ── รวมยอดทุก 1 นาที ──→ [ANALYTICS DB]
```

ให้มองภาพนี้ว่า "พนักงานเปิดประตูให้ลูกค้าเข้าไปก่อน แล้วค่อยหยอดบัตรนับจำนวนลงกล่อง ไว้ให้คนหลังร้านมานับทีหลัง"

> "การแยกนับคลิกออกไปทำแบบ async ทำให้ redirect เร็วเท่าเดิมแม้ traffic จะพุ่งครับ"

#### ขั้นที่ 9 — Reliability

> "ผมไล่ดูทีละชิ้นว่า ถ้าพังแล้วเกิดอะไรขึ้นครับ"

| ถ้าชิ้นนี้พัง | ผลกระทบ | การรับมือ |
|---|---|---|
| Backend 1 เครื่อง | ไม่กระทบ | LB health check ตัดเครื่องออก |
| Redis | ช้าลง ทุก request ตกไปที่ DB | DB ต้องรับไหวชั่วคราว, ใช้ Redis แบบมี replica |
| Primary DB | สร้างลิงก์ใหม่ไม่ได้ | failover ไป replica, ส่วน redirect ยังอ่านจาก replica/cache ได้ |
| Queue | นับคลิกไม่ได้ชั่วคราว | redirect ยังทำงาน (ออกแบบให้ analytics พังได้โดยไม่ลากระบบหลัก) |

> "หลักที่ผมยึดคือ **redirect ต้องรอดก่อนเสมอ** ฟีเจอร์รองอย่าง analytics พังได้ แต่ห้ามทำให้ลิงก์ใช้ไม่ได้ครับ"

#### ขั้นที่ 10 — Security

> "ระบบนี้เป็นเป้าของ spam และ phishing ครับ" (รายละเอียด auth / security ดู PART 7, rate limit ดู PART 16)

| ความเสี่ยง | การรับมือ |
|---|---|
| bot สร้างลิงก์ถล่ม | rate limit ต่อ IP / ต่อ user บน endpoint สร้างลิงก์ |
| ลิงก์ไปเว็บหลอกลวง | ตรวจ URL กับรายการเว็บอันตรายตอนสร้าง, มีช่องทาง report |
| ไล่เดา code เพื่อดูลิงก์คนอื่น | code สุ่ม 7 ตัว, rate limit ฝั่ง redirect ที่ตอบ 404 ถี่ ๆ |
| input อันตราย | validate ว่าเป็น URL จริง scheme http/https เท่านั้น |

#### ขั้นที่ 11 — Monitoring

> "ผมจะวัดสิ่งที่ผู้ใช้รู้สึกได้ก่อนครับ"

| สิ่งที่วัด | ทำไม |
|---|---|
| p95 / p99 latency ของ redirect | redirect ช้าผู้ใช้รู้สึกทันที |
| error rate (5xx) และอัตรา 404 | 404 พุ่งอาจแปลว่ามีคนไล่เดา code หรือข้อมูลหาย |
| cache hit ratio | ถ้า hit ตก DB จะโดนหนักตาม |
| queue depth ของ click events | ถ้าค้างเยอะแปลว่า worker ตามไม่ทัน |

> "ตั้ง alert ที่อาการ เช่น p99 redirect เกินเป้า หรือ error rate เกินเกณฑ์ ไม่ใช่ alert ทุกครั้งที่ CPU สูงครับ" (รายละเอียดดู PART 23)

#### ขั้นที่ 12 — Trade-offs

> "สรุปสิ่งที่ผมเลือกและสิ่งที่ยอมแลกนะครับ"

| เลือก | ได้ | ยอมแลก |
|---|---|---|
| 302 แทน 301 | นับคลิกได้ | ภาระ server มากขึ้น |
| PostgreSQL แทน NoSQL | ง่าย, ทีมคุ้น, unique constraint | ต้อง shard เองถ้าโตมาก |
| Cache-aside + TTL | redirect เร็ว, DB เบา | ลิงก์ที่เพิ่งแก้อาจเก่าชั่วครู่ |
| นับคลิกผ่าน Queue | redirect ไม่ช้าลง | ยอดคลิกไม่ real-time |
| สุ่ม code 7 ตัว | เดายาก, ง่าย | ต้องเช็คชนผ่าน DB |

> "ถ้ามีเวลาเพิ่ม ผมอยากคุยเรื่อง multi-region เพื่อให้ redirect เร็วทั่วโลก หรือเรื่องการลบลิงก์หมดอายุแบบเป็น batch ครับ อยากให้เจาะส่วนไหนเพิ่มไหมครับ"

**จุดที่ได้คะแนน:** ปิดท้ายด้วยการ **ชวนคนสัมภาษณ์เลือกเจาะต่อ** แสดงว่าคุณรู้ว่ายังมีอะไรให้ปรับได้อีก

### ภาพ design สุดท้ายของ URL Shortener

```
[USER กดลิงก์] → [LOAD BALANCER] → [BACKEND x N (stateless)]
                                       ├──→ [REDIS] ── miss ──→ [POSTGRES PRIMARY] → [REPLICA]
                                       └──→ [QUEUE: clicks] → [WORKER] → [ANALYTICS DB]
```

ให้มองภาพนี้ว่า "ถนนสายหลักคือ redirect ที่ต้องเร็วและไม่ล่ม ส่วนการนับคลิกแยกไปอยู่ถนนเส้นรองที่ช้าได้"

สังเกตว่า design นี้ **ไม่มี** CDN, API Gateway, WebSocket, Object Storage เพราะโจทย์ไม่มีปัญหาที่ต้องใช้มัน และการพูดว่า **"ผมยังไม่ใส่ X เพราะยังไม่มีปัญหา Y"** ก็เป็นอีกจุดที่ได้คะแนน

### ตัวอย่างเสริม: ถ้าโจทย์เป็น "ระบบสั่งอาหาร" จะต่างอย่างไร

| ขั้น | ต่างจาก URL Shortener อย่างไร |
|---|---|
| Requirement | มีหลายฝ่าย: ลูกค้า ร้าน ไรเดอร์ ต้องถามว่ามีระบบจ่ายเงินไหม ติดตามไรเดอร์สดไหม |
| Traffic | พีคชัดมากช่วงเที่ยงและเย็น (peak อาจสูงกว่าค่าเฉลี่ยหลายเท่า) |
| Database | ออเดอร์และการจ่ายเงินต้องการ **transaction** และความถูกต้องสูง → relational DB เหมาะ |
| Cache | เมนูร้าน cache ได้ แต่ **สถานะออเดอร์และยอดเงินไม่ควรพึ่ง cache** |
| Queue + Worker | แจ้งร้าน, แจ้งไรเดอร์, ส่งใบเสร็จ ทำแบบ async ได้ |
| WebSocket | ติดตามตำแหน่งไรเดอร์และสถานะออเดอร์แบบสด |
| Object Storage + CDN | รูปเมนูและรูปร้าน |
| Reliability | การจ่ายเงินต้อง **idempotent** กดซ้ำต้องไม่ตัดเงินสองครั้ง (ดู PART 16) |

**บทเรียน:** กรอบ 12 ขั้นเหมือนเดิม แต่ **คำตอบในแต่ละขั้นเปลี่ยนตาม requirement** นี่คือเหตุผลที่การจำ architecture สำเร็จรูปใช้ไม่ได้

## 7. Compare

### 7.1 Horizontal vs Vertical Scaling

| ประเด็น | Vertical (Scale Up) | Horizontal (Scale Out) |
|---|---|---|
| ทำอะไร | เพิ่ม CPU/RAM เครื่องเดิม | เพิ่มจำนวนเครื่อง |
| ความง่าย | ง่าย ไม่ต้องแก้ code | ต้องทำ stateless + มี LB |
| เพดาน | มีเพดานของ hardware | ขยายได้อีกมาก |
| SPOF | ยังเป็นเครื่องเดียว | ทนเครื่องพังได้ |
| เหมาะเมื่อ | ระยะแรก, database ที่ scale out ยาก | backend ที่ stateless, traffic โตต่อเนื่อง |

### 7.2 Load Balancer vs API Gateway vs Reverse Proxy

| ประเด็น | Load Balancer | API Gateway | Reverse Proxy |
|---|---|---|---|
| หน้าที่หลัก | กระจายงานไปเครื่องที่ทำงานเหมือนกัน | ประตูเดียวของหลาย service + policy | ยืนหน้า server รับ request แทน |
| ทำ auth / rate limit | ปกติไม่ทำ | ทำ | ทำได้บางส่วน |
| ตัวอย่างการใช้ | backend 3 เครื่องที่เหมือนกัน | user / order / payment service | Nginx หน้าแอป, ทำ TLS, serve static |
| หมายเหตุ | ในทางปฏิบัติเครื่องมือเดียวอาจทำได้หลายบทบาท | | |

### 7.3 SQL vs NoSQL (ในมุม System Design — ลงลึกดู PART 8)

| ประเด็น | SQL (PostgreSQL, MySQL) | NoSQL (MongoDB, DynamoDB, Cassandra) |
|---|---|---|
| เหมาะเมื่อ | ข้อมูลมีความสัมพันธ์, ต้องการ transaction | ข้อมูลรูปแบบยืดหยุ่น, scale การเขียนสูงมาก |
| Consistency | เข้มงวดเป็นค่าเริ่มต้น | หลายตัวเลือก eventual ได้เพื่อแลกความเร็ว |
| Scale | ขยายการอ่านด้วย replica, การเขียนต้อง shard เอง | หลายตัวออกแบบมาให้กระจายตั้งแต่แรก |
| ตัวอย่างโจทย์ | การจ่ายเงิน, ออเดอร์, บัญชีผู้ใช้ | feed, log event, key-value ขนาดมหาศาล |

### 7.4 Polling vs Long Polling vs SSE vs WebSocket

| ประเด็น | Polling | Long Polling | SSE | WebSocket |
|---|---|---|---|---|
| ทิศทาง | client ถามเป็นระยะ | client ถามแล้ว server ค้างไว้จนมีข่าว | server → client | สองทาง |
| ความสด | ขึ้นกับรอบที่ถาม | ใกล้ real-time | real-time | real-time |
| ภาระ server | request เยอะ | ปานกลาง | connection ค้าง | connection ค้าง |
| เหมาะเมื่อ | อัปเดตไม่บ่อย เช่น dashboard ทุก 30 วินาที | ระบบเก่าที่ใช้ WebSocket ไม่ได้ | แจ้งเตือน, ราคาหุ้น, สถานะงาน | แชท, เกม, ติดตามไรเดอร์ |

### 7.5 Sync vs Async (Queue)

| ประเด็น | Sync (ทำใน request) | Async (ผ่าน Queue) |
|---|---|---|
| ผู้ใช้รอ | รอจนเสร็จ | ได้คำตอบทันที ผลตามมาทีหลัง |
| ความง่าย | ง่าย debug ง่าย | ซับซ้อน ต้องคิดเรื่อง retry และงานซ้ำ |
| รับ traffic พุ่ง | พังง่าย | queue ช่วยพักงานไว้ |
| เหมาะเมื่อ | ผู้ใช้ต้องการผลทันที เช่น login, ดูยอดเงิน | งานช้าหรือไม่ต้องทันที เช่น ส่งอีเมล, ย่อรูป |

### 7.6 Consistency vs Availability

| เลือก | ความหมาย | ตัวอย่างที่เหมาะ |
|---|---|---|
| เน้น Consistency | ยอมให้ระบบปฏิเสธ/ช้าลงดีกว่าให้ข้อมูลผิด | ยอดเงิน, สต็อกสินค้าชิ้นสุดท้าย, การจองที่นั่ง |
| เน้น Availability | ยอมให้ข้อมูลเก่าชั่วครู่ดีกว่าให้ระบบใช้ไม่ได้ | จำนวนไลก์, feed, จำนวนคลิกของ URL shortener |

ประเด็นนี้คือแก่นของ **CAP theorem** ที่คนสัมภาษณ์ชอบถาม: เมื่อ network ระหว่างเครื่องขาดกัน ระบบต้องเลือกว่าจะยอมเสีย consistency หรือ availability

## 8. Common Mistakes

| ความเข้าใจผิด | ความจริง |
|---|---|
| "วาดกล่องเยอะ ๆ ดูเก่ง" | กล่องที่ไม่มีเหตุผลรองรับคือ over-engineering คนสัมภาษณ์จะถาม "ใส่ทำไม" ทุกกล่อง |
| "เริ่มวาดทันทีเพื่อประหยัดเวลา" | ถ้า requirement ผิดตั้งแต่ต้น ทุกอย่างหลังจากนั้นผิดหมด การถาม 3–5 นาทีแรกคือการลงทุนที่คุ้มที่สุด |
| "ต้องใช้ microservices เสมอ" | monolith ที่แบ่งโมดูลดีเหมาะกับทีมเล็กและระยะแรก microservices ดีกว่าเมื่อทีมใหญ่และต้อง deploy แยกกันจริง (ดู PART 17) |
| "ใส่ cache แล้วเร็วขึ้นเสมอ" | cache ข้อมูลที่แทบไม่มีคนอ่านซ้ำไม่ช่วย และ cache ข้อมูลที่ต้องถูกต้องเสมอ (ยอดเงิน) อาจสร้างบั๊ก |
| "Kafka / sharding ทำให้ระบบดูระดับ senior" | senior จริงจะถามก่อนว่า traffic เท่าไร ถ้า 10 writes/วินาที การ shard คือการสร้างปัญหาโดยไม่จำเป็น |
| "คำนวณ back-of-envelope ต้องแม่น" | ต้องการแค่ขนาด (หลักสิบ หลักพัน หลักล้าน) ปัด 86,400 เป็น 100,000 ได้เลย |
| "คำนวณแล้วจบ" | ตัวเลขต้องถูกใช้ตัดสินใจ เช่น "3,000 reads/วินาที จึงใส่ cache" ไม่งั้นคำนวณไปก็ไม่ได้คะแนน |
| "Design ของผมไม่มีจุดอ่อน" | ทุก design มีจุดอ่อน การชี้จุดอ่อนของตัวเองได้คือสัญญาณของ senior |
| "Load Balancer ตัวเดียวก็พอ" | LB ตัวเดียวคือ SPOF ใหม่ ในระบบจริงต้องมีสำรอง (managed LB ของ cloud มักจัดการให้) |
| "ลืม stateless" | เพิ่ม backend หลายเครื่องแต่ยังเก็บ session ใน memory ทำให้ user หลุดแบบสุ่ม |
| "เก็บรูปลง database" | ทำให้ DB บวมและ backup ช้า ควรเก็บใน object storage แล้วเก็บแค่ URL ใน DB |
| "พูดคนเดียวไม่หยุด" | รอบนี้คือการคุย ควรหยุดเช็คเป็นระยะว่า "ทิศทางนี้โอเคไหม อยากให้เจาะส่วนไหน" |
| "จำ design ของ Twitter / Uber มาตอบ" | ถ้า requirement ต่าง design ที่จำมาก็ผิด คนสัมภาษณ์มักเปลี่ยนเงื่อนไขกลางทางเพื่อทดสอบเรื่องนี้ |

## 9. Debugging

System Design ไม่ได้ใช้แค่ในห้องสัมภาษณ์ เมื่อระบบจริงช้าหรือล่ม วิธีคิดแบบเดียวกันจะช่วยหาคอขวด

### ไล่ตามเส้นทางของ request จากหน้าไปหลัง

```
[USER บอกว่าช้า]
      ↓
1. ช้าทุกคน หรือบางคน / บางพื้นที่?     → บางพื้นที่: ดู CDN, DNS, network
      ↓
2. ช้าทุก endpoint หรือบาง endpoint?    → บาง endpoint: ดู query / service นั้น
      ↓
3. Load Balancer: เครื่องไหนถูกตัดออก?   → health check ล้ม, เครื่องเหลือน้อย
      ↓
4. Backend: CPU / memory / thread เต็ม?  → scale out หรือหาโค้ดที่ช้า
      ↓
5. Cache: hit ratio ตกไหม?               → cache ล่ม / key หมดอายุพร้อมกัน
      ↓
6. Database: slow query, connection เต็ม, replication lag?
      ↓
7. Queue: งานค้างสะสมไหม?                → worker ตามไม่ทัน / worker พัง
```

ให้มองภาพนี้ว่า "เดินตามทางที่ request เดินจริง ทีละด่าน จนกว่าจะเจอด่านที่รถติด"

### ตารางอาการ → จุดที่ควรดูก่อน

| อาการ | สงสัยอะไรก่อน | ดูอะไร |
|---|---|---|
| ช้าเฉพาะช่วงพีค | ขาด capacity | CPU, จำนวนเครื่อง, connection pool ของ DB |
| ช้าหลัง deploy | โค้ดหรือ query ใหม่ | เทียบ latency ก่อน/หลัง deploy, slow query log |
| DB หนักขึ้นกะทันหัน | cache ล่มหรือ hit ratio ตก | cache hit ratio, key ที่หมดอายุพร้อมกัน (**cache stampede**) |
| user เห็นข้อมูลเก่าหลังแก้ | replication lag หรือ cache ไม่ถูกลบ | lag ของ replica, logic ลบ cache |
| user หลุด login แบบสุ่ม | backend ไม่ stateless | session เก็บใน memory ของเครื่องหรือไม่ |
| งาน async ไม่เกิด | worker พังหรือ queue ค้าง | queue depth, dead letter queue, log ของ worker |
| real-time ไม่อัปเดตบางคน | WebSocket ต่อคนละเครื่องแต่ไม่มี pub/sub | การกระจาย event ข้ามเครื่อง |
| ระบบล่มทั้งหมด | SPOF | ชิ้นไหนที่มีตัวเดียว (DB primary, LB, cache ตัวเดียว) |

เครื่องมือที่ใช้ไล่ (logs, metrics, traces, dashboard) อธิบายครบใน **PART 23 (Observability)** และขั้นตอน debug ทั่วไปดู **PART 20 (Debugging)**

### คำถามที่ควรถามตัวเองเมื่อ design ใหม่ (debug ล่วงหน้า)

- ชิ้นไหนมีตัวเดียว ถ้าพังแล้วเกิดอะไรขึ้น
- ถ้า traffic โต 10 เท่า อะไรพังก่อน
- ถ้า cache หายหมด DB รับไหวไหม
- ถ้า worker ตาย งานหายไหม หรือรออยู่ใน queue
- เราจะ **รู้ได้ยังไง** ว่าแต่ละข้อข้างบนกำลังเกิดขึ้น

## 11. Answer Like a Developer

### โครงการตอบโจทย์ System Design (ใช้ได้กับทุกโจทย์)

```
1. ถามกลับ   → "ขอเช็ค requirement ก่อนนะครับ..."
      ↓
2. สรุป      → "สรุปคือ ต้องทำ A, B, C / ไม่ทำ D"
      ↓
3. ตัวเลข    → "สมมติ DAU เท่านี้ จะได้ QPS ประมาณ... ข้อมูลปีละ..."
      ↓
4. ตีความ    → "ตัวเลขนี้บอกว่าระบบ read-heavy ผมจะโฟกัสที่..."
      ↓
5. Design ง่าย → วาด User → LB → Backend → DB ก่อน
      ↓
6. เพิ่มทีละชั้น → "ตรงนี้จะเป็นคอขวดเพราะ... ผมจึงเพิ่ม..."
      ↓
7. จุดพัง     → "ถ้าชิ้นนี้พัง จะเกิด... รับมือโดย..."
      ↓
8. สรุป trade-off + ชวนเจาะต่อ
```

ให้มองภาพนี้ว่า "เข้าใจโจทย์ → วัดขนาด → สร้างของง่าย → เพิ่มเมื่อมีเหตุผล → เตรียมรับมือเมื่อพัง → สรุปสิ่งที่ยอมแลก"

### ประโยคเชื่อม (ไม่ใช่ประโยคท่องจำ แต่เป็นรูปแบบความคิด)

| สถานการณ์ | รูปแบบที่ใช้ |
|---|---|
| เริ่มต้น | "ก่อนวาด ขอถามให้ชัดก่อนว่า..." |
| สมมติตัวเลข | "ขอสมมติว่า... ถ้าไม่ใช่ช่วยแก้ได้เลยครับ" |
| เพิ่มชิ้นส่วน | "ตรงนี้จะเป็นคอขวดเมื่อ... ผมจึงเพิ่ม X ซึ่งแลกกับ Y" |
| ไม่เพิ่มชิ้นส่วน | "ผมยังไม่ใส่ X เพราะตอนนี้ยังไม่มีปัญหา Y ถ้าโตถึงระดับ Z ค่อยใส่" |
| เจอคำถามที่ไม่แน่ใจ | "ผมไม่แน่ใจรายละเอียดของเครื่องมือนี้ แต่หลักการที่ผมจะใช้คือ..." |
| คนสัมภาษณ์เปลี่ยนเงื่อนไข | "ถ้าเงื่อนไขเปลี่ยนเป็นแบบนั้น ส่วนที่ต้องเปลี่ยนคือ... เพราะ..." |
| เช็คทิศทาง | "ถึงตรงนี้ทิศทางโอเคไหมครับ อยากให้เจาะส่วนไหนเพิ่ม" |
| ปิดท้าย | "สิ่งที่ผมเลือกคือ... ยอมแลกกับ... ถ้ามีเวลาเพิ่มจะปรับ..." |

### ตัวอย่างคำตอบ: "ถ้า database ช้า จะทำอย่างไร"

**คำตอบที่เสียคะแนน:** "ใส่ Redis ครับ แล้วก็ shard database" ส่วน **คำตอบแบบ developer** มีโครงดังนี้

1. **หาสาเหตุก่อน** — ช้าที่อ่านหรือเขียน, query ไหนช้า, ช้าตลอดหรือช่วงพีค
2. **แก้ที่ถูกที่สุดก่อน** — index, แก้ query, แก้ N+1, ปรับ connection pool
3. **ถ้า read หนัก** — cache สำหรับข้อมูลที่เก่าได้, read replica สำหรับ query หลากหลาย
4. **ถ้า write หนัก** — แยกงานที่ไม่ต้องทันทีไป queue, batch การเขียน
5. **ถ้าข้อมูลใหญ่เกินเครื่องเดียวจริง** — ค่อยคิด sharding พร้อมบอกความซับซ้อนที่ตามมา
6. **ปิดด้วย trade-off + การวัดผล** — "จะวัดว่าดีขึ้นจาก p95 latency และ DB CPU"

### ตัวอย่างคำตอบ: "ทำไมคุณเลือก SQL แทน NoSQL"

**โครง:** ลักษณะข้อมูล → ความต้องการ consistency → ขนาดที่คำนวณไว้ → ความคุ้นเคยของทีม → จุดที่จะเปลี่ยนใจ

> "ข้อมูลเป็นออเดอร์ที่ต้องการ transaction และความถูกต้อง ขนาดที่คำนวณไว้ยังอยู่ในระดับที่เครื่องเดียวบวก replica รับได้ และทีมใช้ SQL อยู่แล้ว ผมจึงเลือก SQL ครับ แต่ถ้าส่วน event log โตมหาศาลและไม่ต้องการ join ผมจะพิจารณา NoSQL แยกเฉพาะส่วนนั้น"

## 12. One-Minute Review

- System Design ไม่มีคำตอบถูกข้อเดียว มีแต่คำตอบที่ **มีเหตุผลรองรับ**
- คนสัมภาษณ์ให้คะแนน **การถาม requirement ก่อนวาด** และ **การอธิบาย trade-off** ไม่ใช่การจำ architecture
- เริ่มจาก **User → Frontend → LB → Backend → Cache → DB** แล้วเพิ่มทีละชั้นเมื่อเจอปัญหา
- CDN = static ช้า / API Gateway = หลาย service / Queue + Worker = งานช้าหรือ traffic พุ่ง / Object Storage = ไฟล์ใหญ่ / WebSocket = real-time
- 12 ขั้น: Requirement → Users → Traffic → Data → API → Database → Cache → Scaling → Reliability → Security → Monitoring → Trade-offs
- สูตร: **QPS ≈ DAU × action ÷ 100,000**, peak × 2–5, ข้อมูล/ปี = แถว/วัน × 365 × ขนาดแถว และตัวเลขต้องถูก **ใช้ตัดสินใจ** ไม่ใช่คำนวณแล้วทิ้ง
- backend ต้อง **stateless** ก่อน scale out
- ทุกชิ้นส่วนต้องถามว่า "ถ้าพังแล้วเกิดอะไร" และ "จะรู้ได้ยังไงว่ามันพัง"
- การบอก "ยังไม่ใส่ X เพราะยังไม่มีปัญหา Y" ได้คะแนนพอ ๆ กับการใส่ X ถูกที่
- ลงลึก Queue / Cache / Idempotency → PART 16, Monitoring → PART 23

1. **ถามก่อนวาด** — requirement ผิด ทุกอย่างผิด
2. **ตัวเลขนำทาง** — DAU ÷ 100,000 = QPS แล้วใช้ตัวเลขตัดสินใจ
3. **เริ่มง่าย เพิ่มเมื่อมีปัญหา** — ทุกกล่องต้องตอบได้ว่า "ใส่เพราะอะไร"
4. **ทุกชิ้นพังได้** — หา SPOF, ให้เส้นทางหลักรอดก่อนฟีเจอร์รอง
5. **พูด trade-off เสมอ** — "เลือก A เพราะ... แลกกับ..."

**Keyword:**

- **Requirement** → ระบบต้องทำอะไร / ดีแค่ไหน → ถามก่อนวาดทุกครั้ง
- **Back-of-Envelope** → คำนวณคร่าว ๆ → รู้ขนาดของปัญหา
- **QPS** → request ต่อวินาที → ตัวกำหนดว่าต้อง scale แค่ไหน
- **Load Balancer** → กระจายงาน → เมื่อ server เดียวไม่พอหรือเป็น SPOF
- **Cache** → ของอ่านบ่อยใกล้มือ → เมื่อ DB โดนอ่านซ้ำ แลกกับข้อมูลเก่า
- **CDN** → สาขาใกล้บ้าน → เมื่อไฟล์ static โหลดช้า
- **API Gateway** → ประตูหน้าตึก → เมื่อมีหลาย service ต้องทำ auth/rate limit ร่วมกัน
- **Queue + Worker** → ตะกร้าใบสั่ง + ครัวหลังร้าน → เมื่องานช้าหรือ traffic พุ่ง
- **Object Storage** → โกดังไฟล์ใหญ่ → เมื่อต้องเก็บรูป วิดีโอ ไฟล์
- **WebSocket** → สายโทรศัพท์ค้าง → เมื่อต้องการ real-time สองทาง
- **Stateless** → server ไม่จำอะไร → เงื่อนไขก่อน scale out
- **SPOF** → จุดตายจุดเดียว → ต้องหาและกำจัดก่อนขึ้น production
- **Trade-off** → ได้อย่างเสียอย่าง → หัวใจของคำตอบ System Design
