# PART 8 — DATABASE

> ตำแหน่งในภาพใหญ่: Data Layer — ชั้นล่างสุดที่เก็บ "ความจริง" ของระบบ ถ้าชั้นนี้ผิด ชั้นบนทั้งหมดผิดตาม

## 1. Big Picture

ลองนึกภาพระบบขายของออนไลน์ ผู้ใช้กดสั่งซื้อ 1 ครั้ง

- **Frontend** ทำให้เขาเห็นปุ่มและกดได้
- **Backend** ตัดสินใจว่าคำสั่งนี้ถูกต้องไหม
- **Database** คือคนที่ต้องจำไว้ว่า "order นี้เกิดขึ้นจริง จำนวนเงินเท่านี้ ของเหลือเท่านี้"

ทุกชั้นข้างบน **restart ได้ ทิ้งได้ scale ใหม่ได้** แต่ database ทิ้งไม่ได้
Server ล่มแล้วเปิดใหม่ = ไม่มีใครเดือดร้อน
Database ข้อมูลหาย = บริษัทเดือดร้อน

นี่คือเหตุผลว่าทำไม interview ระดับ Mid ขึ้นไป **ถามเรื่อง database หนักมาก** เพราะมันเป็นจุดที่:

1. **แก้ยากที่สุด** — เปลี่ยน UI ใช้เวลา 1 วัน เปลี่ยน schema ที่มีข้อมูล 50 ล้านแถวใช้เวลาเป็นเดือน
2. **เป็น bottleneck บ่อยที่สุด** — ระบบช้า 8 ใน 10 ครั้งสาเหตุอยู่ที่ query ไม่ใช่ที่ React
3. **เป็นที่ที่ bug แพงที่สุดเกิด** — เงินหาย ของขายเกินสต็อก ยอดไม่ตรง

**Database → ฐานข้อมูล → ที่เก็บข้อมูลแบบถาวร ที่ค้นหาได้เร็ว และรับประกันความถูกต้องได้แม้มีคนใช้พร้อมกันเป็นพัน**

สังเกตนิยามนี้ให้ดี มันมี 3 ส่วน และ 3 ส่วนนี้คือ 3 หัวข้อใหญ่ของ chapter นี้:

| ส่วนของนิยาม | เรื่องที่ต้องเรียน |
|---|---|
| เก็บถาวร | Table, Document, Key, Relationship, Normalization, Replication |
| ค้นหาได้เร็ว | Query, Index, JOIN, N+1, Pagination, Connection Pool |
| ถูกต้องแม้คนใช้พร้อมกัน | Transaction, ACID, Isolation, Race Condition, Lock |

**ถ้าคุณเข้าใจแค่ 3 บรรทัดนี้ คุณจะรู้ว่าคำถาม database ทุกข้อในโลกกำลังถามเรื่องไหนใน 3 เรื่องนี้**

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| Database | ที่เก็บความจริง | ระบบเก็บข้อมูลถาวร ค้นได้ แก้ได้ ปลอดภัย |
| DBMS | โปรแกรมดูแล DB | ตัวจริงที่รันอยู่ เช่น PostgreSQL, MySQL, MongoDB |
| SQL | ภาษาสั่ง DB | ภาษามาตรฐานสำหรับถาม/แก้ข้อมูลใน relational DB |
| Relational DB | ข้อมูลเป็นตาราง | มี schema ชัด มีความสัมพันธ์ระหว่างตาราง |
| NoSQL | ไม่ใช่ตาราง | เก็บแบบ document / key-value / graph / column |
| Table | ตาราง | ที่เก็บข้อมูลประเภทเดียวกัน เช่น `users` |
| Row / Record | 1 แถว = 1 ชิ้นข้อมูล | user 1 คน = 1 row |
| Column / Field | 1 ช่อง = 1 คุณสมบัติ | `email`, `created_at` |
| Schema | พิมพ์เขียวโครงสร้าง | บอกว่าตารางมี column อะไร ชนิดอะไร |
| Document | ข้อมูล 1 ก้อนแบบ JSON | หน่วยข้อมูลของ MongoDB |
| Collection | กล่องใส่ document | เทียบได้กับ table |
| Primary Key (PK) | บัตรประชาชนของ row | ค่าที่ไม่ซ้ำ ใช้ระบุ row นั้นเฉพาะตัว |
| Foreign Key (FK) | เส้นเชื่อมไปตารางอื่น | column ที่ชี้ไป PK ของตารางอื่น |
| Relationship | ความสัมพันธ์ | 1:1, 1:N, N:M |
| JOIN | ต่อตารางเข้าด้วยกัน | ดึงข้อมูลข้ามตารางใน query เดียว |
| Index | สารบัญของหนังสือ | โครงสร้างช่วยค้นหาเร็วขึ้นมาก |
| Full Table Scan | เปิดอ่านทุกหน้า | DB ไล่อ่านทุก row เพราะไม่มี index ช่วย |
| Query | คำถามที่ถาม DB | คำสั่งดึง/แก้ข้อมูล |
| Query Plan | แผนการทำงานของ query | DB บอกว่ามันจะหาข้อมูลยังไง |
| N+1 Problem | ยิง query ซ้ำเป็นร้อย | ดึง list 1 ครั้ง แล้วยิงเพิ่มทีละ row |
| Pagination | แบ่งหน้า | ดึงข้อมูลทีละหน้าแทนที่จะดึงหมด |
| Offset Pagination | ข้ามไป N แถว | `LIMIT 20 OFFSET 10000` |
| Cursor Pagination | จำว่าหยุดตรงไหน | ดึงต่อจาก id/เวลาล่าสุด |
| Transaction | ทำทั้งชุดหรือไม่ทำเลย | กลุ่มคำสั่งที่ต้องสำเร็จพร้อมกัน |
| Commit | ยืนยัน | บันทึกผลของ transaction ถาวร |
| Rollback | ย้อนกลับ | ยกเลิกทุกอย่างใน transaction |
| ACID | 4 สัญญาของ transaction | Atomicity, Consistency, Isolation, Durability |
| Isolation Level | ระดับการกันคนอื่นเห็น | Read Uncommitted → Serializable |
| Race Condition | แย่งกันแก้พร้อมกัน | ผลลัพธ์ขึ้นกับว่าใครเร็วกว่า |
| Lost Update | เขียนทับกันเงียบ ๆ | update 2 ครั้ง เหลือผลเดียว |
| Lock | ล็อกข้อมูลไว้ก่อน | กันคนอื่นแก้ระหว่างที่เราทำ |
| Pessimistic Lock | ล็อกไว้ก่อนเลย | คิดว่าจะชนแน่ ๆ |
| Optimistic Lock | เช็คตอนจะเขียน | คิดว่าไม่ค่อยชน ใช้ version เช็ค |
| Deadlock | ต่างคนต่างรอกัน | A รอ B, B รอ A ค้างทั้งคู่ |
| Connection Pool | โต๊ะสำรองที่เปิดค้างไว้ | ชุด connection ที่ใช้ซ้ำแทนเปิดใหม่ทุกครั้ง |
| Normalization | ไม่เก็บซ้ำ | แยกตารางให้ข้อมูลอยู่ที่เดียว |
| Denormalization | ยอมเก็บซ้ำเพื่อเร็ว | รวมข้อมูลไว้ด้วยกัน ลด JOIN |
| Replication | ก๊อปปี้ไว้หลายที่ | primary เขียน replica อ่าน |
| Replication Lag | ก๊อปปี้ตามไม่ทัน | replica ข้อมูลเก่ากว่า primary ชั่วขณะ |
| Migration | เปลี่ยนโครงสร้าง DB | script เปลี่ยน schema แบบมีประวัติ |
| ORM | ตัวแปลง object ↔ table | เช่น Prisma, TypeORM, Hibernate |

## 3. Mental Model

### Mental Model หลัก: Database คือ "สมุดบัญชีที่มีคนแย่งกันเขียนพร้อมกัน"

อย่ามอง database เป็นแค่ "ที่เก็บของ" — ถ้ามองแบบนั้น คุณจะตอบ interview ได้แค่ระดับ Junior

ให้มองว่ามันเป็น **สมุดบัญชีเล่มเดียวของบริษัท** ที่:

- มีคน **หลายร้อยคนเขียนพร้อมกัน** (concurrent users)
- **ห้ามมีหน้าไหนหาย** แม้ไฟดับกลางคัน (Durability)
- **ต้องเปิดหาข้อมูลได้เร็ว** ทั้งที่มี 50 ล้านบรรทัด (Index)
- **ห้ามให้ใครเห็นบัญชีครึ่ง ๆ กลาง ๆ** ระหว่างที่อีกคนกำลังเขียน (Isolation)

ทุก feature ของ database ที่ดูซับซ้อน ล้วนเกิดจาก 4 ข้อนี้

### Mental Model ที่ 2: มี 3 คำถามเสมอเวลาออกแบบ

เวลาเจอโจทย์ database ให้ถาม 3 ข้อนี้ในหัวตามลำดับ:

```
1) ข้อมูลนี้ "รูปร่าง" แน่นอนไหม?     → ตอบว่า SQL หรือ NoSQL
         ↓
2) ข้อมูลนี้ถูก "อ่าน" แบบไหนบ่อยสุด?  → ตอบว่าต้องมี Index ตรงไหน
         ↓
3) ข้อมูลนี้ "แก้พร้อมกัน" ได้ไหม?     → ตอบว่าต้องใช้ Transaction / Lock แบบไหน
```

> **ให้มองภาพนี้ว่า** "การออกแบบ database คือการตอบ 3 คำถามตามลำดับ — เก็บยังไง อ่านยังไง แล้วถ้าคนแย่งกันแก้จะเอายังไง"

### Mental Model ที่ 3: Database คือ "ทรัพยากรที่แชร์กัน" ไม่ใช่ของส่วนตัวของ service คุณ

Backend scale จาก 2 pod เป็น 20 pod ได้ง่าย แต่ database ตัวเดียวยังตัวเดิม
ทุก connection ที่คุณเปิด ทุก query ที่คุณยิง คือการ **แย่งทรัพยากรกับทุกคนในทีม**

นี่คือเหตุผลที่ Senior จะพูดประโยคนี้เสมอ:

> "Backend scale ง่าย Database scale ยาก — เพราะฉะนั้นอย่าโยนภาระไปให้ DB โดยไม่จำเป็น"

## 4. 🧠 ภาพจำ

```
🧠 ภาพจำ:
Database         = สมุดบัญชีเล่มเดียวของบริษัท
Table            = ตารางในสมุด (หน้า "ลูกค้า", หน้า "คำสั่งซื้อ")
Row              = 1 บรรทัดในตาราง
Column           = 1 ช่องในบรรทัด
Primary Key      = เลขบัตรประชาชนของบรรทัดนั้น
Foreign Key      = การเขียนว่า "ดูรายละเอียดที่บรรทัดหมายเลข 42 ในหน้าลูกค้า"
Index            = สารบัญท้ายเล่ม
Transaction      = "เขียนทั้งชุดนี้ให้เสร็จ หรือฉีกทิ้งทั้งชุด"
Lock             = เอามือกดหน้ากระดาษไว้ไม่ให้ใครแก้
Replication      = ถ่ายเอกสารสมุดไว้อีกเล่มที่สาขาอื่น
Connection Pool  = โต๊ะทำงาน 10 ตัวที่ตั้งไว้ ไม่ต้องยกโต๊ะใหม่ทุกครั้งที่มีลูกค้า
```

### ภาพจำเจาะลึก: Index = สารบัญของหนังสือ (ข้อนี้ต้องจำให้แม่นที่สุด)

```
หนังสือ 900 หน้า ต้องการหาคำว่า "Kubernetes"

ไม่มีสารบัญ → เปิดอ่านทีละหน้าตั้งแต่หน้า 1    = Full Table Scan
มีสารบัญ    → เปิดสารบัญ เห็นว่า "หน้า 412"   = Index Scan
              แล้วกระโดดไปหน้า 412 ทันที
```

> **ให้มองภาพนี้ว่า** "Index คือสารบัญที่เรียงคำไว้ล่วงหน้า ทำให้ database ไม่ต้องอ่านทุกหน้าเพื่อหาสิ่งเดียว"

**แต่สารบัญไม่ได้ฟรี** — และนี่คือส่วนที่ Junior ส่วนใหญ่ตอบไม่ได้:

| ต้นทุนของสารบัญ | ต้นทุนของ Index จริง ๆ |
|---|---|
| สารบัญกินกระดาษเพิ่ม 20 หน้า | Index กินพื้นที่ disk เพิ่ม (บางทีใหญ่กว่าตารางเอง) |
| แก้เนื้อหา 1 หน้า ต้องตามไปแก้สารบัญด้วย | ทุก INSERT / UPDATE / DELETE ต้องอัปเดต index ทุกตัว → เขียนช้าลง |
| ทำสารบัญ 15 แบบ = หนังสือหนาเป็นสองเท่า | Index เยอะเกิน = write throughput ตก + เปลือง memory |
| สารบัญเรียงตามชื่อ ใช้หาตามหน้าไม่ได้ | Index ผิด column = ไม่ถูกใช้เลย เสียของฟรี |

**ประโยคที่ต้องพูดได้ใน interview:**
"Index เร่ง read แต่ทำให้ write ช้าลงและกินพื้นที่ — เพราะฉะนั้นเราสร้าง index ตาม query ที่ใช้จริง ไม่ใช่สร้างทุก column เผื่อไว้"

## 5. How It Works

### 5.1 Query หนึ่งครั้งเดินทางอย่างไร

```
[APPLICATION CODE]
        ↓  ขอ connection
[CONNECTION POOL]     ← ถ้า pool หมด ต้องรอตรงนี้
        ↓
[DATABASE SERVER]
        ↓
[PARSER]              ตรวจว่า SQL เขียนถูกไหม
        ↓
[QUERY PLANNER]       เลือกวิธีหาข้อมูลที่ถูกที่สุด (ใช้ index ไหม? JOIN แบบไหน?)
        ↓
[EXECUTOR]            ลงมือหาจริง
        ↓
[STORAGE / INDEX]     อ่าน disk หรือ memory cache
        ↓
[RESULT]
        ↓
[APPLICATION CODE]
```

> **ให้มองภาพนี้ว่า** "เราไม่ได้สั่ง database ว่าให้หาข้อมูลยังไง เราแค่บอกว่าอยากได้อะไร แล้ว planner เป็นคนตัดสินใจวิธีให้เอง — การ optimize จึงคือการทำให้ planner เลือกทางที่ดีได้"

ประโยคสุดท้ายสำคัญมาก: SQL คือ **declarative language** เราบอก "what" ไม่ใช่ "how"
เวลา query ช้า เราไม่ได้ไปแก้วิธีค้น เราไปแก้ **ข้อมูลที่ planner มี** (index, statistics, โครงสร้าง query)

### 5.2 Index ทำงานอย่างไร (B-Tree)

```
ค้นหา user ที่ email = 'somchai@mail.com'

ไม่มี Index:
[row 1] → ไม่ใช่
[row 2] → ไม่ใช่
...
[row 4,999,999] → เจอ!          = อ่าน 5 ล้านครั้ง

มี Index (B-Tree):
        [ m ]                    ← เริ่มที่กลาง
       /     \
   [ d-h ]  [ n-t ]              ← s อยู่ฝั่งขวา
              ↓
          [ so-sz ]              ← เจอ block ที่ใช่
              ↓
      ชี้ไปที่ row จริง           = อ่าน ~4 ครั้ง
```

> **ให้มองภาพนี้ว่า** "Index คือการเดาครึ่งหนึ่งทิ้งทุกครั้ง — ข้อมูล 5 ล้านแถวใช้การกระโดดแค่ยี่สิบกว่าครั้งก็เจอ"

**สิ่งที่ต้องรู้เพิ่ม (ระดับ Mid):**

| ประเด็น | สาระ |
|---|---|
| Index เรียงจากซ้าย | index `(status, created_at)` ใช้ค้นด้วย `status` ได้ / ค้นด้วย `created_at` เดี่ยว ๆ ไม่ได้ |
| ฟังก์ชันครอบ column ทำ index ตาย | `WHERE LOWER(email) = ...` จะไม่ใช้ index ของ `email` |
| `LIKE '%abc'` ใช้ index ไม่ได้ | เพราะไม่รู้ตัวอักษรแรก เหมือนเปิดสารบัญโดยไม่รู้ว่าคำขึ้นต้นด้วยอะไร |
| Index ช่วย ORDER BY ด้วย | ถ้าเรียงตรงกับ index DB ไม่ต้อง sort ใหม่ |
| Cardinality ต่ำ = index แทบไร้ค่า | index บน column `gender` ที่มี 2 ค่า ช่วยน้อยมาก |

### 5.3 Transaction ทำงานอย่างไร

```
BEGIN
   ↓
หักเงินบัญชี A -1000
   ↓
เพิ่มเงินบัญชี B +1000
   ↓
สำเร็จทั้งคู่? ──── ใช่ ───→ COMMIT   (บันทึกถาวร)
   │
   └──────────── ไม่ ───→ ROLLBACK (ย้อนกลับเหมือนไม่เคยเกิด)
```

> **ให้มองภาพนี้ว่า** "Transaction คือการบอก database ว่างานชุดนี้ให้คิดเป็นก้อนเดียว จะสำเร็จทั้งก้อนหรือหายไปทั้งก้อน ห้ามสำเร็จครึ่งเดียว"

### 5.4 Replication ทำงานอย่างไร

```
                  ┌── [REPLICA 1]  (อ่านอย่างเดียว)
[PRIMARY] ─ log ──├── [REPLICA 2]  (อ่านอย่างเดียว)
 เขียนที่นี่       └── [REPLICA 3]  (อ่านอย่างเดียว)
```

> **ให้มองภาพนี้ว่า** "เขียนที่เดียวเพื่อไม่ให้ข้อมูลตีกัน แต่ก๊อปปี้ไว้หลายที่เพื่อให้คนอ่านพร้อมกันได้เยอะ ๆ"

**ราคาที่ต้องจ่าย: Replication Lag**
ระหว่างที่ก๊อปปี้ยังตามไม่ทัน replica จะเห็นข้อมูลเก่ากว่า primary เสี้ยววินาทีถึงหลายวินาที

อาการที่เจอจริงในงาน: "user กด save โปรไฟล์ แล้วหน้าถัดไปยังแสดงข้อมูลเดิม"
สาเหตุ: เขียนลง primary แต่อ่านจาก replica ที่ยัง lag
วิธีแก้มาตรฐาน: **read-your-own-write** — หลังเขียนเสร็จ ให้ user คนนั้นอ่านจาก primary ชั่วคราว

### 5.5 Connection Pool ทำงานอย่างไร

```
[REQ 1] ─┐
[REQ 2] ─┤                 ┌── conn 1 ──┐
[REQ 3] ─┼→ [POOL: 10] ────┼── conn 2 ──┼→ [DATABASE  max 100 conn]
[REQ 4] ─┤    (คิวรอ)      └── ...  ────┘
[REQ 5] ─┘
```

> **ให้มองภาพนี้ว่า** "Connection pool คือโต๊ะทำงานจำนวนจำกัดที่เปิดค้างไว้ ใครมาก็ใช้โต๊ะที่ว่าง ใช้เสร็จคืน ไม่ใช่ยกโต๊ะใหม่มาทุกครั้งที่ลูกค้าเดินเข้ามา"

**ทำไมต้องมี:** เปิด TCP connection + authenticate ใหม่ทุกครั้ง แพงมากเมื่อเทียบกับตัว query เอง
**ทำไมต้องจำกัดจำนวน:** database รับ connection ได้จำกัด ถ้า 20 pod × pool 50 = 1000 connection → database ตาย

**สูตรคิดคร่าว ๆ:** `pool size ต่อ instance × จำนวน instance < max_connections ของ DB` (และเผื่อไว้สำหรับ admin/migration)

## 6. Example — ระบบจริง

### 6.1 ออกแบบตารางของระบบ E-commerce

```
users                orders                  order_items           products
─────                ──────                  ───────────           ────────
id (PK)   ←──┐       id (PK)      ←──┐       id (PK)               id (PK)
name         └───FK──user_id          └──FK──order_id              name
email                status                  product_id ──FK──→    price
created_at           total_amount            quantity              stock
                     created_at              price_at_purchase
```

> **ให้มองภาพนี้ว่า** "แต่ละตารางเก็บข้อมูลของตัวเองอย่างเดียว แล้วใช้ Foreign Key เป็นเส้นด้ายโยงหากันแทนการคัดลอกข้อมูลไปเก็บซ้ำ"

**จุดที่ interview ชอบถามจากภาพนี้: ทำไม `order_items` ต้องมี `price_at_purchase` ในเมื่อ `products` มี `price` อยู่แล้ว?**

คำตอบ: เพราะราคาสินค้าเปลี่ยนได้ ถ้าไม่เก็บราคา ณ วันซื้อไว้ พอเดือนหน้าสินค้าลดราคา **ใบเสร็จเก่าทั้งหมดจะเปลี่ยนตาม** ซึ่งผิดทั้งทางบัญชีและทางกฎหมาย

นี่คือตัวอย่างว่า **normalization ที่ถูกต้อง 100% ตามตำรา ไม่ใช่คำตอบที่ถูกต้องเสมอในงานจริง** — ข้อมูลที่เป็น "ข้อเท็จจริง ณ เวลาหนึ่ง" ต้องถูกคัดลอกเก็บไว้

### 6.2 Relationship 3 แบบ ด้วยตัวอย่างจากระบบเดียวกัน

| ความสัมพันธ์ | ตัวอย่าง | เก็บยังไง | สัญญาณว่าเลือกถูก |
|---|---|---|---|
| **One-to-One (1:1)** | user 1 คน มี profile 1 อัน | แยกตาราง `user_profiles` ที่มี `user_id` เป็น FK + unique | ใช้เมื่อข้อมูลนั้นใหญ่ / อ่านไม่บ่อย / มี security level ต่างกัน |
| **One-to-Many (1:N)** | user 1 คน มีหลาย order | ฝั่ง "many" (`orders`) เก็บ FK `user_id` | ฝั่งที่มีเยอะเป็นคนถือ FK เสมอ |
| **Many-to-Many (N:M)** | order มีหลาย product / product อยู่ในหลาย order | ต้องมี **ตารางกลาง** `order_items` | ถ้าเจอ N:M แล้วไม่มีตารางกลาง แปลว่าออกแบบผิด |

**กฎที่จำง่ายที่สุด: "ฝั่งที่มีเยอะ เป็นคนถือ Foreign Key"**
และ **"N:M ต้องมีตารางกลางเสมอ ไม่มีข้อยกเว้นใน relational DB"**

ข้อดีที่มองข้ามของตารางกลาง: มันเก็บ **ข้อมูลของความสัมพันธ์** ได้ด้วย เช่น `order_items` เก็บ `quantity` และ `price_at_purchase` ซึ่งไม่ใช่ของ order และไม่ใช่ของ product แต่เป็นของ "ความสัมพันธ์ระหว่างสองสิ่งนี้"

### 6.3 JOIN — ตัวอย่างและ mental model

```sql
SELECT o.id, u.name
FROM orders o
JOIN users u ON u.id = o.user_id
```

(6 บรรทัดนี้คือ SQL ที่ยาวที่สุดในบทนี้ — ที่เหลือเน้น concept)

**JOIN 4 แบบ:**

| แบบ | ได้อะไร | ใช้เมื่อไร |
|---|---|---|
| INNER JOIN | เฉพาะที่มีคู่ทั้งสองฝั่ง | ปกติที่สุด — order ที่มี user จริง |
| LEFT JOIN | เอาฝั่งซ้ายทั้งหมด ฝั่งขวาไม่มีก็ใส่ NULL | "user ทุกคน พร้อมจำนวน order (ที่อาจเป็น 0)" |
| RIGHT JOIN | กลับด้านกับ LEFT | แทบไม่ใช้ กลับ LEFT เอาอ่านง่ายกว่า |
| FULL OUTER JOIN | เอาหมดทั้งสองฝั่ง | ใช้ตอน reconcile ข้อมูล 2 ระบบ |

🧠 **ภาพจำ JOIN:**

```
INNER JOIN = เฉพาะคนที่มาทั้งคู่ถึงถ่ายรูปได้
LEFT JOIN  = ฝั่งซ้ายมาครบทุกคน ฝั่งขวาใครไม่มาก็ปล่อยว่างไว้
```

**กับดักที่เจอจริง:** `LEFT JOIN` แล้วใส่เงื่อนไขฝั่งขวาใน `WHERE` → มันกลายเป็น `INNER JOIN` ทันที เพราะ row ที่เป็น NULL ถูกกรองทิ้ง (ต้องย้ายเงื่อนไขไปไว้ใน `ON` แทน)

### 6.4 N+1 Problem — ตัวอย่างจริงที่ทำ production ล่มมาแล้วนับไม่ถ้วน

**โจทย์:** หน้า "รายการคำสั่งซื้อ" แสดง order 100 รายการ พร้อมชื่อลูกค้าของแต่ละ order

**โค้ดที่ Junior เขียน (pseudocode):**

```
orders = SELECT * FROM orders LIMIT 100        ← 1 query
for each order:
    user = SELECT * FROM users WHERE id = ?    ← 100 queries
```

รวม **101 queries** = นี่คือชื่อ "N+1" (1 query แรก + N query ตาม)

**ทำไมมันร้ายกว่าที่คิด:**

| ประเด็น | ความจริง |
|---|---|
| ตอน dev ข้อมูล 10 แถว | 11 queries × 1ms = 11ms → ไม่รู้สึกอะไรเลย |
| ตอน production 500 แถว | 501 queries × 3ms (มี network latency) = **1.5 วินาที** |
| แต่ละ query กิน connection | 101 request พร้อมกัน × 101 query = pool หมดทันที |
| Query แต่ละตัวเร็วมาก | ดู slow query log ไม่เจอ เพราะไม่มีตัวไหนช้าเลย |

**บรรทัดนี้คือคำตอบระดับ Senior:** "N+1 ไม่ได้เกิดจาก query ช้า แต่เกิดจาก **จำนวน round-trip** — แต่ละ round-trip มีต้นทุน network + parse + connection ที่คงที่ ต่อให้ query เร็ว 0.5ms การคูณ 500 ครั้งก็ยังแพง"

**วิธีสังเกต N+1 (ข้อนี้ interviewer ชอบถามต่อ):**

| วิธี | ทำยังไง |
|---|---|
| 1. ดูจำนวน query ต่อ 1 request | เปิด query log แล้วยิง request เดียว — ถ้าเห็น query เดิมซ้ำ ๆ ต่างกันแค่ id คือเจอแล้ว |
| 2. ดูรูปแบบของ log | บรรทัดเดียวกันซ้ำ 100 ครั้งเรียงติดกัน = signature ของ N+1 |
| 3. Latency โตตามจำนวนแถว | 10 แถว = 50ms, 100 แถว = 500ms → เป็นเส้นตรง = N+1 แน่นอน |
| 4. APM / Tracing | span ของ DB ซ้อนกันเป็นหวี (ดู PART 23) |
| 5. ORM debug mode | เปิด `logging: true` ใน Prisma/TypeORM/Hibernate แล้วนับ |

**วิธีแก้ 3 ทาง:**

| วิธี | ทำยังไง | เหมาะเมื่อ |
|---|---|---|
| JOIN | ดึงมาพร้อมกันใน query เดียว | ข้อมูลฝั่งเดียวไม่ซ้ำเยอะ |
| IN clause (2 queries) | ดึง order → เก็บ user_id ทั้งหมด → `WHERE id IN (...)` ครั้งเดียว | ปลอดภัยที่สุด ใช้ได้เกือบทุกกรณี |
| ORM eager loading | `include` / `JOIN FETCH` / `select_related` | เมื่อใช้ ORM อยู่แล้ว |

⚠️ **ระวัง over-correction:** แก้ N+1 ด้วย JOIN หลายตารางพร้อมกัน อาจเจอ **cartesian explosion** — order 100 × item 10 × tag 5 = 5,000 rows ที่ต้องส่งกลับ ทั้งที่ข้อมูลจริงมีไม่ถึง 1,000 แถว
ทางออก: แตกเป็น 2-3 queries แบบ IN แทนการ JOIN ทุกอย่างในครั้งเดียว

### 6.5 Pagination — Offset vs Cursor

**Offset Pagination:**

```
หน้า 1:    LIMIT 20 OFFSET 0
หน้า 2:    LIMIT 20 OFFSET 20
หน้า 500:  LIMIT 20 OFFSET 9980
```

**ปัญหาที่ 1 — ยิ่งหน้าลึกยิ่งช้า (สำคัญที่สุด):**

```
OFFSET 9980 LIMIT 20
  ↓
DB ต้องหา + เรียง row ที่ 1 ถึง 10,000
  ↓
แล้ว "ทิ้ง" 9,980 แถวแรก
  ↓
ส่งคืนแค่ 20 แถว
```

> **ให้มองภาพนี้ว่า** "OFFSET ไม่ใช่การกระโดดข้าม แต่คือการนับผ่านทีละแถวแล้วโยนทิ้ง — เพราะฉะนั้นหน้าที่ 500 แพงกว่าหน้าที่ 1 จริง ๆ ไม่ใช่ความรู้สึก"

**ปัญหาที่ 2 — ข้อมูลซ้ำ/หายเมื่อมีการ insert ระหว่างเปิดหน้า:**

```
เวลา 10:00  user ดูหน้า 1 (row 1-20)
เวลา 10:01  มีคนเพิ่ม post ใหม่ 1 อัน → ทุกอย่างเลื่อนลง 1
เวลา 10:02  user กดหน้า 2 (OFFSET 20)
            → เห็น row ที่เคยเป็น row 20 ซ้ำอีกครั้ง
```

**Cursor Pagination:**

```
หน้า 1:  WHERE id < ∞      ORDER BY id DESC LIMIT 20   → ตัวสุดท้าย id = 981
หน้า 2:  WHERE id < 981    ORDER BY id DESC LIMIT 20   → ตัวสุดท้าย id = 961
หน้า 3:  WHERE id < 961    ORDER BY id DESC LIMIT 20
```

> **ให้มองภาพนี้ว่า** "Cursor คือที่คั่นหนังสือ — เราไม่ได้บอกว่าอยากได้หน้าที่เท่าไร เราบอกว่า 'ขอต่อจากตรงนี้' ซึ่งใช้ index กระโดดไปได้ทันทีไม่ว่าจะลึกแค่ไหน"

**ตารางเปรียบเทียบตัวจริง (ข้อนี้ต้องพูดได้ครบใน interview):**

| ประเด็น | Offset | Cursor |
|---|---|---|
| หลักการ | ข้าม N แถว | ดึงต่อจากค่าล่าสุด |
| ความเร็วหน้าแรก | เร็ว | เร็ว |
| ความเร็วหน้าลึก (หน้า 5000) | **ช้าลงเรื่อย ๆ แบบเชิงเส้น** | **เร็วคงที่** |
| กระโดดไปหน้า 37 ได้ไหม | **ได้** | **ไม่ได้** — ข้ามหน้าไม่ได้เลย |
| แสดง "หน้า 1 2 3 ... 500" | ได้ | ไม่ได้ ต้องเป็นปุ่ม "โหลดเพิ่ม" |
| รู้จำนวนหน้าทั้งหมด | ได้ (แต่ต้อง COUNT ซึ่งก็ช้าเอง) | ไม่รู้ |
| ข้อมูลซ้ำ/ตกหล่นตอนมี insert | **มีปัญหา** | ไม่มี (ถ้า cursor เป็นค่าที่ไม่เปลี่ยน) |
| เรียงตาม column ที่แก้ได้ | ทำได้ | **ยาก** — cursor ต้องเรียงตาม field ที่ไม่เปลี่ยนและ unique |
| ซับซ้อนในการ implement | ง่ายมาก | ปานกลาง (ต้อง encode cursor, จัด tie-breaker) |

**Trade-off จริงที่ต้องพูด:**
"Offset ง่ายและกระโดดหน้าได้ แต่ช้าลงเมื่อหน้าลึกและข้อมูลอาจซ้ำ — Cursor เร็วคงที่และข้อมูลไม่ซ้ำ แต่แลกด้วยการกระโดดหน้าไม่ได้และ implement ยากกว่า"

**เลือกยังไงในงานจริง:**

| สถานการณ์ | เลือก |
|---|---|
| ตาราง admin ที่มีข้อมูลหลักพัน ต้องกระโดดหน้า | Offset |
| Feed / timeline / infinite scroll | Cursor |
| Public API ที่ผู้ใช้จะยิงลึก ๆ | Cursor (กัน abuse ด้วย) |
| Export ข้อมูลทั้งหมด | Cursor (offset ลึก ๆ จะฆ่า DB) |

**กับดักของ cursor ที่ต้องรู้:** ถ้าเรียงตาม `created_at` อย่างเดียว แล้วมี 2 row เวลาเท่ากันเป๊ะ → cursor จะข้ามหรือซ้ำ
วิธีแก้: ใช้ **compound cursor** `(created_at, id)` โดย `id` เป็น tie-breaker เสมอ

### 6.6 Transaction + Race Condition — ตัวอย่างโอนเงิน

**โจทย์: โอนเงิน 1,000 บาท จาก A ไป B**

**กรณีไม่มี transaction:**

```
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A'   ✔ สำเร็จ
        ↓
   💥 server crash / network ขาด
        ↓
UPDATE accounts SET balance = balance + 1000 WHERE id = 'B'   ✘ ไม่ได้รัน
```

ผลลัพธ์: **เงิน 1,000 บาทหายไปจากระบบ** — A หายไปแล้ว B ไม่เคยได้รับ

**กรณีมี transaction:** ถ้าคำสั่งที่สองพัง → `ROLLBACK` → บัญชี A กลับมาเหมือนเดิม เหมือนไม่เคยมีอะไรเกิดขึ้น

### ACID — อธิบายด้วยการโอนเงินทั้ง 4 ตัว

| ตัวอักษร | ชื่อเต็ม | แปลไทย | ในการโอนเงินหมายถึง |
|---|---|---|---|
| **A** | Atomicity | ทำหมดหรือไม่ทำเลย | หัก A และเพิ่ม B ต้องเกิดพร้อมกัน ห้ามมีแค่ครึ่งเดียว |
| **C** | Consistency | กฎของข้อมูลต้องไม่ถูกละเมิด | ยอดรวมทั้งระบบก่อนโอนและหลังโอนต้องเท่ากัน / balance ห้ามติดลบถ้าตั้ง constraint ไว้ |
| **I** | Isolation | คนอื่นไม่เห็นสภาพครึ่ง ๆ | ระหว่างโอน คนที่ query ยอดรวมจะไม่เห็นภาพที่เงินหักแล้วแต่ยังไม่เข้า |
| **D** | Durability | commit แล้วหายไม่ได้ | ถ้าระบบตอบว่าโอนสำเร็จ แล้วไฟดับ 1 วินาทีถัดมา เงินต้องยังโอนแล้วอยู่ |

🧠 **ภาพจำ ACID:**

```
A = "ทั้งหมดหรือไม่เอาเลย"
C = "กฎบ้านต้องไม่ถูกละเมิด"
I = "อย่าแอบดูตอนฉันยังทำไม่เสร็จ"
D = "พูดแล้วเป็นพูด ไฟดับก็ไม่คืนคำ"
```

### Isolation Level — 4 ระดับและปัญหาที่มันกัน

```
Read Uncommitted  →  Read Committed  →  Repeatable Read  →  Serializable
   ปลอดภัยน้อย                                                 ปลอดภัยสุด
   เร็ว / concurrent สูง                                       ช้า / ชนกันบ่อย
```

> **ให้มองภาพนี้ว่า** "Isolation level คือปุ่มหมุนที่แลกความเร็วกับความถูกต้อง — หมุนไปทางปลอดภัยมากขึ้น ระบบก็รับคนพร้อมกันได้น้อยลง"

| ปัญหา | คืออะไร | ตัวอย่าง |
|---|---|---|
| **Dirty Read** | อ่านข้อมูลที่อีกคนยังไม่ commit | เห็นเงินที่กำลังจะถูก rollback |
| **Non-repeatable Read** | อ่าน row เดิม 2 ครั้งใน transaction เดียว ได้ค่าต่างกัน | เช็คยอดตอนต้น 5,000 เช็คอีกทีเป็น 3,000 |
| **Phantom Read** | query เงื่อนไขเดิม 2 ครั้ง ได้จำนวนแถวต่างกัน | นับ order วันนี้ได้ 10 อ่านอีกทีเป็น 12 |
| **Lost Update** | 2 คน update พร้อมกัน เหลือผลของคนเดียว | ดูหัวข้อถัดไป |

| Isolation Level | กัน Dirty Read | กัน Non-repeatable | กัน Phantom |
|---|---|---|---|
| Read Uncommitted | ✘ | ✘ | ✘ |
| Read Committed | ✔ | ✘ | ✘ |
| Repeatable Read | ✔ | ✔ | ✘ (บางระบบกันได้) |
| Serializable | ✔ | ✔ | ✔ |

**ค่า default ที่ควรจำ:** PostgreSQL = Read Committed, MySQL (InnoDB) = Repeatable Read
**ประเด็นที่ interviewer ชอบดัก:** default ของสองตัวนี้ไม่เหมือนกัน แปลว่า **ย้าย MySQL → PostgreSQL แล้วพฤติกรรมของ transaction อาจเปลี่ยน** ต้องรู้ตัว

### Lost Update — ปัญหาคลาสสิกที่ต้องอธิบายได้

**โจทย์: สินค้าเหลือ 1 ชิ้น มีคนซื้อพร้อมกัน 2 คน**

```
เวลา   ผู้ใช้ A                      ผู้ใช้ B
────   ─────────────────────────    ─────────────────────────
t1     อ่าน stock = 1
t2                                  อ่าน stock = 1
t3     เช็ค 1 >= 1 → ผ่าน
t4                                  เช็ค 1 >= 1 → ผ่าน
t5     เขียน stock = 0
t6                                  เขียน stock = 0
```

> **ให้มองภาพนี้ว่า** "ทั้งคู่อ่านความจริงชุดเดียวกันตอนที่มันยังเป็นจริง แล้วตัดสินใจจากข้อมูลที่กลายเป็นเก่าไปแล้วตอนลงมือเขียน"

ผลลัพธ์: **ขายของชิ้นเดียวให้ 2 คน** stock เหลือ 0 แต่มี order 2 ใบ
นี่คือ **Race Condition** — ผลลัพธ์ขึ้นกับจังหวะเวลา ไม่ใช่ตรรกะของโค้ด

**ทำไม transaction เฉย ๆ ไม่ช่วย:** transaction รับประกันว่า "ทำครบหรือไม่ทำ" ไม่ได้รับประกันว่า "ไม่มีใครแทรกระหว่างที่เราอ่านแล้วคิด" — ต้องใช้ **Lock** เพิ่ม

### วิธีแก้ 3 ทาง

**1. Pessimistic Lock — ล็อกไว้ก่อน**

```
BEGIN
SELECT stock FROM products WHERE id=1 FOR UPDATE   ← ล็อก row นี้ไว้
  (ใครมาอ่านแบบเดียวกัน ต้องรอคิว)
UPDATE stock = stock - 1
COMMIT                                             ← ปลดล็อก
```

🧠 ภาพจำ: **"เอามือกดหน้ากระดาษไว้ ใครจะแก้ต้องรอเรายกมือ"**

**2. Optimistic Lock — เช็คตอนจะเขียน**

```
อ่าน: stock = 1, version = 5
เขียน: UPDATE ... SET stock=0, version=6 WHERE id=1 AND version=5
        ↓
ถ้ามีคนแก้ไปก่อน version จะเป็น 6 แล้ว → เงื่อนไขไม่ตรง → อัปเดต 0 แถว → retry
```

🧠 ภาพจำ: **"ไม่ล็อกอะไรเลย แต่ก่อนส่งงานเช็คว่ามีใครแก้ต้นฉบับหรือยัง ถ้ามีก็ทำใหม่"**

**3. ให้ database คิดเลขให้ (ง่ายและมักดีที่สุด)**

```
UPDATE products SET stock = stock - 1 WHERE id=1 AND stock >= 1
```

อ่าน-คิด-เขียนเกิดใน statement เดียว database รับประกัน atomicity ให้เอง
ถ้าอัปเดตได้ 0 แถว แปลว่าของหมด → ตอบ error ไป

### Optimistic vs Pessimistic — เลือกยังไง

| ประเด็น | Pessimistic Lock | Optimistic Lock |
|---|---|---|
| หลักคิด | "เดี๋ยวชนแน่ ล็อกก่อน" | "คงไม่ชนหรอก เช็คตอนจบพอ" |
| กลไก | `SELECT ... FOR UPDATE` | column `version` / `updated_at` |
| คนอื่นระหว่างนั้น | **ต้องรอ** | ทำงานต่อได้ แต่คนแพ้ต้อง retry |
| เหมาะเมื่อ | ชนกันบ่อย / เสียหายสูง (stock, เงิน, seat booking) | ชนกันนาน ๆ ครั้ง (แก้โปรไฟล์, แก้ description) |
| ความเสี่ยง | **Deadlock**, lock contention, throughput ตก | retry เยอะจนพังถ้าชนบ่อย, ต้องเขียน retry logic |
| ประสบการณ์ user | ช้าแต่ไม่ error | เร็วแต่บางทีเจอ "ข้อมูลถูกแก้ไปแล้ว กรุณาลองใหม่" |

**ประโยคสรุปที่ใช้ตอบได้เลย:** "Pessimistic ใช้เมื่อคาดว่าชนบ่อยและค่าเสียหายสูง Optimistic ใช้เมื่อคาดว่าชนน้อยและอยากได้ throughput — ไม่มีตัวไหนดีกว่าโดยไม่ดู contention rate"

### Deadlock

```
Transaction A: ล็อก row 1 แล้ว → ขอ row 2
Transaction B: ล็อก row 2 แล้ว → ขอ row 1

      A ──รอ──→ [row 2] ──ถือโดย──→ B
      ↑                                │
      └────────ถือ row 1 ──รอ─────────┘
```

> **ให้มองภาพนี้ว่า** "สองคนต่างถือกุญแจที่อีกฝ่ายต้องใช้ แล้วยืนรอกันจนกว่าจะมีคนยอมแพ้ — database จึงต้องเลือกฆ่าตัวหนึ่งทิ้งเพื่อให้อีกตัวไปต่อได้"

**สาเหตุหลัก:** แต่ละ transaction ล็อก resource ใน**ลำดับที่ต่างกัน**
**วิธีป้องกันที่ใช้ได้จริง:**

1. ล็อก resource **เรียงลำดับเดียวกันเสมอ** (เช่น เรียงตาม id จากน้อยไปมาก)
2. ทำ transaction ให้ **สั้นที่สุด** — ห้ามเรียก external API หรือรอ user ระหว่าง transaction เปิดอยู่
3. ตั้ง `lock_timeout` ไม่ให้รอไม่จำกัด
4. เขียน retry logic เพราะ deadlock เป็นเรื่องที่ **ต้องเจอบ้าง ไม่ใช่กำจัดได้ 100%**

### 6.7 Normalization ในภาษาคน

**ปัญหาที่ normalization แก้: เก็บข้อมูลซ้ำแล้วมันไม่ตรงกัน**

```
ตารางแบบไม่ normalize:
order_id | customer_name  | customer_email
1        | สมชาย          | somchai@mail.com
2        | สมชาย          | somchai@mail.com
3        | สมชาย          | somchi@mail.com    ← พิมพ์ผิด! ตอนนี้ความจริงมี 2 เวอร์ชัน
```

**แก้:** แยก `customers` ออกมา เก็บ email ที่เดียว แล้ว `orders` เก็บแค่ `customer_id`

3 ระดับแรกที่พอใช้งานจริง (ไม่ต้องท่องนิยาม แค่เข้าใจเจตนา):

| ระดับ | ภาษาคน |
|---|---|
| 1NF | ห้ามยัดหลายค่าไว้ใน 1 ช่อง (เช่น `tags = "a,b,c"`) |
| 2NF | ทุก column ต้องขึ้นกับ **ทั้ง** primary key ไม่ใช่แค่บางส่วน |
| 3NF | column ห้ามขึ้นกับ column อื่นที่ไม่ใช่ key (เช่น เก็บ `zipcode` และ `city` ที่เดาจาก zipcode ได้) |

**Denormalization — ตั้งใจเก็บซ้ำ**

| เก็บซ้ำเพื่อ | ตัวอย่าง |
|---|---|
| ความเร็ว | เก็บ `order_count` ใน `users` แทน `COUNT(*)` ทุกครั้ง |
| ความถูกต้องทางประวัติศาสตร์ | `price_at_purchase` ในหัวข้อ 6.1 |
| ลด JOIN ในหน้าที่โหลดหนัก | dashboard / report table |

**Trade-off: normalize = ข้อมูลไม่ขัดแย้งแต่ต้อง JOIN เยอะ / denormalize = อ่านเร็วแต่ต้องดูแลให้ข้อมูลซ้ำตรงกันเอง**

**หลักปฏิบัติของ Senior:** "normalize ก่อนเสมอ แล้ว denormalize เฉพาะจุดที่วัดแล้วว่าช้าจริง" — เพราะ denormalize คือการรับหนี้ว่า "ฉันจะดูแลข้อมูลให้ตรงกันเอง" ซึ่งเป็นหนี้ที่ลืมง่ายมาก

## 7. Compare

### 7.1 SQL vs NoSQL

| ประเด็น | SQL (Relational) | NoSQL (Document) |
|---|---|---|
| ตัวอย่าง | PostgreSQL, MySQL | MongoDB |
| โครงสร้าง | Table / Row / Column | Collection / Document |
| Schema | **บังคับ** — ผิด type คือ error | **ยืดหยุ่น** — แต่ละ document ต่างกันได้ |
| ความสัมพันธ์ | FK + JOIN เป็นของแท้ | embed หรืออ้างอิงเอง (JOIN จำกัด) |
| Transaction | แข็งแรงมาตั้งแต่ต้น | ทำได้ (multi-document) แต่ออกแบบมาให้เลี่ยง |
| Scale | vertical ก่อน + read replica | sharding แนวนอนง่ายกว่าโดยธรรมชาติ |
| เหมาะกับ | ข้อมูลมีความสัมพันธ์ชัด / ต้องการความถูกต้อง (การเงิน, order, บัญชี) | ข้อมูลรูปร่างไม่แน่นอน / อ่านเป็นก้อน (log, catalog, profile, event) |
| ความเสี่ยงจริง | schema change บนตารางใหญ่เจ็บ | **ข้อมูลเละเพราะไม่มีใครบังคับ schema** |

**สิ่งที่ต้องไม่พูดใน interview:** "NoSQL เร็วกว่า SQL"
**สิ่งที่ควรพูดแทน:** "NoSQL เร็วกว่าเมื่อ access pattern ตรงกับวิธีที่เราเก็บ document ไว้ — แต่ถ้าต้อง query ข้ามความสัมพันธ์เยอะ SQL จะเหนือกว่าเพราะ JOIN ถูกออกแบบมาเพื่อสิ่งนั้น"

**ความจริงที่ Senior รู้:** ปัญหาส่วนใหญ่ของทีมที่เลือก NoSQL ไม่ใช่เรื่อง performance แต่คือ **ไม่มีใครบังคับ schema แล้วผ่านไป 2 ปี ข้อมูลมี 6 รูปแบบในคอลเลกชันเดียว**

### 7.2 PostgreSQL vs MySQL vs MongoDB

| ประเด็น | PostgreSQL | MySQL | MongoDB |
|---|---|---|---|
| ประเภท | Relational | Relational | Document |
| จุดเด่น | feature เยอะ (JSONB, CTE, window function), มาตรฐาน SQL แน่น | ใช้แพร่หลายมาก, tooling/hosting เยอะ, อ่านเร็ว | schema ยืดหยุ่น, scale แนวนอน, เก็บ nested ง่าย |
| Isolation default | Read Committed | Repeatable Read | — (ต่างแนวคิด) |
| เหมาะเมื่อ | logic ซับซ้อน, ต้องการความถูกต้องสูง, ข้อมูลกึ่ง structured (JSONB) | web app ทั่วไป, ทีมคุ้นเคย, ecosystem พร้อม | ข้อมูลรูปร่างเปลี่ยนบ่อย, event/log, prototype เร็ว |
| ข้อควรระวัง | ตั้งค่า tuning มีรายละเอียดเยอะ | feature ขั้นสูงบางอย่างตามหลัง | ต้องมีวินัย schema ด้วยตัวเอง |

**ห้ามตอบว่า "PostgreSQL ดีกว่า MySQL"** ให้ตอบว่า "PostgreSQL ดีกว่าเมื่อต้องการ feature เชิง query ที่ซับซ้อนและ data integrity เข้มข้น ส่วน MySQL ดีกว่าเมื่อทีมคุ้นเคยอยู่แล้วและ workload เป็น web app ทั่วไปที่อ่านหนัก"

### 7.3 ตารางเปรียบเทียบคู่ที่สับสนบ่อย

| คู่ที่สับสน | ต่างกันตรงไหน |
|---|---|
| **Primary Key vs Unique** | PK มีได้ตัวเดียวต่อตาราง + ห้าม NULL / Unique มีได้หลายตัว + NULL ได้ (ตามระบบ) |
| **Primary Key vs Foreign Key** | PK = "ฉันคือใคร" / FK = "ฉันชี้ไปหาใคร" |
| **Index vs Primary Key** | PK สร้าง index ให้อัตโนมัติ แต่ index ทั่วไปไม่ได้บังคับความไม่ซ้ำ |
| **WHERE vs HAVING** | WHERE กรองก่อนรวมกลุ่ม / HAVING กรองหลัง `GROUP BY` |
| **DELETE vs TRUNCATE** | DELETE ลบทีละแถว rollback ได้ / TRUNCATE ล้างทั้งตาราง เร็วกว่า แต่ย้อนยาก |
| **Transaction vs Lock** | Transaction = ขอบเขตของงาน / Lock = กลไกกันคนอื่นแทรกในขอบเขตนั้น |
| **Replication vs Backup** | Replication ก๊อปแบบ real-time (ลบผิดก็ลบตาม!) / Backup คือย้อนเวลาได้ |
| **Replication vs Sharding** | Replication = ก๊อปข้อมูลเดิมหลายชุด (ช่วย read) / Sharding = แบ่งข้อมูลคนละส่วน (ช่วย write + ขนาด) |
| **Connection vs Query** | Connection = ท่อที่เปิดไว้ / Query = สิ่งที่ส่งผ่านท่อ |
| **Vertical vs Horizontal scaling** | เครื่องใหญ่ขึ้น / เครื่องเยอะขึ้น |

## 8. Common Mistakes

| # | สิ่งที่ Junior มักเข้าใจผิด | ความจริง |
|---|---|---|
| 1 | "ใส่ index ทุก column ไว้ก่อน เผื่อได้ใช้" | ทุก index ทำให้ write ช้าลง + กินพื้นที่ + planner สับสน — ใส่ตาม query ที่มีจริง |
| 2 | "มี index แล้ว query ต้องเร็ว" | ถ้า query ครอบ column ด้วยฟังก์ชัน หรือใช้ `LIKE '%x'` index จะไม่ถูกใช้เลย |
| 3 | "query แต่ละตัวเร็วอยู่แล้ว ระบบต้องเร็ว" | N+1: 500 query × 2ms = 1 วินาที ทั้งที่ทุกตัวเร็ว |
| 4 | "ดึงข้อมูลมาทั้งหมดแล้วค่อยกรองใน JavaScript" | โยนงานที่ DB ทำได้ดีกว่ามาให้ app ทำ + ส่งข้อมูลผ่าน network เกินจำเป็น |
| 5 | "`SELECT *` สะดวกดี" | ดึง column ที่ไม่ใช้ = เปลือง I/O + network + ทำให้ covering index ใช้ไม่ได้ |
| 6 | "ORM จัดการให้หมด ไม่ต้องรู้ SQL" | ORM ซ่อน query ไว้ — คนที่ไม่รู้ SQL คือคนที่ debug N+1 ไม่เป็น |
| 7 | "Transaction ใช้กันข้อมูลหาย เลยเปิดคลุมทั้ง request" | Transaction ยาว = lock ค้างนาน = deadlock + throughput ตก ต้องสั้นที่สุด |
| 8 | "เช็คก่อนแล้วค่อยเขียน ปลอดภัยแล้ว" | นี่คือ race condition classic — ระหว่างเช็คกับเขียนมีช่องว่างเสมอ |
| 9 | "Replication = Backup" | ลบข้อมูลผิดที่ primary → replica ลบตามทันที ไม่มีอะไรให้กู้ |
| 10 | "OFFSET กระโดดข้ามไปเลย" | OFFSET ต้องนับผ่านทุกแถวแล้วทิ้ง — หน้าลึกจึงช้า |
| 11 | "เปิด connection ใหม่ทุก request ก็ได้" | handshake + auth แพงกว่าตัว query และจะทำให้ DB connection เต็ม |
| 12 | "NoSQL ไม่มี schema เลยไม่ต้องออกแบบ" | ไม่มี schema ใน DB = schema ย้ายไปอยู่ในโค้ด และไม่มีใครบังคับให้ตรงกัน |
| 13 | "ข้อมูลน้อยตอน dev เลยไม่เห็นปัญหา" | ปัญหา DB เกือบทั้งหมดโผล่เมื่อข้อมูลโต — ต้องทดสอบด้วยขนาดข้อมูลจริง |
| 14 | "JOIN ช้า เลี่ยงดีกว่า ไปวนดึงทีละตัวแทน" | การเลี่ยง JOIN แบบนั้นคือการสร้าง N+1 ซึ่งช้ากว่าหลายเท่า |
| 15 | "Soft delete (`is_deleted`) ปลอดภัยกว่า ใช้ทุกที่เลย" | ต้องจำใส่ `WHERE is_deleted = false` ทุก query ตลอดกาล ลืมครั้งเดียวคือ bug ข้อมูลรั่ว |

## 9. Debugging

### 9.1 Framework: "Database ช้า" ให้ไล่ตามลำดับนี้

```
1. ช้าจริงไหม / ช้าที่ไหน?      → วัดก่อน อย่าเดา (APM, log latency)
        ↓
2. ช้าทุก query หรือบางตัว?     → ทุกตัว = ปัญหาทรัพยากร/connection
        ↓                         บางตัว = ปัญหา query/index
3. ดู slow query log             → หา query ที่ช้าที่สุด + ที่ถูกเรียกบ่อยที่สุด
        ↓
4. นับจำนวน query ต่อ 1 request → query เยอะผิดปกติ = N+1
        ↓
5. EXPLAIN / EXPLAIN ANALYZE    → เห็น Seq Scan บนตารางใหญ่ = ขาด index
        ↓
6. ดู connection pool            → รอคิว = pool เล็กไป หรือ query ค้างไม่ปล่อย
        ↓
7. ดู lock / blocking query      → มี transaction ค้างยาวล็อกคนอื่นอยู่ไหม
        ↓
8. ดู resource ของเครื่อง        → CPU / IO / memory / disk เต็มหรือยัง
```

> **ให้มองภาพนี้ว่า** "ไล่จากภายนอกเข้าสู่ภายใน — ยืนยันว่าช้าจริงก่อน แล้วค่อยแคบลงจาก 'ระบบ' → 'query' → 'แผนการทำงานของ query' → 'ทรัพยากรเครื่อง'"

### 9.2 ตารางอาการ → สาเหตุที่น่าสงสัยที่สุด

| อาการ | สงสัยอะไรก่อน | เช็คยังไง |
|---|---|---|
| หน้า list ช้ามาก แต่ query เดี่ยว ๆ เร็ว | **N+1** | นับ query ต่อ 1 request |
| ช้าตอนข้อมูลเยอะ เร็วตอน dev | **ขาด index / full scan** | `EXPLAIN` ดูว่ามี Seq Scan ไหม |
| หน้าแรกเร็ว หน้าท้าย ๆ ช้า | **Offset pagination ลึก** | ดูค่า OFFSET ใน query |
| request ค้างแล้ว timeout ทั้งระบบ | **Connection pool หมด** | ดู active/idle connection, pool wait time |
| ค้างเป็นช่วง ๆ แล้วหายเอง | **Lock contention / long transaction** | ดู blocking query, transaction ที่เปิดนาน |
| error "deadlock detected" | **ลำดับการ lock ไม่ตรงกัน** | ดู log deadlock ว่า transaction ไหนชนกัน |
| ข้อมูลไม่ตรงหลังกด save | **Replication lag** (อ่านจาก replica) | เช็คว่า read ไปที่ replica ไหม + lag เท่าไร |
| ยอดเงิน/สต็อกไม่ตรง | **Race condition / ไม่มี lock** | หา pattern "อ่าน → คิด → เขียน" ในโค้ด |
| write ช้าลงเรื่อย ๆ ทั้งที่ read ปกติ | **index เยอะเกิน** | นับ index ต่อตาราง ลบตัวที่ไม่ถูกใช้ |
| memory ของ DB พุ่ง | query ดึง row เยอะเกิน / sort ใหญ่ | ดู query ที่ไม่มี LIMIT |

### 9.3 เครื่องมือที่ต้องรู้จัก

| เครื่องมือ | ใช้ดูอะไร |
|---|---|
| `EXPLAIN` / `EXPLAIN ANALYZE` | query planner เลือกทางไหน ใช้ index หรือ scan ทั้งตาราง |
| Slow query log | query ที่เกิน threshold |
| `pg_stat_activity` (PostgreSQL) | ตอนนี้มี query อะไรรันอยู่ / ค้างอยู่ |
| `SHOW PROCESSLIST` (MySQL) | เช่นเดียวกัน |
| Connection pool metrics | active / idle / waiting |
| APM / Tracing | เห็น DB span ในบริบทของ request ทั้งเส้น |

**คำที่ต้องอ่านออกใน EXPLAIN:**

| คำที่เห็น | แปลว่า |
|---|---|
| Seq Scan / Full Table Scan | อ่านทุกแถว — บนตารางใหญ่คือสัญญาณอันตราย |
| Index Scan | ใช้ index แล้ว ดี |
| Index Only Scan | ตอบได้จาก index ไม่ต้องแตะตารางเลย ดีที่สุด |
| Nested Loop | JOIN แบบวนซ้อน — ระวังเมื่อฝั่งนอกใหญ่ |
| Hash Join / Merge Join | วิธี JOIN ที่เหมาะกับข้อมูลใหญ่ |
| rows=... (estimate ต่างจากจริงมาก) | statistics เก่า planner เลือกผิดได้ |

## 10. Interview Questions

### 🟢 Junior

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| SQL กับ NoSQL ต่างกันยังไง | โครงสร้าง + schema + ความสัมพันธ์ + เลือกตาม use case ไม่ใช่ตาม "ตัวไหนดีกว่า" |
| Primary Key กับ Foreign Key ต่างกันยังไง | PK = ระบุตัวตนของ row / FK = เชื่อมไปตารางอื่น |
| Index คืออะไร | สารบัญ + เร่ง read + **มีต้นทุนที่ write** (ข้อหลังคือตัวแยก junior ที่อ่านมากับที่ท่องมา) |
| JOIN คืออะไร มีกี่แบบ | รวมข้อมูลข้ามตาราง + INNER/LEFT ต่างกันตรงไหน |
| Transaction คืออะไร | ทำทั้งชุดหรือไม่ทำเลย + ยกตัวอย่างโอนเงิน |
| One-to-Many เก็บยังไง | ฝั่ง many ถือ FK |
| ทำไมต้องมี pagination | ไม่ให้ดึงข้อมูลทั้งตาราง — ประหยัด memory/network |

### 🟡 Mid

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| N+1 คืออะไร เจอแล้วแก้ยังไง | อธิบายด้วยตัวอย่าง + **วิธีสังเกต** + แก้ด้วย JOIN/IN/eager loading |
| Index มีข้อเสียอะไรบ้าง | write ช้า, กินพื้นที่, composite index ใช้ได้จากซ้าย, cardinality ต่ำไม่ช่วย |
| Offset vs Cursor pagination | ทั้ง trade-off ครบ: offset ช้าเมื่อลึก + ข้อมูลซ้ำ / cursor เร็วคงที่ แต่ **ข้ามหน้าไม่ได้** |
| ACID คืออะไร | 4 ตัว + ยกตัวอย่างโอนเงินประกอบทุกตัว |
| Race condition ในระบบ DB เกิดยังไง | อธิบาย timeline แบบ t1–t6 ของ lost update |
| Optimistic vs Pessimistic lock | หลักคิด + เลือกตาม contention rate |
| Connection pool คืออะไร ตั้งเท่าไรดี | ทำไมต้องมี + pool × instance ต้องไม่เกิน max_connections |
| Normalization ทำไปทำไม เมื่อไรควร denormalize | ป้องกันข้อมูลขัดแย้ง / denormalize เมื่อวัดแล้วช้าจริง |
| Replication คืออะไร มีปัญหาอะไร | primary/replica + **replication lag** + read-your-own-write |

### 🔴 Senior

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| ระบบขายบัตรคอนเสิร์ต ที่นั่งเดียวห้ามซ้ำ ออกแบบยังไง | unique constraint ที่ DB + lock/atomic update + idempotency + ยอมรับว่า app-level check อย่างเดียวไม่พอ |
| Isolation level มีผลกับระบบยังไง | อธิบาย anomaly แต่ละแบบ + default ของ PG/MySQL ต่างกัน + trade-off กับ throughput |
| Deadlock เกิดจากอะไร ป้องกันยังไง | ลำดับ lock + transaction สั้น + timeout + **retry เพราะกำจัด 100% ไม่ได้** |
| ตารางมี 100 ล้านแถว query ช้า จะทำยังไง | วัดก่อน → EXPLAIN → index → แก้ query → denormalize/ตารางสรุป → partition → archive → read replica (ตามลำดับต้นทุน) |
| จะเพิ่ม column ในตาราง 50 ล้านแถวบน production ยังไง | เพิ่มแบบ nullable/มี default ที่ไม่ rewrite ตาราง → backfill เป็น batch → เปลี่ยน constraint ทีหลัง → มีแผน rollback |
| เลือก SQL หรือ NoSQL สำหรับ feature นี้เพราะอะไร | ตอบจาก access pattern + ความสัมพันธ์ + ความต้องการ consistency ไม่ใช่ตอบจากความชอบ |
| ทำไม read replica ถึงไม่ได้แก้ปัญหา scale ทุกอย่าง | ช่วยแค่ read / write ยังกระจุกที่ primary / มี lag / บาง query ต้องอ่าน primary |

## 11. Answer Like a Developer

### โครงมาตรฐาน 4 จังหวะ (ใช้ได้กับคำถาม database เกือบทุกข้อ)

```
1. นิยามสั้น 1 ประโยค          "X คือ ..."
        ↓
2. ปัญหาที่มันแก้               "มันเกิดมาเพราะ ..."
        ↓
3. ตัวอย่างจากงานจริง           "เช่นตอนที่ระบบ ... เราเจอว่า ..."
        ↓
4. Trade-off / ข้อควรระวัง      "แต่มันแลกมากับ ... เพราะฉะนั้นใช้เมื่อ ..."
```

> **ให้มองภาพนี้ว่า** "คำตอบที่ดีไม่ใช่นิยามที่ถูกต้อง แต่คือนิยาม + เหตุผลที่มันมีอยู่ + ราคาที่ต้องจ่าย — สามอย่างนี้คือสิ่งที่แยก Mid ออกจาก Junior"

### ตัวอย่างการตอบ: "Index คืออะไร"

**❌ คำตอบระดับท่องจำ:** "Index คือโครงสร้างข้อมูลที่ทำให้ query เร็วขึ้นครับ"

**✅ คำตอบระดับที่อยากได้:**
> "Index คือสารบัญของตารางครับ — แทนที่ database จะอ่านทุกแถวเพื่อหาอันเดียว มันเปิดสารบัญที่เรียงไว้แล้วกระโดดไปหาได้เลย
> มันเกิดมาเพราะพอตารางโตถึงหลักล้านแถว การ scan ทั้งตารางแพงเกินจะทำต่อ request
> ที่งานเก่าผมเจอหน้า search ที่ช้าขึ้นเรื่อย ๆ พอ EXPLAIN ดูก็เห็น Seq Scan บนตาราง 8 ล้านแถว พอเพิ่ม index ที่ column ที่ใช้ filter ก็ลงมาเหลือหลักสิบ ms
> แต่ index ไม่ฟรีครับ ทุก insert/update ต้องอัปเดต index ด้วย เลยทำให้ write ช้าลงและกินพื้นที่เพิ่ม ผมเลยจะสร้าง index จาก query ที่ใช้จริงใน production ไม่ใช่สร้างเผื่อไว้ทุก column"

### ตัวอย่างการตอบคำถาม Race Condition (แบบเล่าเป็นเหตุการณ์)

> "สมมติสินค้าเหลือ 1 ชิ้น มีคนกดซื้อพร้อมกัน 2 คน ทั้งคู่อ่าน stock ได้ 1 เท่ากัน ทั้งคู่เช็คผ่าน แล้วทั้งคู่เขียน stock = 0 ผลคือขายของชิ้นเดียวให้สองคน
> รากของปัญหาคือ 'อ่าน–ตัดสินใจ–เขียน' ไม่ได้เป็น atomic ระหว่างสามขั้นนั้นมีช่องให้คนอื่นแทรกได้
> วิธีที่ผมใช้คือให้ database เป็นคนตัดสิน เช่น `UPDATE stock = stock - 1 WHERE id = ? AND stock >= 1` แล้วดูว่าอัปเดตได้กี่แถว ถ้า 0 แปลว่าของหมด
> ถ้า logic ซับซ้อนกว่านั้นก็จะใช้ `SELECT FOR UPDATE` แต่ต้องระวัง deadlock กับ transaction ที่ยาวเกินไปครับ"

### คำพูดที่ทำให้ดูมีประสบการณ์ (ใช้ได้จริง ไม่ใช่ท่อง)

| สถานการณ์ | พูดแบบนี้ |
|---|---|
| ถูกถามว่าจะ optimize ยังไง | "ผมจะวัดก่อนว่าช้าตรงไหนจริง ๆ ก่อนจะแก้ เพราะเดาผิดแล้วแก้ผิดจุดเสียเวลากว่า" |
| ถูกถามให้เลือก technology | "ขึ้นกับ access pattern ครับ ถ้า... ผมจะเลือก... เพราะ..." |
| ไม่เคยใช้ tool ที่เขาถาม | "ผมยังไม่เคยใช้ตัวนั้นครับ แต่หลักการเดียวกับ... ที่ผมเคยใช้คือ..." |
| ถูกถามเรื่อง trade-off | "มันแลกกันระหว่าง... กับ... ในเคสนี้ผมให้น้ำหนัก... เพราะ..." |

## 12. One-Minute Review

อ่านรอบเดียวก่อนเข้าห้องสัมภาษณ์:

- **Database = สมุดบัญชีที่มีคนแย่งกันเขียน** ทุก feature เกิดจากการแก้ปัญหานี้
- **SQL** = schema แน่น มีความสัมพันธ์ชัด JOIN ได้ / **NoSQL** = ยืดหยุ่น เก็บเป็นก้อน scale แนวนอนง่าย — เลือกตาม access pattern ไม่ใช่ตามความชอบ
- **PK** = ฉันคือใคร / **FK** = ฉันชี้ไปใคร / **N:M ต้องมีตารางกลางเสมอ** / ฝั่ง many ถือ FK
- **Index = สารบัญ** เร่ง read แต่ **ทำให้ write ช้าลงและกินพื้นที่** — สร้างตาม query จริง
- **N+1** = ดึง list 1 ครั้งแล้วยิงเพิ่มทีละแถว สังเกตจาก "query เดิมซ้ำ ๆ" และ latency ที่โตตามจำนวนแถว — แก้ด้วย JOIN / IN / eager loading
- **Offset** = กระโดดหน้าได้แต่หน้าลึกช้าและข้อมูลอาจซ้ำ / **Cursor** = เร็วคงที่และไม่ซ้ำ แต่**ข้ามหน้าไม่ได้**
- **Transaction** = ทำทั้งชุดหรือไม่ทำเลย / **ACID** = Atomicity, Consistency, Isolation, Durability (นึกภาพโอนเงิน)
- **Isolation** = ปุ่มหมุนแลกความเร็วกับความถูกต้อง: Dirty / Non-repeatable / Phantom / Lost update
- **Race Condition** = อ่าน–คิด–เขียน ไม่ atomic → **Pessimistic lock** (ชนบ่อย/เสียหายสูง) vs **Optimistic lock** (ชนน้อย/อยากได้ throughput)
- **Deadlock** = ล็อกคนละลำดับ ป้องกันด้วยลำดับเดียวกัน + transaction สั้น + timeout + retry
- **Connection Pool** = โต๊ะที่เปิดค้างไว้ pool × instance ต้องไม่เกิน max_connections
- **Normalization** = ไม่เก็บซ้ำเพื่อกันข้อมูลขัดแย้ง / **Denormalize** เมื่อวัดแล้วช้าจริง
- **Replication** = primary เขียน replica อ่าน มี **lag** และ **ไม่ใช่ backup**
- ระบบช้า: **วัดก่อน → EXPLAIN → นับ query ต่อ request → ดู pool → ดู lock → ดู resource**

## 13. Memory Card

### จำ 5 อย่างนี้พอ

1. **Database คือสมุดบัญชีที่มีคนแย่งกันเขียน** — ทุกเรื่องแตกจาก "เก็บถาวร / ค้นให้เร็ว / ถูกต้องแม้พร้อมกัน"
2. **Index = สารบัญ — เร่ง read แต่ทำให้ write ช้าและกินพื้นที่** อย่าใส่ทุก column
3. **N+1 คือคูณจำนวน round-trip ไม่ใช่ query ช้า** — สังเกตจาก query เดิมซ้ำ ๆ และ latency โตตามจำนวนแถว
4. **Offset ลึกแล้วช้าและข้อมูลอาจซ้ำ / Cursor เร็วคงที่แต่ข้ามหน้าไม่ได้**
5. **Race condition แก้ที่ database ไม่ใช่แก้ที่ if ในโค้ด** — atomic update / pessimistic / optimistic lock
