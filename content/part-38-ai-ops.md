## 1. Big Picture

ลองนึกภาพนี้

ทีมคุณทำ chatbot ตอบคำถามลูกค้า demo วันศุกร์ผ่านสวยมาก ทุกคนปรบมือ
เปิดให้ลูกค้าจริงใช้วันจันทร์ ผ่านไปหนึ่งเดือน:

- **ฝ่ายการเงินส่งบิลมา** — แพงกว่าที่ประเมินไว้ 6 เท่า
- **ผู้ใช้บ่น** — "รอนานจนนึกว่าค้าง" (แต่ตอน demo มันเร็ว)
- **ช่วงบ่ายวันพุธระบบตอบ error รัว ๆ** — ไม่มีใครรู้ว่าเพราะ provider ล่ม หรือเราโดน rate limit
- **สัปดาห์ถัดมาคำตอบแย่ลง** — ไม่มีใครแก้ prompt เลย แต่ provider อัปเดต model เงียบ ๆ
- **มีคนแอบใช้ bot ของเราเขียนการบ้าน** วันละหลายพันข้อความ บน quota ของบริษัท

**ไม่มีข้อไหนเลยที่เป็นปัญหาของ "prompt ไม่ดี"** ทั้งหมดคือปัญหาของ **การรันระบบ** ที่มีชิ้นส่วนสำคัญที่สุดเป็น API ภายนอกซึ่ง:

1. **คิดเงินทุกครั้งที่เรียก ตามจำนวน token** — ไม่เหมือน DB query ที่ต้นทุนแทบเป็นศูนย์ต่อครั้ง
2. **ช้าในระดับวินาที ไม่ใช่มิลลิวินาที** — และยิ่งตอบยาวยิ่งช้า
3. **ผลลัพธ์ไม่แน่นอน (non-deterministic)** — input เดิม คำตอบอาจไม่เหมือนเดิม
4. **เราไม่ได้เป็นเจ้าของ** — มี rate limit, ล่มได้, เปลี่ยนพฤติกรรมได้โดยเราไม่ได้แก้โค้ดสักบรรทัด

**AI Ops → การดูแล feature ที่ใช้ LLM ใน production → ให้ต้นทุนคุมได้ ความเร็วรับได้ ทนต่อความล้มเหลวของ provider และมองเห็นคุณภาพที่เปลี่ยนไปตามเวลา**

chapter นี้แบ่งเป็น 3 เรื่องใหญ่ ตรงกับ tagline ของมัน:

| เรื่องใหญ่ | ตอบคำถาม | หัวข้อในบท |
|---|---|---|
| **Cost** | จ่ายเท่าไร ทำไมแพง ลดยังไง | Token, billing, prompt caching, response caching, batch, budget guard, quota |
| **Routing** | ส่งงานไปที่ไหน ถ้าพังไปทางไหน | Model routing, cascade, fallback, rate limit, retry, timeout, gateway |
| **Monitoring** | รู้ได้ยังไงว่ายังดีอยู่ | Trace ต่อ step, token/cost ต่อ request, latency percentile, eval, drift, versioning, PII, security |

> **ให้มองภาพนี้ว่า** "LLM คือ dependency ภายนอกที่ช้า แพง ไม่แน่นอน และเปลี่ยนเองได้ — งาน AI Ops คือเอาหลักการเดิมของ backend (cache, retry, timeout, observability) มาใช้กับ dependency ที่ประหลาดที่สุดที่คุณเคยเจอ"

ประโยคที่ต้องจำไปห้องสัมภาษณ์:

> **"Demo วัดว่ามันตอบถูกไหม Production วัดว่ามันตอบถูกทุกวัน ในราคาที่จ่ายไหว และรู้ตัวเมื่อมันเริ่มไม่ถูก"**

## 2. Keywords

### 2.1 Token & Cost

| Keyword | ภาษาคน | จำสั้น ๆ |
|---|---|---|
| Token | ชิ้นส่วนของข้อความที่ model อ่าน/เขียน | หน่วยนับเงินและนับความยาว |
| Tokenizer | ตัวหั่นข้อความเป็น token | แต่ละ model หั่นไม่เหมือนกัน |
| Input Token | token ที่เราส่งเข้าไป (prompt + context + history) | ขาเข้า ราคาถูกกว่า |
| Output Token | token ที่ model เขียนตอบ | ขาออก ราคาแพงกว่า + ช้ากว่า |
| Cached Input | input ส่วนที่ provider จำไว้แล้วจากครั้งก่อน | ส่งซ้ำ จ่ายถูกลง |
| Context Window | จำนวน token สูงสุดที่ส่งได้ใน 1 ครั้ง | โต๊ะทำงานมีขนาดจำกัด |
| Max Output Tokens | เพดานความยาวคำตอบ | กันบิลบาน + กันรอนาน |
| Unit Economics | ต้นทุนต่อ user / ต่อ feature เทียบกับรายได้ | feature นี้คุ้มไหม |

### 2.2 Latency & UX

| Keyword | ภาษาคน | จำสั้น ๆ |
|---|---|---|
| TTFT (Time to First Token) | เวลาจนเห็นคำแรก | ความรู้สึกว่า "มันเริ่มแล้ว" |
| Tokens per Second (TPS) | ความเร็วในการพิมพ์ของ model | ความยาว ÷ TPS = เวลาที่เหลือ |
| Total Latency | เวลาทั้งหมดจนตอบจบ | TTFT + (output ÷ TPS) |
| Streaming | ส่งคำตอบทีละส่วนระหว่างที่ยังคิดอยู่ | ไม่ได้เร็วขึ้น แต่รู้สึกเร็วขึ้น |
| Latency Percentile (p50/p95/p99) | เวลาของคนส่วนใหญ่ vs คนที่โชคร้าย | ดู p95 ไม่ใช่ average |

### 2.3 Caching & Batching

| Keyword | ภาษาคน | จำสั้น ๆ |
|---|---|---|
| Prompt Caching | provider จำส่วนต้นของ prompt ที่ซ้ำกันไว้ | ของนิ่งไว้ข้างหน้า |
| Cache Prefix | ส่วนต้นของ prompt ที่ต้องเหมือนกันเป๊ะถึงจะ hit | เปลี่ยน 1 ตัวอักษร = miss |
| Response Cache | เราเก็บคำตอบไว้ตอบซ้ำเอง | คำถามเดิม ไม่ต้องเรียก model |
| Semantic Cache | ตอบซ้ำถ้าคำถาม "ความหมายใกล้กัน" | ประหยัดมาก แต่เสี่ยงตอบผิดคน |
| Batch API | ส่งงานกองใหญ่ ให้ทำเสร็จทีหลัง | ช้าแต่ถูก เหมาะกับงาน offline |

### 2.4 Routing & Reliability

| Keyword | ภาษาคน | จำสั้น ๆ |
|---|---|---|
| Model Routing | เลือก model ตามชนิดงาน | งานง่ายไม่ต้องใช้ตัวแพง |
| Cascade | ลองตัวถูกก่อน ไม่มั่นใจค่อยส่งต่อตัวแพง | บันไดจากถูกไปแพง |
| Fallback | ตัวหลักพัง สลับไปตัวสำรอง | ยางอะไหล่ |
| Rate Limit (RPM / TPM) | เพดานคำขอต่อนาที / token ต่อนาที | ท่อมีขนาดจำกัด |
| 429 Too Many Requests | provider บอกว่าเรายิงเกินเพดาน | ช้าลงแล้วลองใหม่ |
| Exponential Backoff + Jitter | รอนานขึ้นเรื่อย ๆ แบบสุ่มนิดหน่อยก่อน retry | อย่ารุมกันกลับมาพร้อมกัน |
| Idempotency Key | รหัสบอกว่า "งานนี้คืองานเดิม" | retry แล้วไม่ทำซ้ำ/ไม่คิดเงินซ้ำ |
| Timeout | เวลารอสูงสุดก่อนยอมแพ้ | อย่ารอตลอดกาล |
| Circuit Breaker | พังบ่อยเกิน ตัดทิ้งชั่วคราว | เบรกเกอร์ไฟบ้าน |
| AI Gateway | ชั้นกลางระหว่าง app กับ provider ทุกเจ้า | จุดเดียวคุม key/log/quota/routing |

### 2.5 Context & Budget

| Keyword | ภาษาคน | จำสั้น ๆ |
|---|---|---|
| Context Trimming | ตัด history เก่าทิ้ง | เก็บแค่ที่จำเป็น |
| Conversation Summarization | ย่อ history เก่าเป็นสรุปสั้น | จดโน้ตแทนอัดเสียงทั้งหมด |
| Budget Guard | ด่านหยุดเมื่อค่าใช้จ่ายเกินเพดาน | ฟิวส์ค่าไฟ |
| Per-tenant Quota | เพดานการใช้ต่อลูกค้า/องค์กร | ลูกค้าคนเดียวอย่ากินของทุกคน |

### 2.6 Monitoring, Quality & Safety

| Keyword | ภาษาคน | จำสั้น ๆ |
|---|---|---|
| LLM Trace | ร่องรอยทุก step ของ 1 คำขอ (retrieve → prompt → call → tool) | PART 23 ฉบับ LLM |
| Eval / Eval Score | ชุดทดสอบวัดคุณภาพคำตอบ | unit test ของ prompt |
| LLM-as-Judge | ให้ model อีกตัวให้คะแนนคำตอบ | ถูกและเร็ว แต่ต้องสอบเทียบกับคน |
| User Feedback Signal | 👍/👎, กด regenerate, copy, ถามซ้ำ | เสียงจริงจากหน้างาน |
| Model Drift | พฤติกรรม model เปลี่ยนตามเวลา | ไม่ได้แก้โค้ด แต่ผลเปลี่ยน |
| Regression | ของที่เคยดี กลับแย่ลงหลังเปลี่ยนอะไรบางอย่าง | ต้องมี eval ก่อนถึงจะรู้ |
| Model Pinning | ล็อกเวอร์ชัน model ที่ใช้ | ไม่ให้เปลี่ยนเองใต้เท้าเรา |
| Prompt Versioning | ให้ prompt มีเลขเวอร์ชันเหมือนโค้ด | prompt คือ code |
| Canary / A/B Rollout | ปล่อย prompt/model ใหม่ให้คนส่วนน้อยก่อน | ลองน้ำก่อนกระโดด |
| PII Redaction | ลบ/ปิดข้อมูลส่วนบุคคลก่อนส่งหรือก่อน log | ไม่ส่ง ไม่เก็บ ไม่รั่ว |
| Data Retention | provider/เราเก็บข้อมูลไว้นานเท่าไร | ตั้งค่าให้รู้ อย่าเดา |
| Prompt Injection | ข้อความที่พยายามสั่ง model ให้ทำนอกคำสั่งเรา | SQL injection ของยุค LLM |
| Abuse Monitoring | จับการใช้งานผิดวัตถุประสงค์ | ใครใช้ bot เราทำอย่างอื่น |

## 3. Mental Model

### Mental Model #1 — LLM คือ "ฟรีแลนซ์คิดค่าจ้างต่อคำ ที่อยู่ต่างประเทศ"

ลองมอง model เป็นฟรีแลนซ์เก่งมากคนหนึ่ง:

- **คิดเงินตามจำนวนคำ** ทั้งคำที่เราเขียนบรีฟส่งไป (input) และคำที่เขาเขียนกลับมา (output) — **คำที่เขาเขียนแพงกว่าคำที่เขาอ่าน**
- **อยู่ไกล** — ส่งงานไปต้องรอ และยิ่งสั่งให้เขียนยาวยิ่งรอนาน
- **รับงานได้จำกัดต่อนาที** — ส่งพร้อมกันเยอะ เขาจะตอบว่า "ตอนนี้ไม่ว่าง" (429)
- **บางวันไม่สบาย** (provider ล่ม) — ต้องมีฟรีแลนซ์สำรอง
- **ไปเรียนคอร์สใหม่มา** (model update) — ลายมือเปลี่ยน บางงานดีขึ้น บางงานแย่ลง
- **ทุกอย่างที่เราส่งไป เขาเห็นหมด** — ข้อมูลลูกค้าที่ไม่จำเป็น อย่าแนบไป

ทุกหัวข้อของบทนี้คือการจัดการฟรีแลนซ์คนนี้ให้คุ้มค่าจ้าง

### Mental Model #2 — สามเส้นที่ดึงกันเสมอ: Cost · Latency · Quality

```
                QUALITY
                  ▲
                 / \
                /   \
               /     \
              /       \
   COST  ◀───────────────▶  LATENCY
```

- ใช้ model ใหญ่ขึ้น → quality ขึ้น แต่ cost และ latency ขึ้น
- ใส่ context เยอะขึ้น → quality อาจขึ้น แต่ cost ขึ้น และ TTFT ช้าลง
- cache เยอะขึ้น → cost และ latency ลง แต่เสี่ยงตอบคำตอบเก่า/ผิดบริบท (quality ลง)

> **ให้มองภาพนี้ว่า** "ทุกการตัดสินใจใน AI Ops คือการเลื่อนจุดในสามเหลี่ยมนี้ — ไม่มีปุ่มไหนที่ดีขึ้นทุกด้านฟรี ๆ ถ้ามีคนบอกว่ามี แปลว่าเขายังไม่ได้วัด"

### Mental Model #3 — ทุก optimization ต้องเริ่มจาก "วัดเป็น token"

Junior คิดเป็น "จำนวน request" — "วันละ 10,000 request ไม่เยอะหรอก"
Senior คิดเป็น **token × ราคา × จำนวน** — "10,000 request × 8,000 input token × ... = เท่าไรต่อเดือน"

```
ต้นทุน = (input tokens × ราคา input)
       + (cached tokens × ราคา cached)
       + (output tokens × ราคา output)
```

request เดียวกันอาจถูกกว่ากัน 20 เท่า ขึ้นกับว่า prompt ยาวเท่าไร ใช้ model ไหน และ cache hit ไหม

### Mental Model #4 — Prompt และ Model คือ "code ที่ deploy ได้"

ถ้าเปลี่ยน SQL query แล้วไม่ test ไม่ review ไม่มี version → ทุกคนรู้ว่าอันตราย
แต่หลายทีม **แก้ prompt ตรงใน production โดยไม่มีใครรู้** ทั้งที่ผลกระทบแรงพอกัน

ให้ถือกฎนี้: **prompt, model version, temperature, tool list = config ที่ต้อง version, test (eval), rollout, rollback ได้** (ดู PART 15 CI/CD)

## 4. 🧠 ภาพจำ

```
🧠 ภาพจำ:
Token            = คำที่ฟรีแลนซ์คิดเงิน (คำที่เขาเขียนแพงกว่าคำที่เขาอ่าน)
Context Window   = ขนาดโต๊ะทำงาน วางเอกสารได้จำกัด
Prompt Caching   = บรีฟมาตรฐานที่ฟรีแลนซ์จำได้แล้ว ส่งซ้ำคิดถูกลง
Response Cache   = คำตอบเก่าที่เราถ่ายเอกสารเก็บไว้เอง
Semantic Cache   = "คำถามคล้าย ๆ กัน ใช้คำตอบเดิมไปก่อน" (ระวังคล้ายแต่ไม่เหมือน)
Batch API        = ส่งงานกองใหญ่ทางไปรษณีย์ ช้าแต่ค่าส่งถูก
Routing          = พนักงานต้อนรับคัดว่าเคสนี้ให้เด็กฝึกงานหรือผู้เชี่ยวชาญ
Cascade          = ให้เด็กฝึกงานลองก่อน ไม่มั่นใจค่อยยกให้หัวหน้า
Fallback         = ยางอะไหล่
Rate Limit       = ท่อน้ำขนาดจำกัด
Budget Guard     = ฟิวส์ ตัดไฟก่อนบิลไหม้บ้าน
Eval             = ข้อสอบมาตรฐานที่ใช้วัดทุกครั้งที่เปลี่ยน prompt/model
Drift            = ฟรีแลนซ์คนเดิมแต่ลายมือเปลี่ยน
Gateway          = แผนกจัดซื้อกลาง ทุกคนต้องสั่งงานผ่านที่นี่
```

### ภาพจำเจาะลึก: Output แพงกว่าและช้ากว่า Input (ข้อนี้ต้องจำให้แม่นที่สุด)

```
INPUT  (อ่าน)   : model อ่านทุก token "พร้อมกัน" เป็นก้อน   → เร็ว, ราคาต่อ token ต่ำกว่า
OUTPUT (เขียน)  : model เขียนทีละ token ต่อกันเป็นลำดับ    → ช้า, ราคาต่อ token สูงกว่า
                  token ถัดไปต้องรอ token ก่อนหน้าเสร็จก่อน
```

> 🧠 ภาพจำ: "อ่านหนังสือ 10 หน้ากวาดตาทีเดียวได้ แต่เขียนเรียงความ 10 หน้าต้องเขียนทีละคำ — เพราะงั้นการสั่งให้ตอบสั้นลง ช่วยทั้งเงินและเวลาพร้อมกัน"

ผลที่ตามมาในงานจริง:

| ถ้าคุณ... | ผลต่อ cost | ผลต่อ latency |
|---|---|---|
| ตัด system prompt ลงครึ่งหนึ่ง | ลดพอสมควร | TTFT ดีขึ้นนิดหน่อย |
| ตัด output จาก 800 เหลือ 300 token | **ลดเยอะ** (เพราะ output แพง) | **ลดเยอะมาก** (เพราะ output คือส่วนที่ช้า) |
| ใส่ RAG context 20 ชิ้นแทน 5 ชิ้น | input เพิ่มหลายเท่า | TTFT ช้าลง |
| เปิด prompt caching | ส่วนที่ hit ถูกลงมาก | TTFT มักดีขึ้น |

**ประโยคที่ต้องพูดได้ใน interview:**
"ถ้าอยากลดทั้งเงินและเวลาในครั้งเดียว ให้ดูที่ output length ก่อน เพราะ output ทั้งแพงกว่าต่อ token และเป็นส่วนที่ต้องสร้างทีละ token"

## 5. How It Works

### 5.1 Token คืออะไร และทำไมภาษาไทยแพงกว่า

model ไม่ได้อ่าน "ตัวอักษร" หรือ "คำ" แต่อ่าน **token** — ชิ้นส่วนที่ tokenizer หั่นไว้จากสถิติของข้อมูลที่ใช้ train

```
ภาษาอังกฤษ:  "Please reset my password"
              [Please][ reset][ my][ password]          ≈ 4 tokens (ตัวอย่างสมมติ)

ภาษาไทย:     "กรุณารีเซ็ตรหัสผ่านให้หน่อย"
              [กร][ุณ][า][รี][เซ็ต][รห][ัส][ผ่าน][ให้][หน่อย]   ≈ 10 tokens (ตัวอย่างสมมติ)
```

**ทำไมภาษาไทยมักใช้ token มากกว่าสำหรับความหมายเท่ากัน:**

| สาเหตุ | อธิบาย |
|---|---|
| ข้อมูล train ส่วนใหญ่เป็นภาษาอังกฤษ | tokenizer เลยมี "ชิ้นใหญ่" สำหรับคำอังกฤษเยอะ แต่คำไทยถูกหั่นเป็นชิ้นเล็ก |
| ภาษาไทยไม่มีเว้นวรรคระหว่างคำ | ขอบเขตคำไม่ชัด การหั่นจึงไม่ตรงกับคำจริง |
| สระ/วรรณยุกต์เป็นตัวแยก | บางครั้งถูกนับเป็นชิ้นของตัวเอง |

ผลกระทบ: **prompt ภาษาไทยความหมายเท่ากัน อาจใช้ token มากกว่าภาษาอังกฤษหลายเท่า** (ตัวเลขจริงขึ้นกับ tokenizer ของแต่ละ model — ต้องวัดเอง) ซึ่งกระทบทั้ง:

- **ค่าใช้จ่าย** — จ่ายต่อ token
- **latency** — output ไทยยาวเป็น token มากกว่า = พิมพ์นานกว่า
- **context window** — เอกสารไทยกิน "โต๊ะ" เร็วกว่า

**Trade-off ที่พบบ่อย:** เขียน system prompt เป็นภาษาอังกฤษ (ประหยัด token และ model มักทำตามได้ดี) แต่สั่งให้ตอบผู้ใช้เป็นภาษาไทย — ประหยัดฝั่ง input ได้ แต่ต้อง eval ว่าคุณภาพภาษาไทยไม่ตก และ output ภาษาไทยก็ยังแพงเท่าเดิม

> **ให้มองภาพนี้ว่า** "อย่าประเมินต้นทุนจากจำนวนตัวอักษรหรือจำนวนคำ — ให้เอาข้อความจริงของ product คุณไปนับด้วย tokenizer ของ model ที่จะใช้จริง แล้วค่อยคูณ"

### 5.2 Billing ทำงานอย่างไร

```
[1 REQUEST]
    │
    ├── system prompt ─────┐
    ├── tool definitions ──┤
    ├── RAG context ───────┼──→ INPUT TOKENS  ── ส่วนที่ cache hit → ราคา cached (ถูกสุด)
    ├── chat history ──────┤                   └─ ส่วนที่เหลือ     → ราคา input
    └── user message ──────┘
    │
    └── คำตอบของ model ────────→ OUTPUT TOKENS ── ราคา output (แพงสุด)
                                  (รวม "ความคิด"/reasoning ที่ model สร้างด้วย ถ้ามี)
```

สิ่งที่คนมักลืมว่า **นับเป็น input ทุกครั้ง:**

- **chat history ทั้งหมด** — ข้อความที่ 20 ของบทสนทนาต้องส่ง 19 ข้อความก่อนหน้าไปด้วย → ต้นทุนต่อข้อความ **โตขึ้นเรื่อย ๆ** ตามความยาวบทสนทนา
- **tool / function definitions** — schema ของทุก tool ถูกส่งไปทุกครั้ง
- **ผลลัพธ์ของ tool** ใน agent loop (PART 37) — ทุกรอบของ loop ส่ง context สะสมเข้าไปใหม่

และสิ่งที่มักลืมว่า **นับเป็น output:**

- reasoning / thinking token ของ model ที่ "คิดก่อนตอบ" — ผู้ใช้อาจไม่เห็น แต่คุณจ่าย

### 5.3 Latency Anatomy — เวลาหายไปไหน

```
t=0          ผู้ใช้กดส่ง
 │
 ├── [app ของเรา]        auth, โหลด history, RAG retrieve (PART 36)    ~ 50–500 ms
 ├── [network → provider]
 ├── [คิวที่ provider]
 ├── [prefill]           model อ่าน input ทั้งหมด (ยาวมาก = ช้า)
 │
 ├──────────── TTFT ──── เห็นคำแรก ◀── ผู้ใช้รู้สึกว่า "มันเริ่มแล้ว"
 │
 ├── [decode]            เขียนทีละ token ตามความเร็ว TPS
 │                       400 tokens ÷ 50 TPS = 8 วินาที  (ตัวเลขสมมติ)
 │
 └──────────── TOTAL ─── ตอบจบ
```

**สูตรคร่าว ๆ:** `Total ≈ เวลาใน app + TTFT + (output tokens ÷ TPS)`

**ตัวอย่างสมมติ:** TTFT 0.8 วินาที, 50 tokens/วินาที, ตอบ 400 tokens → 0.8 + 8 = **8.8 วินาที**
ถ้าสั่งให้ตอบสั้นเหลือ 150 tokens → 0.8 + 3 = **3.8 วินาที** — ลดเกินครึ่งโดยไม่ต้องเปลี่ยน model

| อยากลด | ทำที่ไหน |
|---|---|
| TTFT | prompt สั้นลง, prompt caching, RAG เร็วขึ้น, เลือก model/region ที่ใกล้ |
| เวลาเขียน | **output สั้นลง**, model ที่ TPS สูงกว่า (มักเป็นตัวเล็ก) |
| ความรู้สึกรอ | streaming, แสดงสถานะ "กำลังค้นเอกสาร..." |
| เวลารวมของ agent | ลดจำนวนรอบ, เรียก tool ขนานกันเมื่อเป็นอิสระต่อกัน |

### 5.4 Streaming — เร็วขึ้นจริงหรือแค่รู้สึก

```
ไม่ streaming:   [.................รอ 8.8s.................][คำตอบทั้งก้อน]
streaming:       [0.8s][คำ][คำ][คำ][คำ][คำ][คำ][คำ]...[จบที่ 8.8s]
```

> **ให้มองภาพนี้ว่า** "Streaming ไม่ได้ทำให้คำตอบเสร็จเร็วขึ้นเลย มันแค่ย้ายเวลารอจาก 8 วินาทีที่หน้าจอนิ่ง ไปเป็น 0.8 วินาทีแล้วเห็นของขยับ — ซึ่งสำหรับมนุษย์ คือคนละโลก"

**Trade-off ของ streaming:**

| ได้ | เสีย |
|---|---|
| perceived latency ดีขึ้นมาก | ต้องจัดการ connection ค้าง / หลุดกลางทาง (SSE / WebSocket — ดู PART 16) |
| ผู้ใช้กดหยุดได้เมื่อได้คำตอบพอแล้ว (ประหยัด output) | **ตรวจคำตอบทั้งก้อนก่อนแสดงไม่ได้** — ถ้าต้องกรองเนื้อหา/validate JSON ต้องออกแบบใหม่ |
| ใช้กับคำตอบยาวได้ดี | retry กลางทางยาก — ผู้ใช้เห็นครึ่งแรกไปแล้ว |
| — | นับ token/cost ต้องรอ event สุดท้าย — ถ้าหลุดกลางทางอาจไม่ได้ usage |

กฎคร่าว ๆ: **คนอ่าน → stream / เครื่องอ่าน (JSON ไปทำงานต่อ) → ไม่ต้อง stream** แต่ต้องมี timeout

### 5.5 ควบคุมความยาว output

output คือส่วนที่ทั้งแพงและช้า จึงเป็นคันโยกที่คุ้มที่สุด:

1. **ตั้ง `max_output_tokens`** เป็นเพดานเสมอ — กันกรณี model พูดวนไม่จบ
2. **สั่งรูปแบบใน prompt** — "ตอบไม่เกิน 3 bullet", "ตอบเป็น JSON ตาม schema นี้เท่านั้น"
3. **ใช้ structured output** — ไม่มีคำเกริ่น ไม่มี "แน่นอนครับ! ยินดีช่วย..."
4. **ตรวจ finish reason** — ถ้าหยุดเพราะชนเพดาน แปลว่าคำตอบถูกตัดกลางทาง ต้องจัดการ (อย่าส่ง JSON ครึ่งก้อนไป parse)

⚠️ **ระวัง:** ตั้งเพดานต่ำเกินไป = คำตอบถูกตัดกลางประโยค ผู้ใช้เห็นของขาด ๆ — ต้อง monitor สัดส่วน request ที่ชนเพดาน

### 5.6 Prompt Caching — เอาของนิ่งไว้ข้างหน้า

provider หลายเจ้าจำ **ส่วนต้น (prefix)** ของ prompt ที่ส่งซ้ำไว้ได้ ครั้งต่อไปที่ prefix เหมือนเดิมเป๊ะ จะคิดราคาส่วนนั้นถูกลงมาก และมักเร็วขึ้นด้วย

```
❌ ลำดับที่ cache แทบไม่เคย hit:
[วันที่เวลาปัจจุบัน][ชื่อ user][system prompt 2,000 tok][tools][history][คำถาม]
  ↑ เปลี่ยนทุกครั้ง → prefix ไม่เคยเหมือนเดิม → miss ทั้งหมด

✅ ลำดับที่ cache hit ได้:
[system prompt 2,000 tok][tools][เอกสารอ้างอิงคงที่] | [history][ชื่อ user][เวลา][คำถาม]
 └──────────── ของนิ่ง → cache ได้ ────────────┘   └───── ของเปลี่ยน ─────┘
```

> **ให้มองภาพนี้ว่า** "Cache จับแค่ส่วนหัวที่เหมือนกันเป๊ะตั้งแต่ตัวแรก — ใส่ของที่เปลี่ยนทุกครั้ง (เวลา, ชื่อ, id) ไว้ข้างหน้าเมื่อไร ทุกอย่างข้างหลังก็ cache ไม่ได้ทันที"

**สิ่งที่ต้องรู้เพิ่ม:**

| ประเด็น | สาระ |
|---|---|
| ต้องเหมือนเป๊ะ | เว้นวรรคเกิน 1 ตัว, ลำดับ tool สลับ, JSON key เรียงไม่เหมือนเดิม = miss |
| มีอายุ | cache หมดอายุเองถ้าไม่ถูกใช้สักพัก — traffic น้อยอาจ hit ยาก |
| บางเจ้าคิดค่าเขียน cache | ครั้งแรกอาจแพงกว่าปกตินิดหน่อย คุ้มเมื่อถูกใช้ซ้ำหลายครั้ง |
| วัดได้ | response มักบอกจำนวน cached tokens — **ต้อง log แล้วดู hit rate** ไม่ใช่เดาว่าได้ผล |

### 5.7 Response Cache และ Semantic Cache — ประหยัดสุด แต่เสี่ยงสุด

```
[คำถามเข้ามา]
     ↓
exact match?  ── hit ──→ ตอบจาก cache (ไม่เรียก model เลย: cost ≈ 0, latency ต่ำมาก)
     ↓ miss
semantic match (embedding ใกล้กันเกิน threshold)? ── hit ──→ ตอบจาก cache
     ↓ miss
เรียก model → เก็บคำตอบลง cache (พร้อม key ที่ถูกต้อง + TTL)
```

**ความเสี่ยงที่ต้องพูดได้ (ข้อนี้แยก Junior กับ Senior):**

| ความเสี่ยง | ตัวอย่าง | ป้องกัน |
|---|---|---|
| **ข้อมูลรั่วข้ามคน** | "ยอดค้างของฉันเท่าไร" ของ user A ถูกตอบให้ user B | ใส่ user/tenant/สิทธิ์ ใน cache key, ไม่ cache คำตอบที่มีข้อมูลส่วนตัว |
| **คล้ายแต่ความหมายตรงข้าม** | "ยกเลิก order ได้ไหม" vs "ยกเลิก order ไม่ได้เพราะอะไร" | threshold เข้ม, ใช้เฉพาะ FAQ ที่ควบคุมได้ |
| **คำตอบเก่า** | นโยบายคืนเงินเปลี่ยนแล้ว cache ยังตอบแบบเดิม | TTL + invalidate เมื่อเอกสารต้นทางเปลี่ยน (PART 16) |
| **cache คำตอบที่ผิด** | ตอบผิดครั้งเดียว ถูกเสิร์ฟซ้ำเป็นพันครั้ง | ไม่ cache คำตอบที่ได้ 👎 / eval ต่ำ |
| **ปิดความหลากหลาย** | งานสร้างสรรค์ผู้ใช้อยากได้คำตอบใหม่ | ไม่ใช้กับงาน creative |

**หลักปฏิบัติ:** exact cache สำหรับงาน deterministic (เช่น แปลข้อความเดิม, สรุปเอกสารเดิม) ใช้ได้ค่อนข้างปลอดภัย / semantic cache ใช้กับ **คำถามสาธารณะที่ไม่มีบริบทส่วนตัว** เท่านั้น

### 5.8 Batch API — งานที่ไม่ต้องรีบ อย่าจ่ายราคาด่วน

```
ONLINE (real-time):   user รออยู่ → ต้องตอบในไม่กี่วินาที → ราคาปกติ + ติด rate limit
OFFLINE (batch):      ส่งงาน 50,000 ชิ้นเป็นไฟล์ → provider ทำเสร็จภายในหลายชั่วโมง
                      → มักได้ราคาถูกกว่า + ไม่แย่ rate limit กับ traffic จริง
```

**เหมาะกับ:** จัดหมวด ticket เก่าทั้งหมด, สร้าง embedding เอกสารทั้งคลัง, สรุปรีวิวรายคืน, รัน eval suite
**ไม่เหมาะกับ:** อะไรก็ตามที่มีคนรออยู่หน้าจอ

**Trade-off:** ถูกกว่าและไม่กิน quota ช่วงกลางวัน แต่ **ไม่รู้ว่าเสร็จเมื่อไรแน่** ต้องมีระบบรับผล, จัดการชิ้นที่ fail, และ idempotency (ส่งซ้ำแล้วไม่ทำซ้ำ) — คล้าย background job ใน PART 16

### 5.9 Model Routing & Cascade

**Routing** — ตัดสินใจล่วงหน้าว่างานไหนไปตัวไหน

```
[request]
    ↓
[ROUTER]  (กฎง่าย ๆ / classifier ตัวเล็ก)
    ├── จัดหมวด, ดึงข้อมูลจากข้อความ, ตอบ FAQ    → SMALL model (ถูก เร็ว)
    ├── สรุปเอกสารยาว, เขียนตอบลูกค้า              → MEDIUM model
    └── วิเคราะห์ซับซ้อน, วางแผนหลายขั้น            → LARGE model (แพง ช้า)
```

**Cascade** — ลองตัวถูกก่อน ไม่ผ่านค่อยขยับขึ้น

```
[request] → SMALL ──→ ตรวจคำตอบ ── ผ่าน ──→ ส่งผู้ใช้  (ส่วนใหญ่จบตรงนี้)
                          │
                       ไม่ผ่าน (JSON ไม่ valid / confidence ต่ำ / validator ตก)
                          ↓
                        LARGE ──→ ส่งผู้ใช้
```

> **ให้มองภาพนี้ว่า** "Cascade คือให้เด็กฝึกงานรับเคสก่อน ถ้าเขาตอบได้มั่นใจก็จบ ถ้าไม่มั่นใจค่อยยกให้หัวหน้า — ประหยัดได้เยอะเมื่อเคสส่วนใหญ่ง่าย แต่เคสยากจะจ่ายสองต่อและรอนานขึ้น"

**สัญญาณ "ไม่มั่นใจ" ที่ใช้ได้จริง:** output ไม่ตรง schema, validator ทาง business ไม่ผ่าน, model ตอบว่าไม่รู้, คะแนนจาก judge ตัวเล็กต่ำ, คำถามอยู่นอกหมวดที่ตัวเล็กเคยทำได้ดี

| ประเด็น | Routing | Cascade |
|---|---|---|
| ตัดสินใจเมื่อไร | ก่อนเรียก | หลังเห็นผลของตัวถูก |
| เคสยาก | จ่ายครั้งเดียว | **จ่ายสองครั้ง + รอนานขึ้น** |
| ต้องมี | ตัวจัดหมวดที่แม่น | ตัวตรวจคุณภาพคำตอบที่เชื่อได้ |
| คุ้มเมื่อ | รู้ชนิดงานชัดตั้งแต่ต้น | งานส่วนใหญ่ง่าย มีส่วนน้อยที่ยาก |

### 5.10 Fallback, Rate Limit, Retry, Timeout

```
[call primary provider]
      │
      ├── สำเร็จ ─────────────────────────────→ จบ
      ├── 429 (rate limit) ─→ backoff + jitter → retry (จำกัดจำนวนครั้ง)
      ├── 5xx / timeout ─────→ retry 1–2 ครั้ง ──→ ยังพัง → FALLBACK provider/model สำรอง
      ├── 400 (prompt ผิด / ยาวเกิน context) ─→ **ห้าม retry** แก้ที่ request
      └── circuit เปิดอยู่ (พังต่อเนื่อง) ─→ ข้าม primary ไป fallback ทันที
```

**Rate limit มี 2 มิติ (ต้องพูดได้ทั้งคู่):**

| มิติ | ความหมาย | ชนเมื่อ |
|---|---|---|
| RPM (requests per minute) | จำนวนครั้งที่เรียก | request เล็กแต่ถี่ |
| TPM (tokens per minute) | จำนวน token รวม | request น้อยแต่ prompt ยาวมาก |

ทีมที่ดูแต่ RPM มักงงว่า "ยิงแค่ 20 ครั้งต่อนาที ทำไมโดน 429" — คำตอบคือแต่ละครั้งส่ง context 50,000 token จนชน TPM

**Retry ที่ถูกต้อง (pseudocode):**

```
for attempt in 1..3:
    res = call(model, prompt, timeout=20s, idempotency_key=req_id)
    if res.ok: return res
    if res.status in [400, 401, 403]: raise      ← retry ไปก็ผิดเหมือนเดิม
    if attempt < 3: sleep(res.retry_after or (base * 2^attempt + random_jitter))   ← เคารพ Retry-After ของ 429
return fallback(prompt)
```

**Idempotency สำคัญกว่าที่คิด** — ถ้าการเรียก model ไปสั่งให้ tool ทำอะไรที่มีผลจริง (ส่งอีเมล, สร้าง ticket, คืนเงิน) แล้ว retry → อาจทำซ้ำสองรอบ ต้องใช้ idempotency key ที่ชั้น action ไม่ใช่แค่ชั้นเรียก model (ดู PART 16)

**Timeout ต้องตั้งเป็นชั้น ๆ:**

- timeout ต่อการเรียก model หนึ่งครั้ง
- timeout รวมทั้ง request (รวม retry + fallback) ที่ต้อง **น้อยกว่า** timeout ของ gateway/load balancer ข้างหน้า
- สำหรับ streaming: ใช้ "ไม่มี token ใหม่มา X วินาที = ถือว่าค้าง" แทน timeout รวมอย่างเดียว

**Fallback ข้าม provider — ง่ายบนกระดาษ ยากในงานจริง:**

| สิ่งที่ต่าง | ผลกระทบ |
|---|---|
| prompt ที่ tune กับตัวหลัก | ตัวสำรองอาจตอบคนละสไตล์/คุณภาพต่างกัน |
| tokenizer และ context window | prompt ที่พอดีตัวหลักอาจยาวเกินตัวสำรอง |
| รูปแบบ tool calling / structured output | parser ของเราอาจพัง |
| นโยบายข้อมูล / region | ข้อมูลลูกค้าบางประเภทอาจห้ามส่งไปเจ้าอื่น |

**กฎ:** fallback ที่ไม่เคยถูกทดสอบ = ไม่มี fallback — ต้องรัน eval กับตัวสำรองด้วย และลองสลับจริงเป็นระยะ

### 5.11 Context Window Management

```
ข้อความที่ 1   ─┐
ข้อความที่ 2    │
...             ├─ ยิ่งคุยนาน input ยิ่งโต → แพงขึ้น ช้าลง และสุดท้ายเกิน context window
ข้อความที่ 40  ─┘
```

| วิธี | ทำยังไง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| Sliding window / trimming | เก็บ N ข้อความล่าสุด | ง่าย คุมต้นทุนได้แน่นอน | ลืมสิ่งที่พูดไว้ต้นบทสนทนา |
| Summarization | ย่อ history เก่าเป็นสรุปสั้น | จำใจความได้ยาว | เสียค่าเรียก model เพิ่ม, สรุปอาจตกรายละเอียดสำคัญ |
| Retrieval ของ history | เก็บ history ลง vector store แล้วดึงเฉพาะที่เกี่ยว (PART 36) | ขยายได้ไม่จำกัด | ซับซ้อน, ดึงพลาดได้ |
| ตัด tool output | เก็บเฉพาะส่วนที่ใช้ต่อ ไม่ยัดผลดิบทั้งก้อน | ลด token เยอะมากใน agent | ต้องรู้ว่าส่วนไหนจำเป็น |

**กฎที่มักลืม:** "context ยาว ≠ คำตอบดีขึ้นเสมอ" — ยัดของไม่เกี่ยวเข้าไปเยอะ ๆ อาจทำให้ model หลุดประเด็น จ่ายแพงขึ้นเพื่อได้ผลแย่ลง

### 5.12 Budget Guards & Per-tenant Quotas

```
[request เข้ามา]
     ↓
[ตรวจ quota ของ user / tenant]      ── เกิน → ตอบ 429 ของเราเอง / ลดเกรดไปใช้ model ถูก
     ↓
[ประเมิน token ก่อนส่ง]              ── prompt ยาวผิดปกติ → ตัด / ปฏิเสธ
     ↓
[เรียก model พร้อม max_output_tokens]
     ↓
[บันทึก usage จริง → หักจาก quota]
     ↓
[ภาพรวมรายวันของทั้งบริษัท]         ── ใกล้เพดาน → alert / เกินเพดาน → ปิด feature ที่ไม่สำคัญ
```

**ต้องมีหลายชั้น:**

| ชั้น | กันอะไร |
|---|---|
| ต่อ request (max tokens, max tool loops) | agent วนไม่จบ, prompt ยาวผิดปกติ |
| ต่อ user (ต่อวัน/ต่อนาที) | คนเดียวสคริปต์ยิงรัว ๆ |
| ต่อ tenant/องค์กร (ตาม plan ที่จ่าย) | ลูกค้า free tier กิน quota ของลูกค้าที่จ่ายเงิน |
| ต่อ feature | feature ทดลองตัวเดียวกินงบทั้งเดือน |
| ทั้งบริษัท + ที่ console ของ provider | บั๊กยิงลูปไม่จบตอนตีสาม |

> **ให้มองภาพนี้ว่า** "Budget guard คือฟิวส์หลายตัว ฟิวส์ห้องนอน ฟิวส์ทั้งชั้น ฟิวส์ทั้งบ้าน — ถ้ามีแค่ตัวใหญ่ตัวเดียว พอมันตัด ทุกห้องมืดพร้อมกัน"

**Trade-off:** quota เข้มเกิน = ผู้ใช้ดีโดนบล็อกและ churn / หลวมเกิน = บิลบาน — ต้องเลือกพฤติกรรมตอนเกินให้ดี (บล็อก vs ลดเกรด model vs เข้าคิว) และบอกผู้ใช้ตรง ๆ

### 5.13 Observability สำหรับ LLM (PART 23 ฉบับ LLM)

หลักการเดิมของ PART 23 ใช้ได้หมด — logs, metrics, traces, trace ID — แต่ต้องเพิ่มมิติที่ระบบปกติไม่มี: **token, cost, และ quality**

**1 request ของ RAG + agent ควรเห็นเป็น trace แบบนี้:**

```
trace_id=abc123  user=u_981(hashed)  tenant=t_12  feature=support_bot  prompt_v=14
│
├── span: retrieve          120ms   docs=5   top_score=0.82
├── span: build_prompt        3ms   input_tokens=6,200  cached=2,000
├── span: llm_call#1 (small) 1.9s   out_tokens=180  finish=stop  cost=$0.0016*
├── span: validate            1ms   result=FAIL (schema)
├── span: llm_call#2 (large) 4.1s   ttft=0.7s  out_tokens=350  cost=$0.037*
└── span: tool:create_ticket 220ms  status=ok  idempotency=req_77
                                                  * ตัวเลขสมมติ
TOTAL 6.4s   total_cost=$0.039*   user_feedback=👍
```

> **ให้มองภาพนี้ว่า** "Trace ของ LLM app ต้องตอบได้ไม่ใช่แค่ว่า 'ช้าตรงไหน' แต่ต้องตอบได้ว่า 'แพงตรงไหน' และ 'ผิดตรงไหน' ด้วย"

**Metrics ที่ต้องมีบน dashboard:**

| หมวด | Metric | ทำไม |
|---|---|---|
| Cost | token in/out/cached ต่อ request, cost ต่อ request/user/tenant/feature, cache hit rate | รู้ว่าเงินไปไหน |
| Latency | TTFT และ total latency ที่ **p50 / p95 / p99** แยกตาม model | average หลอกตา — คนโชคร้าย 5% คือคนที่บ่น |
| Reliability | error rate แยกประเภท (429, 5xx, timeout, context overflow, content filter, parse fail), fallback rate, retry rate | แยกให้ออกว่าเราผิดหรือ provider ผิด |
| Output | finish reason (stop vs length), ความยาว output, สัดส่วน JSON invalid | จับคำตอบถูกตัด/พัง |
| Quality | 👍/👎 rate, regenerate rate, eval score รายวัน, escalation rate ของ cascade, สัดส่วน "ส่งต่อเจ้าหน้าที่" | จับ drift ก่อนลูกค้าบ่น |

**Log prompt/response อย่างปลอดภัย:**

- **redact PII ก่อน log** (เลขบัตร, เบอร์โทร, อีเมล, ที่อยู่) — ดู PART 23 หัวข้อ "ห้าม log ของพวกนี้"
- เก็บ prompt ฉบับเต็มแยก store ที่ **สิทธิ์เข้าถึงจำกัด + มีอายุ** ส่วน log ทั่วไปเก็บแค่ metadata (version, token, latency, hash)
- **sampling** — เก็บเต็มเฉพาะบางส่วน + ทุกเคสที่ error/👎 เพื่อคุมต้นทุน storage และลดความเสี่ยง
- ใส่ `prompt_version`, `model_version`, `trace_id` ทุกบรรทัด — ไม่งั้นตอนคุณภาพตกจะไม่รู้ว่าเกิดจากอะไร

### 5.14 Drift, Regression, Versioning & Rollout

**ทำไม LLM app ถึงเสื่อมได้ทั้งที่ไม่มีใครแก้โค้ด:**

| สาเหตุ | ตัวอย่าง |
|---|---|
| Provider อัปเดต model (ถ้าชี้ชื่อ alias ที่เลื่อนเอง) | ตอบยาวขึ้น, รูปแบบ JSON เปลี่ยนนิดหน่อย, ปฏิเสธบ่อยขึ้น |
| ข้อมูลต้นทาง (RAG) เปลี่ยน | เอกสารใหม่เขียนคนละสไตล์ ดึงผิดชิ้น |
| พฤติกรรมผู้ใช้เปลี่ยน | ช่วงโปรโมชันคนถามคำถามแบบที่ไม่เคยเจอ |
| คนในทีมแก้ prompt "นิดเดียว" | แก้ให้เคสหนึ่งดีขึ้น เคสอื่นพังเงียบ ๆ |

**วิธีป้องกันเป็นขั้น:**

```
1. PIN model version            ← ใช้ชื่อเวอร์ชันที่ล็อก ไม่ใช่ alias "latest"
        ↓
2. VERSION prompt + config      ← prompt_v14 = {template, model, temperature, tools}
        ↓
3. EVAL SET (golden set)        ← ชุดคำถามจริง + คำตอบที่คาดหวัง/เกณฑ์ให้คะแนน
        ↓
4. รัน eval ก่อน merge (CI)     ← คะแนนตกเกิน threshold = ไม่ให้ deploy (PART 15, 18)
        ↓
5. CANARY / A-B                 ← ปล่อยให้ 5% ก่อน เทียบ quality/cost/latency กับของเดิม
        ↓
6. เฝ้า metric + feedback        ← ดีเท่าเดิมหรือดีกว่า → ขยาย / แย่ลง → rollback ทันที
```

> **ให้มองภาพนี้ว่า** "ถ้าไม่มี eval set คุณไม่มีทางรู้ว่า prompt ใหม่ดีกว่าเก่า — คุณแค่ 'รู้สึก' ว่าดีกว่า จากตัวอย่าง 3 ข้อที่ลองในแชท"

**A/B vs Canary:** canary ถามว่า "ของใหม่พังไหม" (ปล่อยน้อยแล้วดู error/cost) ส่วน A/B ถามว่า "ของใหม่ดีกว่าไหม" (แบ่งกลุ่มแล้ววัดผลทาง business/quality อย่างมีสถิติ) — ใช้คู่กันได้

**เมื่อ provider ประกาศเลิกใช้ model เวอร์ชันที่ pin ไว้:** ถือเป็น migration จริงจัง — รัน eval กับเวอร์ชันใหม่, ปรับ prompt, canary, แล้วค่อยย้าย อย่ารอจนวันสุดท้าย

### 5.15 Privacy, Data Retention & Security

**Privacy / PII:**

- **ส่งเท่าที่จำเป็น** — model ต้องรู้เลขบัตรประชาชนลูกค้าไหมถึงจะตอบคำถามเรื่องการจัดส่งได้? ส่วนใหญ่ไม่ต้อง
- **redact / pseudonymize ก่อนส่ง** — แทน `0812345678` ด้วย `<PHONE_1>` แล้วแทนกลับหลังได้คำตอบ (ถ้าจำเป็น)
- **รู้ data retention ทั้งสองฝั่ง** — provider เก็บ input/output ไว้นานเท่าไร เอาไป train ไหม มีตัวเลือกไม่เก็บไหม และ **log ของเราเอง** เก็บนานเท่าไร ใครอ่านได้
- **ภูมิภาค / กฎหมาย** — ข้อมูลบางประเภทอาจห้ามออกนอกประเทศหรือนอก vendor ที่อนุมัติ (มีผลกับ fallback ข้าม provider)

**Security:**

| ภัย | ป้องกัน |
|---|---|
| API key หลุด (ฝังใน frontend / commit ขึ้น git) | key อยู่ฝั่ง server เท่านั้น, secret manager (PART 7), key แยกต่อ environment/feature, rotate ได้, ตั้ง spend limit ต่อ key |
| Frontend เรียก provider ตรง | ทุกการเรียกผ่าน backend/gateway ที่ auth user + ใส่ quota |
| Prompt injection (ผู้ใช้หรือเอกสารใน RAG แอบสั่ง "ลืมคำสั่งเดิม...") | ถือว่า input ทุกชิ้นไม่น่าไว้ใจ, จำกัดสิทธิ์ tool (least privilege), ให้คนยืนยันก่อน action ที่มีผลจริง (PART 37) |
| Data exfiltration ผ่าน tool | tool ที่ส่งข้อมูลออกนอก (อีเมล, URL) ต้องมี allowlist |
| Abuse (ใช้ bot ทำงานอื่น, สคริปต์ยิงรัว) | rate limit ต่อ user, ตรวจ topic นอกขอบเขต, flag ผู้ใช้ที่ token พุ่งผิดปกติ |

**Monitoring ด้าน security:** log และ alert เมื่อเจอ pattern injection ที่รู้จัก, tool call ที่ถูกปฏิเสธ, ผู้ใช้ที่ใช้ token สูงผิดปกติเทียบค่าเฉลี่ย, คำตอบที่มีสิ่งที่หน้าตาเหมือน secret/PII — ไม่มีวิธีกัน injection ได้ 100% จึงต้อง **จำกัดความเสียหาย + ตรวจจับ** ควบคู่กัน

### 5.16 AI Gateway — Build vs Buy

```
[Service A] ─┐
[Service B] ─┼─→ [AI GATEWAY] ─┬─→ Provider 1
[Batch job] ─┘   │             └─→ Provider 2
                 ├─ auth + key management (app ไม่ถือ key ของ provider เอง)
                 ├─ routing / fallback / retry / timeout
                 ├─ quota ต่อ tenant + budget guard
                 ├─ cache (prompt / response)
                 ├─ PII redaction
                 └─ log / trace / cost attribution กลาง
```

| ประเด็น | Build เอง | Buy / ใช้ของสำเร็จรูป (managed หรือ open source) |
|---|---|---|
| เริ่มได้เร็ว | ช้า | **เร็ว** |
| ปรับตาม business logic เฉพาะ | **ยืดหยุ่นเต็มที่** | ทำได้เท่าที่ตัวนั้นเปิดให้ |
| ภาระดูแล | ต้องตาม API ของทุก provider เอง | ผู้ขาย/ชุมชนตามให้ |
| ข้อมูลผ่านบุคคลที่สาม | ไม่ผ่าน | managed = prompt ผ่านอีกเจ้าหนึ่ง ต้องประเมิน privacy/compliance |
| latency เพิ่ม | ควบคุมเอง | มี hop เพิ่ม ต้องวัด |
| ความเสี่ยง | สร้างแล้วเป็นหนี้ดูแลระยะยาว | lock-in, ผู้ขายเลิกกิจการ/เปลี่ยนราคา |

**หลักคิดของ Senior:** เริ่มจาก **wrapper บาง ๆ ใน codebase** (ฟังก์ชันเดียวที่ทุกที่เรียกผ่าน ใส่ log/token/cost/timeout) ตั้งแต่วันแรก — พอมีหลายทีม หลาย provider หรือต้องมี quota ต่อ tenant ค่อยตัดสินใจว่าจะโตเป็น gateway เองหรือซื้อ ข้อสำคัญคือ **อย่าให้โค้ดเรียก SDK ของ provider กระจายไปทั่ว** เพราะวันที่ต้องใส่ fallback หรือ log จะต้องแก้ร้อยที่

## 6. Example — ประเมินต้นทุนและลดราคา Support Bot

> ⚠️ **ตัวเลขทั้งหมดในหัวข้อนี้เป็นตัวเลขสมมติแบบกลม ๆ เพื่อฝึกวิธีคิด ไม่ใช่ราคาจริงของ provider หรือ model ใด** ราคาจริงเปลี่ยนบ่อย ให้เปิดหน้าราคาปัจจุบันแล้วแทนค่าเอง

### 6.1 โจทย์

Chatbot ตอบคำถามลูกค้าของร้านค้าออนไลน์ ใช้ RAG ดึงนโยบายร้านมาประกอบ (PART 36)

**ราคาสมมติ (ต่อ 1 ล้าน token):**

| Model (สมมติ) | Input | Cached Input | Output |
|---|---|---|---|
| Model-L (ใหญ่) | $6.00 | $0.60 | $30.00 |
| Model-S (เล็ก) | $0.20 | $0.02 | $0.80 |

**ขนาด request ปกติ 1 ครั้ง (สมมติ):**

| ส่วน | Tokens |
|---|---|
| System prompt + tool definitions | 2,000 |
| RAG context (5 ชิ้น) | 3,000 |
| Chat history | 1,000 |
| ข้อความผู้ใช้ | 200 |
| **รวม input** | **6,200** |
| **Output** | **400** |

**การใช้งานสมมติ:** 10,000 active users/เดือน, คนละ 10 ข้อความ/วัน, ใช้ 20 วัน/เดือน = **200 ข้อความ/user/เดือน**

### 6.2 รอบที่ 1 — ใช้ Model-L ทุกข้อความ ไม่มี cache

```
input  : 6,200 × $6.00 / 1,000,000  = $0.0372
output :   400 × $30.00 / 1,000,000 = $0.0120
─────────────────────────────────────────────
ต่อ request                         = $0.0492
ต่อ user ต่อเดือน  : $0.0492 × 200   = $9.84
ทั้งระบบต่อเดือน   : $9.84 × 10,000  = $98,400
```

สังเกต: output มีแค่ 400 token แต่คิดเป็น **ประมาณ 1 ใน 4 ของค่าใช้จ่าย** เพราะแพงกว่า input ต่อ token 5 เท่า (ในตัวเลขสมมตินี้)

แล้วถามคำถามทาง business: **ถ้า plan ที่ลูกค้าจ่ายคือ $5/เดือน feature นี้ขาดทุนเกือบเท่าตัว** — นี่คือเหตุผลที่ต้องคำนวณก่อน launch ไม่ใช่หลังบิลมา

### 6.3 รอบที่ 2 — จัดลำดับ prompt ให้ cache hit

ย้ายของนิ่ง (system prompt + tools 2,000 token) ไว้หน้าสุด สมมติ hit แทบทุกครั้ง

```
cached    : 2,000 × $0.60 / 1M  = $0.0012
input ปกติ : 4,200 × $6.00 / 1M  = $0.0252
output    :   400 × $30.00 / 1M = $0.0120
────────────────────────────────────────
ต่อ request                     = $0.0384   (ลด ~22%)
```

แทบไม่ต้องแก้ logic อะไรเลย แค่ **สลับลำดับ** — ลงแรงน้อย ได้ผลทันที (แต่ต้อง log ดู cache hit rate จริง)

### 6.4 รอบที่ 3 — Cascade: Model-S ก่อน ไม่ผ่านค่อยส่ง Model-L

สมมติวัดจาก eval แล้วพบว่า Model-S ตอบผ่านเกณฑ์ **70%** ของคำถาม (ส่วนใหญ่เป็นคำถามสถานะ order, เวลาจัดส่ง) อีก 30% ต้องส่งต่อ

```
Model-S ทุก request  : 6,200 × $0.20/1M + 400 × $0.80/1M = $0.00124 + $0.00032 = $0.00156
Model-L 30% (มี cache): 0.3 × $0.0384                                           = $0.01152
──────────────────────────────────────────────────────────────────────────────────────────
เฉลี่ยต่อ request                                                               ≈ $0.0131
ต่อ user ต่อเดือน  : $0.0131 × 200   ≈ $2.62
ทั้งระบบต่อเดือน   : ≈ $26,200      (จาก $98,400 → ลด ~73%)
```

**แต่ราคาที่จ่ายไม่ใช่แค่เงิน:**

| ได้ | เสีย |
|---|---|
| ค่าใช้จ่ายลด ~73% | 30% ที่ escalate **รอนานขึ้น** (เรียกสองรอบ) → p95 latency แย่ลง |
| 70% ที่จบที่ Model-S ตอบเร็วขึ้น (ตัวเล็กมักเร็วกว่า) | ต้องมี validator ที่เชื่อได้ — ถ้าปล่อยคำตอบผิดของตัวเล็กผ่าน = quality ตก |
| — | ระบบซับซ้อนขึ้น ต้อง monitor escalation rate (ถ้าพุ่ง ต้นทุนก็พุ่งตาม) |

### 6.5 รอบที่ 4 — ของที่ทำเพิ่มได้ และคำเตือน

| วิธีเพิ่มเติม | ผลคร่าว ๆ | ความเสี่ยง |
|---|---|---|
| สั่งตอบสั้น "ไม่เกิน 4 ประโยค" (400 → 200 token) | ลด output + latency ชัดเจน | คำตอบห้วนเกิน ต้อง eval |
| ลด RAG จาก 5 → 3 ชิ้น | ลด input | ดึงไม่ครบ ตอบผิด |
| Trim history เหลือ 6 ข้อความล่าสุด | คุมไม่ให้ต้นทุนโตตามความยาวบทสนทนา | ลืมบริบทต้นเรื่อง |
| Exact cache สำหรับ FAQ สาธารณะ ("ส่งกี่วัน") | request ส่วนนั้นแทบฟรี | ต้อง invalidate เมื่อนโยบายเปลี่ยน |
| ย้ายงานสรุป ticket รายวันไป batch API | ถูกลง + ไม่แย่ rate limit | ได้ผลช้า |
| Quota ต่อ user: 50 ข้อความ/วัน | ตัดหางยาวจากคนที่ใช้ผิดวัตถุประสงค์ | ผู้ใช้หนักตัวจริงอาจไม่พอใจ |

⚠️ **ข้อควรจำที่สุดของตัวอย่างนี้:** ทุกขั้นที่ลดต้นทุน ต้องมี **eval + metric คุณภาพ** เดินคู่กัน ไม่งั้นคุณอาจได้ระบบที่ถูกลง 70% และแย่ลง 40% โดยไม่มีใครรู้จนลูกค้าเลิกใช้

### 6.6 Incident ตัวอย่าง — "บิลวันนี้สูงกว่าปกติ 8 เท่า"

```
09:10  alert: daily spend เกิน 3× ของค่าเฉลี่ย 7 วัน
09:15  dashboard: cost ต่อ tenant → tenant t_45 คนเดียวคิดเป็น 70%
09:18  trace ของ t_45: request เดียวมี llm_call 25 รอบ, input โตขึ้นทุกรอบ
09:25  root cause: agent เรียก tool ค้นหาแล้วได้ผลว่าง → model ลองใหม่ไม่รู้จบ
       (ไม่มีเพดาน max tool loops, ไม่มี budget ต่อ request)
09:30  mitigate: ตั้ง max loops = 5, budget ต่อ request, ลด quota t_45 ชั่วคราว
ถัดมา  postmortem: เพิ่ม eval เคส "tool คืนผลว่าง", alert เมื่อ loop > 5 (PART 23)
```

> **ให้มองภาพนี้ว่า** "ถ้าไม่มี cost ต่อ tenant และ trace ต่อ step ข้อความเดียวที่คุณมีคือ 'บิลแพง' — ซึ่งบอกอะไรไม่ได้เลยว่าจะไปแก้ตรงไหน"

## 7. Compare

### 7.1 Prompt Caching vs Response Cache vs Semantic Cache

| ประเด็น | Prompt Caching | Response Cache (exact) | Semantic Cache |
|---|---|---|---|
| ใครเก็บ | provider | เรา | เรา |
| ยังเรียก model ไหม | **เรียก** (แค่ input ส่วนหัวถูกลง) | ไม่เรียก | ไม่เรียก |
| คำตอบใหม่ทุกครั้งไหม | ใช่ | ไม่ — คำตอบเดิมเป๊ะ | ไม่ — คำตอบของคำถามที่ "คล้าย" |
| ความเสี่ยงด้านถูกต้อง | แทบไม่มี | ข้อมูลเก่า, รั่วข้ามคน | **สูงสุด** — คล้ายแต่ไม่เหมือน |
| เหมาะกับ | แทบทุกระบบที่ system prompt ยาว | งาน deterministic ซ้ำ ๆ | FAQ สาธารณะ |

### 7.2 Streaming vs Non-streaming

| ประเด็น | Streaming | Non-streaming |
|---|---|---|
| เวลาจนจบจริง | เท่ากัน | เท่ากัน |
| ความรู้สึกของผู้ใช้ | **เร็ว** เห็นตั้งแต่ TTFT | ช้า จอนิ่งจนจบ |
| ตรวจ/กรองทั้งก้อนก่อนแสดง | ยาก | ง่าย |
| เหมาะกับ | UI แชท, คำตอบยาวให้คนอ่าน | JSON ที่ระบบเอาไปใช้ต่อ, background job |

### 7.3 Routing vs Cascade vs Fallback

| | ตอบคำถาม | ทำงานเมื่อ |
|---|---|---|
| **Routing** | "งานนี้ควรใช้ตัวไหน" | ก่อนเรียก เลือกตามชนิดงาน |
| **Cascade** | "ตัวถูกทำได้ดีพอไหม" | หลังตัวถูกตอบแล้วไม่ผ่านเกณฑ์ |
| **Fallback** | "ตัวหลักพัง จะไปทางไหน" | ตัวหลัก error / timeout / ถูกตัดวงจร |

> **ให้มองภาพนี้ว่า** "Routing และ Cascade เป็นเรื่องของ **เงินกับคุณภาพ** ส่วน Fallback เป็นเรื่องของ **ความอยู่รอด** — ระบบที่ดีมีทั้งสามแบบ และไม่สับสนว่าตัวไหนแก้ปัญหาอะไร"

### 7.4 Traditional Observability vs LLM Observability

| ประเด็น | ระบบทั่วไป (PART 23) | LLM app |
|---|---|---|
| "ถูกไหม" | status 200 = ส่วนใหญ่ถูก | **200 แต่คำตอบผิด/มั่ว ได้** — ต้องมี eval/feedback |
| ต้นทุนต่อ request | แทบคงที่ ไม่ค่อยวัด | แปรผันสูง **ต้องวัดทุก request** |
| Latency | ms | วินาที, แยก TTFT กับ total |
| สิ่งที่ต้อง log เพิ่ม | — | prompt/model version, token, cost, finish reason, cache hit |
| เปลี่ยนโดยเราไม่ได้แก้ | น้อย | provider อัปเดต model, ข้อมูล RAG เปลี่ยน |
| ความเสี่ยงของ log | PII ใน request | **PII ทั้งในคำถามและในคำตอบ** + เอกสารที่ดึงมา |

### 7.5 ตารางเปรียบเทียบคู่ที่สับสนบ่อย

| คู่ที่สับสน | ต่างกันตรงไหน |
|---|---|
| **Token vs Word** | token คือชิ้นที่ tokenizer หั่น อาจเล็กกว่าคำ (โดยเฉพาะภาษาไทย) |
| **Context Window vs Max Output** | context = input + output รวมกันต้องไม่เกิน / max output = เพดานเฉพาะขาออก |
| **TTFT vs Total Latency** | TTFT = เห็นคำแรก / Total = ตอบจบ — streaming ช่วยแค่ความรู้สึกของตัวแรก |
| **RPM vs TPM** | จำนวนครั้ง vs จำนวน token — ชนตัวไหนก็ได้ 429 เหมือนกัน |
| **Retry vs Fallback** | retry = ลองที่เดิมอีกครั้ง / fallback = เปลี่ยนไปที่อื่น |
| **Canary vs A/B** | canary = ของใหม่พังไหม / A/B = ของใหม่ดีกว่าไหม |
| **Drift vs Regression** | drift = เปลี่ยนไปเองตามเวลา / regression = แย่ลงหลังการเปลี่ยนที่ระบุได้ |
| **Eval vs Monitoring** | eval = สอบกับชุดข้อสอบก่อน/หลังเปลี่ยน / monitoring = ดูของจริงใน production ตลอดเวลา |
| **Rate Limit (ของ provider) vs Quota (ของเรา)** | provider คุมเรา / เราคุม user และ tenant ของเรา |

## 8. Common Mistakes

| # | สิ่งที่ Junior มักเข้าใจผิด | ความจริง |
|---|---|---|
| 1 | "ประเมินต้นทุนจากจำนวน request" | ต้นทุนมาจาก **token × ราคา** — request เดียวกันต่างกันได้เป็นสิบเท่า |
| 2 | "input กับ output ราคาเท่ากัน" | output มักแพงกว่าต่อ token หลายเท่า และเป็นส่วนที่ช้า |
| 3 | "นับตัวอักษรหาร 4 ก็ได้ token" | กฎนี้ใช้หยาบ ๆ กับภาษาอังกฤษ ภาษาไทยมักเพี้ยนมาก — **ต้องนับด้วย tokenizer จริง** |
| 4 | "ข้อความในแชทคิดเงินแค่ข้อความล่าสุด" | ส่ง history ทั้งหมดทุกครั้ง → ต้นทุนต่อข้อความโตตามความยาวบทสนทนา |
| 5 | "Streaming ทำให้ตอบเร็วขึ้น" | เวลารวมเท่าเดิม เร็วขึ้นแค่ **ความรู้สึก** (ซึ่งก็สำคัญมาก) |
| 6 | "เปิด prompt caching แล้วจบ" | ถ้าใส่ timestamp/ชื่อ user ไว้หน้า prompt จะ miss ตลอด — ต้องวัด hit rate |
| 7 | "Semantic cache ประหยัดดี ใช้ทุกคำถาม" | เสี่ยงตอบข้ามคน ตอบคำถามที่ความหมายต่าง ตอบข้อมูลเก่า |
| 8 | "เจอ 429 ก็ retry ทันทีวนไป" | ทำให้ยิ่งโดนหนัก — ต้อง backoff + jitter + จำกัดครั้ง และรู้ว่าชน RPM หรือ TPM |
| 9 | "retry ทุก error" | 400 (prompt ผิด/ยาวเกิน) retry ไปก็ผิดเหมือนเดิม เปลืองเงินฟรี |
| 10 | "มี fallback provider แล้ว ปลอดภัย" | ถ้าไม่เคย eval กับตัวสำรอง วันที่สลับจริงอาจพังทั้ง format และคุณภาพ |
| 11 | "ใช้ model ตัวใหญ่สุดไว้ก่อน ชัวร์" | จ่ายแพงและช้าเกินจำเป็นกับงานง่ายที่เป็นส่วนใหญ่ของ traffic |
| 12 | "context ยิ่งเยอะยิ่งตอบดี" | ของไม่เกี่ยวทำให้หลุดประเด็น + แพง + TTFT ช้า |
| 13 | "API key ใส่ใน frontend ก็ได้ สะดวก" | ใครเปิด DevTools ก็เอาไปใช้ได้บน quota ของคุณ — ต้องผ่าน backend เสมอ |
| 14 | "ใช้ชื่อ model แบบ latest จะได้ของดีเสมอ" | พฤติกรรมเปลี่ยนใต้เท้าคุณโดยไม่มี eval — ควร pin แล้วย้ายอย่างตั้งใจ |
| 15 | "แก้ prompt ตรง production เร็วดี" | prompt คือ code — ต้อง version, eval, rollout, rollback ได้ |
| 16 | "log prompt/response เต็ม ๆ ไว้ debug" | เท่ากับเก็บ PII ลูกค้าไว้ใน log ที่ทั้งทีมอ่านได้ — redact + จำกัดสิทธิ์ + มีอายุ |
| 17 | "HTTP 200 = ใช้งานได้" | LLM ตอบ 200 พร้อมคำตอบมั่วได้ — ต้องมี quality signal |
| 18 | "ตั้ง budget ไว้ที่ console provider ก็พอ" | พอถึงเพดาน ทุก feature ดับพร้อมกัน — ต้องมี quota หลายชั้นในระบบเราด้วย |

## 9. Debugging

### 9.1 Framework: LLM feature มีปัญหา ให้แยกก่อนว่าเป็นปัญหา "แบบไหน"

```
1. อาการคืออะไร?       → แพง / ช้า / error / ตอบแย่   (แยก 4 ทางก่อน อย่าเหมาเป็น "AI พัง")
        ↓
2. เริ่มเมื่อไร?          → ตรงกับ deploy, เปลี่ยน prompt_version, model update, traffic spike, เอกสาร RAG เปลี่ยน?
        ↓
3. กระทบใคร?            → ทุกคน / tenant เดียว / feature เดียว / ภาษาเดียว / model เดียว
        ↓
4. เปิด trace ของ request ที่เป็นปัญหา → ดูทีละ span: retrieve → prompt → call → validate → tool
        ↓
5. เทียบกับ request ที่ปกติ → token ต่างกันไหม, cache hit ต่างไหม, model ต่างไหม, จำนวนรอบต่างไหม
        ↓
6. Reproduce ด้วย prompt_version + model_version + input เดิม (temperature ต่ำ)
        ↓
7. แก้ → เพิ่มเคสนั้นเข้า eval set → เพิ่ม alert ถ้ามันควรถูกจับได้เร็วกว่านี้
```

> **ให้มองภาพนี้ว่า** "คำว่า 'AI มันแย่ลง' ไม่ใช่ bug report — งานแรกคือแปลงมันให้เป็น 'แพงขึ้น / ช้าลง / error มากขึ้น / คุณภาพตก' ที่ใคร ตั้งแต่เมื่อไร แล้วค่อยเปิด trace"

### 9.2 ตารางอาการ → สาเหตุที่น่าสงสัยที่สุด

| อาการ | สงสัยอะไรก่อน | เช็คยังไง |
|---|---|---|
| บิลพุ่งทั้งที่ traffic ปกติ | agent loop ไม่จบ / prompt ยาวขึ้น / cache miss | token ต่อ request, จำนวน llm_call ต่อ trace, cache hit rate |
| บิลพุ่งจาก tenant เดียว | abuse / integration ของลูกค้ายิงลูป | cost ต่อ tenant, request rate ต่อ key |
| cache hit rate ตกฮวบหลัง deploy | ใส่ของที่เปลี่ยนไว้ส่วนหน้า prompt / เปลี่ยนลำดับ tools | diff prompt template ก่อน-หลัง |
| ผู้ใช้บอกว่า "ช้า" แต่ average ปกติ | p95/p99 แย่ / cascade escalate เยอะขึ้น | ดู percentile แยก model, escalation rate |
| TTFT ช้าลง | input ยาวขึ้น (RAG, history) / provider ช้า | input tokens trend, เทียบ latency ฝั่ง provider |
| 429 ทั้งที่จำนวน request ไม่เยอะ | ชน **TPM** ไม่ใช่ RPM | token ต่อนาทีเทียบเพดาน |
| error รัวเป็นช่วง ๆ | provider มีปัญหา / timeout ตั้งสั้นเกิน | status page provider, แยก error type, fallback rate |
| คำตอบถูกตัดกลางประโยค / JSON parse fail | ชน max output tokens | finish reason = length สัดส่วนเท่าไร |
| คุณภาพตกโดยไม่มีใครแก้อะไร | model alias เลื่อน / เอกสาร RAG เปลี่ยน / ผู้ใช้ถามแบบใหม่ | model version ใน log, รัน eval set ย้อนหลัง, ดู 👎 rate |
| ตอบเรื่องของคนอื่น | response/semantic cache key ไม่มี user/tenant | ตรวจ cache key design **ทันที (เป็น security incident)** |
| bot ทำตามคำสั่งแปลก ๆ ในเอกสาร | prompt injection ผ่าน RAG | trace ดูเอกสารที่ถูกดึง, tool call ที่เกิด |
| ภาษาไทยแพงกว่าที่ประเมินมาก | ประเมินจากจำนวนตัวอักษร/คำ | นับด้วย tokenizer จริงจาก traffic จริง |

## 10. Interview Questions

### 🟢 Junior

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| Token คืออะไร เกี่ยวกับค่าใช้จ่ายยังไง | ชิ้นข้อความที่ model อ่าน/เขียน + คิดเงินตาม token + แยก input/output |
| ทำไม output แพงกว่า input | เขียนทีละ token ตามลำดับ อ่านได้เป็นก้อน — แพงกว่าและช้ากว่า |
| ทำไมภาษาไทยใช้ token มากกว่า | tokenizer ถูก train กับภาษาอังกฤษเป็นหลัก + ไทยไม่มีเว้นวรรค → หั่นเป็นชิ้นเล็ก |
| Streaming มีไว้ทำไม | ลด perceived latency — เห็นคำแรกเร็ว แม้เวลารวมเท่าเดิม |
| เจอ 429 ควรทำยังไง | backoff + jitter + จำกัดจำนวนครั้ง ไม่ retry รัวทันที |
| ทำไมห้ามใส่ API key ใน frontend | ใครก็เอาไปใช้ได้ — ต้องเรียกผ่าน backend ที่ auth user |
| Context window คืออะไร | เพดาน token รวมต่อ 1 ครั้ง — history ยาวไปก็ต้องตัด/ย่อ |

### 🟡 Mid

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| ประเมินค่าใช้จ่าย feature chatbot ต่อเดือนยังไง | แตก token ต่อ request (system/RAG/history/user/output) × ราคา × request ต่อ user × user — **พร้อมบอกว่าตัวเลขต้องวัดจากของจริง** |
| Prompt caching ทำงานยังไง ออกแบบ prompt ให้ hit ยังไง | prefix ต้องเหมือนเป๊ะ → ของนิ่งไว้หน้า ของเปลี่ยนไว้ท้าย + วัด hit rate |
| Semantic cache มีความเสี่ยงอะไร | รั่วข้าม user, คล้ายแต่ความหมายต่าง, ข้อมูลเก่า — ใส่ tenant ใน key, จำกัดขอบเขต, TTL |
| RPM กับ TPM ต่างกันยังไง | จำนวนครั้ง vs จำนวน token + เคส "ยิงน้อยแต่โดน 429" |
| ออกแบบ retry สำหรับ LLM call ยังไง | แยก error ที่ retry ได้/ไม่ได้, backoff+jitter, timeout เป็นชั้น, idempotency ที่ชั้น action |
| จะลด latency ของ chatbot ที่ตอบช้ายังไง | วัดก่อนว่าช้าที่ TTFT หรือช่วงเขียน → ตอบสั้นลง / cache / model เล็กลง / streaming / tool ขนาน |
| จัดการ chat history ที่ยาวขึ้นเรื่อย ๆ ยังไง | trim / summarize / retrieve — พร้อม trade-off ความจำ vs ต้นทุน |
| LLM app ต้อง log และวัดอะไรบ้าง | trace ต่อ step, token/cost ต่อ request, TTFT+total p95, error type, finish reason, version, quality signal + redact PII |

### 🔴 Senior

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| ออกแบบ model routing/cascade ให้ลดต้นทุนโดยคุณภาพไม่ตก | eval set แยกหมวด → หาว่าตัวเล็กผ่านหมวดไหน → validator ที่เชื่อได้ → วัด escalation rate, p95 latency, quality ใน canary |
| provider หลักล่มครึ่งวัน ระบบคุณควรเป็นยังไง | circuit breaker → fallback ที่ **eval มาแล้ว** + ข้อจำกัดด้าน privacy/region + graceful degradation (ปิด feature รองก่อน) + สื่อสารผู้ใช้ |
| คุณภาพคำตอบตกโดยไม่มีใครแก้โค้ด จะหาสาเหตุยังไง | ยืนยันด้วย metric (feedback/eval) → timeline เทียบกับ model/prompt/RAG/traffic → pin version → eval ย้อนหลัง → canary การแก้ |
| ปล่อย prompt หรือ model ใหม่อย่างปลอดภัยยังไง | version + eval ใน CI + canary/A-B + เฝ้า quality/cost/latency + rollback ทันที |
| ออกแบบระบบ quota/budget สำหรับ SaaS หลาย tenant | หลายชั้น (request/user/tenant/feature/บริษัท), นับจาก usage จริง, พฤติกรรมตอนเกิน (block/degrade/queue), attribution ต่อ tenant, alert anomaly |
| จะจัดการ PII และ data retention ใน LLM pipeline ยังไง | ส่งเท่าที่จำเป็น, redact/pseudonymize ก่อนส่งและก่อน log, รู้ retention ของ provider และของเรา, จำกัดสิทธิ์ log, ผลต่อ fallback ข้าม vendor |
| จะสร้าง AI gateway เองหรือซื้อ | เริ่มจาก wrapper บาง ๆ → เกณฑ์ตัดสิน: จำนวนทีม/provider, ความต้องการ quota/compliance, privacy ของ managed, lock-in, ภาระดูแล |
| ป้องกันและตรวจจับ prompt injection ใน production ยังไง | ยอมรับว่ากัน 100% ไม่ได้ → least privilege ของ tool, human-in-the-loop สำหรับ action เสี่ยง, allowlist การส่งข้อมูลออก, monitor pattern + tool call ผิดปกติ |

## 11. Answer Like a Developer

### โครงมาตรฐาน 4 จังหวะ (ใช้ได้กับคำถาม AI Ops เกือบทุกข้อ)

```
1. นิยาม + หน่วยวัด            "X คือ ... วัดเป็น token / วินาที / เปอร์เซ็นต์"
        ↓
2. ทำไมมันสำคัญใน production    "เพราะ LLM แพง/ช้า/ไม่แน่นอน/เปลี่ยนเองได้ ..."
        ↓
3. ตัวอย่างพร้อมตัวเลข (สมมติ)   "สมมติ request ละ 6,000 input 400 output ..."
        ↓
4. Trade-off + สิ่งที่ต้องวัดคู่   "แต่แลกกับ ... เลยต้องมี eval/metric ... คอยดู"
```

> **ให้มองภาพนี้ว่า** "คำตอบ AI Ops ที่ดีมีตัวเลขเสมอ และทุกการลดต้นทุนต้องมีประโยคตามว่า 'แล้วเราจะรู้ได้ยังไงว่าคุณภาพไม่ตก'"

### ตัวอย่างการตอบ: "ค่า LLM ของ feature นี้แพงเกิน จะลดยังไง"

**❌ คำตอบระดับท่องจำ:** "เปลี่ยนไปใช้ model ที่ถูกกว่าครับ"

**✅ คำตอบระดับที่อยากได้:**
> "ผมจะเริ่มจากดูก่อนว่าเงินไปไหนครับ — แตกต้นทุนต่อ request เป็น input, cached, output และแยกตาม feature กับ tenant ส่วนใหญ่จะเจอว่าต้นทุนกระจุกอยู่ไม่กี่จุด
> อย่างแรกที่ทำได้เร็วคือจัดลำดับ prompt ให้ของนิ่งอยู่ข้างหน้าเพื่อให้ prompt caching hit แล้วคุม output ให้สั้นลงเพราะ output แพงที่สุดและเป็นส่วนที่ช้าด้วย
> ถ้ายังไม่พอ ผมจะดูว่า traffic ส่วนไหนเป็นงานง่าย แล้วลอง cascade ให้ model เล็กตอบก่อน ส่วนที่ไม่ผ่าน validator ค่อยส่งตัวใหญ่ งานที่ไม่มีคนรอก็ย้ายไป batch
> แต่ทุกขั้นผมจะรัน eval set และเฝ้า feedback กับ p95 latency ควบคู่ไป เพราะถ้าลดเงินได้ 70% แต่คุณภาพตกจนลูกค้าเลิกใช้ ก็ไม่คุ้มครับ"

### ตัวอย่างการตอบ: "Provider ที่ใช้อยู่ล่ม ระบบคุณจะเป็นยังไง" (แบบเล่าเป็นเหตุการณ์)

> "ถ้าออกแบบไว้ดี ผู้ใช้ควรรู้สึกแค่ช้าลงนิดหน่อยครับ — เราตั้ง timeout ต่อ call และ retry แค่ error ที่ควร retry แบบ backoff พอ error ต่อเนื่องจน circuit breaker เปิด ระบบจะข้ามไป fallback เลยโดยไม่ต้องรอ timeout ทุกครั้ง
> แต่ fallback ต้องเคยถูก eval มาก่อนนะครับ เพราะ prompt ที่ tune กับตัวหลักอาจให้ผลต่างกับอีกเจ้า และต้องเช็คด้วยว่าข้อมูลประเภทนั้นส่งไปอีก vendor ได้ตามนโยบายไหม
> ถ้าไม่มี fallback ที่ใช้ได้ ก็ควร degrade อย่างสุภาพ เช่น ปิดปุ่ม AI ชั่วคราวแล้วพาไปคุยกับเจ้าหน้าที่ แทนที่จะให้ผู้ใช้เห็นหน้าหมุนค้าง ระหว่างนั้น dashboard ต้องบอกได้ว่านี่คือปัญหา provider ไม่ใช่ของเรา จาก error type ที่แยกไว้ครับ"

### คำพูดที่ทำให้ดูมีประสบการณ์ (ใช้ได้จริง ไม่ใช่ท่อง)

| สถานการณ์ | พูดแบบนี้ |
|---|---|
| ถูกถามเรื่อง cost | "ขอคิดเป็น token ต่อ request ก่อนครับ แล้วค่อยคูณออกไปเป็นต่อ user ต่อเดือน" |
| ถูกถามว่า prompt ใหม่ดีกว่าไหม | "ผมจะไม่ตัดสินจากการลองในแชทครับ ผมจะรันกับ eval set แล้ว canary ดู metric จริง" |
| ถูกถามให้เลือก model | "ขึ้นกับว่างานนั้นต้องการคุณภาพระดับไหน ผมจะเริ่มจากตัวเล็กที่ผ่าน eval แล้วค่อยขยับขึ้น" |
| ถูกถามเรื่องราคา model ปัจจุบัน | "ราคาเปลี่ยนบ่อยครับ ผมจะเปิดหน้าราคาล่าสุด แต่วิธีคิดคือ input/cached/output คูณปริมาณจริง" |

## 12. One-Minute Review

อ่านรอบเดียวก่อนเข้าห้องสัมภาษณ์:

- **LLM = dependency ภายนอกที่ช้า แพง ไม่แน่นอน และเปลี่ยนเองได้** — AI Ops คือหลัก backend เดิมที่เอามาใช้กับมัน
- **Token** = หน่วยนับเงินและความยาว / **Output แพงกว่าและช้ากว่า Input** / **Cached input ถูกที่สุด**
- **ภาษาไทยมักใช้ token มากกว่า** สำหรับความหมายเท่ากัน — ต้องนับด้วย tokenizer จริง
- **ต้นทุน = token × ราคา × ปริมาณ** — history, tool definitions, tool output และ reasoning ก็นับด้วย
- **Latency ≈ app + TTFT + (output ÷ TPS)** — ลด output คือคันโยกที่คุ้มที่สุด / **Streaming** ลดความรู้สึกรอ ไม่ได้ลดเวลาจริง
- **Prompt caching** = ของนิ่งไว้หน้า ของเปลี่ยนไว้ท้าย + วัด hit rate / **Semantic cache** ประหยัดแต่เสี่ยงรั่วข้ามคนและตอบผิดความหมาย
- **Batch** สำหรับงานที่ไม่มีคนรอ — ถูกกว่าแต่ช้า
- **Routing** = เลือกก่อน / **Cascade** = ถูกก่อนไม่ผ่านค่อยแพง (เคสยากจ่ายสองต่อ) / **Fallback** = ตัวหลักพังไปตัวสำรอง (ต้อง eval มาแล้ว)
- **RPM vs TPM** / retry แค่ error ที่ควร retry + backoff + jitter / **idempotency ที่ชั้น action** / timeout เป็นชั้น
- **Context**: trim / summarize / retrieve — context ยาว ≠ ดีขึ้นเสมอ
- **Budget guard + quota หลายชั้น**: request / user / tenant / feature / บริษัท
- **LLM observability** = PART 23 + token + cost + quality: trace ต่อ step, p95 TTFT/total, error type, finish reason, version, feedback, eval — **redact PII ก่อน log**
- **Drift** เกิดได้โดยไม่แก้โค้ด → pin model, version prompt, eval ใน CI, canary/A-B, rollback
- **Security**: key อยู่ server เท่านั้น, least privilege ของ tool, monitor injection และ abuse
- **Gateway**: เริ่มจาก wrapper บาง ๆ ตั้งแต่วันแรก แล้วค่อยตัดสินใจ build vs buy

## 13. Memory Card

### จำ 5 อย่างนี้พอ

1. **คิดเป็น token ไม่ใช่ request — output แพงและช้ากว่า input, cached ถูกสุด, ภาษาไทยกิน token มากกว่า**
2. **ของนิ่งไว้หน้า prompt, ตอบให้สั้น, งานไม่รีบไป batch** — สามคันโยกที่ลดต้นทุนได้เร็วที่สุด
3. **Routing/Cascade เพื่อเงินกับคุณภาพ, Fallback เพื่อความอยู่รอด** — และ fallback ที่ไม่เคย eval คือไม่มี fallback
4. **ทุก request ต้องมี trace_id, token, cost, latency (p95), version และ quality signal** — log แบบ redact PII แล้ว
5. **Prompt และ model คือ code** — pin, version, eval, canary, rollback — เพราะมันเปลี่ยนเองได้โดยที่คุณไม่ได้แก้อะไรเลย
