# PART 22 — PERFORMANCE

> ตำแหน่งในภาพใหญ่: Cross-Cutting Layer — เรื่องที่พาดผ่านทุกชั้นตั้งแต่ Browser ยัน Database ไม่ได้อยู่ชั้นใดชั้นหนึ่ง

## 1. Big Picture

ลองนึกภาพนี้ก่อน

ผู้ใช้กดปุ่ม "ค้นหาร้านอาหาร" แล้วหน้าจอค้าง 6 วินาที
เขาไม่รู้หรอกว่าใครผิด เขารู้แค่ว่า **"แอปนี้ช้า"**

แต่ 6 วินาทีนั้น จริง ๆ แล้วมันแตกออกได้เป็น:

```
0.0s  กดปุ่ม
0.3s  JS bundle ใหญ่ ยังโหลดไม่เสร็จ         ← Frontend
0.9s  DNS + TLS + Request เดินทาง             ← Network
1.2s  Backend รับเรื่อง
1.4s  Backend serialize JSON ก้อนยักษ์         ← Backend CPU
4.8s  Query ไม่มี index สแกนทั้งตาราง          ← Database
5.4s  ส่ง response 4MB กลับมา                  ← Network
6.0s  React re-render ทั้งหน้า                 ← Frontend Rendering
```

> **ให้มองภาพนี้ว่า** "คำว่าช้า ไม่ใช่ปัญหาเดียว แต่เป็นผลรวมของเวลาที่เสียไปในหลายชั้น และงานของเราคือหาว่าชั้นไหนกินเวลามากที่สุด ไม่ใช่เดาว่าชั้นไหนน่าจะช้า"

**Performance → ประสิทธิภาพ → ความสามารถของระบบในการทำงานให้เสร็จเร็วพอ และรับคนได้มากพอ ภายใต้ทรัพยากรที่มีอยู่**

สังเกตว่านิยามนี้มี **สองครึ่ง** และสองครึ่งนี้คือหัวใจของ chapter ทั้งบท:

| ครึ่งของนิยาม | ศัพท์จริง | คำถามที่ตอบ |
|---|---|---|
| ทำงานให้เสร็จเร็วพอ | **Latency** | "คนหนึ่งคนรอนานแค่ไหน" |
| รับคนได้มากพอ | **Throughput** | "รับได้พร้อมกันกี่คนต่อวินาที" |

สองอันนี้ **ไม่ใช่เรื่องเดียวกัน** และหลายครั้ง **ขัดกันเอง**
คนที่แยกสองอันนี้ไม่ออก จะปรับระบบผิดทางตลอดชีวิต

### หลักการกลางของ chapter นี้: Measure Before Optimize

ถ้าคุณจำอะไรจาก chapter นี้ได้แค่บรรทัดเดียว ให้จำบรรทัดนี้

> **วัดก่อน แล้วค่อยแก้ — Measure Before Optimize**

เหตุผลไม่ใช่เรื่องความสวยงามของกระบวนการ แต่เป็นเรื่องจริงที่โหดร้าย:

1. **ความรู้สึกของเราผิดเกือบตลอด** — เราชอบคิดว่า React re-render คือปัญหา ทั้งที่ 80% ของกรณีคือ query ที่ไม่มี index
2. **การ optimize ทุกครั้งมีต้นทุน** — code ซับซ้อนขึ้น อ่านยากขึ้น bug เพิ่มขึ้น ถ้าแก้ผิดจุด = จ่ายต้นทุนฟรี
3. **ถ้าไม่วัดก่อน จะไม่รู้ว่าแก้แล้วดีขึ้นจริงไหม** — คุณจะไม่มีทางพิสูจน์ผลงานตัวเองได้

```
[รู้สึกว่าช้า]
      ↓
[วัด — Measure]          เก็บตัวเลขจริง ไม่ใช่ความรู้สึก
      ↓
[หาคอขวด — Profile]      ชั้นไหน ฟังก์ชันไหน query ไหน กินเวลาเท่าไร
      ↓
[ตั้งสมมติฐาน]           "ถ้าแก้ตรงนี้ น่าจะลดจาก 4.8s เหลือ 0.2s"
      ↓
[แก้จุดเดียว — Fix One]  แก้ทีละอย่าง ไม่แก้พร้อมกัน 5 อย่าง
      ↓
[วัดซ้ำ — Verify]        ดีขึ้นจริงไหม ดีขึ้นเท่าไร
      ↓
   ดีขึ้นพอหรือยัง? ── ยัง ──┐
      ↓ พอแล้ว              │
   [หยุด]  ←────────────────┘ (วนกลับไปหาคอขวดตัวถัดไป)
```

> **ให้มองภาพนี้ว่า** "การแก้ performance คือการวนลูปหมอรักษาคนไข้ ไม่ใช่การเดาแล้วจ่ายยาทุกขนานพร้อมกัน"

จุดที่ junior พลาดมากที่สุดคือลูกศรสุดท้าย — **"ดีขึ้นพอหรือยัง"**
เพราะ performance ไม่มีคำว่า "เร็วที่สุด" มีแต่ **"เร็วพอตาม requirement แล้วหยุด"**

### 4 ชั้นของ Performance

chapter นี้แบ่งเป็น 4 ชั้นตามลำดับที่ request เดินทาง

```
[FRONTEND]        Network / Rendering / Re-render / Bundle / Image / Lazy Load / Code Split
      ↓
[BACKEND]         CPU / Memory / I/O / Blocking
      ↓
[DATABASE]        Query / Index / N+1 / Connection Pool
      ↓
[INFRASTRUCTURE]  Scaling / Load Balancer / Cache / CDN
```

> **ให้มองภาพนี้ว่า** "ปัญหา performance มีบ้านอยู่ 4 หลัง หน้าที่แรกคือรู้ให้ได้ว่าปัญหานี้อยู่บ้านไหน ก่อนจะเคาะประตูเข้าไปซ่อม"

## 2. Keywords

|---|---|---|
| Performance | เร็วพอ + รับไหว | ความสามารถทำงานเสร็จเร็วพอภายใต้ทรัพยากรที่มี |
| Latency | ช้าต่อคน | เวลาที่ผู้ใช้ 1 คนต้องรอ วัดเป็น ms |
| Throughput | รับได้กี่คน | จำนวนงานที่ระบบทำเสร็จต่อหน่วยเวลา เช่น req/s |
| Bottleneck | คอขวด | จุดที่ช้าที่สุดในระบบ ซึ่งกำหนดความเร็วรวม |
| Profiling | ส่องหาจุดช้า | การวัดว่าเวลาถูกใช้ไปที่ส่วนไหนของโปรแกรม |
| Benchmark | วัดเทียบ | การวัดตัวเลขเพื่อเทียบก่อน/หลังแก้ |
| p50 / Median | ค่ากลาง | เวลาที่ 50% ของ request เร็วกว่านี้ |
| p95 | ช้ากว่าปกติ | 95% ของ request เร็วกว่านี้ — คนที่เจอวันแย่ ๆ |
| p99 | หางยาว | 99% เร็วกว่านี้ — 1 ใน 100 คนที่เจอหนักสุด |
| Tail Latency | หางของการกระจาย | กลุ่ม request ช้าสุดที่ค่าเฉลี่ยมองไม่เห็น |
| TTFB | ไบต์แรกมาเมื่อไร | Time To First Byte — วัดว่า server ตอบเร็วแค่ไหน |
| LCP | ของชิ้นใหญ่ขึ้นเมื่อไร | Largest Contentful Paint — ผู้ใช้เห็นเนื้อหาหลักเมื่อไร |
| CLS | หน้ากระตุก | Cumulative Layout Shift — เนื้อหาเด้งไปมาระหว่างโหลด |
| INP | กดแล้วตอบสนองเร็วไหม | Interaction to Next Paint — วัดการตอบสนองต่อการกด |
| Bundle | ก้อน JS ที่ส่งไป | ไฟล์ JS ที่ browser ต้องโหลดและ parse |
| Tree Shaking | เขย่าโค้ดที่ไม่ใช้ทิ้ง | ตัด code ที่ไม่ถูก import ออกจาก bundle |
| Code Splitting | แบ่งก้อนโหลดทีหลัง | แยก bundle เป็นหลายก้อน โหลดเมื่อจำเป็น |
| Lazy Loading | ขี้เกียจโหลด | เลื่อนการโหลดจนถึงตอนที่ต้องใช้จริง |
| Re-render | React วาดใหม่ | React คำนวณ component ใหม่เมื่อ state/props เปลี่ยน |
| Memoization | จำคำตอบเดิม | เก็บผลลัพธ์ที่คำนวณแล้ว ไม่คำนวณซ้ำ |
| Virtualization | วาดเฉพาะที่เห็น | render เฉพาะ row ที่อยู่ในจอ ไม่ render ทั้ง 10,000 row |
| Debounce | รอให้หยุดก่อนค่อยทำ | รวบหลาย event เป็นครั้งเดียวหลังผู้ใช้หยุดพิมพ์ |
| Throttle | จำกัดความถี่ | จำกัดให้ทำงานมากสุด 1 ครั้งต่อช่วงเวลา |
| Blocking | ขวางคิว | งานที่ยึด thread ไว้จนคนอื่นทำงานไม่ได้ |
| Event Loop | คิวงานของ Node | กลไกที่ Node ใช้สลับงาน I/O บน thread เดียว |
| GC | เก็บขยะ | Garbage Collection — คืน memory ที่ไม่ใช้แล้ว |
| Memory Leak | รั่ว | memory ที่ถูกจองแล้วไม่ถูกคืน สะสมจนล่ม |

| Connection Pool | สระของท่อต่อ DB | ชุด connection ที่ใช้ซ้ำ ไม่เปิด/ปิดใหม่ทุกครั้ง |
| Cache | ที่เก็บของใกล้มือ | เก็บผลลัพธ์ไว้ตอบซ้ำโดยไม่คำนวณ/ไม่ query ใหม่ |
| Cache Hit / Miss | เจอ / ไม่เจอ | เจอใน cache = เร็ว, ไม่เจอ = ต้องไปเอาของจริง |
| CDN | โกดังใกล้บ้าน | เครือข่าย server กระจายทั่วโลกที่เก็บไฟล์ static |
| Scaling | ขยาย | เพิ่มความสามารถรับโหลด |
| Vertical Scaling | เครื่องใหญ่ขึ้น | เพิ่ม CPU/RAM ให้เครื่องเดิม |
| Horizontal Scaling | เครื่องเยอะขึ้น | เพิ่มจำนวนเครื่อง แล้วกระจายโหลด |
| Load Balancer | คนจัดคิว | ตัวกระจาย request ไปหลาย server |
| Rate Limiting | จำกัดโควตา | จำกัดจำนวน request ต่อผู้ใช้เพื่อกัน overload |
| Backpressure | ดันกลับเมื่อรับไม่ไหว | กลไกบอกต้นทางว่าให้ส่งช้าลง |
| Premature Optimization | แก้ก่อนรู้ปัญหา | optimize สิ่งที่ยังไม่รู้ว่าเป็นปัญหา = เสียเปล่า |

## 3. Mental Model

### Mental Model 1 — ระบบเร็วเท่าคอขวดของมัน

ระบบไม่ได้เร็วเท่าค่าเฉลี่ยของทุกชั้น
ระบบเร็วเท่า **ชั้นที่ช้าที่สุด**

```
Frontend 50ms  +  Backend 30ms  +  Database 4000ms  =  4080ms
                                   └──── คอขวด ────┘
```

ถ้าคุณไปเร่ง Frontend จาก 50ms เหลือ 10ms คุณประหยัดได้ 40ms จาก 4080ms
= **ดีขึ้น 1%** ทั้งที่เหนื่อยเท่ากับแก้ database

> **กฎ:** optimize ที่ไม่ใช่คอขวด = ไม่มีผล

### Mental Model 2 — Latency กับ Throughput ไม่ใช่เรื่องเดียวกัน

นี่คือจุดที่แยก junior ออกจาก mid ในห้องสัมภาษณ์

```
🧠 ภาพจำ:
Latency    = ร้านก๋วยเตี๋ยว 1 ชาม ใช้เวลาทำกี่นาที
Throughput = ร้านนี้เสิร์ฟได้กี่ชามต่อชั่วโมง
```

ร้านที่ทำ 1 ชามใน 3 นาที แต่มีเตาเดียว → latency ดี throughput แย่
ร้านที่ทำ 1 ชามใน 8 นาที แต่มี 20 เตาทำพร้อมกัน → latency แย่ throughput ดี

| สถานการณ์ | Latency | Throughput | เกิดจาก |
|---|---|---|---|
| คนใช้คนเดียวก็ช้า | แย่ | ยังไม่รู้ | code/query ช้าจริง |
| คนเดียวเร็ว คนเยอะช้า | ดีตอนว่าง | ถึงเพดาน | ทรัพยากรไม่พอ / คิวยาว |
| เพิ่มเครื่องแล้วดีขึ้น | เท่าเดิม | ดีขึ้น | เป็นปัญหา throughput |
| เพิ่มเครื่องแล้วไม่ดีขึ้น | เท่าเดิม | เท่าเดิม | เป็นปัญหา latency ของ code เอง |

**บรรทัดทองสำหรับห้องสัมภาษณ์:**

> "เพิ่มเครื่องช่วย throughput แต่ไม่ช่วย latency — ถ้า query เดียวใช้ 4 วินาที เพิ่มเครื่องเป็น 10 เครื่อง มันก็ยัง 4 วินาทีต่อคนอยู่ดี"

และในทางกลับกัน เมื่อระบบเริ่มแน่น **latency จะแย่ลงเพราะ throughput ถึงเพดาน**
เพราะ request ต้องไปต่อคิว เวลารวมที่ผู้ใช้เจอ = เวลาทำงานจริง + เวลารอคิว

```
Load น้อย     → latency = เวลาทำงานจริง
Load เกือบเต็ม → latency = เวลาทำงานจริง + เวลารอคิว (พุ่งขึ้นเร็วมาก)
```

> **ให้มองภาพนี้ว่า** "ถนนที่รถยังไม่เต็มกับถนนที่รถเต็มพอดี ต่างกันแค่คันเดียว แต่เวลาเดินทางต่างกันสามเท่า"

### Mental Model 3 — ค่าเฉลี่ยหลอกเรา ให้ดู Percentile

สมมติมี request 100 ครั้ง

- 99 ครั้ง ใช้เวลา 100ms
- 1 ครั้ง ใช้เวลา 10,000ms (10 วินาที)

**ค่าเฉลี่ย (average) = 199ms** → ดูดีมาก ผ่าน SLA สบาย
แต่ความจริงคือ **มีลูกค้า 1 คนรอ 10 วินาที** และเขาคือคนที่จะไปรีวิว 1 ดาว

```
🧠 ภาพจำ:
ค่าเฉลี่ย = "คนไทยมีเงินเฉลี่ยคนละ 2 ล้าน"
ความจริง  = มหาเศรษฐี 1 คน กับคนธรรมดา 999 คน
```

**Percentile → เปอร์เซ็นไทล์ → ค่าที่บอกว่า "X% ของ request เร็วกว่าตัวเลขนี้"**

| ค่า | อ่านว่า | ใช้ดูอะไร |
|---|---|---|
| p50 (median) | ครึ่งหนึ่งเร็วกว่านี้ | ประสบการณ์ของคน "ทั่วไป" |
| p95 | 95% เร็วกว่านี้ / 5% ช้ากว่า | ประสบการณ์ของคนวันแย่ ๆ |
| p99 | 99% เร็วกว่านี้ / 1% ช้ากว่า | ประสบการณ์แย่สุดที่ยังต้องรับผิดชอบ |
| avg | ค่าเฉลี่ย | **แทบไม่ควรใช้ตัดสินใจเดี่ยว ๆ** |
| max | ช้าสุด | มักเป็น outlier เช่น timeout เดียว |

```
จำนวน request
  │        ▇▇▇▇▇
  │      ▇▇▇▇▇▇▇▇
  │    ▇▇▇▇▇▇▇▇▇▇▇
  │  ▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁
  └──────┬─────────┬──────┬────────┬──── เวลา (ms)
        p50       p95    p99     max
                          └── Tail Latency ──┘
```

> **ให้มองภาพนี้ว่า** "request ส่วนใหญ่กองอยู่ซ้ายมือ แต่ชื่อเสียงของระบบถูกตัดสินโดยหางยาวทางขวาที่ค่าเฉลี่ยมองไม่เห็น"

**ทำไม p99 สำคัญกว่าที่คิด:** หน้าเว็บ 1 หน้ายิง API 20 เส้น
ถ้าแต่ละเส้นมีโอกาสช้า 1% (p99) โอกาสที่หน้านี้จะมีอย่างน้อย 1 เส้นช้า ≈ **18%**
แปลว่า **เกือบ 1 ใน 5 ของการโหลดหน้า จะเจอ p99** ทั้งที่ p99 แปลว่า "แค่ 1%"

### Mental Model 4 — Performance คือ Trade-off ไม่ใช่ชัยชนะ

ทุกการ optimize จ่ายด้วยอะไรบางอย่างเสมอ

| วิธีเร่ง | ได้ | จ่ายด้วย |
|---|---|---|
| Cache | latency ดีขึ้นมาก | ข้อมูลอาจเก่า (stale), ต้องจัดการ invalidation |
| Index | query เร็วขึ้น | write ช้าลง, กิน disk |
| Denormalize | ลด JOIN | ข้อมูลซ้ำ, เสี่ยงไม่ตรงกัน |
| Code Splitting | โหลดแรกเร็ว | กดเข้าหน้าใหม่แล้วรอโหลดเพิ่ม |
| Memoization | ไม่คำนวณซ้ำ | กิน memory, code ซับซ้อนขึ้น |
| เพิ่มเครื่อง | throughput ดีขึ้น | จ่ายเงินเพิ่มทุกเดือน |
| Queue / Async | response เร็วทันที | ผู้ใช้ไม่เห็นผลลัพธ์ทันที ต้องออกแบบ UX ใหม่ |

> ในห้องสัมภาษณ์ ถ้าคุณพูดวิธีแก้แล้วไม่พูดราคาที่ต้องจ่าย คะแนนจะหายทันที

## 4. ภาพจำ

```
🧠 ภาพจำหลัก:
Performance = การไล่จับคอขวดในท่อน้ำ 4 ท่อนที่ต่อกัน

น้ำไหลได้เร็วเท่าท่อนที่แคบที่สุดเท่านั้น
ขยายท่อนที่ไม่แคบ = เหนื่อยฟรี

[FRONTEND] ══╗
[BACKEND]  ══╣  ท่อไหนแคบสุด = คอขวด
[DATABASE] ═╗║
[INFRA]    ══╝
```

> **ให้มองภาพนี้ว่า** "งานของเราไม่ใช่ทำทุกท่อให้ใหญ่ แต่คือหาท่อที่แคบที่สุดให้เจอแล้วขยายเฉพาะท่อนั้น"

```
🧠 ภาพจำ Measure Before Optimize:
หมอที่ดีไม่ผ่าตัดก่อน X-ray

รู้สึกปวด → X-ray → เจอจุด → ผ่าจุดเดียว → ตรวจซ้ำ
เดาแล้วผ่า = คนไข้เจ็บฟรี
```

```
🧠 ภาพจำ Latency vs Throughput:
Latency    = ลิฟต์ขึ้นชั้น 20 ใช้เวลากี่วินาที
Throughput = ตึกนี้ขนคนขึ้นได้กี่คนต่อชั่วโมง

เพิ่มลิฟต์ = คนขึ้นได้เยอะขึ้น (throughput ดีขึ้น)
แต่ลิฟต์แต่ละตัวก็ยังใช้เวลาเท่าเดิม (latency เท่าเดิม)
```

```
🧠 ภาพจำ p50 / p95 / p99:
เข้าคิวธนาคาร 100 คน

p50 = คนที่ 50 รอกี่นาที      → "ปกติเป็นยังไง"
p95 = คนที่ 95 รอกี่นาที      → "วันซวยเป็นยังไง"
p99 = คนที่ 99 รอกี่นาที      → "ซวยสุดที่ยังต้องรับผิดชอบ"
avg = เอาเวลาทุกคนมาหารเฉลี่ย → "ตัวเลขที่ทำให้เราสบายใจผิด ๆ"
```

```
🧠 ภาพจำ Cache:
Cache = ตู้เย็นในห้อง เทียบกับ ซูเปอร์มาร์เก็ต

หยิบจากตู้เย็น = 5 วินาที (cache hit)
ขับไปซูเปอร์   = 30 นาที (cache miss)
ของในตู้เย็นอาจหมดอายุ = stale data
```

```
🧠 ภาพจำ N+1:
ไปส่งของ 100 บ้านในซอยเดียวกัน
N+1 = ขับกลับโกดังทุกครั้งที่ส่งเสร็จ 1 บ้าน
วิธีที่ถูก = ขนของ 100 ชิ้นไปรอบเดียว
```

## 5. How It Works

### 5.1 Flow รวม — request หนึ่งครั้งเสียเวลาที่ไหนบ้าง

```
[USER คลิก]
      ↓
[BROWSER]   parse HTML / โหลด JS bundle / execute       ← Bundle, Code Split
      ↓
[NETWORK]   DNS → TCP → TLS → Request                   ← ค่าเดินทาง
      ↓
[CDN]       ถ้าเป็นไฟล์ static จบตรงนี้เลย               ← Cache ชั้น 1
      ↓
[LOAD BALANCER]  เลือก server ที่ว่าง
      ↓
[BACKEND]   auth → business logic → serialize            ← CPU / Memory
      ↓
[CACHE]     มีใน Redis ไหม? มี → ตอบเลย                  ← Cache ชั้น 2
      ↓ miss
[DATABASE]  query → index → อ่าน disk                    ← Query / Index / N+1
      ↓
[NETWORK]   ส่ง response กลับ                            ← ขนาด payload
      ↓
[BROWSER]   parse JSON → setState → render → paint       ← Re-render
      ↓
[USER เห็นผล]
```

> **ให้มองภาพนี้ว่า** "ทุกลูกศรคือที่ที่เวลาหายไปได้ และเครื่องมือวัดแต่ละตัวส่องเห็นได้แค่บางลูกศรเท่านั้น"

### 5.2 ชั้นที่ 1 — Frontend

**Network (ฝั่ง browser)**

```
[DNS Lookup]    หา IP ของ domain
      ↓
[TCP Handshake] จับมือเปิดการเชื่อมต่อ   1 รอบไป-กลับ
      ↓
[TLS Handshake] แลกกุญแจเข้ารหัส        1-2 รอบไป-กลับ
      ↓
[HTTP Request]  ส่งคำขอ
      ↓
[TTFB]          ไบต์แรกกลับมา          ← ตัวเลขที่ใช้ตัดชั้น
      ↓
[Download]      ดาวน์โหลดเนื้อ ขึ้นกับขนาด
```

> **ให้มองภาพนี้ว่า** "ก่อนได้ข้อมูลไบต์แรก เราจ่ายค่าเดินทางไป-กลับหลายรอบไปแล้ว ซึ่งลดได้ด้วยการลดจำนวน request ไม่ใช่ลดขนาดอย่างเดียว"

| ปัญหา | ทางแก้หลัก | เหตุผล |
|---|---|---|
| request เยอะเกิน | รวม request / HTTP/2 multiplexing | ค่าเดินทางต่อรอบแพงกว่าค่าข้อมูล |
| ไฟล์ใหญ่ | compress (gzip/brotli) | ลดไบต์ที่ต้องเดินทาง |
| server ไกลผู้ใช้ | CDN | ลดระยะทางทางกายภาพ |
| โหลดซ้ำทุกครั้ง | `Cache-Control` | ไม่โหลดใหม่เลย = เร็วที่สุด |

**Rendering — เส้นทางจาก HTML ถึงภาพบนจอ**

```
[HTML] → [DOM] ─┐
[CSS]  → [CSSOM]┴→ [Render Tree]
                        ↓
                    [Layout]     คำนวณตำแหน่ง/ขนาด   ← แพงที่สุด
                        ↓
                    [Paint]      ระบายสี
                        ↓
                    [Composite]  ซ้อน layer          ← ถูกที่สุด
```

> **ให้มองภาพนี้ว่า** "การเปลี่ยนสิ่งที่กระทบขนาดหรือตำแหน่ง บังคับให้ browser คำนวณใหม่ตั้งแต่ Layout ซึ่งแพงกว่าการเปลี่ยนแค่สีหรือเลื่อนด้วย transform มาก"

- animate ด้วย `transform` / `opacity` → กระทบแค่ Composite = ลื่น
- animate ด้วย `width` / `top` / `margin` → บังคับ Layout ใหม่ทุกเฟรม = กระตุก
- อ่านค่าขนาดจาก DOM สลับกับเขียนใน loop → **layout thrashing** (คำนวณ layout ซ้ำ ๆ)

**Re-render (React)**

```
[State เปลี่ยน]
      ↓
[Component นั้น re-render]
      ↓
[ลูกทุกตัว re-render ตาม (โดย default)]
      ↓
[Virtual DOM diff]
      ↓
[แก้ DOM จริงเฉพาะส่วนที่ต่าง]
```

> **ให้มองภาพนี้ว่า** "re-render ไม่ได้แปลว่า DOM ถูกแก้ แต่แปลว่า React ต้องคิดใหม่ทั้งต้นไม้ ซึ่งฟรีเมื่อ component เล็ก และแพงมากเมื่อมีห้าพันตัว"

| สาเหตุ | อาการ | ทางแก้ |
|---|---|---|
| state อยู่สูงเกินไป | พิมพ์ 1 ตัวอักษร → ทั้งหน้าคิดใหม่ | ย้าย state ลงไปใกล้จุดที่ใช้ |
| ส่ง object/function ใหม่ทุกรอบเป็น props | `memo` ไม่ทำงาน | `useMemo` / `useCallback` |
| render list ยาวมาก | scroll กระตุก | Virtualization (วาดเฉพาะที่เห็น) |
| คำนวณหนักใน render | ทุก keystroke ช้า | `useMemo` หรือย้ายออกนอก render |
| ทำงานทุก keystroke | ยิง API รัว | Debounce |

**Bundle / Code Splitting / Lazy Loading**

```
ก่อน:  [app.js 2.5MB]  ← ต้องโหลด+parse+execute จบก่อนเห็นอะไร

หลัง:  [main.js 180KB]   โหลดทันที
             ↓ ผู้ใช้กดเข้าหน้า report
       [report.js 400KB] ค่อยโหลดตอนนั้น
             ↓ ผู้ใช้เปิด chart
       [chart.js 600KB]  ค่อยโหลดตอนนั้น
```

> **ให้มองภาพนี้ว่า** "Code Splitting คือการเลิกบังคับให้ผู้ใช้ดาวน์โหลดทั้งห้างสรรพสินค้า เพียงเพราะเขาอยากเข้าร้านเดียว"

| คำ | คืออะไร | ใช้เมื่อไร |
|---|---|---|
| Code Splitting | แบ่ง bundle ตาม route/feature | หน้าที่ผู้ใช้ส่วนใหญ่ไม่เข้า |
| Lazy Loading | เลื่อนโหลดจนถึงตอนต้องใช้ | modal, chart, editor, รูปล่างจอ |
| Tree Shaking | ตัด code ที่ไม่ถูก import ตอน build | ได้ฟรีถ้าใช้ ES module |
| Dynamic Import | ไวยากรณ์ที่ทำให้ split เกิดจริง | `import()` ในจุดที่ต้องการแบ่ง |

**Image** — มักเป็นตัวการอันดับหนึ่งของน้ำหนักหน้าเว็บ มากกว่า JS เสียอีก

| เทคนิค | ทำอะไร | ได้อะไร |
|---|---|---|
| Resize ให้พอดีจอ | ไม่ส่งรูป 4000px ไปแสดงในกล่อง 400px | ลดไบต์มหาศาล |
| Format ใหม่ (WebP/AVIF) | codec ที่บีบดีกว่า JPEG | เล็กลงที่คุณภาพเท่าเดิม |
| `loading="lazy"` | ไม่โหลดรูปที่ยังไม่ถึงจอ | first load เร็วขึ้นมาก |
| กำหนด width/height | จองพื้นที่ไว้ก่อน | กัน CLS (หน้าเด้ง) |
| Responsive `srcset` | ส่งขนาดตามอุปกรณ์ | มือถือไม่โหลดรูป desktop |

### 5.3 ชั้นที่ 2 — Backend

แกนของ backend performance คือแยกให้ออกว่า **ช้าเพราะคิด หรือช้าเพราะรอ**

```
[งานเข้ามา]
      ↓
  ช้าเพราะอะไร?
      ├── CPU สูง 90%+   → CPU Bound  (encrypt, resize, JSON ใหญ่, loop ซ้อน)
      └── CPU ต่ำ แต่ช้า → I/O Bound  (รอ DB, API ภายนอก, disk, network)
```

> **ให้มองภาพนี้ว่า** "CPU สูงแปลว่าครัวทำอาหารไม่ทัน ส่วน CPU ต่ำแต่ช้าแปลว่าครัวว่างแต่ยังรอของจากซัพพลายเออร์อยู่"

| ประเภท | อาการ | แก้ด้วย | **ห้ามแก้ด้วย** |
|---|---|---|---|
| CPU Bound | CPU เต็ม, event loop lag | ลดงาน, cache ผล, worker thread, เพิ่มเครื่อง | เพิ่ม concurrency (ยิ่งแย่) |
| I/O Bound | CPU ว่าง แต่ latency สูง | async/parallel, pool, cache, batch | เพิ่ม CPU (ไม่ช่วย) |

**Memory**

```
[Allocate] → [Use] → [GC เก็บคืนเมื่อไม่มีใครอ้างถึง]
                          ↓
        ถ้ายังมีใครอ้างถึงทั้งที่ไม่ใช้แล้ว → Memory Leak
```

> **ให้มองภาพนี้ว่า** "memory leak ไม่ใช่การลืมคืนของ แต่เป็นการเผลอถือของไว้ในมือทั้งที่ไม่ต้องใช้แล้ว ทำให้คนเก็บของไม่กล้าเอาไปทิ้ง"

สาเหตุที่เจอบ่อยจริง: เก็บของลง global/Map ที่ไม่มีวันลบ (ทำ cache เองแบบไม่มี limit), ลืม `removeEventListener`, ลืม clear `setInterval`, closure จับ object ใหญ่ไว้, เก็บ response ทุกอันไว้ "เผื่อ debug"

```
Memory
  │                        ╱  ← leak: ขึ้นเรื่อย ๆ ไม่ลงเลย
  │                    ╱
  │    ╱╲  ╱╲  ╱╲  ╱      ← ปกติ: ขึ้นแล้วลงหลัง GC
  │  ╱   ╲╱  ╲╱  ╲╱
  └────────────────────── เวลา
```

> **ให้มองภาพนี้ว่า** "memory ที่ขึ้น ๆ ลง ๆ คือระบบสุขภาพดี ส่วน memory ที่ขึ้นอย่างเดียวคือระบบกำลังเดินไปหาวันที่มันจะล่ม"

**I/O และการทำงานขนาน**

```
Sequential: [A 200ms] → [B 300ms] → [C 250ms]  = 750ms

Parallel:   [A 200ms] ┐
            [B 300ms] ├─ พร้อมกัน              = 300ms
            [C 250ms] ┘
```

> **ให้มองภาพนี้ว่า** "ถ้างานสามอย่างไม่ต้องรอผลของกันและกัน การทำทีละอันคือการจ่ายเวลาฟรี"

แต่ trade-off คือ ยิงขนานมากเกินไปจะ **ทับ database ตายเอง** ต้องมีเพดาน (concurrency limit)

### 5.4 ชั้นที่ 3 — Database

**Query & Index**

```
ไม่มี Index: [WHERE user_id = 42] → [อ่านทีละแถวครบ 10,000,000 แถว] → คืน 12 แถว
                                      └─── Full Table Scan ───┘

มี Index:    [WHERE user_id = 42] → [เปิดสารบัญ → กระโดดตรงจุด]   → คืน 12 แถว
```

> **ให้มองภาพนี้ว่า** "index คือสารบัญท้ายเล่ม การไม่มี index คือการอ่านหนังสือทั้งเล่มเพื่อหาคำเดียว"

| หลัก | เหตุผล |
|---|---|
| index ช่วย read แต่ทำให้ write ช้าลง | ทุก insert/update ต้องอัปเดต index ด้วย |
| ใส่ index ทุกคอลัมน์ = ผิด | เปลืองที่ write ช้า planner สับสน |
| index ต้องมาจาก query จริงที่ช้า | ไม่ใช่มาจากการเดา |
| ใช้ `EXPLAIN` ยืนยันว่าใช้ index จริง | บางที index มีแต่ไม่ถูกใช้ |
| ฟังก์ชันครอบคอลัมน์มักทำให้ index ใช้ไม่ได้ | เช่น `WHERE LOWER(email) = ...` |

**N+1 Query — ปัญหาอันดับหนึ่งของระบบที่ใช้ ORM**

```
ผิด:  [SELECT * FROM posts]                  ← 1 query ได้ 100 posts
           ↓ for each post
      [SELECT * FROM users WHERE id = ?]     ← อีก 100 queries  = รวม 101

ถูก:  [SELECT * FROM posts]
           ↓
      [SELECT * FROM users WHERE id IN (…)]  ← 1 query ทีเดียว  = รวม 2
```

> **ให้มองภาพนี้ว่า** "N+1 คือการกลับไปโกดังใหม่ทุกครั้งที่ต้องหยิบของชิ้นเดียว ทั้งที่หยิบทีเดียวร้อยชิ้นก็ได้"

อาการที่ใช้จับได้เร็ว: แต่ละ query เร็วมาก (2ms) แต่ endpoint ช้า (800ms) / จำนวน query แปรผันตามจำนวนแถวที่แสดง / log เต็มไปด้วย query หน้าตาเหมือนกันเป๊ะ ต่างแค่ id

**Connection Pool**

```
ไม่มี Pool: [Request] → [เปิด connection ใหม่ (แพง)] → [query] → [ปิด]

                       ┌── conn 1 ──┐
มี Pool:  [Request] → [Pool]── 2 ───┤ → [Database]
                       └── conn 3 ──┘   (ยืม → คืน → คนต่อไปใช้ต่อ)
```

> **ให้มองภาพนี้ว่า** "connection pool คือรถเช่าที่คืนแล้วคนต่อไปขับต่อได้เลย แทนที่จะซื้อรถใหม่ทุกครั้งที่จะออกไปข้างนอก"

| ตั้งค่า | ผลที่ได้ |
|---|---|
| pool เล็กเกิน | request ไปกองรอ connection — latency พุ่งทั้งที่ DB ยังว่าง |
| pool ใหญ่เกิน | DB รับ connection เกินกำลัง — ช้าลงทั้งระบบ |
| ลืมคืน connection (leak) | pool หมด → ระบบค้างทั้งหมดในไม่กี่นาที |
| timeout ยาวเกิน | request ค้างรอยาว แทนที่จะ fail เร็วแล้วลองใหม่ |

### 5.5 ชั้นที่ 4 — Infrastructure

**Scaling**

```
Vertical (ขยายขึ้น):    [Server 2 CPU] → [Server 16 CPU]
                        ง่าย ไม่ต้องแก้ code แต่มีเพดาน + เป็นจุดตายจุดเดียว

                                     ┌── Server 1
Horizontal (ขยายออก):  [Load Balancer]├── Server 2
                                     └── Server 3
                        ไม่มีเพดานชัด ทนเครื่องพัง แต่ code ต้อง stateless
```

> **ให้มองภาพนี้ว่า** "ขยายขึ้นคือซื้อเตาที่ใหญ่ขึ้น ขยายออกคือเปิดครัวเพิ่มอีกห้อง — อย่างหลังรองรับได้ไม่จำกัดกว่า แต่ต้องออกแบบให้ครัวทุกห้องทำงานแทนกันได้"

**เงื่อนไขของ horizontal scaling:** application ต้อง **stateless** — ถ้าเก็บ session ใน memory ของเครื่อง ผู้ใช้ที่ถูกส่งไปอีกเครื่องจะหลุด login ทันที ต้องย้าย state ไปไว้ที่ Redis/Database

**Load Balancer**

```
[Users]
   ↓
[Load Balancer] ── health check ──┐
   ├── Server A (healthy)         │
   ├── Server B (healthy)         │
   └── Server C (unhealthy) ✗ ────┘ ถูกตัดออกจากคิวอัตโนมัติ
```

> **ให้มองภาพนี้ว่า** "load balancer คือพนักงานหน้าร้านที่ทั้งแบ่งลูกค้าให้พนักงานที่ว่าง และเลิกส่งลูกค้าให้คนที่ป่วยแล้ว"

| Algorithm | ทำงานยังไง | เหมาะเมื่อ |
|---|---|---|
| Round Robin | วนส่งทีละเครื่อง | request ใช้ทรัพยากรพอ ๆ กัน |
| Least Connections | ส่งให้เครื่องที่งานน้อยสุด | request หนักเบาไม่เท่ากัน |
| IP Hash / Sticky | ผู้ใช้เดิมไปเครื่องเดิม | จำเป็นเมื่อยังมี state ในเครื่อง (ควรเลี่ยง) |

**Cache — เครื่องมือเร่งที่แรงที่สุด และอันตรายที่สุด**

```
[Browser Cache]     เร็วที่สุด — ไม่ยิง network เลย
      ↓ miss
[CDN Cache]         ใกล้ผู้ใช้ — static asset, รูป
      ↓ miss
[Application Cache] Redis — ผลลัพธ์ที่คำนวณแล้ว
      ↓ miss
[Database Cache]    buffer pool ภายใน DB เอง
      ↓ miss
[Disk]              ช้าที่สุด
```

> **ให้มองภาพนี้ว่า** "cache คือชั้นวางของหลายชั้นเรียงจากใกล้มือที่สุดไปไกลที่สุด และทุกชั้นที่หยิบไม่เจอ คือค่าเดินทางเพิ่มหนึ่งรอบ"

หัวใจของ cache ไม่ใช่การใส่ แต่คือ **การเอาออกเมื่อข้อมูลเปลี่ยน (invalidation)**

| กลยุทธ์ | วิธี | trade-off |
|---|---|---|
| TTL | ตั้งอายุ เช่น 60 วินาที | ง่ายสุด แต่ข้อมูลเก่าได้ถึง 60 วินาที |
| Write-through | เขียน DB พร้อมอัปเดต cache | ข้อมูลตรงเสมอ แต่ write ช้าลง |
| Cache-aside | อ่านไม่เจอค่อยโหลดแล้วใส่ | ใช้บ่อยที่สุด ต้องระวัง stampede |
| Explicit invalidation | ลบ key ตอนข้อมูลเปลี่ยน | ตรงที่สุด แต่ลืมง่ายที่สุด |

**สิ่งที่ห้าม cache:** ข้อมูลส่วนตัวที่ใช้ key ร่วมกันทั้งระบบ เพราะจะกลายเป็นช่องโหว่ข้อมูลรั่วข้ามผู้ใช้ทันที

## 6. Example

### สถานการณ์จริง: หน้า Dashboard ร้านอาหารช้า 6 วินาที

ทีมได้รับ ticket: *"หน้า Dashboard ของร้านช้ามาก ลูกค้าบ่นกันเยอะ"*

**สิ่งที่ junior ทำ (ผิด):** เปิด code แล้วเริ่มใส่ `useMemo` ทุกที่ในหน้า Dashboard

**สิ่งที่ควรทำ — เดินตาม Measure Before Optimize**

**ขั้น 1 — ทำให้ "ช้า" กลายเป็นตัวเลข**

| คำถาม | คำตอบที่ได้ |
|---|---|
| ช้าเท่าไร | p50 = 1.2s, p95 = 5.8s, p99 = 9.1s |
| ช้าตั้งแต่เมื่อไร | เริ่มแย่ชัดเจนเมื่อ 3 สัปดาห์ก่อน |
| ช้าทุกคนไหม | ร้านเล็กเร็ว ร้านใหญ่ช้ามาก |
| ช้าตลอดเวลาไหม | ช้าสุดช่วง 11:00-13:00 |

สังเกตว่า **ค่าเฉลี่ยบอกว่า "ก็ประมาณ 2 วินาที ไม่แย่"** แต่ p95 บอกความจริงคนละเรื่อง
และข้อมูล "ร้านใหญ่ช้ากว่า" เป็นเบาะแสว่าเวลาแปรผันตาม **จำนวนข้อมูล** → กลิ่น database

**ขั้น 2 — หาว่าชั้นไหน**

เปิด DevTools Network:

```
GET /api/dashboard      →  TTFB 5.2s   Download 0.1s   ขนาด 240KB
```

TTFB 5.2 วินาที = **server ยังไม่ทันเริ่มส่งไบต์แรกด้วยซ้ำ**
แปลว่าปัญหา**ไม่ได้อยู่ที่ Frontend** — bundle, re-render, รูป ไม่เกี่ยวเลย

> ถ้าไม่ได้ทำขั้นนี้ ทีมจะเสียเวลาสองสัปดาห์ optimize React ฟรี ๆ

**ขั้น 3 — เจาะเข้าไปใน Backend**

ดู trace ของ endpoint นี้:

```
GET /api/dashboard  total 5200ms
  ├── auth check              12ms
  ├── getShopInfo             8ms
  ├── getOrdersToday          4850ms   ← ตัวการ
  ├── calculateSummary        180ms
  └── serialize JSON          150ms
```

**ขั้น 4 — เจาะเข้าไปใน `getOrdersToday`**

ดู query log พบว่า endpoint นี้ยิง query **1,240 ครั้ง**

```
SELECT * FROM orders WHERE shop_id = ? AND date = ?     ← 1 ครั้ง (420 แถว)
SELECT * FROM users WHERE id = ?                        ← 420 ครั้ง
SELECT * FROM order_items WHERE order_id = ?            ← 420 ครั้ง
```

= **N+1 ซ้อนสองชั้น** และร้านใหญ่มี order เยอะ จึงช้ากว่าร้านเล็กพอดี ตรงกับเบาะแสขั้น 1

รัน `EXPLAIN` กับ query แรกเพิ่มเติม พบว่าเป็น **Full Table Scan** เพราะไม่มี index บน `(shop_id, date)`

**ขั้น 5 — แก้ทีละอย่าง แล้ววัดทุกครั้ง**

| ครั้งที่ | แก้อะไร | p95 ก่อน | p95 หลัง |
|---|---|---|---|
| 1 | เพิ่ม index `(shop_id, date)` | 5.8s | 3.1s |
| 2 | แก้ N+1 ของ users (ใช้ `IN`) | 3.1s | 1.4s |
| 3 | แก้ N+1 ของ order_items | 1.4s | 0.6s |
| 4 | cache summary 60 วินาที | 0.6s | 0.25s |

**ขั้น 6 — รู้ว่าพอเมื่อไร**

requirement ที่ตกลงกับ product คือ p95 < 1 วินาที
ทำถึงข้อ 3 ก็ผ่านแล้ว — ข้อ 4 ทำเพิ่มเพราะราคาถูกและไม่ซับซ้อน

แต่ทีมตัดสินใจ **ไม่ทำ** ข้อ 5 ที่เสนอไว้ (แยก read replica + precompute เป็น materialized view)
เพราะจะเพิ่มความซับซ้อนมากเพื่อกำไรอีก 0.1s ที่ผู้ใช้ไม่รู้สึก

> นี่คือคำตอบของคำถาม "เมื่อไรควรหยุด optimize" — **หยุดเมื่อผ่าน requirement และกำไรถัดไปไม่คุ้มความซับซ้อน**

### ตัวอย่างที่สอง (สั้น): ปุ่มค้นหากระตุกตอนพิมพ์

| ขั้น | สิ่งที่ทำ | สิ่งที่พบ |
|---|---|---|
| วัด | React Profiler | ทุก keystroke re-render 3,400 components |
| หาคอขวด | ดูว่าใคร render | `<SearchResults>` มี 1,200 rows และ state ของ input อยู่ที่ root |
| แก้ 1 | ย้าย input state ลงไปใน component ตัวเอง | ลดเหลือ 1,210 |
| แก้ 2 | virtualize list | ลดเหลือ ~30 |
| แก้ 3 | debounce การยิง API 300ms | ลด request จาก 12 → 1 ต่อคำค้น |

สังเกตว่า **ครั้งนี้ไม่ได้แตะ database เลย** เพราะการวัดชี้ไปคนละชั้น
นี่คือเหตุผลว่าทำไม "วัดก่อน" ถึงสำคัญกว่าการมีรายการวิธีแก้ในหัว

## 7. Compare

### ตารางหลัก: อาการ → ชั้นที่น่าสงสัย → เครื่องมือที่ใช้วัด

| อาการที่เจอ | ชั้นที่น่าสงสัย | เครื่องมือที่ใช้วัด | ตัวเลขที่ต้องดู |
|---|---|---|---|
| หน้าขาวนานก่อนเห็นอะไร | Frontend — Bundle | DevTools Network, Lighthouse, bundle analyzer | ขนาด JS, FCP, LCP |
| TTFB สูง แต่ download เร็ว | Backend หรือ Database | APM / trace, server log | TTFB, server time |
| Download นานแต่ TTFB เร็ว | Network / payload ใหญ่ | DevTools Network | ขนาด response, compression |
| พิมพ์แล้วหน่วง กดแล้วหน่วง | Frontend — Re-render | React Profiler, Performance tab | จำนวน component ที่ render, INP |
| Scroll กระตุก | Frontend — Rendering/Layout | Performance tab (frame chart) | long task, layout time |
| หน้าเด้งระหว่างโหลด | Frontend — Image/Layout | Lighthouse | CLS |
| ช้าเฉพาะตอนคนเยอะ | Infrastructure / Pool | metrics ของ LB, pool, CPU | req/s, CPU%, queue depth, pool wait |
| ช้าเท่ากันตลอด แม้คนน้อย | Backend หรือ Database (latency แท้) | trace, query log | p50 ของ endpoint |
| ช้าแปรผันตามจำนวนแถวที่แสดง | Database — N+1 | query log / ORM log | จำนวน query ต่อ 1 request |
| แต่ละ query เร็ว แต่รวมช้า | Database — N+1 | query log | count ของ query |
| query เดียวช้ามาก | Database — Index | `EXPLAIN` / slow query log | scan type, rows examined |
| CPU 100% | Backend — CPU Bound | top / CPU profiler / flame graph | CPU%, hot function |
| CPU ต่ำแต่ช้า | Backend — I/O Bound | trace, event loop lag metric | wait time |
| Memory ขึ้นเรื่อย ๆ ไม่ลง | Backend — Memory Leak | heap snapshot, memory metric | heap used trend |
| ระบบค้างพร้อมกันทั้งหมดกะทันหัน | Connection Pool หมด | pool metrics, DB connection count | active/idle/waiting |
| ผู้ใช้ต่างประเทศช้ากว่าคนไทย | Network / ไม่มี CDN | RUM, WebPageTest แยก region | latency แยกตามภูมิภาค |

> ตารางนี้คือของที่ควรจำติดตัวไปห้องสัมภาษณ์ ถ้าคุณตอบคำถาม "ระบบช้าทำยังไง" ด้วยการเริ่มจาก **อาการ → ชั้น → เครื่องมือ** คุณจะดูเหมือนคนที่เคยแก้ของจริง

### Latency vs Throughput

| หัวข้อ | Latency | Throughput |
|---|---|---|
| วัดอะไร | เวลาต่อ 1 request | จำนวน request ต่อวินาที |
| หน่วย | ms | req/s, QPS, TPS |
| ผู้ใช้รู้สึกยังไง | "มันช้า" | "มันล่มตอนคนเยอะ" |
| แก้ด้วย | ลดงานต่อ request, index, cache | เพิ่มเครื่อง, เพิ่ม concurrency, queue |
| เพิ่มเครื่องช่วยไหม | **ไม่ช่วย** | ช่วย |
| ตัวอย่างปัญหา | query 4 วินาที | รับได้ 200 req/s แต่คนยิงมา 2,000 |

### p50 vs p95 vs p99 vs Average

| ค่า | บอกอะไร | ใช้ทำอะไร | กับดัก |
|---|---|---|---|
| Average | ค่าเฉลี่ยรวม | เห็นแนวโน้มหยาบ ๆ | outlier ตัวเดียวทำให้เพี้ยน / ซ่อนหางยาว |
| p50 | คนทั่วไปเจออะไร | ดู baseline | ดีขึ้นแต่ p99 แย่ลงได้ |
| p95 | วันแย่ ๆ เป็นยังไง | ตั้ง SLA ส่วนใหญ่ใช้ตัวนี้ | ต้องมี traffic พอจะมีความหมาย |
| p99 | แย่สุดที่รับผิดชอบ | หา tail latency, GC pause, cold start | ผันผวนมากถ้า sample น้อย |

**ทำไมค่าเฉลี่ยหลอกเรา — สรุปสามข้อ**

1. ค่าเฉลี่ยถูกดึงโดยค่าสุดโต่งเพียงไม่กี่ค่า
2. ค่าเฉลี่ยซ่อน bimodal — เช่น cache hit 20ms กับ cache miss 900ms เฉลี่ยได้ 200ms ทั้งที่ **ไม่มีใครเจอ 200ms สักคน**
3. ผู้ใช้ไม่ได้เจอค่าเฉลี่ย ผู้ใช้เจอ request ของตัวเอง — และหน้าเดียวยิงหลาย request ทำให้โอกาสโดนหางยาวสูงกว่าที่ตัวเลขบอก

### Vertical vs Horizontal Scaling

| หัวข้อ | Vertical | Horizontal |
|---|---|---|
| ทำอะไร | เพิ่ม CPU/RAM เครื่องเดิม | เพิ่มจำนวนเครื่อง |
| แก้ code ไหม | ไม่ต้อง | ต้อง stateless |
| เพดาน | มี (ขนาดเครื่องใหญ่สุด) | แทบไม่มี |
| ทนเครื่องพัง | ไม่ทน (SPOF) | ทน |
| ราคา | ถูกตอนเริ่ม แพงตอนปลาย | แพงตอนเริ่ม คุ้มตอนปลาย |
| เหมาะเมื่อ | ระบบเล็ก-กลาง, database | stateless API, traffic ผันผวน |

### Debounce vs Throttle

| หัวข้อ | Debounce | Throttle |
|---|---|---|
| ทำงานยังไง | รอจนหยุดพิมพ์ครบ X ms แล้วค่อยทำ 1 ครั้ง | ทำมากสุด 1 ครั้งต่อ X ms |
| เหมาะกับ | search input, auto-save | scroll, resize, mousemove |
| ถ้าใช้สลับกัน | scroll จะไม่ทำงานเลยจนกว่าจะหยุด scroll | ยิง search รัวเกินจำเป็น |

### Cache ที่ชั้นไหน

| ชั้น | เร็วแค่ไหน | เก็บอะไร | ปัญหาหลัก |
|---|---|---|---|
| Browser | เร็วสุด (0 network) | static asset, response ที่ตั้ง header | invalidate ยากมาก ต้องใช้ hash ในชื่อไฟล์ |
| CDN | เร็วมาก | รูป, JS, CSS, หน้า public | purge ต้องสั่ง |
| Application (Redis) | เร็ว | ผลลัพธ์ query, session, computed | invalidation, stampede |
| Database internal | ปานกลาง | data page ที่เพิ่งอ่าน | ควบคุมไม่ได้ตรง ๆ |

## 8. Common Mistakes

| # | สิ่งที่ junior มักทำ | ทำไมผิด | สิ่งที่ถูก |
|---|---|---|---|
| 1 | Optimize ก่อนวัด | 80% ของเวลาจะไปแก้จุดที่ไม่ใช่คอขวด | วัดก่อนเสมอ แม้จะ "แน่ใจ" |
| 2 | ใช้ average ตัดสิน | ซ่อนคนที่เจอ 10 วินาที | ดู p95/p99 ควบคู่ |
| 3 | คิดว่า "ช้า" = ปัญหา frontend | TTFB มักชี้ไป backend/DB | ดู TTFB แยกจาก download เสมอ |
| 4 | ใส่ `useMemo`/`useCallback` ทุกที่ | memo เองก็มีต้นทุน + code อ่านยาก | ใส่หลังจาก profiler ชี้จุดแล้ว |
| 5 | คิดว่าเพิ่มเครื่องแก้ได้ทุกอย่าง | ไม่ช่วย latency, ไม่ช่วยถ้าคอขวดคือ DB | แยกให้ออกก่อนว่าเป็นปัญหา latency หรือ throughput |
| 6 | ใส่ index ทุกคอลัมน์ | write ช้าลง เปลือง disk | ใส่ตาม query จริงที่ช้า + ตรวจด้วย `EXPLAIN` |
| 7 | ใช้ ORM แล้วไม่ดู query ที่มันสร้าง | N+1 เกิดโดยที่ code ดูสะอาดมาก | เปิด query log ในเครื่อง dev เสมอ |
| 8 | Cache ทุกอย่างโดยไม่คิด invalidation | ผู้ใช้เห็นข้อมูลเก่า แก้ยากกว่าช้า | ตั้ง TTL + รู้ว่าลบเมื่อไร ตั้งแต่วันแรก |
| 9 | ทดสอบ performance บนเครื่องตัวเอง | เครื่อง dev เร็วกว่า + ข้อมูลน้อยกว่า production 1000 เท่า | วัดจาก production/staging ที่มีข้อมูลจริง |
| 10 | เพิ่ม connection pool ให้ใหญ่สุดไว้ก่อน | DB รับไม่ไหว ช้าลงทั้งระบบ | ตั้งตามกำลัง DB ไม่ใช่ตามความอยากของ app |
| 11 | โหลดข้อมูลทั้งหมดแล้วค่อยกรองใน JS | ส่ง 50,000 แถวมากรองเอา 20 แถว | กรอง/แบ่งหน้า (pagination) ที่ database |
| 12 | คิดว่า lazy loading คือแก้ทุกอย่าง | ทำให้กดแล้วรอโหลดแทน = ย้ายความช้า | lazy เฉพาะสิ่งที่ผู้ใช้ส่วนใหญ่ไม่ใช้ |
| 13 | วัดครั้งเดียวแล้วสรุป | โหลดแต่ละช่วงเวลาไม่เท่ากัน | วัดหลายครั้ง หลายช่วงเวลา ดู trend |
| 14 | แก้ 5 อย่างพร้อมกัน | ไม่รู้ว่าอันไหนได้ผล และอันไหนทำให้แย่ลง | แก้ทีละอย่าง วัดทีละครั้ง |
| 15 | ไม่มีเป้าหมายตัวเลข | optimize ไม่จบสิ้น เสียเวลาทีม | ตกลง requirement ก่อน เช่น "p95 < 1s" |
| 16 | ส่งรูปขนาดเต็มไปแสดงในกรอบเล็ก | รูปคือน้ำหนักหลักของหน้าเว็บ | resize + format ใหม่ + lazy |
| 17 | ยิง API แบบเรียงทั้งที่ไม่ต้องรอกัน | เสียเวลารวมฟรี | ยิงขนานเมื่อไม่มี dependency (แต่มีเพดาน) |
| 18 | คิดว่า performance เป็นงานตอนท้าย | แก้ architecture ทีหลังแพงมาก | คิดเรื่อง data access pattern ตั้งแต่ออกแบบ |

### โครงตอบ "Latency vs Throughput"

1. นิยามสั้น: latency = เวลาต่อคน, throughput = คนต่อเวลา
2. ภาพจำ: ร้านก๋วยเตี๋ยว 1 ชามกี่นาที vs เสิร์ฟได้กี่ชามต่อชั่วโมง
3. จุดที่แยกระดับ: "เพิ่มเครื่องช่วย throughput แต่ไม่ช่วย latency"
4. จุดเชื่อม: "แต่พอ throughput ตัน latency จะแย่ตาม เพราะ request ไปรอคิว"
5. ปิดด้วยการวัด: "เลยต้องดูคู่กันเสมอ ไม่ใช่ดูตัวเดียว"

### โครงตอบ "ทำไมไม่ดู average"

1. ยกตัวเลข: 99 ครั้ง 100ms + 1 ครั้ง 10s → avg 199ms ดูดี แต่มีคนรอ 10 วินาที
2. บอกว่า average ซ่อน bimodal: cache hit/miss เฉลี่ยได้ตัวเลขที่ไม่มีใครเจอจริง
3. บอกว่าใช้อะไรแทน: p50 ดู baseline, p95 ตั้ง SLA, p99 ดู tail
4. ต่อยอด: "หน้าเดียวยิง 20 API ทำให้โอกาสเจอ p99 สูงกว่าที่คนคิดมาก"

| อย่าพูด | พูดแบบนี้แทน |
|---|---|
| "ใส่ cache ครับ" (ทันที) | "ขอดูก่อนว่าคอขวดอยู่ไหน ถ้าเป็น read ซ้ำ ๆ cache จะคุ้ม แต่ต้องคุยเรื่อง invalidation" |

## 12. One-Minute Review

- **Performance = Latency (ช้าต่อคน) + Throughput (รับได้กี่คน)** สองอันนี้คนละเรื่อง และบางทีขัดกัน
- **เพิ่มเครื่องช่วย throughput ไม่ช่วย latency** — จำประโยคนี้ไปห้องสัมภาษณ์
- **ค่าเฉลี่ยหลอกเรา** ให้ดู p50 (ปกติ), p95 (วันแย่), p99 (หางยาว)
- **Measure Before Optimize** — วัด → หาคอขวด → ตั้งสมมติฐาน → แก้ทีละอย่าง → วัดซ้ำ → ถึงเป้าแล้วหยุด
- **ระบบเร็วเท่าคอขวด** — optimize ที่ไม่ใช่คอขวด = ไม่มีผล
- **ตัดชั้นด้วย TTFB** — TTFB สูง = backend/DB, TTFB ต่ำแต่รวมช้า = frontend/network
- **Frontend:** bundle, code splitting, lazy loading, image, re-render, virtualization, debounce
- **Backend:** แยก CPU bound (คิดหนัก) กับ I/O bound (รอ) เพราะวิธีแก้ตรงข้ามกัน
- **Database:** index (`EXPLAIN` ยืนยัน), N+1 (นับจำนวน query), connection pool (เล็กไปคิวยาว ใหญ่ไป DB ตาย)
- **Infrastructure:** horizontal scaling ต้อง stateless, load balancer ต้อง health check, cache ต้องคิด invalidation ตั้งแต่วันแรก
- **ทุกวิธีเร่งมีราคา** — พูดวิธีแก้แล้วต้องพูด trade-off เสมอ
- **หยุดเมื่อถึง requirement** ไม่ใช่หยุดเมื่อเร็วที่สุด

## 13. Memory Card

### จำ 5 อย่าง

1. **วัดก่อนแก้เสมอ** — Measure → Profile → Hypothesis → Fix One → Verify → Stop at target
2. **Latency ≠ Throughput** — เพิ่มเครื่องช่วยอันหลัง ไม่ช่วยอันแรก
3. **ดู p95/p99 ไม่ใช่ average** — ค่าเฉลี่ยซ่อนคนที่รอ 10 วินาที
4. **ระบบเร็วเท่าคอขวด** — 4 ชั้นคือ Frontend / Backend / Database / Infrastructure ตัดชั้นด้วย TTFB
5. **ทุกการเร่งมีราคา** — cache แลกความสด, index แลก write, split แลกการรอตอนกด

### Keyword Card

- **Latency** → เวลาที่ 1 คนรอ → วัดเป็น ms ดูด้วย percentile
- **Throughput** → งานที่เสร็จต่อวินาที → วัดเป็น req/s แก้ด้วยการขยาย
- **p50 / p95 / p99** → ปกติ / วันแย่ / หางยาว → ใช้ตั้ง SLA และหา tail latency
- **Bottleneck** → จุดที่ช้าที่สุด → กำหนดความเร็วของทั้งระบบ
- **TTFB** → ไบต์แรกกลับมาเมื่อไร → ใช้ตัดว่าปัญหาอยู่ฝั่ง client หรือ server
- **Bundle / Code Splitting / Lazy Loading** → ก้อน JS / แบ่งก้อน / เลื่อนโหลด → ลดเวลาโหลดแรก
- **Re-render / Memoization / Virtualization** → React คิดใหม่ / จำผลเดิม / วาดเฉพาะที่เห็น → แก้หน้าหน่วง
- **CPU Bound / I/O Bound** → ช้าเพราะคิด / ช้าเพราะรอ → วิธีแก้ตรงข้ามกัน
- **Memory Leak** → ถือของไว้ทั้งที่ไม่ใช้ → กราฟ memory ขึ้นอย่างเดียวไม่ลง
- **Index / Full Table Scan** → สารบัญ / อ่านทั้งเล่ม → ยืนยันด้วย `EXPLAIN`
- **N+1 Query** → ยิงซ้ำในลูป → จับได้ด้วยการนับ query ต่อ 1 request
- **Connection Pool** → สระท่อต่อ DB → เล็กไปคิวยาว ใหญ่ไป DB พัง
- **Cache / Hit / Miss / Invalidation** → ของใกล้มือ / เจอ / ไม่เจอ / เอาออกเมื่อเปลี่ยน → เร็วที่สุดแต่เสี่ยงข้อมูลเก่าที่สุด
- **CDN** → โกดังใกล้ผู้ใช้ → ลดระยะทางทางกายภาพของ static asset
- **Vertical / Horizontal Scaling** → เครื่องใหญ่ขึ้น / เครื่องเยอะขึ้น → อย่างหลังต้อง stateless
- **Load Balancer** → คนจัดคิว + ตัดเครื่องป่วยออก → หัวใจของ horizontal scaling
- **Premature Optimization** → แก้ก่อนรู้ปัญหา → จ่ายความซับซ้อนโดยไม่ได้ความเร็ว
