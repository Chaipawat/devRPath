## 1. Big Picture

ถ้าคุณเพิ่งเริ่มต้น และยังไม่รู้อะไรเลย ให้เริ่มจากประโยคเดียวนี้:

> **Software คือชุดคำสั่งที่บอกคอมพิวเตอร์ว่า "เมื่อผู้ใช้ทำแบบนี้ ให้ทำแบบนั้น"**

แค่นั้นจริง ๆ ส่วนที่เหลือทั้งหมด — React, Node.js, Docker, Kubernetes, Database — คือ **เครื่องมือที่คนคิดขึ้นมาเพื่อทำให้ชุดคำสั่งนั้นใหญ่ขึ้น เร็วขึ้น พังน้อยลง และมีคนหลายคนช่วยกันเขียนได้**

ทีนี้ลองนึกถึงเหตุการณ์ที่คุณทำทุกวัน:

คุณเปิดแอปธนาคารในมือถือ → กดปุ่ม "ดูยอดเงิน" → รอแป๊บนึง → ตัวเลขขึ้นมา

ระหว่าง "กดปุ่ม" กับ "ตัวเลขขึ้นมา" มีสิ่งที่เกิดขึ้นเยอะมาก และ **หนังสือทั้งเล่มนี้คือการอธิบายช่องว่างตรงนั้น**

เราจะแยกโลก software ออกเป็น 2 ฝั่งใหญ่ ๆ ก่อน แล้วค่อยเติมรายละเอียด:

| ฝั่ง | อยู่ที่ไหน | ใครเห็น | ทำอะไร |
|---|---|---|---|
| **Client** (ลูกค้า) | เครื่องของผู้ใช้ — browser หรือมือถือ | ผู้ใช้เห็นและกดได้ | แสดงผล + รับ input + ส่งคำขอ |
| **Server** (ผู้ให้บริการ) | เครื่องคอมพิวเตอร์ของบริษัท อยู่ใน data center | ผู้ใช้ไม่เห็น | คิด ตัดสินใจ เก็บข้อมูล ตอบกลับ |

**ทำไมต้องแยกเป็น 2 ฝั่ง?** เพราะข้อมูลจริง (เช่นยอดเงินของคุณ) **ห้ามอยู่ในมือถือคุณ** ถ้าอยู่ในมือถือ คุณก็แก้ตัวเลขเองได้ เงินก็เพิ่มเองได้ ดังนั้นข้อมูลและ "การตัดสินใจ" ต้องอยู่ฝั่ง server ที่เราคุมได้

นี่คือหลักการพื้นฐานที่สุดของ software engineering ทั้งหมด:
**สิ่งที่ผู้ใช้เห็น เชื่อไม่ได้ — สิ่งที่ server ตัดสิน เชื่อได้**

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย + ใช้ทำอะไร |
|---|---|---|
| **Software** | ชุดคำสั่ง | โปรแกรมที่สั่งให้คอมพิวเตอร์ทำงานตามที่เราต้องการ จับต้องไม่ได้ (ตรงข้ามกับ Hardware) |
| **Application (App)** | software ที่มีหน้าตาให้ใช้ | software ที่ทำงานเฉพาะเรื่องให้ผู้ใช้คนหนึ่งใช้ เช่น แอปธนาคาร แอปสั่งอาหาร |
| **Web Application** | แอปที่รันใน browser | แอปที่เปิดผ่าน URL ไม่ต้องติดตั้ง อัปเดตแล้วทุกคนได้ทันที |
| **Mobile Application** | แอปที่ติดตั้งในมือถือ | แอปที่โหลดจาก App Store / Play Store ใช้ความสามารถเครื่องได้ (กล้อง GPS notification) |
| **Frontend** | ส่วนที่เห็นและกด | โค้ดที่รันบนเครื่องผู้ใช้ ทำหน้าที่แสดงผลและรับ input |
| **Backend** | ส่วนที่คิดและจำ | โค้ดที่รันบน server ทำหน้าที่ตัดสินใจ ตรวจสอบสิทธิ์ และคุยกับ database |
| **Full-stack** | ทำได้ทั้งสองฝั่ง | คนที่เขียนได้ทั้ง frontend และ backend และสำคัญกว่านั้นคือ "เห็นภาพเชื่อมกัน" |
| **Client** | ฝั่งที่ขอ | ตัวที่ส่งคำขอ — browser, มือถือ, หรือแม้แต่ service อีกตัวก็เป็น client ได้ |
| **Server** | ฝั่งที่ตอบ | เครื่อง/โปรแกรมที่รอรับคำขอแล้วตอบกลับ ทำงาน 24 ชั่วโมง |
| **Database (DB)** | ที่เก็บความจำถาวร | ที่เก็บข้อมูลที่ต้องอยู่รอดแม้ปิดเครื่อง และค้นหาได้เร็ว |
| **API** | สัญญาว่าจะคุยกันยังไง | ประตูที่ backend เปิดไว้ให้ frontend เรียกใช้ โดยไม่ต้องรู้ว่าข้างในทำอะไร |
| **Network** | ถนนที่ข้อมูลวิ่ง | ระบบที่ทำให้เครื่องสองเครื่องคุยกันได้ข้ามโลก |
| **Infrastructure** | พื้นที่ที่ระบบยืนอยู่ | เครื่อง server, network, storage, ระบบ deploy — ของที่ต้องมีเพื่อให้โค้ดรันจริง |
| **Request** | คำขอ | ข้อความที่ client ส่งไปหา server บอกว่า "ฉันอยากได้/อยากทำอะไร" |
| **Response** | คำตอบ | ข้อความที่ server ส่งกลับ บอกว่า "ผลเป็นยังไง และนี่คือข้อมูล" |
| **Business Logic** | กฎของธุรกิจ | เงื่อนไขจริงของงาน เช่น "โอนเงินได้ถ้ายอดคงเหลือพอ" — หัวใจของระบบ |
| **Deploy** | เอาขึ้นใช้งานจริง | การนำโค้ดจากเครื่องเราไปรันบน server ให้ผู้ใช้จริงใช้ |
| **Production** | ของจริงที่ผู้ใช้ใช้อยู่ | environment ที่ผู้ใช้จริงกำลังใช้งาน — พังแล้วมีคนเดือดร้อนจริง |
| **Latency** | ความหน่วง | เวลาที่ใช้ตั้งแต่ส่ง request จนได้ response กลับมา |
| **Scalable** | ขยายรับคนเพิ่มได้ | ระบบที่เมื่อคนใช้เพิ่ม 10 เท่า ยังทำงานได้โดยไม่ต้องเขียนใหม่ทั้งหมด |

## 3. Mental Model

ให้มองระบบ software เป็น **"ร้านอาหาร"** ไม่ใช่ "โค้ดกองหนึ่ง"

| ในร้านอาหาร | ในระบบ software | หน้าที่จริง |
|---|---|---|
| ลูกค้า | User | คนที่มีความต้องการ |
| เมนู + โต๊ะ + หน้าร้าน | Frontend | สิ่งที่ลูกค้าเห็นและสั่งได้ |
| พนักงานเสิร์ฟ | API / HTTP | ตัวรับออเดอร์ไปส่งครัว และเอาอาหารกลับมา |
| ครัว | Backend | ที่ทำงานจริง ตัดสินใจจริง |
| สูตรอาหาร + กฎร้าน | Business Logic | "ถ้าของหมด ห้ามรับออเดอร์" |
| ตู้เย็น / คลังของ | Database | ที่เก็บวัตถุดิบถาวร ค้นหาได้ |
| ตัวอาคาร ไฟ น้ำ แก๊ส | Infrastructure | ของที่ต้องมีร้านถึงเปิดได้ |
| กล้องวงจรปิด + บิลขาย | Logs / Metrics | หลักฐานว่าเกิดอะไรขึ้นบ้าง |

**สิ่งที่ mental model นี้ช่วยได้จริงตอนสัมภาษณ์:**

- ถามว่า "ทำไมต้องมี backend ในเมื่อ frontend เขียนได้หมด?"
  → ตอบ: "เพราะลูกค้าห้ามเดินเข้าครัว — validation และสิทธิ์ต้องตัดสินในที่ที่ลูกค้าแก้ไม่ได้"
- ถามว่า "หน้าเว็บช้า จะเริ่มดูตรงไหน?"
  → ตอบ: "ดูก่อนว่าช้าที่หน้าร้าน (render) ช้าที่พนักงานเดิน (network) หรือช้าที่ครัว (backend/DB)"

**กฎเหล็กของ mental model นี้:**
ปัญหาทุกอย่างในระบบ **เกิดที่ชั้นใดชั้นหนึ่ง** งานของ engineer คือ "ระบุชั้น" ให้ได้ก่อน แล้วค่อยลงรายละเอียด

## 5. How It Works

### 5.1 ภาพใหญ่: หนึ่ง Request เดินทางอย่างไร

```
[USER]                      กดปุ่ม "ดูยอดเงิน"
   ↓
[BROWSER / MOBILE]          เครื่องของผู้ใช้
   ↓
[FRONTEND]                  React / Next.js / React Native
   |                        เตรียมคำขอ แล้วยิงออกไป
   ↓
[HTTP REQUEST]              GET /api/accounts/123/balance
   ↓
[NETWORK / INTERNET]        DNS → IP → เดินทางข้ามโลก
   ↓
[BACKEND]                   Node.js+Express / Spring Boot / Python
   ↓
[AUTH]                      "คุณเป็นใคร? มีสิทธิ์ดูบัญชีนี้ไหม?"
   ↓
[BUSINESS LOGIC]            "ถ้าบัญชีถูกระงับ ห้ามแสดงยอด"
   ↓
[DATABASE]                  SELECT balance FROM accounts WHERE id=123
   ↓
[RESPONSE]                  200 OK  { "balance": 12450 }
   ↓
[FRONTEND]                  รับข้อมูล → เก็บใส่ state
   ↓
[UI UPDATE]                 ตัวเลขขึ้นบนหน้าจอ
```

> **ให้มองภาพนี้ว่า** "คำขอหนึ่งครั้งคือการเดินทางไปกลับ ที่ทุกด่านมีสิทธิ์ปฏิเสธหรือทำให้ช้าได้ — และหน้าที่เราคือรู้ว่าแต่ละด่านทำอะไร"

### 5.2 ซูมเข้าไปดู Frontend กับ Backend แยกกัน

```
FRONTEND ภายใน
─────────────────
[USER EVENT]  คลิก / พิมพ์
     ↓
[STATE]       ข้อมูลที่หน้าจอกำลังถืออยู่
     ↓
[RENDER]      วาดหน้าจอใหม่ตาม state
     ↓
[UI]          สิ่งที่ตาเห็น
```

> **ให้มองภาพนี้ว่า** "Frontend คือฟังก์ชันที่รับ state เข้าไปแล้วพ่นหน้าจอออกมา — state เปลี่ยน หน้าจอต้องเปลี่ยนตาม"

```
BACKEND ภายใน
─────────────────
[ROUTE]        รับรู้ว่า URL นี้ใครดูแล
     ↓
[MIDDLEWARE]   ตรวจ token / log / validate
     ↓
[CONTROLLER]   แปลง request เป็นคำสั่งงาน
     ↓
[SERVICE]      Business Logic ตัวจริง
     ↓
[REPOSITORY]   คุยกับ Database
     ↓
[DATABASE]
```

> **ให้มองภาพนี้ว่า** "Backend คือสายพานที่ request ต้องเดินผ่านทีละสถานี และแต่ละสถานีมีหน้าที่เดียวชัดเจน"

### 5.3 Infrastructure — โค้ดของเรารันอยู่บนอะไร

```
[CODE]                  โค้ดที่เราเขียน
   ↓
[DOCKER IMAGE]          แพ็กโค้ด + สิ่งที่ต้องใช้รัน ไว้ด้วยกัน
   ↓
[CONTAINER]             กล่องที่รันจริง
   ↓
[KUBERNETES]            ผู้จัดการที่ดูแลว่ามีกี่กล่อง กล่องไหนตาย
   ↓
[CLOUD / SERVER]        เครื่องจริงใน data center
   ↓
[INTERNET]              ผู้ใช้เข้าถึงได้
```

> **ให้มองภาพนี้ว่า** "Infrastructure คือการเอาโค้ดใส่กล่อง แล้วจ้างผู้จัดการมาคอยดูว่ากล่องยังมีชีวิตอยู่ครบตามจำนวนที่สั่งไว้"

### 5.4 Network — ทำไม request ถึงหา server เจอ

```
[BROWSER]  พิมพ์ app.example.com
   ↓
[DNS]      "ชื่อนี้ = IP 203.0.113.25"     ← สมุดโทรศัพท์ของอินเทอร์เน็ต
   ↓
[IP]       รู้ว่าจะไปเครื่องไหน
   ↓
[PORT]     รู้ว่าจะไปคุยกับโปรแกรมตัวไหนในเครื่องนั้น (443 = HTTPS)
   ↓
[SERVER]   รับคำขอ
```

> **ให้มองภาพนี้ว่า** "IP คือเลขที่บ้าน Port คือเลขห้อง และ DNS คือคนที่แปลงชื่อร้านให้เป็นที่อยู่จริง"

## 6. Example — Scenario จากงานจริง

### Scenario: ระบบสั่งอาหารออนไลน์ ผู้ใช้กด "สั่งซื้อ"

**สิ่งที่ผู้ใช้เห็น:** กดปุ่ม → หมุน ๆ 1 วินาที → ขึ้น "สั่งซื้อสำเร็จ #10293"

**สิ่งที่เกิดขึ้นจริงข้างหลัง:**

| ลำดับ | ชั้น | เกิดอะไรขึ้น | ถ้าชั้นนี้พัง ผู้ใช้เห็นอะไร |
|---|---|---|---|
| 1 | Frontend | ตรวจว่ากรอกที่อยู่ครบไหม (ตรวจเพื่อ UX เท่านั้น) | ปุ่มกดไม่ได้ / ขึ้น error ใต้ช่อง |
| 2 | Frontend | disable ปุ่มกันกดซ้ำ + แสดง loading | กดซ้ำได้ → สั่งซ้ำ 2 ออเดอร์ |
| 3 | Network | ยิง `POST /api/orders` ผ่าน HTTPS | หมุนค้าง แล้ว timeout |
| 4 | Backend — Auth | ตรวจ token ว่า login อยู่จริงไหม | ขึ้น "กรุณาเข้าสู่ระบบใหม่" |
| 5 | Backend — Validation | ตรวจซ้ำอีกรอบ ว่าที่อยู่ครบ ราคาถูกต้อง | 400 Bad Request |
| 6 | Backend — Business Logic | ของยังมีสต็อกไหม ร้านเปิดอยู่ไหม โปรโมชันใช้ได้ไหม | "สินค้าหมด" / "ร้านปิดแล้ว" |
| 7 | Database | บันทึกออเดอร์ + ตัดสต็อก ใน transaction เดียว | 500 / ออเดอร์หาย |
| 8 | Backend | ส่งงานเข้า queue ให้ระบบส่งอีเมล/แจ้งร้าน | ออเดอร์สำเร็จแต่ร้านไม่รู้ |
| 9 | Response | ตอบ `201 Created` + เลขออเดอร์ | — |
| 10 | Frontend | อัปเดต state → เปลี่ยนหน้าไปหน้า "ติดตามออเดอร์" | ค้างที่หน้าเดิม |

**สิ่งที่ interviewer อยากได้ยินจาก scenario นี้:**

1. **Validation ทำ 2 ที่** — frontend ทำเพื่อ UX (ตอบเร็ว), backend ทำเพื่อความถูกต้อง (เชื่อได้) — ไม่ใช่ทำซ้ำเปล่า ๆ
2. **ตัดสต็อกกับบันทึกออเดอร์ต้องอยู่ด้วยกัน** — ถ้าอย่างใดอย่างหนึ่งสำเร็จอย่างเดียว ข้อมูลจะเพี้ยน (นี่คือที่มาของ Transaction)
3. **งานที่ไม่ต้องรอ ให้ยกออกไป** — ส่งอีเมลไม่ควรทำให้ผู้ใช้รอ (นี่คือที่มาของ Queue / Background Job)
4. **กดซ้ำต้องไม่เกิดออเดอร์ซ้ำ** — นี่คือที่มาของคำว่า **Idempotency**

### 7.1 ตารางแผนที่ใหญ่ (จำตารางนี้ให้ได้ = เข้าใจครึ่งเล่ม)

| Technology | อยู่ชั้นไหนของภาพใหญ่ | มันคืออะไร | **แก้ปัญหาอะไร** |
|---|---|---|---|
| **HTML / CSS** | Frontend | โครงสร้างและหน้าตาของหน้าเว็บ | ทำให้ browser รู้ว่าจะวาดอะไร ตรงไหน |
| **JavaScript** | Frontend + Backend | ภาษาโปรแกรม ภาษาเดียวที่ browser รันได้ | ทำให้หน้าเว็บ "ตอบสนอง" ได้ ไม่ใช่กระดาษนิ่ง ๆ |
| **React** | Frontend (Library) | เครื่องมือสร้าง UI จาก component | ก่อนมี React เราต้องสั่งแก้หน้าจอทีละจุดเอง พอแอปใหญ่ขึ้นจะคุมไม่อยู่ — React ให้เราประกาศว่า "state นี้ควรได้หน้าตาแบบนี้" แล้วมันจัดการอัปเดตให้ |
| **Next.js** | Frontend (Framework ครอบ React) | React + routing + server rendering + optimization ในกล่องเดียว | React เปล่า ๆ ไม่มี routing ไม่มี SEO ไม่มี server rendering ต้องประกอบเอง — Next.js ให้มาครบและมี convention ชัด |
| **React Native** | Frontend (Mobile) | เขียน React แล้วได้ UI ของ iOS/Android จริง | ไม่ต้องเขียนแอปเดียวกัน 2 รอบด้วย Swift และ Kotlin — ใช้ทีมเดียว logic เดียว |
| **Node.js** | Backend (Runtime) | ตัวรัน JavaScript นอก browser | ก่อนหน้านี้ JS รันได้แค่ใน browser — Node ทำให้เขียน server ด้วย JS ได้ และเก่งเรื่องรับงาน I/O เยอะ ๆ พร้อมกัน |
| **Express** | Backend (Framework บน Node) | ตัวจัด route และ middleware | Node เปล่า ๆ ต้องแกะ HTTP เอง เหนื่อยมาก — Express ให้เขียนแค่ "URL นี้ ทำอะไร" |
| **Java** | Backend (ภาษา) | ภาษา static typing รันบน JVM | ต้องการระบบใหญ่ที่คนเยอะ อยู่ยาวหลายปี และอยากให้ compiler จับ error ให้ตั้งแต่ยังไม่รัน |
| **Spring Boot** | Backend (Framework บน Java) | Java + Dependency Injection + config อัตโนมัติ | Java เปล่า ๆ ต้อง wire ของเองเยอะมาก — Spring Boot ประกอบให้ พร้อม security/ORM/monitoring |
| **Python** | Backend / Data | ภาษาที่อ่านง่าย เขียนเร็ว | เหมาะกับงานที่ต้องการความเร็วในการพัฒนา งาน data / AI / automation และ API ที่ไม่ซับซ้อนมาก |
| **Database (PostgreSQL / MySQL / MongoDB)** | Data Layer | ที่เก็บข้อมูลถาวร + ค้นหาได้เร็ว | ถ้าเก็บในหน่วยความจำ ปิดเครื่องแล้วหาย และหาข้อมูลใน file ธรรมดาจะช้ามากเมื่อข้อมูลเยอะ |
| **Redis** | Cache Layer (หน้า DB) | ที่เก็บข้อมูลชั่วคราวใน memory เร็วมาก | ลดภาระ DB สำหรับข้อมูลที่ถูกอ่านซ้ำบ่อย ๆ |
| **Docker** | Infrastructure | แพ็กโค้ด + dependency + OS config ไว้ในกล่องเดียว | แก้ปัญหา "เครื่องผมรันได้นะ" — กล่องเดียวกันรันเหมือนกันทุกเครื่อง |
| **Kubernetes** | Infrastructure (Orchestration) | ผู้จัดการกล่อง Docker หลาย ๆ กล่อง | เมื่อมี container เป็นสิบเป็นร้อย ต้องมีคนคอยเช็กว่าตายไหม ต้องเพิ่มไหม อัปเดตยังไงไม่ให้ล่ม |
| **CI/CD** | Delivery | ระบบ build/test/deploy อัตโนมัติ | ลด human error และทำให้ deploy บ่อย ๆ ได้อย่างปลอดภัย |
| **Git** | Process | ระบบเก็บประวัติโค้ด | ทำให้หลายคนแก้โค้ดเดียวกันได้ และย้อนกลับได้เมื่อพัง |

### 7.2 วางบนภาพใหญ่จริง ๆ

```
                 ┌─ React ──────── UI component
[FRONTEND] ──────┼─ Next.js ────── routing + SSR + SEO
                 └─ React Native ─ UI บนมือถือ
        ↓
   [HTTP / REST API]  ←── สัญญาที่ทั้งสองฝั่งตกลงกัน
        ↓
                 ┌─ Node.js + Express ── JS ฝั่ง server, I/O เยอะ
[BACKEND] ───────┼─ Java + Spring Boot ─ ระบบใหญ่ ทีมใหญ่ อยู่ยาว
                 └─ Python (FastAPI) ─── พัฒนาเร็ว / งาน data
        ↓
   [BUSINESS LOGIC]
        ↓
[DATA] ──────────┬─ Redis ──── cache (เร็ว ชั่วคราว)
                 └─ Database ─ ความจริงถาวร
        ↓
[INFRA] ─────────┬─ Docker ───── ใส่กล่อง
                 └─ Kubernetes ─ จัดการกล่อง
```

> **ให้มองภาพนี้ว่า** "แต่ละแถวคือชั้นหนึ่งของระบบ และ technology ที่อยู่แถวเดียวกันคือ 'ตัวเลือก' ที่แก้ปัญหาคล้ายกัน แต่เหมาะกับสถานการณ์ต่างกัน"

### 7.3 ตารางเทียบคู่ที่คนสับสนบ่อยที่สุด

| หัวข้อ | A | B | ต่างกันตรงไหนจริง ๆ |
|---|---|---|---|
| **Frontend vs Backend** | รันบนเครื่องผู้ใช้ | รันบน server ของเรา | ผู้ใช้แก้ frontend ได้ (เปิด DevTools ก็แก้ได้) จึงเชื่อไม่ได้ / backend ผู้ใช้แตะไม่ได้ จึงเชื่อได้ |
| **Client vs Server** | ตัวที่เริ่มถาม | ตัวที่รอตอบ | เป็น "บทบาท" ไม่ใช่ "ชนิดเครื่อง" — backend ที่ไปเรียก API อื่น ตอนนั้นมันเป็น client |
| **Web App vs Mobile App** | เปิดผ่าน URL | ติดตั้งจาก store | Web: อัปเดตทันที ทุกคนได้เหมือนกัน / Mobile: เข้าถึง hardware ได้ลึก ทำงาน offline ดีกว่า แต่อัปเดตต้องผ่าน store |
| **Website vs Web Application** | อ่านอย่างเดียว | โต้ตอบได้ มี state | บทความข่าว = website / Google Docs = web application |
| **Library vs Framework** | เราเรียกมัน | มันเรียกเรา | React = library (เราตัดสินใจโครงเอง) / Next.js, Spring Boot = framework (มันกำหนดโครงให้) |
| **Database vs Cache** | ความจริงถาวร | สำเนาชั่วคราว | ข้อมูลใน cache หายได้โดยระบบต้องไม่พัง — ถ้าหายแล้วพัง แปลว่าคุณใช้ cache เป็น database |
| **Docker vs Kubernetes** | สร้างและรันกล่อง | จัดการกล่องหลายใบ | Docker = "ทำกล่องให้รันได้" / K8s = "ดูแลกล่อง 100 ใบให้มีชีวิตตามที่ประกาศไว้" |
| **Frontend Dev vs Full-stack Dev** | ชำนาญชั้นบน | เห็นทั้งสายพาน | Full-stack ไม่ได้แปลว่าเก่งทุกชั้นเท่ากัน แต่แปลว่า "รู้ว่าปัญหาควรถูกแก้ที่ชั้นไหน" |

## 8. Common Mistakes

| ❌ ความเข้าใจผิด | ✅ ความจริง | ทำไมถึงสำคัญ |
|---|---|---|
| "Frontend คือความสวย Backend คือของจริง" | Frontend คือ **สัญญากับผู้ใช้** — ถ้า UX พัง ระบบที่ถูกต้องก็ไม่มีใครใช้ | คนที่ดูถูก frontend มักเขียน API ที่ frontend ใช้ไม่ได้จริง |
| "Validate ที่ frontend พอแล้ว" | ผู้ใช้เลี่ยง frontend ได้ (Postman, curl, DevTools) — **backend ต้อง validate เสมอ** | นี่คือช่องโหว่ security ที่พบบ่อยที่สุดในระบบจริง |
| "API = Backend" | API คือ **หน้าสัญญา** ที่ backend เปิดออกมา ไม่ใช่ตัว backend เอง | ทำให้เข้าใจว่า backend เปลี่ยนข้างในได้ ตราบใดที่ API contract ไม่เปลี่ยน |
| "Database = ที่เก็บไฟล์" | Database คือ **ระบบที่รับประกันความถูกต้องของข้อมูลเมื่อมีคนแก้พร้อมกัน** | ถ้าคิดว่าเป็นแค่ที่เก็บ จะไม่เข้าใจว่าทำไมต้องมี transaction / index / lock |
| "Full-stack = เก่งหมด" | Full-stack = **เห็นภาพเชื่อมกัน** และรู้ว่าจะขุดต่อที่ไหน | interviewer ถามเพื่อดู "การเชื่อมโยง" ไม่ได้ถามเพื่อวัดความกว้าง |
| "Server คือเครื่องคอมพิวเตอร์" | Server คือ **บทบาท** — โปรแกรมที่รอรับ request เครื่องเดียวรัน server ได้หลายตัว | ทำให้เข้าใจ Docker/Kubernetes ได้ง่ายขึ้นมาก |
| "ใช้ technology ใหม่ที่สุดดีที่สุด" | ดีที่สุด = **เหมาะกับปัญหา ทีม และเวลา ที่มี** | คำตอบที่ไม่มี trade-off คือคำตอบที่ยังคิดไม่ครบ |
| "Deploy = คัดลอกไฟล์ขึ้น server" | Deploy = build → test → package → ปล่อยอย่างปลอดภัย → **ย้อนกลับได้** | ระบบจริงต้องการ rollback เสมอ |
| "ระบบเร็วหรือช้า อยู่ที่ภาษาที่ใช้" | ส่วนใหญ่ช้าที่ **Database query, N+1, network round-trip** ไม่ใช่ภาษา | ทำให้ optimize ถูกจุด แทนที่จะเถียงเรื่องภาษา |
| "Infrastructure เป็นเรื่องของ DevOps ไม่เกี่ยวกับ dev" | Dev ที่ไม่รู้ว่าโค้ดตัวเองรันอยู่บนอะไร จะ debug production ไม่เป็น | เป็นเส้นแบ่งชัดระหว่าง junior กับ mid-level |

## 9. Debugging — ระบบพัง ไล่ดูอะไรตามลำดับ

**หลักการ: ไล่จากชั้นที่ผู้ใช้สัมผัส ลงไปหาชั้นที่ลึกที่สุด และ "ตัดชั้นออกทีละชั้น"**

```
STEP 1  ผู้ใช้เห็นอะไร?          → เอาอาการจริง ไม่ใช่คำว่า "มันพัง"
   ↓
STEP 2  Request ออกจากเครื่องไหม? → เปิด DevTools → tab Network
   ↓
STEP 3  Request ไปถึง server ไหม? → ดู log ฝั่ง server ว่ามี request เข้ามาไหม
   ↓
STEP 4  Server ตอบอะไรกลับ?      → ดู status code + body
   ↓
STEP 5  Backend ทำงานถึงไหน?     → ไล่ log ตาม controller → service → repository
   ↓
STEP 6  Database ตอบถูกไหม?      → รัน query เดียวกันมือเปล่า ดูผลลัพธ์
   ↓
STEP 7  Infra ปกติไหม?           → container ยังอยู่ไหม, memory เต็มไหม, restart วนไหม
```

> **ให้มองภาพนี้ว่า** "การ debug คือการหาว่า request ตายที่ด่านไหน แล้วค่อยเข้าไปดูในด่านนั้นด่านเดียว"

### ตารางอ่านอาการเบื้องต้น

| อาการที่ผู้ใช้เจอ | น่าจะพังที่ชั้นไหน | ดูอะไรก่อน |
|---|---|---|
| หน้าขาว ไม่มีอะไรเลย | Frontend | Console error — มักเป็น JS error ตอน render |
| ข้อมูลไม่ขึ้น แต่หน้ายังอยู่ | Network หรือ Backend | Network tab: status code เท่าไหร่ |
| ขึ้น 401 / 403 | Auth | token หมดอายุ หรือสิทธิ์ไม่พอ (ดู PART 1 และ 7) |
| ขึ้น 404 | Routing | URL ผิด หรือ route ไม่ได้ถูก register |
| ขึ้น 500 | Backend | ดู stack trace ใน server log |
| ขึ้น 502 / 503 | Infrastructure | service ตาย / container restart / scale ไม่พอ |
| ช้ามากแต่ไม่ error | Database หรือ Network | ดู query ช้า, N+1, payload ใหญ่ |
| พังเป็นบางคน | Cache / Session / เวอร์ชันเก่าค้าง | เทียบ environment และ client version |
| พังเฉพาะ production | Config / Environment Variable | เทียบ config dev vs prod |

**ประโยคที่ต้องติดหัว:**
> "อย่าเดา — ให้หา**หลักฐาน**ว่า request ตายตรงไหน แล้วค่อยตั้งสมมติฐาน"

## 10. Interview Questions

### 🟢 Junior

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| Frontend กับ Backend ต่างกันอย่างไร | ที่ตั้งของโค้ด + ใครเชื่อถือได้ ไม่ใช่แค่ "หน้าบ้าน/หลังบ้าน" |
| Client กับ Server คืออะไร | ว่ามันคือ "บทบาท" ไม่ใช่ "เครื่อง" |
| API คืออะไร อธิบายให้คนไม่ใช่ dev ฟัง | ความสามารถในการอธิบายด้วยภาษาคน (นี่คือคำถามวัด communication) |
| Database มีไว้ทำไม ทำไมไม่เก็บใน memory | ความถาวร + ค้นหาได้เร็ว + ปลอดภัยเมื่อหลายคนแก้พร้อมกัน |
| Web App กับ Mobile App ต่างกันยังไง | การติดตั้ง การอัปเดต และการเข้าถึง hardware |
| เล่าว่าเกิดอะไรขึ้นตั้งแต่กดปุ่มจนข้อมูลขึ้นหน้าจอ | ว่าคุณเห็นทั้งสายพาน ไม่ใช่เห็นแค่ชั้นตัวเอง |

### 🟡 Mid-level

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| ทำไมต้อง validate ทั้งสองฝั่ง ไม่ซ้ำซ้อนเหรอ | frontend = UX, backend = trust boundary |
| Full-stack สำหรับคุณคืออะไร | "รู้ว่าปัญหาควรแก้ที่ชั้นไหน" ไม่ใช่ "เก่งทุกอย่าง" |
| ระบบช้า จะเริ่มหาจากตรงไหน | วิธีตัดชั้น + **วัดก่อนแก้** |
| Docker แก้ปัญหาอะไร ไม่มีได้ไหม | "เครื่องผมรันได้" + environment consistency |
| Business logic ควรอยู่ที่ frontend หรือ backend เพราะอะไร | backend เป็นหลัก เพราะเป็นที่เดียวที่บังคับใช้ได้จริง |
| API contract เปลี่ยนแล้วเกิดอะไรขึ้นกับ frontend | ความเข้าใจเรื่อง versioning และ breaking change |

### 🔴 Senior

| คำถาม | เขาอยากฟังอะไร |
|---|---|
| ระบบมีคนใช้เพิ่ม 10 เท่า จะเริ่มจากตรงไหน | หา bottleneck ก่อน (มักคือ DB) → cache → scale out → แยก workload |
| เลือก Node.js หรือ Spring Boot อย่างไร | ตอบด้วย context: ทีม, ประเภท workload (I/O vs CPU), ระบบเดิม, การจ้างคน — ห้ามตอบว่าตัวไหนดีกว่า |
| Monolith กับ Microservices เลือกยังไง | ขนาดทีม + ความเร็วในการ deploy + ต้นทุนความซับซ้อน — เริ่ม monolith ที่แยกชั้นดีมักปลอดภัยกว่า |
| ถ้า Database ล่ม ระบบควรทำตัวอย่างไร | degrade อย่างสง่างาม: read จาก cache, ปิดฟีเจอร์ write, บอกผู้ใช้ตรง ๆ |
| คุณวัดว่าระบบ "สุขภาพดี" จากอะไร | Latency (p95/p99), Error rate, Throughput, Saturation — ไม่ใช่ "ไม่มีใครบ่น" |
| ถ้าต้องอธิบายสถาปัตยกรรมระบบให้ CEO ฟัง จะพูดยังไง | ความสามารถในการ abstract ขึ้นไปหาภาษาธุรกิจ |

## 11. Answer Like a Developer

**โครงสร้างการตอบ 4 ชั้น (ใช้ได้กับเกือบทุกคำถาม):**

```
1. นิยามสั้น       → "มันคืออะไร" 1 ประโยค
2. ทำไมถึงมี        → "แก้ปัญหาอะไร"
3. ตัวอย่างจริง     → "ผมเคยเจอตอน..."
4. Trade-off       → "แต่มันแลกมากับ..."
```

### ตัวอย่างการตอบ: "API คืออะไร"

❌ **แบบท่องจำ:** "API คือ Application Programming Interface เป็นตัวกลางในการเชื่อมต่อระหว่างระบบ"
(ถูกแต่ว่างเปล่า — interviewer ไม่ได้อะไรเลย)

✅ **แบบ developer:**
> "API คือ **สัญญา** ที่ backend ประกาศว่า 'ถ้าคุณส่งมาแบบนี้ ผมจะตอบแบบนี้'
> มันมีเพื่อให้ frontend ทำงานได้โดยไม่ต้องรู้ว่าข้างใน backend ใช้ database อะไรหรือเขียนด้วยภาษาไหน
> เช่นในโปรเจกต์ที่ผมทำ frontend เรียก `GET /api/orders/:id` แล้วได้ JSON กลับมา ระหว่างทาง backend เปลี่ยนจาก MySQL ไป PostgreSQL แต่ frontend ไม่ต้องแก้อะไรเลย เพราะสัญญาไม่เปลี่ยน
> ข้อแลกเปลี่ยนคือพอมันเป็นสัญญาแล้ว **การแก้ API เป็น breaking change** ต้องทำ versioning หรือแจ้งทีมล่วงหน้า"

### ตัวอย่างการตอบ: "Full-stack คืออะไรสำหรับคุณ"

✅ **แบบ developer:**
> "สำหรับผม full-stack ไม่ได้แปลว่าเก่งทุกชั้นเท่ากัน แต่แปลว่า **เมื่อเจอปัญหา ผมรู้ว่าควรเริ่มขุดที่ชั้นไหน**
> เช่นเวลาหน้าเว็บช้า ผมจะไม่รีบไป optimize React ทันที ผมจะดูก่อนว่า network request ใช้เวลาเท่าไหร่ ถ้า API ตอบ 2 วินาที ปัญหาอยู่ที่ backend หรือ query ไม่ใช่ที่ frontend
> ข้อจำกัดคือความลึก — ผมลึกทาง frontend มากกว่า infra ดังนั้นเวลาแตะเรื่อง Kubernetes ผมจะคุยกับทีม platform ก่อนตัดสินใจ"

**3 ประโยคที่ทำให้คุณดูเป็น mid-level ทันที:**

1. "ขอถามก่อนว่า context เป็นแบบไหน เพราะคำตอบต่างกัน"
2. "ผมจะวัดก่อนว่าปัญหาอยู่ตรงไหน แล้วค่อยแก้"
3. "ข้อแลกเปลี่ยนของวิธีนี้คือ..."

## 12. One-Minute Review

อ่าน 1 นาทีก่อนเข้าห้องสัมภาษณ์:

- **Software** = ชุดคำสั่งที่บอกคอมพิวเตอร์ว่าต้องทำอะไรเมื่อผู้ใช้ทำอะไร
- **Client** = ฝ่ายที่เริ่มถาม / **Server** = ฝ่ายที่รอตอบ — เป็นบทบาท ไม่ใช่ชนิดเครื่อง
- **Frontend** = รันบนเครื่องผู้ใช้ → เชื่อไม่ได้ / **Backend** = รันบน server เรา → เชื่อได้
- **API** = สัญญาระหว่างสองฝั่ง ไม่ใช่ตัว backend
- **Database** = ความจริงถาวร + รับประกันความถูกต้องเมื่อมีคนแก้พร้อมกัน
- **Infrastructure** = พื้นที่ที่โค้ดยืนอยู่ (Docker ใส่กล่อง → Kubernetes ดูแลกล่อง)
- **Request → Response** = การเดินทางไปกลับที่ทุกด่านทำให้ช้าหรือปฏิเสธได้
- **Validation ต้องทำ 2 ที่**: frontend เพื่อ UX, backend เพื่อความถูกต้อง
- **React/Next.js/React Native** = ชั้น Frontend / **Node+Express, Java+Spring Boot, Python** = ชั้น Backend / **Docker+K8s** = ชั้น Infra
- **Debug** = ไล่จากชั้นบนลงล่าง หาว่า request ตายด่านไหนก่อน แล้วค่อยลงลึก
- **ไม่มี technology ไหน "ดีกว่า"** มีแต่ "เหมาะกว่าเมื่อ..."

## 13. Memory Card

### จำ 5 อย่าง

1. **ทุกอย่างคือ Request → Response** — ผู้ใช้ทำอะไร → ส่งคำขอ → ผ่านด่าน → ได้คำตอบ → หน้าจอเปลี่ยน
2. **Frontend เชื่อไม่ได้ Backend เชื่อได้** — ทุกการตรวจสอบที่สำคัญต้องเกิดฝั่ง server
3. **แต่ละ Technology = คำตอบของปัญหาหนึ่ง** — ก่อนจำชื่อ ให้จำว่า "มันเกิดมาเพื่อแก้อะไร"
4. **Debug = ตัดชั้นทีละชั้น** — อย่าเดา ให้หาหลักฐานว่า request ตายด่านไหน
5. **ตอบทุกคำถามด้วย Trade-off** — "ดีกว่าเมื่อ..." ไม่ใช่ "ดีกว่า"

### Keyword

- **Software** → ชุดคำสั่ง
- **Application** → software ที่มีหน้าตาให้คนใช้
- **Web App** → เปิดผ่าน URL อัปเดตทันที
- **Mobile App** → ติดตั้งจาก store เข้าถึง hardware ได้ลึก
- **Frontend** → รันบนเครื่องผู้ใช้ แสดงผล + รับ input
- **Backend** → รันบน server คิด ตัดสินใจ จำ
- **Full-stack** → รู้ว่าปัญหาควรแก้ที่ชั้นไหน
- **Client** → ฝ่ายที่เริ่มถาม
- **Server** → ฝ่ายที่รอตอบ ทำงาน 24 ชม.
- **Database** → ความจริงถาวร ค้นหาเร็ว
- **API** → สัญญาว่าจะคุยกันยังไง
- **Network** → ถนนที่ข้อมูลวิ่ง (DNS → IP → Port)
- **Infrastructure** → พื้นที่ที่ระบบยืนอยู่
- **Request** → คำขอออกไป
- **Response** → คำตอบกลับมา
- **Business Logic** → กฎของธุรกิจ หัวใจของระบบ
- **React** → สร้าง UI จาก component ตาม state
- **Next.js** → React + routing + SSR + SEO ในกล่องเดียว
- **React Native** → เขียน React ได้ UI มือถือจริง
- **Node.js** → รัน JS นอก browser เก่งงาน I/O
- **Express** → จัด route/middleware บน Node
- **Java + Spring Boot** → ระบบใหญ่ ทีมใหญ่ อยู่ยาว typing แน่น
- **Python** → เขียนเร็ว งาน data/AI/automation
- **Docker** → ใส่โค้ดลงกล่องให้รันเหมือนกันทุกที่
- **Kubernetes** → ผู้จัดการกล่องหลายร้อยใบ
- **Deploy** → เอาโค้ดขึ้นใช้งานจริง
- **Production** → ของจริงที่ผู้ใช้ใช้อยู่ พังแล้วมีคนเดือดร้อน
