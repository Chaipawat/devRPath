# PART 3 — REACT

> ตำแหน่งในภาพใหญ่: Frontend Layer — ชั้นที่แปลง "ข้อมูล" ให้กลายเป็น "สิ่งที่ผู้ใช้เห็นและกดจริง" บนหน้าจอ

---

## 1. Big Picture

### React แก้ปัญหาอะไร

ก่อนจะมี React การทำเว็บที่มีข้อมูลเปลี่ยนตลอดเวลาเป็นงานที่เจ็บปวดมาก เพราะเราต้อง **สั่งเบราว์เซอร์ทีละขั้น** ว่า:

> "ไปหา element ที่ id ชื่อ cart-count → เปลี่ยนตัวเลขข้างในเป็น 3 → แล้วไปหา element ชื่อ cart-badge → เปลี่ยนสีเป็นแดง → แล้วถ้าตะกร้าว่างให้ซ่อนปุ่ม checkout ด้วยนะ"

ปัญหาคือเมื่อแอปโตขึ้น **จำนวนเส้นทางที่ต้องจำว่า "ถ้าข้อมูลนี้เปลี่ยน ต้องไปแก้ตรงไหนบ้าง" เพิ่มขึ้นแบบทวีคูณ** สุดท้ายไม่มีใครในทีมกล้าแก้อะไร เพราะไม่รู้ว่าจะไปทำอะไรพังที่อื่น

React เปลี่ยนวิธีคิดใหม่ทั้งหมด จาก "สั่งทีละขั้น" (Imperative) มาเป็น **"ประกาศว่าอยากให้หน้าตาเป็นแบบไหน"** (Declarative)

เราเขียนแค่ว่า:

> "ถ้าตะกร้ามี 3 ชิ้น หน้าตาต้องเป็นแบบนี้"

แล้ว React จะรับผิดชอบเองว่าจะไปแก้ DOM ตรงไหนให้ตรงกับที่เราประกาศ

**ประโยคเดียวที่ต้องจำ:**

> **UI = f(state)** — หน้าจอคือผลลัพธ์ของข้อมูล ถ้าข้อมูลเปลี่ยน React จะคำนวณหน้าจอใหม่ให้เอง เราไม่ต้องไปสั่ง DOM เอง

### React คืออะไร (และไม่ใช่อะไร)

| React คือ | React ไม่ใช่ |
|---|---|
| **Library** สำหรับสร้าง UI | Framework ที่มีของครบทุกอย่าง |
| ตัวจัดการ "หน้าตาตามข้อมูล" | ตัวจัดการ routing (ต้องใช้ React Router / Next.js) |
| ระบบ component ที่ประกอบกันได้ | ตัวจัดการ data fetching (ต้องใช้ TanStack Query / SWR) |
| ตัวที่ optimize การแก้ DOM ให้ | ตัวที่ "เร็วกว่า vanilla JS เสมอ" |

**คำถามสัมภาษณ์ข้อคลาสสิก:** "React เป็น library หรือ framework?"
คำตอบที่ดี: "เป็น library ครับ เพราะมันรับผิดชอบแค่ชั้น UI ส่วน routing, state management, data fetching ต้องเลือกเอง — ซึ่งเป็นทั้งข้อดี (ยืดหยุ่น) และข้อเสีย (ทีมต้องตัดสินใจเยอะ และแต่ละโปรเจกต์หน้าตาไม่เหมือนกัน) ซึ่งเป็นเหตุผลที่ Next.js ถือกำเนิดขึ้นมาเติมช่องว่างนั้น"

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Component** | ชิ้นส่วน Lego | function ที่รับข้อมูลแล้วคืนหน้าตา นำกลับมาใช้ซ้ำได้ |
| **Component Tree** | ผังต้นไม้ของหน้าจอ | โครงสร้างว่า component ไหนอยู่ในใคร |
| **JSX** | เขียน HTML ในไฟล์ JS | syntax ที่ถูกแปลงเป็นคำสั่งสร้าง element |
| **Props** | พัสดุที่ส่งจากแม่ | ข้อมูลที่ไหลจาก parent → child ทางเดียว แก้ไม่ได้ |
| **State** | ความจำของ component | ข้อมูลที่เปลี่ยนได้ และเมื่อเปลี่ยนจะทำให้ re-render |
| **Event** | ผู้ใช้ทำอะไรบางอย่าง | คลิก, พิมพ์, submit — จุดเริ่มของการเปลี่ยน state |
| **Render** | คำนวณหน้าตา | React เรียก component function เพื่อดูว่าผลลัพธ์ควรเป็นอะไร |
| **Re-render** | คำนวณหน้าตาใหม่ | เกิดเมื่อ state/props/context เปลี่ยน — **ไม่ได้แปลว่า DOM เปลี่ยน** |
| **Commit** | ลงมือแก้ DOM จริง | ขั้นที่ React เอาผลต่างไปแก้ DOM |
| **Virtual DOM** | พิมพ์เขียวในกระดาษ | โครงสร้าง object ในหน่วยความจำที่แทนหน้าตาที่ควรจะเป็น |
| **DOM** | ตัวอาคารจริง | โครงสร้างหน้าเว็บจริงที่เบราว์เซอร์ถืออยู่ |
| **Reconciliation** | เทียบพิมพ์เขียวเก่า-ใหม่ | กระบวนการหาว่า "ต่างกันตรงไหน" เพื่อแก้เฉพาะจุดนั้น |
| **Diffing** | หาจุดต่าง | อัลกอริทึมที่เทียบ tree เก่ากับ tree ใหม่ |
| **Key** | เลขประจำตัวในรายการ | บอก React ว่าแต่ละ item ใน list คือ "ตัวเดิม" หรือ "ตัวใหม่" |
| **Hook** | ตะขอต่อพลังให้ function | function พิเศษที่ให้ component มี state / side effect / ค่า memo ได้ |
| **useState** | ความจำที่ทำให้วาดใหม่ | เก็บค่าที่เปลี่ยนได้ และ trigger re-render |
| **useEffect** | ซิงก์กับโลกภายนอก | ทำสิ่งที่อยู่นอก React (network, timer, subscription) หลัง render |
| **useRef** | กล่องจำที่ไม่ปลุก React | เก็บค่าข้าม render โดยไม่ทำให้ re-render + ใช้อ้างถึง DOM |
| **useMemo** | จำผลคำนวณไว้ | ไม่คำนวณซ้ำถ้า dependency ไม่เปลี่ยน |
| **useCallback** | จำ function ตัวเดิมไว้ | ไม่สร้าง function ใหม่ทุก render |
| **useContext** | เสียงตามสายในตึก | อ่านค่าที่ provider ส่งลงมา โดยไม่ต้องส่งผ่านทุกชั้น |
| **Lifecycle** | ช่วงชีวิตของ component | Mount → Update → Unmount |
| **Mount** | เกิด | ครั้งแรกที่ component ปรากฏบนจอ |
| **Unmount** | ตาย | ตอนถูกถอดออกจากหน้าจอ — ต้องเก็บกวาดให้เรียบร้อย |
| **Controlled Component** | React ถือพวงมาลัย | ค่าของ input มาจาก state |
| **Uncontrolled Component** | DOM ถือพวงมาลัย | ค่าอยู่ใน DOM เอง เราไปอ่านตอนต้องใช้ |
| **Lifting State Up** | ยกความจำขึ้นไปหาพ่อแม่ | ย้าย state ไปไว้ที่ parent ร่วมกัน เมื่อลูกหลายคนต้องใช้ |
| **Prop Drilling** | ส่งพัสดุผ่านคนกลางหลายชั้น | ส่ง props ลงไปลึก ๆ ทั้งที่ชั้นกลางไม่ได้ใช้ |
| **Context** | ตู้ของกลางประจำตึก | ทางส่งค่าลงไปทั้ง subtree โดยไม่ผ่านทุกชั้น |
| **Local State** | ความจำส่วนตัวของ component | เช่น modal เปิด/ปิด |
| **Global State** | ความจำส่วนกลางของแอป | เช่น theme, ข้อมูลผู้ใช้ที่ล็อกอิน |
| **Server State** | ข้อมูลที่เจ้าของจริงคือ server | ข้อมูลจาก API ที่เราแค่ยืมมาแสดง |
| **Memoization** | จำคำตอบเดิมไว้ | แลกหน่วยความจำเพื่อลดการคำนวณซ้ำ |
| **React.memo** | ยามหน้าประตู component | ข้าม re-render ถ้า props เหมือนเดิม |
| **Code Splitting** | แบ่งกระเป๋าเดินทาง | แยก bundle เป็นก้อนย่อย โหลดเท่าที่ต้องใช้ |
| **Lazy Loading** | โหลดตอนจะใช้ | เลื่อนการโหลดออกไปจนถึงเวลาจำเป็น |
| **Virtualization** | วาดเฉพาะที่ตามองเห็น | render เฉพาะแถวที่อยู่ในจอ สำหรับ list ยาวมาก |
| **Error Boundary** | เบรกเกอร์ไฟฟ้า | component ที่ดัก error ของลูก ไม่ให้ทั้งแอปจอขาว |
| **Strict Mode** | โหมดตรวจสุขภาพตอน dev | เรียกบางอย่าง 2 ครั้งเพื่อจับ side effect ที่เขียนผิด |

## 3. Mental Model

### Mental Model หลัก: UI = f(state)

```
     STATE (ข้อมูล)
          ↓
    React คำนวณ
          ↓
       UI (หน้าจอ)
```

> **ให้มองภาพนี้ว่า** "หน้าจอคือ 'ผลลัพธ์' ของข้อมูล ไม่ใช่สิ่งที่เราไปแก้มือ — ถ้าอยากให้หน้าจอเปลี่ยน ให้ไปเปลี่ยนข้อมูล แล้ว React จะจัดการหน้าจอเอง"

นี่คือเหตุผลที่ **ห้าม** ไปแก้ DOM เองด้วย `document.getElementById(...)` ในแอป React — เพราะคุณกำลังไปแก้ "ผลลัพธ์" ในขณะที่ React กำลังคำนวณ "ผลลัพธ์" ของมันเอง สุดท้ายทั้งสองฝ่ายจะทับกันเละ

### Mental Model รอง 4 ข้อ

**1. Component คือ function ธรรมดา ไม่ใช่ของวิเศษ**
รับ props เข้ามา → คืนคำอธิบายหน้าตาออกไป ถ้าใส่ input เดิม ควรได้ output เดิมเสมอ (pure) — นี่คือกติกาที่ React ทั้งระบบตั้งอยู่บนนั้น

**2. Render ≠ แก้ DOM**
"Render" แปลว่า React เรียก function ของคุณเพื่อดูผลลัพธ์ ส่วนการแก้ DOM จริงเกิดใน "Commit" ซึ่งจะเกิดก็ต่อเมื่อ **มีอะไรต่างจากเดิมจริง ๆ** — Junior เกือบทุกคนเข้าใจผิดข้อนี้

**3. ข้อมูลไหลลงทางเดียว (One-way Data Flow)**
Props ไหลลงจาก parent → child เท่านั้น ถ้า child อยากเปลี่ยนอะไร ต้องเรียก function ที่ parent ส่งลงมาให้ ไม่มีการ "ยิงข้อมูลย้อนขึ้น" โดยตรง — ที่ทำแบบนี้เพราะเมื่อมีอะไรผิด เราจะตามหาต้นทางได้เสมอ

**4. State คือ snapshot ไม่ใช่ตัวแปรสด**
ในหนึ่งรอบ render ค่า state คือค่าที่ "ถ่ายภาพไว้" ตอนเริ่ม render นั้น ไม่ว่าคุณจะ `setState` กี่ครั้ง ตัวแปรในรอบนั้นก็ไม่เปลี่ยน — นี่คือรากของ bug "ทำไมค่าไม่อัปเดตทันที"

## 4. 🧠 ภาพจำ

```
🧠 ภาพจำที่ 1 — React = ร้านป้ายไฟ LED

เราไม่ได้เดินไปเปลี่ยนหลอดทีละดวง
เราแค่ "พิมพ์ข้อความใหม่" แล้วป้ายจัดการหลอดเอง

State เปลี่ยน
      ↓
React Render
      ↓
UI Update
```

```
🧠 ภาพจำที่ 2 — Props = พัสดุ / State = ความจำส่วนตัว

Props  = กล่องพัสดุที่แม่ส่งมา → ลูกเปิดดูได้ แต่ห้ามแก้แล้วส่งคืน
State  = สมุดบันทึกของตัวเอง → แก้ได้ และพอแก้ปุ๊บก็ต้องวาดหน้าจอใหม่
```

```
🧠 ภาพจำที่ 3 — Virtual DOM = พิมพ์เขียว / DOM = อาคารจริง

อยากต่อเติมบ้าน → ไม่ทุบกำแพงเลย
แต่วาดพิมพ์เขียวใหม่ → เทียบกับพิมพ์เขียวเก่า → ทุบเฉพาะกำแพงที่ต่างกัน
```

```
🧠 ภาพจำที่ 4 — useEffect = "ซิงก์กับโลกนอก" ไม่ใช่ "ทำหลัง render"

React = โลกข้างใน (state, props)
โลกนอก = API, timer, localStorage, WebSocket, DOM ของคนอื่น
useEffect = สะพานเชื่อมสองโลก และต้องมี "ทางกลับ" (cleanup) เสมอ
```

```
🧠 ภาพจำที่ 5 — Key = เลขที่นั่งในโรงหนัง

ไม่มี key → React นับตามลำดับที่นั่ง → แทรกคนข้างหน้าทีเดียว ทุกคนเลื่อนหมด
มี key   → React รู้ว่า "คนนี้คือคนเดิม" ต่อให้ย้ายที่นั่ง
```

```
🧠 ภาพจำที่ 6 — Context = เสียงตามสายในตึก

ไม่มี Context → ส่งจดหมายจากชั้น 1 ไปชั้น 10 ต้องผ่านมือทุกชั้น (Prop Drilling)
มี Context   → ประกาศเสียงตามสาย ใครอยู่ในตึกก็ได้ยินหมด
              แต่... ประกาศทีเดียว ทุกชั้นที่ฟังอยู่ก็ตื่นหมดเช่นกัน
```

```
🧠 ภาพจำที่ 7 — Error Boundary = เบรกเกอร์ไฟฟ้า

ไฟช็อตที่ห้องเดียว → เบรกเกอร์ตัดเฉพาะห้องนั้น
ไม่มีเบรกเกอร์ → ไฟดับทั้งตึก (จอขาวทั้งแอป)
```

## 5. How It Works

### 5.1 Component Tree — โครงสร้างพื้นฐาน

```
                  App
                   │
      ┌────────────┼────────────┐
   Header        Main         Footer
                   │
        ┌──────────┼──────────┐
   ProductList  Sidebar    CartPanel
        │                      │
   ProductCard ×N        CartItem ×N
```

> **ให้มองภาพนี้ว่า** "หน้าจอทั้งหน้าคือต้นไม้ที่ประกอบจากชิ้นส่วนย่อย ๆ และข้อมูลไหลจากรากลงไปหาใบเสมอ"

### 5.2 วงจรชีวิตของการเปลี่ยนแปลง 1 ครั้ง (สำคัญที่สุดใน chapter นี้)

```
[1] USER EVENT              ผู้ใช้กดปุ่ม "เพิ่มลงตะกร้า"
        ↓
[2] setState()              เรียก setter เพื่อเปลี่ยน state
        ↓
[3] SCHEDULE RE-RENDER      React ตั้งคิวไว้ (ไม่ได้ทำทันที + รวมหลายครั้งเป็นครั้งเดียว = Batching)
        ↓
[4] RENDER PHASE            React เรียก component function ใหม่
                            → ได้ Virtual DOM ชุดใหม่
                            *** ยังไม่แตะ DOM จริงเลยแม้แต่นิดเดียว ***
        ↓
[5] RECONCILIATION          เทียบ Virtual DOM เก่า vs ใหม่ (Diffing)
        ↓
[6] ต่างกันไหม? ──ไม่ต่าง──→ จบ ไม่แตะ DOM เลย
        ↓ ต่าง
[7] COMMIT PHASE            แก้ DOM เฉพาะจุดที่ต่างจริง
        ↓
[8] BROWSER PAINT           เบราว์เซอร์วาดหน้าจอใหม่
        ↓
[9] useEffect RUN           effect ทำงานหลังจอถูกวาดแล้ว
```

> **ให้มองภาพนี้ว่า** "การกดปุ่ม 1 ครั้งไม่ได้แก้หน้าจอทันที แต่จุดชนวนกระบวนการ คิด → เทียบ → แก้เท่าที่จำเป็น → วาด → ค่อยไปคุยกับโลกภายนอก"

**จุดที่ต้องเน้นย้ำ:** ระหว่าง `[4]` ถึง `[6]` คือ "Re-render" ซึ่ง **เกิดบ่อยมากและไม่ใช่เรื่องน่ากลัวโดยตัวมันเอง** สิ่งที่แพงจริงคือ `[7]` การแก้ DOM และ `[8]` การวาดหน้าจอ

### 5.3 Virtual DOM vs DOM — ทำไมถึงมี

```
ถ้าไม่มี Virtual DOM (แก้ DOM ตรง ๆ ทุกครั้ง)
state เปลี่ยน → แก้ DOM → browser คำนวณ layout ใหม่ → วาดใหม่
state เปลี่ยน → แก้ DOM → browser คำนวณ layout ใหม่ → วาดใหม่   ← 10 ครั้ง = 10 รอบ
state เปลี่ยน → แก้ DOM → browser คำนวณ layout ใหม่ → วาดใหม่

ถ้ามี Virtual DOM
state เปลี่ยน ×10 → รวมเป็น VDOM ชุดเดียว → diff → แก้ DOM รอบเดียว → วาดรอบเดียว
```

> **ให้มองภาพนี้ว่า** "Virtual DOM ไม่ได้เร็วกว่าการแก้ DOM ทีละจุด แต่มันช่วยไม่ให้เราเผลอแก้ DOM ซ้ำซ้อนโดยไม่จำเป็น และทำให้เราเขียนโค้ดแบบประกาศได้โดยไม่ต้องคิดเรื่อง optimize เอง"

**ประโยคที่ต้องพูดให้ถูกในห้องสัมภาษณ์:**
> "Virtual DOM ไม่ได้เร็วกว่า DOM ครับ — มันคือ DOM ที่ถูกจำลองเป็น object ซึ่งการสร้างและเทียบก็มีต้นทุนของมันเอง แต่มันซื้อสองอย่างให้เรา: หนึ่ง คือลดการแตะ DOM จริงที่แพงกว่ามาก และสอง คือทำให้เราเขียนแบบ declarative ได้โดยไม่ต้องจัดการ optimize เอง ถ้าเขียน vanilla JS ที่รู้ว่าต้องแก้ node ไหนพอดี อันนั้นเร็วกว่าแน่นอน แต่มันดูแลไม่ไหวเมื่อแอปโต"

### 5.4 Reconciliation & Key

```
รายการเดิม (ไม่มี key)          รายการใหม่ (แทรก "ไข่" ไว้หน้าสุด)
[0] นม                          [0] ไข่      ← React มองว่า "ตำแหน่ง 0 เปลี่ยนจาก นม → ไข่"
[1] ขนมปัง                       [1] นม      ← "ตำแหน่ง 1 เปลี่ยนจาก ขนมปัง → นม"
[2] เนย                         [2] ขนมปัง   ← "ตำแหน่ง 2 เปลี่ยน..."
                                [3] เนย     ← "เพิ่มตัวใหม่"
ผล: แก้ 4 จุด ทั้งที่จริง ๆ แค่แทรก 1 ตัว

รายการเดิม (มี key)             รายการใหม่
key=milk   นม                   key=egg    ไข่    ← ตัวใหม่จริง เพิ่มเข้ามา
key=bread  ขนมปัง                key=milk   นม     ← ตัวเดิม แค่ย้ายที่
key=butter เนย                  key=bread  ขนมปัง  ← ตัวเดิม แค่ย้ายที่
                                key=butter เนย    ← ตัวเดิม แค่ย้ายที่
ผล: เพิ่ม 1 จุด ที่เหลือแค่ย้ายตำแหน่ง
```

> **ให้มองภาพนี้ว่า** "Key คือบัตรประชาชนของ item — ถ้าไม่มีบัตร React ก็รู้จักคนจากตำแหน่งที่ยืนเท่านั้น พอมีคนแทรกคิวเข้ามา React จะเข้าใจผิดว่าทุกคนเปลี่ยนตัวหมด"

**ทำไมห้ามใช้ index เป็น key:** เพราะ index คือ "ตำแหน่งที่ยืน" ไม่ใช่ "ตัวตน" — พอเรียงลำดับใหม่หรือแทรกกลางรายการ ตัวตนก็สลับกันทันที ผลที่เห็นจริงคือ **ค่าใน input ของแถวหนึ่งไปโผล่อีกแถว** หรือ checkbox ติ๊กผิดแถว

**เมื่อไรใช้ index ได้:** เมื่อรายการนั้น static ไม่มีการเพิ่ม/ลบ/เรียงใหม่ และ item ไม่มี state ภายในเลย

### 5.5 Props vs State — ทิศทางของข้อมูล

```
              [ PARENT ]
              state: cart
                 │   ↑
    props ลง ────┘   └──── callback ขึ้น
                 ↓   │
              [ CHILD ]
              อ่าน props ได้ / แก้ไม่ได้
              อยากเปลี่ยน → เรียก callback ที่แม่ให้มา
```

> **ให้มองภาพนี้ว่า** "ข้อมูลไหลลงทางเดียวเสมอ ส่วนการขอเปลี่ยนแปลงไหลขึ้นในรูปของการเรียก function ที่แม่ยื่นให้ — ทำให้เวลา bug เกิด เราตามหาต้นทางได้เสมอว่าใครเป็นคนสั่งเปลี่ยน"

### 5.6 Lifecycle — Mount / Update / Unmount

```
┌─────────── MOUNT ───────────┐
│ component ถูกสร้างครั้งแรก      │
│   → render ครั้งแรก           │
│   → commit ลง DOM            │
│   → useEffect(..., []) ทำงาน  │
│   ใช้ทำ: โหลดข้อมูลครั้งแรก,      │
│         subscribe, setup      │
└──────────────┬───────────────┘
               ↓
┌────────── UPDATE ───────────┐
│ state / props / context เปลี่ยน│
│   → re-render                │
│   → diff → commit เท่าที่ต่าง   │
│   → cleanup effect เก่า       │
│   → effect ใหม่ทำงาน           │
│   ใช้ทำ: ซิงก์ข้อมูลตาม param   │
└──────────────┬───────────────┘
               ↓
┌────────── UNMOUNT ──────────┐
│ component ถูกถอดออกจากจอ      │
│   → cleanup function ทำงาน    │
│   ใช้ทำ: clearInterval,        │
│         removeEventListener,  │
│         ยกเลิก request         │
└──────────────────────────────┘
```

> **ให้มองภาพนี้ว่า** "component มีชีวิตเหมือนคนเช่าห้อง — ตอนเข้าต้องติดตั้งของ ตอนอยู่ต้องปรับตามสถานการณ์ และตอนย้ายออกต้องเก็บของให้หมด ไม่งั้นห้องถัดไปจะรก (memory leak)"

### 5.7 Hooks — ทุกตัวในที่เดียว

#### useState

| หัวข้อ | รายละเอียด |
|---|---|
| **คืออะไร** | ความจำของ component ที่เมื่อเปลี่ยนแล้วทำให้ re-render |
| **ใช้เมื่อไร** | ค่าที่เปลี่ยนแล้ว **หน้าจอต้องเปลี่ยนตาม** เช่น modal เปิด/ปิด, ค่าใน form, tab ที่เลือกอยู่ |
| **ไม่ควรใช้เมื่อไร** | 1. ค่าที่คำนวณจาก state อื่นได้ (derived state) — คำนวณตอน render แทน<br>2. ค่าที่เปลี่ยนแล้วหน้าจอไม่ต้องเปลี่ยน — ใช้ `useRef`<br>3. ข้อมูลจาก server ที่ต้อง cache/refetch — ใช้ TanStack Query |
| **ปัญหาที่พบบ่อย** | • คิดว่า `setState` เปลี่ยนค่าทันที (จริง ๆ ค่าใหม่จะเห็นในรอบ render ถัดไป)<br>• เก็บ state ซ้ำซ้อนจนไม่ sync กัน เช่นเก็บทั้ง `items` และ `itemCount`<br>• mutate ของเดิมแล้ว set ตัวเดิมกลับไป → React เห็น reference เดิม → ไม่ re-render |

pseudocode ที่อธิบาย "state คือ snapshot":

```
const [n, setN] = useState(0)
setN(n + 1)
setN(n + 1)   // ยังเห็น n เป็นค่าเดิม → ผลลัพธ์ได้ 1 ไม่ใช่ 2
setN(x => x + 1)  // แบบนี้ถูก เพราะรับค่าล่าสุดมาคำนวณต่อ
```

#### useEffect

| หัวข้อ | รายละเอียด |
|---|---|
| **คืออะไร** | สะพานเชื่อม React กับโลกภายนอก ทำงาน**หลัง**จอถูกวาดแล้ว |
| **ใช้เมื่อไร** | • subscribe / unsubscribe (WebSocket, event listener)<br>• timer, interval<br>• ซิงก์กับ localStorage / document.title<br>• เรียก API เมื่อไม่มี library จัดการ server state |
| **ไม่ควรใช้เมื่อไร** | • **คำนวณค่าจาก props/state** — คำนวณตอน render ตรง ๆ ดีกว่า<br>• **ตอบสนอง event ของผู้ใช้** — เขียนใน event handler ตรงนั้นเลย<br>• **แปลงข้อมูลก่อนแสดงผล** — ทำตอน render<br>• **ทำ data fetching ในโปรเจกต์ที่มี TanStack Query / Server Component แล้ว** |
| **ปัญหาที่พบบ่อย** | • ลืม cleanup → memory leak, event listener ซ้อน, interval ซ้อน<br>• dependency array ไม่ครบ → effect ใช้ค่าเก่า (stale closure)<br>• ใส่ object/function ที่สร้างใหม่ทุก render ใน deps → effect รันทุกรอบเป็น loop<br>• `setState` ใน effect ที่ dep มี state ตัวนั้นเอง → infinite loop<br>• race condition: ยิง 2 request แล้วอันเก่ากลับมาทีหลัง ทับของใหม่ |

```
เจอ useEffect ให้ถามตัวเอง 3 ข้อ:
[1] นี่คือการ "ซิงก์กับของนอก React" จริงไหม?  ไม่ใช่ → ย้ายออก
[2] deps ครบและถูกต้องไหม?                    ไม่ครบ → จะได้ค่าเก่า
[3] ต้อง cleanup อะไรไหม?                     ต้อง → เขียน return ทุกครั้ง
```

> **ให้มองภาพนี้ว่า** "useEffect ไม่ใช่ที่ไว้ทำอะไรก็ได้หลัง render แต่คือที่ไว้จัดการสิ่งที่ React ควบคุมไม่ได้เท่านั้น"

#### useRef

| หัวข้อ | รายละเอียด |
|---|---|
| **คืออะไร** | กล่องที่เก็บค่าข้าม render ได้ โดย**ไม่**ทำให้ re-render |
| **ใช้เมื่อไร** | 1. อ้างถึง DOM element จริง (focus input, scroll, วัดขนาด)<br>2. เก็บค่าที่ต้องจำแต่ไม่ต้องแสดงผล เช่น id ของ timer, ค่าครั้งก่อน, flag "ยิง request ไปแล้ว" |
| **ไม่ควรใช้เมื่อไร** | • ค่าที่ต้องแสดงบนหน้าจอ — ต้องใช้ `useState` ไม่งั้นเปลี่ยนแล้วจอไม่อัปเดต<br>• ใช้เพื่อ "หนี" การ re-render ทั้งที่ต้นเหตุคือ state ที่ออกแบบผิด |
| **ปัญหาที่พบบ่อย** | • เปลี่ยนค่า ref แล้วสงสัยว่าทำไมหน้าจอไม่เปลี่ยน (ถูกแล้ว มันตั้งใจให้เป็นแบบนั้น)<br>• อ่าน `ref.current` ของ DOM ตอน render แรก ได้ `null` เพราะ DOM ยังไม่ถูก commit<br>• ใช้ ref เก็บ state จริงจนโค้ดตามยาก ไม่มีใครรู้ว่าค่าถูกเปลี่ยนตอนไหน |

#### useMemo

| หัวข้อ | รายละเอียด |
|---|---|
| **คืออะไร** | จำ **ผลลัพธ์ของการคำนวณ** ไว้ ถ้า deps ไม่เปลี่ยนก็คืนค่าเดิม |
| **ใช้เมื่อไร** | 1. คำนวณที่แพงจริง ๆ และ**วัดแล้ว**ว่าแพง เช่น sort/filter ข้อมูลหลักพันหลักหมื่นแถว<br>2. ต้องการรักษา **reference เดิม** ของ object/array ที่จะส่งเป็น props ให้ลูกที่ห่อ `React.memo`<br>3. ค่าที่ใช้เป็น dependency ของ effect อื่น |
| **ไม่ควรใช้เมื่อไร** | • คำนวณง่าย ๆ เช่นบวกเลข, `.length`, format string สั้น ๆ<br>• ห่อทุกอย่างไปหมด "เผื่อไว้" |
| **ปัญหาที่พบบ่อย** | • คิดว่าใส่แล้วเร็วขึ้นเสมอ — จริง ๆ มันมีต้นทุน (เก็บค่า, เทียบ deps, กินหน่วยความจำ) ซึ่งอาจแพงกว่างานที่ประหยัดได้<br>• deps ไม่ครบ → ได้ค่าเก่าค้าง กลายเป็น bug ที่หายาก<br>• memo ค่าแล้วส่งให้ลูกที่ไม่ได้ห่อ `React.memo` → ไม่มีผลอะไรเลย |

#### useCallback

| หัวข้อ | รายละเอียด |
|---|---|
| **คืออะไร** | `useMemo` เวอร์ชันที่จำ **function** แทนค่าผลลัพธ์ |
| **ใช้เมื่อไร** | 1. ส่ง function เป็น props ให้ลูกที่ห่อ `React.memo`<br>2. function ที่เป็น dependency ของ `useEffect` |
| **ไม่ควรใช้เมื่อไร** | • ส่งให้ element ธรรมดา เช่น `onClick` ของ `<button>` — การสร้าง function ใหม่ราคาถูกมาก<br>• ลูกไม่ได้ห่อ memo — ยังไงก็ re-render อยู่ดี |
| **ปัญหาที่พบบ่อย** | • ใส่ `useCallback` แต่ลืมว่าข้างในจับตัวแปรที่เปลี่ยนทุก render → reference ก็เปลี่ยนอยู่ดี<br>• จับค่าเก่าค้าง (stale closure) เพราะ deps ไม่ครบ<br>• โค้ดอ่านยากขึ้นแลกกับผลลัพธ์ที่วัดไม่ได้ |

#### useContext

| หัวข้อ | รายละเอียด |
|---|---|
| **คืออะไร** | ช่องทางอ่านค่าที่ Provider ส่งลงมา โดยไม่ต้องส่งผ่าน props ทุกชั้น |
| **ใช้เมื่อไร** | ค่าที่ **เปลี่ยนไม่บ่อย** แต่ **ใช้กระจายทั่วแอป** เช่น theme, ภาษา, ข้อมูลผู้ใช้ที่ล็อกอิน, feature flag |
| **ไม่ควรใช้เมื่อไร** | • ข้อมูลที่เปลี่ยนถี่มาก เช่นทุกตัวอักษรที่พิมพ์ในช่อง search — ทุก consumer จะ re-render หมด<br>• ใช้แทน state management ทั้งระบบทั้งที่ต้องการ selector / middleware / devtools<br>• เก็บ server state ที่ต้อง cache + refetch |
| **ปัญหาที่พบบ่อย** | • ยัดทุกอย่างลง context เดียว → ค่าใดค่าหนึ่งเปลี่ยน ทุกคนที่ใช้ context นี้ re-render หมด<br>• ส่ง object literal เป็น value ตรง ๆ → reference ใหม่ทุก render → ทุก consumer re-render ทุกครั้งแม้ค่าเหมือนเดิม<br>• ลืมครอบ Provider → ได้ค่า default โดยไม่มี error เตือนชัด ๆ |

**กฎของ Hooks (ถามบ่อยมาก):** ต้องเรียกที่ระดับบนสุดของ component เสมอ ห้ามอยู่ใน if / loop / nested function
**เหตุผลจริง:** React จำ hook แต่ละตัวด้วย **ลำดับการเรียก** ไม่ใช่ชื่อ ถ้าลำดับเปลี่ยนระหว่าง render ค่าจะสลับกันมั่ว

### 5.8 Controlled vs Uncontrolled Component

```
CONTROLLED (React ถือพวงมาลัย)
user พิมพ์ → onChange → setState → re-render → value ใหม่ลง input
  * ทุกตัวอักษร = 1 รอบ render

UNCONTROLLED (DOM ถือพวงมาลัย)
user พิมพ์ → DOM เก็บค่าเอง → React ไม่รู้เรื่อง
  * ตอน submit ค่อยอ่านผ่าน ref
```

> **ให้มองภาพนี้ว่า** "Controlled คือ React เป็นแหล่งความจริงเดียว ทำให้ validate และควบคุมได้ทุกจังหวะ ส่วน Uncontrolled คือปล่อยให้เบราว์เซอร์ทำงานของมันแล้วเราไปเก็บผลตอนท้าย ซึ่งเร็วกว่าแต่ควบคุมระหว่างทางไม่ได้"

### 5.9 Lifting State Up → Prop Drilling → Context → State Management

```
ขั้นที่ 1: LOCAL STATE
   ComponentA มี state ของตัวเอง — จบ ไม่ต้องคิดอะไรมาก

ขั้นที่ 2: LIFTING STATE UP
   ComponentA และ ComponentB ต้องใช้ข้อมูลเดียวกัน
   → ยก state ขึ้นไปไว้ที่ parent ที่ใกล้ที่สุดของทั้งคู่

        Parent (ถือ state)
        ├── A (รับ props)
        └── B (รับ props)

ขั้นที่ 3: PROP DRILLING (อาการเริ่มไม่ดี)
   Parent → Layout → Section → Panel → Widget → ตัวที่ใช้จริง
   ชั้นกลาง 4 ชั้นไม่ได้ใช้เลย แต่ต้องรับ-ส่งต่อ

ขั้นที่ 4: CONTEXT
   Provider ที่ Parent → Widget อ่านเองได้เลย ไม่ต้องผ่านชั้นกลาง

ขั้นที่ 5: STATE MANAGEMENT LIBRARY
   เมื่อ state ซับซ้อน มี logic การอัปเดตหลายทาง ต้องการ devtools / middleware
```

> **ให้มองภาพนี้ว่า** "การจัดการ state คือบันไดที่ควรขึ้นทีละขั้นตามปัญหาที่เจอจริง ไม่ใช่กระโดดไปขั้นบนสุดตั้งแต่วันแรก"

**ข้อควรระวัง:** Prop Drilling **ไม่ได้ผิดเสมอไป** — ลึก 2-3 ชั้นยังอ่านง่ายและตามโค้ดได้ชัด การรีบใส่ Context อาจทำให้ตามหาที่มาของข้อมูลยากกว่าเดิม

### 5.10 State 3 ประเภท (สำคัญมากสำหรับ Mid-level ขึ้นไป)

```
                     STATE
                       │
     ┌─────────────────┼─────────────────┐
  LOCAL             GLOBAL            SERVER
  ของ component     ของทั้งแอป         เจ้าของจริงคือ server
     │                 │                  │
 useState          Context /          TanStack Query /
 useReducer        Zustand / Redux    SWR / RTK Query
     │                 │                  │
 modal เปิด/ปิด      theme, auth,       รายการสินค้า,
 tab ที่เลือก        ตะกร้าสินค้า        โปรไฟล์ผู้ใช้
```

> **ให้มองภาพนี้ว่า** "ก่อนจะเลือกเครื่องมือ ต้องถามก่อนว่าข้อมูลนี้ 'เจ้าของตัวจริงคือใคร' — ถ้าเจ้าของคือ server เราไม่ได้เก็บ state เราแค่ทำ cache ของข้อมูลคนอื่น"

**Insight ที่ทำให้คำตอบดูเป็น Mid-level ทันที:**
> "ปัญหา state management ส่วนใหญ่ที่ทีมเจอ จริง ๆ แล้วคือการเอา **server state** ไปยัดใน global store แล้วต้องเขียนเองทั้ง loading, error, cache, refetch, ข้อมูลเก่าค้าง — ซึ่ง TanStack Query แก้ให้หมดเพราะมันถูกออกแบบมาเพื่อเรื่องนี้โดยเฉพาะ พอแยกสองอย่างนี้ออกจากกัน global state ที่เหลือจริง ๆ มักเล็กมากจนไม่ต้องใช้ Redux ด้วยซ้ำ"

| Library | จุดแข็ง | เหมาะเมื่อ | trade-off |
|---|---|---|---|
| **Context (React เอง)** | มากับ React ไม่ต้องลง lib | ค่าเปลี่ยนไม่บ่อย, แอปเล็ก | ไม่มี selector — ค่าเปลี่ยนที ทุก consumer re-render |
| **Redux (Toolkit)** | เข้มงวด, devtools ดีมาก, ย้อน action ได้, มาตรฐานทีมใหญ่ | ทีมใหญ่, logic ซับซ้อน, ต้องตามรอยว่าใครเปลี่ยนอะไร | boilerplate มากกว่า, ต้องเรียนรู้ pattern |
| **Zustand** | เบา, API น้อย, มี selector ในตัว | ต้องการ global state แบบไม่เยิ่นเย้อ | ความอิสระสูง — ถ้าไม่มีวินัยทีม โครงสร้างจะกระจัดกระจาย |
| **TanStack Query** | จัดการ cache/refetch/stale/retry ให้หมด | ทุกแอปที่คุยกับ API | เรียนรู้แนวคิด cache key, ไม่ได้ออกแบบมาเก็บ client state |

**กฎการตอบ:** ห้ามพูดว่า "Zustand ดีกว่า Redux" ให้พูดว่า **"Zustand ดีกว่าเมื่อ..."** เสมอ

### 5.11 React Performance — ลำดับการคิด

```
[0] วัดก่อน (React DevTools Profiler) ← ห้ามข้ามขั้นนี้เด็ดขาด
      ↓
[1] ปัญหาอยู่ที่ "render บ่อยเกิน" หรือ "render ครั้งเดียวแต่หนัก"?
      ↓
   ┌──┴──────────────────────┐
render บ่อยเกิน            render หนัก
   ↓                          ↓
• ย้าย state ลงให้ใกล้ที่ใช้    • useMemo คำนวณที่แพงจริง
• แยก component ให้เล็กลง     • Virtualization (list ยาว)
• React.memo ตรงจุดคอขวด      • ลดจำนวน DOM node
• แยก context เป็นก้อนย่อย     • Lazy Loading / Code Splitting
      ↓
[2] วัดซ้ำ — ดีขึ้นจริงไหม? ไม่ดีขึ้น → ถอยออก อย่าเก็บโค้ดที่ซับซ้อนไว้เปล่า ๆ
```

> **ให้มองภาพนี้ว่า** "การ optimize React คือการหาว่าใครทำงานเกินจำเป็น ไม่ใช่การโปรยคำว่า memo ไปทั่วโค้ด"

**เทคนิคที่ถูกมองข้ามแต่ได้ผลที่สุด: ย้าย state ลงไปให้ใกล้ที่ใช้มากที่สุด**

```
ก่อน (state อยู่บนสุด — ทั้ง tree re-render ทุกตัวอักษร)
App [searchText] ──┬── Header
                   ├── HugeTable    ← re-render โดยไม่จำเป็น
                   └── SearchBox

หลัง (ย้าย state ลงไปอยู่ในตัวที่ใช้จริง)
App ──┬── Header
      ├── HugeTable                 ← ไม่ re-render แล้ว
      └── SearchBox [searchText]
```

> **ให้มองภาพนี้ว่า** "state ที่วางไว้สูงเกินไป เหมือนประกาศเสียงตามสายทั้งตึกเพื่อบอกเรื่องที่มีแค่ห้องเดียวต้องรู้"

| เทคนิค | ใช้เมื่อ | trade-off / ข้อควรระวัง |
|---|---|---|
| **React.memo** | component ลูกหนัก + props ไม่ค่อยเปลี่ยน | เทียบ props ทุกครั้งก็มีต้นทุน และพังทันทีถ้ามี props เป็น object/function ที่สร้างใหม่ทุก render |
| **useMemo / useCallback** | คำนวณแพงจริง หรือต้องรักษา reference | ถ้าใช้เกินจำเป็น = เพิ่มความซับซ้อน + กินหน่วยความจำโดยไม่ได้อะไร |
| **Code Splitting** | bundle ใหญ่, มีหน้าที่ผู้ใช้ส่วนน้อยเข้า | ผู้ใช้จะเจอ loading ตอนเข้าหน้านั้นครั้งแรก |
| **Lazy Loading** | component หนักที่ไม่ได้ใช้ทันที (modal, chart, editor) | ต้องออกแบบ fallback UI ให้ไม่กระตุก |
| **Virtualization** | list ยาวหลักพันหลักหมื่นแถว | ค้นหาในหน้า (Ctrl+F), การ print, SEO ทำได้ไม่ครบ |
| **ย้าย state ลงล่าง** | state ถูกวางสูงเกินความจำเป็น | แทบไม่มี trade-off — ควรลองอันนี้ก่อนเสมอ |

### 5.12 Error Boundary

```
              App
               │
      ┌── ErrorBoundary ──┐
      │                    │
   Dashboard          ChartWidget  ← พังตรงนี้
                           ↓
            ErrorBoundary จับไว้ แสดง fallback UI
                           ↓
            ส่วนอื่นของแอปยังใช้งานได้ปกติ
```

> **ให้มองภาพนี้ว่า** "Error Boundary คือเบรกเกอร์ไฟฟ้า — ไฟช็อตห้องเดียวก็ตัดเฉพาะห้องนั้น ไม่ต้องดับทั้งตึก"

**สิ่งที่ Error Boundary จับ **ไม่ได้** (ถามบ่อยมาก):**

| จับไม่ได้ | ต้องใช้อะไรแทน |
|---|---|
| Error ใน event handler (onClick ฯลฯ) | `try/catch` ตรงนั้นเอง |
| Error ใน async code / setTimeout | `.catch()` หรือ `try/catch` รอบ `await` |
| Error ใน Error Boundary ตัวมันเอง | ต้องมี boundary ชั้นนอกอีกชั้น |
| Error ฝั่ง Server-side rendering | จัดการที่ระดับ framework |

**เหตุผล:** Error Boundary ดักเฉพาะ error ที่เกิด**ระหว่าง render / lifecycle ของลูก** เท่านั้น ส่วน event handler รันนอกรอบ render ไปแล้ว

**วางไว้ตรงไหนดี:** วางหลายชั้นตามความสำคัญ — ชั้นนอกสุดกันจอขาว ชั้นในครอบ widget ที่เสี่ยง (chart, embed ของ third-party, ส่วนที่ข้อมูลไม่แน่นอน) เพื่อให้พังแค่กล่องเดียว

### 5.13 Forms

```
[ผู้ใช้พิมพ์]
     ↓
[เก็บค่า]        Controlled (state) หรือ Uncontrolled (ref)
     ↓
[Validate ฝั่ง client]   บอกผู้ใช้เร็ว — แต่ไว้ใจไม่ได้
     ↓
[Submit]        ต้องกันกดซ้ำ (disable ปุ่มระหว่างส่ง)
     ↓
[Validate ฝั่ง server]   ด่านจริงที่ตัดสิน — ห้ามข้าม
     ↓
[แสดงผล]        success / error ของแต่ละ field
```

> **ให้มองภาพนี้ว่า** "Validation ฝั่ง client มีไว้เพื่อประสบการณ์ที่ดีของผู้ใช้ ส่วน validation ฝั่ง server มีไว้เพื่อความถูกต้องของระบบ — ขาดอย่างหลังคือช่องโหว่ ขาดอย่างแรกคือ UX แย่"

**ประเด็นที่มักถูกถามต่อ:** ทำไม form ใหญ่ ๆ ถึงกระตุก
ตอบ: เพราะ controlled input ทำให้ทุกตัวอักษร trigger re-render ทั้ง form ถ้า form มี 40 field และแต่ละ field หนัก ก็กระตุกได้ — ทางแก้คือแยก component ให้ state อยู่ใกล้ field, ใช้ uncontrolled + ref, หรือใช้ form library ที่ออกแบบมาลด re-render โดยเฉพาะ

## 6. Example — Scenario จากงานจริง

### Scenario 1: หน้า Dashboard กระตุกเวลาพิมพ์ในช่องค้นหา

**อาการ:** พิมพ์ 1 ตัวอักษร หน่วงประมาณครึ่งวินาที

**วิธีไล่:**

1. เปิด React DevTools Profiler อัดตอนพิมพ์
2. เห็นว่า `<DataTable>` (2,000 แถว) re-render ทุกตัวอักษร
3. ดู state พบว่า `searchText` ถูกเก็บไว้ที่ `<App>` ซึ่งเป็นแม่ของทุกอย่าง

**ทางแก้เรียงตามลำดับที่ควรลอง:**

| ลำดับ | ทำอะไร | ทำไมลองอันนี้ก่อน |
|---|---|---|
| 1 | ย้าย `searchText` ลงไปไว้ใน `<SearchBox>` แล้วส่งค่าที่ "ยืนยันแล้ว" ขึ้นมา | แก้ที่ต้นเหตุ ไม่เพิ่มความซับซ้อน |
| 2 | debounce การค้นหา ~300ms | ลดจำนวนครั้งที่ต้องคำนวณจริง |
| 3 | `useMemo` การ filter ผลลัพธ์ | ตอนนี้ถึงจะคุ้ม เพราะยืนยันแล้วว่าการ filter แพง |
| 4 | Virtualization ถ้ายังช้า | 2,000 DOM node เป็นภาระของเบราว์เซอร์เอง |

**บทเรียน:** ทางแก้ที่ดีที่สุดคือข้อ 1 ซึ่ง **ไม่ได้ใช้ memo อะไรเลย** — คนส่วนใหญ่กระโดดไปข้อ 3 ทันทีโดยไม่วัด

### Scenario 2: ลบรายการที่ 2 แต่ค่าใน input ของแถวอื่นสลับกันมั่ว

**อาการ:** list ของ form แถว ๆ ลบแถวกลางแล้วค่าที่พิมพ์ไว้ย้ายไปแถวอื่น

**สาเหตุ:** ใช้ `key={index}` — พอลบแถวที่ 2 ออก แถวที่ 3 กลายเป็น index 2 React จึงมองว่า "ตัวที่ index 2 คือตัวเดิม แค่เนื้อหาเปลี่ยน" แล้ว**เก็บ DOM node กับ state ภายในของเดิมไว้**

**ทางแก้:** ใช้ id จริงของข้อมูลเป็น key

**คำถาม follow-up ที่มักตามมา:** "แล้วถ้าข้อมูลไม่มี id ล่ะ?"
คำตอบที่ดี: "สร้าง id ตอนเพิ่ม item เข้ามาในรายการครั้งแรก แล้วเก็บติดกับข้อมูลนั้นไปตลอด ห้ามสร้าง id ใหม่ตอน render เพราะ key จะเปลี่ยนทุกรอบ ซึ่งเท่ากับบอก React ว่าทุก item เป็นตัวใหม่หมด แย่กว่าใช้ index อีก"

### Scenario 3: API ถูกยิงซ้ำ 2 ครั้งทุกครั้งที่เปิดหน้า

**อาการ:** ดู Network tab เห็น request ซ้ำ 2 ครั้ง

**ต้องแยก 2 กรณี:**

| กรณี | สาเหตุ | ทางจัดการ |
|---|---|---|
| เกิดเฉพาะตอน dev | React Strict Mode ตั้งใจเรียก effect 2 รอบ เพื่อจับว่า cleanup เขียนครบไหม | **ไม่ใช่ bug** — แต่มันกำลังบอกว่าถ้าเรายกเลิก request ไม่เป็น เราจะมีปัญหา race condition จริงใน production |
| เกิดใน production ด้วย | deps ของ effect มี object/function ที่สร้างใหม่ทุก render หรือ component ถูก mount ซ้ำจาก key ที่เปลี่ยน | แก้ deps, ใช้ AbortController ยกเลิก request เก่า, หรือใช้ TanStack Query ที่ dedupe ให้ |

**คำตอบระดับ Mid-level:** "Strict Mode ไม่ได้สร้างปัญหา มันแค่เปิดโปงปัญหาที่มีอยู่แล้วให้เห็นตั้งแต่ตอน dev"

### Scenario 4: กดปุ่มแล้ว state ไม่เปลี่ยนทันที

**อาการ:** `setCount(count + 1)` แล้ว `console.log(count)` บรรทัดถัดไปยังได้ค่าเดิม

**สาเหตุ:** state คือ **snapshot ของรอบ render นั้น** — `setState` ไม่ได้เปลี่ยนตัวแปรในรอบปัจจุบัน แต่บอก React ว่า "รอบหน้าใช้ค่าใหม่นะ"

**สิ่งที่ต้องตอบเพิ่มให้ดูเป็น Mid:** "และถ้ากดปุ่มเดียวแล้วเรียก `setCount(count+1)` สองครั้ง จะได้ +1 ไม่ใช่ +2 เพราะทั้งสองครั้งอ่าน `count` ตัวเดียวกัน — ต้องใช้ updater function ที่รับค่าล่าสุดมาคำนวณต่อ ซึ่งปลอดภัยกว่าเสมอเมื่อค่าใหม่ขึ้นกับค่าเก่า"

### Scenario 5: Modal ปิดแล้ว แต่ interval ยังทำงานอยู่

**อาการ:** ปิด modal ที่มีนาฬิกานับถอยหลังแล้ว console ยัง log ทุกวินาที เปิด-ปิดหลายรอบยิ่ง log ถี่ขึ้นเรื่อย ๆ

**สาเหตุ:** `useEffect` ที่ `setInterval` แต่ไม่มี cleanup — ทุกครั้งที่ mount ก็สร้าง interval ใหม่ทับกันไปเรื่อย ๆ

**บทเรียนที่ต้องพูดให้ได้:** "ทุกอย่างที่เรา 'เปิด' ใน effect ต้องมีคนไป 'ปิด' ใน cleanup เสมอ — interval, event listener, subscription, request ที่ยังค้าง ไม่งั้นมันคือ memory leak ที่ค่อย ๆ กินทรัพยากรจนแอปช้าลงเรื่อย ๆ โดยไม่มีใครเห็น error"

### Scenario 6: เปลี่ยน theme ทีเดียว ทั้งแอป re-render

**อาการ:** toggle dark mode แล้ว Profiler ขึ้นแดงทั้งต้นไม้

**สาเหตุ:** Context ตัวเดียวเก็บทั้ง theme, ข้อมูลผู้ใช้, การตั้งค่า, ตะกร้าสินค้า → ค่าใดค่าหนึ่งเปลี่ยน ทุก consumer ก็ re-render หมด ยิ่งถ้าส่ง `value={{...}}` เป็น object literal ตรง ๆ ก็ได้ reference ใหม่ทุก render ด้วย

**ทางแก้:**

1. แยก context เป็นก้อนย่อยตามรอบการเปลี่ยนแปลง (`ThemeContext` แยกจาก `UserContext`)
2. `useMemo` ค่า `value` ของ Provider เพื่อรักษา reference
3. ถ้าต้องการ selector จริง ๆ (อยากให้ re-render เฉพาะคนที่ใช้ field นั้น) ให้พิจารณา Zustand — เพราะ Context ไม่มี selector ในตัว

**trade-off:** แยก context เยอะเกินก็เกิด provider ซ้อนกันเป็นชั้น ๆ อ่านยาก — ต้องหาจุดสมดุลตามความถี่ของการเปลี่ยนค่า

## 7. Compare

### 7.1 Props vs State

| หัวข้อ | Props | State |
|---|---|---|
| มาจากไหน | parent ส่งลงมา | component สร้างเอง |
| แก้ได้ไหม | ไม่ได้ (read-only) | ได้ ผ่าน setter |
| เปลี่ยนแล้วเกิดอะไร | child re-render | component นั้น + ลูก ๆ re-render |
| เปรียบเหมือน | พัสดุที่ได้รับ | สมุดบันทึกส่วนตัว |
| ใช้เมื่อ | ส่งข้อมูล/ฟังก์ชันลงไป | เก็บค่าที่เปลี่ยนตามการใช้งาน |

### 7.2 Virtual DOM vs DOM

| หัวข้อ | Virtual DOM | DOM |
|---|---|---|
| คืออะไร | JavaScript object ในหน่วยความจำ | โครงสร้างจริงที่เบราว์เซอร์ถือ |
| ต้นทุนการแก้ | ถูก (แค่สร้าง object) | แพง (กระทบ layout + paint) |
| ใครใช้ | React | เบราว์เซอร์ |
| เร็วกว่ากันไหม | **ไม่ใช่เรื่องเร็วกว่า** — เป็นเรื่องแก้ DOM น้อยครั้งลง + เขียน declarative ได้ | - |

### 7.3 Render vs Re-render vs Repaint

| หัวข้อ | เกิดอะไรขึ้น | แพงแค่ไหน |
|---|---|---|
| **Render** | React เรียก component function ได้ VDOM | ถูก (ถ้า component ไม่หนัก) |
| **Re-render** | เรียกซ้ำเพราะ state/props/context เปลี่ยน | ถูก-ปานกลาง |
| **Commit** | React แก้ DOM จริงเฉพาะจุดที่ต่าง | แพงขึ้น |
| **Repaint / Reflow** | เบราว์เซอร์คำนวณ layout และวาดใหม่ | **แพงที่สุด** |

**บทสรุปที่ต้องจำ:** Re-render 10 ครั้งที่ไม่มีอะไรเปลี่ยน = แก้ DOM 0 ครั้ง = ไม่แพงอย่างที่คิด
สิ่งที่ควรกลัวคือ re-render ที่ **ทุกครั้งพ่นผลลัพธ์ใหม่จริง ๆ** ต่างหาก

### 7.4 useMemo vs useCallback vs React.memo

| หัวข้อ | useMemo | useCallback | React.memo |
|---|---|---|---|
| จำอะไร | ค่าผลลัพธ์ | function | ผลของ component |
| ใช้ที่ไหน | ใน component | ใน component | ห่อ component ตอน export |
| แก้ปัญหาอะไร | คำนวณซ้ำ / reference ของค่า | reference ของ function | re-render ของลูกที่ไม่จำเป็น |
| พังเมื่อ | deps ไม่ครบ | deps ไม่ครบ | props มี object/function ที่สร้างใหม่ทุกรอบ |

**ความสัมพันธ์:** ทั้งสามตัวมักต้องใช้ **ด้วยกัน** — `React.memo` จะไร้ผลทันทีถ้าเราส่ง object หรือ function ที่สร้างใหม่ทุก render ลงไปให้

### 7.5 Controlled vs Uncontrolled

| หัวข้อ | Controlled | Uncontrolled |
|---|---|---|
| แหล่งความจริง | React state | DOM |
| validate ระหว่างพิมพ์ | ทำได้ทันที | ทำได้ยาก |
| จำนวน re-render | ทุกตัวอักษร | แทบไม่มี |
| ใช้เมื่อ | ต้อง validate สด, แสดงผลตามค่าที่พิมพ์, disable ปุ่มตามเงื่อนไข | form ง่าย ๆ, form ใหญ่มาก ๆ ที่ต้องการ performance, file input |
| trade-off | ควบคุมได้เต็มที่ แต่ render เยอะ | เบา แต่ควบคุมระหว่างทางไม่ได้ |

### 7.6 Context vs Redux vs Zustand vs TanStack Query

| หัวข้อ | Context | Redux Toolkit | Zustand | TanStack Query |
|---|---|---|---|---|
| ออกแบบมาเพื่อ | ส่งค่าลง subtree | client state ที่ซับซ้อน | client state แบบเบา | **server state** |
| มี selector | ไม่มี | มี | มี | ไม่เกี่ยว (คนละปัญหา) |
| cache / refetch / stale | ต้องเขียนเอง | ต้องเขียนเอง | ต้องเขียนเอง | มีให้ครบ |
| devtools | ไม่มี | ดีมาก | มี | มี |
| เหมาะเมื่อ | theme, auth, locale | ทีมใหญ่ ต้องการความเข้มงวดและตามรอยได้ | อยากได้ global state แบบไม่เยิ่นเย้อ | ทุกแอปที่คุยกับ API |
| trade-off | ค่าเปลี่ยนที ทุก consumer ตื่น | boilerplate + เรียนรู้ pattern | อิสระสูง ต้องมีวินัยทีม | ต้องเข้าใจแนวคิด cache key |

### 7.7 Prop Drilling vs Context vs Composition

| ทางเลือก | ข้อดี | ข้อเสีย | เหมาะเมื่อ |
|---|---|---|---|
| **Prop Drilling** | ตามรอยข้อมูลง่ายที่สุด ชัดเจนว่ามาจากไหน | เยิ่นเย้อเมื่อลึกเกิน 3-4 ชั้น | ลึกไม่มาก |
| **Context** | ข้ามชั้นกลางได้ | ตามรอยยากขึ้น, re-render เป็นวง | ค่าที่ใช้ทั่วแอปและเปลี่ยนไม่บ่อย |
| **Composition (ส่ง children)** | ไม่ต้องส่ง props ลึก และไม่ต้องใช้ context | ต้องออกแบบโครงสร้าง component ให้ดี | ชั้นกลางแค่ "ห่อ" ไม่ได้ใช้ข้อมูล |

**Composition คือทางเลือกที่คนลืมบ่อยที่สุด** — แทนที่จะส่ง props ลง 4 ชั้น ให้ parent สร้าง element แล้วส่งลงไปเป็น `children` ชั้นกลางก็ไม่ต้องรู้จักข้อมูลเลย

### 7.8 React vs Vanilla JS

| หัวข้อ | React | Vanilla JS |
|---|---|---|
| วิธีคิด | Declarative (ประกาศผลลัพธ์) | Imperative (สั่งทีละขั้น) |
| ความเร็วดิบ | มี overhead ของ VDOM | เร็วกว่าถ้าเขียนถูกจุด |
| ความง่ายเมื่อแอปโต | ดีกว่ามาก | ยากขึ้นแบบทวีคูณ |
| เหมาะเมื่อ | UI ซับซ้อน state เยอะ ทีมหลายคน | หน้า static, widget เล็ก, ต้องการ bundle เล็กที่สุด |

## 8. React Interview Trap

หัวข้อนี้คือ "กับดัก" ที่ผู้สัมภาษณ์ชอบวางไว้ เพราะมันแยกคนที่ **ท่องมา** ออกจากคนที่ **เข้าใจจริง** ได้ทันที

### Trap 1 — "useMemo ทำให้เร็วขึ้น" ❌

**ความเชื่อผิด:** ใส่ `useMemo` เยอะ ๆ แอปจะเร็วขึ้น

**ความจริง:** `useMemo` **มีต้นทุนของมันเอง**:

- ต้องเก็บค่าเก่าไว้ในหน่วยความจำ
- ต้องเทียบ dependency array ทุก render
- เพิ่มความซับซ้อนให้คนอ่านโค้ด

ถ้างานที่ประหยัดได้ถูกกว่าต้นทุนพวกนี้ **แปลว่าคุณทำให้มันช้าลงและอ่านยากขึ้นพร้อมกัน**

```
งานที่ memo แพงกว่าต้นทุน memo     → คุ้ม ✓
งานที่ memo ถูกกว่าต้นทุน memo     → ขาดทุน ✗   ← กรณีส่วนใหญ่ในโค้ดจริง
```

**ยิ่งกว่านั้น:** `useMemo` ที่ deps ไม่ครบ = ได้ค่าเก่าค้าง = **bug ที่หายากที่สุดแบบหนึ่ง** เพราะมันไม่ error มันแค่แสดงข้อมูลผิด

**คำตอบที่ได้คะแนน:**
> "`useMemo` ไม่ใช่เครื่องมือเร่งความเร็ว มันคือเครื่องมือ **แลกหน่วยความจำกับการคำนวณซ้ำ** ผมจะใช้เมื่อ 2 กรณี: หนึ่ง วัดแล้วว่าการคำนวณนั้นแพงจริง สอง ต้องรักษา reference ให้คงที่เพื่อให้ `React.memo` หรือ dependency array ของ effect ทำงานถูกต้อง นอกจากสองกรณีนี้ผมมองว่ามันเพิ่มหนี้ทางเทคนิคมากกว่าได้ประโยชน์"

### Trap 2 — "useEffect คือที่ไว้ทำทุกอย่าง" ❌

**ความเชื่อผิด:** อะไรที่ต้องทำ "หลังจาก state เปลี่ยน" ให้ยัดลง `useEffect`

**ความจริง:** `useEffect` มีไว้ **ซิงก์กับสิ่งที่อยู่นอกการควบคุมของ React** เท่านั้น

| สิ่งที่คนชอบยัดลง useEffect | ควรทำที่ไหนจริง ๆ | ทำไม |
|---|---|---|
| คำนวณค่าจาก state อื่น | คำนวณตอน render ตรง ๆ | ไม่ต้องรอ render รอบสอง และไม่มีจังหวะที่ค่าไม่ sync |
| filter / sort ข้อมูลก่อนแสดง | คำนวณตอน render (+ `useMemo` ถ้าแพงจริง) | เหมือนข้อบน |
| ทำอะไรหลังผู้ใช้กดปุ่ม | ใน event handler นั้นเลย | ผู้ใช้กดปุ่ม = เรารู้เหตุการณ์อยู่แล้ว ไม่ต้องรอ effect มาบอก |
| reset state เมื่อ props เปลี่ยน | ใช้ `key` เพื่อบังคับสร้าง component ใหม่ | ตรงไปตรงมากว่า และไม่มีจังหวะที่จอแสดงค่าเก่าแวบหนึ่ง |
| ส่ง event ไปบอก parent | เรียก callback ตอนเกิดเหตุการณ์จริง | effect ไม่รู้ว่า "ทำไม" ค่าถึงเปลี่ยน |

**ทำไมถึงสำคัญ:** การใส่ effect เกินจำเป็นทำให้เกิด **render รอบพิเศษทุกครั้ง** (render → effect → setState → render อีกรอบ) ซึ่งผู้ใช้อาจเห็นจอกระพริบค่าเก่าแวบหนึ่ง และยังเสี่ยงต่อ infinite loop

**คำตอบที่ได้คะแนน:**
> "เวลาผมเห็น `useEffect` ผมจะถามก่อนว่า 'นี่คือการซิงก์กับของนอก React จริงไหม' ถ้าไม่ใช่ เช่นเป็นการคำนวณค่าหรือตอบสนอง event ผมจะย้ายออก เพราะ effect ที่ไม่จำเป็นทำให้เกิด render รอบพิเศษและทำให้ลำดับการทำงานตามยากขึ้น"

### Trap 3 — "State เปลี่ยน = DOM เปลี่ยนทุกครั้ง" ❌

**ความเชื่อผิด:** ทุกครั้งที่ `setState` DOM จะถูกแก้

**ความจริง:** มีอย่างน้อย 3 จุดที่ทำให้ไม่เกิดการแก้ DOM:

```
setState ด้วยค่าเดิมเป๊ะ (เทียบด้วย Object.is)
      ↓ React อาจข้าม re-render ไปเลย
      
re-render แล้วได้ VDOM เหมือนเดิมทุกจุด
      ↓ Reconciliation ไม่พบความต่าง → ไม่แตะ DOM
      
มีความต่างจริง
      ↓ Commit เฉพาะ node ที่ต่าง — ไม่ได้สร้างใหม่ทั้ง tree
```

> **ให้มองภาพนี้ว่า** "Re-render คือการคิดใหม่ ส่วนการแก้ DOM คือการลงมือ — React คิดบ่อยกว่าที่มันลงมือมาก"

**และกลับกัน** — DOM ก็อาจเปลี่ยนโดยที่ state ไม่เปลี่ยน เช่น เบราว์เซอร์จัดการ layout ใหม่ตอน resize หรือ animation ที่รันด้วย CSS

**คำตอบที่ได้คะแนน:**
> "Re-render ไม่เท่ากับการแก้ DOM ครับ Re-render คือ React เรียก function ของเราเพื่อดูว่าผลลัพธ์ควรเป็นอะไร แล้วค่อยเทียบกับของเดิม ถ้าไม่ต่างก็ไม่แตะ DOM เลย เพราะฉะนั้นเวลา optimize ผมจะไม่ไล่ลด re-render ทุกตัว แต่จะดูว่า re-render ตัวไหนที่นำไปสู่การแก้ DOM จริงและกินเวลาจริง"

### Trap 4 — "Virtual DOM เร็วกว่า DOM" ❌

**ความเชื่อผิด:** React เร็วเพราะมี Virtual DOM

**ความจริง:** Virtual DOM คือ **ชั้นเพิ่มเติม** มันไม่มีทางเร็วกว่าการแก้ DOM ที่จุดเดียวโดยตรง เพราะมันต้อง:

1. สร้าง object tree ใหม่
2. เดินเทียบทั้ง tree
3. แล้วค่อยแก้ DOM อยู่ดี

```
Vanilla JS ที่รู้จุดพอดี:  แก้ DOM 1 จุด                  ← เร็วที่สุด
React:                    สร้าง VDOM → diff → แก้ DOM 1 จุด  ← มี overhead
React (แย่ที่สุด):         สร้าง VDOM ทั้ง tree → diff → แก้ DOM 0 จุด
```

**แล้ว React ชนะตรงไหน:**

| React ให้อะไร | ทำไมสำคัญในงานจริง |
|---|---|
| ป้องกันการแก้ DOM ซ้ำซ้อน | คนเขียน imperative มักแก้ DOM เกินจำเป็นโดยไม่รู้ตัว |
| Batching | setState หลายครั้งรวมเป็นการวาดรอบเดียว |
| เขียนแบบ declarative ได้ | ไม่ต้องจำว่า "ถ้าข้อมูลนี้เปลี่ยน ต้องไปแก้ที่ไหนบ้าง" |
| ประสิทธิภาพที่คาดเดาได้ | ไม่ต้องพึ่งว่าโปรแกรมเมอร์แต่ละคนเขียน optimize เก่งแค่ไหน |

**คำตอบที่ได้คะแนน:**
> "Virtual DOM ไม่ได้เร็วกว่า DOM ครับ มันช้ากว่าด้วยซ้ำถ้าเทียบต่อการแก้ 1 จุด สิ่งที่มันซื้อให้เราคือความสามารถในการเขียนแบบ declarative โดยที่ประสิทธิภาพยังอยู่ในระดับที่ยอมรับได้เสมอ — เราแลกความเร็วสูงสุดทางทฤษฎี กับความเร็วที่ 'ดีพอ' ซึ่งไม่ขึ้นกับว่าคนเขียนจะเก่ง optimize แค่ไหน ในทีมที่มีหลายคนแก้โค้ดเดียวกัน ข้อแลกเปลี่ยนนี้คุ้มมาก"

### Trap 5 — "ห่อ React.memo ให้หมดทุก component เลยดีไหม" ❌

**ความจริง:** `React.memo` ต้องเทียบ props ทุกครั้งที่ parent render ซึ่งก็มีต้นทุน และจะ **ไม่มีผลเลย** ถ้า props มี object / array / function ที่สร้างใหม่ทุก render — ซึ่งเป็นกรณีส่วนใหญ่ถ้าไม่ได้ตั้งใจจัดการ

> ใส่ `React.memo` โดยไม่จัดการ reference ของ props = จ่ายค่าเทียบ props ฟรี ๆ โดยไม่ได้อะไรกลับมา

### Trap 6 — "useState เก็บได้ทุกอย่าง" ❌

**ความจริง:** ถามก่อนเสมอว่าค่านี้คืออะไร

```
ค่านี้คำนวณจาก state อื่นได้ไหม?  ได้ → คำนวณตอน render อย่าเก็บเป็น state
ค่านี้เปลี่ยนแล้วจอต้องเปลี่ยนไหม?  ไม่ → ใช้ useRef
เจ้าของตัวจริงคือ server ไหม?     ใช่ → ใช้ TanStack Query อย่าเก็บเอง
```

**ปัญหาที่ตามมาจากการเก็บ state เกิน:** ต้องคอย sync หลายที่ให้ตรงกัน ซึ่งเป็นแหล่งกำเนิด bug อันดับหนึ่งของ frontend

### Trap 7 — "ใช้ index เป็น key ก็ได้ ไม่เห็นพังเลย" ❌

**ความจริง:** มันไม่พังจน**วันที่มีคนเพิ่มฟีเจอร์ "ลบ" หรือ "เรียงลำดับ"** เข้ามา แล้ว bug จะโผล่ในที่ที่ไม่มีใครเดาได้ — ค่าใน input ย้ายแถว, checkbox ติ๊กผิดตัว, animation เล่นผิดอัน

### Trap 8 — "Error Boundary จับได้ทุก error" ❌

**ความจริง:** จับได้เฉพาะ error ตอน render / lifecycle ของลูก — **ไม่จับ** event handler, async, และ error ในตัวมันเอง (ดูตาราง 5.12)

### สรุป Interview Trap ในตารางเดียว

| ประโยคที่ได้ยินบ่อย | ความจริงสั้น ๆ |
|---|---|
| "useMemo ทำให้เร็วขึ้น" | ทำให้เร็วขึ้น**เมื่อ**งานแพงกว่าต้นทุน memo — ไม่งั้นคือขาดทุน |
| "useEffect ไว้ทำทุกอย่างหลัง render" | ไว้ซิงก์กับของนอก React เท่านั้น |
| "state เปลี่ยน = DOM เปลี่ยน" | re-render ≠ commit ≠ repaint |
| "Virtual DOM เร็วกว่า DOM" | ช้ากว่าต่อ 1 จุด แต่ซื้อความ declarative + ลดการแก้ซ้ำซ้อน |
| "memo ทุกตัวปลอดภัยกว่า" | จ่ายต้นทุนเทียบ props ฟรี ๆ ถ้าไม่จัดการ reference |
| "index เป็น key ก็ได้" | ได้จนกว่าจะมีการ ลบ/แทรก/เรียงใหม่ |
| "Error Boundary จับได้หมด" | ไม่จับ event handler และ async |

## 8b. Common Mistakes (นอกเหนือจาก Interview Trap)

| # | ความเข้าใจผิด / สิ่งที่ทำผิด | ความจริง / ทางที่ถูก |
|---|---|---|
| 1 | Mutate state ตรง ๆ (`arr.push(x)` แล้ว `setArr(arr)`) | reference เดิม → React มองว่าไม่เปลี่ยน → ต้องสร้างชุดใหม่ |
| 2 | เรียก `useState` ใน if / loop | ผิดกฎของ Hooks — React จำ hook ด้วยลำดับการเรียก |
| 3 | ใช้ `document.getElementById` แก้ DOM ใน React | ไปแก้ "ผลลัพธ์" ที่ React เป็นเจ้าของ → ทับกันเละ ให้ใช้ state หรือ ref |
| 4 | ลืม cleanup ใน `useEffect` | interval / listener / subscription ซ้อนกัน = memory leak |
| 5 | ใส่ `setState` ใน effect ที่ dep มี state ตัวนั้น | infinite loop |
| 6 | เก็บ derived state ซ้ำ (`items` + `totalPrice`) | สอง state ต้องคอย sync กัน → คำนวณตอน render แทน |
| 7 | คิดว่า `setState` ทำงานทันที | เป็น snapshot ของรอบ render — ต้องใช้ updater function เมื่อค่าใหม่ขึ้นกับค่าเก่า |
| 8 | ส่ง object literal เป็น `value` ของ Context | reference ใหม่ทุก render → consumer ทุกตัว re-render |
| 9 | ยัดทุกอย่างลง Context เดียว | ค่าใดค่าหนึ่งเปลี่ยน ทุกคน re-render → แยกตามรอบการเปลี่ยน |
| 10 | เอาข้อมูลจาก API ไปเก็บใน global store เอง | ต้องเขียน loading/error/cache/refetch/invalidate เอง → ใช้เครื่องมือ server state |
| 11 | ใส่ `key` ที่สร้างใหม่ทุก render (เช่น `Math.random()`) | React มองว่าทุก item เป็นตัวใหม่ → unmount/mount ทั้งหมดทุกรอบ |
| 12 | ไม่ disable ปุ่ม submit ระหว่างส่ง | ผู้ใช้กดซ้ำ → request ซ้ำ → ข้อมูลซ้ำ |
| 13 | validate แค่ฝั่ง client | ฝั่ง server คือด่านจริง — client validation คือ UX ไม่ใช่ security |
| 14 | ทำ optimization โดยไม่วัดก่อน | เสียเวลากับจุดที่ไม่ใช่คอขวด และเพิ่มความซับซ้อนถาวร |
| 15 | คิดว่า Strict Mode ที่เรียก effect 2 ครั้งคือ bug ของ React | มันคือเครื่องมือจับ effect ที่ cleanup ไม่ครบ |
| 16 | แยก component ตามหน้าตา ไม่ใช่ตามความรับผิดชอบ | component ที่รับผิดชอบหลายเรื่องจะ re-render บ่อยและ test ยาก |

### 9.2 "หน้าจอไม่อัปเดตทั้งที่ข้อมูลเปลี่ยนแล้ว"

| ลำดับ | ตรวจอะไร | ถ้าใช่แปลว่า |
|---|---|---|
| 1 | เรา mutate ของเดิมแล้ว set กลับหรือเปล่า | reference เดิม → React ไม่เห็นความเปลี่ยนแปลง |
| 2 | ค่าอยู่ใน `useRef` แทนที่จะเป็น `useState` หรือเปล่า | ref ไม่ trigger re-render โดยตั้งใจ |
| 3 | ลืมครอบ Provider ของ Context หรือเปล่า | อ่านได้ค่า default เงียบ ๆ |
| 4 | component นี้ถูกห่อ `React.memo` แล้ว props ไม่เปลี่ยนจริงไหม | memo บล็อกการ re-render อยู่ |
| 5 | ข้อมูลมาจาก cache ที่ยังไม่ invalidate หรือเปล่า | ต้อง invalidate key หลัง mutate |

### 9.4 "Infinite loop / effect รันไม่หยุด"

| ตรวจอะไร | เหตุผล |
|---|---|
| ใน effect มี `setState` ที่ทำให้ dep ของตัวเองเปลี่ยนไหม | วนไม่จบแน่นอน |
| dep array มี object / array / function ที่สร้างใหม่ทุก render ไหม | reference ใหม่ทุกครั้ง = dep เปลี่ยนทุกครั้ง |
| ลืมใส่ dep array ไปเลยหรือเปล่า | effect รันทุก render |
| มี `key` ที่เปลี่ยนทุก render ไหม | component ถูก unmount/mount ใหม่ตลอด |

### 9.5 "ข้อมูลแวบมาแล้วหายไป / แสดงข้อมูลเก่า"

[3] มีการยกเลิก request เก่าเมื่อ dep เปลี่ยนหรือเปล่า

| เมื่อไรที่ "ไม่" ควรใช้ React | หน้า static ล้วน, widget เล็กที่ต้องการ bundle จิ๋ว, ทีมที่ไม่มีคนดูแลระยะยาว |

## 11. Answer Like a Developer

### โครงการตอบ 5 ชั้นสำหรับคำถาม React

```
[1] นิยาม 1 ประโยค (ภาษาคน)
      ↓
[2] มันแก้ปัญหาอะไร (ก่อนมีสิ่งนี้เจ็บปวดยังไง)
      ↓
[3] ทำงานอย่างไรคร่าว ๆ (mechanism)
      ↓
[4] ใช้เมื่อไร / ไม่ใช้เมื่อไร  ← ชั้นนี้แยก Junior ออกจาก Mid
      ↓
[5] ข้อควรระวัง + เคยเจออะไรจริง  ← ชั้นนี้แยก Mid ออกจาก Senior
```

> **ให้มองภาพนี้ว่า** "ผู้สัมภาษณ์ไม่ได้อยากรู้แค่ว่าคุณรู้จักมันไหม แต่อยากรู้ว่าคุณรู้ว่าเมื่อไรไม่ควรใช้มันด้วย"

### ตัวอย่างที่ 1 — "useEffect คืออะไร"

**แบบท่องจำ (คะแนนต่ำ):**
> "useEffect คือ hook ที่ใช้ทำ side effect หลังจาก component render เสร็จครับ"

**แบบตอบเหมือน Developer:**
> "`useEffect` คือที่ที่เราเอาไว้ซิงก์ React กับของที่อยู่นอกการควบคุมของ React ครับ เช่น network, timer, subscription หรือ browser API
> เหตุผลที่ต้องมีคือ React ควบคุมแค่การวาดหน้าจอจาก state ส่วนของนอกพวกนี้มีชีวิตของมันเอง ต้องมีคนคอยเปิดและปิดให้ตรงกับช่วงชีวิตของ component
> จุดที่ผมระวังที่สุดคือสองเรื่อง: หนึ่ง cleanup — ทุกอย่างที่เปิดต้องมีคนปิด ไม่งั้นเปิด-ปิดหน้าไม่กี่รอบก็มี interval ซ้อนกันหลายตัว
> สอง คือผมจะไม่ใช้ `useEffect` กับสิ่งที่ไม่ใช่ของนอก React เช่นการคำนวณค่าจาก state อื่น ผมจะคำนวณตอน render ตรง ๆ เพราะถ้าใช้ effect มันจะเกิด render รอบพิเศษ และผู้ใช้อาจเห็นค่าเก่าแวบหนึ่งก่อนค่าใหม่จะมา
> เคสจริงที่ผมเคยเจอคือทีมเขียน effect ไว้ filter ข้อมูลแล้ว setState ผลลัพธ์ ซึ่งทำให้ทุกการเปลี่ยน filter เกิด render 2 รอบ พอย้ายไปคำนวณตอน render ปัญหาหายและโค้ดสั้นลงด้วยครับ"

**ทำไมได้คะแนน:** ครบทั้ง why → mechanism → ไม่ควรใช้ตอนไหน → ประสบการณ์จริง

### ตัวอย่างที่ 2 — "ทำไมหน้านี้ช้า"

**สิ่งที่ห้ามทำ:** รีบตอบว่า "ใส่ useMemo ครับ"

**โครงที่ควรใช้:**

1. **ถามกลับก่อน**: "ช้าตอนโหลดครั้งแรก หรือช้าตอนใช้งาน (interaction) ครับ" — สองอันนี้คนละปัญหาคนละทางแก้
2. **บอกวิธีพิสูจน์**: "ผมจะเปิด Profiler อัดช่วงที่ช้า แล้วดูว่าเป็นเพราะ render บ่อยเกินหรือ render ครั้งเดียวแต่หนัก"
3. **เรียงทางแก้ตามลำดับ**: ย้าย state ลงล่าง → แยก component → memo ตรงจุด → virtualization
4. **ปิดท้ายด้วยหลักการ**: "ผมจะวัดซ้ำทุกครั้งหลังแก้ ถ้าไม่ดีขึ้นจริงผมจะถอยออก เพราะโค้ดที่ซับซ้อนขึ้นโดยไม่ได้ผลคือหนี้ทางเทคนิค"

### ตัวอย่างที่ 3 — "จะจัดการ state ของแอปนี้อย่างไร"

**โครงที่ควรใช้:**

1. แยกก่อนว่าข้อมูลแต่ละก้อน "เจ้าของตัวจริงคือใคร" — server หรือ client
2. server state → เครื่องมือที่ทำ cache/refetch/stale ให้ (TanStack Query)
3. client state → เริ่มจาก local ให้มากที่สุด ยกขึ้นเมื่อจำเป็นจริง
4. global ที่เหลือ → ถ้าเปลี่ยนไม่บ่อยใช้ Context, ถ้าต้องการ selector หรือ logic ซับซ้อนค่อยดู Zustand/Redux
5. ปิดด้วย trade-off: "ผมจะไม่เริ่มจาก Redux ตั้งแต่วันแรก เพราะส่วนใหญ่พอแยก server state ออกไปแล้ว global state ที่เหลือมักเล็กกว่าที่คิดมาก"

### ประโยคที่ควรมีติดตัว

| สถานการณ์ | ประโยค |
|---|---|
| ถูกถามเรื่อง performance | "ผมจะวัดก่อนเสมอ เพราะ optimize ผิดจุดคือเพิ่มความซับซ้อนโดยไม่ได้อะไร" |
| ถูกถามเรื่อง Virtual DOM | "มันไม่ได้เร็วกว่า DOM แต่มันทำให้เราเขียนแบบ declarative ได้โดยที่ performance ยังคาดเดาได้" |
| ถูกถามเรื่อง useEffect | "ผมจะถามก่อนว่านี่คือการซิงก์กับของนอก React จริงไหม ถ้าไม่ใช่ผมจะย้ายออก" |
| ถูกถามเรื่อง state management | "ผมจะแยก server state ออกจาก client state ก่อน เพราะสองอันนี้มีปัญหาคนละแบบ" |
| ถูกถามว่าเลือก library ไหน | "ขึ้นกับว่าทีมต้องการอะไรครับ — ถ้า... ผมจะเลือก... เพราะ..." (ห้ามตอบว่า A ดีกว่า B ลอย ๆ) |
| ไม่รู้คำตอบ | "ผมยังไม่เคยเจอเคสนี้ตรง ๆ แต่ผมจะเริ่มจากการดู... แล้วตั้งสมมติฐานว่า... ครับ" |

## 12. One-Minute Review

**React คือ library สำหรับสร้าง UI ด้วยแนวคิด `UI = f(state)`** — เราประกาศว่าหน้าตาควรเป็นอย่างไรตามข้อมูล แล้ว React จัดการ DOM ให้เอง แทนที่เราจะไปสั่งแก้ DOM ทีละขั้น

**Component** คือ function ที่รับ **Props** (ไหลลงจากแม่ แก้ไม่ได้) และมี **State** (ความจำของตัวเอง แก้ได้ และเปลี่ยนแล้วทำให้ **Re-render**) ประกอบกันเป็น **Component Tree** ข้อมูลไหลลงทางเดียว ส่วนการขอเปลี่ยนแปลงไหลขึ้นผ่าน callback

**วงจร 1 รอบ:** event → setState → schedule (batching) → **Render** (ได้ Virtual DOM ใหม่ ยังไม่แตะ DOM) → **Reconciliation** (diff เทียบเก่า-ใหม่ โดยใช้ type + **Key**) → **Commit** (แก้ DOM เฉพาะที่ต่างจริง) → paint → **useEffect**
สิ่งที่ต้องจำ: **Re-render ≠ แก้ DOM** และ **Virtual DOM ไม่ได้เร็วกว่า DOM** — มันซื้อความ declarative และลดการแก้ DOM ซ้ำซ้อนให้เรา

**Hooks:** `useState` (ค่าที่เปลี่ยนแล้วจอต้องเปลี่ยน) / `useEffect` (ซิงก์กับของนอก React เท่านั้น + cleanup ทุกครั้ง) / `useRef` (จำค่าโดยไม่ปลุก React + อ้าง DOM) / `useMemo` (จำผลคำนวณที่แพงจริง หรือรักษา reference) / `useCallback` (จำ function สำหรับ memo/deps) / `useContext` (อ่านค่าที่ส่งลงทั้ง subtree ค่าที่เปลี่ยนไม่บ่อย)
กฎของ Hooks: เรียกที่ระดับบนสุดเสมอ เพราะ React จำด้วย **ลำดับ**

**Lifecycle:** Mount (ติดตั้ง) → Update (ซิงก์ตาม deps) → Unmount (เก็บกวาด — ไม่เก็บคือ memory leak)

**State 3 ประเภท:** Local (useState) / Global (Context, Zustand, Redux) / **Server State** (TanStack Query) — ถามก่อนเสมอว่า "เจ้าของข้อมูลตัวจริงคือใคร" ปัญหา state management ส่วนใหญ่คือการเอา server state ไปยัดใน global store

**Performance:** **วัดก่อนเสมอ** → ย้าย state ลงให้ใกล้ที่ใช้ (ได้ผลที่สุดและ trade-off น้อยที่สุด) → แยก component → `React.memo` + `useMemo`/`useCallback` ตรงจุดคอขวด → Code Splitting / Lazy Loading สำหรับ bundle → Virtualization สำหรับ list ยาว

**กับดักที่ต้องจำ:** `useMemo` ไม่ได้ทำให้เร็วเสมอ / `useEffect` ไม่ใช่ที่ไว้ทำทุกอย่าง / state เปลี่ยนไม่ได้แปลว่า DOM เปลี่ยน / Virtual DOM ไม่ได้เร็วกว่า DOM / index เป็น key พังเมื่อมีการลบหรือเรียงใหม่ / Error Boundary ไม่จับ event handler และ async

## 13. Memory Card

### จำ 5 อย่าง

1. **UI = f(state)** — อยากให้จอเปลี่ยน ให้ไปเปลี่ยนข้อมูล ห้ามไปแก้ DOM เอง
2. **Re-render ≠ แก้ DOM** — React คิดบ่อยกว่าที่มันลงมือมาก สิ่งที่แพงจริงคือ commit และ repaint
3. **useEffect มีไว้ซิงก์กับของนอก React เท่านั้น** — และทุกอย่างที่เปิดต้องมีคนปิด (cleanup)
4. **ถามก่อนว่า "เจ้าของข้อมูลคือใคร"** — server state ไม่ใช่ global state และต้องใช้เครื่องมือคนละตัว
5. **วัดก่อน optimize เสมอ** — `useMemo`/`React.memo` มีต้นทุน ใส่มั่วคือขาดทุนสองต่อ

### Keyword สั้น

- **React** → library สำหรับ UI แบบ declarative
- **Component** → function ที่รับข้อมูลแล้วคืนหน้าตา
- **Props** → พัสดุจากแม่ อ่านได้ แก้ไม่ได้
- **State** → สมุดบันทึกส่วนตัว เปลี่ยนแล้วจอเปลี่ยน
- **Render** → React เรียก function เพื่อดูผลลัพธ์
- **Re-render** → เรียกซ้ำเพราะ state/props/context เปลี่ยน
- **Commit** → ขั้นที่แก้ DOM จริง
- **Virtual DOM** → พิมพ์เขียวในกระดาษ
- **DOM** → อาคารจริง
- **Reconciliation** → เทียบพิมพ์เขียวเก่า-ใหม่ แล้วทุบเฉพาะที่ต่าง
- **Key** → บัตรประชาชนของ item ห้ามใช้ index เมื่อมีการลบ/แทรก/เรียง
- **useState** → ความจำที่ปลุก React
- **useEffect** → สะพานไปโลกนอก + ต้องมีทางกลับ
- **useRef** → กล่องจำที่ไม่ปลุก React
- **useMemo** → จำผลคำนวณ (ใช้เมื่อวัดแล้วคุ้ม)
- **useCallback** → จำ function (ใช้คู่กับ React.memo หรือ deps)
- **useContext** → เสียงตามสายในตึก
- **Mount / Update / Unmount** → เข้าอยู่ / ปรับตัว / เก็บของออก
- **Controlled** → React ถือพวงมาลัย
- **Uncontrolled** → DOM ถือพวงมาลัย
- **Lifting State Up** → ยกความจำขึ้นไปหาพ่อแม่ร่วม
- **Prop Drilling** → ส่งพัสดุผ่านคนกลางที่ไม่ได้ใช้
- **Context** → ตู้ของกลางประจำตึก (ไม่มี selector)
- **Server State** → ข้อมูลที่เจ้าของจริงคือ server → ใช้ TanStack Query
- **React.memo** → ยามหน้าประตู component
- **Code Splitting** → แบ่งกระเป๋าเดินทาง
- **Lazy Loading** → โหลดตอนจะใช้
- **Virtualization** → วาดเฉพาะที่ตามองเห็น
- **Error Boundary** → เบรกเกอร์ไฟฟ้า (ไม่จับ event handler / async)
- **Strict Mode** → หมอตรวจสุขภาพตอน dev ที่เรียก effect ซ้ำเพื่อจับ cleanup ที่ขาด
