# PART 9 — JAVA FUNDAMENTALS

> ตำแหน่งในภาพใหญ่: Backend Layer — ภาษาที่ระบบองค์กรขนาดใหญ่ใช้เขียน business logic ฝั่ง server

## 1. Big Picture

ถ้าคุณมาจากสาย JavaScript แล้วต้องไปสัมภาษณ์งานที่ใช้ Java ให้เริ่มจากความจริงข้อแรกก่อน:

> **Java กับ JavaScript ไม่เกี่ยวข้องกันเลย** — เหมือน "ข้าวหอมมะลิ" กับ "ข้าวโพด" มีคำว่าข้าวเหมือนกันแต่คนละเรื่อง

ชื่อคล้ายกันเพราะเหตุผลทางการตลาดในยุค 90 เท่านั้น

**Java → ภาษา programming ที่ compile เป็น bytecode แล้วรันบน JVM → ใช้เขียนระบบ backend ขนาดใหญ่ที่ต้องอยู่ยาวและมีคนดูแลหลายคน**

### ทำไมองค์กรใหญ่ถึงเลือก Java

| เหตุผล | ความหมายจริงในงาน |
|---|---|
| **Static typing** | compiler จับ error ให้ตั้งแต่ก่อนรัน ไม่ใช่ตอน user กดใช้งาน |
| **เขียนครั้งเดียวรันได้ทุก OS** | JVM เป็นตัวกลาง — โค้ดเดิมรันได้ทั้ง Windows / Linux / Mac |
| **Ecosystem ใหญ่และเสถียร** | Spring Boot, library ระดับ enterprise, มี pattern มาตรฐาน |
| **อ่านโค้ดคนอื่นได้ง่าย** | โครงสร้างบังคับให้ชัดเจน คนใหม่เข้าโปรเจกต์ได้เร็ว |
| **Backward compatibility ดีมาก** | โค้ดอายุ 10 ปียัง compile ผ่าน — สำคัญมากกับระบบธนาคาร/ประกัน |

### สิ่งที่ต้องเข้าใจให้ได้ในบทนี้ (ไม่ต้องจำ syntax แม้แต่บรรทัดเดียว)

```
1) Java รันยังไง          → JDK / JVM / JRE / Compile / Bytecode
        ↓
2) Java คิดยังไง           → OOP + 4 Pillars + Class/Object
        ↓
3) Java จัดการหน่วยความจำยังไง → Stack / Heap / Garbage Collection
        ↓
4) Java ทำงานพร้อมกันยังไง   → Thread / Concurrency
        ↓
5) Java เก็บข้อมูลยังไง      → Collection: List / Set / Map
```

> **ให้มองภาพนี้ว่า** "เข้าใจ Java คือเข้าใจ 5 เรื่อง — มันรันยังไง คิดยังไง จำยังไง ทำงานพร้อมกันยังไง และเก็บของยังไง"

**หมายเหตุสำคัญ:** บทนี้ **ไม่มี syntax** เพราะ interviewer ระดับ Mid ไม่ได้ถามว่า `public static void main` เขียนยังไง เขาถามว่า "ทำไม Java ถึงต้องมี JVM" และ "Interface กับ Abstract Class ต่างกันตรงไหน คุณเลือกใช้อันไหนเมื่อไร"

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| Java | ภาษา + platform | ภาษาที่ compile เป็น bytecode รันบน JVM |
| JVM | เครื่องจำลองที่รัน Java | Java Virtual Machine — ตัวที่รัน bytecode จริง |
| JRE | ชุดสำหรับ "รัน" | JVM + library พื้นฐาน (ไม่มีเครื่องมือ compile) |
| JDK | ชุดสำหรับ "เขียน" | JRE + compiler + เครื่องมือ dev |
| Compile | แปลก่อนรัน | แปลง `.java` → `.class` (bytecode) |
| Bytecode | ภาษากลาง | ภาษาที่ JVM เข้าใจ ไม่ผูกกับ OS |
| JIT | แปลซ้ำตอนรันให้เร็วขึ้น | Just-In-Time compiler แปลง bytecode ที่ใช้บ่อยเป็น machine code |
| Static Typing | ประกาศชนิดตายตัว | ชนิดข้อมูลถูกตรวจตั้งแต่ตอน compile |
| OOP | คิดเป็นวัตถุ | Object-Oriented Programming |
| Class | พิมพ์เขียว | แม่แบบที่บอกว่า object มีอะไรและทำอะไรได้ |
| Object / Instance | ของจริงที่สร้างจากพิมพ์เขียว | สิ่งที่มีอยู่จริงใน memory |
| Encapsulation | ห่อไว้ อย่าให้แตะตรง ๆ | ซ่อนข้อมูลภายใน เปิดเฉพาะทางที่อนุญาต |
| Inheritance | สืบทอด | class ลูกรับคุณสมบัติจาก class แม่ |
| Polymorphism | หน้าตาเดียว หลายพฤติกรรม | เรียกแบบเดียวกันแต่ทำงานต่างกันตามชนิดจริง |
| Abstraction | ซ่อนรายละเอียด เหลือแต่สิ่งที่ต้องรู้ | บอกว่า "ทำอะไรได้" โดยไม่บอกว่า "ทำยังไง" |
| Interface | สัญญา | รายการความสามารถที่ class ต้องมี |
| Abstract Class | แม่แบบครึ่งสำเร็จ | มีทั้งส่วนที่ทำเสร็จแล้วและส่วนที่ลูกต้องเติม |
| Exception | เหตุผิดปกติที่โยนออกมา | กลไกจัดการ error |
| Checked Exception | compiler บังคับให้จัดการ | เช่น ปัญหาไฟล์ / network |
| Unchecked Exception | compiler ไม่บังคับ | เช่น null, index เกิน, หารศูนย์ |
| Garbage Collection (GC) | แม่บ้านเก็บของที่ไม่มีใครใช้ | คืน memory ของ object ที่ไม่มีใครอ้างถึงแล้ว |
| Stack | ที่วางงานที่กำลังทำ | เก็บ local variable + ลำดับการเรียก method |
| Heap | โกดังของจริง | เก็บ object ทั้งหมด |
| Thread | สายงาน 1 เส้น | หน่วยการทำงานที่รันขนานกันได้ |
| Concurrency | จัดการหลายงานคาบเกี่ยวกัน | ไม่จำเป็นต้องรันพร้อมกันจริง |
| Parallelism | รันพร้อมกันจริงบนหลาย core | ทำได้จริงเมื่อมี CPU หลาย core |
| Race Condition | แย่งกันแก้ตัวแปรเดียวกัน | ผลลัพธ์ขึ้นกับจังหวะ |
| Synchronized | ให้เข้าได้ทีละคน | กลไกกัน race condition |
| Thread Safe | ใช้หลาย thread แล้วไม่พัง | คุณสมบัติของ class/โค้ด |
| Collection | ชุดเก็บข้อมูล | List / Set / Map |
| List | เรียงลำดับ ซ้ำได้ | ตะกร้าที่จำลำดับ |
| Set | ห้ามซ้ำ | ชุดสมาชิกที่ไม่ซ้ำกัน |
| Map | คู่ key → value | สมุดโทรศัพท์ |
| Generics | ระบุชนิดที่บรรจุ | `List<String>` = list ที่มีแต่ String |
| Null | ไม่มีค่า | ต้นเหตุ error ที่พบบ่อยที่สุดใน Java |
| Package | โฟลเดอร์ของ class | จัดกลุ่มโค้ด |
| Maven / Gradle | ตัวจัดการ dependency + build | เทียบได้กับ npm |
| JAR | ไฟล์ผลลัพธ์ที่เอาไปรัน | โค้ดที่ package แล้ว |

## 3. Mental Model

### Mental Model ที่ 1: Java = "ภาษาที่ให้ compiler เป็นเพื่อนร่วมงานคนแรก"

ใน JavaScript เพื่อนร่วมงานคนแรกที่บอกว่าคุณเขียนผิดคือ **ผู้ใช้จริงใน production**
ใน Java เพื่อนร่วมงานคนแรกคือ **compiler ตอนที่คุณยังนั่งอยู่ที่โต๊ะ**

```
JavaScript:  เขียน → รัน → ผู้ใช้เจอ error → เรารู้
Java:        เขียน → compile ไม่ผ่าน → เรารู้ก่อนรันเลย
```

> **ให้มองภาพนี้ว่า** "Java แลกความเร็วในการเขียนไปกับความมั่นใจก่อนรัน — จึงคุ้มมากในระบบใหญ่ที่คนเยอะและอยู่ยาว แต่รู้สึกเยิ่นเย้อในสคริปต์เล็ก ๆ"

นี่คือ trade-off หลักของ Java และเป็นคำตอบของคำถาม "ทำไมธนาคารถึงใช้ Java"

### Mental Model ที่ 2: JVM = "ล่ามที่ทำให้โค้ดเดียวคุยกับทุก OS ได้"

```
[Java Code .java]
        ↓ compile (javac)
[Bytecode .class]        ← เหมือนกันทุกที่ ไม่ผูกกับ OS
        ↓
      [JVM]              ← มี JVM คนละตัวสำหรับแต่ละ OS
    ↙   ↓   ↘
Windows Linux macOS
```

> **ให้มองภาพนี้ว่า** "เราไม่ได้แปลภาษาให้ทุกประเทศเอง เราแปลเป็นภาษากลางครั้งเดียว แล้วให้ล่ามประจำแต่ละประเทศเป็นคนแปลต่อให้"

นี่คือที่มาของคำโฆษณาในตำนาน **"Write Once, Run Anywhere"**

### Mental Model ที่ 3: OOP = "จำลองสิ่งของและความรับผิดชอบ ไม่ใช่จำลองขั้นตอน"

Java บังคับให้คุณคิดแบบนี้:
- อย่าถามว่า "ขั้นตอนถัดไปคืออะไร"
- ให้ถามว่า **"ใครควรเป็นคนรับผิดชอบเรื่องนี้"**

```
❌ คิดแบบขั้นตอน:  คำนวณราคา → เช็คสต็อก → หักเงิน → ส่งอีเมล   (ทุกอย่างอยู่ใน 1 ก้อน)
✅ คิดแบบ OOP:     PriceCalculator / StockChecker / PaymentService / MailSender
                    แต่ละตัวรู้เรื่องของตัวเองอย่างเดียว
```

> **ให้มองภาพนี้ว่า** "OOP คือการแบ่งงานให้พนักงานหลายคนที่แต่ละคนรู้เรื่องของตัวเองลึก แทนที่จะมีคนเดียวที่ทำทุกอย่างและไม่มีใครกล้าแก้"

### Mental Model ที่ 4: Memory = "โต๊ะทำงาน (Stack) กับโกดัง (Heap)"

```
[STACK]  โต๊ะทำงาน — เล็ก เร็ว ส่วนตัวของแต่ละ thread
   ├── local variable
   ├── ลำดับการเรียก method
   └── "ที่อยู่" ของ object ใน heap

[HEAP]   โกดัง — ใหญ่ ช้ากว่า ใช้ร่วมกันทุก thread
   └── object จริงทั้งหมดอยู่ที่นี่  ← GC ทำงานที่นี่
```

> **ให้มองภาพนี้ว่า** "Stack คือโต๊ะที่วางกระดาษโน้ตว่า 'ของอยู่ชั้นไหนในโกดัง' ส่วนตัวของจริงอยู่ในโกดัง — object จึงถูกส่งต่อกันด้วยที่อยู่ ไม่ได้ถูกคัดลอกทั้งก้อน"

### ภาพจำ JDK / JRE / JVM (ต้องจำให้แม่น ข้อนี้ถูกถามบ่อยมากในระดับ Junior)

> **ให้มองภาพนี้ว่า** "JVM คือเครื่องยนต์ JRE คือรถที่ขับได้ JDK คือรถพร้อมอู่ซ่อม — นักพัฒนาต้องการ JDK ส่วนเครื่อง production ต้องการแค่ระดับ JRE ก็รันได้"

## 5. How It Works

### 5.1 จากโค้ดถึงการทำงานจริง

```
[Developer เขียน Hello.java]
          ↓  javac (compile)
[Hello.class = Bytecode]
          ↓  ส่งให้ JVM
[CLASS LOADER]        โหลด class เข้ามาใน memory
          ↓
[BYTECODE VERIFIER]   ตรวจว่า bytecode ปลอดภัย ไม่โกงกฎ
          ↓
[INTERPRETER]         เริ่มรันทีละคำสั่ง
          ↓
[JIT COMPILER]        โค้ดส่วนที่ถูกเรียกบ่อย → แปลเป็น machine code เก็บไว้
          ↓
[OS / CPU]
```

> **ให้มองภาพนี้ว่า** "Java เริ่มต้นช้าเพราะต้องแปลทีละคำสั่งก่อน แต่ยิ่งรันนาน JIT ยิ่งเรียนรู้ว่าส่วนไหนถูกใช้บ่อยแล้วแปลงเป็น machine code จนเร็วขึ้นเรื่อย ๆ"

ข้อนี้อธิบายพฤติกรรมจริงที่เจอในงาน: **Java แอปพลิเคชันมัก "อุ่นเครื่อง" (warm-up) ช้าตอนเพิ่ง deploy แล้วค่อย ๆ เร็วขึ้น** — เป็นเหตุผลที่ต้องตั้ง readiness probe และ warm-up traffic ให้ดี (ดู PART 14)

### 5.2 Static Typing ทำงานอย่างไร

```
[เขียนโค้ด]
    ↓
[COMPILER ตรวจชนิดข้อมูล]
    ↓
ชนิดผิด? ──ใช่──→ compile ไม่ผ่าน ❌  (เรารู้ตั้งแต่ตอนนี้)
    │
   ไม่
    ↓
[รันได้]
```

> **ให้มองภาพนี้ว่า** "Static typing คือด่านตรวจก่อนออกเดินทาง — ถ้าของไม่ตรงใบรายการ รถไม่ได้ออกจากอู่เลย ไม่ใช่ไปพังกลางทาง"

**ผลที่ตามมาในงานจริง:**

| ได้อะไร | เสียอะไร |
|---|---|
| refactor ปลอดภัย (เปลี่ยนชื่อ method แล้ว compiler ชี้ทุกจุดที่ต้องแก้) | เขียนโค้ดยาวกว่า ประกาศชนิดเยอะ |
| IDE autocomplete แม่นมาก | prototype เร็ว ๆ ไม่คล่องเท่าภาษา dynamic |
| bug ประเภท "ส่ง string ไปให้ฟังก์ชันที่ต้องการ number" หายไปเลย | ต้องเขียน boilerplate เพิ่ม |

### 5.3 Garbage Collection ทำงานอย่างไร

```
สร้าง object → อยู่ใน Heap
        ↓
ยังมีตัวแปรชี้ถึงอยู่ไหม?
        ↓
   ใช่ ──→ เก็บไว้
   ไม่ ──→ กลายเป็นขยะ
             ↓
         [GC เก็บกวาด]
             ↓
        คืน memory ให้ระบบ
```

> **ให้มองภาพนี้ว่า** "GC คือแม่บ้านที่เดินดูว่ากล่องไหนไม่มีใครถือเชือกโยงถึงแล้ว แล้วเก็บกล่องนั้นทิ้ง — เราจึงไม่ต้องคืน memory เอง แต่ก็ควบคุมเวลาที่มันมาเก็บไม่ได้"

**สิ่งที่ต้องรู้ระดับ Mid:**

| ประเด็น | สาระ |
|---|---|
| Java ไม่มี memory leak จริงไหม | **มี** — leak ใน Java คือ "ยังมีคนถืออ้างอิงอยู่ทั้งที่ไม่ใช้แล้ว" เช่น static collection ที่ใส่เข้าไม่เคยเอาออก |
| GC pause | ตอน GC ทำงานหนัก แอปอาจหยุดชั่วขณะ (stop-the-world) → latency spike |
| จูน GC ได้ไหม | ได้ (เลือก collector, ตั้งขนาด heap) แต่ควรแก้โค้ดที่สร้างขยะเยอะก่อน |
| อาการเมื่อ heap ไม่พอ | `OutOfMemoryError` + GC ทำงานถี่จน CPU พุ่งแต่งานไม่เดิน |

### 5.4 Thread ทำงานอย่างไร

```
[MAIN THREAD]
      ├──→ [THREAD 1]  จัดการ request A
      ├──→ [THREAD 2]  จัดการ request B
      └──→ [THREAD 3]  จัดการ request C

        ทุก thread ใช้ HEAP ร่วมกัน  ← จุดที่เกิด race condition
        แต่ละ thread มี STACK ของตัวเอง ← ส่วนตัว ปลอดภัย
```

> **ให้มองภาพนี้ว่า** "แต่ละ thread มีโต๊ะทำงานของตัวเอง แต่ใช้โกดังร่วมกัน — ปัญหาทั้งหมดของ concurrency เกิดที่โกดัง ไม่ได้เกิดที่โต๊ะ"

**นี่คือความต่างเชิงโครงสร้างที่สำคัญที่สุดระหว่าง Java กับ Node.js:**

```
Node.js:  1 thread หลัก + Event Loop        → ไม่มี shared-memory race condition โดยธรรมชาติ
Java:     หลาย thread ใช้ memory ร่วมกัน    → เร็วกว่าเมื่องานหนัก แต่ต้องกันเรื่อง thread safety เอง
```

**ปัญหาคลาสสิก: Race Condition ใน Java**

```
counter = 0
Thread A อ่าน counter = 0 ─┐
Thread B อ่าน counter = 0 ─┤ พร้อมกัน
Thread A เขียน counter = 1 ─┤
Thread B เขียน counter = 1 ─┘
ผลลัพธ์: 1  (ควรจะเป็น 2)
```

> **ให้มองภาพนี้ว่า** "การบวกหนึ่งไม่ใช่การกระทำเดียว แต่คืออ่าน–บวก–เขียน สามจังหวะ ซึ่งมีช่องให้อีก thread แทรกได้เสมอ"

**วิธีแก้ในภาษาคน (ไม่ต้องจำ syntax):**

| วิธี | ภาษาคน |
|---|---|
| `synchronized` | ให้เข้าไปทำทีละคนเท่านั้น |
| Atomic classes | ให้ CPU รับประกันว่า "อ่าน–บวก–เขียน" เป็นจังหวะเดียว |
| Immutable object | ถ้าไม่มีใครแก้ได้ ก็ไม่มีอะไรให้แย่ง |
| Concurrent Collections | ใช้โครงสร้างข้อมูลที่ออกแบบมาให้หลาย thread ใช้ได้ |
| ไม่แชร์ state เลย | ทางที่ปลอดภัยที่สุดเสมอ |

### 5.5 Exception ทำงานอย่างไร

```
[method C]  เกิดปัญหา → throw exception
      ↑
[method B]  ไม่ได้ catch → โยนต่อขึ้นไป
      ↑
[method A]  catch ได้ → จัดการ / แปลงเป็น error response
      ↑
ถ้าไม่มีใคร catch เลย → thread ตาย / โปรแกรมพัง
```

> **ให้มองภาพนี้ว่า** "Exception ลอยขึ้นตาม call stack เหมือนควันไฟที่ลอยขึ้นตามชั้นตึก จนกว่าจะเจอชั้นที่มีคนดับไฟได้ ถ้าไม่มีเลยก็ไหม้ทั้งตึก"

## 6. Example — 4 Pillars ด้วยงานจริง

**อย่าท่องนิยาม 4 Pillars** — interviewer ระดับ Mid ฟังออกทันทีว่าท่องมาหรือเข้าใจจริง
วิธีที่ทำให้เขาเชื่อคือ **อธิบายด้วยปัญหาที่ pillar นั้นแก้**

### 6.1 Encapsulation — "อย่าให้ใครแตะตัวแปรตรง ๆ"

**โจทย์จริง:** ระบบบัญชีธนาคาร มี `balance` เป็นตัวเลข

**ถ้าไม่มี encapsulation:** ใครก็ตั้งค่า `account.balance = -5000` ได้จากทุกที่ในโค้ด
พอยอดติดลบขึ้นมา คุณต้องไล่หาว่า **โค้ดตรงไหนใน 200 ไฟล์เป็นคนเซ็ต** — หาไม่เจอ

**ถ้ามี encapsulation:** `balance` เป็น private ใครจะเปลี่ยนต้องผ่าน `deposit()` / `withdraw()` เท่านั้น
และใน `withdraw()` มีเงื่อนไข "ถอนเกินยอดไม่ได้" อยู่ **ที่เดียว**

```
[โค้ดภายนอก]
      ↓  เรียกได้เฉพาะทางนี้
[deposit() / withdraw()]   ← กฎธุรกิจอยู่ตรงนี้ที่เดียว
      ↓
[private balance]          ← ไม่มีใครแตะตรง ๆ ได้
```

> **ให้มองภาพนี้ว่า** "Encapsulation คือการทำให้มีประตูเดียวเข้าห้องนิรภัย — ไม่ใช่เพื่อความลับ แต่เพื่อให้มียามอยู่จุดเดียวที่ต้องดูแล"

**ประโยคที่ควรพูดใน interview:** "Encapsulation ไม่ได้มีไว้ซ่อนข้อมูล แต่มีไว้ **รวมกฎการเปลี่ยนแปลงข้อมูลไว้ที่เดียว** เพื่อให้ข้อมูลอยู่ในสถานะที่ถูกต้องเสมอ"

### 6.2 Inheritance — "ของที่เหมือนกันเขียนครั้งเดียว"

**โจทย์จริง:** ระบบมี user 3 ประเภท — Customer, Admin, Vendor
ทั้ง 3 แบบมี `id`, `email`, `login()`, `changePassword()` เหมือนกันหมด แต่สิทธิ์ต่างกัน

```
            [User]              ← id, email, login(), changePassword()
           /   |   \
   [Customer][Admin][Vendor]    ← เพิ่มเฉพาะสิ่งที่ตัวเองมี
```

> **ให้มองภาพนี้ว่า** "Inheritance คือการบอกว่า 'ทั้งสามคนนี้เป็น User ที่ต่างกันแค่รายละเอียด' — แก้ logic login ที่แม่ที่เดียว ลูกทั้งสามได้ตาม"

⚠️ **คำเตือนที่ทำให้ดูเป็น Senior:** Inheritance ถูกใช้ผิดมากที่สุดใน 4 pillars
ใช้มันเมื่อความสัมพันธ์เป็น **"is-a" จริง ๆ** (Admin **เป็น** User)
ถ้าเป็น **"has-a"** ให้ใช้ **composition** แทน (Order **มี** PaymentMethod ไม่ใช่ Order **เป็น** PaymentMethod)

**ประโยคที่ควรพูด:** "ในงานจริงผมใช้ composition มากกว่า inheritance เพราะ inheritance ลึก ๆ ทำให้แก้ class แม่ทีเดียวแล้วพังทั้งสายโดยไม่รู้ตัว"

### 6.3 Polymorphism — "เรียกแบบเดียว ได้พฤติกรรมที่ถูกต้องเอง"

**โจทย์จริงที่ชัดที่สุด: ระบบชำระเงินที่รับ 3 ช่องทาง**

**ถ้าไม่มี polymorphism:**

```
ถ้า credit card    → ทำแบบ A
ไม่งั้นถ้า พร้อมเพย์ → ทำแบบ B
ไม่งั้นถ้า wallet   → ทำแบบ C
```

พอเพิ่มช่องทางที่ 4 คุณต้อง **ไปแก้ if-else ทุกที่ในระบบที่เคยเขียนแบบนี้** ซึ่งมักจะมีมากกว่า 1 จุด และมักจะลืมจุดใดจุดหนึ่ง

**ถ้ามี polymorphism:**

```
[PaymentService] ── เรียก ──→ pay()
                                ↓
                    ┌───────────┼───────────┐
             [CreditCard]  [PromptPay]  [Wallet]
              pay() ของตัว   pay() ของตัว  pay() ของตัว
```

> **ให้มองภาพนี้ว่า** "คนเรียกรู้แค่ว่า 'สิ่งนี้จ่ายเงินได้' โดยไม่ต้องรู้ว่าจ่ายด้วยวิธีไหน — เพิ่มช่องทางใหม่จึงไม่ต้องแก้โค้ดคนเรียกเลยแม้แต่บรรทัดเดียว"

**นี่คือหัวใจของ Open/Closed Principle** (เปิดให้เพิ่ม ปิดไม่ให้แก้ของเดิม — ดู PART 17)

**ประโยคที่ควรพูด:** "Polymorphism ทำให้ผมเพิ่ม feature ใหม่โดยไม่ต้องแตะโค้ดเก่า ซึ่งแปลว่าไม่มีความเสี่ยงที่จะทำของเดิมพัง"

### 6.4 Abstraction — "รู้ว่าใช้ยังไงพอ ไม่ต้องรู้ว่าข้างในทำอะไร"

**โจทย์จริง:** Service ต้องส่ง notification

```
[OrderService]
      ↓  รู้แค่ว่า "ส่งข้อความได้"
[Notifier (interface)]
      ↓
┌─────┼─────┐
Email  SMS  Push        ← ข้างในคนละเรื่องกันเลย
```

> **ให้มองภาพนี้ว่า** "Abstraction คือการที่คนขับรถรู้แค่ว่าเหยียบคันเร่งแล้วรถวิ่ง โดยไม่ต้องรู้เรื่องหัวฉีดน้ำมัน — เปลี่ยนเครื่องยนต์ได้โดยไม่ต้องสอนคนขับใหม่"

**คุณค่าจริงในงาน:** ตอนเขียน test คุณสลับ `Notifier` เป็นตัวปลอมได้ทันที ไม่ต้องส่งอีเมลจริงตอนรัน unit test (ดู PART 18)

**ความต่างจาก Encapsulation ที่สับสนบ่อย:**

| | ซ่อนอะไร | เพื่อใคร |
|---|---|---|
| **Encapsulation** | ซ่อน **ข้อมูล** ภายใน object | เพื่อปกป้องความถูกต้องของ state |
| **Abstraction** | ซ่อน **วิธีทำงาน** ที่ซับซ้อน | เพื่อให้คนเรียกใช้ง่ายและสลับ implementation ได้ |

### 6.5 Interface vs Abstract Class — ตัวอย่างที่ตัดสินใจจริง

**Interface = สัญญาจ้าง** — "ใครก็ได้ที่ทำ 3 อย่างนี้ได้ ถือว่าใช้ได้"
**Abstract Class = แม่แบบครึ่งสำเร็จ** — "ทุกคนในตระกูลนี้มีส่วนที่เหมือนกันอยู่แล้ว เหลือแค่เติมส่วนที่ต่าง"

**สถานการณ์จริงที่ใช้ Interface:**
ระบบ export รายงานเป็น PDF / Excel / CSV — สามตัวนี้ข้างในไม่มีอะไรเหมือนกันเลย แค่ต้อง `export()` ได้เหมือนกัน → **Interface**

**สถานการณ์จริงที่ใช้ Abstract Class:**
ระบบเชื่อมต่อธนาคาร 5 แห่ง ทุกแห่งมีขั้นตอนเหมือนกัน: เชื่อมต่อ → ยืนยันตัวตน → ส่งข้อมูล → ปิดการเชื่อมต่อ
มีแค่ขั้น "ส่งข้อมูล" ที่ต่างกันจริง → **Abstract Class** เขียน 3 ขั้นที่เหมือนกันไว้ให้เลย

```
[AbstractBankClient]
  connect()      ← เขียนเสร็จแล้ว ใช้ร่วมกัน
  authenticate() ← เขียนเสร็จแล้ว
  send()         ← abstract ลูกต้องเขียนเอง
  close()        ← เขียนเสร็จแล้ว
        ↓
[BankA] [BankB] [BankC]   ← เขียนแค่ send()
```

> **ให้มองภาพนี้ว่า** "Abstract class คือแบบฟอร์มที่กรอกไว้ให้ 3 ใน 4 ช่อง ส่วน interface คือใบสั่งงานที่บอกแค่ว่าต้องส่งอะไรบ้าง"

## 7. Compare

### 7.1 Java vs JavaScript — ชื่อคล้าย แต่คนละเรื่องโดยสิ้นเชิง

| ประเด็น | Java | JavaScript |
|---|---|---|
| **ความสัมพันธ์กัน** | **ไม่เกี่ยวกันเลย** ชื่อคล้ายเพราะการตลาดยุค 90 | เช่นเดียวกัน |
| ประเภทภาษา | Compiled → bytecode → รันบน JVM | Interpreted / JIT ใน runtime (browser, Node.js) |
| Typing | **Static** — ตรวจตอน compile | **Dynamic** — ตรวจตอนรัน |
| ต้องประกาศชนิดไหม | ต้อง | ไม่ต้อง |
| เจอ type error เมื่อไร | ตอน compile (ก่อน deploy) | ตอนรัน (บางทีคือตอน user ใช้) |
| Concurrency model | **Multi-thread** ใช้ memory ร่วมกัน | **Single-thread + Event Loop** |
| ปัญหาที่ต้องระวัง | Race condition, deadlock, thread safety | Blocking event loop, callback ซ้อน |
| Memory | Stack + Heap + **GC** | Heap + **GC** (จัดการให้เหมือนกัน) |
| OOP | class-based (มีมาแต่ต้น) | **prototype-based** (`class` เป็น syntax ที่ครอบ prototype) |
| ที่รันหลัก | Server / Android / Desktop | Browser / Server (Node.js) |
| Package manager | Maven / Gradle | npm / yarn / pnpm |
| เหมาะกับ | ระบบใหญ่ อยู่ยาว ทีมใหญ่ ต้องการ type safety | งาน UI, ระบบที่ I/O หนัก, พัฒนาเร็ว |
| ความเร็วในการเขียนครั้งแรก | ช้ากว่า (boilerplate เยอะ) | เร็วกว่า |
| ความปลอดภัยตอน refactor | สูงมาก (compiler ชี้ทุกจุด) | ต่ำกว่า (ต้องใช้ TypeScript ช่วย) |

**สิ่งที่ต้องพูดได้เป็นประโยคเดียว:**
> "Java กับ JavaScript ไม่ได้เกี่ยวข้องกันเลยครับ ต่างกันตั้งแต่ typing, concurrency model ไปจนถึงที่ที่มันรัน — เหมือนชื่อ 'ข้าว' ที่อยู่ในทั้งข้าวหอมมะลิและข้าวโพด"

**คำถามต่อที่ interviewer ชอบยิง:** "แล้ว TypeScript ล่ะ เหมือน Java ไหม"
**คำตอบที่ดี:** "ใกล้ขึ้นเรื่อง typing ครับ แต่ยังต่างกันตรงที่ type ของ TypeScript หายไปตอน runtime (compile ทิ้ง) ส่วน Java type ยังอยู่จริงตอนรันและ JVM ใช้มันจริง ๆ"

### 7.2 Java vs Python

| ประเด็น | Java | Python |
|---|---|---|
| Typing | Static — ประกาศชนิดตายตัว | Dynamic — ชนิดตัดสินตอนรัน (มี type hint แต่ไม่บังคับ) |
| การรัน | Compile → bytecode → JVM | Interpret ทีละบรรทัด (มี bytecode ภายในเช่นกัน) |
| ความยาวของโค้ด | ยาวกว่ามาก | สั้นและอ่านง่ายกว่า |
| ความเร็วในการพัฒนา | ช้ากว่าตอนเริ่ม | เร็วมากตอนเริ่ม |
| ความเร็วตอนรัน (CPU-bound) | เร็วกว่าโดยทั่วไป (JIT) | ช้ากว่า (แต่เรียก C library ได้) |
| Concurrency | Multi-thread จริง ใช้หลาย core ได้ | มี **GIL** ทำให้ thread ไม่ได้ใช้หลาย core พร้อมกันจริงสำหรับงาน CPU (ดู PART 11) |
| จุดแข็ง | ระบบ enterprise, ระบบใหญ่, Android | Data / AI / automation / script / API เล็กถึงกลาง |
| Framework backend | Spring Boot | Django / FastAPI / Flask |
| Package manager | Maven / Gradle | pip + virtual environment |
| ทีมใหญ่ 20 คน ดูแล 5 ปี | ได้เปรียบ (compiler บังคับสัญญา) | ต้องใช้วินัย + type hint + test ช่วยมาก |
| เหมาะเมื่อ | ต้องการความมั่นคง ระบบใหญ่ ทีมหลายคน อยู่ยาว | ต้องการความเร็วในการพัฒนา งาน data/AI ทีมเล็ก |

**ห้ามตอบว่า "Java ดีกว่า Python"** ให้ตอบว่า:
> "Java ได้เปรียบเมื่อระบบใหญ่ ทีมหลายคน และต้องดูแลยาว เพราะ compiler บังคับให้สัญญาระหว่างโมดูลชัดเจน ส่วน Python ได้เปรียบเมื่อต้องการความเร็วในการพัฒนาหรืองานสาย data ที่ ecosystem แข็งกว่ามาก"

### 7.3 Interface vs Abstract Class

| ประเด็น | Interface | Abstract Class |
|---|---|---|
| ความหมายเชิงแนวคิด | **"ทำอะไรได้"** (capability) | **"เป็นอะไร"** (identity / ตระกูล) |
| มี code ที่เขียนเสร็จแล้วไหม | มีได้บางส่วน (default method) แต่ไม่ใช่จุดประสงค์หลัก | **มีเป็นเรื่องปกติ** |
| เก็บ state (field) ได้ไหม | ไม่ได้ (มีได้แค่ค่าคงที่) | **ได้** |
| 1 class ใช้ได้กี่ตัว | **หลายตัว** | **ตัวเดียว** |
| ใช้เมื่อ | หลาย class ที่ไม่เกี่ยวข้องกัน ต้องทำสิ่งเดียวกันได้ | หลาย class ในตระกูลเดียวกัน มีโค้ดร่วมกันเยอะ |
| ตัวอย่าง | `Exportable`, `Comparable`, `Notifier` | `AbstractBankClient`, `AbstractRepository` |

**กฎตัดสินใจง่าย ๆ:** "มีโค้ดที่อยากแชร์ไหม" → มี = Abstract Class / ไม่มี = Interface
และในงานจริงสมัยใหม่ **ให้เริ่มจาก Interface ก่อนเสมอ** เพราะยืดหยุ่นกว่าและ test ง่ายกว่า

### 7.4 Checked vs Unchecked Exception

| ประเด็น | Checked Exception | Unchecked Exception |
|---|---|---|
| compiler บังคับจัดการไหม | **บังคับ** — ไม่ handle คือ compile ไม่ผ่าน | ไม่บังคับ |
| แทนอะไร | ปัญหาจาก**ภายนอก**ที่คาดเดาได้ | **bug ของโปรแกรมเมอร์** |
| ตัวอย่าง | อ่านไฟล์ไม่เจอ, network ขาด, DB ต่อไม่ได้ | null, index เกินขอบเขต, หารด้วยศูนย์, แปลง type ผิด |
| ท่าที่ถูกต้อง | จัดการหรือโยนต่ออย่างมีความหมาย | **แก้โค้ด** ไม่ใช่ไล่ catch |

🧠 **ภาพจำ:** "Checked = ฝนอาจตก ควรพกร่ม / Unchecked = คุณเดินชนเสาเอง ต้องแก้ที่การเดิน"

### 7.5 Collection — List vs Set vs Map

| | List | Set | Map |
|---|---|---|---|
| เก็บอะไร | ค่าเรียงกัน | ค่าที่ไม่ซ้ำ | คู่ key → value |
| มีลำดับไหม | **มี** | โดยทั่วไปไม่รับประกัน | ไม่รับประกัน (มีแบบที่เรียงให้) |
| ซ้ำได้ไหม | **ได้** | **ไม่ได้** | key ซ้ำไม่ได้ / value ซ้ำได้ |
| ใช้เมื่อ | ต้องการลำดับ เช่น รายการสินค้าในตะกร้า | ต้องการความไม่ซ้ำ เช่น รายการ tag, user id ที่เคยเห็น | ค้นหาด้วย key เช่น userId → User |
| หาของเร็วแค่ไหน | ช้ากว่า (ต้องไล่หา) | เร็ว (hash) | **เร็วที่สุดเมื่อรู้ key** |
| ภาพจำ | แถวคิว | รายชื่อสมาชิกชมรม | สมุดโทรศัพท์ |

**ตัวอย่างการเลือกในงานจริง:**

| โจทย์ | เลือก | เพราะ |
|---|---|---|
| รายการสินค้าในตะกร้า (ลำดับสำคัญ ใส่ซ้ำได้) | List | ต้องรักษาลำดับ |
| เช็คว่า user เคยกดไลก์โพสต์นี้หรือยัง | Set | สนใจแค่ "มีหรือไม่มี" และห้ามซ้ำ |
| แปลง userId เป็นชื่อ เพื่อแก้ N+1 (ดู PART 8) | Map | ค้นด้วย key ได้ทันที |
| นับจำนวนครั้งที่แต่ละคำปรากฏ | Map | คำ → จำนวน |

### 7.6 Stack vs Heap

| ประเด็น | Stack | Heap |
|---|---|---|
| เก็บอะไร | local variable, ลำดับการเรียก method, reference | **object ทั้งหมด** |
| ขนาด | เล็ก | ใหญ่ |
| ความเร็ว | เร็วมาก | ช้ากว่า |
| ใครใช้ | **แต่ละ thread มีของตัวเอง** | **ทุก thread ใช้ร่วมกัน** |
| คืนพื้นที่ยังไง | อัตโนมัติเมื่อจบ method | **GC** เป็นคนจัดการ |
| error ที่เกิด | `StackOverflowError` (recursion ไม่มีจุดจบ) | `OutOfMemoryError` (object เยอะเกิน / leak) |

🧠 **ภาพจำ:** "Stack = โต๊ะทำงานของคุณ (ส่วนตัว ล้างเองอัตโนมัติ) / Heap = โกดังกลางของบริษัท (ใช้ร่วมกัน มีแม่บ้านมาเก็บ)"

## 8. Common Mistakes

| # | สิ่งที่ Junior มักเข้าใจผิด | ความจริง |
|---|---|---|
| 1 | "Java กับ JavaScript คงเกี่ยวกันบ้าง" | **ไม่เกี่ยวกันเลย** — ต่างตั้งแต่ typing, concurrency ยัน runtime |
| 2 | "JDK JRE JVM ก็คืออันเดียวกัน" | JVM = เครื่องยนต์ / JRE = รถที่ขับได้ / JDK = รถ + อู่ (มี compiler) |
| 3 | "Java ไม่มี memory leak เพราะมี GC" | **มี** — leak คือยังถืออ้างอิงไว้ทั้งที่ไม่ใช้ เช่น static map ที่ใส่เข้าไม่เคยลบ |
| 4 | "GC มาเก็บทันทีที่เลิกใช้" | GC ทำงานเมื่อมันตัดสินใจเอง — เราคุมเวลาไม่ได้ และตอนมันทำงานหนักอาจเกิด pause |
| 5 | "Inheritance ยิ่งลึกยิ่งดี ใช้ซ้ำได้เยอะ" | inheritance ลึกทำให้แก้แม่ทีเดียวพังทั้งสาย — ใช้ composition แทนเมื่อไม่ใช่ "is-a" |
| 6 | "Interface กับ Abstract Class เหมือนกัน เลือกอันไหนก็ได้" | ต่างกันชัด: มีโค้ด/state ที่ต้องแชร์ไหม + 1 class ใช้ interface ได้หลายตัวแต่ extends ได้ตัวเดียว |
| 7 | "catch Exception ครอบทุกอย่างไว้ก่อน ปลอดภัยดี" | **กลบ bug** — error ที่ควรดังกลับเงียบ ทำให้ debug ยากขึ้นหลายเท่า |
| 8 | "Exception ใช้ควบคุม flow ปกติได้" | Exception แพงกว่า if มาก และทำให้อ่านโค้ดยาก — ใช้กับกรณีผิดปกติเท่านั้น |
| 9 | "เพิ่ม thread เยอะ ๆ แล้วระบบจะเร็วขึ้น" | thread กิน memory + context switch — เกินจำนวนที่เหมาะสมกลับช้าลง |
| 10 | "Java เป็น multi-thread เลยไม่มีปัญหา concurrency" | ตรงข้าม — เพราะ multi-thread จึงต้องกัน **race condition** ที่ Node.js ไม่เจอโดยธรรมชาติ |
| 11 | "`==` ใช้เทียบค่าได้ทุกกรณี" | `==` เทียบว่าเป็น object ตัวเดียวกันไหม การเทียบ "ค่าเท่ากัน" ต้องใช้ `equals` |
| 12 | "Static typing แปลว่าไม่มี runtime error" | ยังมี null, ข้อมูลจากภายนอกผิดรูป, DB ล่ม — static typing กันได้แค่ error เรื่องชนิดข้อมูล |
| 13 | "Java ช้าเพราะรันบน VM" | JIT ทำให้โค้ดที่รันบ่อยเร็วมาก — Java ช้าเฉพาะช่วง warm-up และช้าที่ startup time |
| 14 | "OOP คือการสร้าง class เยอะ ๆ" | OOP คือ **แบ่งความรับผิดชอบ** — class เยอะแต่แบ่งผิด แย่กว่า class น้อยที่แบ่งถูก |
| 15 | "Java ต้องเขียนยาว เลยเป็นภาษาที่ล้าสมัย" | โค้ดยาวคือราคาที่จ่ายเพื่อความชัดเจนและ refactor ที่ปลอดภัย — เป็น trade-off ไม่ใช่ข้อบกพร่อง |

## 9. Debugging

### 9.1 Framework: แอป Java มีปัญหา ไล่ตามนี้

```
1. อ่าน stack trace จากล่างขึ้นบน    → หา exception ต้นทางจริง ไม่ใช่ตัวที่ถูก wrap
        ↓
2. Exception ประเภทไหน               → NPE? OOM? StackOverflow? Timeout?
        ↓
3. เกิดที่ไหนในโค้ดของเรา            → มองหาบรรทัดแรกที่เป็น package ของเราเอง
        ↓
4. reproduce ได้ไหม                  → ทุกครั้ง = logic / บางครั้ง = concurrency หรือข้อมูล
        ↓
5. เกี่ยวกับ memory ไหม              → ดู heap usage + GC log + จำนวน object
        ↓
6. เกี่ยวกับ thread ไหม              → ดู thread dump: thread ค้างที่ไหน รออะไร
        ↓
7. เกี่ยวกับ dependency ภายนอกไหม     → DB / API / queue ช้าหรือล่ม
```

> **ให้มองภาพนี้ว่า** "Java บอกที่เกิดเหตุมาให้ครบใน stack trace อยู่แล้ว งานของเราคืออ่านมันให้เป็น ไม่ใช่เดาจากอาการ"

### 9.2 ตารางอาการ → สาเหตุ

| อาการ / Error | แปลว่า | เช็คอะไรก่อน |
|---|---|---|
| `NullPointerException` | เรียก method จากตัวแปรที่ไม่มีค่า | ค่านั้นมาจากไหน — DB ไม่เจอ? API คืน null? ลืม initialize? |
| `OutOfMemoryError: Java heap space` | object เยอะเกิน heap | ดึงข้อมูลมาทั้งตารางไหม / collection ที่โตไม่หยุด / heap เล็กเกิน |
| `StackOverflowError` | recursion ไม่มีจุดจบ | หา method ที่เรียกตัวเองแล้วไม่มีเงื่อนไขหยุด |
| `ClassCastException` | แปลง type ผิด | ตรวจ generic / การ cast ที่ไม่ปลอดภัย |
| `ConcurrentModificationException` | แก้ collection ระหว่างวนอ่านมัน | เก็บสิ่งที่จะลบไว้ก่อนแล้วค่อยลบทีหลัง |
| แอปค้างเป็นช่วง ๆ แล้วหายเอง | **GC pause** หรือ lock contention | ดู GC log / thread dump |
| ตัวเลขผิดเป็นบางครั้ง | **Race condition** | หา state ที่หลาย thread แชร์กันโดยไม่มี synchronization |
| ทุกอย่างค้างไม่มีอะไรขยับ | **Deadlock** | thread dump จะบอกตรง ๆ ว่ามี deadlock |
| ช้ามากช่วงหลัง deploy แล้วดีขึ้นเอง | JIT ยัง warm-up ไม่เสร็จ | ปกติ — ตั้ง readiness probe / warm-up ให้เหมาะ |
| memory ค่อย ๆ โตจนพังทุก 3 วัน | **Memory leak** (ถืออ้างอิงค้าง) | static collection, cache ที่ไม่มี eviction, listener ที่ไม่ถูก unregister |

### 9.3 วิธีอ่าน Stack Trace ให้ถูก

```
Exception A: ...                     ← ตัวนอกสุด (มักถูก wrap มา)
   at ServiceX.method()
   ...
Caused by: Exception B: ...          ← ★ อ่านตรงนี้ก่อน คือต้นเหตุจริง
   at RepositoryY.method()
```

**กฎ 3 ข้อ:**

1. หา `Caused by:` **ตัวล่างสุด** — นั่นคือต้นเหตุจริง
2. ไล่หาบรรทัดแรกที่เป็น **package ของเราเอง** ไม่ใช่ของ framework
3. Exception ที่ถูก wrap หลายชั้น ไม่ได้แปลว่าปัญหาซับซ้อน มักเป็นแค่ layer ที่ห่อต่อกันมา

### 9.4 เครื่องมือที่ควรรู้จัก

| เครื่องมือ | ใช้ดูอะไร |
|---|---|
| Stack trace / log | ต้นเหตุของ exception |
| Thread dump | ตอนนี้แต่ละ thread ทำอะไร / ค้างรออะไร / มี deadlock ไหม |
| Heap dump | object ไหนกิน memory มากที่สุด — ใช้หา leak |
| GC log | GC ทำงานถี่แค่ไหน pause นานแค่ไหน |
| Profiler (เช่น JFR / VisualVM) | CPU hotspot, allocation |
| Spring Boot Actuator | health, metrics, memory ของแอปจริง (ดู PART 10) |

## 11. Answer Like a Developer

### โครงการตอบ 4 จังหวะ

```
1. บอกว่ามันคืออะไรใน 1 ประโยค
        ↓
2. บอกว่ามันแก้ปัญหาอะไร (ทำไมถึงมีสิ่งนี้)
        ↓
3. ยกตัวอย่างจากงานจริง
        ↓
4. บอก trade-off / เมื่อไรไม่ควรใช้
```

> **ให้มองภาพนี้ว่า** "คนที่ท่องมาจะจบที่ข้อ 1 คนที่เข้าใจจริงจะไปถึงข้อ 4 เสมอ — ข้อ 4 คือสิ่งที่ interviewer ฟังอยู่"

### ตัวอย่าง: "Polymorphism คืออะไร"

**❌ แบบท่องจำ:** "Polymorphism คือการที่ object สามารถมีได้หลายรูปแบบครับ"
(interviewer จะรู้ทันทีว่าท่องมา เพราะประโยคนี้ไม่ได้อธิบายอะไรเลย)

**✅ แบบที่อยากได้:**
> "Polymorphism คือการที่เราเรียกเมธอดเดียวกัน แต่ได้พฤติกรรมต่างกันตามชนิดจริงของ object ครับ
> มันมีไว้แก้ปัญหา if-else ที่บวมขึ้นเรื่อย ๆ เวลาเรามีหลายกรณี
> ตัวอย่างที่ผมเจอคือระบบชำระเงินที่รับทั้งบัตรเครดิต พร้อมเพย์ และ wallet ถ้าเขียนแบบ if-else พอเพิ่มช่องทางที่สี่ต้องไล่แก้ทุกจุดที่เคยเช็ค ผมเลยทำเป็น interface `PaymentMethod` ที่มี `pay()` แล้วให้แต่ละช่องทางไป implement เอง คนเรียกไม่ต้องรู้ว่ามีกี่แบบ
> ข้อควรระวังคืออย่าใช้ polymorphism กับกรณีที่มีแค่สองแบบและจะไม่เพิ่มอีกแล้ว เพราะจะกลายเป็นโครงสร้างที่ซับซ้อนเกินความจำเป็นครับ"

### ตัวอย่าง: "Java กับ JavaScript ต่างกันยังไง"

> "ต่างกันหมดเลยครับ ไม่ได้เกี่ยวข้องกันเลย ชื่อคล้ายเพราะเหตุผลทางการตลาดสมัยก่อน
> สามข้อที่ต่างชัดที่สุดคือ หนึ่ง Java เป็น static typing ตรวจชนิดตั้งแต่ compile ส่วน JavaScript เป็น dynamic ตรวจตอนรัน
> สอง concurrency คนละแบบ — Java ใช้หลาย thread ที่แชร์ memory กัน เลยต้องระวัง race condition ส่วน JavaScript เป็น single thread + event loop เลยไม่มีปัญหานั้นโดยธรรมชาติ แต่ต้องระวังการ block event loop แทน
> สาม ระบบ OOP ต่างกัน Java เป็น class-based ตั้งแต่ต้น ส่วน JavaScript เป็น prototype-based แม้จะมีคำว่า class ในภาษาก็ตาม
> เวลาเลือกใช้ ผมมองจากขนาดทีมกับอายุของระบบเป็นหลักครับ"

## 12. One-Minute Review

- **Java ≠ JavaScript** — ต่างตั้งแต่ typing, concurrency model, ยัน runtime
- **JVM** รัน bytecode / **JRE** = JVM + library / **JDK** = JRE + compiler (เขียนโปรแกรมต้องใช้ JDK)
- **Compile → Bytecode → JVM → JIT** — Java จึง startup ช้าแต่เร็วขึ้นเมื่อรันไปเรื่อย ๆ
- **Static Typing** = compiler จับ error ก่อนรัน → refactor ปลอดภัย แลกกับโค้ดที่ยาวกว่า
- **Class** = พิมพ์เขียว / **Object** = ของจริงใน heap
- **4 Pillars:** Encapsulation = รวมกฎไว้ที่เดียว / Inheritance = ของเหมือนเขียนครั้งเดียว (ระวังใช้เกิน) / Polymorphism = เพิ่ม feature โดยไม่แก้โค้ดเดิม / Abstraction = ซ่อนวิธีทำ เหลือแต่สิ่งที่ต้องรู้
- **Interface** = "ทำอะไรได้" ใช้ได้หลายตัว / **Abstract Class** = "เป็นอะไร" แชร์โค้ดได้ แต่สืบทอดได้ตัวเดียว
- **Checked** = ปัญหาภายนอก compiler บังคับจัดการ / **Unchecked** = bug ของเราเอง ต้องแก้โค้ด
- **GC** เก็บ object ที่ไม่มีใครอ้างถึง — **Java มี memory leak ได้** ถ้ายังถืออ้างอิงค้างไว้
- **Stack** = ส่วนตัวของแต่ละ thread / **Heap** = ใช้ร่วมกันทุก thread → **race condition เกิดที่ heap**
- **Thread** หลายเส้นแชร์ memory → ต้องกัน race condition (ต่างจาก Node.js ที่ single-thread)
- **List** มีลำดับซ้ำได้ / **Set** ห้ามซ้ำ / **Map** ค้นด้วย key
- Debug: **อ่าน stack trace จาก `Caused by:` ตัวล่างสุด** → ดูประเภท exception → heap dump ถ้า memory → thread dump ถ้าค้าง

## 13. Memory Card

### จำ 5 อย่างนี้พอ

1. **Java ≠ JavaScript** — static typing + multi-thread + รันบน JVM คือ 3 จุดที่ต่างชัดที่สุด
2. **JDK = JRE + compiler, JRE = JVM + library, JVM = ตัวรัน bytecode**
3. **4 Pillars ตอบด้วยปัญหาที่มันแก้ ไม่ใช่นิยาม** — Encapsulation รวมกฎ / Inheritance ลดซ้ำ / Polymorphism เพิ่มโดยไม่แก้ของเดิม / Abstraction สลับ implementation ได้
4. **Stack ส่วนตัวของ thread / Heap แชร์กัน → ปัญหา concurrency ทั้งหมดอยู่ที่ heap**
5. **GC ไม่ได้แปลว่าไม่มี memory leak** — leak คือการถืออ้างอิงค้างโดยไม่ได้ใช้
