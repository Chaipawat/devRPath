## 1. Big Picture

คนส่วนใหญ่เรียนรู้ git แบบ "ท่องคำสั่ง"

```
git add .
git commit -m "fix"
git push
```

สามบรรทัดนี้พาไปได้ไกลจนถึงวันที่ conflict โผล่ วันที่ต้อง revert ของขึ้น production
หรือวันที่เผลอ `reset --hard` แล้วงานสองวันหายไป
วันนั้นคนที่ท่องคำสั่งจะตกใจ ส่วนคนที่เข้าใจ **โมเดล** จะรู้ว่าของไม่ได้หายไปไหน

**Git คืออะไรจริง ๆ:**

> Git คือระบบบันทึกประวัติของโปรเจกต์ ที่เก็บ "สภาพทั้งโปรเจกต์ ณ จุดเวลาหนึ่ง" ไว้เป็นก้อน ๆ แล้วร้อยก้อนเหล่านั้นให้รู้ว่าก้อนไหนมาก่อนก้อนไหน

พูดให้ HR ฟังรู้เรื่อง:

> "Git เหมือนปุ่ม Save ของเกม แต่ save ได้ไม่จำกัดช่อง จำได้ว่าใคร save ตอนไหนเพราะอะไร และเล่นแยกเส้นเรื่องพร้อมกันหลายเส้นแล้วค่อยเอามารวมกันได้"

### Git มีไว้ทำอะไรจริง ๆ (เรียงตามน้ำหนักจริงในงาน)

| เหตุผล | อธิบาย |
|---|---|
| 1. **ย้อนกลับได้** | ปล่อยของแล้วพัง → กลับไปสภาพที่ใช้ได้ภายในไม่กี่นาที นี่คือคุณค่าอันดับหนึ่ง |
| 2. **ทำงานขนานกันได้** | 5 คนแก้ไฟล์คนละที่พร้อมกัน แล้วรวมกันทีหลังโดยไม่ต้องส่งไฟล์ zip หากัน |
| 3. **ตอบคำถามว่า "ใครแก้บรรทัดนี้ ทำไม"** | ประวัติที่ดีคือเอกสารที่ไม่มีวันล้าสมัย |
| 4. **เป็นจุดเริ่มของ CI/CD** | ทุก pipeline เริ่มจากเหตุการณ์ใน git (push / merge / tag) |
| 5. **เป็นเวทีรีวิวโค้ด** | Pull Request คือที่ที่ความรู้ถูกส่งต่อระหว่างคนในทีม |

### Git ≠ GitHub

จุดนี้ถูกถามในสัมภาษณ์ระดับ junior บ่อยมาก

| | Git | GitHub / GitLab / Bitbucket |
|---|---|---|
| คืออะไร | โปรแกรมบนเครื่องเรา | บริการ host repository บนอินเทอร์เน็ต |
| ทำอะไร | สร้าง commit, branch, merge | เก็บสำเนากลาง + PR + review + CI + issue |
| ไม่มีเน็ตใช้ได้ไหม | ได้เกือบทุกอย่าง | ไม่ได้ |
| ใครเป็นเจ้าของ | open source | บริษัท |

> Git ทำงานแบบ **distributed** — ทุกคนมีประวัติทั้งหมดอยู่ในเครื่องตัวเอง server กลางเป็นแค่ "จุดนัดพบ" ที่ทุกคนตกลงกันว่าจะเชื่อถือ ไม่ใช่เจ้าของความจริงเพียงหนึ่งเดียว

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Repository (repo)** | กล่องเก็บประวัติ | โฟลเดอร์โปรเจกต์ + โฟลเดอร์ `.git` ที่เก็บประวัติทั้งหมด |
| **Working Directory** | โต๊ะทำงาน | ไฟล์จริงที่เราเห็นและแก้อยู่ตอนนี้ |
| **Staging Area (Index)** | ถาดเตรียมของ | ที่พักของการเปลี่ยนแปลงที่เลือกแล้วว่าจะใส่ commit ถัดไป |
| **Commit** | snapshot + พ่อ | ภาพรวมทั้งโปรเจกต์ ณ จุดหนึ่ง พร้อมตัวชี้ไป commit ก่อนหน้า |
| **Hash (SHA)** | เลขประจำ commit | รหัสที่คำนวณจากเนื้อหา — เปลี่ยนเนื้อหา = เปลี่ยนรหัส = คนละ commit |
| **HEAD** | "ตอนนี้เรายืนตรงไหน" | ตัวชี้ว่าเรากำลังอยู่ที่ branch/commit ไหน |
| **Branch** | ป้ายชี้ commit | ชื่อที่ชี้ไปยัง commit ล่าสุดของเส้นงานหนึ่ง (แค่ไฟล์ข้อความ 41 ไบต์) |
| **Remote / origin** | สำเนาปลายทาง | repo อีกชุดบนเซิร์ฟเวอร์ `origin` คือชื่อ default |
| **Clone / Fetch / Pull / Push** | ดึง–ส่ง | clone=ดึงทั้ง repo, fetch=ดึงประวัติมาดู, pull=fetch+รวม, push=ส่งขึ้น |
| **Merge** | รวมสองเส้น | สร้าง commit ใหม่ที่มีพ่อ 2 ตัว เพื่อรวมงานสองเส้นเข้าด้วยกัน |
| **Fast-forward** | เลื่อนป้ายเฉย ๆ | merge ที่ไม่ต้องสร้าง commit ใหม่เพราะไม่มีงานแยกจริง |
| **Rebase** | ย้ายฐาน | เขียน commit ของเราใหม่ให้ต่อท้ายงานล่าสุดของคนอื่น ประวัติเป็นเส้นตรง |
| **Conflict** | จุดที่ git ตัดสินแทนไม่ได้ | สองฝั่งแก้บรรทัดเดียวกันคนละแบบ ต้องให้คนเลือก |
| **Pull Request (PR / MR)** | คำขอรวมงาน + เวทีรีวิว | เสนอให้เอา branch เรารวมเข้า branch หลัก พร้อมให้คนรีวิว |
| **Revert** | ลบล้างด้วยของใหม่ | สร้าง commit ใหม่ที่ทำตรงข้ามกับ commit เก่า ประวัติเดิมยังอยู่ |
| **Reset** | ย้ายป้าย | เลื่อน branch/HEAD ไปชี้ commit อื่น (soft / mixed / hard) |
| **Cherry Pick** | หยิบเฉพาะลูก | ก็อป commit หนึ่งจากเส้นหนึ่งมาแปะอีกเส้น |
| **Tag** | หมุดเวอร์ชัน | ป้ายถาวรชี้ commit เช่น `v1.4.0` ใช้ทำ release |
| **Stash** | เก็บงานค้างเข้าลิ้นชัก | พักงานที่ยังไม่ commit ชั่วคราวเพื่อสลับไปทำอย่างอื่น |
| **Reflog** | กล้องวงจรปิดของ HEAD | บันทึกว่า HEAD เคยชี้ที่ไหนบ้าง — ไม้ตายตอนกู้ของหาย |
| **Squash** | ยุบหลาย commit เป็นหนึ่ง | ทำประวัติให้อ่านง่ายตอน merge เข้า main |
| **Force push** | ทับประวัติปลายทาง | อันตราย — เขียนทับสิ่งที่คนอื่นอาจดึงไปแล้ว |
| **Git Flow** | หลาย branch ยาว | รูปแบบการทำงานที่มี develop / release / hotfix แยกชัด |
| **Trunk Based** | branch สั้น เข้า main ไว | รูปแบบที่ทุกคน merge เข้า main วันละครั้ง ใช้ feature flag คุมของที่ยังไม่เสร็จ |

## 3. Mental Model

ถ้าจำได้แค่สามประโยคจากบทนี้ ขอให้เป็นสามประโยคนี้

### 3.1 Commit = Snapshot + Parent

commit **ไม่ใช่** "diff" หรือ "รายการบรรทัดที่เปลี่ยน" อย่างที่หลายคนเข้าใจ
commit คือ **ภาพถ่ายของทั้งโปรเจกต์ ณ ตอนนั้น** บวกข้อมูลอีก 4 อย่าง

```
COMMIT a1b2c3
├── snapshot  : สภาพไฟล์ทั้งหมดตอนนั้น
├── parent    : c9d8e7   ← ชี้ไป commit ก่อนหน้า
├── author    : ใคร เมื่อไร
└── message   : ทำไมถึงแก้
```

> **ให้มองภาพนี้ว่า** "commit คือรูปถ่ายทั้งห้องหนึ่งใบ ที่ด้านหลังเขียนไว้ว่ารูปก่อนหน้านี้คือใบไหน"

เมื่อทุก commit ชี้ไป parent ได้ ประวัติทั้งหมดก็กลายเป็น **กราฟ** ที่เดินย้อนกลับได้เสมอ
และเพราะ hash คำนวณจากเนื้อหา + parent → **แก้ประวัติเก่า = สร้าง commit ใหม่เสมอ ไม่มีการ "แก้ในที่เดิม"**
นี่คือเหตุผลว่าทำไม rebase/amend ถึงทำให้ hash เปลี่ยนทั้งชุด

### 3.2 Branch = ป้ายชี้ commit (ไม่ใช่โฟลเดอร์ ไม่ใช่สำเนา)

ประโยคเดียวที่เปลี่ยนความเข้าใจ git ของคนส่วนใหญ่:

> **branch ไม่ได้เก็บโค้ด branch เก็บแค่ "รหัส commit หนึ่งตัว"**

`main` คือไฟล์ข้อความไฟล์เดียวที่ข้างในมีคำว่า `a1b2c3` เท่านั้นจริง ๆ

```
commit:   C1 ──→ C2 ──→ C3 ──→ C4
                          ↑      ↑
                       [dev]   [main] ← HEAD
```

> **ให้มองภาพนี้ว่า** "branch คือสติกเกอร์ที่แปะบนรูปใบใดใบหนึ่งในอัลบั้ม ย้ายสติกเกอร์ไม่ได้ทำให้รูปหาย"

ผลที่ตามมาทั้งหมดอธิบายได้ด้วยประโยคเดียวนี้:

| สิ่งที่เกิดขึ้น | อธิบายด้วยโมเดล "ป้าย" |
|---|---|
| สร้าง branch เร็วมาก | แค่เขียนไฟล์เล็ก ๆ 1 ไฟล์ ไม่ได้ก็อปโค้ด |
| commit ใหม่ | สร้างรูปใหม่ แล้ว **ป้ายที่เรายืนอยู่เลื่อนตาม** |
| สลับ branch | ย้าย HEAD ไปอีกป้าย แล้วจัดไฟล์บนโต๊ะให้ตรงกับรูปนั้น |
| ลบ branch | ลอกสติกเกอร์ออก รูปยังอยู่ (จนกว่าจะไม่มีใครชี้ถึงแล้วจริง ๆ) |
| `reset` | **ย้ายป้าย** ไปชี้รูปอื่น |
| `merge` | สร้างรูปใหม่ที่มีพ่อสองคน |

### 3.3 ทุกคำสั่ง git ตอบได้ด้วย 2 คำถาม

```
คำสั่งนี้ (1) สร้าง commit ใหม่ไหม ?
          (2) ย้ายป้ายอันไหน ไปที่ไหน ?
```

| คำสั่ง | สร้าง commit ใหม่ | ย้ายป้าย |
|---|---|---|
| `commit` | ✅ 1 ตัว | ป้ายปัจจุบันเลื่อนตาม |
| `merge` | ✅ (ถ้าไม่ fast-forward) | ป้ายปัจจุบัน |
| `rebase` | ✅ ชุดใหม่ทั้งชุด (hash เปลี่ยน) | ป้ายปัจจุบัน |
| `revert` | ✅ 1 ตัว (ตรงข้ามของเก่า) | ป้ายปัจจุบันเลื่อนไปข้างหน้า |
| `reset` | ❌ | **ย้ายป้ายย้อนหลัง** |
| `cherry-pick` | ✅ (สำเนาของ commit อื่น) | ป้ายปัจจุบัน |
| `checkout` / `switch` | ❌ | ย้าย HEAD เฉย ๆ |

### 3.4 สามโซนของ Git

```
[WORKING DIRECTORY]   ไฟล์ที่เราแก้อยู่
        ↓  git add
[STAGING AREA]        ของที่เลือกว่าจะเข้า commit นี้
        ↓  git commit
[LOCAL REPOSITORY]    ประวัติในเครื่องเรา
        ↓  git push
[REMOTE REPOSITORY]   ประวัติบนเซิร์ฟเวอร์กลาง
```

> **ให้มองภาพนี้ว่า** "staging area คือถาดที่เราค่อย ๆ หยิบของใส่ก่อนแพ็กกล่อง เพื่อให้แต่ละกล่อง (commit) มีของเรื่องเดียวกัน ไม่ใช่กวาดทั้งโต๊ะลงกล่องเดียว"

## 4. ภาพจำ

```
🧠 ภาพจำที่ 1 — Commit = รูปถ่าย + โน้ตหลังรูป
ถ่ายรูปห้องทั้งห้อง แล้วเขียนหลังรูปว่า "ใบก่อนหน้าคือ #C3"
เรียงรูปย้อนกลับได้ตลอดเวลา

C1 ← C2 ← C3 ← C4
(ลูกศรชี้ "พ่อ" เสมอ)
```

```
🧠 ภาพจำที่ 2 — Branch = สติกเกอร์บนรูป
main, dev, feature/login = สติกเกอร์คนละสี
ย้ายสติกเกอร์ = เปลี่ยนว่า "เส้นนี้ล่าสุดอยู่รูปไหน"
รูปไม่หายไปไหนแม้ลอกสติกเกอร์ออก
```

```
🧠 ภาพจำที่ 3 — Merge vs Rebase = ประวัติศาสตร์ vs หนังสือเรียน
Merge  = บันทึกตามจริง "วันนั้นสองสายมารวมกัน"  (ประวัติจริง อ่านยากกว่า)
Rebase = เรียบเรียงใหม่ให้เป็นเส้นตรง          (อ่านง่าย แต่เป็นเรื่องที่เขียนใหม่)
```

```
🧠 ภาพจำที่ 4 — Revert vs Reset = สมุดบัญชี
Revert = ลงรายการใหม่ "คืนเงิน 500"      → ตรวจสอบย้อนหลังได้ ปลอดภัย
Reset  = ฉีกหน้าสมุดทิ้ง                  → สมุดสวยขึ้น แต่ถ้าคนอื่นถ่ายสำเนาไปแล้วจะงง
```

```
🧠 ภาพจำที่ 5 — Cherry Pick = ถ่ายเอกสารเฉพาะหน้า
ไม่ได้ยกแฟ้มทั้งแฟ้มมา เอามาแค่หน้าเดียวที่ต้องการ
ได้ "สำเนา" คนละใบกับต้นฉบับ (hash ใหม่) แม้เนื้อหาเหมือนกัน
```

```
🧠 ภาพจำที่ 6 — Conflict = พี่น้องสองคนแก้ประโยคเดียวกันในเรียงความ
git ไม่กล้าเลือกแทน เพราะมันไม่รู้ว่าอันไหน "ถูก" ในเชิงธุรกิจ
มันจึงวางทั้งสองเวอร์ชันไว้ตรงหน้า แล้วบอกว่า "คุณเลือก"
```

## 5. How It Works

### 5.1 ชีวิตของการเปลี่ยนแปลงหนึ่งอัน

```
[แก้ไฟล์]
    ↓
[git add]      → เข้า staging (เลือกเฉพาะเรื่องเดียวกัน)
    ↓
[git commit]   → สร้าง snapshot ใหม่ + ป้ายเลื่อนตาม
    ↓
[git push]     → ส่งขึ้น remote
    ↓
[Pull Request] → ทีมรีวิว + CI รันเทสต์
    ↓
[Merge]        → เข้า main
    ↓
[CI/CD Deploy] → ขึ้น production
```

> **ให้มองภาพนี้ว่า** "git คือสายพานที่พาความคิดหนึ่งอันจากหัวเรา เดินผ่านด่านตรวจทีละด่าน จนถึงมือผู้ใช้จริง"

### 5.2 Branch เกิดและโตอย่างไร

```
ตอนแตก branch:
C1 ── C2 ── C3          ← [main] [feature]  (ทั้งคู่ชี้ C3)

หลัง commit บน feature 2 ครั้ง:
C1 ── C2 ── C3 ──────── [main]
              \
               C4 ── C5 ← [feature]

ระหว่างนั้นคนอื่น merge เข้า main:
C1 ── C2 ── C3 ── C6 ── [main]
              \
               C4 ── C5 ← [feature]
```

> **ให้มองภาพนี้ว่า** "งานของเรากับงานของทีมเดินแยกกันจากจุดร่วมจุดหนึ่ง และยิ่งปล่อยให้ห่างกันนาน วันที่ต้องเอามารวมก็ยิ่งเจ็บ"

### 5.3 Merge — สร้าง commit ที่มีพ่อสองคน

```
ก่อน merge:
C3 ── C6 ← [main]
  \
   C4 ── C5 ← [feature]

หลัง git merge feature (บน main):
C3 ── C6 ─────── M ← [main]
  \             /
   C4 ── C5 ───
   (M มี parent = C6 และ C5)
```

> **ให้มองภาพนี้ว่า** "merge คือการบันทึกความจริงว่า ณ จุดนี้งานสองสายที่เคยแยกกันได้มาบรรจบกัน"

**Fast-forward** คือกรณีพิเศษ: ถ้า main ไม่มี commit ใหม่เลยตั้งแต่เราแตก branch git ไม่ต้องสร้าง M
แค่ **เลื่อนป้าย main ไปข้างหน้า** เท่านั้น

```
C3 ── C4 ── C5
 ↑            ↑
[main]  →  [main]   (เลื่อนป้ายเฉย ๆ ไม่มี commit ใหม่)
```

> **ให้มองภาพนี้ว่า** "fast-forward คือการเลื่อนสติกเกอร์ตามไปเฉย ๆ เพราะไม่มีเส้นทางไหนแยกไปจริง"

### 5.4 Rebase — ยกงานเราไปต่อท้ายของใหม่

```
ก่อน rebase:
C3 ── C6 ← [main]
  \
   C4 ── C5 ← [feature]

หลัง git rebase main (ยืนบน feature):
C3 ── C6 ── C4' ── C5' ← [feature]
            ↑ hash ใหม่ (เนื้อหาเดิม แต่เป็นคนละ commit)
```

> **ให้มองภาพนี้ว่า** "rebase คือการถอดงานเราออกมา แล้วเอาไปวางต่อท้ายงานล่าสุดของทีม เหมือนเล่าเรื่องใหม่ว่าเราเริ่มทำหลังเขาเสร็จ"

**กฎเหล็กของ rebase:**

> อย่า rebase branch ที่คนอื่นดึงไปใช้แล้ว เพราะ hash เปลี่ยนทั้งชุด ประวัติของเขาจะไม่ตรงกับของเรา แล้วต้องแก้กันทั้งทีม
> rebase ใช้กับ **branch ส่วนตัวของเรา** เพื่อจัดบ้านก่อนเปิด PR — นี่คือการใช้งานที่ปลอดภัยที่สุด

### 5.5 Conflict เกิดตอนไหน

```
[main]     บรรทัด 10:  const TAX = 0.07
[feature]  บรรทัด 10:  const TAX = 0.10
                ↓ merge
git: "สองฝั่งแก้บรรทัดเดียวกัน ฉันเลือกแทนไม่ได้"
                ↓
<<<<<<< HEAD          ← ฝั่งที่เรายืนอยู่
const TAX = 0.07
=======
const TAX = 0.10
>>>>>>> feature       ← ฝั่งที่กำลังเอาเข้ามา
```

> **ให้มองภาพนี้ว่า** "conflict ไม่ใช่ error แต่คือคำถามที่ git ถามเราว่า 'ธุรกิจต้องการอันไหน' เพราะมันรู้แค่ตัวอักษร ไม่รู้เจตนา"

**ลำดับการแก้ conflict ที่ถูกต้อง:**

```
1. อ่านทั้งสองฝั่งให้เข้าใจ "เจตนา" ของแต่ละฝั่งก่อน
2. ถ้าไม่แน่ใจว่าอีกฝั่งตั้งใจอะไร → ไปถามเจ้าของโค้ด (อย่าเดา)
3. เขียนผลลัพธ์ที่ถูกต้อง (บางครั้งไม่ใช่ทั้งสองฝั่ง แต่เป็นอันที่สาม)
4. ลบเครื่องหมาย <<<< ==== >>>> ให้หมด
5. รันเทสต์ + รันแอปจริง ก่อน commit
```

### 5.6 Pull Request flow

```
[feature branch] ── push ──→ [remote]
                                ↓
                          [Pull Request]
                                ↓
                ┌───────────────┴───────────────┐
           [CI: build/lint/test]        [Human Review]
                └───────────────┬───────────────┘
                                ↓
                        ผ่านทั้งคู่ → Merge
                                ↓
                         [main] → deploy
```

> **ให้มองภาพนี้ว่า** "PR คือด่านที่มีทั้งเครื่องตรวจ (CI) และคนตรวจ (reviewer) — เครื่องจับสิ่งที่วัดได้ คนจับสิ่งที่วัดไม่ได้ เช่น ชื่อฟังก์ชันสื่อความหรือเปล่า"

### 5.7 Git Flow vs Trunk Based (แนวคิด)

```
GIT FLOW:
main ────────●──────────────●────   (เฉพาะ release)
develop ──●──┼──●──●────────┼───
feature ──┘  │     └──┘     │
hotfix ──────┴──────────────┘

TRUNK BASED:
main ──●──●──●──●──●──●──●──●──   (merge ทุกวัน)
        \_/ \_/ \_/           branch อายุไม่กี่ชั่วโมง–1 วัน
        ของที่ยังไม่เสร็จ → ซ่อนด้วย feature flag
```

> **ให้มองภาพนี้ว่า** "Git Flow เหมาะกับของที่ปล่อยเป็นรอบและต้องดูแลหลายเวอร์ชันพร้อมกัน ส่วน Trunk Based เหมาะกับทีมที่ปล่อยของบ่อยและมี CI/CD กับเทสต์อัตโนมัติแข็งแรงพอ"

## 6. Example

### 6.1 Scenario A — ทีม 4 คนทำฟีเจอร์ checkout

สถานการณ์: ทีมมี main เป็น branch หลัก ทุกคนทำ branch ของตัวเอง

```
วันจันทร์  : แตก feature/checkout-coupon จาก main
วันอังคาร  : commit 3 ครั้ง (แยกเรื่อง: validate → คำนวณ → UI)
วันพุธเช้า : เพื่อน merge งาน refactor ของ cart เข้า main
วันพุธบ่าย : เรา rebase main เข้ามา → เจอ conflict ที่ cartService
วันพุธเย็น : แก้ conflict, รันเทสต์, push, เปิด PR
วันพฤหัส  : reviewer ขอแก้ 2 จุด → commit เพิ่ม → CI เขียว → squash merge
```

บทเรียนจริงจาก flow นี้:

| ทำอะไร | ทำไมสำคัญ |
|---|---|
| แยก commit ตามเรื่อง | เวลาต้อง revert จะได้ revert เฉพาะส่วนที่พัง ไม่ใช่ทั้งก้อน |
| ดึง main เข้ามาทุกวัน | conflict เล็ก 5 อันแก้ง่ายกว่า conflict ใหญ่ 1 อันตอนวันสุดท้าย |
| branch อายุสั้น | branch อายุ 3 สัปดาห์ = วันรวมกลายเป็นวันสยองขวัญ |
| squash ตอน merge | ประวัติบน main อ่านรู้เรื่อง 1 บรรทัด = 1 ฟีเจอร์ |

### 6.2 Scenario B — Commit message ที่ใช้งานได้จริง

```
❌ fix
❌ update code
❌ แก้ตามที่พี่บอก

✅ fix(checkout): cap coupon discount at 200 THB

   ก่อนหน้านี้คูปอง 10% ไม่มีเพดาน ทำให้ออเดอร์ 50,000 ลด 5,000
   แก้ให้เพดานอยู่ที่ 200 ตาม business rule ใหม่
   Ref: BUG-1421
```

> โครงที่จำง่าย: **บรรทัดแรก = ทำอะไร (สั้น) / ย่อหน้าถัดมา = ทำไม** — "ทำอะไร" อ่านจาก diff ได้อยู่แล้ว แต่ "ทำไม" อยู่ในหัวเราคนเดียว

### 6.3 🔴 Scenario บังคับ — "push bug ขึ้น production แล้วทำยังไง"

นี่คือคำถามที่แยก junior ออกจาก mid/senior ได้เร็วที่สุด
คนที่ตอบว่า "ก็ `git revert` ครับ" ตอบไม่ผิด แต่ตอบไม่ครบ
เพราะคำถามนี้ไม่ได้ถามคำสั่ง **แต่ถามลำดับความคิดตอนมีคนกำลังเดือดร้อนอยู่**

**หลักการเดียวที่ต้องจำ: หยุดเลือดก่อน แล้วค่อยหาสาเหตุ**

```
[รู้ว่ามีบั๊กบน production]
        ↓
1. STOP THE BLEEDING — ทำให้ผู้ใช้กลับมาใช้งานได้ก่อน
        ↓
2. สื่อสาร — บอกทีม/ผู้เกี่ยวข้องว่ากำลังจัดการอยู่
        ↓
3. หาสาเหตุ — commit ไหน / เปลี่ยนอะไร
        ↓
4. HOTFIX — แก้ให้ถูกที่ต้นเหตุ
        ↓
5. REGRESSION TEST — เขียนเทสต์ที่ fail ซ้ำอาการก่อน แล้วค่อยแก้ให้เขียว
        ↓
6. POSTMORTEM — ทำไมมันหลุดด่านทั้งหมดมาได้
```

> **ให้มองภาพนี้ว่า** "เจอบั๊กบน production เหมือนคนเลือดออก — หมอไม่เริ่มด้วยการหาสาเหตุว่าเขาล้มเพราะอะไร แต่ห้ามเลือดก่อนเสมอ"

#### ขั้นที่ 1 — หยุดเลือด (เลือกทางที่เร็วและเสี่ยงต่ำที่สุด)

เรียงตามลำดับที่ควรพิจารณา:

| ทางเลือก | เมื่อไรถึงใช้ | ข้อควรระวัง |
|---|---|---|
| **ปิดด้วย Feature Flag** | ถ้าฟีเจอร์นั้นมี flag อยู่แล้ว | เร็วที่สุด ไม่ต้อง deploy ใหม่ — นี่คือเหตุผลที่ flag มีค่ามาก |
| **Rollback deployment** | ระบบ deploy รองรับการกลับ version ก่อนหน้า | เร็ว แต่ย้อนทุกอย่างในรอบนั้น ไม่ใช่เฉพาะบั๊ก |
| **Revert commit แล้ว deploy ใหม่** | rollback ไม่มี หรือรอบ deploy มีของดี ๆ ปนอยู่ | ต้องรอ pipeline รอบใหม่ |
| **Fix forward (แก้แล้วปล่อยทับ)** | บั๊กเล็ก เข้าใจสาเหตุแน่ชัด แก้ได้ใน 10 นาที | เสี่ยงถ้าเข้าใจผิด เพราะกำลังเดาใต้แรงกดดัน |

**ทำไมใช้ `revert` ไม่ใช่ `reset` ในสถานการณ์นี้:**

> main เป็น branch สาธารณะ ทุกคนดึงไปแล้ว การ `reset` + force push จะไปเขียนทับประวัติที่คนอื่นถืออยู่
> ส่วน `revert` แค่ **เพิ่ม** commit ใหม่ที่ทำตรงข้าม → ทุกคน pull ตามได้ปกติ และยังเห็นร่องรอยว่าเคยเกิดอะไรขึ้น

```
ก่อน:  C10 ── C11(bug) ── C12 ← [main]
revert: C10 ── C11 ── C12 ── C13(ยกเลิกผลของ C11) ← [main]
```

> **ให้มองภาพนี้ว่า** "revert คือลงบันทึกในสมุดบัญชีว่า 'คืนเงินรายการที่ 11' ไม่ใช่ฉีกหน้าที่ 11 ทิ้ง"

#### ขั้นที่ 2 — สื่อสาร

สั้น ๆ แต่ต้องมี: **อาการที่ผู้ใช้เจอ / กระทบใครบ้าง / ตอนนี้กำลังทำอะไร / จะอัปเดตอีกเมื่อไร**
เงียบแล้วซ่อมเงียบ ๆ คือสิ่งที่ทำให้ทีมอื่นตัดสินใจผิดตามไปด้วย

#### ขั้นที่ 3 — หาสาเหตุ

```
[อาการ] → [เริ่มตั้งแต่เวลาไหน] → [รอบ deploy ไหนคร่อมเวลานั้น]
                                          ↓
                             [commit ในรอบนั้นมีอะไรบ้าง]
                                          ↓
                    ยังไม่ชัด → git bisect หา commit แรกที่พัง
                                          ↓
                            git blame ดูบรรทัดต้นเหตุ + เหตุผลใน PR
```

> **ให้มองภาพนี้ว่า** "การหาสาเหตุคือการบีบช่วงเวลาให้แคบลงเรื่อย ๆ จนเหลือ commit เดียวที่ต้องอ่าน ไม่ใช่การนั่งเดาทั้งระบบ"

#### ขั้นที่ 4–5 — Hotfix + Regression Test

```
1. แตก branch hotfix/xxx จาก main (หรือจาก tag ที่อยู่บน production)
2. เขียนเทสต์ที่ "fail ซ้ำอาการบั๊กนั้น" ให้ได้ก่อน   ← ห้ามข้าม
3. แก้โค้ดจนเทสต์เขียว
4. PR แบบ fast-track (ยังต้องมีคนรีวิว แม้จะรีบ)
5. deploy + ยืนยันบน production ด้วยตาจริง ไม่ใช่เชื่อ pipeline อย่างเดียว
6. merge กลับเข้า develop/branch อื่นที่เกี่ยวข้อง (ไม่งั้นบั๊กกลับมารอบหน้า)
```

ข้อ 2 คือหัวใจ: **ถ้ายังเขียนเทสต์ที่ reproduce อาการไม่ได้ แปลว่าเรายังไม่เข้าใจสาเหตุ**
การแก้โดยไม่มีเทสต์ที่ fail ก่อน = เดาแล้วหวังว่าอาการจะหาย

#### กรณีที่ **revert ไม่ได้** — ข้อที่ mid/senior ต้องพูดถึง

revert ใช้ได้เฉพาะกับสิ่งที่ "ย้อนได้ด้วยโค้ด" แต่ของบางอย่างออกจากระบบไปแล้วย้อนไม่ได้

| สถานการณ์ | ทำไม revert ไม่พอ | ต้องทำอะไรแทน |
|---|---|---|
| **Database migration รันไปแล้ว** (drop column / เปลี่ยน type) | revert โค้ดไม่ได้เอาคอลัมน์กลับมา และโค้ดเก่าจะวิ่งบน schema ใหม่ | เตรียม **down migration** หรือทำ migration แบบ backward compatible (expand → migrate → contract) |
| **ข้อมูลถูกเขียนผิดไปแล้ว** (คิดเงินผิด ส่งของผิด) | โค้ดหยุดพังแล้ว แต่ข้อมูลเสียยังอยู่ | เขียน **data fix script** แยก + ตรวจสอบยอดก่อน/หลัง |
| **ส่งอีเมล / push / webhook ออกไปแล้ว** | ดึงกลับไม่ได้ | สื่อสารแก้ไข + ส่งฉบับแก้ |
| **มีการจ่ายเงิน / เรียก API ภายนอกไปแล้ว** | ระบบภายนอกมี state ของตัวเอง | ทำ compensating action (refund / cancel) |
| **client เก่า cache ของพังไปแล้ว** | revert ฝั่ง server ไม่ได้ล้าง cache ที่เครื่องผู้ใช้ | bust cache / เปลี่ยน asset version |

**กฎที่ควรพูดในห้องสัมภาษณ์:**

> "ผมแยกสองอย่างเสมอ: **หยุดอาการ** กับ **ซ่อมข้อมูล** — revert แก้ได้แค่อาการ ส่วนข้อมูลที่เสียไปแล้วต้องมีแผนแยกและต้องตรวจนับก่อนหลังทุกครั้ง
> และถ้ารอบ deploy นั้นมี migration ที่ย้อนไม่ได้ ผมจะไม่ rollback มั่ว ๆ เพราะโค้ดเก่าอาจพังหนักกว่าเดิมบน schema ใหม่ — กรณีนั้นต้อง fix forward"

#### ขั้นที่ 6 — Postmortem (โทษระบบ ไม่โทษคน)

```
เกิดอะไรขึ้น → กระทบเท่าไร (คน/เงิน/เวลา) → ทำไมหลุดด่านมาได้ → ครั้งหน้าจะกันยังไง
```

คำถามที่ควรถามในทุก postmortem:

1. ทำไม **เทสต์** ไม่จับ → เคสนี้ควรมี regression test ตัวไหนเพิ่ม
2. ทำไม **review** ไม่จับ → PR ใหญ่เกินไปหรือเปล่า
3. ทำไม **monitoring** ไม่แจ้งก่อนผู้ใช้ → ควรมี alert อะไรเพิ่ม
4. ทำไม **กว่าจะกลับคืน** ใช้เวลานาน → rollback ควรกดได้เร็วกว่านี้ไหม

### 6.4 🔴 Scenario บังคับ — "เผลอ push secret ขึ้น repo"

เช่น `.env` ที่มี database password หรือ API key หลุดเข้าไปใน commit

**สิ่งที่คนส่วนใหญ่ทำเป็นอย่างแรก (และผิดลำดับ):** รีบลบไฟล์ แล้ว commit ใหม่
ผิดเพราะ **การลบไฟล์ไม่ได้ลบประวัติ** — commit เก่ายังมี key อยู่ครบ และที่สำคัญกว่านั้นคือ **key อาจถูกคัดลอกไปแล้ว**

**ลำดับที่ถูกต้อง:**

```
1. หมุน secret ทันที (rotate/revoke)   ← อันดับหนึ่งเสมอ
        ↓
2. ตรวจว่ามีการใช้ key นั้นผิดปกติไหม (audit log)
        ↓
3. ลบออกจากประวัติ + force push (ประสานทั้งทีม)
        ↓
4. กันไม่ให้เกิดซ้ำ (.gitignore, secret scanning, pre-commit hook, secret manager)
```

> **ให้มองภาพนี้ว่า** "กุญแจบ้านหล่นกลางถนน สิ่งแรกที่ทำคือเปลี่ยนลูกบิด ไม่ใช่วิ่งไปเก็บกุญแจ เพราะเราไม่มีทางรู้ว่าใครถ่ายรูปไว้แล้วบ้าง"

เหตุผลที่ "หมุน secret" ต้องมาก่อนเสมอ:

| ข้อเท็จจริง | ผลที่ตามมา |
|---|---|
| repo public → bot กวาด key ภายในไม่กี่วินาที | ช้าไปแค่ 5 นาทีก็อาจสายแล้ว |
| repo private → ยังมีคนในทีม/CI log/สำเนาเครื่องคนอื่น | ขอบเขตคนที่เห็นกว้างกว่าที่คิด |
| ใครก็ตามที่ `clone` ไปแล้ว มีประวัติทั้งหมดในเครื่อง | ลบบน server ไม่ได้ลบในเครื่องเขา |
| fork / mirror / cache ของ hosting | บางจุดยังเข้าถึง commit เก่าได้แม้ลบแล้ว |

ส่วนขั้นตอนลบประวัติ (ใช้เครื่องมืออย่าง `git filter-repo` หรือ BFG) ให้มองว่าเป็น **การทำความสะอาด ไม่ใช่การกู้ความปลอดภัย** และมันจะเขียน hash ใหม่ทั้ง repo ทุกคนต้อง re-clone — จึงต้องนัดกันทั้งทีมก่อนทำ

## 7. Compare

### 7.1 Merge vs Rebase

| | Merge | Rebase |
|---|---|---|
| ทำอะไร | สร้าง commit ใหม่ที่มีพ่อ 2 ตัว | เขียน commit ของเราใหม่บนฐานใหม่ |
| ประวัติ | เป็นกราฟ เห็นความจริงว่าแยกแล้วมารวม | เป็นเส้นตรง อ่านง่าย |
| hash | ของเดิมไม่เปลี่ยน | เปลี่ยนทั้งชุด |
| ปลอดภัยกับ branch สาธารณะ | ✅ | ❌ (ถ้าคนอื่นดึงไปแล้ว) |
| conflict | แก้ครั้งเดียวตอน merge | อาจต้องแก้ทีละ commit |
| เหมาะเมื่อ | รวมงานเข้า main / branch ที่แชร์กัน | จัดบ้าน branch ตัวเองก่อนเปิด PR |

> ไม่มีอันไหน "ดีกว่า" ลอย ๆ — **merge ดีกว่าเมื่อ** ต้องการบันทึกความจริงและ branch ถูกแชร์แล้ว / **rebase ดีกว่าเมื่อ** เป็น branch ส่วนตัวและอยากให้ประวัติบน main อ่านง่าย

### 7.2 Revert vs Reset ← ถามบ่อยที่สุด

| | `git revert` | `git reset` |
|---|---|---|
| หลักการ | **สร้าง commit ใหม่** ที่ทำตรงข้ามกับของเก่า | **ย้ายป้าย** branch ไปชี้ commit อื่น |
| ประวัติเดิม | ยังอยู่ครบ (เห็นว่าเคยมีและถูกยกเลิก) | หายจากเส้น (ยังกู้ได้ด้วย reflog ชั่วคราว) |
| ใช้กับ branch สาธารณะ | ✅ ปลอดภัย ทุกคน pull ตามได้ปกติ | ❌ อันตราย ต้อง force push ทับของคนอื่น |
| ใช้กับ branch ส่วนตัวที่ยังไม่ push | ใช้ได้ แต่เกินจำเป็น | ✅ เหมาะมาก |
| เดินไปทางไหน | ไปข้างหน้า (เพิ่ม commit) | ถอยหลัง (ย้ายป้ายย้อน) |
| สถานการณ์ตัวอย่าง | ของขึ้น production แล้วพัง | commit message ผิด / เผลอ commit ไฟล์เกิน ตอนยังไม่ push |

ประโยคจำ:

> **"push ไปแล้ว → revert / ยังไม่ push → reset"**

### 7.3 Reset 3 โหมด

| โหมด | ย้ายป้าย | staging | ไฟล์บนโต๊ะ | ใช้ตอนไหน |
|---|---|---|---|---|
| `--soft` | ✅ | คงไว้ | คงไว้ | อยากรวม commit ใหม่ / แก้ message |
| `--mixed` (default) | ✅ | ล้าง | คงไว้ | อยาก add ใหม่ เลือกของใหม่ |
| `--hard` | ✅ | ล้าง | **ล้างด้วย** | อยากทิ้งทุกอย่างจริง ๆ — คำสั่งที่ทำงานหายบ่อยที่สุด |

> `--hard` ลบงานที่ยังไม่ commit ทิ้งถาวร (reflog ช่วยได้เฉพาะของที่ commit แล้ว) — ก่อนใช้ ถามตัวเองว่า "ของที่ยังไม่ commit ตอนนี้ ยอมเสียได้ไหม"

### 7.4 Fetch vs Pull

| | `fetch` | `pull` |
|---|---|---|
| ทำอะไร | ดึงประวัติจาก remote มาเก็บ | fetch + merge (หรือ rebase) เข้า branch เรา |
| เปลี่ยนไฟล์บนโต๊ะเรา | ❌ | ✅ |
| ความเสี่ยง | แทบไม่มี | อาจเกิด conflict ทันที |
| ใช้เมื่อ | อยากดูก่อนว่ามีอะไรใหม่ | พร้อมรวมงานเข้าแล้ว |

### 7.5 Cherry Pick vs Merge vs Rebase

| | Cherry Pick | Merge | Rebase |
|---|---|---|---|
| หยิบมาเท่าไร | เฉพาะ commit ที่เลือก | ทั้ง branch | ทั้ง branch (ย้ายฐาน) |
| ได้ commit ใหม่ | ✅ สำเนา hash ใหม่ | ✅ merge commit | ✅ ทั้งชุด |
| ใช้เมื่อ | เอา hotfix จาก main ไปใส่ release เก่า | รวมงานปกติ | จัดประวัติให้ตรง |
| ข้อเสีย | ประวัติซ้ำ (เนื้อหาเดียวกันสอง commit) ถ้าใช้พร่ำเพรื่อ | ประวัติรก | เขียนประวัติใหม่ |

### 7.6 Git Flow vs Trunk Based

| | Git Flow | Trunk Based |
|---|---|---|
| จำนวน branch ยาว | หลาย (main/develop/release) | เดียว (main) |
| อายุ feature branch | วัน–สัปดาห์ | ชั่วโมง–1 วัน |
| ความถี่ปล่อยของ | เป็นรอบ | ได้ตลอดเวลา |
| conflict | ใหญ่ เพราะแยกกันนาน | เล็ก เพราะรวมบ่อย |
| ต้องมีอะไรรองรับ | คนคุม release | CI/CD + เทสต์อัตโนมัติ + feature flag |
| เหมาะเมื่อ | ของที่ปล่อยเป็นเวอร์ชัน ดูแลหลายเวอร์ชันพร้อมกัน (เช่น mobile app, on-premise) | เว็บ/SaaS ที่ deploy ได้บ่อย |

> **Trunk Based ดีกว่าเมื่อ** ทีมมี automated test และ CI/CD ที่เชื่อถือได้ — **ถ้าไม่มี** แล้วรีบเข้า Trunk Based จะกลายเป็น "ทุกคนพัง main พร้อมกัน"

### 7.7 Merge Commit vs Squash vs Rebase Merge (ตอนกด PR)

| | Merge commit | Squash and merge | Rebase and merge |
|---|---|---|---|
| ประวัติบน main | เห็นทุก commit ย่อย + merge commit | 1 PR = 1 commit | ทุก commit ต่อเป็นเส้นตรง |
| revert ทั้งฟีเจอร์ | ทำได้ (revert merge commit) | ง่ายที่สุด | ต้อง revert หลายตัว |
| เหมาะเมื่อ | อยากเก็บรายละเอียดการทำงาน | อยากให้ main อ่านเป็นเรื่อง ๆ (นิยมที่สุด) | ทีมชอบเส้นตรงและ commit ย่อยมีคุณภาพจริง |

## 8. Common Mistakes

### 8.1 คิดว่า branch คือสำเนาโค้ด

ทำให้กลัวสร้าง branch กลัวลบ branch และไม่เข้าใจว่าทำไม `reset` ถึงเร็วมาก
**ความจริง:** branch = ป้ายชี้ commit หนึ่งตัว ลบป้ายไม่ได้ลบรูป

### 8.2 คิดว่า `revert` = ลบประวัติ

`revert` **เพิ่ม** commit ไม่ได้ลบอะไร — ถ้าอยากให้ประวัติหายจริงต้องเขียนประวัติใหม่ (ซึ่งอันตรายกับ branch สาธารณะ)
ผลคือหลายคนเลือก `reset --hard` + force push ทั้งที่ควรใช้ revert

### 8.3 `reset --hard` แล้วคิดว่างานหายถาวร

งานที่ **commit แล้ว** ยังอยู่ — `git reflog` เก็บร่องรอยว่า HEAD เคยชี้ที่ไหนบ้าง หา hash แล้วกลับไปได้

```
[reset --hard ผิด]
      ↓
git reflog        ← หาบรรทัดก่อนหน้าที่ยังถูกต้อง
      ↓
git reset --hard <hash เดิม>  หรือ  git branch กู้ <hash>
```

> **ให้มองภาพนี้ว่า** "reflog คือกล้องวงจรปิดที่บันทึกว่าเราเดินไปยืนตรงไหนมาบ้าง แม้ป้ายจะถูกย้ายไปแล้วก็ยังตามรอยกลับได้"

ข้อยกเว้นสำคัญ: งานที่ **ยังไม่เคย commit** (อยู่บนโต๊ะเฉย ๆ) — อันนั้นหายจริง

### 8.4 Rebase branch ที่แชร์แล้ว / force push ทับเพื่อน

อาการ: เพื่อน pull ไม่ได้ ประวัติแตกเป็นสองเส้น commit หายจากฝั่งใครคนหนึ่ง
ป้องกัน: rebase เฉพาะ branch ตัวเอง และถ้าจำเป็นต้อง force จริง ๆ ให้ใช้ `--force-with-lease` ซึ่งจะไม่ยอมทับถ้ามีคนอื่น push เข้ามาหลังจากที่เราดึงไป

### 8.5 Commit ก้อนเดียวมี 5 เรื่อง

`"fix bug + refactor + เปลี่ยนสี + อัป dependency"` — เวลาต้อง revert เฉพาะบั๊ก จะ revert ไม่ได้เพราะของดีติดไปด้วย
กฎ: **1 commit = 1 เหตุผล** ถ้าอธิบาย message ต้องใช้คำว่า "และ" หลายครั้ง แปลว่าควรแยก

### 8.6 Commit message ไร้ข้อมูล

`fix`, `update`, `wip`, `.` — 6 เดือนต่อมาไม่มีใครรู้ว่าทำไมแก้ รวมทั้งตัวเราเอง
เขียน "ทำไม" เสมอ เพราะ "ทำอะไร" อ่านจาก diff ได้อยู่แล้ว

### 8.7 แก้ conflict แบบเลือกฝั่งมั่ว

กด "accept ours/theirs" ให้จบ ๆ → โค้ดคอมไพล์ผ่านแต่ตรรกะธุรกิจหาย (เช่น เพื่อนเพิ่มเช็คสิทธิ์ไว้ เราลบทิ้งตอนแก้ conflict)
กฎ: หลังแก้ conflict **ต้องรันเทสต์และดูไฟล์ที่ conflict ทั้งไฟล์อีกรอบเสมอ**

### 8.8 ปล่อย branch อายุยาว

branch 3 สัปดาห์ = ตอนรวมมี conflict หลายสิบจุด และ reviewer ต้องอ่าน diff 3,000 บรรทัด (ซึ่งแปลว่าเขาจะกด approve โดยไม่อ่านจริง)
กฎ: ดึง main เข้ามาอย่างน้อยวันละครั้ง และซอย PR ให้เล็ก

### 8.9 เก็บ secret / ไฟล์ build ใน repo

`.env`, `node_modules`, ไฟล์ dump ฐานข้อมูล — ทำให้ repo บวมและเสี่ยงข้อมูลรั่ว
กฎ: `.gitignore` ตั้งแต่ commit แรก + เปิด secret scanning + เก็บ secret ไว้ใน secret manager ของ CI/CD

### 8.10 `git pull` โดยไม่รู้ว่ามันทำอะไร

`pull` = `fetch` + `merge` โดยอัตโนมัติ ทำให้มี merge commit งอกโดยไม่ตั้งใจ หรือเกิด conflict กลางคัน
คนที่เข้าใจจะ `fetch` ดูก่อน แล้วค่อยตัดสินใจว่าจะ merge หรือ rebase

### 8.11 ทำงานบน main โดยตรง

ทุก commit ไปโผล่บน main ทันที ไม่มีด่านรีวิว ไม่มี CI กันไว้
แม้ทีมเล็กก็ควรใช้ PR เพราะมันคือที่ที่ความรู้ถูกส่งต่อ ไม่ใช่แค่ด่านตรวจ

### 8.12 Detached HEAD แล้วตกใจ

เกิดจาก checkout ไปที่ commit โดยตรง (ไม่ได้ยืนบน branch) → commit ที่ทำตรงนั้นไม่มีป้ายชี้ พอสลับ branch ก็ "หาย"
วิธีแก้: ยังอยู่ตรงนั้นก็ `git branch <ชื่อ>` ปักป้ายไว้ก่อน ถ้าสลับไปแล้วก็ใช้ reflog หา hash กลับมา

## 9. Debugging

### 9.1 หลักทั่วไป — ก่อนพิมพ์คำสั่งใด ๆ ตอบ 3 คำถามนี้

```
1. ตอนนี้ฉันยืนอยู่ที่ไหน            → git status / git branch
2. ประวัติหน้าตาเป็นยังไง            → git log --oneline --graph --all
3. คำสั่งที่จะพิมพ์ ย้ายป้ายหรือสร้าง commit ?
```

> **ให้มองภาพนี้ว่า** "git ที่ดูเหมือนพังส่วนใหญ่แค่ 'เรายืนผิดที่' — ดูแผนที่ก่อนเดิน ปัญหาครึ่งหนึ่งหายไปเอง"

### 9.2 ตารางอาการ → สาเหตุ → ทางไล่

| อาการ | สาเหตุที่พบบ่อย | ไล่ยังไง |
|---|---|---|
| push ไม่ได้ (`non-fast-forward` / `rejected`) | remote มี commit ที่เราไม่มี | `fetch` แล้ว `rebase`/`merge` ก่อน แล้วค่อย push — **อย่ารีบ force** |
| "งานหายหลัง reset/checkout" | ป้ายถูกย้าย ไม่ใช่ของหาย | `git reflog` หา hash → กลับไป |
| ไฟล์ที่แก้หายหลังสลับ branch | ยังไม่ commit และถูก stash/ทับ | `git stash list` / reflog |
| conflict ซ้ำ ๆ ทุกครั้งที่ rebase | branch อายุยาวเกิน + แก้ไฟล์เดียวกับทีม | ซอยงาน, sync ถี่ขึ้น, คุยกันเรื่องเจ้าของไฟล์ |
| ไฟล์ที่ควรถูก ignore ยังขึ้นใน status | มันถูก track ไปแล้วก่อนใส่ .gitignore | ถอดออกจาก index แล้ว commit (ถ้าเป็น secret → ดู 6.4) |
| ประวัติกลายเป็นสองเส้นซ้ำกัน | มีคน rebase/force push branch ที่แชร์ | ตกลงกันในทีมว่าใครถือของจริง แล้วให้ที่เหลือ re-clone |
| "commit นี้มาจากไหน ใครใส่" | — | `git log -S"ข้อความ"` หา commit ที่เพิ่ม/ลบข้อความนั้น, `git blame` ดูรายบรรทัด |
| ไม่รู้ว่าบั๊กเริ่มพังที่ commit ไหน | — | `git bisect` แบ่งครึ่งหาทีละรอบ (log n ครั้ง) |
| CI เขียวบนเครื่องเรา แต่แดงบน CI | ไฟล์ที่ยังไม่ได้ commit / ยังไม่ push | `git status` ต้องสะอาด + เทียบว่า branch ตรงกับ remote |

### 9.3 ลำดับไล่บั๊กที่ "เพิ่งพังหลัง deploy"

```
[พังตั้งแต่เมื่อไร]
      ↓
[รอบ deploy ไหนคร่อมเวลานั้น]   ← ดู tag / release notes
      ↓
[commit ในรอบนั้นมีอะไร]        ← git log <tag เก่า>..<tag ใหม่> --oneline
      ↓
[ยังไม่ชัด → git bisect]        ← หา commit แรกที่พัง
      ↓
[git blame + อ่าน PR เดิม]      ← เข้าใจ "เจตนา" ก่อนแก้
      ↓
[เขียนเทสต์ให้ fail ซ้ำอาการ]   ← แล้วค่อยแก้
```

> **ให้มองภาพนี้ว่า** "การไล่บั๊กด้วย git คือการหดช่วงเวลาที่ต้องสงสัยลงครึ่งหนึ่งไปเรื่อย ๆ จนเหลือ commit เดียวที่ต้องอ่านจริง"

### 9.4 อ่านประวัติให้เป็น = ทักษะ debug ที่ถูกมองข้าม

| อยากรู้ | ใช้อะไร |
|---|---|
| ประวัติภาพรวมพร้อมเส้นแตก | `git log --oneline --graph --all` |
| ใครแก้บรรทัดนี้ | `git blame <file>` |
| commit ไหนที่ทำให้ข้อความนี้โผล่/หาย | `git log -S"keyword"` |
| ต่างกันตรงไหนระหว่างสอง branch | `git diff main..feature` |
| ระหว่างสอง release มีอะไรเข้า | `git log v1.2..v1.3 --oneline` |
| ฉันเคยยืนตรงไหนมาบ้าง | `git reflog` |

## 11. Answer Like a Developer

**โครงการตอบคำถาม git ที่ใช้ได้เกือบทุกข้อ:**

```
1. บอกโมเดลก่อน      → "commit คือ snapshot, branch คือป้าย"
2. ตอบคำถามตรง ๆ     → ต่างกันตรงไหน / ทำอะไร
3. บอกว่าใช้ตอนไหน    → พร้อมเงื่อนไข ไม่ใช่ "อันนี้ดีกว่า"
4. บอกความเสี่ยง      → อะไรพังได้ และป้องกันยังไง
5. ผูกกับงานจริง      → "ตอนทำ X ผมเจอ Y เลยเลือก Z"
```

### ตัวอย่าง: "Merge กับ Rebase ต่างกันยังไง"

❌ แบบท่องจำ: "merge รวม branch ส่วน rebase ย้ายฐาน"

✅ แบบเข้าใจ:

> "ทั้งคู่จบที่ผลลัพธ์เดียวกันคือโค้ดรวมกัน แต่ต่างกันที่ **ประวัติ**
> merge สร้าง commit ใหม่ที่มีพ่อสองตัว เก็บความจริงว่าเคยแยกแล้วมารวม ส่วน rebase เขียน commit ของเราใหม่ให้ต่อท้ายงานล่าสุด ประวัติเลยเป็นเส้นตรง
> ผมใช้ rebase กับ branch ส่วนตัวก่อนเปิด PR เพื่อให้ diff อ่านง่าย และใช้ merge ตอนเข้า main
> ข้อควรระวังคือ rebase เปลี่ยน hash ทั้งชุด เพราะฉะนั้นถ้ามีคนดึง branch นั้นไปแล้วผมจะไม่ rebase ครับ"

### ตัวอย่าง: "Revert กับ Reset ต่างกันยังไง"

✅

> "`revert` คือการ **เพิ่ม** commit ใหม่ที่ทำตรงข้ามกับ commit เดิม ประวัติเก่ายังอยู่ครบ
> `reset` คือการ **ย้ายป้าย** branch ไปชี้ commit อื่น ประวัติหลังจุดนั้นหลุดออกจากเส้น
> กฎที่ผมใช้ตัดสินคือดูว่ามันถูก push แล้วหรือยัง — push แล้วใช้ revert เพราะคนอื่นถือประวัติชุดนั้นอยู่ ถ้าไป reset แล้ว force push จะไปทับของเขา
> ส่วนยังไม่ push ผม reset ได้สบาย ๆ เช่นเผลอ commit ไฟล์ .env ติดไป ผม reset --soft แล้ว commit ใหม่ครับ"

### ตัวอย่าง: "Push bug ขึ้น production แล้วทำยังไง"

✅ (ตอบเป็นลำดับ ไม่ใช่ตอบเป็นคำสั่ง)

> "อย่างแรกผมไม่หาสาเหตุก่อนครับ ผมหยุดเลือดก่อน — ถ้าฟีเจอร์นั้นมี feature flag ผมปิด flag เพราะเร็วที่สุดและไม่ต้อง deploy ใหม่ ถ้าไม่มีก็ rollback deployment หรือ `git revert` commit นั้นแล้วปล่อยรอบใหม่
> ผมใช้ revert ไม่ใช่ reset เพราะ main เป็น branch สาธารณะ
> ระหว่างนั้นผมแจ้งทีมและฝั่งธุรกิจว่ากระทบใครและกำลังทำอะไรอยู่
> พอเลือดหยุดผมค่อยหาสาเหตุ ดูว่าพังตั้งแต่ deploy รอบไหน ถ้าไม่ชัดก็ใช้ bisect หา commit แรกที่พัง
> แล้วผมจะเขียนเทสต์ที่ fail ซ้ำอาการนั้นให้ได้ก่อนแก้ เพราะถ้า reproduce ไม่ได้แปลว่าผมยังไม่เข้าใจสาเหตุจริง
> ข้อที่ผมระวังมากคือถ้ารอบนั้นมี migration ที่ย้อนไม่ได้ หรือมีข้อมูลถูกเขียนผิดไปแล้ว การ revert โค้ดอย่างเดียวไม่พอ ต้องมี data fix แยกและตรวจยอดก่อน–หลัง
> สุดท้ายทำ postmortem ว่าทำไมเทสต์ รีวิว และ monitoring ไม่จับ แล้วเพิ่ม regression test กับ alert ครับ"

### ตัวอย่าง: "เผลอ push secret"

✅

> "อันดับแรกคือ **หมุน secret ทันที** ครับ ไม่ใช่ลบไฟล์
> เพราะลบไฟล์ไม่ได้ลบประวัติ และที่สำคัญกว่าคือใครก็ตามที่ clone หรือ bot ที่กวาด repo อาจได้ key ไปแล้ว — เราคุมได้แค่การทำให้ key เก่าใช้ไม่ได้
> จากนั้นตรวจ audit log ว่ามีการใช้ผิดปกติไหม แล้วค่อยล้างประวัติด้วยเครื่องมืออย่าง filter-repo ซึ่งต้องนัดทั้งทีมเพราะทุกคนต้อง re-clone
> สุดท้ายกันไม่ให้เกิดซ้ำด้วย .gitignore, secret scanning และย้าย secret ไปอยู่ใน secret manager ครับ"

## 12. One-Minute Review

- **Commit = snapshot ทั้งโปรเจกต์ + ตัวชี้ไป parent** ไม่ใช่ diff
- **Branch = ป้ายชี้ commit หนึ่งตัว** สร้าง/ลบถูกและเร็ว เพราะไม่ได้ก็อปโค้ด
- **HEAD = เรายืนอยู่ตรงไหน** — ปัญหา git ส่วนใหญ่คือยืนผิดที่
- ทุกคำสั่งตอบได้ด้วย: สร้าง commit ใหม่ไหม + ย้ายป้ายอันไหน
- **Merge** เก็บความจริง / **Rebase** เก็บความสวย — rebase เฉพาะ branch ตัวเอง
- **Revert = เพิ่ม commit ที่ยกเลิกของเก่า (ปลอดภัยกับ branch สาธารณะ)**
- **Reset = ย้ายป้าย (อันตรายถ้า push ไปแล้ว)** → กฎ: push แล้ว revert / ยังไม่ push reset
- `reset --hard` ไม่ได้ลบ commit ถาวร — `reflog` กู้ได้ แต่ของที่ยังไม่ commit หายจริง
- **Cherry pick** = ก็อปเฉพาะ commit เดียว ใช้กับ hotfix ข้าม branch
- **Conflict** ไม่ใช่ error แต่คือคำถามว่า "ธุรกิจต้องการอันไหน" — แก้แล้วต้องรันเทสต์เสมอ
- **Git Flow** เหมาะกับปล่อยเป็นรอบ / **Trunk Based** เหมาะกับ deploy บ่อยและมี CI+test แข็งแรง
- **Push bug ขึ้น prod:** หยุดเลือด → สื่อสาร → หาสาเหตุ → hotfix → regression test → postmortem
- **revert ไม่ได้ทุกกรณี:** migration ย้อนไม่ได้ / ข้อมูลเสียไปแล้ว / อีเมลส่งไปแล้ว → ต้อง fix forward + data fix
- **Secret หลุด:** หมุน secret ก่อนเสมอ แล้วค่อยลบประวัติ

## 13. Memory Card

**จำ 5 อย่าง**

1. **Commit = รูปถ่าย + ชื่อรูปก่อนหน้า** → ประวัติคือกราฟที่เดินย้อนได้เสมอ
2. **Branch = สติกเกอร์บนรูป** → ย้ายป้ายไม่ได้ทำให้รูปหาย (reflog ตามรอยได้)
3. **Revert = เพิ่มรายการคืนเงิน / Reset = ฉีกหน้าสมุด** → push แล้วใช้ revert เท่านั้น
4. **Merge เก็บความจริง / Rebase เก็บความสวย** → rebase เฉพาะของส่วนตัว
5. **Production พัง: หยุดเลือดก่อน หาสาเหตุทีหลัง** และแก้จบด้วยเทสต์ที่ fail ซ้ำอาการได้

**Keyword:**

- **Commit** → snapshot + parent + ใคร/เมื่อไร/ทำไม
- **Branch** → ป้ายชี้ commit ล่าสุดของเส้นงานหนึ่ง
- **HEAD** → ตอนนี้เรายืนอยู่ที่ไหน
- **Merge** → commit ใหม่ที่มีพ่อสองตัว (ปลอดภัยกับ branch สาธารณะ)
- **Rebase** → ย้ายฐาน เขียน commit ใหม่ hash เปลี่ยน
- **Conflict** → จุดที่ git ไม่กล้าตัดสินแทนเรา
- **Pull Request** → เวทีรีวิว + ด่าน CI ก่อนเข้า main
- **Revert** → ยกเลิกด้วยการเพิ่ม commit ใหม่
- **Reset** → ย้ายป้าย (soft เก็บของ / mixed ล้าง stage / hard ล้างหมด)
- **Cherry Pick** → ก็อป commit เดียวข้ามเส้น
- **Reflog** → กล้องวงจรปิดของ HEAD ใช้กู้ของ
- **Git Flow** → หลาย branch ยาว ปล่อยเป็นรอบ
- **Trunk Based** → branch สั้น merge ทุกวัน ต้องมี CI + feature flag
- **Hotfix** → สายด่วนซ่อม production ต้องจบด้วย regression test + merge กลับทุก branch
