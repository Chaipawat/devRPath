# PART 12 — REACT NATIVE

> ตำแหน่งในภาพใหญ่: Frontend Layer — แต่เป็น frontend ที่รันอยู่ในมือผู้ใช้จริง ไม่ได้อยู่ในเบราว์เซอร์

---

## 1. Big Picture

React Native คือการเอา **วิธีคิดแบบ React** (component, state, props, hooks) มาใช้สร้างแอปมือถือ โดยที่ **UI ที่ออกมาเป็นของจริงของระบบปฏิบัติการ** ไม่ใช่หน้าเว็บที่ยัดใส่กรอบ

ประโยคที่ต้องเข้าใจให้แม่นก่อนอย่างอื่น:

> **"Learn once, write anywhere" ไม่ใช่ "Write once, run anywhere"**

แปลว่า: ความรู้ React ใช้ต่อได้เกือบหมด แต่ **โค้ดไม่ได้เหมือนเว็บ** เพราะไม่มี DOM ไม่มี `<div>` ไม่มี CSS แบบเว็บ ไม่มี URL bar และที่สำคัญที่สุด — **ไม่มีการ deploy แล้วผู้ใช้ได้ทันที**

```
[ REACT ]         → เรนเดอร์ออกเป็น DOM (div, span) ในเบราว์เซอร์
[ REACT NATIVE ]  → เรนเดอร์ออกเป็น Native View (UIView ของ iOS / View ของ Android)
       ↑ ใช้ mental model เดียวกัน แต่ปลายทางคนละโลก
```

> **ให้มองภาพนี้ว่า** "React คือสมองที่บอกว่า UI ควรหน้าตาอย่างไร ส่วน React Native คือการเปลี่ยนปลายทางของสมองนั้นจากหน้าเว็บไปเป็นหน้าจอมือถือจริง ๆ"

**สิ่งที่ทำให้ mobile ต่างจาก web โดยพื้นฐาน 5 ข้อ** (เป็นแกนของบทนี้ทั้งบท):

| เรื่อง | Web | Mobile |
|---|---|---|
| การส่งของใหม่ให้ผู้ใช้ | deploy แล้วผู้ใช้เห็นทันทีตอน refresh | ต้องผ่าน review + ผู้ใช้กดอัปเดตเอง |
| สถานะแอป | เปิดอยู่ = ทำงาน | มี foreground / background / killed |
| สิทธิ์การเข้าถึง | มีน้อย | ต้องขอ permission แทบทุกความสามารถ |
| เครือข่าย | สมมติว่ามี net | ต้องคิดเรื่อง offline / net หลุดกลางทาง |
| อุปกรณ์ | จอใหญ่ ไฟบ้าน | จอเล็ก แบตจำกัด แรมจำกัด |

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **React Native (RN)** | React ที่ออกจอมือถือ | framework สร้างแอป iOS/Android ด้วย React |
| **Native App** | เขียนด้วยภาษาของแพลตฟอร์ม | Swift/Kotlin — เข้าถึงทุกอย่างได้เต็มที่ |
| **Cross-platform** | เขียนชุดเดียวใช้หลาย OS | RN / Flutter |
| **Native View / Native UI** | ชิ้นส่วน UI จริงของ OS | `UIView` (iOS), `View` (Android) |
| **DOM** | ต้นไม้ element ของเว็บ | **ไม่มีใน RN** |
| **JS Thread** | เส้นที่รันโค้ดเรา | รัน JavaScript ของแอป |
| **UI Thread (Main Thread)** | เส้นที่วาดจอ | ถ้าเส้นนี้ค้าง = แอปกระตุก |
| **Bridge** | สะพานส่งข้อความ | สถาปัตยกรรมเดิม: JS ↔ Native คุยกันแบบ async ผ่าน JSON |
| **New Architecture** | สะพานใหม่ที่เรียกตรงได้ | JSI / TurboModules / Fabric — ลดคอขวดของ Bridge |
| **JSI** | ให้ JS เรียก C++ ได้ตรง | JavaScript Interface — รากฐานของ New Architecture |
| **Fabric** | ระบบเรนเดอร์ใหม่ | renderer ที่ทำงานร่วมกับ JSI |
| **TurboModule** | Native Module รุ่นใหม่ | โหลดเมื่อใช้ (lazy) และเรียกแบบ sync ได้ |
| **Native Module** | ปลั๊กต่อความสามารถ OS | โค้ด native ที่เปิดให้ JS เรียกใช้ |
| **Navigation** | ระบบเปลี่ยนหน้า | Stack / Tab / Drawer / Modal |
| **Stack Navigator** | กองกระดาษวางซ้อน | เข้าหน้าใหม่ทับ แล้ว back ถอยกลับ |
| **Tab Navigator** | แถบล่างสลับโหมด | แต่ละ tab เก็บ state ของตัวเอง |
| **Modal** | หน้าต่างเด้งทับ | เลือก/ยืนยันแล้วปิด |
| **Deep Link** | ลิงก์เปิดหน้าในแอป | `myapp://order/123` |
| **Universal Link / App Link** | ลิงก์ https ที่เปิดแอป | ปลอดภัยกว่าเพราะยืนยันความเป็นเจ้าของโดเมน |
| **Push Notification** | ข้อความส่งเข้าเครื่อง | ผ่าน APNs (iOS) / FCM (Android) |
| **Device Token** | ที่อยู่ของเครื่อง | ใช้ส่ง push ถึงเครื่องนั้น |
| **Permission** | ขออนุญาตใช้ความสามารถ | กล้อง, ตำแหน่ง, ไมค์, notification |
| **App Lifecycle** | สถานะแอป | active / background / inactive / killed |
| **AsyncStorage** | กล่องเก็บของเล็ก ๆ | key-value storage แบบ async (ไม่ปลอดภัยสำหรับความลับ) |
| **Keychain / Keystore** | ตู้เซฟของ OS | เก็บ token/ความลับอย่างปลอดภัย |
| **FlatList** | ลิสต์ที่เรนเดอร์เท่าที่เห็น | virtualized list สำหรับข้อมูลเยอะ |
| **Virtualization** | วาดเฉพาะที่มองเห็น | เทคนิคหลักของลิสต์ยาว |
| **Hermes** | เครื่องยนต์ JS ของ RN | engine ที่เน้น startup time และแรมต่ำ |
| **Metro** | ตัวรวมไฟล์ JS | bundler ของ RN |
| **Expo** | ชุดเครื่องมือครบ | ทำให้เริ่ม/บิลด์/ปล่อยแอปง่ายขึ้น |
| **OTA Update** | อัปเดตฝั่ง JS โดยไม่ผ่านสโตร์ | ใช้ได้กับส่วน JS เท่านั้น มีข้อจำกัดตามนโยบายสโตร์ |
| **Build / Release** | ทำไฟล์ติดตั้ง | ipa (iOS) / apk-aab (Android) |
| **App Review** | สโตร์ตรวจก่อนปล่อย | ใช้เวลา และ reject ได้ |
| **Backward Compatibility** | เวอร์ชันเก่าต้องยังใช้ได้ | เพราะผู้ใช้ไม่อัปเดตพร้อมกัน |

## 3. Mental Model

มอง React Native เป็น **"สองโลกที่คุยกันข้ามเส้น"**

```
        โลกของ JavaScript                 โลกของ Native
┌───────────────────────────┐   ┌───────────────────────────┐
│ React component tree      │   │ UIView / View จริงของ OS   │
│ state / props / hooks     │ ↔ │ กล้อง GPS Bluetooth        │
│ business logic            │   │ สิทธิ์ แบตเตอรี่ ระบบไฟล์   │
│ รันบน JS Thread           │   │ วาดบน UI Thread            │
└───────────────────────────┘   └───────────────────────────┘
              └──── Bridge / JSI ────┘
```

> **ให้มองภาพนี้ว่า** "โค้ดของเราไม่ได้วาดจอเอง มันเป็นคนสั่งการอยู่อีกฝั่งหนึ่งของสะพาน แล้วให้ฝั่ง native เป็นคนวาดจริง"

**4 หลักคิดที่ต้องติดหัว:**

1. **ไม่มี DOM** — ที่เราเขียน `<View>` `<Text>` มันไม่ใช่ HTML tag แต่คือคำสั่งให้สร้าง native view
2. **ทุกอย่างที่ข้ามสะพานมีต้นทุน** — ส่งข้อมูลก้อนใหญ่หรือถี่เกินไป = กระตุก (New Architecture ลดต้นทุนนี้ แต่หลักคิดยังเหมือนเดิม)
3. **แอปไม่ได้เปิดอยู่ตลอด** — OS มีสิทธิ์พักหรือฆ่าแอปเมื่อไรก็ได้ → state ในหน่วยความจำหายได้เสมอ
4. **โค้ดที่ผู้ใช้ใช้อยู่วันนี้ อาจเป็นเวอร์ชันเมื่อ 8 เดือนที่แล้ว** → ทุกการเปลี่ยน API ต้องคิดย้อนกลับเสมอ

## 4. 🧠 ภาพจำ

```
🧠 ภาพจำที่ 1 — React vs React Native = นักออกแบบคนเดียว งานสองแบบ

React        = ออกแบบแล้วสั่งช่างทำ "ป้ายในเว็บ"      → ผลลัพธ์เป็น DOM
React Native = ออกแบบแล้วสั่งช่างทำ "ป้ายในมือถือ"    → ผลลัพธ์เป็น Native View

วิธีคิด (component/state/props) เหมือนกัน แต่วัสดุคนละอย่าง
```

```
🧠 ภาพจำที่ 2 — Bridge = ล่ามยืนคั่นกลางระหว่างสองห้อง

JS Thread (ห้อง A) พูด → ล่ามแปล → Native (ห้อง B) ทำ
ส่งข้อความสั้น ๆ นาน ๆ ครั้ง = ลื่น
ส่งข้อความยาว ๆ ทุก 16 มิลลิวินาที (เช่น animation ผ่าน JS) = ล่ามพูดไม่ทัน → จอกระตุก

New Architecture = เจาะกำแพงให้สองห้องคุยกันตรง ๆ ได้ (ไม่ต้องรอล่ามทุกประโยค)
```

```
🧠 ภาพจำที่ 3 — App Lifecycle = การประชุมที่ถูกขัดจังหวะ

Foreground = คุณอยู่ในห้องประชุม พูดอยู่
Background = คุณออกไปรับโทรศัพท์ (ห้องยังอยู่ แต่คุณไม่ได้พูด และเวลาคุยของคุณถูกจำกัด)
Killed     = ห้องถูกเก็บไปแล้ว กลับมาต้องจัดใหม่ทั้งหมด

ดังนั้น "state ที่อยู่แค่ในหัว" จะหาย → ของสำคัญต้องจดลงกระดาษ (storage)
```

```
🧠 ภาพจำที่ 4 — FlatList = หน้าต่างรถไฟ

ข้อมูล 10,000 แถว = ทิวทัศน์ยาวตลอดทาง
จอมือถือ = หน้าต่างบานเดียว

FlatList วาดเฉพาะที่เห็นในหน้าต่าง + เผื่ออีกนิด แล้วรีไซเคิลกรอบเดิมเมื่อเลื่อน
ScrollView + map = พยายามวาดทิวทัศน์ทั้งเส้นทางพร้อมกัน → แรมพัง
```

```
🧠 ภาพจำที่ 5 — Release Cycle = เว็บคือหนังสือพิมพ์ออนไลน์ แอปคือหนังสือที่พิมพ์แล้วส่งไปบ้านคน

เว็บ: แก้ข่าวผิดปุ๊บ ทุกคนเห็นฉบับใหม่ทันทีที่ refresh
แอป: พิมพ์ส่งไปแล้ว ดึงกลับไม่ได้ ต้องพิมพ์เล่มใหม่ ให้สโตร์ตรวจ แล้วรอคนสมัครใจมารับ

→ ดังนั้น "API เก่าต้องยังตอบเล่มเก่าได้" เสมอ
```

## 5. How It Works

### 5.1 โครงสร้างการทำงานของแอป RN

```
[ โค้ด React ของเรา (JS/TS) ]
          ↓  Metro bundler รวมเป็น bundle
[ JS ENGINE (Hermes) ]        ← รันบน JS Thread
          ↓  สั่งว่า "UI ควรหน้าตาแบบนี้"
[ BRIDGE / JSI ]              ← เส้นทางข้ามโลก
          ↓
[ NATIVE MODULES + RENDERER ] ← Fabric สร้าง/อัปเดต native view
          ↓
[ NATIVE UI ]                 ← UIView (iOS) / View (Android) วาดบน UI Thread
          ↓
[ หน้าจอผู้ใช้ ]
```

> **ให้มองภาพนี้ว่า** "JavaScript ของเราเป็นผู้กำกับที่ไม่เคยแตะกล้องเลย มันสั่งให้ฝั่ง native เป็นคนถ่ายทำและฉายจริง"

### 5.2 Web vs Mobile Rendering

```
WEB:
  React → Virtual DOM → diff → แก้ DOM จริง → Browser วาด

MOBILE (RN):
  React → Virtual Tree → diff → ส่งคำสั่งข้ามไป Native → OS วาด Native View
```

> **ให้มองภาพนี้ว่า** "สองทางใช้หลักเดียวกันคือคำนวณความต่างก่อนแล้วค่อยแก้ของจริง ต่างกันแค่ว่า 'ของจริง' คือ DOM หรือ Native View"

### 5.3 Navigation

```
[ NAVIGATION CONTAINER ]
         │
    ┌────┴─────────────────────────────┐
    │                                  │
[ TAB NAVIGATOR ]                 [ MODAL ]  ← ซ้อนทับทุกอย่าง
  ├── Tab: Home  → [STACK] Home → Detail → Review
  ├── Tab: Order → [STACK] List → OrderDetail
  └── Tab: Me    → [STACK] Profile → Settings
```

> **ให้มองภาพนี้ว่า** "Tab คือการสลับโลกที่ต่างคนต่างจำประวัติของตัวเอง ส่วน Stack คือการวางกระดาษทับกันในโลกนั้น และ Modal คือกระดาษที่วางทับทุกอย่างชั่วคราว"

| ชนิด | พฤติกรรม | ใช้เมื่อ | ระวัง |
|---|---|---|---|
| Stack | push ทับ / pop ถอย | flow ที่มีลำดับ (list → detail → form) | stack ลึกเกินไป = แรมและ back งง |
| Tab | สลับส่วนหลักของแอป | โหมดการใช้งานคนละเรื่อง | แต่ละ tab ต้องจำ state ของตัวเอง |
| Drawer | เมนูสไลด์จากข้าง | เมนูรองที่ไม่ใช้บ่อย | ผู้ใช้มือถือหลายคนหาไม่เจอ |
| Modal | ทับชั่วคราว แล้วปิด | ยืนยัน/เลือก/ฟอร์มสั้น | ต้องจัดการปุ่ม back ของ Android ให้ถูก |

**ข้อควรรู้ที่ต่างจากเว็บชัดมาก:** Android มี **ปุ่ม back ของระบบ** ที่ผู้ใช้กดได้ตลอดเวลา — ถ้าจัดการไม่ดี ผู้ใช้จะเด้งออกจากแอปกลางฟอร์ม ส่วน iOS ใช้ **swipe จากขอบซ้าย** แทน

### 5.4 App Lifecycle

```
[ NOT RUNNING ]
      │ ผู้ใช้เปิดแอป
      ↓
[ ACTIVE / FOREGROUND ]  ← ทำงานเต็มที่ รับ input ได้
      │ กด home / สลับแอป / มีสายเข้า
      ↓
[ BACKGROUND ]           ← ยังอยู่ในแรม แต่ทำงานได้จำกัดและมีเวลาจำกัด
      │ OS ต้องการแรมคืน
      ↓
[ KILLED ]               ← state ในหน่วยความจำหายหมด
      │ ผู้ใช้เปิดใหม่
      ↓
[ COLD START ]           ← เริ่มจากศูนย์ ต้องกู้สถานะจาก storage
```

> **ให้มองภาพนี้ว่า** "แอปมือถือไม่ได้เป็นเจ้าของเครื่อง มันเป็นแขกที่ระบบปฏิบัติการจะเชิญออกเมื่อไรก็ได้"

**ผลที่ตามมาในการออกแบบ (นี่คือสิ่งที่สัมภาษณ์อยากได้ยิน):**

| สถานการณ์ | ต้องทำอะไร |
|---|---|
| ผู้ใช้กรอกฟอร์มยาวแล้วสลับไปรับสาย | เซฟ draft ลง storage ไม่ใช่เก็บใน state อย่างเดียว |
| กลับมาจาก background หลังผ่านไปครึ่งชั่วโมง | refetch ข้อมูลที่เก่าแล้ว / ตรวจ token ว่าหมดอายุหรือยัง |
| อัปโหลดไฟล์อยู่แล้วแอปถูกพักไว้ | ต้องรองรับการทำต่อ/ทำใหม่ และ **idempotency** ฝั่ง server |
| เปิดแอปครั้งแรกของวัน (cold start) | ลดงานตอนเปิดให้น้อยที่สุด — ผู้ใช้ตัดสินแอปจากวินาทีแรก |

### 5.5 Permission

```
[ ผู้ใช้กดปุ่ม "ถ่ายรูปสินค้า" ]
        ↓
[ เช็คสถานะสิทธิ์ก่อน ]
        ↓
   ┌────┴──────┬──────────────┬───────────────┐
granted     denied      blocked/นโยบาย     ยังไม่เคยถาม
   ↓           ↓               ↓                ↓
เปิดกล้อง   อธิบายเหตุผล   ส่งไปหน้า Settings   ขอสิทธิ์
            แล้วขอใหม่      (ขอซ้ำไม่ขึ้นแล้ว)
```

> **ให้มองภาพนี้ว่า** "การขอ permission ไม่ใช่ if/else ครั้งเดียว แต่เป็น flow ที่ต้องรองรับทุกคำตอบของผู้ใช้ รวมถึงคำตอบว่า 'ไม่ และอย่าถามอีก'"

หลักปฏิบัติที่ดี:

- **ขอตอนที่ผู้ใช้เข้าใจว่าทำไม** (ขอกล้องตอนกดถ่ายรูป ไม่ใช่ตอนเปิดแอปครั้งแรก)
- **แอปต้องยังใช้งานได้แม้ถูกปฏิเสธ** — อย่าให้จอขาวหรือแอปค้าง
- ใน iOS ถ้าผู้ใช้ปฏิเสธไปแล้ว ระบบจะ **ไม่แสดง dialog อีก** → ต้องพาไป Settings
- ต้องประกาศเหตุผลการใช้งานในไฟล์ config ของแอป ไม่งั้น **ถูก reject ตอน review**

### 5.6 Deep Link / Universal Link

```
[ ผู้ใช้กดลิงก์ในแชท / อีเมล / SMS ]
        ↓
  myapp://order/123           (Custom Scheme = Deep Link)
  https://shop.com/order/123  (Universal Link / App Link)
        ↓
[ OS ตรวจว่ามีแอปที่รับลิงก์นี้ไหม ]
        ↓
   ┌────┴────────────────┐
มีแอป → เปิดแอป          ไม่มีแอป → เปิดเว็บ (เฉพาะ Universal Link)
        ↓
[ แอปเปิดอยู่แล้ว?  → เปลี่ยนหน้าไปที่ order 123 ]
[ แอปยังไม่เปิด?    → cold start แล้วค่อยพาไป order 123 ]
        ↓
[ ยังไม่ได้ login?  → พาไป login ก่อน แล้วค่อยกลับมาที่ order 123 ]
```

> **ให้มองภาพนี้ว่า** "Deep link คือการที่คนนอกโยนพิกัดเข้ามาในแอปเรา และแอปต้องพาผู้ใช้ไปถึงพิกัดนั้นให้ได้ ไม่ว่าตอนนั้นแอปจะอยู่ในสภาพไหน"

| | Deep Link (custom scheme) | Universal Link / App Link |
|---|---|---|
| รูปแบบ | `myapp://...` | `https://...` |
| ต้องยืนยันความเป็นเจ้าของโดเมน | ไม่ | **ใช่** (ไฟล์ยืนยันบนเว็บไซต์) |
| แอปอื่นแอบอ้าง scheme เดียวกันได้ | ได้ | ไม่ได้ |
| ถ้าไม่ได้ติดตั้งแอป | ไม่เกิดอะไร / error | เปิดหน้าเว็บแทน |

### 5.7 Push Notification

```
[ แอป ]  ขอ permission แจ้งเตือน
   ↓ ได้รับ DEVICE TOKEN จาก APNs/FCM
[ ส่ง token ไปเก็บที่ BACKEND ]
   ↓
[ เกิดเหตุการณ์: ออเดอร์ถูกจัดส่ง ]
   ↓
[ BACKEND → APNs (iOS) / FCM (Android) ]
   ↓
[ เครื่องผู้ใช้ ]
   ├── แอปเปิดอยู่ (foreground) → แอปได้รับ event เอง มักต้องแสดง UI เอง
   ├── แอปอยู่ background      → OS แสดง notification
   └── แอปถูก kill             → OS แสดง notification (แอปยังไม่ได้รัน)
   ↓
[ ผู้ใช้กด notification ] → เปิด/ปลุกแอป → พาไปหน้าที่เกี่ยวข้อง (ใช้กลไกเดียวกับ deep link)
```

> **ให้มองภาพนี้ว่า** "push ไม่ได้ส่งจากเราไปหาแอปตรง ๆ แต่ส่งผ่านเจ้าของระบบปฏิบัติการ ซึ่งแปลว่าเราควบคุมการส่งถึงไม่ได้ 100% และห้ามใช้ push เป็นช่องทางส่งข้อมูลที่ขาดไม่ได้"

**สิ่งที่มืออาชีพต้องพูดถึง:** push **ไม่การันตีการส่งถึง** (ผู้ใช้ปิดแจ้งเตือน, เครื่องออฟไลน์, token หมดอายุ) → ข้อมูลสำคัญต้องดึงจาก API ตอนเปิดแอปด้วยเสมอ และ token ต้องอัปเดตทุกครั้งที่เปลี่ยน + ลบเมื่อ logout

### 5.8 Storage

| ที่เก็บ | เหมาะกับ | ห้ามเก็บ |
|---|---|---|
| **State ในหน่วยความจำ** | ข้อมูลชั่วคราวระหว่างใช้งาน | อะไรที่หายไม่ได้ (แอปถูก kill แล้วหาย) |
| **AsyncStorage / key-value** | ค่าตั้งค่า, flag, cache เล็ก ๆ, draft | token, รหัสผ่าน, ข้อมูลส่วนบุคคล (ไม่เข้ารหัส) |
| **Keychain (iOS) / Keystore (Android)** | access/refresh token, ความลับ | — |
| **SQLite / ฐานข้อมูลในเครื่อง** | ข้อมูลเยอะ ต้อง query, offline-first | ข้อมูลที่ต้องสดตลอดเวลา |
| **File system** | รูป/ไฟล์ที่ดาวน์โหลดมา | ข้อมูลที่ต้องค้นหา |

> หลักง่าย ๆ: **"ความลับลงตู้เซฟ ของทั่วไปลงลิ้นชัก ของเยอะลงฐานข้อมูล"**

### 5.9 Large List / FlatList

```
ScrollView + items.map()            FlatList
┌──────────────┐                    ┌──────────────┐
│ item 1 ✓วาด  │                    │ item 1 ✓วาด  │
│ item 2 ✓วาด  │  ← เห็นแค่นี้        │ item 2 ✓วาด  │ ← เห็นแค่นี้
├──────────────┤                    ├──────────────┤
│ item 3..9999 │ ✓วาดหมด (เปลือง)   │ item 3..9999 │ ✗ ยังไม่วาด
└──────────────┘                    └──────────────┘
```

> **ให้มองภาพนี้ว่า** "FlatList ทำงานเหมือนโรงหนังที่มีเก้าอี้เท่าจำนวนคนดูจริง ไม่ใช่สร้างเก้าอี้ให้คนทั้งเมืองล่วงหน้า"

สิ่งที่ต้องทำให้ถูกเวลาใช้ FlatList:

- ใส่ `keyExtractor` ที่เป็น **id จริง** ไม่ใช่ index (เหตุผลเดียวกับ key ใน React — ดู PART 3)
- ทำ item component เป็น **pure/memo** ไม่ให้ re-render ทั้งลิสต์เมื่อ state อื่นเปลี่ยน
- ถ้าความสูงแต่ละแถวเท่ากัน ให้บอกความสูงล่วงหน้าได้ → เลื่อนลื่นขึ้นมาก
- ทำ **pagination** ตอนเลื่อนถึงท้าย ไม่ใช่โหลดทั้งหมดรวดเดียว
- อย่าสร้าง function/object ใหม่ใน `renderItem` ทุกรอบ

### 5.10 Build & Release

```
[ โค้ดใน main ]
      ↓
[ CI: lint + test + typecheck ]
      ↓
[ BUILD ]  iOS → .ipa (ต้องมี certificate/provisioning)
           Android → .aab / .apk (ต้อง sign key)
      ↓
[ อัปโหลดขึ้น App Store Connect / Google Play Console ]
      ↓
[ ปล่อยให้ผู้ทดสอบภายใน (TestFlight / Internal Track) ]
      ↓
[ APP REVIEW ]   ← ใช้เวลา และถูก reject ได้
      ↓
[ RELEASE ]      ← ทยอยปล่อย (staged rollout) ได้
      ↓
[ ผู้ใช้ต้องกดอัปเดตเอง (หรือรอ auto-update) ]
      ↓
[ ผู้ใช้จำนวนมากยังใช้เวอร์ชันเก่าต่อไปอีกหลายเดือน ]
```

> **ให้มองภาพนี้ว่า** "การปล่อยแอปไม่ใช่เส้นชัย แต่เป็นการเริ่มต้นช่วงเวลาที่โค้ดหลายเวอร์ชันของเราต้องอยู่ร่วมกันในโลกจริงพร้อมกัน"

**นี่คือเหตุผลว่าทำไม backward compatibility ของ API สำคัญมากในงาน mobile:**

| กฎ | เหตุผล |
|---|---|
| ห้ามลบ/เปลี่ยนความหมายของ field เดิม | แอปเวอร์ชันเก่ายังอ่าน field นั้นอยู่ |
| เพิ่ม field ใหม่ได้ (client ต้องไม่พังเมื่อเจอ field ที่ไม่รู้จัก) | รองรับการโตของ API |
| ถ้าต้องเปลี่ยนจริง → ทำ **versioning** (`/v2/...`) แล้วเลี้ยง v1 ไว้จนคนใช้น้อยพอ | ไม่ทำให้ผู้ใช้เก่าแอปพัง |
| มี **force update / soft update** | เมื่อจำเป็นต้องบังคับให้เลิกใช้เวอร์ชันเก่า (เช่น ช่องโหว่ความปลอดภัย) |
| ดู metric ว่าเวอร์ชันไหนมีคนใช้เท่าไร | ใช้ตัดสินใจว่าเลิกรองรับได้เมื่อไร |

**OTA update** (อัปเดตเฉพาะ bundle JS โดยไม่ผ่านสโตร์) ช่วยแก้บั๊กเล็ก ๆ ได้เร็ว แต่ **ใช้กับส่วน native ไม่ได้** และต้องอยู่ในกรอบนโยบายของสโตร์ → อย่าตอบว่า "แก้อะไรก็ได้ไม่ต้องผ่านสโตร์"

## 6. Example — Scenario จากงานจริง

### Scenario A: "แอปสั่งอาหาร — ผู้ใช้กดสั่งตอนสัญญาณขาด ๆ หาย ๆ"

ปัญหาจริง: ผู้ใช้กดปุ่ม "สั่งซื้อ" แล้วหมุนค้าง เน็ตหลุด ผู้ใช้กดซ้ำอีก 3 ครั้ง → ได้ 4 ออเดอร์

```
[ กดสั่ง ] → [ ส่ง POST /orders ] → เน็ตหลุดตอนรอ response
                                       ↓
                       ไม่รู้ว่า server ได้รับหรือยัง ← จุดตายของ mobile
```

> **ให้มองภาพนี้ว่า** "บนมือถือ การไม่ได้รับคำตอบ ไม่ได้แปลว่าคำขอไม่ถึง"

ทางแก้ที่ต้องพูดได้:

| ชั้น | ทำอะไร |
|---|---|
| UI | ปิดปุ่มทันทีที่กด + แสดงสถานะกำลังส่ง |
| Client | สร้าง **request id** (idempotency key) ต่อหนึ่งความตั้งใจของผู้ใช้ แล้วใช้ค่าเดิมเมื่อ retry |
| Network | ตั้ง timeout + retry แบบ exponential backoff (อย่า retry POST ที่ไม่ idempotent โดยไม่มี key) |
| Server | รับ key ซ้ำ = คืนผลเดิม ไม่สร้างออเดอร์ใหม่ |
| UX | ถ้ายังไม่แน่ใจ ให้พาผู้ใช้ไปหน้ารายการออเดอร์ให้เห็นความจริง |

### Scenario B: "หน้า feed กระตุกตอนเลื่อน"

ไล่ตามลำดับ:

```
[ วัดก่อน ] → เป็น JS thread ช้า หรือ UI thread ช้า?
      ├── JS ช้า  → re-render เยอะ / คำนวณหนักใน render / ส่งข้อมูลข้ามสะพานถี่
      └── UI ช้า  → รูปใหญ่เกินไป / เงา-โปร่งใสเยอะ / layout ซ้อนลึก
```

รายการตรวจที่ใช้จริง:

| ตรวจ | ทำไม |
|---|---|
| ใช้ FlatList ไม่ใช่ ScrollView + map | virtualization |
| item เป็น memo + callback คงที่ | ลด re-render ทั้งลิสต์ |
| รูปย่อขนาดจาก server มาแล้ว | มือถือไม่ควรโหลดรูป 4000px มาแสดง 100px |
| animation ใช้ native driver | ให้ animation รันฝั่ง native ไม่ต้องข้ามสะพานทุกเฟรม |
| ไม่คำนวณหนักใน render | ย้ายไป memo/worker/ล่วงหน้า |

### Scenario C: "ผู้ใช้บอกว่ากดลิงก์จากไลน์แล้วแอปเปิดหน้าแรกเฉย ๆ"

สาเหตุที่พบบ่อยที่สุด: จัดการ deep link เฉพาะตอน **แอปเปิดอยู่** แต่ไม่ได้จัดการตอน **cold start** หรือ **ยังไม่ได้ login**

ทางแก้เชิงออกแบบ: เก็บ "ปลายทางที่ตั้งใจไป" ไว้ก่อน → ทำ auth ให้เสร็จ → แล้วค่อย navigate ไปปลายทางนั้น (pattern เดียวกับ `redirect after login` ของเว็บ)

### Scenario D: "ต้องต่อเครื่องชั่งน้ำหนักผ่าน Bluetooth"

ไม่มี library สำเร็จรูปที่ตรงกับอุปกรณ์ → ต้องเขียน **Native Module**

```
[ JS: startScan() ]
      ↓ ผ่าน Bridge / TurboModule
[ Native (Swift/Kotlin) ]  คุยกับ Bluetooth stack ของ OS
      ↓ ส่ง event กลับ
[ JS รับค่าน้ำหนักแบบ stream ]
```

> **ให้มองภาพนี้ว่า** "Native Module คือปลั๊กที่เราเดินสายเองเมื่อสะพานมาตรฐานไม่มีช่องที่เราต้องการ"

ต้นทุนที่ต้องบอกให้ทีมรู้: ต้องดูแลโค้ดสองแพลตฟอร์ม, ต้องทดสอบบนเครื่องจริงหลายรุ่น, และทำให้การอัปเกรด RN ยากขึ้น

### Scenario E: "แอปเวอร์ชัน 1.2 พัง เพราะ backend เปลี่ยน field"

backend เปลี่ยน `price` จาก number เป็น object `{amount, currency}` → แอปเวอร์ชันเก่าที่ยังอยู่ในมือผู้ใช้ **crash ทันทีทั้งหมด** และ **แก้ไม่ได้ด้วยการ deploy** เพราะโค้ดอยู่ในเครื่องผู้ใช้

บทเรียน 3 ข้อ:

1. API ที่มี mobile client = **API สาธารณะ** เปลี่ยนแบบ breaking ไม่ได้
2. แอปควร **ทนต่อข้อมูลที่ไม่รู้จัก** (parse แบบป้องกัน ไม่ crash ทั้งหน้าจอ)
3. ต้องมี **crash reporting** ที่แยกตามเวอร์ชันแอป เพื่อรู้ว่าใครพังและมีกี่คน

## 7. Compare

### 7.1 React vs React Native

| หัวข้อ | React (Web) | React Native |
|---|---|---|
| ปลายทางการเรนเดอร์ | DOM | Native View ของ OS |
| element พื้นฐาน | `<div> <span> <p> <img>` | `<View> <Text> <Image> <Pressable>` |
| ข้อความ | อยู่ใน tag อะไรก็ได้ | **ต้องอยู่ใน `<Text>` เท่านั้น** |
| จัดสไตล์ | CSS / CSS-in-JS / class | object สไตล์ใน JS (subset ของ CSS) |
| layout | flexbox + block/inline/grid | **flexbox เป็นหลัก** และ `flexDirection` default เป็น `column` |
| หน่วย | px, rem, %, vh | ตัวเลข (density-independent) |
| Navigation | URL + router | navigation library (stack/tab) ไม่มี URL bar |
| Hooks | เหมือนกัน | **เหมือนกัน** (useState/useEffect/useMemo ใช้เหมือนเดิม) |
| เข้าถึงฮาร์ดแวร์ | จำกัดมาก | กล้อง GPS Bluetooth ไฟล์ ฯลฯ ผ่าน native module |
| การส่งของใหม่ | deploy ได้ทันที | ต้องผ่านสโตร์ (ยกเว้น OTA เฉพาะ JS) |
| ทดสอบ | เบราว์เซอร์ | ต้องทดสอบบนเครื่องจริงหลายรุ่น/หลาย OS version |

**ประโยคสรุปสำหรับสัมภาษณ์:** "ความรู้ React ย้ายมาใช้ได้เกือบทั้งหมด สิ่งที่ต้องเรียนใหม่คือชั้นที่ติดกับแพลตฟอร์ม: UI primitives, navigation, permission, lifecycle และ release"

### 7.2 React Native vs Native App (Swift/Kotlin)

| หัวข้อ | React Native | Native |
|---|---|---|
| โค้ดใช้ร่วมสองแพลตฟอร์ม | ส่วนใหญ่ใช้ร่วมได้ | แยกกันคนละชุด |
| ความเร็วในการพัฒนา | เร็วกว่าเมื่อทำสองแพลตฟอร์ม | ช้ากว่า (ทำสองรอบ) |
| ทีมที่ต้องใช้ | ทีม React เดิมต่อยอดได้ | ต้องมีคน iOS + คน Android |
| ประสิทธิภาพสูงสุด | ดีพอสำหรับแอปทั่วไป | เหนือกว่าในงานหนัก (กราฟิก, กล้อง realtime, เกม) |
| เข้าถึง API ใหม่ของ OS | ต้องรอ library หรือเขียน native module เอง | ได้ทันทีที่ OS ปล่อย |
| ความรู้สึก "เป็นแอปของแพลตฟอร์ม" | ต้องตั้งใจทำให้ได้ | ได้มาโดยธรรมชาติ |
| ขนาดแอป | ใหญ่กว่าเล็กน้อย (มี runtime) | เล็กกว่า |
| การดูแลระยะยาว | ต้องตาม RN upgrade | ตาม OS อย่างเดียว |
| เลือกเมื่อ | แอปธุรกิจ/CRUD/e-commerce, ทีมเล็ก, ต้องออกทั้งสอง OS เร็ว | งานที่ performance/ฮาร์ดแวร์เป็นหัวใจ, ทีมมี native อยู่แล้ว |

**ห้ามตอบว่า "RN ดีกว่า native"** — ต้องตอบว่า "RN ได้เปรียบเมื่อ..." ตามตารางนี้

### 7.3 DOM vs Native UI

| | DOM | Native UI |
|---|---|---|
| คืออะไร | ต้นไม้ element ในเบราว์เซอร์ | ต้นไม้ view ของระบบปฏิบัติการ |
| ใครวาด | Browser engine | OS |
| จัดสไตล์ด้วย | CSS เต็มรูปแบบ | ชุด property ที่ RN รองรับ (subset) |
| ตรวจสอบด้วย | DevTools ดู element | ตัวตรวจ layout ของ RN / เครื่องมือ native |
| ทำอะไรได้ที่อีกฝั่งไม่ได้ | hover, URL, SEO | เข้าถึงฮาร์ดแวร์, background task, push |

### 7.4 Bridge (Old) vs New Architecture

| หัวข้อ | Bridge เดิม | New Architecture (JSI/Fabric/TurboModules) |
|---|---|---|
| วิธีคุยกัน | ส่งข้อความ async แบบ serialize (JSON) | JS เรียก native ผ่าน C++ ได้ตรง |
| คอขวด | ข้อมูลเยอะ/ถี่ = ช้า, สั่งแบบ sync ไม่ได้ | ลด serialize, เรียก sync ได้บางกรณี |
| การโหลด module | โหลดทุกตัวตอนเริ่ม | โหลดเมื่อใช้งาน (lazy) |
| ผลต่อนักพัฒนา | ต้องเลี่ยงการยิงข้ามสะพานถี่ ๆ | ยังต้องคิดเรื่องเดิม แต่เพดานสูงขึ้น |

**วิธีตอบให้ปลอดภัย:** อธิบาย **แนวคิด** (ทำไมสะพานเป็นคอขวด และ New Architecture แก้ที่อะไร) ดีกว่าท่องชื่อ version — ผู้สัมภาษณ์อยากรู้ว่าคุณเข้าใจปัญหา ไม่ใช่จำศัพท์

### 7.5 Storage: AsyncStorage vs Secure Storage vs SQLite

| | AsyncStorage | Keychain/Keystore | SQLite |
|---|---|---|---|
| รูปแบบ | key-value | key-value ที่เข้ารหัสโดย OS | ตาราง + query |
| ปลอดภัยพอเก็บ token | **ไม่** | **ใช่** | ไม่ (เว้นแต่เข้ารหัสเอง) |
| ข้อมูลเยอะ | ไม่เหมาะ | ไม่เหมาะ | เหมาะ |
| ใช้กับ | setting, flag, draft, cache | access/refresh token | offline-first, ข้อมูลที่ต้องค้นหา |

### 7.6 Web deploy vs Mobile release

| | Web | Mobile |
|---|---|---|
| เวลาจาก merge → ผู้ใช้ได้ใช้ | นาที | วัน–สัปดาห์ (review + ผู้ใช้อัปเดต) |
| ถอยกลับเมื่อพัง | rollback ได้ทันที | ต้องส่งเวอร์ชันใหม่เข้ารีวิว (หรือ OTA เฉพาะ JS) |
| จำนวนเวอร์ชันที่ต้องรองรับพร้อมกัน | 1 | หลายเวอร์ชันพร้อมกัน |
| การเปลี่ยน API แบบ breaking | ทำได้ถ้าคุม client ได้ | **ทำไม่ได้** ต้อง versioning |
| ทดสอบก่อนปล่อย | staging | staging + TestFlight/Internal + เครื่องจริง |

## 8. Common Mistakes

**1. คิดว่า React Native = เว็บที่ยัดใส่แอป**
RN เรนเดอร์เป็น native view จริง ส่วน WebView คือการฝังหน้าเว็บ — คนละเรื่องกันคนละชั้น

**2. คิดว่า "เขียนครั้งเดียวได้ทั้งสอง OS 100%"**
ในงานจริงมีส่วนที่ต้องแยก iOS/Android เสมอ: permission, push, การจัดการ back, ความสูง status bar/notch, พฤติกรรม keyboard

**3. เก็บ access token ใน AsyncStorage**
ไม่ได้เข้ารหัส → ต้องใช้ Keychain/Keystore

**4. ใช้ `ScrollView` + `map` กับลิสต์ยาว**
สร้าง view ทั้งหมดพร้อมกัน → แรมพุ่ง แอปช้า/crash บนเครื่องระดับกลาง-ล่าง

**5. ใช้ index เป็น key ของลิสต์**
พอมีการเพิ่ม/ลบ/เรียงใหม่ → React จับคู่ผิด → state ของแถวสลับกัน (เหตุผลเดียวกับใน PART 3)

**6. ขอ permission ทั้งหมดตอนเปิดแอปครั้งแรก**
อัตราการกดปฏิเสธสูงมาก และเสี่ยงโดน reject ตอน review — ต้องขอตอนที่ผู้ใช้เข้าใจบริบท

**7. ไม่จัดการกรณี "ถูกปฏิเสธถาวร"**
แอปค้างหรือจอขาวเมื่อผู้ใช้ไม่ให้สิทธิ์ ต้องมีทางเลือกสำรองและปุ่มไป Settings

**8. เก็บ state สำคัญไว้ในหน่วยความจำอย่างเดียว**
แอปถูก kill ตอน background → ผู้ใช้กลับมาแล้วข้อมูลหาย (ฟอร์มยาว ตะกร้าสินค้า)

**9. สมมติว่ามีอินเทอร์เน็ตเสมอ**
มือถืออยู่ในลิฟต์ ในรถไฟใต้ดิน สัญญาณ 1 ขีด → ต้องมี timeout, retry, สถานะ offline และ idempotency

**10. ยิง animation ผ่าน JS ทุกเฟรม**
ทำให้กระตุกเพราะต้องข้ามสะพานถี่ — ใช้ native driver / library ที่รัน animation ฝั่ง native

**11. จัดการ deep link เฉพาะตอนแอปเปิดอยู่**
ลืม cold start และลืมเคส "ยังไม่ login"

**12. เชื่อว่า push notification ส่งถึงแน่นอน**
ผู้ใช้อาจปิดแจ้งเตือน เครื่องอาจออฟไลน์ — ห้ามใช้ push เป็นทางเดียวของข้อมูลสำคัญ

**13. ทดสอบแค่บน simulator / เครื่องเรือธง**
ปัญหา performance และ permission ส่วนใหญ่โผล่บนเครื่องจริงระดับกลาง-ล่าง และ OS version เก่า

**14. เปลี่ยน API แบบ breaking แล้วคิดว่า "เดี๋ยวให้ผู้ใช้อัปเดตแอป"**
ผู้ใช้จำนวนมากไม่อัปเดตอีกหลายเดือน → นี่คือความผิดพลาดที่แพงที่สุดของทีมที่ย้ายจากเว็บมาทำ mobile

**15. คิดว่า OTA update แก้ได้ทุกอย่าง**
แก้ได้เฉพาะฝั่ง JS ไม่ครอบคลุมโค้ด native และอยู่ใต้กฎของสโตร์

## 9. Debugging — พังแล้วไล่ดูอะไรตามลำดับ

### 9.1 คำถามแรกเสมอ: "พังที่ชั้นไหน"

```
[ JS ของเรา ] → [ RN framework ] → [ Native Module ] → [ OS / Device ] → [ Network / Backend ]
      ①               ②                   ③                  ④                 ⑤
```

> **ให้มองภาพนี้ว่า** "การ debug แอปคือการตัดสินใจว่าปัญหาอยู่ในโค้ดเรา ในสะพาน ในเครื่อง หรือที่หลังบ้าน"

วิธีตัดทางเลือกเร็ว ๆ:

- เกิดทั้งสอง OS ไหม? → เกิดทั้งคู่ = มักเป็นโค้ด JS / backend, เกิดข้างเดียว = เรื่อง native/permission/OS
- เกิดทุกเครื่องหรือบางรุ่น? → บางรุ่น = แรม/OS version/หน้าจอ
- เกิดหลังอัปเดตอะไร? → library, RN version, OS update, API เปลี่ยน

### 9.2 ตารางอาการ → สาเหตุ → ที่ต้องดู

| อาการ | สาเหตุที่พบบ่อย | ไล่ดูตามลำดับ |
|---|---|---|
| จอขาว/แอปเด้งปิดตอนเปิด | JS error ตอน init / bundle ไม่ตรง / native crash | log ของเครื่อง (Xcode/Logcat) → crash report → ลอง clean build |
| ทำงานบน dev แต่ release พัง | โค้ดที่พึ่ง dev only / env var ไม่ถูกใส่ตอน build / minify | เทียบ config ของ build → ทดสอบ release build ก่อนส่ง |
| iOS ได้ Android ไม่ได้ (หรือกลับกัน) | permission/config เฉพาะแพลตฟอร์ม | ไฟล์ config ของแต่ละ OS → เอกสารของ library |
| เลื่อนลิสต์กระตุก | ไม่ virtualize / re-render เยอะ / รูปใหญ่ | ตรวจว่าใช้ FlatList → memo → ขนาดรูป → animation |
| แอปกินแรมจนถูกฆ่า | โหลดข้อมูล/รูปทั้งหมดไว้ในหน่วยความจำ | ดู memory graph → เปลี่ยนเป็น paging + cache รูป |
| กลับจาก background แล้วข้อมูลผิด | ไม่ refetch / token หมดอายุ | ผูก event ตอนกลับ foreground → ตรวจอายุ token |
| ปิดแอปแล้วเปิดใหม่ ข้อมูลหาย | เก็บไว้ใน state อย่างเดียว | ย้ายของสำคัญลง storage |
| กดลิงก์แล้วไม่เข้าหน้าที่ควร | ไม่จัดการ cold start / ไม่ได้ตั้งค่า link | ทดสอบทั้ง 3 สถานะแอป → ตรวจไฟล์ยืนยันโดเมน |
| push ไม่เข้า | permission ไม่ได้ / token ไม่ถูกส่ง / ส่งผิด environment | ตรวจสถานะ permission → token ใน backend → log ของ APNs/FCM |
| API ใช้ได้บนเว็บ แต่แอป error | header/TLS/timeout/ที่อยู่ localhost | ทดสอบด้วยเครื่องจริง → ดู request จริง → ตรวจ base URL ต่อ environment |
| ผู้ใช้บางกลุ่ม crash เท่านั้น | เวอร์ชันแอปเก่า + API เปลี่ยน | crash report แยกตามเวอร์ชันแอป/OS |
| ถูก reject ตอน review | permission ไม่มีคำอธิบาย / ฟีเจอร์ผิดนโยบาย / ล็อกอินให้ทดสอบไม่ได้ | อ่านเหตุผลที่สโตร์แจ้ง → แก้ให้ตรงข้อ |

### 9.3 เครื่องมือประจำตัว

| เครื่องมือ | ใช้เมื่อ |
|---|---|
| Log ของ OS (Xcode Console / Logcat) | native crash ที่ JS ไม่เห็น |
| React Native DevTools / debugger | ดู component tree, state, network |
| Performance monitor (FPS ของ JS และ UI thread) | หาว่ากระตุกเพราะฝั่งไหน |
| Crash reporting (แยกตามเวอร์ชัน) | รู้ว่าใครพัง กี่คน เวอร์ชันไหน |
| Analytics/ตัวติดตามการใช้งาน | รู้ว่าผู้ใช้ค้างที่ขั้นไหนของ flow |
| เครื่องจริงหลายรุ่น + OS เก่า | ทดสอบสิ่งที่ simulator บอกไม่ได้ |

## 11. Answer Like a Developer

**โครงการตอบ 4 จังหวะ:**

```
1) นิยามสั้น
2) ต่างจากเว็บตรงไหน (จุดที่คนสัมภาษณ์อยากได้ยินในบทนี้)
3) ตัวอย่างจากงานจริง
4) trade-off / สิ่งที่ต้องระวังใน production
```

**ตัวอย่างที่ 1 — "React Native ต่างจาก React ยังไง"**

> (1) React Native ใช้วิธีคิดเดียวกับ React คือ component, state, props, hooks
> (2) ต่างที่ปลายทาง — React เรนเดอร์เป็น DOM ส่วน RN เรนเดอร์เป็น native view ของ OS จริง ๆ ดังนั้นไม่มี div ไม่มี CSS เต็มรูปแบบ ไม่มี URL และ layout เป็น flexbox ที่ตั้งต้นเป็นแนวตั้ง
> (3) เวลาทำงานจริง ส่วนที่ต้องเรียนใหม่ไม่ใช่ React แต่เป็นชั้นที่ติดกับแพลตฟอร์ม เช่น navigation, permission, app lifecycle และการ build/release
> (4) และข้อที่กระทบสถาปัตยกรรมที่สุดคือ แอปที่ผู้ใช้ถืออยู่อาจเป็นเวอร์ชันเก่าหลายเดือน ดังนั้น API ต้อง backward compatible เสมอ

**ตัวอย่างที่ 2 — "ทำไม mobile ต้องคิดเรื่อง lifecycle"**

> "เพราะแอปไม่ได้เป็นเจ้าของเครื่อง ระบบปฏิบัติการมีสิทธิ์พักหรือฆ่าแอปเมื่อไรก็ได้ ผมเลยถือหลักว่าอะไรที่อยู่ใน state หน่วยความจำอย่างเดียวคือของที่หายได้ ถ้าเป็นฟอร์มยาวหรือตะกร้าสินค้าผมจะเซฟ draft ลง storage และตอนกลับมา foreground ผมจะเช็คว่าข้อมูลเก่าไปหรือยัง และ token ยังใช้ได้ไหม ก่อนจะปล่อยให้ผู้ใช้กดอะไรต่อ"

**ตัวอย่างที่ 3 — "RN กับ Native เลือกอะไร"**

> "ขึ้นกับโจทย์ครับ ถ้าเป็นแอปธุรกิจที่เป็น CRUD และต้องออกทั้ง iOS และ Android เร็ว ๆ ด้วยทีมที่ถนัด React อยู่แล้ว RN คุ้มกว่าชัดเจน แต่ถ้าหัวใจของโปรดักต์คือการประมวลผลกล้องแบบ realtime หรือกราฟิกหนัก หรือเราต้องใช้ API ใหม่ของ OS ทันทีที่ปล่อย native จะได้เปรียบ และในงานจริงหลายทีมก็ผสม — ใช้ RN เป็นหลักแล้วเขียน native module เฉพาะส่วนที่ต้องการจริง ๆ"

**สิ่งที่ไม่ควรตอบ:**

## 12. One-Minute Review

- **React Native** = React ที่เรนเดอร์ออกเป็น **native view** ไม่ใช่ DOM — "learn once, write anywhere"
- **ไม่มี DOM/CSS เต็มรูปแบบ** → ใช้ `<View>/<Text>/<Image>`, style เป็น object, layout เป็น flexbox (default `column`)
- **Hooks/state/props เหมือนเว็บ** สิ่งที่ต่างคือชั้นที่ติดแพลตฟอร์ม
- **Bridge** = ทางข้ามระหว่าง JS กับ Native และเป็นคอขวดเมื่อยิงถี่ → **New Architecture (JSI/Fabric/TurboModules)** ลดคอขวดนี้
- **Navigation** = Stack (ซ้อน) / Tab (สลับโลก) / Modal (ทับชั่วคราว) และต้องจัดการปุ่ม back ของ Android
- **Native Module** = ปลั๊กที่เขียนเองเมื่อ RN ไม่มีของให้ (Bluetooth, SDK เฉพาะทาง)
- **Permission** = flow ไม่ใช่ if เดียว — ต้องรองรับ denied/blocked และขอในบริบทที่ผู้ใช้เข้าใจ
- **Lifecycle** = foreground / background / killed → **state ในหน่วยความจำหายได้เสมอ**
- **Deep Link** (`myapp://`) vs **Universal Link** (`https://` + ยืนยันโดเมน) และต้องรองรับ cold start + ยังไม่ login
- **Push** ผ่าน APNs/FCM — **ไม่การันตีการส่งถึง** ต้องมี fallback ดึงข้อมูลตอนเปิดแอป
- **Storage**: ความลับ → Keychain/Keystore, ทั่วไป → key-value, เยอะ → SQLite
- **FlatList** = virtualization + key จริง + memo + pagination
- **Performance** = แยกให้ออกว่า JS thread ช้าหรือ UI thread ช้า
- **Release** = build → สโตร์ review → ผู้ใช้อัปเดตเอง → **หลายเวอร์ชันอยู่ร่วมกัน** → API ต้อง backward compatible + มี force update

## 13. Memory Card

**จำ 5 อย่าง**

1. **RN = React ที่ปลายทางเป็น Native View** — วิธีคิดเดิม แต่ไม่มี DOM/CSS/URL
2. **ทุกอย่างวิ่งข้ามสะพานระหว่าง JS กับ Native** — ยิงถี่หรือหนัก = กระตุก (New Architecture ลดต้นทุนนี้)
3. **แอปถูกพัก/ถูกฆ่าได้ตลอด** — ของสำคัญต้องลง storage และต้อง refetch ตอนกลับ foreground
4. **มือถือคือโลกของ "ไม่แน่นอน"** — permission ถูกปฏิเสธได้, เน็ตหลุดได้, push ไม่ถึงได้ → ต้องมี fallback + idempotency
5. **Release ไม่ใช่เส้นชัย** — ต้องผ่าน review ผู้ใช้อัปเดตเอง และหลายเวอร์ชันอยู่พร้อมกัน → **API ห้าม breaking change**

**Keyword**

- **React Native** → React ที่เรนเดอร์เป็น native view
- **Native App** → เขียนด้วยภาษาของแพลตฟอร์มโดยตรง
- **Native View** → ชิ้นส่วน UI จริงของ OS
- **JS Thread / UI Thread** → เส้นรันโค้ด / เส้นวาดจอ
- **Bridge** → ทางข้ามระหว่างสองโลก (แบบเดิม)
- **JSI / Fabric / TurboModule** → New Architecture เรียกตรง เร็วขึ้น โหลดเมื่อใช้
- **Native Module** → ปลั๊กต่อความสามารถ OS ที่เราเขียนเอง
- **Stack / Tab / Modal** → ซ้อนหน้า / สลับโลก / ทับชั่วคราว
- **Permission** → สิทธิ์ที่ต้องขอและอาจถูกปฏิเสธถาวร
- **App Lifecycle** → foreground / background / killed
- **Cold Start** → เปิดใหม่จากศูนย์
- **Deep Link** → `myapp://` เปิดหน้าในแอป
- **Universal Link** → `https://` ที่ยืนยันโดเมนแล้ว
- **Push / Device Token** → แจ้งเตือนผ่าน APNs/FCM ด้วยที่อยู่ของเครื่อง
- **AsyncStorage** → key-value ไม่เข้ารหัส
- **Keychain / Keystore** → ตู้เซฟของ OS สำหรับ token
- **FlatList / Virtualization** → วาดเฉพาะที่เห็น
- **Hermes** → JS engine ที่เน้น startup และแรม
- **Metro** → bundler ของ RN
- **OTA Update** → อัปเดตเฉพาะ JS ไม่ผ่านสโตร์
- **App Review** → สโตร์ตรวจก่อนปล่อย
- **Staged Rollout** → ทยอยปล่อยทีละสัดส่วน
- **Force Update** → บังคับให้เลิกใช้เวอร์ชันเก่า
- **Backward Compatibility** → API เก่าต้องยังตอบแอปเก่าได้
