# PART 15 — CI/CD

> ตำแหน่งในภาพใหญ่: Delivery Layer — สะพานที่พา code จากเครื่อง developer ไปถึง Kubernetes (PART 14) และถึงมือผู้ใช้จริง โดยไม่ต้องมีใครไป deploy ด้วยมือ

---

## 1. Big Picture

ลองนึกภาพทีมที่ยังไม่มี CI/CD:

- Developer เขียน code เสร็จ → zip ไฟล์ → ส่งให้ทีม ops ทาง chat
- Ops ssh เข้า server → copy ไฟล์ทับ → restart service
- ลืม build ก่อน copy → ขึ้น production เป็น code เก่า
- ลืมรัน test → bug หลุดถึงลูกค้า
- คนที่ deploy ได้มีคนเดียว วันที่เขาลาหยุด = ทีมทั้งทีม deploy ไม่ได้
- พอพัง ไม่มีใครรู้ว่า "version ก่อนหน้า" คือไฟล์ไหน → ย้อนกลับไม่ได้

ทุกปัญหาข้างบนไม่ใช่ปัญหาเรื่อง "เขียน code ไม่เก่ง" แต่เป็นปัญหาเรื่อง **ขั้นตอนการส่งของที่พึ่งพาคน**

**CI/CD → "ระบบอัตโนมัติที่พา code จาก git ไปถึงผู้ใช้" → มีไว้เพื่อลบ "คน" ออกจากขั้นตอนที่คนทำผิดบ่อย**

แยกเป็น 2 ครึ่งชัด ๆ:

| ครึ่ง | ชื่อเต็ม | ตอบคำถามว่า |
|---|---|---|
| **CI** | Continuous Integration | "code ที่เพิ่งเขียน พังของเดิมหรือเปล่า?" |
| **CD** | Continuous Delivery / Deployment | "ของที่ผ่านแล้ว จะไปถึงผู้ใช้ยังไงให้ปลอดภัย?" |

จุดสำคัญที่ junior มักไม่เห็น: **CI/CD ไม่ใช่เครื่องมือ แต่เป็นวินัย**

Jenkins / GitHub Actions / GitLab CI / CircleCI เป็นแค่ "คนกดปุ่มแทนเรา" ถ้าทีมยังไม่เขียน test ยังไม่แยก config ออกจาก code ต่อให้ติดตั้ง Jenkins ก็ได้แค่ "ระบบอัตโนมัติที่ปล่อยของพังได้เร็วขึ้น"

**ประโยคที่ควรพูดได้ในห้องสัมภาษณ์:**

> "CI/CD ทำให้การ deploy กลายเป็นเรื่องน่าเบื่อ — และการ deploy ที่น่าเบื่อคือการ deploy ที่ดี"

**ทำไมเรื่องนี้สำคัญกับ Frontend/Full-stack Developer ที่ไม่ใช่ DevOps?**

เพราะ 3 เรื่องนี้จะตกมาที่เราเสมอ ไม่ว่าจะชอบหรือไม่:

1. **Pipeline แดงเพราะ code เรา** → เราต้องอ่าน log เป็น
2. **ขึ้น production แล้วพัง** → เราต้องรู้ว่า rollback ยังไง และต้องรู้ว่า rollback แล้ว database จะพังตามไหม
3. **Build ผ่านบนเครื่องเรา แต่ไม่ผ่านบน CI** → เราต้องรู้ว่าทำไม

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **CI** (Continuous Integration) | รวม code บ่อย ๆ + ตรวจอัตโนมัติ | ทุกครั้งที่ push จะถูก build + test ทันที เพื่อจับของพังให้เร็วที่สุด |
| **CD** (Continuous Delivery) | พร้อมปล่อยเสมอ แต่คนกดปุ่ม | ของผ่าน pipeline แล้วรอ "อนุมัติ" ก่อนขึ้น production |
| **CD** (Continuous Deployment) | ผ่านแล้วขึ้นเองอัตโนมัติ | ไม่มีปุ่มให้กด ผ่าน test = ขึ้น production เลย |
| **Pipeline** | สายพานโรงงาน | ลำดับขั้นตอนอัตโนมัติ: lint → test → build → deploy |
| **Stage / Job / Step** | ช่วง / งาน / คำสั่ง | โครงย่อยใน pipeline (stage ประกอบด้วยหลาย job, job ประกอบด้วยหลาย step) |
| **Runner / Agent** | คนงานที่ลงมือทำ | เครื่อง (หรือ container) ที่รันคำสั่งของ pipeline จริง ๆ |
| **Trigger** | ตัวจุดชนวน | เหตุที่ทำให้ pipeline เริ่มทำงาน เช่น push, pull request, tag, cron |
| **Lint** | ตรวจสไตล์ code | จับ code ผิดรูปแบบ / ตัวแปรไม่ได้ใช้ / import ซ้ำ ก่อนถึงมือคนรีวิว |
| **Test** | พิสูจน์ว่ายังทำงานถูก | unit / integration / e2e (รายละเอียดอยู่ PART 18) |
| **Build** | แปลง source เป็นของพร้อมใช้ | compile / bundle / minify ให้กลายเป็นไฟล์ที่รันได้จริง |
| **Artifact** | ของที่ build เสร็จแล้ว | ผลลัพธ์ของ build เช่น `dist/`, `.jar`, Docker Image — สิ่งที่จะถูกเอาไป deploy |
| **Docker Build** | แพ็ค artifact ลงกล่อง | สร้าง Docker Image จาก Dockerfile ให้รันเหมือนกันทุกที่ |
| **Registry** | โกดังเก็บ Image | ที่เก็บ Docker Image เช่น Docker Hub, ECR, GCR, GitLab Registry |
| **Tag** | ป้ายชื่อ version ของ Image | ตัวระบุ version เช่น `app:1.4.2` หรือ `app:<git-sha>` |
| **Environment** | สนามซ้อม / สนามจริง | Development, Staging, Production |
| **Deployment** | เอาของไปวางให้ใช้จริง | ขั้นตอนที่ artifact ถูกนำไปรันใน environment ปลายทาง |
| **Rollback** | ถอยกลับ version เดิม | ย้อนกลับไป version ก่อนหน้าที่รู้ว่าใช้ได้ |
| **Blue-Green** | สลับสวิตช์ทั้งก้อน | รัน 2 ชุดคู่กัน แล้วสลับ traffic ไปชุดใหม่ทีเดียว |
| **Canary** | ปล่อยทีละนิดแล้วดูอาการ | ส่ง traffic ส่วนน้อย (เช่น 5%) ไป version ใหม่ก่อน |
| **Smoke Test** | เช็กชีพจรหลัง deploy | test สั้น ๆ หลัง deploy ว่าระบบยังหายใจอยู่ |
| **Promote** | เลื่อนขั้นของชิ้นเดิม | เอา artifact ตัวเดียวกันเลื่อนจาก staging → production |
| **Secret** | ของลับใน pipeline | password / token / key ที่ pipeline ต้องใช้ แต่ห้ามโผล่ใน log |
| **Migration** | คำสั่งแก้โครงสร้าง database | script ที่เปลี่ยน schema เช่น เพิ่ม column |
| **Feature Flag** | สวิตช์เปิด/ปิด feature | แยก "deploy code" ออกจาก "เปิดให้ผู้ใช้เห็น" |
| **Idempotent** | ทำซ้ำแล้วผลเหมือนเดิม | รัน deploy ซ้ำ 3 รอบต้องได้ผลเท่ารอบเดียว |

## 3. Mental Model

### 3.1 มองเป็น "ด่านกรอง" ที่แคบลงเรื่อย ๆ

```
[ code ทุกบรรทัดที่เขียน ]
            ↓  ด่าน 1: Lint      (เร็วมาก, จับเรื่องผิว)
[ code ที่รูปแบบถูก ]
            ↓  ด่าน 2: Unit Test (เร็ว, จับ logic ผิด)
[ code ที่ logic ถูก ]
            ↓  ด่าน 3: Build     (จับ compile/type error)
[ artifact ที่รันได้ ]
            ↓  ด่าน 4: Integration/E2E (ช้า, จับการต่อกันผิด)
[ artifact ที่ไว้ใจได้ ]
            ↓  ด่าน 5: Staging   (จับเรื่อง config/environment)
[ ของที่พร้อมขึ้นจริง ]
            ↓
     [ PRODUCTION ]
```

ให้มองภาพนี้ว่า pipeline คือตะแกรงหลายชั้นที่รูเล็กลงเรื่อย ๆ ชั้นบนสุดต้องเร็วและจับของเสียง่าย ๆ ให้หมดก่อน เพื่อไม่ให้ของเสียไปกินเวลาชั้นล่างที่แพงกว่า

**กฎที่ได้จากภาพนี้: เรียง test จาก "เร็วและถูก" ไป "ช้าและแพง" เสมอ**

ถ้าเอา e2e test 20 นาทีไว้หน้าสุด แล้ว lint ไว้หลังสุด ทุกคนในทีมจะรอ 20 นาทีเพื่อรู้ว่า "ลืมใส่ semicolon"

### 3.2 Mental Model หลัก: Build Once, Promote Many

นี่คือหลักคิดที่แยก junior ออกจาก senior ได้ชัดที่สุดในบทนี้

**แบบที่ผิด (build ใหม่ทุก environment):**

```
git commit abc123
      ├── build → deploy → Development
      ├── build → deploy → Staging      ← คนละ binary กัน!
      └── build → deploy → Production   ← คนละ binary กัน!
```

ให้มองภาพนี้ว่าเราทดสอบขนมชิ้นหนึ่งจนมั่นใจ แล้วกลับไปอบชิ้นใหม่ให้ลูกค้ากิน — สิ่งที่เราทดสอบกับสิ่งที่ลูกค้าได้รับ ไม่ใช่ชิ้นเดียวกัน

**แบบที่ถูก (build ครั้งเดียว แล้ว promote):**

```
git commit abc123
      ↓
   BUILD (ครั้งเดียว)
      ↓
  Image: app:abc123        ← ของชิ้นนี้ชิ้นเดียว ตลอดทาง
      ↓
   Development  (config ของ dev)
      ↓ promote (ตัวเดิม)
   Staging      (config ของ staging)
      ↓ promote (ตัวเดิม)
   Production   (config ของ prod)
```

ให้มองภาพนี้ว่าเราอบขนมชิ้นเดียว แล้วยกชิ้นนั้นเดินผ่านห้องชิม ห้องตรวจ แล้วถึงมือลูกค้า — ทุกคนกินขนมชิ้นเดียวกัน ต่างกันแค่จานที่ใส่

**ทำไมเรื่องนี้สำคัญมาก:**

ถ้า build ใหม่ทุก environment แปลว่าอาจมีความต่างเกิดขึ้นได้จาก:

- `npm install` ดึง dependency version ใหม่กว่าเดิม (ถ้าไม่ล็อกไว้)
- base image `node:20` ถูกอัปเดตระหว่างนั้น
- เครื่อง runner คนละเครื่อง environment ต่างกัน

ผลคือ **"staging ผ่าน แต่ production พัง"** ซึ่งเป็นปัญหาที่หาสาเหตุยากที่สุดประเภทหนึ่ง เพราะเราไม่ได้เทียบของชิ้นเดียวกัน

**สิ่งที่เปลี่ยนได้ระหว่าง environment คือ config เท่านั้น ไม่ใช่ binary**

### 3.3 Config ต้องอยู่นอก Image

```
[ Docker Image ]  = code + dependency + runtime   (เหมือนกันทุก env)
          +
[ Config/Secret ] = URL, key, flag                 (ต่างกันตาม env)
          ↓
   [ Running App ใน environment นั้น ]
```

ให้มองภาพนี้ว่า Image คือเครื่องใช้ไฟฟ้ารุ่นเดียวกันที่ขายทั่วโลก ส่วน config คือปลั๊กแปลงที่เปลี่ยนตามประเทศที่เอาไปเสียบ

ในโลก Kubernetes (PART 14) config มาจาก **ConfigMap** และ **Secret** ซึ่ง inject เข้าเป็น environment variable ตอน Pod รัน — Image ไม่รู้เลยว่าตัวเองอยู่ env ไหน

**สัญญาณอันตรายที่เจอบ่อย:** มีไฟล์ `Dockerfile.prod` แยกจาก `Dockerfile.staging` → แปลว่าของที่ทดสอบกับของที่ขึ้นจริงไม่ใช่ตัวเดียวกันแล้ว

### 3.4 Deploy ≠ Release

```
DEPLOY  = เอา code ขึ้นไปวางบน production server
RELEASE = เปิดให้ผู้ใช้เห็น feature นั้นจริง ๆ
```

สองอย่างนี้แยกออกจากกันได้ด้วย **Feature Flag** — deploy code ที่มี feature ใหม่ขึ้นไปก่อน แต่ปิดสวิตช์ไว้ พอพร้อมค่อยเปิดให้ทีละกลุ่ม

ประโยชน์: ถ้า feature มีปัญหา เราแค่ **ปิดสวิตช์** (ใช้เวลาเป็นวินาที) แทนที่จะต้อง rollback ทั้ง deployment (ใช้เวลาเป็นนาที และกระทบ feature อื่นที่ขึ้นมาพร้อมกัน)

## 4. ภาพจำ

```
🧠 ภาพจำหลัก:
CI/CD = สายพานโรงงาน

Developer = คนออกแบบสินค้า
CI        = แผนก QC ต้นสาย (ตรวจก่อนของขึ้นสายพาน)
Artifact  = สินค้าที่แพ็คกล่องแล้ว มีหมายเลขล็อต
Registry  = โกดังเก็บสินค้า
CD        = รถขนส่งที่ส่งของถึงหน้าร้าน
Production= หน้าร้านที่ลูกค้าเดินเข้ามาซื้อ
Rollback  = เรียกคืนล็อตนี้ แล้วเอาล็อตเก่ากลับขึ้นชั้น
```

```
     Developer
         ↓
   [ CI = QC ต้นสาย ]
         ↓ ผ่าน
   [ กล่องสินค้ามีเลขล็อต ]
         ↓
   [ CD = รถส่งของ ]
         ↓
     [ หน้าร้าน ]
```

ให้มองภาพนี้ว่าโรงงานที่ดีจะไม่มีวันปล่อยของออกจากสายพานโดยไม่ผ่าน QC และจะรู้เสมอว่าสินค้าในร้านตอนนี้เป็นล็อตหมายเลขอะไร

**ภาพจำย่อยที่ต้องจำคู่กัน:**

```
🧠 Build Once, Promote Many
= อบขนมชิ้นเดียว แล้วยกชิ้นนั้นเดินผ่านทุกห้อง
  ไม่ใช่อบใหม่ทุกห้อง
```

```
🧠 Blue-Green vs Canary
Blue-Green = สับสวิตช์ไฟทั้งห้องทีเดียว (ทุกคนเห็นของใหม่พร้อมกัน)
Canary     = เปิดไฟทีละดวง แล้วดูว่ามีใครบ่นไหม
```

```
🧠 Environment
Development = ห้องซ้อมของเราคนเดียว (พังได้ ไม่มีใครเดือดร้อน)
Staging     = เวทีซ้อมใหญ่ที่เหมือนของจริงทุกอย่าง
Production  = เวทีจริง มีคนดู มีคนจ่ายเงิน
```

```
🧠 Secret ใน CI
= กุญแจบ้านที่ให้คนส่งของยืม
ต้องยืมได้ชั่วคราว, ใช้ได้เฉพาะประตูที่จำเป็น, และห้ามถ่ายรูปลง log
```

## 5. How It Works

### 5.1 Flow หลักที่ต้องจำให้ขึ้นใจ

```
Developer
    ↓  (เขียน code เสร็จ)
Git Push
    ↓  (trigger)
   CI
    ↓
  Test
    ↓
 Build
    ↓
Docker Image
    ↓  (push)
Registry
    ↓  (pull)
Kubernetes
    ↓
Production
```

ให้มองภาพนี้ว่า code ของเราเดินทางเป็นเส้นตรงเส้นเดียวจากคีย์บอร์ดไปถึงผู้ใช้ และทุกจุดบนเส้นนี้มีระบบตรวจแทนคนอยู่

### 5.2 ขยายภาพ: อะไรเกิดขึ้นในแต่ละกล่อง

```
[1] Developer push branch  →  เปิด Pull Request
                                     ↓
[2] CI TRIGGER
      ├── Install dependency (ใช้ cache ถ้ามี)
      ├── Lint            (~30 วินาที)
      ├── Type check      (~1 นาที)
      ├── Unit test       (~2 นาที)
      └── Build           (~3 นาที)
                                     ↓
              ผ่านทั้งหมด? ── ไม่ผ่าน → แจ้ง developer + บล็อก merge
                    │ ผ่าน
                    ↓
[3] MERGE เข้า main
                    ↓
[4] CD TRIGGER (จาก main เท่านั้น)
      ├── Docker Build → Image: app:<git-sha>
      ├── Push เข้า Registry
      ├── Deploy ไป Staging (ใช้ config staging)
      ├── Smoke Test + E2E บน staging
      └── รออนุมัติ (Continuous Delivery)
          หรือไปต่อเลย (Continuous Deployment)
                    ↓
[5] DEPLOY PRODUCTION
      ├── Database Migration (แบบเข้ากันได้กับ version เก่า)
      ├── kubectl set image / apply manifest
      ├── Rolling Update ทีละ Pod (PART 14)
      ├── Health Check ผ่านถึงจะรับ traffic
      └── Smoke Test บน production
                    ↓
[6] MONITOR
      ├── Error rate สูงขึ้น? → ROLLBACK
      └── ปกติ → จบงาน
```

ให้มองภาพนี้ว่าก่อน merge เราตรวจ "ตัว code" แต่หลัง merge เราตรวจ "ตัวของที่แพ็คแล้ว" — เป็นคนละคำถามและคนละความเสี่ยงกัน

### 5.3 Artifact เดินทางอย่างไร (ภาพที่ต้องวาดได้ในห้องสัมภาษณ์)

```
   git sha: abc123
        ↓
   docker build -t app:abc123 .
        ↓
   docker push registry/app:abc123
        ↓
   ┌───────── REGISTRY (app:abc123) ─────────┐
   │                                          │
   ↓              ↓                ↓
 Staging      Production        Rollback ย้อนมาใช้ได้ทุกเมื่อ
(config A)    (config B)
```

ให้มองภาพนี้ว่า Registry คือคลังสินค้ากลางที่เก็บของทุกล็อตไว้ ทำให้เราหยิบล็อตเก่ากลับมาขายใหม่ได้ทันทีเมื่อล็อตใหม่มีปัญหา

**นี่คือเหตุผลว่าทำไม tag Image ด้วย `latest` อย่างเดียวถึงเป็นความผิดพลาดร้ายแรง** — ถ้าทุกอันชื่อ `latest` เราจะไม่รู้เลยว่า "ของที่รันอยู่บน production ตอนนี้คือ commit ไหน" และจะ rollback กลับไปหาอะไรก็ไม่รู้

ควร tag ด้วยสิ่งที่ **ไม่ซ้ำและสาวกลับได้**: `app:abc123` (git sha) หรือ `app:1.4.2`

### 5.4 Rollback ทำงานยังไง

```
ตอนนี้: Production รัน app:v5  → error rate พุ่ง
                 ↓
   สั่ง rollback (kubectl rollout undo / deploy tag เก่า)
                 ↓
   Kubernetes ดึง app:v4 จาก Registry
                 ↓
   Rolling Update ย้อนกลับทีละ Pod
                 ↓
ตอนนี้: Production รัน app:v4  → error rate ปกติ
```

ให้มองภาพนี้ว่า rollback คือการเปลี่ยน "ใบสั่ง" ให้ชี้กลับไปที่ของล็อตเก่าที่ยังอยู่ในโกดัง ไม่ใช่การสร้างของใหม่

**ข้อควรระวังที่สำคัญที่สุดของ rollback:** rollback ย้อนได้แค่ **code** แต่ **ย้อน database ไม่ได้ง่าย ๆ**

ถ้า migration ของ v5 ลบ column ทิ้ง แล้วเรา rollback กลับไป v4 ที่ยังอ่าน column นั้นอยู่ → ระบบพังหนักกว่าเดิม นี่คือเหตุผลของข้อถัดไป

### 5.5 Database Migration ที่เข้ากันได้ทั้งเวอร์ชันเก่าและใหม่

ระหว่าง Rolling Update จะมีช่วงหนึ่งที่ **code เก่ากับ code ใหม่รันพร้อมกัน** และคุยกับ database ตัวเดียวกัน

```
ช่วงกลางของ deploy:

[ Pod v4 (code เก่า) ]  ┐
                        ├──→ [ DATABASE ตัวเดียวกัน ]
[ Pod v5 (code ใหม่) ]  ┘
```

ให้มองภาพนี้ว่าระหว่างเปลี่ยนกะ จะมีช่วงที่พนักงานกะเก่ากับกะใหม่ทำงานอยู่ในห้องเดียวกัน — ของในห้องต้องใช้ได้กับทั้งสองกะ

ดังนั้น migration ต้องออกแบบแบบ **expand → migrate → contract**:

| ขั้น | ทำอะไร | code เก่ายังทำงานได้ไหม |
|---|---|---|
| **1. Expand** | เพิ่ม column ใหม่ (nullable) ไม่ลบของเก่า | ได้ (มันไม่รู้จัก column ใหม่ ก็ไม่แตะ) |
| **2. Deploy code ใหม่** | code ใหม่เขียนทั้ง column เก่าและใหม่ | ได้ |
| **3. Backfill** | ย้ายข้อมูลเก่าเข้า column ใหม่ | ได้ |
| **4. Deploy code ที่ใช้ column ใหม่อย่างเดียว** | เลิกเขียน column เก่า | (เริ่มเลิกใช้) |
| **5. Contract** | ลบ column เก่าทิ้ง — **หลังจากมั่นใจว่าไม่ rollback แล้วเท่านั้น** | ไม่ได้แล้ว |

**กฎเหล็ก:** อย่าทำ step 1 กับ step 5 ใน deploy เดียวกัน

**สิ่งที่ห้ามทำเด็ดขาดใน migration เดียวกับที่ deploy code:**

- `DROP COLUMN` / `RENAME COLUMN` — ทำให้ code เก่าที่ยังรันอยู่พังทันที
- เพิ่ม `NOT NULL` โดยไม่มี default — insert ของ code เก่าจะ error
- migration ที่ล็อกตารางใหญ่นาน ๆ — ทำให้ request ทั้งระบบค้าง

### 5.6 Blue-Green และ Canary

**Blue-Green:**

```
ก่อนสลับ:
  Traffic 100% → [ BLUE: v4 ]
                 [ GREEN: v5 ]  ← รันแล้ว แต่ยังไม่มี traffic (ทดสอบได้)

หลังสลับ:
  Traffic 100% → [ GREEN: v5 ]
                 [ BLUE: v4 ]   ← เก็บไว้เฉย ๆ เผื่อต้องสลับกลับ
```

ให้มองภาพนี้ว่าเราเตรียมร้านสาขาใหม่ให้พร้อมเปิดทุกอย่าง แล้วค่อยย้ายป้ายบอกทางทั้งหมดมาที่สาขาใหม่ทีเดียว ถ้าไม่ดีก็ย้ายป้ายกลับ

**Canary:**

```
ขั้นที่ 1:  Traffic  95% → [ v4 ]      5% → [ v5 ]   ← ดู error rate 10 นาที
ขั้นที่ 2:  Traffic  75% → [ v4 ]     25% → [ v5 ]   ← ดูต่อ
ขั้นที่ 3:  Traffic  50% → [ v4 ]     50% → [ v5 ]
ขั้นที่ 4:  Traffic   0% → [ v4 ]    100% → [ v5 ]   ← เสร็จ
```

ให้มองภาพนี้ว่าเราให้ลูกค้ากลุ่มเล็ก ๆ ลองชิมเมนูใหม่ก่อน ถ้าไม่มีใครท้องเสียค่อยขยายให้ทั้งร้าน

**ที่มาของชื่อ Canary:** สมัยก่อนคนงานเหมืองเอานกคานารีลงไปด้วย ถ้านกเป็นลม แปลว่ามีแก๊สพิษ ให้รีบขึ้น — นกตัวเล็กเสี่ยงแทนคนทั้งทีม

## 6. Example

### 6.1 Scenario: ทีม 6 คน ทำเว็บ e-commerce (React + Node + PostgreSQL บน Kubernetes)

**สถานการณ์ตั้งต้น (ก่อนมี CI/CD):**

ทีม deploy สัปดาห์ละครั้ง ทุกวันศุกร์ตอน 4 ทุ่ม ใช้เวลา 2 ชั่วโมง มี 1 คนที่ทำเป็น และเดือนที่แล้วพัง 2 ครั้ง

**ปัญหาที่แท้จริงไม่ใช่ "เขา deploy ช้า" แต่คือ "deploy แล้วเสี่ยง เลยต้องสะสมของไว้ deploy ทีเดียว ซึ่งยิ่งทำให้เสี่ยงขึ้นไปอีก"** — วงจรนี้เรียกว่า deploy ใหญ่ = เสี่ยงมาก = deploy ถี่ไม่ได้ = ยิ่งต้องใหญ่

**สิ่งที่ทีมทำ ทีละขั้น:**

**ขั้นที่ 1 — ทำ CI ก่อน CD (สำคัญมาก)**

ตั้ง pipeline ที่รันทุก pull request:

```
PR เปิด → lint → type check → unit test → build
         ผ่านหมด = merge ได้ / ไม่ผ่าน = ปุ่ม merge ถูกล็อก
```

ให้มองภาพนี้ว่าเราติดเครื่องสแกนที่ประตูทางเข้า main branch — ของที่ไม่ผ่านสแกนจะเข้าไม่ได้ ไม่ว่าใครจะเป็นคนถือ

ผลภายในเดือนแรก: bug ที่เคยหลุดถึง staging ลดลงชัดเจน เพราะ 6 คนไม่ต้องคอยเตือนกันเรื่องเดิม ๆ อีก

**ขั้นที่ 2 — ทำ artifact ให้มีตัวตน**

เปลี่ยนจาก "ssh ไป git pull แล้ว npm run build บน server" เป็น:

```
build ครั้งเดียว → docker build -t shop-api:<git-sha> → push เข้า registry
```

ตอนนี้ทุก commit บน main มี Image ของตัวเองเก็บอยู่ในโกดัง → rollback กลายเป็นเรื่องง่ายทันที

**ขั้นที่ 3 — แยก config ออกจาก image**

ก่อนหน้านี้มี `config.prod.js` ติดอยู่ใน repo (และมี password อยู่ในนั้นด้วย)

เปลี่ยนเป็น:

| ค่า | เก็บที่ไหน |
|---|---|
| `DATABASE_URL` | Kubernetes Secret ของแต่ละ namespace |
| `PAYMENT_API_KEY` | Secret Manager ภายนอก แล้ว sync เข้ามา |
| `FEATURE_NEW_CHECKOUT` | ConfigMap (เปลี่ยนได้โดยไม่ต้อง build ใหม่) |
| `LOG_LEVEL` | ConfigMap |

**ขั้นที่ 4 — staging ที่เหมือน production จริง ๆ**

จุดที่ทีมเคยพลาด: staging ใช้ SQLite แต่ production ใช้ PostgreSQL → query ที่ผ่านบน staging ไป error บน production

แก้โดยให้ staging ใช้ database engine เดียวกัน version เดียวกัน และมี seed data ที่มีหน้าตาคล้ายของจริง (แต่ไม่ใช่ข้อมูลลูกค้าจริง — ต้อง anonymize)

**ขั้นที่ 5 — deploy production แบบ canary**

```
merge เข้า main
      ↓
build image: shop-api:9f2c1a
      ↓
deploy staging → e2e ผ่าน
      ↓
deploy production แบบ canary 10%
      ↓
เฝ้า error rate + latency 15 นาที (อัตโนมัติ)
      ↓
ปกติ → ขยายเป็น 100%
ผิดปกติ → rollback อัตโนมัติ
```

ให้มองภาพนี้ว่าเราไม่ได้เชื่อ test อย่างเดียว แต่เชื่อ "ผู้ใช้จริงจำนวนน้อย" เป็นด่านสุดท้ายด้วย

**ผลลัพธ์หลัง 3 เดือน:**

| ตัวชี้วัด | ก่อน | หลัง |
|---|---|---|
| ความถี่ deploy | สัปดาห์ละ 1 | วันละหลายครั้ง |
| เวลาที่ใช้ deploy | 2 ชั่วโมง (คนทำ) | 12 นาที (อัตโนมัติ) |
| เวลาในการ rollback | ~40 นาที | ~2 นาที |
| จำนวนคนที่ deploy ได้ | 1 | ทุกคนในทีม |
| ขนาดของแต่ละ deploy | 40+ commits | 1-3 commits |

**ข้อสังเกตระดับ senior:** ตัวเลขที่สำคัญที่สุดในตารางนี้ไม่ใช่ "เร็วขึ้น" แต่คือ **"ขนาดของแต่ละ deploy เล็กลง"** เพราะ deploy ที่มี 2 commits เวลาพังจะหาสาเหตุเจอใน 5 นาที ส่วน deploy ที่มี 40 commits เวลาพังจะหาทั้งคืน

### 6.2 Scenario ย่อย: เคสจริงที่ pipeline ทำร้ายทีม

ทีมหนึ่งมี pipeline ที่ใช้เวลา **45 นาที** ต่อ 1 PR

ผลที่ตามมาโดยที่ไม่มีใครตั้งใจ:

- คนเริ่ม "รวมงานหลายอย่างใน PR เดียว" เพื่อไม่ต้องรอหลายรอบ → PR ใหญ่ขึ้น → review ยากขึ้น → bug หลุดมากขึ้น
- คนเริ่มขอสิทธิ์ "skip CI" ตอนรีบ → ด่านกรองหายไปตอนที่เสี่ยงที่สุด
- คน push แล้วไปทำอย่างอื่น พอ pipeline แดงกลับมาดูอีกทีคือ 2 ชั่วโมงถัดมา → context หายหมด

**บทเรียนระดับ senior: pipeline ต้องเร็วพอที่คนจะไม่หาทางข้ามมัน**

Pipeline ที่ช้าไม่ได้แค่ "เสียเวลา" แต่มัน **บิดพฤติกรรมของทีมให้แย่ลง** ซึ่งอันตรายกว่ามาก

วิธีที่ทีมนี้ใช้ลดเวลาจาก 45 → 9 นาที:

| วิธี | ประหยัดได้ |
|---|---|
| Cache dependency (`node_modules`, layer ของ Docker) | มาก |
| รัน lint / test / type check **แบบขนาน** แทนที่จะเรียงกัน | มาก |
| แยก e2e ออกไปรันหลัง merge แทนที่จะรันทุก PR | มาก |
| รัน test เฉพาะส่วนที่เปลี่ยน (ใน monorepo) | ปานกลาง |
| ใช้ runner ที่แรงขึ้น | ปานกลาง |

## 7. Compare

### 7.1 Continuous Delivery vs Continuous Deployment (คำถามยอดฮิต)

| หัวข้อ | Continuous **Delivery** | Continuous **Deployment** |
|---|---|---|
| หลัง test ผ่าน | ของพร้อมขึ้น **รอคนกดปุ่ม** | **ขึ้น production เอง** ทันที |
| มี manual approval ไหม | มี | ไม่มี |
| เหมาะกับ | ระบบที่มีข้อบังคับ เช่น การเงิน / ต้องนัดเวลากับ business | ทีมที่ test แน่น + monitoring ดี + rollback เร็ว |
| ความเสี่ยง | ของค้างในคิวนาน สะสมเป็น deploy ใหญ่ | ถ้า test ไม่แน่นพอ bug ถึงผู้ใช้ทันที |
| เงื่อนไขที่ต้องมีก่อน | test พอประมาณ | test ครอบคลุม + auto rollback + observability ดี |

> **ตอบสั้นในห้องสัมภาษณ์:** "ต่างกันที่ปุ่มอนุมัติปุ่มเดียว — Delivery คือ 'พร้อมขึ้นเสมอ' ส่วน Deployment คือ 'ขึ้นเองเสมอ'"

### 7.2 CI vs CD

| หัวข้อ | CI | CD |
|---|---|---|
| ตอบคำถามว่า | "code นี้พังของเดิมไหม" | "จะพาของไปถึงผู้ใช้ยังไงให้ปลอดภัย" |
| ทำงานตอนไหน | ทุก push / ทุก PR | หลัง merge เข้า main |
| ผลลัพธ์ | ผ่าน/ไม่ผ่าน + artifact | ระบบที่รัน version ใหม่ |
| ถ้าไม่มี | ของพังเข้า main แล้วทุกคนเดือดร้อน | deploy ด้วยมือ ช้า ผิดพลาดง่าย ย้อนยาก |
| ทำก่อน | **ควรทำก่อนเสมอ** | ทำหลังจาก CI นิ่งแล้ว |

### 7.3 Blue-Green vs Canary vs Rolling Update

| หัวข้อ | Rolling Update | Blue-Green | Canary |
|---|---|---|---|
| วิธี | เปลี่ยน Pod ทีละตัว | รัน 2 ชุด สลับ traffic ทีเดียว | ส่ง traffic บางส่วนไป version ใหม่ |
| ใช้ทรัพยากร | เพิ่มเล็กน้อย | **2 เท่า** ช่วงหนึ่ง | เพิ่มเล็กน้อย |
| ความเร็วในการ rollback | ปานกลาง (ต้องม้วนกลับทีละตัว) | **เร็วที่สุด** (สลับ traffic กลับ) | เร็ว (ดึง % กลับเป็น 0) |
| ผู้ใช้ที่เจอ bug ถ้าพัง | บางส่วนแล้วขยายขึ้น | **ทุกคนพร้อมกัน** | **น้อยที่สุด** |
| ความซับซ้อน | ต่ำ (K8s ทำให้ฟรี) | ปานกลาง | สูง (ต้องมี traffic routing + metrics) |
| เหมาะเมื่อ | ระบบทั่วไป ค่าเริ่มต้นที่ดี | ต้องการ rollback ทันทีและมีงบ resource | feature เสี่ยงสูง / ระบบมีผู้ใช้เยอะ |
| ข้อควรระวัง | มีช่วงที่ 2 version รันพร้อมกัน | ต้องจัดการ database/session ตอนสลับ | ต้องมี monitoring ที่เชื่อถือได้ ไม่งั้นไม่รู้ว่าควรขยายหรือถอย |

**ไม่มีอันไหน "ดีกว่า" แบบลอย ๆ:**

- Rolling Update ดีกว่าเมื่อ **ทีมยังไม่มี monitoring ที่ดีพอ** และอยากได้ของที่ K8s ทำให้ฟรี
- Blue-Green ดีกว่าเมื่อ **ต้องการความสามารถในการย้อนกลับภายในไม่กี่วินาที** และยอมจ่ายค่า resource 2 เท่าได้
- Canary ดีกว่าเมื่อ **มีผู้ใช้จำนวนมากพอที่ 5% จะให้สัญญาณที่มีความหมาย** และมี metrics ที่เชื่อถือได้

### 7.4 Environment 3 ชั้น

| หัวข้อ | Development | Staging | Production |
|---|---|---|---|
| ใครใช้ | developer | ทีม + QA + บางที stakeholder | ผู้ใช้จริง |
| ข้อมูล | ปลอม / น้อย | คล้ายของจริง (ต้อง anonymize) | ข้อมูลจริง |
| พังได้ไหม | ได้ตลอด | ได้ แต่ควรแจ้งทีม | **ห้าม** |
| ควรเหมือน production แค่ไหน | ไม่ต้องมาก | **ให้เหมือนที่สุด** | — |
| deploy บ่อยแค่ไหน | ตลอดเวลา | ทุก merge | ตามนโยบายทีม |
| Secret | ค่าปลอม | ค่าของ staging (แยกจาก prod) | ค่าจริง เข้าถึงได้จำกัดที่สุด |

**กฎที่ senior ย้ำเสมอ:** staging ที่ไม่เหมือน production คือ staging ที่ให้ความมั่นใจปลอม ๆ — และความมั่นใจปลอมอันตรายกว่าไม่มี staging เลย

### 7.5 Artifact vs Image vs Release

| คำ | คืออะไร | ตัวอย่าง |
|---|---|---|
| **Artifact** | ผลลัพธ์ของ build ที่เก็บไว้ได้ | `dist/`, `app.jar`, `.apk` |
| **Docker Image** | artifact ชนิดหนึ่งที่รวม runtime ไว้ด้วย | `shop-api:9f2c1a` |
| **Release** | การประกาศว่า version นี้ให้ผู้ใช้ใช้แล้ว | `v1.4.0` ที่เปิด feature flag แล้ว |

### 7.6 Monorepo vs Multi-repo ในมุม CI/CD

| หัวข้อ | Monorepo | Multi-repo |
|---|---|---|
| Pipeline | ซับซ้อนกว่า ต้องตรวจว่าอะไรเปลี่ยนแล้ว build เฉพาะส่วนนั้น | ง่ายกว่า แต่ละ repo มี pipeline ของตัวเอง |
| แก้ของที่ใช้ร่วมกัน | แก้ที่เดียว ทุกที่ได้พร้อมกัน | ต้องปล่อย version แล้วไล่อัปเดตทีละ repo |
| เวลา build | เสี่ยงช้าถ้าไม่ทำ selective build | เร็วโดยธรรมชาติ |
| ดีกว่าเมื่อ | ทีมใหญ่ที่ต้องแก้ข้าม service บ่อย | service แยกขาดจากกันจริง ๆ ปล่อย version อิสระ |

## 8. Common Mistakes

### ❌ 1. build ใหม่ทุก environment

**ที่ผิด:** staging build จาก main, production build จาก tag → คนละ binary
**ที่ถูก:** build ครั้งเดียว ได้ image tag เดียว แล้ว promote ตัวเดิมไปทุก environment
**ผลถ้าไม่แก้:** เจอปัญหา "staging ผ่าน production พัง" ที่หาสาเหตุไม่เจอ

### ❌ 2. tag image ว่า `latest` อย่างเดียว

**ที่ผิด:** `docker push app:latest` แล้วจบ
**ที่ถูก:** tag ด้วย git sha หรือ semantic version เสมอ (`latest` มีเพิ่มได้ แต่ห้ามใช้ตัวเดียว)
**ผลถ้าไม่แก้:** ไม่รู้ว่า production รัน commit ไหน + rollback ไม่ได้ + `latest` วันนี้กับเมื่อวานไม่ใช่ของเดียวกัน

### ❌ 3. เอา secret ใส่ใน Dockerfile / repo / build arg

**ที่ผิด:** `ENV API_KEY=sk_live_xxxx` ใน Dockerfile หรือ commit ไฟล์ `.env` เข้า git
**ที่ถูก:** ใส่ตอน runtime ผ่าน Secret ของ K8s หรือ secret store
**ผลถ้าไม่แก้:** key ติดอยู่ใน layer ของ image ถาวร ใครที่ pull image ได้ = อ่าน key ได้ และ git history ลบยากมาก

### ❌ 4. คิดว่า secret ใน CI ปลอดภัยโดยอัตโนมัติ

ต้องจำ 3 เรื่องนี้:

- CI มักจะ **mask** secret ใน log ให้ แต่ถ้าเรา `echo $TOKEN | base64` หรือพิมพ์ออกมาแบบแปลงรูป มันจะ mask ไม่ทัน
- **Pull request จาก fork ไม่ควรเห็น secret** — ไม่งั้นใครก็เปิด PR ที่พิมพ์ secret ออกมาได้
- secret ควรมี **อายุสั้น** และ **สิทธิ์แคบ** ที่สุด (ปัจจุบันนิยมให้ CI แลก token ชั่วคราวกับ cloud ผ่าน OIDC แทนการเก็บ key ถาวร)

### ❌ 5. deploy พร้อม migration ที่ทำลายของเก่า

**ที่ผิด:** deploy code ใหม่ + `DROP COLUMN old_name` ใน migration เดียวกัน
**ที่ถูก:** expand → deploy → backfill → deploy → contract (แยกหลาย release)
**ผลถ้าไม่แก้:** rollback ไม่ได้เลย และระหว่าง rolling update Pod เก่าจะ error ทันที

### ❌ 6. คิดว่า "test ผ่าน = ปลอดภัย" แล้วไม่ต้อง monitor

Test บอกได้แค่ว่า "สิ่งที่เรานึกออกว่าจะพัง ไม่พัง" แต่ production พังจากสิ่งที่เราไม่ได้นึกถึงเสมอ (traffic จริง, ข้อมูลจริงที่หน้าตาแปลก, network จริง)

**ที่ถูก:** หลัง deploy ต้องมี smoke test + เฝ้า error rate/latency อย่างน้อย 15-30 นาที

### ❌ 7. ทำ CD ก่อนที่ CI จะนิ่ง

ถ้า test ยังไม่ครอบคลุม แล้วเปิด auto-deploy ขึ้น production = สร้าง "ท่อส่ง bug อัตโนมัติ" ที่ทำงานเร็วมาก

**ลำดับที่ถูก:** test ให้พอ → CI นิ่ง → CD ไป staging → CD ไป production (แบบมี approval) → ค่อยพิจารณาตัด approval ออก

### ❌ 8. pipeline ที่ flaky แล้วปล่อยไว้

Flaky test = test ที่บางทีผ่าน บางทีไม่ผ่าน ทั้งที่ code ไม่เปลี่ยน

สิ่งที่เกิดขึ้นจริงเมื่อปล่อยไว้: ทุกคนจะเรียนรู้ว่า "แดงแล้วกด re-run ไปเรื่อย ๆ เดี๋ยวก็เขียว" → **pipeline สูญเสียความหมายทั้งระบบ** เพราะไม่มีใครเชื่อว่าสีแดงแปลว่ามีปัญหาจริง

**ที่ถูก:** flaky test ต้องถือเป็น bug ระดับเดียวกับ bug production — แก้ หรือถอดออกชั่วคราวพร้อมตั๋วติดตาม อย่าปล่อยให้อยู่กลาง ๆ

### ❌ 9. deploy วันศุกร์ตอนเย็นโดยไม่มีคนเฝ้า

ไม่ใช่เพราะวันศุกร์มีเวทมนตร์ แต่เพราะ **ถ้าพังตอนไม่มีคนอยู่ จะไม่มีใครกด rollback**

**หลักที่ถูกกว่า "ห้าม deploy วันศุกร์":** deploy เมื่อไรก็ได้ ถ้ามีคนพร้อมดูแลอีก 1-2 ชั่วโมงหลังจากนั้น

### ❌ 10. ลืมว่า pipeline ก็คือ production ระบบหนึ่ง

Pipeline มีสิทธิ์ deploy ขึ้น production มี secret มีสิทธิ์เข้า registry — ถ้าใครยึด pipeline ได้ เขาแทบจะยึดระบบทั้งหมดได้

**ที่ถูก:** จำกัดสิทธิ์ของ runner, ตรวจ script ที่ดึงมาจากภายนอก, ล็อก version ของ action/plugin ที่ใช้ (อย่าชี้ไปที่ branch ลอย ๆ)

## 9. Debugging

### 9.1 ลำดับการไล่ปัญหา "pipeline แดง"

```
[1] แดงที่ stage ไหน?
        ↓
[2] lint/type/test/build/deploy — ดู log บรรทัดแรกที่ error ไม่ใช่บรรทัดสุดท้าย
        ↓
[3] เกิดกับทุกคนหรือเฉพาะ branch เรา?
        ↓
[4] รันคำสั่งเดียวกันบนเครื่องตัวเองได้ผลเหมือนกันไหม?
        ↓
[5] ถ้าเครื่องเราผ่านแต่ CI ไม่ผ่าน → หา "ความต่างของ environment"
        ↓
[6] re-run แล้วหายไหม? → ถ้าหาย = flaky (ต้องแก้ ไม่ใช่ปล่อย)
```

ให้มองภาพนี้ว่าการไล่ pipeline แดงคือการหาจุดที่ "สายพานสะดุด" ไม่ใช่การเดาว่า code ตรงไหนผิด

### 9.2 "ผ่านบนเครื่องเรา แต่ไม่ผ่านบน CI" — ตรวจตามลำดับนี้

| ลำดับ | สงสัยอะไร | วิธีตรวจ |
|---|---|---|
| 1 | Node/Java/Python คนละ version | เทียบ version ที่ประกาศใน pipeline กับเครื่องเรา |
| 2 | dependency คนละ version | มี lock file ไหม / CI ใช้คำสั่งที่เคารพ lock file หรือเปล่า |
| 3 | ไฟล์ที่ไม่ได้ commit | CI เห็นเฉพาะสิ่งที่อยู่ใน git — ไฟล์ที่ถูก ignore จะไม่มี |
| 4 | ตัวพิมพ์ใหญ่-เล็กของชื่อไฟล์ | เครื่อง mac/windows มักไม่สนใจ แต่ Linux บน CI สนใจ → `import './Button'` vs `'./button'` |
| 5 | environment variable | เครื่องเรามี `.env` แต่ CI ไม่มี |
| 6 | timezone / locale | test ที่เกี่ยวกับวันที่มักพังเพราะเรื่องนี้ |
| 7 | cache ค้าง | ลองรันแบบล้าง cache ดูว่าผลต่างไหม |
| 8 | จำนวน CPU/RAM ของ runner | test ที่ใช้ timeout สั้นจะพังบนเครื่องช้ากว่า |

### 9.3 "deploy สำเร็จ แต่ production ยังเป็นของเก่า"

```
[1] pipeline บอกว่าสำเร็จจริงไหม หรือ deploy step ถูก skip?
        ↓
[2] image tag ที่ deploy คือ tag ไหน? ตรงกับ commit ที่เราคิดไหม?
        ↓
[3] ใช้ tag `latest` อยู่หรือเปล่า? → K8s อาจใช้ image ที่ cache ไว้ในเครื่องแทนที่จะดึงใหม่
        ↓
[4] Pod ใหม่ถูกสร้างจริงไหม (ดูอายุของ Pod)
        ↓
[5] Pod ใหม่ Running แต่ไม่ Ready หรือเปล่า? → traffic ยังไปตัวเก่าอยู่
        ↓
[6] มี CDN / browser cache หน้าบ้านที่ยังเสิร์ฟไฟล์เก่าไหม
```

ให้มองภาพนี้ว่าปัญหา "deploy แล้วไม่เปลี่ยน" มักไม่ได้อยู่ที่ตอน deploy แต่อยู่ที่ "ของเก่ายังถูกเสิร์ฟจากที่ไหนสักแห่ง"

### 9.4 "deploy แล้ว production พัง" — สิ่งที่ต้องทำตามลำดับ

```
[1] หยุดเลือดก่อน: ROLLBACK ทันที  ← อย่าเพิ่งหาสาเหตุ
        ↓
[2] ยืนยันว่า error rate กลับปกติแล้ว
        ↓
[3] ค่อยหาสาเหตุจาก log/metric ของช่วงที่พัง
        ↓
[4] ถ้ามี migration ที่รันไปแล้ว → ตรวจว่า code เก่ายังทำงานกับ schema ใหม่ได้ไหม
        ↓
[5] เขียน postmortem: อะไรพัง / ทำไมด่านกรองไม่จับ / จะเพิ่มด่านอะไร
```

**หลักที่ต้องจำ:** เวลา production พัง หน้าที่แรกคือ **หยุดผลกระทบต่อผู้ใช้** ไม่ใช่ **เข้าใจสาเหตุ** — การ debug บน production ที่กำลังพังอยู่คือการให้ผู้ใช้จ่ายค่าเรียนรู้ของเรา

### 9.5 คำถามที่ควรถามตัวเองเมื่อ pipeline ช้า

| อาการ | สงสัยอะไรก่อน |
|---|---|
| ทุก stage ช้าเท่า ๆ กัน | runner ช้า / ไม่มี cache เลย |
| install dependency นานมาก | cache ไม่ทำงาน (key ของ cache เปลี่ยนทุกครั้ง) |
| Docker build นาน | เรียงคำสั่งใน Dockerfile ผิด ทำให้ layer cache ใช้ไม่ได้ |
| test นาน | รันเรียงกันแทนที่จะขนาน / e2e ปนอยู่ใน PR pipeline |
| รอคิวนาน | runner ไม่พอ |

## 11. Answer Like a Developer

### 11.1 โครงตอบมาตรฐาน 4 ชั้น

```
[1] นิยามสั้น 1 ประโยค
       ↓
[2] ปัญหาที่มันมาแก้
       ↓
[3] ตัวอย่างจากงานจริง
       ↓
[4] trade-off / ข้อควรระวัง
```

ให้มองภาพนี้ว่าเราไม่ได้ตอบ "คำจำกัดความ" แต่กำลังเล่าว่า "ทำไมโลกถึงต้องมีสิ่งนี้"

### 11.2 ตัวอย่าง: "CI/CD คืออะไร"

**แบบท่องจำ (คะแนนน้อย):**

> "CI คือ Continuous Integration, CD คือ Continuous Deployment ครับ"

**แบบ developer จริง:**

> "CI คือการที่ทุกครั้งที่ push code ระบบจะ build และ test ให้อัตโนมัติ เพื่อจับว่า code ใหม่ทำของเดิมพังหรือเปล่า — เพราะถ้าไม่มี เราจะไปรู้ตอน merge ทีเดียวซึ่งแก้ยากกว่ามาก
>
> ส่วน CD คือการพา artifact ที่ผ่าน CI แล้วไปถึง environment ปลายทางแบบอัตโนมัติ ที่ทีมผมทำคือ build Docker image ครั้งเดียว tag ด้วย git sha แล้ว promote image ตัวเดิมจาก staging ไป production ต่างกันแค่ config
>
> trade-off คือมันต้องลงทุนกับ test ก่อน ถ้า test ไม่แน่นแล้วเปิด auto-deploy เท่ากับสร้างท่อส่ง bug ที่เร็วมาก ทีมผมเลยเริ่มจาก CI ให้นิ่งก่อน แล้วค่อยขยับ CD ทีละ environment"

### 11.3 ตัวอย่าง: "ทำไมต้อง build once, promote many"

> "เพราะถ้า build ใหม่ทุก environment ของที่เราทดสอบบน staging กับของที่ขึ้น production เป็นคนละ binary กัน ต่อให้ commit เดียวกันก็ตาม เพราะ dependency หรือ base image อาจเปลี่ยนระหว่างนั้น
>
> ผลคือเจอบั๊กประเภท 'staging ผ่าน แต่ production พัง' ที่หาสาเหตุไม่เจอ เพราะเราเทียบของคนละชิ้นกัน
>
> วิธีที่ถูกคือ build ครั้งเดียวได้ image ที่ tag ด้วย git sha แล้วเอา image ตัวนั้นเลื่อนขั้นไปเรื่อย ๆ สิ่งเดียวที่เปลี่ยนตาม environment คือ config ซึ่งฉีดเข้าไปตอน runtime ผ่าน ConfigMap กับ Secret
>
> ผลพลอยได้คือ rollback ง่ายมาก เพราะทุก version ยังอยู่ใน registry แค่ชี้ deployment กลับไปที่ tag เก่า"

### 11.4 ตัวอย่าง: "database migration ที่ rollback ได้"

> "หลักคือ migration ต้องเข้ากันได้ทั้งกับ code เวอร์ชันเก่าและใหม่ เพราะระหว่าง rolling update จะมีช่วงที่ Pod สองเวอร์ชันคุยกับ database ตัวเดียวกัน
>
> ผมจะใช้แนวทาง expand แล้วค่อย contract — release แรกเพิ่ม column ใหม่แบบ nullable โดยไม่แตะของเก่า, release ถัดมาให้ code เขียนทั้งสองที่แล้ว backfill ข้อมูล, แล้วค่อยลบ column เก่าใน release หลัง ๆ เมื่อมั่นใจว่าไม่ต้อง rollback แล้ว
>
> สิ่งที่ผมจะไม่ทำเด็ดขาดคือ rename หรือ drop column ใน deploy เดียวกับที่ปล่อย code ใหม่ เพราะทันทีที่ทำ เราจะ rollback ไม่ได้อีกเลย"

### 11.5 ตัวอย่าง: "จะวัดว่า CI/CD ดีด้วยอะไร"

> "ผมจะดู 4 ตัวหลัก: ความถี่ในการ deploy, เวลาจาก commit ถึง production, อัตราที่ deploy แล้วต้องแก้ตาม และเวลาที่ใช้กู้คืนเมื่อพัง
>
> จุดที่ผมให้ความสำคัญที่สุดคือ **เวลาในการกู้คืน** เพราะระบบที่ deploy บ่อยแล้วพังบ้างแต่กู้ได้ใน 2 นาที ปลอดภัยกว่าระบบที่ deploy เดือนละครั้งแต่พังทีต้องใช้เวลาครึ่งวัน
>
> อีกตัวที่ผมดูแต่ไม่ค่อยมีใครพูดถึงคือ 'คนในทีมพยายามข้าม pipeline บ่อยแค่ไหน' ถ้ามีคนขอ skip CI บ่อย แปลว่า pipeline ช้าเกินไปจนกลายเป็นอุปสรรค ไม่ใช่เครื่องมือ"

### 11.6 ประโยคที่ใช้ได้ดีในห้องสัมภาษณ์

- "การ deploy ที่ดีคือการ deploy ที่น่าเบื่อ"
- "Deploy กับ Release ไม่ใช่เรื่องเดียวกัน — feature flag แยกสองอย่างนี้ออกจากกันได้"
- "Pipeline ที่ช้าไม่ได้แค่เสียเวลา แต่มันทำให้คนหาทางเลี่ยง ซึ่งอันตรายกว่า"
- "Test บอกได้แค่ว่าสิ่งที่เรานึกออกว่าจะพัง มันไม่พัง — ที่เหลือต้องพึ่ง monitoring"
- "Rollback ย้อน code ได้ แต่ย้อน database ไม่ได้ ดังนั้น migration ต้องออกแบบให้ถอยได้ตั้งแต่แรก"

## 12. One-Minute Review

**CI/CD คืออะไร:** ระบบอัตโนมัติที่พา code จาก git ไปถึงผู้ใช้ โดยมีด่านตรวจแทนคนทุกจุด

**Flow ที่ต้องวาดได้:**

```
Developer → Git Push → CI → Test → Build → Docker Image
   → Registry → Kubernetes → Production
```

ให้มองภาพนี้ว่า code เดินทางเป็นเส้นตรงเส้นเดียว และทุกจุดบนเส้นนี้มีระบบตรวจแทนคน

**แก่นที่ต้องจำ:**

- **CI** ตอบว่า "code นี้พังของเดิมไหม" / **CD** ตอบว่า "จะส่งของไปถึงผู้ใช้ยังไงให้ปลอดภัย"
- **Continuous Delivery** = พร้อมขึ้นแต่รอคนกด / **Continuous Deployment** = ขึ้นเองอัตโนมัติ
- **Build once, promote many** — build ครั้งเดียว เอาของชิ้นเดิมเลื่อนขั้นทุก environment
- **Config อยู่นอก image** — image เหมือนกันทุก env ต่างกันแค่ ConfigMap/Secret
- **Tag ด้วย git sha** ไม่ใช่ `latest` — ไม่งั้น rollback ไม่ได้
- **Migration ต้องเข้ากันได้ทั้งเวอร์ชันเก่าและใหม่** — expand ก่อน contract ทีหลัง
- **Deploy ≠ Release** — feature flag แยกสองอย่างนี้ออกจากกัน
- **Rolling Update** = ค่าเริ่มต้นที่ดี / **Blue-Green** = สลับทีเดียว rollback เร็วสุด / **Canary** = เสี่ยงน้อยสุดแต่ซับซ้อนสุด
- **Pipeline ต้องเร็วพอที่คนจะไม่หาทางข้าม** — pipeline ช้าบิดพฤติกรรมทีม
- **Secret ต้องอายุสั้น สิทธิ์แคบ ไม่โผล่ใน log และไม่อยู่ใน image**
- **เวลาพัง: rollback ก่อน หาสาเหตุทีหลัง**

## 13. Memory Card

**จำ 5 อย่าง:**

1. **CI = ด่านกรองก่อนเข้า main / CD = สายพานส่งของถึงผู้ใช้** — CI ต้องนิ่งก่อนถึงจะทำ CD
2. **Build ครั้งเดียว แล้ว promote ตัวเดิม** — ของที่ทดสอบกับของที่ขึ้นจริงต้องเป็นชิ้นเดียวกัน ต่างกันแค่ config
3. **Tag ด้วย git sha เก็บทุก version ใน registry** — เพื่อให้ตอบได้ว่า production รันอะไร และ rollback ได้ใน 2 นาที
4. **Migration ต้องถอยได้** — expand → deploy → backfill → contract อย่า drop/rename ใน deploy เดียวกับ code ใหม่
5. **Pipeline เร็ว = ทีมไม่หาทางข้าม** — pipeline ที่ช้าหรือ flaky จะทำลายความเชื่อถือของทั้งระบบ

**Keyword:**

- **CI** → build + test อัตโนมัติทุก push เพื่อจับของพังให้เร็วที่สุด
- **CD (Delivery)** → ของพร้อมขึ้นเสมอ แต่รอคนกดอนุมัติ
- **CD (Deployment)** → ผ่าน test แล้วขึ้น production เองทันที
- **Pipeline** → ลำดับ stage: lint → test → build → deploy
- **Lint** → ตรวจรูปแบบ code ด่านแรกสุดเพราะเร็วที่สุด
- **Artifact** → ของที่ build เสร็จ พร้อม deploy เช่น Docker Image
- **Docker Build** → แพ็ค artifact + runtime ให้รันเหมือนกันทุกที่
- **Registry** → โกดังเก็บ Image ทุก version → หัวใจของการ rollback
- **Tag** → ป้ายชื่อ version ควรเป็น git sha ไม่ใช่ `latest`
- **Environment** → Development (ซ้อมคนเดียว) / Staging (ซ้อมใหญ่ให้เหมือนจริง) / Production (เวทีจริง)
- **Promote** → เลื่อนขั้น artifact ชิ้นเดิมข้าม environment
- **Rollback** → ชี้ deployment กลับไปที่ tag เก่า — ย้อน code ได้ แต่ไม่ย้อน database
- **Rolling Update** → เปลี่ยน Pod ทีละตัว ค่าเริ่มต้นที่ดีของ Kubernetes
- **Blue-Green** → รัน 2 ชุดคู่กัน สลับ traffic ทีเดียว rollback เร็วที่สุด แต่ใช้ resource 2 เท่า
- **Canary** → ปล่อยให้ traffic ส่วนน้อยก่อน ดู metric แล้วค่อยขยาย ผู้ใช้เจอ bug น้อยที่สุด
- **Smoke Test** → test สั้น ๆ หลัง deploy ว่าระบบยังหายใจ
- **Migration** → script เปลี่ยน schema ต้องเข้ากันได้ทั้ง code เก่าและใหม่
- **Feature Flag** → สวิตช์แยก "deploy code" ออกจาก "เปิดให้ผู้ใช้เห็น"
- **Secret** → ของลับใน pipeline ต้องอายุสั้น สิทธิ์แคบ ไม่อยู่ใน image ไม่โผล่ใน log
- **Flaky Test** → test ที่ผลไม่คงที่ ต้องถือเป็น bug ไม่ใช่เรื่องปกติที่กด re-run ทิ้ง
