# PART 17 — SOFTWARE ARCHITECTURE

> ตำแหน่งในภาพใหญ่: Design Layer — ชั้นที่ไม่มีผู้ใช้คนไหนมองเห็น แต่เป็นตัวตัดสินว่าทีมจะแก้ code พรุ่งนี้ได้เร็วหรือช้า

## 1. Big Picture

Chapter ก่อนหน้าสอนให้ระบบ **ทำงานได้** และ **ทนโหลดได้**
Chapter นี้สอนให้ code **ยังแก้ได้อยู่ในอีก 2 ปีข้างหน้า** ตอนที่คนเขียนคนแรกลาออกไปแล้ว

นี่คือเรื่องที่ junior มักคิดว่า "ไม่จำเป็น" และ senior ทุกคนรู้ว่า "แพงที่สุดตอนไม่มี"

### ปัญหาจริงที่ Architecture แก้

ลองนึกภาพนี้ — เป็นเรื่องที่เกิดกับทุกทีมจริง ๆ:

```
เดือนที่ 1  →  แก้ฟีเจอร์ใช้เวลา 1 วัน
เดือนที่ 6  →  แก้ฟีเจอร์เดิม ใช้เวลา 3 วัน
เดือนที่ 12 →  แก้ฟีเจอร์เดิม ใช้เวลา 1 สัปดาห์ + พังที่อื่น 2 จุด
```

> **ให้มองภาพนี้ว่า** "code ไม่ได้พังเพราะเขียนผิด แต่พังเพราะมันแก้ยากขึ้นเรื่อย ๆ จนทีมไม่กล้าแตะ"

Architecture ไม่ได้มีไว้ทำให้ code สวย
**Architecture มีไว้ทำให้ต้นทุนการเปลี่ยนแปลงในอนาคตคงที่**

ถ้าจำอะไรจาก chapter นี้ได้แค่ประโยคเดียว ให้จำประโยคนี้:

> **สถาปัตยกรรมที่ดี = เวลาเปลี่ยนความต้องการ 1 อย่าง ต้องแก้ code แค่ที่เดียว**

### ทั้ง chapter นี้ตอบแค่ 3 คำถาม

| คำถาม | เครื่องมือในบทนี้ |
|---|---|
| **1. code ควรแบ่งเป็นชิ้น ๆ ยังไง** | Separation of Concerns, Layered, MVC, Clean Architecture, Controller/Service/Repository |
| **2. ชิ้นแต่ละชิ้นควรผูกกันแค่ไหน** | Coupling, Cohesion, Dependency, DI, SOLID |
| **3. เมื่อไรควรลงทุนทำให้ดี เมื่อไรควรปล่อย** | DRY, KISS, YAGNI, Technical Debt, Refactoring |

### สิ่งที่คนสัมภาษณ์อยากได้ยินจริง ๆ

คนสัมภาษณ์ระดับ Senior **ไม่ได้อยากฟังนิยาม SOLID**
เขาอยากรู้ว่าคุณเคย "เจ็บ" มาก่อนไหม

- เคยแก้ที่หนึ่งแล้วพังอีกที่ไหม → เขาอยากฟังเรื่อง **Coupling**
- เคยเปิดไฟล์แล้วเจอ 2,000 บรรทัดทำ 10 อย่างไหม → เขาอยากฟังเรื่อง **Cohesion**
- เคยทำ abstraction ไว้เผื่ออนาคต แล้วไม่ได้ใช้เลยไหม → เขาอยากฟังเรื่อง **YAGNI**

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Architecture** | ผังบ้าน | การตัดสินใจระดับโครงสร้างที่เปลี่ยนทีหลังแล้วแพง |
| **Separation of Concerns** | แยกเรื่องแยกห้อง | code แต่ละส่วนรับผิดชอบเรื่องเดียว ไม่ปนกัน |
| **Layered Architecture** | บ้านหลายชั้น | แบ่ง code เป็นชั้น ชั้นบนเรียกชั้นล่างเท่านั้น |
| **MVC** | Model-View-Controller | แยกข้อมูล / หน้าตา / ตัวรับคำสั่ง ออกจากกัน |
| **Clean Architecture** | ธุรกิจอยู่แกนกลาง | logic ธุรกิจไม่รู้จัก framework / DB / HTTP |
| **Controller** | พนักงานรับออเดอร์ | รับ request ตรวจ input แล้วส่งต่อ ไม่คิด logic เอง |
| **Service** | ครัว | ที่อยู่ของ business logic จริง |
| **Repository** | คนไปหยิบของในสต็อก | ตัวกลางคุยกับ DB ซ่อนรายละเอียดการเก็บข้อมูล |
| **Coupling** | ผูกกันแน่นแค่ไหน | ระดับที่ module หนึ่งต้องรู้จัก/พึ่งพาอีก module |
| **Cohesion** | เรื่องเดียวกันอยู่ด้วยกันไหม | ระดับที่ของใน module เดียวกันเกี่ยวข้องกันจริง |
| **Dependency** | ของที่เราต้องพึ่ง | สิ่งที่ code เราเรียกใช้เพื่อทำงานให้เสร็จ |
| **Dependency Injection** | ยื่นของให้ ไม่ใช่ไปหยิบเอง | ส่ง dependency เข้ามาจากข้างนอก แทนที่จะ new เอง |
| **Inversion of Control** | กลับทิศการควบคุม | ให้ภายนอกเป็นคนตัดสินว่าจะใช้ implementation ไหน |
| **Interface / Abstraction** | สัญญาว่าทำอะไรได้ | ข้อตกลงว่ามี method อะไร โดยไม่บอกว่าทำยังไง |
| **SOLID** | หลัก 5 ข้อของ OOP | ชุดแนวทางให้ code ขยายได้โดยไม่ต้องรื้อ |
| **SRP** | 1 คลาส 1 เหตุผลที่จะเปลี่ยน | Single Responsibility Principle |
| **OCP** | เพิ่มได้ ไม่ต้องแก้ของเดิม | Open/Closed Principle |
| **LSP** | ลูกต้องแทนพ่อได้ | Liskov Substitution Principle |
| **ISP** | อย่ายัดเยียด method ที่ไม่ใช้ | Interface Segregation Principle |
| **DIP** | พึ่ง interface ไม่ใช่ของจริง | Dependency Inversion Principle |
| **DRY** | อย่าเขียนความรู้เดิมซ้ำ | Don't Repeat Yourself |
| **KISS** | เรียบง่ายไว้ก่อน | Keep It Simple, Stupid |
| **YAGNI** | ยังไม่ต้องใช้ ก็ยังไม่ต้องทำ | You Aren't Gonna Need It |
| **Technical Debt** | หนี้ทางเทคนิค | ทางลัดที่เลือกวันนี้ แล้วต้องจ่ายดอกเบี้ยทีหลัง |
| **Refactoring** | จัดบ้านใหม่ ของเหมือนเดิม | เปลี่ยนโครงสร้าง code โดยพฤติกรรมไม่เปลี่ยน |
| **Design Pattern** | ท่ามาตรฐานที่คนเจอปัญหาซ้ำ ๆ คิดไว้ให้ | วิธีแก้ปัญหาที่พบบ่อย พร้อมชื่อเรียกที่ทุกคนเข้าใจตรงกัน |
| **Factory** | โรงงานผลิตของ | ซ่อนการตัดสินใจว่าจะสร้าง object ตัวไหน |
| **Strategy** | เปลี่ยนวิธีคิดได้ระหว่างวิ่ง | สลับ algorithm ได้โดยไม่แตะ code ที่เรียกใช้ |
| **Observer** | คนสมัครรับข่าว | ของหนึ่งเปลี่ยน แล้วคนที่สนใจรู้เองอัตโนมัติ |
| **Adapter** | หัวแปลงปลั๊ก | ทำให้ของสองอย่างที่หน้าตาไม่เข้ากัน คุยกันได้ |
| **God Object** | คลาสที่ทำทุกอย่าง | สัญญาณอันตรายว่า cohesion ต่ำมาก |
| **Spaghetti Code** | เส้นพันกัน | code ที่ไล่ทางเดินไม่ได้ เพราะทุกอย่างเรียกทุกอย่าง |
| **Boundary** | เส้นแบ่งเขต | จุดที่เราตั้งใจ "ตัด" ระบบ เพื่อคุมการเปลี่ยนแปลง |

## 3. Mental Model

### Model 1 — Architecture คือการจัดการ "การเปลี่ยนแปลง" ไม่ใช่การจัดการ "code"

คำถามที่ผิด: *"code นี้สวยไหม"*
คำถามที่ถูก: **"ถ้าพรุ่งนี้ลูกค้าขอเปลี่ยนเรื่องนี้ ผมต้องเปิดกี่ไฟล์"**

ทุกครั้งที่คุณตัดสินใจเรื่องโครงสร้าง ให้เติมประโยคนี้:

> **"ถ้า ____ เปลี่ยน ผมอยากให้แก้แค่ที่ ____ ที่เดียว"**

ตัวอย่างจริง:

| ถ้าสิ่งนี้เปลี่ยน | อยากให้แก้ที่เดียวตรงไหน |
|---|---|
| เปลี่ยนจาก MySQL เป็น PostgreSQL | Repository layer |
| เปลี่ยนจาก REST เป็น GraphQL | Controller layer |
| เปลี่ยนสูตรคิดส่วนลด | Service layer |
| เปลี่ยนเจ้าของบริการส่ง email | Adapter ตัวเดียว |
| เปลี่ยนสีปุ่ม | Component เดียว |

ถ้าคำตอบของแถวไหนคือ "แก้หลายที่มาก" — นั่นคือจุดที่สถาปัตยกรรมกำลังบอกว่ามีปัญหา

### Model 2 — ทุก architecture pattern คือคำตอบของคำถามเดียว: "ใครควรรู้จักใคร"

Layered, MVC, Clean Architecture ฟังดูต่างกันมาก
แต่ทั้งหมดกำลังตอบคำถามเดียวกัน คือ **"ลูกศรการพึ่งพา ควรชี้ไปทางไหน"**

```
        ทุก pattern ตอบคำถามเดียว
                  ↓
        "ใครควรรู้จักใคร และห้ามรู้จักใคร"
                  ↓
   ┌──────────────┼──────────────┐
Layered          MVC       Clean Architecture
บนเรียกล่าง    แยกหน้าที่   ข้างนอกรู้จักข้างใน
```

> **ให้มองภาพนี้ว่า** "ชื่อ pattern เยอะแต่แก่นเดียว — มันแค่กำหนดกฎว่าใครห้ามเรียกใคร เพื่อไม่ให้ทุกอย่างพันกันเป็นก้อนเดียว"

### Model 3 — Coupling กับ Cohesion คือมาตรวัดตัวจริง ที่เหลือคือวิธีการ

SOLID, DI, Clean Architecture, Design Pattern ทั้งหมด **เป็นแค่วิธี**
สิ่งที่เราวัดจริง ๆ มีแค่ 2 ตัว:

```
เป้าหมายของทุกสถาปัตยกรรม
            ↓
   ┌────────┴────────┐
Coupling ต่ำ      Cohesion สูง
(ผูกกันหลวม)     (ของที่เกี่ยวกันอยู่ด้วยกัน)
```

> **ให้มองภาพนี้ว่า** "เป้าหมายมีแค่สองข้อ คือแยกของที่ไม่เกี่ยวกันออกจากกัน และรวมของที่เกี่ยวกันไว้ด้วยกัน — ที่เหลือคือเทคนิคเพื่อไปถึงสองข้อนี้"

เวลาสัมภาษณ์ ถ้าคุณอธิบาย pattern แล้วปิดท้ายด้วย
*"ทั้งหมดนี้ทำเพื่อลด coupling และเพิ่ม cohesion ครับ"* — คุณจะดูเหมือนคนที่เข้าใจจริง ไม่ใช่คนที่ท่องมา

### Model 4 — เวลาแบ่ง layer ให้แบ่งตาม "เหตุผลที่จะเปลี่ยน" ไม่ใช่ตามชนิดของไฟล์

junior แบ่ง code แบบนี้: `controllers/`, `services/`, `models/`, `utils/`
เพราะ tutorial สอนมาแบบนั้น

senior จะถามต่อว่า: *"เวลาเราทำฟีเจอร์ใหม่ 1 อัน เราต้องเปิดกี่โฟลเดอร์"*

ถ้าคำตอบคือ "ต้องเปิด 5 โฟลเดอร์ทุกครั้ง" แสดงว่าโครงสร้างกำลังแบ่งตาม **ชนิดของ code** ไม่ใช่แบ่งตาม **ฟีเจอร์** ซึ่งพอระบบโตขึ้น การแบ่งตามฟีเจอร์ (`order/`, `payment/`, `user/` แล้วข้างในค่อยมี controller/service/repo) มักจะดูแลง่ายกว่า

จุดสำคัญ: **ไม่มีคำตอบตายตัว** ระบบเล็กแบ่งตามชนิดไฟล์ก็อ่านง่ายดี ระบบใหญ่แบ่งตามฟีเจอร์มักชนะ — ในห้องสัมภาษณ์ให้บอกทั้งสองแบบพร้อมเงื่อนไข

## 4. ภาพจำ

```
🧠 ภาพจำหลัก:
Software Architecture = ผังร้านอาหาร

ลูกค้า (Request)
      ↓
พนักงานรับออเดอร์ (Controller)  ← ไม่ทำอาหารเอง แค่จดและเช็คว่าสั่งถูกไหม
      ↓
ครัว (Service)                  ← ที่ที่ "สูตร" อยู่จริง = business logic
      ↓
คนไปหยิบของในสต็อก (Repository) ← รู้ว่าของอยู่ชั้นไหน ตู้ไหน
      ↓
สต็อก (Database)
```

> **ให้มองภาพนี้ว่า** "ถ้าพนักงานรับออเดอร์วิ่งเข้าไปผัดเองแล้ววิ่งไปหยิบของเอง ร้านก็ยังทำงานได้ตอนลูกค้า 2 โต๊ะ แต่จะพังทันทีตอน 50 โต๊ะ และตอนพนักงานคนนั้นลาออก"

ภาพจำย่อยที่ใช้ได้ทั้ง chapter:

| Concept | 🧠 ภาพจำ |
|---|---|
| **Separation of Concerns** | ห้องน้ำแยกจากห้องครัว — ไม่ใช่เพราะสวย แต่เพราะปนกันแล้วมีปัญหา |
| **Layered** | ตึกที่ชั้นบนกดลิฟต์ลงชั้นล่างได้ แต่ชั้นล่างห้ามสั่งงานชั้นบน |
| **Clean Architecture** | หัวหอม — สูตรธุรกิจอยู่แกนกลาง เปลือกนอกคือ DB/HTTP ที่เปลี่ยนได้ |
| **Coupling สูง** | พวงกุญแจที่มัดรวมกัน — ดึงดอกเดียว มาทั้งพวง |
| **Cohesion สูง** | ลิ้นชักที่มีแต่ช้อนส้อม ไม่ใช่ลิ้นชักรวมทุกอย่างในบ้าน |
| **Dependency Injection** | เชฟไม่ได้ปลูกผักเอง มีคนส่งผักมาให้ — วันไหนอยากเปลี่ยนเจ้า ก็เปลี่ยนคนส่ง |
| **Technical Debt** | รูดบัตรเครดิต — ได้ของวันนี้ แต่ดอกเบี้ยเดินทุกวัน |
| **Refactoring** | จัดบ้านใหม่ — ของเท่าเดิม หาเจอเร็วขึ้น |
| **Factory** | ร้านกาแฟ สั่ง "ลาเต้" พอ ไม่ต้องรู้ว่าเครื่องไหนชงยังไง |
| **Strategy** | Google Maps — ปลายทางเดิม แต่เลือกโหมดขับ/เดิน/รถเมล์ได้ |
| **Observer** | กดกระดิ่ง subscribe — มีคลิปใหม่ ระบบเตือนเอง ไม่ต้องคอยเข้ามาดู |
| **Adapter** | หัวแปลงปลั๊กตอนไปต่างประเทศ — ไฟเหมือนเดิม แค่หัวเสียบไม่ตรงกัน |
| **Repository** | บรรณารักษ์ — เราขอ "หนังสือเล่มนี้" ไม่ต้องรู้ว่าเก็บชั้นไหน |

## 5. How It Works

### 5.1 Separation of Concerns — รากของทุกอย่างในบทนี้

**Separation of Concerns (SoC)** → แยกเรื่องแยกส่วน → ให้ code แต่ละส่วนสนใจเรื่องเดียว

ลองดู code ในหัวแบบนี้ (ไม่ต้องเขียนจริง แค่เห็นภาพ):

```
function createOrder(req, res) {
  ตรวจ input
  คิดส่วนลด + คิด VAT
  เขียนลง database
  ส่ง email
  ตอบ JSON กลับ
}
```

function เดียวทำ 5 เรื่องที่ **เปลี่ยนด้วยเหตุผลคนละอย่างกัน**:

| เรื่อง | จะเปลี่ยนตอนไหน |
|---|---|
| ตรวจ input | ตอน API เปลี่ยน format |
| คิดส่วนลด/VAT | ตอนฝ่ายการเงินเปลี่ยนกฎ |
| เขียน DB | ตอนย้าย database |
| ส่ง email | ตอนเปลี่ยนผู้ให้บริการ email |
| ตอบ JSON | ตอน frontend ขอ field เพิ่ม |

พอ 5 เรื่องนี้อยู่ไฟล์เดียวกัน = **ทุกคนในทีมต้องแก้ไฟล์นี้ = conflict ตลอด = แก้เรื่องหนึ่งพังอีกเรื่อง**

นี่คือ "อาการ" ที่ทำให้เราต้องแบ่ง layer ไม่ใช่เพราะหนังสือบอกให้แบ่ง

### 5.2 Layered Architecture และ MVC

**Layered Architecture** → สถาปัตยกรรมแบบชั้น → แบ่ง code เป็นชั้น และกำหนดว่า**ชั้นบนเรียกชั้นล่างได้เท่านั้น**

```
[PRESENTATION]   ← Controller / UI — รับ-ส่งข้อมูลกับโลกภายนอก
       ↓
[APPLICATION]    ← Service — ลำดับขั้นตอนการทำงาน
       ↓
[DOMAIN]         ← กฎธุรกิจ / Entity
       ↓
[INFRASTRUCTURE] ← Repository / DB / External API
```

> **ให้มองภาพนี้ว่า** "เป็นตึกที่คนชั้นบนเดินลงไปขอของชั้นล่างได้ แต่ห้ามให้ชั้นล่างวิ่งขึ้นมาสั่งงานชั้นบน — เพราะถ้าเดินขึ้นเดินลงได้ทั้งคู่ สุดท้ายจะไล่ไม่ออกว่าใครเริ่มอะไร"

กฎเหล็ก 2 ข้อของ layered:

1. **ลูกศรชี้ทางเดียว** — ชั้นล่างต้องไม่รู้จักชั้นบน (Repository ต้องไม่รู้จัก HTTP request)
2. **ห้ามข้ามชั้นแบบมั่ว ๆ** — Controller เรียก Repository ตรง ๆ ทำได้ในระบบเล็กมาก แต่พอ logic เริ่มเยอะ มันจะกลายเป็นที่ซ่อน logic ที่ไม่มีใครหาเจอ

**MVC (Model-View-Controller)** → รูปแบบแยก 3 ส่วน → ใช้มานานตั้งแต่ยุค desktop จนถึง web

| ส่วน | หน้าที่ | สิ่งที่มักเข้าใจผิด |
|---|---|---|
| **Model** | ข้อมูล + กฎของข้อมูล | ไม่ใช่แค่ "ตาราง DB" — ควรมีกฎธุรกิจอยู่ด้วย |
| **View** | แสดงผล | ไม่ควรมี logic ตัดสินใจทางธุรกิจ |
| **Controller** | รับ input แล้วประสานงาน | **ไม่ใช่ที่เก็บ business logic** — แต่ในโลกจริงมักบวมที่สุด |

```
[USER ACTION]
      ↓
[CONTROLLER] ── เรียก ──→ [MODEL]
      │                      │
      └──── เลือก ────→ [VIEW] ←── ข้อมูล ──┘
```

> **ให้มองภาพนี้ว่า** "Controller คือคนกลางที่รับคำสั่งแล้วสั่งต่อ ไม่ใช่คนลงมือทำเอง — พอ Controller ลงมือทำเองเมื่อไร มันจะโตจนกลายเป็นไฟล์ 1,500 บรรทัดที่ไม่มีใครกล้าแตะ"

**MVC ต่างจาก Layered ยังไง** — คนสับสนข้อนี้บ่อยมาก

- MVC เน้นแยก **หน้าตา (View)** ออกจาก **ข้อมูล (Model)** — เกิดมาเพื่อ UI
- Layered เน้นแยก **ระดับความใกล้เทคโนโลยี** — เกิดมาเพื่อทั้งระบบ
- ในงานจริงมักใช้ทั้งคู่พร้อมกัน: MVC อยู่ชั้นบนสุด แล้วข้างใต้ยังแบ่งเป็น service/repository ต่อ

### 5.3 Controller / Service / Repository — ท่ามาตรฐานที่ต้องอธิบายได้

นี่คือโครงที่เจอบ่อยที่สุดใน Express, NestJS, Spring Boot, Laravel และเป็นคำถามสัมภาษณ์ระดับ mid ที่ถูกถามบ่อยที่สุดของบทนี้

```
[HTTP REQUEST]
      ↓
[CONTROLLER]   รับ request, ตรวจรูปแบบ input, แปลง error เป็น status code
      ↓        ❌ ไม่มี if ทางธุรกิจ  ❌ ไม่มี SQL
[SERVICE]      business logic ทั้งหมด, ลำดับขั้นตอน, transaction
      ↓        ❌ ไม่รู้จัก req/res   ❌ ไม่เขียน SQL เอง
[REPOSITORY]   คุยกับ DB, แปลง row เป็น object
      ↓        ❌ ไม่มีกฎธุรกิจ
[DATABASE]
```

> **ให้มองภาพนี้ว่า** "แต่ละชั้นมีสิ่งที่ 'ห้ามมี' ชัดเจน — ถ้าคุณจำได้แค่ช่อง ❌ ของแต่ละชั้น คุณจะวางโครงโปรเจกต์ได้ถูกแล้ว 80%"

**วิธีทดสอบว่าแบ่งถูกไหม — 3 คำถาม**

1. ถ้าเปลี่ยนจาก REST เป็น gRPC → Service ต้องแก้ไหม? (ไม่ควรต้องแก้)
2. ถ้าเปลี่ยนจาก MySQL เป็น MongoDB → Service ต้องแก้ไหม? (ไม่ควรต้องแก้ ควรแก้แค่ Repository)
3. ถ้าจะเขียน test ของ "สูตรคิดส่วนลด" → ต้องเปิด server ขึ้นมาไหม? (ไม่ควรต้อง)

ถ้าข้อ 3 ตอบว่า "ต้องยิง API เข้าไปถึงจะ test ได้" แปลว่า business logic ยังติดอยู่ใน Controller

**ข้อควรระวังที่คนไม่ค่อยพูด: ไม่ใช่ทุกโปรเจกต์ต้องมี 3 ชั้น**

| สถานการณ์ | คำแนะนำ |
|---|---|
| CRUD ล้วน ไม่มี logic เลย | Controller → Repository ตรงก็พอ (Service จะเป็นชั้นเปล่าที่แค่ส่งต่อ) |
| มี business logic ชัดเจน | ใช้ 3 ชั้นเต็ม |
| logic ซับซ้อนมาก หลาย use case | เริ่มพิจารณา Clean Architecture / แยก domain layer |

การใส่ Service ที่มีแค่ `return repo.findAll()` ทุกไฟล์ คือ **ceremony** ไม่ใช่ architecture — และเป็นสิ่งที่ YAGNI เตือนไว้พอดี

### 5.4 Clean Architecture และ Dependency Rule

**Clean Architecture** → สถาปัตยกรรมที่เอากฎธุรกิจไว้แกนกลาง → เพื่อให้ business logic **ไม่รู้จัก** framework, database, HTTP เลย

```
        ┌─────────────────────────┐
        │   Frameworks & Drivers  │  Express, React, MySQL
        │  ┌───────────────────┐  │
        │  │ Interface Adapters│  │  Controller, Repository impl
        │  │  ┌─────────────┐  │  │
        │  │  │  Use Cases  │  │  │  "สร้างออเดอร์", "ยกเลิกออเดอร์"
        │  │  │  ┌───────┐  │  │  │
        │  │  │  │Entity │  │  │  │  กฎธุรกิจแท้ ๆ
        │  │  │  └───────┘  │  │  │
        │  │  └─────────────┘  │  │
        │  └───────────────────┘  │
        └─────────────────────────┘
        ลูกศรพึ่งพา: ข้างนอก → ข้างใน เท่านั้น
```

> **ให้มองภาพนี้ว่า** "หัวใจของธุรกิจคือแกนหัวหอม ส่วน database กับ framework เป็นแค่เปลือกที่ปอกทิ้งแล้วเปลี่ยนใหม่ได้ โดยแกนไม่รู้สึกอะไร"

**Dependency Rule** — กฎข้อเดียวที่สำคัญที่สุดของ Clean Architecture:

> **code ข้างในห้ามรู้จักชื่อของอะไรที่อยู่ข้างนอก**

แปลเป็นภาษาคน: ในไฟล์ที่เก็บกฎธุรกิจ **ห้ามมีคำว่า `req`, `res`, `SELECT`, ชื่อ ORM, ชื่อ library HTTP**

**แล้วมันทำงานยังไงถ้าข้างในต้องเขียน DB?**
คำตอบคือ **ข้างในประกาศ interface ไว้ ข้างนอกมาทำตาม** (นี่คือ DIP ในหัวข้อ SOLID)

```
Use Case ประกาศ:  "ฉันต้องการใครสักคนที่ save(order) ได้"
                              ↓
Infrastructure ทำตาม:  MySqlOrderRepository implements ตัวนั้น
```

**ราคาที่ต้องจ่ายของ Clean Architecture** — ข้อนี้ต้องพูดในห้องสัมภาษณ์เสมอ

| ได้ | เสีย |
|---|---|
| เปลี่ยน DB/framework ได้โดยไม่แตะ logic | ไฟล์เยอะขึ้นมาก (mapping ไป-กลับหลายชั้น) |
| test business logic ได้โดยไม่ต้องมี DB | คนใหม่เข้าทีมงงกว่าเดิม ต้องมีคนอธิบาย |
| ขอบเขตชัด ทีมใหญ่ทำงานพร้อมกันได้ | โปรเจกต์เล็กจะรู้สึกว่า "เขียนเยอะเพื่ออะไร" |

**ใช้เมื่อไร:** ระบบที่ business logic ซับซ้อนจริง อายุยาว มีหลายทีม
**ไม่ควรใช้เมื่อไร:** CRUD admin panel, MVP ที่ยังไม่รู้ว่าโดเมนหน้าตายังไง, ทีม 1-2 คน

### 5.5 Coupling และ Cohesion — มาตรวัดตัวจริง

**Coupling** → ระดับการผูกติดกันระหว่าง module → ยิ่งต่ำยิ่งดี
**Cohesion** → ระดับที่ของใน module เดียวกันเกี่ยวข้องกันจริง → ยิ่งสูงยิ่งดี

```
[COUPLING สูง — ไม่ดี]          [COUPLING ต่ำ — ดี]

  A ──→ B                        A ──→ [Interface] ←── B
  ↑ ↘  ↙ ↓                       
  D ←── C                        เปลี่ยน B ไม่กระทบ A
  เปลี่ยน B = พัง A, C, D
```

> **ให้มองภาพนี้ว่า** "coupling สูงคือพวงกุญแจที่มัดรวมกัน ดึงดอกเดียวมาทั้งพวง — เวลาแก้ bug จุดเดียวแล้วพังอีก 3 ที่ นั่นแหละคืออาการของมัน"

**สัญญาณของ Coupling สูง (ที่เจอในงานจริง)**

- แก้ 1 บรรทัด แล้ว test พัง 20 ไฟล์
- ต้องเปิด 6 ไฟล์ถึงจะเข้าใจว่า 1 ฟีเจอร์ทำงานยังไง
- เปลี่ยนชื่อ column ใน DB แล้วต้องแก้ถึง frontend
- ไม่กล้าลบ code เก่า เพราะไม่รู้ว่าใครใช้อยู่

**สัญญาณของ Cohesion ต่ำ**

- มีไฟล์ชื่อ `utils.js` / `helper.js` / `common.js` ที่มี 40 function ไม่เกี่ยวกันเลย
- คลาสเดียวทำทั้งคิดเงิน ส่ง email เขียน log และ export Excel (God Object)
- ชื่อไฟล์บอกไม่ได้ว่าข้างในทำอะไร

**จุดที่หลายคนพลาด:** พยายามลด coupling จน **เกินพอดี** แล้วได้ abstraction 5 ชั้นที่ไม่มีใครตามทัน
เป้าหมายคือ **coupling ต่ำพอที่จะเปลี่ยนแปลงได้** ไม่ใช่ coupling = 0 (ซึ่งเป็นไปไม่ได้ เพราะระบบต้องมีส่วนที่คุยกัน)

### 5.6 Dependency และ Dependency Injection

**Dependency** → สิ่งที่ code เราต้องพึ่งพาเพื่อทำงานให้เสร็จ เช่น service ตัวอื่น, DB, ตัวส่ง email

ปัญหาเกิดตอนเราไป **"หยิบเอง"** ข้างใน:

```
class OrderService {
  constructor() {
    this.mailer = new SendGridMailer()   // ← ผูกตายกับ SendGrid
  }
}
```

3 บรรทัดนี้สร้างปัญหา 3 อย่างพร้อมกัน:

1. เปลี่ยนไปใช้เจ้าอื่น = ต้องแก้ข้างในคลาสนี้
2. เขียน test ไม่ได้ เพราะทุกครั้งที่ test จะยิง email จริง
3. คลาสนี้รู้เรื่องที่ไม่ควรรู้ (รู้ชื่อยี่ห้อผู้ให้บริการ)

**Dependency Injection (DI)** → ยื่น dependency เข้ามาจากข้างนอก → แทนที่จะให้คลาสไปสร้างเอง

```
[ภายนอก (ตัวประกอบระบบ)]
        │ สร้าง Mailer ตัวจริง แล้วยื่นให้
        ↓
[OrderService] ── ใช้ผ่าน ──→ [Mailer Interface]
                                    ↑
                     ┌──────────────┴──────────────┐
             SendGridMailer                   FakeMailer (ตอน test)
```

> **ให้มองภาพนี้ว่า** "เชฟไม่ได้ไปปลูกผักเอง มีคนส่งผักมาให้ — วันไหนอยากเปลี่ยนเจ้าของผัก ก็เปลี่ยนที่คนจัดส่ง ไม่ต้องสอนเชฟใหม่"

**DI ให้อะไรจริง ๆ (พูดให้ได้ 3 ข้อในห้องสัมภาษณ์)**

1. **เปลี่ยน implementation ได้โดยไม่แก้ผู้ใช้งาน** — เปลี่ยนเจ้าผู้ให้บริการ email แก้ที่เดียว
2. **Test ง่ายขึ้นมาก** — ยัด fake เข้าไปแทนของจริงได้
3. **เห็น dependency ชัดเจน** — ดู constructor แล้วรู้เลยว่าคลาสนี้พึ่งอะไรบ้าง (ถ้ามี 9 ตัว = สัญญาณว่าคลาสนี้ทำเยอะเกินไป)

**Inversion of Control (IoC)** → การกลับทิศการควบคุม → คือ "แนวคิด" ส่วน DI คือ "วิธีทำที่พบบ่อยที่สุด"
DI Container (เช่นใน Spring, NestJS) เป็นแค่ **เครื่องมืออัตโนมัติ** ที่ช่วยประกอบของให้ — **ไม่มี container ก็ทำ DI ได้** ด้วยการส่งผ่าน constructor เองมือ ๆ ข้อนี้คนตอบผิดบ่อย

**ราคาที่ต้องจ่าย:** ไล่ code ยากขึ้น (กด "go to definition" แล้วเจอ interface ไม่เจอของจริง) และถ้าใช้ container แบบ magic มาก ๆ ปัญหาตอน runtime จะหายาก

### 5.7 SOLID — อธิบายด้วยภาษาคน ไม่ใช่ท่องนิยาม

SOLID คือ 5 หลักที่เกิดจากคนที่เจ็บมาก่อน ไม่ใช่ทฤษฎีลอย ๆ
วิธีจำที่ดีที่สุดคือจำ **"อาการเจ็บ"** ของแต่ละข้อ

| ข้อ | ชื่อ | ภาษาคน | อาการเจ็บที่มันแก้ |
|---|---|---|---|
| **S** | Single Responsibility | 1 คลาส ควรมีเหตุผลที่จะเปลี่ยนแค่เหตุผลเดียว | แก้เรื่อง A แล้วพังเรื่อง B |
| **O** | Open/Closed | เพิ่มของใหม่ได้ โดยไม่ต้องแก้ของเดิม | เพิ่ม case ใหม่ ต้องกลับไปแก้ if-else ก้อนเดิมทุกครั้ง |
| **L** | Liskov Substitution | ของลูกต้องใช้แทนของพ่อได้ โดยไม่เกิดเรื่องประหลาด | ใส่ subclass เข้าไปแล้วระบบพังทั้งที่ type ถูก |
| **I** | Interface Segregation | อย่าบังคับให้ใครทำ method ที่เขาไม่ได้ใช้ | ต้อง implement method เปล่า ๆ เต็มไปหมด |
| **D** | Dependency Inversion | พึ่ง "สัญญา" อย่าพึ่ง "ของจริง" | เปลี่ยนผู้ให้บริการทีเดียว ต้องแก้ 30 ไฟล์ |

#### S — Single Responsibility (ข้อที่ถูกเข้าใจผิดมากที่สุด)

คนส่วนใหญ่จำผิดว่า *"1 คลาสทำได้แค่ 1 อย่าง"* — **ไม่ใช่**
ของจริงคือ **"1 คลาสควรมีเหตุผลที่จะถูกแก้แค่เหตุผลเดียว"** หรือพูดอีกแบบคือ **ควรตอบต่อคนกลุ่มเดียว**

ตัวอย่างจากงานจริง: คลาส `Invoice` ที่ทำทั้ง

- คิดยอดรวม → เปลี่ยนเมื่อ **ฝ่ายการเงิน** เปลี่ยนกฎ
- จัดรูปแบบ PDF → เปลี่ยนเมื่อ **ฝ่ายการตลาด** เปลี่ยน layout
- บันทึกลง DB → เปลี่ยนเมื่อ **ทีม infra** ย้าย database

3 เจ้านาย 3 ทิศทาง = ไฟล์นี้จะถูกแก้ตลอดเวลาและจะพังตลอดเวลา

#### O — Open/Closed

อาการ: ทุกครั้งที่เพิ่มช่องทางจ่ายเงินใหม่ ต้องกลับไปแก้ `if (type === 'credit') ... else if (type === 'promptpay') ...` ก้อนเดิม

ปัญหาไม่ใช่ว่า if-else ไม่ดี — ปัญหาคือ **ทุกการเพิ่มของใหม่ = ความเสี่ยงที่จะพังของเก่า** เพราะไปแตะไฟล์ที่ทำงานอยู่ดี ๆ

ทางแก้ในทางปฏิบัติคือ Strategy pattern (ดูหัวข้อ 5.9): เพิ่ม "วิธีจ่ายใหม่" = เพิ่มไฟล์ใหม่ 1 ไฟล์ ไม่ต้องแตะของเดิม

ข้อควรรู้: **อย่าทำ OCP ล่วงหน้าทุกที่** ถ้ามีช่องทางจ่ายเดียว การเขียน if ธรรมดาชัดเจนกว่ามาก (KISS + YAGNI) — เริ่มทำตอนมีตัวที่สองหรือสามแล้วถึงคุ้ม

#### L — Liskov Substitution

อธิบายให้จำง่าย: *"ถ้าอะไรอ้างว่าเป็นเป็ด มันต้องว่ายน้ำได้จริง"*

ตัวอย่างคลาสสิก: มี `Bird` ที่มี method `fly()` แล้วสร้าง `Penguin extends Bird` โดยให้ `fly()` โยน error
ผลคือ code ที่รับ `Bird` มาแล้วสั่งบิน จะพังตอนเจอเพนกวิน ทั้งที่ compiler บอกว่าถูกต้อง

ในงานจริงมันโผล่มาแบบนี้: subclass ที่ override แล้ว **เข้มงวดกว่าเดิม** (เช่นเดิมรับค่าว่างได้ ตัวใหม่ throw) หรือ **คืนค่าน้อยกว่าที่สัญญาไว้** — ทุกครั้งที่คุณเขียน `if (obj instanceof X)` เพื่อจัดการกรณีพิเศษของ subclass นั่นคือกลิ่นของ LSP ที่ถูกละเมิด

#### I — Interface Segregation

อาการ: interface ชื่อ `IUserService` มี 25 method พอมีคลาสใหม่มา implement ต้องเขียน method เปล่า 18 ตัวที่เขียนว่า `throw new Error('not supported')`

วิธีคิด: **interface ควรถูกออกแบบจากมุมของ "คนใช้" ไม่ใช่มุมของ "คนทำ"**
ถ้า Controller ใช้แค่ 2 method ก็ควรมี interface เล็ก ๆ ที่มีแค่ 2 method นั้น

#### D — Dependency Inversion

ประโยคทางการ: *"module ระดับสูงไม่ควรพึ่ง module ระดับต่ำ ทั้งคู่ควรพึ่ง abstraction"*
ภาษาคน: **"ครัวไม่ควรผูกกับซัพพลายเออร์เจ้าเดียว ควรผูกกับ 'ข้อตกลงว่าต้องส่งของสด' "**

```
[แบบผูกตาย]                 [แบบ DIP]

OrderService                OrderService
      ↓                           ↓
SendGridMailer            [Mailer Interface]
                                  ↑
                          SendGridMailer
```

> **ให้มองภาพนี้ว่า** "DIP คือการกลับหัวลูกศร — เดิม logic ชี้ไปหาเทคโนโลยี พอกลับหัวแล้วเทคโนโลยีกลายเป็นฝ่ายวิ่งมาทำตามสัญญาที่ logic ตั้งไว้"

**ความสัมพันธ์ที่ควรพูดได้:** DIP คือ "หลักการ", DI คือ "วิธีทำ", IoC Container คือ "เครื่องมือช่วย" — สามอย่างนี้ไม่ใช่สิ่งเดียวกัน แต่เกี่ยวข้องกันตรง ๆ

### 5.8 DRY / KISS / YAGNI — สามข้อที่ตีกันเอง

| หลัก | บอกอะไร | อันตรายเมื่อใช้เกิน |
|---|---|---|
| **DRY** | ความรู้หนึ่งอย่างควรอยู่ที่เดียว | รวม code ที่แค่ "หน้าตาเหมือนกัน" แต่เปลี่ยนคนละเหตุผล → coupling พุ่ง |
| **KISS** | เลือกทางที่เข้าใจง่ายที่สุดที่ยังแก้ปัญหาได้ | ง่ายเกินจนไม่รองรับกรณีที่รู้อยู่แล้วว่าต้องเจอ |
| **YAGNI** | อย่าสร้างของเผื่ออนาคตที่ยังไม่มา | ไม่เผื่ออะไรเลยจนต้องรื้อใหญ่ตอนของมาจริง |

**DRY ที่คนเข้าใจผิดที่สุด**

DRY ไม่ได้แปลว่า "ห้ามมี code ซ้ำ" — DRY แปลว่า **"ห้ามมีความรู้ทางธุรกิจชิ้นเดียวกันอยู่หลายที่"**

ตัวอย่าง: มี 2 ฟังก์ชันที่คำนวณเหมือนกันเป๊ะ

- ถ้าทั้งคู่คือ "สูตรคิด VAT" → **ควรรวม** เพราะถ้ากฎเปลี่ยนต้องเปลี่ยนพร้อมกัน
- ถ้าอันหนึ่งคือ "ค่าธรรมเนียมสมาชิก" อีกอันคือ "ค่าจัดส่ง" ที่บังเอิญ 7% เท่ากัน → **ห้ามรวม** เพราะวันหนึ่งมันจะเปลี่ยนแยกกัน แล้วคุณจะต้องแยกมันออกด้วยความเจ็บปวด

ประโยคที่ senior ใช้: **"duplication ถูกกว่า abstraction ที่ผิด"**

**YAGNI กับสถานการณ์จริง**

- ❌ "เผื่อวันหนึ่งต้องรองรับ 5 ภาษา" → สร้างระบบ i18n ซับซ้อนทั้งที่มีภาษาเดียว
- ❌ "เผื่อวันหนึ่งย้ายไป MongoDB" → สร้าง abstraction 3 ชั้นคลุม DB
- ✅ สิ่งที่ควรเผื่อจริง ๆ คือสิ่งที่ **แก้ทีหลังแล้วแพงมหาศาล** เช่น การออกแบบ ID, การแยก tenant, การเก็บ log/audit trail — ของพวกนี้ไม่ใช่ YAGNI แต่เป็น "การตัดสินใจที่ย้อนกลับยาก"

เกณฑ์ตัดสินที่ใช้ได้จริง: **"การตัดสินใจนี้ย้อนกลับได้ง่ายไหม"** ถ้าย้อนได้ง่าย → ทำง่าย ๆ ไปก่อน (KISS/YAGNI) ถ้าย้อนยาก → คิดให้ดีก่อนลงมือ

### 5.9 Design Pattern — แต่ละตัวแก้ปัญหาอะไร

**Design Pattern** → ท่ามาตรฐานสำหรับปัญหาที่เจอซ้ำ ๆ → ประโยชน์ที่แท้จริงคือ **ทำให้ทีมคุยกันด้วยคำเดียวแล้วเข้าใจตรงกัน**

กฎที่ต้องจำ: **อย่าเริ่มจาก pattern แล้วหาที่ใช้ ให้เริ่มจากปัญหาแล้วค่อยพบว่ามันมีชื่อ**

| Pattern | แก้ปัญหาอะไร | 🧠 ภาพจำ |
|---|---|---|
| **Factory** | ผู้เรียกไม่ควรต้องรู้ว่าจะสร้าง object ตัวไหน/สร้างยังไง | ร้านกาแฟ — สั่ง "ลาเต้" ไม่ต้องรู้ว่าเครื่องไหนชง |
| **Strategy** | มีหลายวิธีทำสิ่งเดียวกัน อยากสลับได้โดยไม่แก้ผู้เรียก | Google Maps — ปลายทางเดิม เปลี่ยนโหมดเดินทางได้ |
| **Observer** | ของหนึ่งเปลี่ยน แล้วหลายคนต้องรู้ โดยต้นทางไม่ต้องรู้จักใคร | กดกระดิ่ง subscribe — มีคลิปใหม่ ระบบเตือนเอง |
| **Adapter** | ของสองชิ้นทำงานร่วมกันได้ แต่หน้าตา interface ไม่ตรง | หัวแปลงปลั๊กตอนไปต่างประเทศ |
| **Repository** | ไม่อยากให้ business logic รู้ว่าข้อมูลเก็บที่ไหน/ยังไง | บรรณารักษ์ — ขอหนังสือ ไม่ต้องรู้ว่าชั้นไหน |

#### Factory — สถานการณ์จริง

ระบบ export รายงานได้ 4 แบบ: PDF, Excel, CSV, JSON
ถ้าไม่มี Factory → ทุกที่ที่อยาก export ต้องเขียน if-else เลือก class เอง และเวลาคอนสตรัคเตอร์เปลี่ยน ต้องตามแก้ทุกจุด

มี Factory → ที่เรียกใช้บอกแค่ `"pdf"` แล้วได้ exporter กลับมา **จุดที่รู้เรื่องการสร้างมีจุดเดียว**

**ใช้เมื่อไร:** เมื่อการตัดสินใจ "จะสร้างตัวไหน" กระจายอยู่หลายที่
**ราคาที่จ่าย:** เพิ่มชั้นอ้อม 1 ชั้น ถ้ามี type เดียวก็ไม่ต้องใช้

#### Strategy — สถานการณ์จริง

ระบบคิดค่าส่ง: ส่งธรรมดา / ส่งด่วน / ส่งแบบ EMS / ฟรีค่าส่งถ้าซื้อเกินยอด
กฎแต่ละแบบซับซ้อนพอควร และฝ่ายการตลาดเพิ่มรูปแบบใหม่ทุกไตรมาส

ไม่มี Strategy → มี `calculateShipping()` ยาว 300 บรรทัดที่มี if-else ซ้อนกัน 5 ชั้น และทุกครั้งที่เพิ่มแบบใหม่ ต้องกลับไปแก้ฟังก์ชันเดิม (ผิด OCP)

มี Strategy → แต่ละวิธีคิดเป็นไฟล์แยก เพิ่มแบบใหม่ = เพิ่มไฟล์ ไม่แตะของเดิม และ test แต่ละสูตรแยกได้

**นี่คือ pattern ที่ใช้บ่อยที่สุดในงานจริง** และเป็นคำตอบที่ดีมากเวลาถูกถามว่า "เคยใช้ design pattern อะไรบ้าง"

#### Observer — สถานการณ์จริง

เมื่อ "ออเดอร์ถูกจ่ายเงินสำเร็จ" ต้องเกิด 5 อย่าง: ตัดสต็อก, ส่ง email, ส่ง LINE, บันทึก analytics, ให้แต้มสมาชิก

ไม่มี Observer → `PaymentService` ต้องรู้จักทั้ง 5 ระบบ และทุกครั้งที่ธุรกิจอยากเพิ่มอย่างที่ 6 ต้องแก้ `PaymentService` (coupling สูงมาก)

มี Observer → `PaymentService` แค่ประกาศว่า *"เหตุการณ์ OrderPaid เกิดขึ้นแล้ว"* ใครสนใจก็ไปสมัครฟังเอง

```
[OrderPaid Event]
        ↓
 ┌──────┼──────┬──────────┬──────────┐
ตัดสต็อก  ส่ง email  ส่ง LINE   analytics   ให้แต้ม
```

> **ให้มองภาพนี้ว่า** "ต้นทางแค่ตะโกนบอกว่าเกิดอะไรขึ้น แล้วใครสนใจก็เดินมาฟังเอง — ต้นทางไม่ต้องรู้เลยว่ามีคนฟังกี่คน"

**ความเชื่อมโยงกับ PART 16:** นี่คือแนวคิดเดียวกับ **Event Driven Architecture** แค่ Observer อยู่ในโปรเซสเดียว ส่วน Event Driven ข้ามเครื่องผ่าน message broker

**ราคาที่จ่าย:** ไล่ flow ยากขึ้นมาก — เปิด code แล้วไม่เห็นว่าหลังจาก publish แล้วเกิดอะไรต่อ ต้องมี log/tracing ที่ดีช่วย

#### Adapter — สถานการณ์จริง

ระบบเดิมใช้ payment gateway เจ้า A ที่เรียก `charge(amount, cardToken)`
วันหนึ่งต้องเพิ่มเจ้า B ที่เรียก `createPayment({ value, currency, source })`

ไม่มี Adapter → business logic เต็มไปด้วย if เช็คว่าใช้เจ้าไหน แล้วแปลงข้อมูลคนละแบบ

มี Adapter → เขียน "หัวแปลง" ของเจ้า B ให้หน้าตาเหมือน interface ที่ระบบเราใช้อยู่ แล้ว business logic ไม่รู้ตัวเลยว่ามีการเปลี่ยนเจ้า

**ใช้บ่อยมากตอนต้องคุยกับ third-party** และเป็นวิธีมาตรฐานในการกันไม่ให้ library ภายนอกแทรกซึมเข้าไปทั่ว codebase

#### Repository — สถานการณ์จริง

ที่จริงคือ Adapter เวอร์ชันเฉพาะทางสำหรับ "ที่เก็บข้อมูล"

ประโยชน์จริงที่คนมองข้าม: ไม่ใช่แค่ "เผื่อเปลี่ยน DB" (ซึ่งแทบไม่เกิด) แต่คือ **ทำให้ business logic ทดสอบได้โดยไม่ต้องมี DB** และ **รวม query ที่ซับซ้อนไว้ที่เดียว** ไม่ให้ SQL กระจายไปทั่ว service

**ข้อถกเถียงที่ควรรู้:** ถ้าใช้ ORM ที่มี abstraction อยู่แล้ว การเพิ่ม Repository อีกชั้นอาจเป็นชั้นเปล่าที่ไม่ได้ให้อะไร — ตอบในห้องสัมภาษณ์ว่า *"ขึ้นกับว่ามี query ซับซ้อนและมี logic ที่ต้อง test แยกหรือไม่"* จะดูเป็นคนที่คิดเอง

### 5.10 Technical Debt และ Refactoring

**Technical Debt** → หนี้ทางเทคนิค → ทางลัดที่เลือกวันนี้เพื่อให้ส่งงานทัน แล้วต้องจ่ายคืนด้วยเวลาที่มากขึ้นในอนาคต

```
[เลือกทางลัด]
      ↓
ส่งงานทันวันนี้ ✅
      ↓
ดอกเบี้ย: ทุกฟีเจอร์ถัดไปช้าลงนิดหน่อย
      ↓
ถ้าไม่จ่ายคืน → ดอกทบต้น → ทีมใช้เวลา 80% ไปกับการแก้ของเก่า
```

> **ให้มองภาพนี้ว่า** "หนี้เทคนิคเหมือนบัตรเครดิต — รูดได้และบางครั้งควรรูด แต่ถ้าไม่เคยจ่ายคืนเลย สุดท้ายรายได้ทั้งหมดจะหมดไปกับดอกเบี้ย"

**หนี้มี 2 ชนิด และต้องแยกให้ออก**

| ชนิด | คำอธิบาย | ท่าทีที่ถูก |
|---|---|---|
| **หนี้ที่ตั้งใจก่อ** | "รู้ว่าวิธีนี้ไม่ดี แต่เลือกเพราะต้องทันดีล" | โอเค ถ้ามีการบันทึกไว้และมีแผนจ่ายคืน |
| **หนี้ที่เกิดจากไม่รู้** | เขียนแบบนั้นเพราะไม่รู้ว่ามีวิธีที่ดีกว่า | แก้ด้วยการ review / เรียนรู้ ไม่ใช่การจัดตารางจ่ายหนี้ |

**เมื่อไรการเป็นหนี้คือการตัดสินใจที่ถูกต้อง** (ข้อนี้คือคำถามระดับ senior)

| สถานการณ์ | ควรก่อหนี้ไหม | เหตุผล |
|---|---|---|
| ทำ MVP ทดสอบว่าตลาดเอาไหม | ✅ ควร | ถ้าตลาดไม่เอา code สวยก็ไม่มีความหมาย |
| ต้องส่งทัน deadline ที่มีสัญญาผูกพัน | ✅ ควร (แบบมีบันทึก) | ธุรกิจเสียหายจริงถ้าไม่ทัน |
| ฟีเจอร์ทดลองที่อาจถูกลบใน 2 เดือน | ✅ ควร | อย่าลงทุนกับของที่จะถูกลบ |
| ระบบคิดเงิน / ระบบความปลอดภัย | ❌ ไม่ควร | ดอกเบี้ยคือเงินหายและลูกค้าหาย |
| ส่วนที่ทั้งทีมต้องแตะทุกวัน | ❌ ไม่ควร | ดอกเบี้ยคูณด้วยจำนวนคนในทีม |

**วิธีคุยเรื่อง Technical Debt กับ PM / หัวหน้า** — เรื่องนี้สำคัญกว่าที่คิด และ senior ถูกวัดที่ตรงนี้

❌ **วิธีที่ไม่ได้ผล:** "code มันแย่มาก ขอเวลา 2 สัปดาห์ refactor ครับ"
เพราะ PM ได้ยินว่า "หยุดสร้างรายได้ 2 สัปดาห์ เพื่อให้ได้สิ่งที่ลูกค้าไม่เห็น"

✅ **วิธีที่ได้ผล — แปลงเป็นภาษาธุรกิจ 4 ขั้น:**

```
1. บอกผลกระทบเป็นตัวเลข   "ทุกฟีเจอร์ในโมดูลนี้ใช้เวลามากกว่าเดิม ~40%"
2. บอกความเสี่ยง          "3 เดือนที่ผ่านมา bug production 6 จาก 9 ตัวมาจากไฟล์นี้"
3. เสนอทางเลือก ไม่ใช่คำขาด "มี 3 ทาง: ปล่อยไว้ / แก้เฉพาะจุด 3 วัน / รื้อ 2 สัปดาห์"
4. เสนอแบบแบ่งจ่าย        "ขอกัน 20% ของทุก sprint แทนการหยุดยาว"
```

> **ให้มองภาพนี้ว่า** "PM ไม่ได้ต่อต้านการ refactor เขาแค่ไม่มีข้อมูลพอจะเลือก — หน้าที่เราคือแปลงความเจ็บทางเทคนิคให้เป็นตัวเลขเวลาและความเสี่ยงที่เขาตัดสินใจได้"

**Refactoring** → ปรับโครงสร้างภายในโดย**พฤติกรรมภายนอกไม่เปลี่ยน**

ข้อนี้คนเข้าใจผิดบ่อยมาก:

- แก้ bug ระหว่าง refactor = **ไม่ใช่ refactoring** แล้ว (พฤติกรรมเปลี่ยน)
- เขียนใหม่ทั้งหมด (rewrite) = **ไม่ใช่ refactoring** แต่เป็นโครงการใหม่ที่มีความเสี่ยงสูงมาก

**เงื่อนไขก่อน refactor ที่ต้องพูดให้ได้:** ต้องมี **test ครอบก่อน** ไม่งั้นคุณไม่มีทางรู้ว่าพฤติกรรมยังเหมือนเดิมจริงไหม — refactor โดยไม่มี test คือการเดาเฉย ๆ

**วิธี refactor ที่ปลอดภัยที่สุดในระบบจริง** คือทำทีละนิดระหว่างทำฟีเจอร์ปกติ (กฎลูกเสือ: *"ออกจากที่ตั้งแคมป์ให้สะอาดกว่าตอนมาถึง"*) แทนที่จะรอทำทีเดียวใหญ่ ๆ ซึ่งมักถูกยกเลิกกลางทางเพราะธุรกิจเปลี่ยนแผน

## 6. Example — สถานการณ์จากงานจริง

### สถานการณ์: ระบบ E-commerce ที่เริ่มแก้ไม่ไหว

คุณเข้าทีมใหม่ ระบบอายุ 2 ปี ทีม 6 คน PM บอกว่า *"ทำไมทีมช้าลงเรื่อย ๆ"*

**สิ่งที่คุณเจอวันแรก**

- ไฟล์ `orderController.js` ยาว 2,400 บรรทัด
- มี SQL อยู่ใน controller 12 จุด
- สูตรคิดส่วนลดอยู่ 4 ที่ และให้ผลไม่ตรงกัน 1 ที่ (นี่คือที่มาของ bug ที่ลูกค้าร้องเรียน)
- ตัวส่ง email ถูก `new` ขึ้นมาใน 9 ไฟล์

**ขั้นที่ 1 — วินิจฉัยด้วยภาษาของบทนี้**

| อาการ | ชื่อทางเทคนิค |
|---|---|
| Controller 2,400 บรรทัด | Cohesion ต่ำ / ผิด SRP / God Object |
| SQL ใน controller | ไม่มี Separation of Concerns, เปลี่ยน DB ไม่ได้ |
| สูตรส่วนลด 4 ที่ | ผิด DRY จริง (เป็นความรู้ธุรกิจชิ้นเดียวกัน) |
| `new` mailer 9 ไฟล์ | Coupling สูง, ผิด DIP, test ไม่ได้ |

**ขั้นที่ 2 — ลำดับการแก้ (สำคัญกว่าตัวการแก้เอง)**

```
1. เขียน test ครอบ flow สั่งซื้อก่อน     ← ตาข่ายนิรภัย ไม่มีอันนี้ห้ามเริ่ม
      ↓
2. ดึงสูตรส่วนลดออกมาไว้ที่เดียว          ← แก้ bug จริงของลูกค้า + คุ้มที่สุด
      ↓
3. ดึง SQL ออกไปเป็น Repository          ← ทำให้ test ง่ายขึ้นอีก
      ↓
4. ย้าย business logic ไป Service        ← Controller เหลือแค่รับ-ส่ง
      ↓
5. ทำ Mailer เป็น interface + inject      ← เปลี่ยนเจ้าได้ + test ไม่ยิงเมลจริง
```

> **ให้มองภาพนี้ว่า** "เราไม่ได้เริ่มจากสิ่งที่น่ารำคาญที่สุด แต่เริ่มจากสิ่งที่ทำให้ปลอดภัยที่สุดก่อน แล้วค่อยไล่ไปที่สิ่งที่ให้ผลตอบแทนทางธุรกิจสูงสุด"

**ขั้นที่ 3 — สิ่งที่ตั้งใจ "ไม่ทำ"**

นี่คือส่วนที่ทำให้คำตอบดูเป็น senior:

- ❌ ไม่ทำ Clean Architecture เต็มรูปแบบ — ทีม 6 คนกับโดเมนนี้ยังไม่คุ้ม
- ❌ ไม่แยก microservices — ปัญหาคือ code ไม่เป็นระเบียบ ไม่ใช่ปัญหา scale
- ❌ ไม่ rewrite — ระบบมีรายได้อยู่ การหยุด 3 เดือนเพื่อเขียนใหม่คือความเสี่ยงที่ไม่จำเป็น
- ❌ ไม่แตะโมดูลที่ไม่มีใครแก้มา 1 ปี — code น่าเกลียดที่ไม่มีใครแตะ ไม่ใช่หนี้ที่มีดอกเบี้ย

**ขั้นที่ 4 — วิธีขายให้ PM**

> "ตอนนี้ bug ที่ลูกค้าเจอเรื่องส่วนลดผิด มาจากการที่เรามีสูตรคิดอยู่ 4 ที่ครับ
> ผมขอ 3 วันรวมมันให้เหลือที่เดียว จะปิด bug นี้ถาวรและทำให้ฟีเจอร์โปรโมชั่นที่จะทำเดือนหน้าเร็วขึ้น
> ส่วนที่เหลือผมจะทยอยทำไปพร้อมฟีเจอร์ปกติ โดยขอกัน 20% ของแต่ละ sprint ไม่ต้องหยุดงานอื่นครับ"

สังเกต: **ผูกงานทางเทคนิคเข้ากับปัญหาที่ธุรกิจรู้สึกอยู่แล้ว** และ **เสนอแบบแบ่งจ่าย** ไม่ใช่ขอหยุดยาว

### สถานการณ์เล็ก: เพิ่มช่องทางชำระเงินที่สอง

PM ขอเพิ่ม PromptPay เพิ่มจากบัตรเครดิต

| ทางเลือก | ผลลัพธ์ |
|---|---|
| เติม `else if` ในฟังก์ชันเดิม | เร็วที่สุดวันนี้ แต่ตัวที่ 3-4-5 จะเจ็บขึ้นเรื่อย ๆ |
| ทำ Strategy + Adapter เลย | ลงทุนเพิ่ม ~1 วัน แต่ตัวถัดไปแทบไม่มีต้นทุน |

คำตอบที่ถูกคือ **"ขึ้นกับว่ามีตัวที่ 3 ไหม"** — ถ้า roadmap มีอีก 3 เจ้าใน 6 เดือน ควรทำ Strategy ตอนนี้ ถ้ามีแค่ 2 เจ้าและไม่มีแผนเพิ่ม การเขียน if ตรง ๆ อ่านง่ายกว่าและถูกต้องตาม KISS

**นี่คือคำตอบที่คนสัมภาษณ์อยากได้ยิน** — ไม่ใช่ "ใช้ Strategy ครับ" แบบอัตโนมัติ

## 7. Compare — ตารางเปรียบเทียบสิ่งที่มักสับสน

### 7.1 Layered vs MVC vs Clean Architecture

| | Layered | MVC | Clean Architecture |
|---|---|---|---|
| เกิดมาแก้ปัญหา | code ปนกันทั้งระบบ | UI ปนกับข้อมูล | logic ผูกกับ framework/DB |
| หน่วยที่แบ่ง | ชั้นตามความใกล้เทคโนโลยี | 3 บทบาท | วงชั้นตามความ "แกน" ของธุรกิจ |
| ทิศลูกศร | บน → ล่าง | Controller ประสาน | ข้างนอก → ข้างใน เสมอ |
| ความยากตอนเริ่ม | ต่ำ | ต่ำ | สูง |
| เหมาะกับ | ระบบทั่วไปส่วนใหญ่ | ระบบที่มี UI | โดเมนซับซ้อน อายุยาว หลายทีม |
| ราคาที่จ่าย | อาจกลายเป็น layer เปล่า | Controller บวมง่าย | ไฟล์เยอะ mapping เยอะ คนใหม่งง |

### 7.2 Coupling vs Cohesion

| | Coupling | Cohesion |
|---|---|---|
| วัดอะไร | ความผูกพัน **ระหว่าง** module | ความเกี่ยวข้อง **ภายใน** module |
| อยากได้แบบไหน | ต่ำ | สูง |
| อาการเมื่อผิดทาง | แก้ที่หนึ่งพังอีกที่ | ไฟล์เดียวทำ 10 เรื่อง ไม่มีใครกล้าแตะ |
| เครื่องมือช่วย | Interface, DI, Event, Adapter | แบ่งไฟล์ตามฟีเจอร์, SRP |

### 7.3 DRY vs YAGNI vs KISS (เวลาตีกัน ใช้อันไหน)

| สถานการณ์ | หลักที่ชนะ | เหตุผล |
|---|---|---|
| code ซ้ำ 2 ที่ แต่เป็นคนละเรื่องทางธุรกิจ | KISS | รวมแล้วจะแยกยากทีหลัง |
| กฎธุรกิจเดียวกันอยู่ 4 ที่ | DRY | เปลี่ยนกฎแล้วลืมแก้ = bug จริง |
| "เผื่ออนาคตอาจต้องรองรับ X" | YAGNI | อนาคตส่วนใหญ่ไม่มาแบบที่คิด |
| การตัดสินใจที่ย้อนกลับยาก (เช่น รูปแบบ ID) | คิดล่วงหน้า | YAGNI ใช้กับของที่แก้ทีหลังได้ถูกเท่านั้น |

### 7.4 Dependency Injection vs Service Locator vs new ตรง ๆ

| | new ตรง ๆ | Service Locator | Dependency Injection |
|---|---|---|---|
| ใครตัดสินใจว่าใช้ตัวไหน | คลาสนั้นเอง | คลาสไปถามจาก registry | ผู้ประกอบระบบข้างนอก |
| เห็น dependency จากข้างนอกไหม | ไม่เห็น | ไม่เห็น (ซ่อนอยู่ข้างใน) | เห็นชัดที่ constructor |
| test ง่ายไหม | ยาก | กลาง | ง่าย |
| เหมาะกับ | script เล็ก ๆ, ของที่ไม่มีทางเปลี่ยน | legacy ที่แก้โครงไม่ได้ | ระบบทั่วไป |

### 7.5 Refactoring vs Rewrite vs Redesign

| | Refactoring | Rewrite | Redesign |
|---|---|---|---|
| พฤติกรรมเปลี่ยนไหม | ไม่เปลี่ยน | มักเปลี่ยน (ตั้งใจหรือไม่ก็ตาม) | เปลี่ยนโครงสร้างใหญ่ |
| ความเสี่ยง | ต่ำ (ถ้ามี test) | สูงมาก | กลาง-สูง |
| ส่งมอบระหว่างทางได้ไหม | ได้ ทีละนิด | มัก "ได้ตอนจบ" เท่านั้น | ได้ถ้าแบ่งเฟส |
| ใช้เมื่อไร | เกือบทุกกรณี | เทคโนโลยีตายจริง / เปลี่ยนโมเดลธุรกิจทั้งหมด | ขอบเขตระบบเปลี่ยนชัดเจน |

### 7.6 Design Pattern ที่มักถูกสับสนกัน

| คู่ที่สับสน | แยกยังไง |
|---|---|
| **Factory vs Strategy** | Factory ตอบ "จะสร้างตัวไหน" · Strategy ตอบ "จะทำงานด้วยวิธีไหน" |
| **Strategy vs State** | Strategy ผู้ใช้เป็นคนเลือก · State ตัวมันเปลี่ยนตัวเองตามสถานการณ์ |
| **Observer vs Event Driven (ข้ามเครื่อง)** | Observer อยู่ในโปรเซสเดียว · Event Driven ข้ามเครื่องผ่าน broker |
| **Adapter vs Facade** | Adapter แปลงหน้าตาให้เข้ากันได้ · Facade รวมของหลายชิ้นให้เรียกง่ายขึ้น |
| **Repository vs DAO** | แนวคิดใกล้กันมาก · Repository เน้นมุมโดเมน DAO เน้นมุมตาราง |

## 8. Common Mistakes

- **ท่อง SOLID ได้ แต่ยกตัวอย่างจากงานจริงไม่ได้** — นี่คือจุดที่คนสัมภาษณ์จับได้ทันที ให้จำ "อาการเจ็บ" ไม่ใช่นิยาม
- **คิดว่า SRP แปลว่า "1 คลาสทำได้แค่ 1 อย่าง"** — ที่ถูกคือ "มีเหตุผลที่จะเปลี่ยนแค่เหตุผลเดียว"
- **ใช้ DRY ผิดจุด** รวม code ที่แค่หน้าตาเหมือนกันแต่เปลี่ยนคนละเหตุผล ทำให้ coupling พุ่งและแยกยากทีหลัง
- **ใส่ Service layer เปล่า ๆ ทุกไฟล์** ที่มีแค่ `return repo.find()` แล้วคิดว่าเป็น architecture — จริง ๆ คือ ceremony
- **ทำ abstraction ล่วงหน้าเผื่ออนาคต** เช่นคลุม DB ไว้ 3 ชั้น "เผื่อย้าย MongoDB" ทั้งที่ 5 ปีผ่านไปก็ยังไม่ย้าย
- **เอา business logic ไปไว้ใน Controller** เพราะ "มันสั้นดี" แล้ววันหนึ่งมันยาว 2,000 บรรทัด
- **ให้ Repository รู้กฎธุรกิจ** เช่นมี method `findActivePremiumUsersWithDiscount()` ที่ฝังกฎไว้ในชื่อ query
- **คิดว่า Clean Architecture = ดีเสมอ** แล้วเอาไปใช้กับ CRUD 5 ตาราง ทำให้ทีมช้าลงโดยไม่ได้อะไรกลับมา
- **ใช้ design pattern เพราะอยากใช้** ไม่ใช่เพราะมีปัญหา — pattern ที่ใส่ผิดที่ทำให้ code อ่านยากกว่าเดิม
- **คิดว่า Technical Debt = code แย่** ทั้งที่หนี้ที่ตั้งใจก่อและมีแผนคืน คือการตัดสินใจทางธุรกิจที่ถูกต้อง
- **ขอ refactor โดยไม่มีตัวเลขสนับสนุน** แล้วโกรธที่ PM ไม่อนุมัติ
- **Refactor โดยไม่มี test** แล้วแยกไม่ออกว่าที่พังเพราะ refactor หรือเพราะ bug เดิม
- **เชื่อว่า "เขียนใหม่ทั้งหมดจะเร็วกว่า"** — เป็นกับดักคลาสสิก เพราะ code เก่าบรรจุ edge case ที่ไม่มีใครจำได้แล้วเอาไว้

## 9. Debugging — เมื่อสถาปัตยกรรมมีปัญหา ไล่ดูอะไรตามลำดับ

"Debug architecture" ไม่ใช่การหา bug แต่คือการหาว่า **ทำไมทีมถึงช้าลง**

```
1. อาการคืออะไรกันแน่
      ↓
2. แก้ 1 ที่แล้วพังที่อื่นไหม        → ปัญหา Coupling
      ↓
3. ต้องเปิดกี่ไฟล์เพื่อทำ 1 ฟีเจอร์   → ปัญหาการแบ่ง boundary
      ↓
4. ไฟล์ไหนถูกแก้บ่อยที่สุด          → จุดนั้นคือหนี้ที่มีดอกเบี้ยจริง
      ↓
5. bug production มาจากไฟล์ไหน      → จัดลำดับความสำคัญจากข้อมูลจริง
      ↓
6. test เขียนยากตรงไหน             → ตรงนั้นแหละคือจุดที่ออกแบบผิด
```

> **ให้มองภาพนี้ว่า** "code ที่ test ยาก ไม่ได้แปลว่าเราเขียน test ไม่เก่ง แต่มันกำลังบอกเราว่าชิ้นส่วนตรงนั้นผูกกับอย่างอื่นแน่นเกินไป"

### ตารางอาการ → สาเหตุ → สิ่งที่ต้องดู

| อาการ | น่าจะเป็นสาเหตุ | เริ่มดูตรงไหน |
|---|---|---|
| แก้ฟีเจอร์เล็ก ๆ ใช้เวลาเป็นวัน | Coupling สูง / ไม่มี boundary | ลองวาดว่า 1 request ผ่านกี่ไฟล์ |
| แก้ที่หนึ่งพังอีกที่เสมอ | ความรู้ธุรกิจกระจายหลายที่ | หาค่าคงที่/สูตรที่ซ้ำกันหลายไฟล์ |
| เขียน test ต้องเปิด DB ทุกครั้ง | business logic ติดอยู่กับ infrastructure | ดูว่า logic อยู่ใน controller/repository ไหม |
| คนใหม่เข้าทีมใช้เวลา 2 เดือนกว่าจะทำงานได้ | โครงสร้างไม่สื่อความหมาย / ceremony เยอะ | ดูว่าชื่อโฟลเดอร์บอกเรื่องธุรกิจหรือบอกแค่ชนิดไฟล์ |
| conflict ตอน merge บ่อยมาก | หลายคนต้องแก้ไฟล์เดียวกัน (cohesion ต่ำ) | ดู git ว่าไฟล์ไหนถูกแก้โดยหลายคนที่สุด |
| กลัวการ deploy | ไม่มี test + coupling สูง | เริ่มจากใส่ test ที่ flow สำคัญที่สุดก่อน |
| เพิ่ม case ใหม่ต้องแก้ if-else ก้อนเดิมทุกครั้ง | ผิด OCP | พิจารณา Strategy เมื่อมีตัวที่ 3 |
| ไล่ flow ไม่เจอว่าหลังจากนี้เกิดอะไร | Observer/Event มากเกินไปโดยไม่มี tracing | ใส่ correlation id + log ที่ publish/subscribe |

### เครื่องมือวินิจฉัยที่ใช้ได้จริง (ไม่ต้องใช้ tool พิเศษ)

1. **git log ต่อไฟล์** — ไฟล์ที่ถูกแก้บ่อยที่สุดคือจุดที่ควรลงทุนปรับปรุงก่อน (ไฟล์ที่ไม่มีใครแตะ ต่อให้น่าเกลียดก็ไม่มีดอกเบี้ย)
2. **นับจำนวนไฟล์ต่อ 1 ฟีเจอร์** — ถ้าทำฟีเจอร์เล็กแล้วต้องแก้ 11 ไฟล์ แปลว่าการแบ่งชิ้นส่วนยังไม่ตรงกับวิธีที่ธุรกิจเปลี่ยน
3. **ลองอธิบาย flow ให้คนใหม่ฟังใน 5 นาที** — ถ้าอธิบายไม่จบ แปลว่าโครงสร้างไม่สื่อความหมาย
4. **ดู constructor** — คลาสที่รับ dependency 8 ตัว คือคลาสที่ทำงานมากเกินไปเกือบเสมอ

### 🟢 Junior

1. Separation of Concerns คืออะไร ทำไมต้องแยก
2. Controller / Service / Repository แต่ละชั้นทำอะไร
3. ทำไมไม่ควรเขียน SQL ใน Controller
4. MVC คืออะไร แต่ละตัวรับผิดชอบอะไร
5. Coupling กับ Cohesion ต่างกันยังไง แบบไหนที่เราอยากได้
6. DRY คืออะไร ยกตัวอย่าง
7. KISS กับ YAGNI บอกอะไรเรา
8. Refactoring คืออะไร ต่างจากการแก้ bug ยังไง
9. Technical Debt คืออะไร
10. Dependency Injection คืออะไร ช่วยอะไร

### 🟡 Mid

1. อธิบาย SOLID ทั้ง 5 ข้อ พร้อมตัวอย่างจากงานที่เคยทำ
2. SRP แปลว่า "1 คลาสทำ 1 อย่าง" ใช่หรือไม่ เพราะอะไร
3. DI ทำให้ test ง่ายขึ้นยังไง ยกตัวอย่างสถานการณ์
4. เมื่อไรที่ DRY เป็นสิ่งที่ผิด
5. Strategy pattern แก้ปัญหาอะไร คุณเคยใช้ตอนไหน
6. Observer pattern เหมาะกับสถานการณ์แบบไหน และข้อเสียคืออะไร
7. Repository pattern มีประโยชน์จริงอะไรบ้าง นอกจาก "เผื่อเปลี่ยน DB"
8. Clean Architecture ต่างจาก Layered ธรรมดายังไง
9. คุณจะรู้ได้ยังไงว่า code ตรงไหนควร refactor ก่อน
10. ถ้าทีมไม่มี test เลย คุณจะเริ่ม refactor ยังไง
11. Adapter pattern ใช้ตอนไหนในงานจริง
12. โครงสร้างโฟลเดอร์ควรแบ่งตามชนิดไฟล์หรือตามฟีเจอร์ เพราะอะไร

### 🔴 Senior

1. Technical Debt เมื่อไรคือการตัดสินใจที่ถูกต้อง และคุณจะอธิบายให้ PM เข้าใจยังไง
2. ทีมขอเวลา 3 เดือน rewrite ระบบ คุณจะตอบยังไง
3. คุณจะออกแบบ boundary ของระบบยังไง ใช้อะไรเป็นเกณฑ์ตัด
4. abstraction ที่มากเกินไป สร้างปัญหาอะไรบ้าง ยกตัวอย่าง
5. ถ้าเข้าทีมใหม่ที่ code รก คุณจะเริ่มจากอะไรใน 30 วันแรก
6. Clean Architecture ไม่คุ้มในกรณีไหนบ้าง
7. คุณตัดสินใจยังไงระหว่าง "ทำให้ยืดหยุ่นไว้ก่อน" กับ "ทำง่าย ๆ ไปก่อน"
8. อธิบายกรณีที่คุณ "จงใจ" ละเมิดหลัก SOLID และเหตุผล
9. ถ้าไฟล์หนึ่งถูกแก้โดย 5 คนทุก sprint คุณจะทำอะไร
10. วัดยังไงว่าการ refactor ครั้งนั้นคุ้ม
11. Design pattern ที่ถูกใช้ผิดบ่อยที่สุดคืออะไร เพราะอะไร
12. ถ้าต้องเลือกระหว่าง code ที่ทดสอบง่ายกับ code ที่อ่านง่าย คุณเลือกอะไร

## 11. Answer Like a Developer

### โครงตอบกลาง — ใช้ได้กับทุกคำถามในบทนี้

```
1. ปัญหาที่หลักการนี้แก้คืออะไร   "ปัญหาจริงคือ ..."
2. อาการตอนไม่มีมัน              "ถ้าไม่มี จะเจอ ..."
3. ตัวอย่างจากงานจริง             "เคสที่ผมเจอคือ ..."
4. ราคาที่ต้องจ่าย                 "แต่มันแลกมากับ ..."
5. เกณฑ์ว่าจะใช้ตอนไหน            "ผมจะใช้เมื่อ ... และจะไม่ใช้เมื่อ ..."
```

**ข้อ 4 กับ 5 คือข้อที่แยก Senior ออกจาก Mid** — คนที่รู้ว่า "เมื่อไรไม่ควรใช้" คือคนที่เคยใช้จริง

### ตัวอย่างที่ 1: "อธิบาย Dependency Injection หน่อย"

❌ **ตอบแบบท่องจำ:** "คือการ inject dependency เข้ามาแทนการ new เองครับ ทำให้ loosely coupled"

✅ **ตอบแบบ Developer:**

> "ปัญหาที่มันแก้คือ ตอนคลาสหนึ่ง `new` ของที่มันต้องใช้ขึ้นมาเอง มันจะผูกตายกับของชิ้นนั้นครับ
>
> เคสที่ผมเจอจริงคือ `OrderService` สร้างตัวส่ง email ของผู้ให้บริการเจ้าหนึ่งขึ้นมาเอง
> ผลคือเวลาเขียน test มันยิง email จริงทุกครั้ง และพอบริษัทเปลี่ยนเจ้า ผมต้องไล่แก้ 9 ไฟล์
>
> พอเปลี่ยนเป็นรับ mailer เข้ามาทาง constructor ผ่าน interface แทน ตอน test ผมยัดตัวปลอมเข้าไปได้
> และตอนเปลี่ยนเจ้า ผมแก้ที่จุดประกอบระบบจุดเดียว
>
> ราคาที่จ่ายคือไล่ code ยากขึ้น เพราะกดตามไปจะเจอ interface ไม่เจอตัวจริง
> ผมเลยจะไม่ใช้กับของที่ไม่มีทางเปลี่ยนจริง ๆ เช่น utility คำนวณวันที่ — อันนั้น new ตรง ๆ ชัดเจนกว่า"

### ตัวอย่างที่ 2: "ทีมอยากหยุด 3 เดือนเพื่อ rewrite คุณจะตอบยังไง"

✅ **โครงคำตอบที่ดี:**

> "ผมจะถามก่อนว่าปัญหาที่เจ็บที่สุดตอนนี้คืออะไร เพราะ rewrite เป็นคำตอบของบางปัญหาเท่านั้นครับ
>
> ถ้าปัญหาคือ 'แก้ยาก ช้า พังบ่อย' — rewrite มักไม่ใช่คำตอบ เพราะ code เก่ามันบรรจุ edge case
> ที่ไม่มีใครจำได้แล้วไว้เยอะมาก เขียนใหม่คือการเจอ bug เดิมซ้ำอีกรอบ
>
> ผมจะเสนอแทนว่า ขอดูข้อมูลก่อนว่าไฟล์ไหนถูกแก้บ่อยที่สุดและเป็นต้นเหตุ bug production มากที่สุด
> แล้วลงทุนเฉพาะตรงนั้น พร้อมใส่ test ครอบไว้ก่อน แบ่งทำไปกับ sprint ปกติ
>
> กรณีที่ผมจะสนับสนุน rewrite จริง ๆ คือตอนเทคโนโลยีที่ใช้หมดการซัพพอร์ตแล้ว
> หรือโมเดลธุรกิจเปลี่ยนจนของเดิมตอบไม่ได้ ซึ่งนั่นคือระบบใหม่ ไม่ใช่การเขียนของเดิมใหม่
>
> และถ้าตัดสินใจทำจริง ผมจะไม่หยุดของเก่า แต่จะย้ายทีละส่วนโดยให้สองระบบอยู่ร่วมกันได้ก่อน"

### ตัวอย่างที่ 3: "SOLID สำคัญยังไง"

✅ **ตอบสั้น ๆ แต่ดูเข้าใจ:**

> "สำหรับผม SOLID เป็นชุดคำเตือนที่คนเคยเจ็บมาก่อนสรุปไว้ครับ มากกว่าจะเป็นกฎที่ต้องทำตามทุกข้อ
>
> ข้อที่ผมใช้บ่อยที่สุดคือ SRP กับ DIP เพราะสองตัวนี้ตอบคำถามว่า
> 'ไฟล์นี้จะถูกแก้เพราะเหตุผลอะไรบ้าง' และ 'ถ้าเปลี่ยนเทคโนโลยี ผมต้องแก้กี่ที่'
>
> แต่ผมไม่ได้พยายามทำให้ครบทั้ง 5 ข้อทุกไฟล์ เพราะการทำ OCP ตั้งแต่ยังมี case เดียว
> มันสร้าง abstraction ที่ไม่มีใครได้ใช้ และทำให้คนใหม่อ่านยากขึ้นโดยไม่ได้ประโยชน์อะไร"

### ประโยคที่ใช้ปิดคำตอบได้เกือบทุกข้อในบทนี้

- *"ทั้งหมดนี้เป้าหมายเดียวคือลด coupling และเพิ่ม cohesion ครับ"*
- *"ผมจะเลือกตามว่าการตัดสินใจนี้ย้อนกลับได้ง่ายแค่ไหน"*
- *"ถ้าโดเมนยังไม่นิ่ง ผมจะยังไม่ล็อกโครงสร้าง"*

## 12. One-Minute Review

**แก่นเดียวของทั้งบท**

> สถาปัตยกรรมที่ดี = เปลี่ยนความต้องการ 1 อย่าง แก้ code ที่เดียว

**การแบ่ง code**

- **Separation of Concerns** = รากของทุกอย่าง แยกสิ่งที่เปลี่ยนด้วยเหตุผลต่างกันออกจากกัน
- **Layered** = ชั้นบนเรียกชั้นล่างเท่านั้น
- **MVC** = แยกหน้าตา / ข้อมูล / ตัวประสาน — Controller ไม่ใช่ที่เก็บ logic
- **Controller / Service / Repository** = จำ "สิ่งที่ห้ามมี" ของแต่ละชั้น
- **Clean Architecture** = ธุรกิจอยู่แกนกลาง ลูกศรชี้เข้าเสมอ — ทรงพลังแต่แพง ใช้เมื่อโดเมนซับซ้อนจริง

**การวัดคุณภาพ**

- **Coupling ต่ำ + Cohesion สูง** คือมาตรวัดตัวจริง ที่เหลือคือวิธีการ
- **DI** = ยื่นของให้ ไม่ใช่ไปหยิบเอง → เปลี่ยนง่าย test ง่าย เห็น dependency ชัด
- **DIP** คือหลักการ, **DI** คือวิธีทำ, **IoC Container** คือเครื่องมือ — ไม่ใช่สิ่งเดียวกัน

**SOLID แบบจำอาการ**

| ข้อ | อาการที่มันแก้ |
|---|---|
| S | แก้เรื่อง A แล้วพังเรื่อง B |
| O | เพิ่ม case ใหม่ ต้องแก้ if-else ก้อนเดิม |
| L | subclass ทำให้ระบบพังทั้งที่ type ถูก |
| I | ต้อง implement method เปล่าเต็มไปหมด |
| D | เปลี่ยนผู้ให้บริการทีเดียว แก้ 30 ไฟล์ |

**หลัก 3 ตัวที่ตีกัน**

- **DRY** ใช้กับ "ความรู้ทางธุรกิจ" ไม่ใช่ "ตัวอักษรที่เหมือนกัน"
- **KISS / YAGNI** ใช้กับการตัดสินใจที่ย้อนกลับได้ง่าย
- ของที่ย้อนกลับยาก (รูปแบบ ID, การแยก tenant, audit log) → ต้องคิดล่วงหน้า

**Design Pattern — จำว่าแก้ปัญหาอะไร ไม่ต้องจำ code**

- **Factory** = ไม่อยากให้ผู้เรียกรู้ว่าสร้างตัวไหน
- **Strategy** = หลายวิธีทำสิ่งเดียวกัน สลับได้ (ใช้บ่อยที่สุดในงานจริง)
- **Observer** = ของหนึ่งเปลี่ยน หลายคนต้องรู้ โดยต้นทางไม่ต้องรู้จักใคร
- **Adapter** = หัวแปลงให้ของสองอย่างคุยกันได้ (ใช้กับ third-party)
- **Repository** = ซ่อนที่มาของข้อมูล ทำให้ logic test ได้โดยไม่มี DB

**Technical Debt**

- หนี้ที่ **ตั้งใจก่อ + บันทึกไว้ + มีแผนคืน** = การตัดสินใจทางธุรกิจที่ถูกต้อง
- ควรก่อหนี้: MVP, ฟีเจอร์ทดลอง, deadline ที่มีผลทางธุรกิจจริง
- ไม่ควรก่อหนี้: ระบบเงิน, ความปลอดภัย, ส่วนที่ทั้งทีมแตะทุกวัน
- คุยกับ PM ด้วย **ตัวเลขเวลา + ความเสี่ยง + ทางเลือก 3 ทาง + แบ่งจ่ายทีละ sprint**
- **Refactor ต้องมี test ก่อนเสมอ** และทำทีละนิดปลอดภัยกว่าทำทีเดียวใหญ่

## 13. Memory Card

### จำ 5 อย่าง

1. **สถาปัตยกรรมวัดที่ "ต้นทุนของการเปลี่ยนแปลง" ไม่ใช่ความสวยของ code** — เปลี่ยน 1 เรื่อง ควรแก้ที่เดียว
2. **เป้าหมายจริงมีแค่ 2 ข้อ: Coupling ต่ำ + Cohesion สูง** — SOLID, DI, Clean Architecture, Design Pattern ทั้งหมดเป็นแค่วิธีไปถึงสองข้อนี้
3. **จำ SOLID ด้วย "อาการเจ็บ" ไม่ใช่ด้วยนิยาม** — และอย่าพยายามทำครบ 5 ข้อทุกไฟล์
4. **Design Pattern เริ่มจากปัญหา ไม่ใช่เริ่มจาก pattern** — Strategy = หลายวิธีทำสิ่งเดียวกัน, Observer = ตะโกนบอกแล้วใครสนใจก็มาฟัง, Adapter = หัวแปลงปลั๊ก, Factory = ไม่ต้องรู้ว่าสร้างตัวไหน, Repository = ซ่อนที่เก็บข้อมูล
5. **หนี้ที่ตั้งใจก่อและมีแผนคืน คือการตัดสินใจที่ถูก** — คุยกับ PM ด้วยตัวเลขเวลาและความเสี่ยง เสนอแบ่งจ่ายทีละ sprint อย่าขอหยุดยาว

### Keyword Map

**Separation of Concerns** → แยกเรื่องแยกห้อง · **Layered** → ชั้นบนเรียกชั้นล่างเท่านั้น · **MVC** → แยกหน้าตา/ข้อมูล/ตัวประสาน · **Clean Architecture** → ธุรกิจอยู่แกนกลาง ลูกศรชี้เข้า

**Controller** → พนักงานรับออเดอร์ ห้ามมี logic · **Service** → ครัว ที่อยู่ของสูตร · **Repository** → บรรณารักษ์ ซ่อนว่าของอยู่ชั้นไหน

**Coupling** → ผูกกันแน่นแค่ไหน อยากให้ต่ำ · **Cohesion** → ของในลิ้นชักเกี่ยวกันไหม อยากให้สูง · **God Object** → คลาสที่ทำทุกอย่าง · **Boundary** → เส้นที่เราตั้งใจตัด

**Dependency** → ของที่เราต้องพึ่ง · **DI** → ยื่นให้ ไม่ใช่ไปหยิบเอง · **IoC** → กลับทิศการควบคุม · **Interface** → สัญญาว่าทำอะไรได้

**S** → เหตุผลที่จะเปลี่ยนมีเหตุผลเดียว · **O** → เพิ่มได้ ไม่ต้องแก้ของเดิม · **L** → ลูกต้องแทนพ่อได้ · **I** → อย่ายัดเยียด method ที่ไม่ใช้ · **D** → พึ่งสัญญา ไม่พึ่งของจริง

**DRY** → ความรู้ธุรกิจอยู่ที่เดียว (ไม่ใช่ห้าม code ซ้ำ) · **KISS** → ง่ายที่สุดที่ยังแก้ปัญหาได้ · **YAGNI** → ยังไม่ใช้ก็ยังไม่ต้องทำ · **duplication ถูกกว่า abstraction ที่ผิด**

**Factory** → ร้านกาแฟ สั่งลาเต้ไม่ต้องรู้เครื่อง · **Strategy** → Google Maps เปลี่ยนโหมดเดินทาง · **Observer** → กดกระดิ่ง subscribe · **Adapter** → หัวแปลงปลั๊ก · **Repository** → บรรณารักษ์

**Technical Debt** → บัตรเครดิต รูดได้แต่ต้องคืน · **Refactoring** → จัดบ้านใหม่ ของเหมือนเดิม ต้องมี test ก่อน · **Rewrite** → ความเสี่ยงสูงสุด ใช้เมื่อเทคโนโลยีตายจริงเท่านั้น

```
        คำถาม architecture ทุกข้อ
                  ↓
   ┌──────────────┼──────────────┐
แบ่งยังไง      ผูกกันแค่ไหน     ลงทุนเมื่อไร
   ↓              ↓              ↓
SoC            Coupling        KISS
Layered        Cohesion        YAGNI
MVC            DI / DIP        Tech Debt
Clean Arch     SOLID           Refactoring
C/S/R          Patterns
```

> **ให้มองภาพนี้ว่า** "ทุกคำถามสถาปัตยกรรมในห้องสัมภาษณ์ตกอยู่ใน 1 ใน 3 กิ่งนี้ — จับให้ได้ก่อนว่าเขาถามกิ่งไหน แล้วค่อยหยิบเครื่องมือในกิ่งนั้นมาตอบ"
