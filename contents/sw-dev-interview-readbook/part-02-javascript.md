## 1. Big Picture

ลองนึกภาพพนักงานร้านกาแฟที่เก่งมาก **แต่มีคนเดียว** และเขาทำได้ทีละอย่างเท่านั้น

ถ้าร้านนี้ทำงานแบบ "ลูกค้าสั่งกาแฟ → ชงเสร็จ → ค่อยรับลูกค้าคนต่อไป" ร้านจะช้ามาก เพราะช่วงที่เครื่องกำลังสกัดกาแฟอยู่ 40 วินาที พนักงานยืนเฉย ๆ ทำอะไรไม่ได้เลย

แต่ร้านกาแฟจริง ๆ ไม่ได้ทำแบบนั้น พนักงานจะ:

1. รับออร์เดอร์ลูกค้า A
2. กดเครื่องสกัด แล้ว**ปล่อยให้เครื่องทำงานเอง**
3. ไปรับออร์เดอร์ลูกค้า B ต่อทันที
4. พอเครื่องของ A เสร็จ ("ปิ๊ง!") ค่อยกลับมาหยิบไปเสิร์ฟ

**JavaScript คือพนักงานคนนั้น** — มีมือเดียว (single-threaded) แต่มี "เครื่องจักรรอบตัว" ที่ทำงานแทนได้ (Web API / libuv) และมี "ระบบเรียกคิว" ที่คอยบอกว่าอันไหนเสร็จแล้วให้กลับมาทำต่อ (Event Loop)

ประโยคเดียวที่ต้องจำให้ได้ก่อนเข้าห้องสัมภาษณ์:

> **JavaScript รันโค้ดทีละบรรทัดด้วย thread เดียว แต่ "ไม่รอ" งานที่ช้า เพราะโยนงานช้าให้สภาพแวดล้อมรอบตัวทำแทน แล้วรับผลกลับมาผ่าน Event Loop**

ทุกเรื่องใน chapter นี้ — Promise, async/await, Microtask, Callback — เป็นแค่ "วิธีเขียน" ของประโยคข้างบนทั้งสิ้น

และอีกครึ่งหนึ่งของ chapter นี้คือเรื่องที่ทำให้ React พัง: **ค่ากับ reference ต่างกันอย่างไร** ซึ่งเป็นรากของคำว่า Mutable / Immutable ที่ React ทั้งตัวสร้างขึ้นมาบนนั้น

## 2. Keywords

| Keyword | จำสั้น ๆ | ความหมาย / ใช้ทำอะไร |
|---|---|---|
| **Runtime** | สนามที่ให้โค้ดวิ่ง | สภาพแวดล้อมที่รัน JavaScript ได้จริง = Engine + API รอบตัว (Browser หรือ Node.js) |
| **Engine (V8)** | เครื่องยนต์แปลโค้ด | ตัวที่อ่าน JavaScript แล้วแปลเป็นคำสั่งเครื่อง มี Call Stack + Heap อยู่ข้างใน |
| **Call Stack** | กองจานที่วางซ้อน | ที่เก็บว่า "ตอนนี้กำลังทำ function อะไรอยู่" เข้าหลัง–ออกก่อน (LIFO) |
| **Heap** | โกดังของ | พื้นที่หน่วยความจำที่เก็บ object / array / function ซึ่งขนาดไม่แน่นอน |
| **Event Loop** | คนเรียกคิว | ตัวคอยดูว่า Stack ว่างไหม ถ้าว่างก็หยิบงานจาก Queue เข้ามาทำ |
| **Web API / libuv** | ลูกน้องที่ทำงานแทน | ส่วนนอก Engine ที่รับงานช้า (timer, network, file) ไปทำเอง |
| **Callback** | ฝากเบอร์ไว้ เดี๋ยวโทรกลับ | function ที่ส่งไปให้คนอื่นถือไว้ เพื่อเรียกกลับเมื่อพร้อม |
| **Promise** | ใบจองคิว | object ที่แทน "ผลลัพธ์ที่จะมาในอนาคต" มี 3 สถานะ pending / fulfilled / rejected |
| **async/await** | เขียน async ให้อ่านเหมือน sync | น้ำตาลเคลือบของ Promise ทำให้โค้ดอ่านบนลงล่างได้ |
| **Microtask** | คิว VIP | คิวของ Promise `.then` — ทำให้หมดก่อนเสมอ |
| **Macrotask** | คิวธรรมดา | คิวของ setTimeout / I/O event — ทำทีละ 1 งานต่อรอบ |
| **Synchronous** | ต่อคิวรอ | ทำเสร็จทีละอย่าง บรรทัดถัดไปต้องรอ |
| **Asynchronous** | ฝากไว้ก่อน | สั่งแล้วไปทำอย่างอื่นต่อ ผลลัพธ์มาทีหลัง |
| **Blocking** | ยืนขวางประตู | งานที่ครองสาย Call Stack จนคนอื่นเข้าไม่ได้ |
| **Non-blocking** | ไม่ขวางทาง | งานที่ปล่อยให้ Stack ว่างระหว่างรอ |
| **Concurrency** | สลับทำหลายงาน | จัดการหลายงานพร้อมกันในเชิงเวลา แต่อาจทำจริงทีละอย่าง |
| **Parallelism** | ทำพร้อมกันจริง | หลายงานเดินพร้อมกันบนหลาย core จริง ๆ |
| **Value (Primitive)** | ก๊อปแล้วแยกร่าง | number, string, boolean, null, undefined, symbol, bigint — คัดลอกค่า |
| **Reference** | ก๊อปแล้วชี้ที่เดิม | object, array, function — คัดลอก "ที่อยู่" ไม่ใช่ตัวของ |
| **Mutable** | แก้ของเดิมได้ | เปลี่ยนข้างในโดยที่ยังเป็น object เดิม |
| **Immutable** | ห้ามแก้ ให้สร้างใหม่ | ไม่แก้ของเดิม แต่สร้างชุดใหม่แทน |
| **Scope** | รั้วบ้านของตัวแปร | ขอบเขตที่ตัวแปรถูกมองเห็น (Global / Function / Block) |
| **Scope Chain** | หาของไล่ออกไปข้างนอก | ถ้าหาตัวแปรในบ้านไม่เจอ ให้ไปหาบ้านแม่ต่อเรื่อย ๆ |
| **Closure** | function ที่จำบ้านเกิด | function ที่ยังเข้าถึงตัวแปรของ scope ที่มันถือกำเนิดได้ แม้ scope นั้นจบไปแล้ว |
| **Hoisting** | ประกาศถูกยกขึ้นบน | การประกาศตัวแปร/function ถูกจองไว้ก่อนโค้ดเริ่มรัน |
| **TDZ** | เขตห้ามแตะ | ช่วงที่ `let`/`const` มีอยู่แล้วแต่ยังใช้ไม่ได้ |
| **Error Handling** | แผนสำรองเมื่อพัง | การดัก error ไม่ให้ทั้งระบบล้ม และให้ข้อมูลพอสำหรับตามหาสาเหตุ |
| **Unhandled Rejection** | Promise พังแล้วไม่มีคนรับ | reject ที่ไม่มี `.catch` — ใน Node.js ทำ process ตายได้ |
| **Starvation** | คิวนอกอดตาย | Microtask ที่ไม่จบสักที ทำให้ Macrotask ไม่ได้คิว |

## 3. Mental Model

ให้มอง JavaScript เป็น **"ครัวที่มีเชฟคนเดียว แต่มีเตาอบหลายตัว"**

| องค์ประกอบในครัว | ตรงกับอะไรใน JavaScript |
|---|---|
| เชฟ 1 คน | Call Stack — ทำได้ทีละงาน |
| โต๊ะเตรียมของ | Heap — วางวัตถุดิบไว้ ใครก็หยิบไปใช้ได้ |
| เตาอบ / หม้อต้ม | Web API หรือ libuv — ทำงานเองได้โดยเชฟไม่ต้องยืนเฝ้า |
| ใบออร์เดอร์ที่เสร็จแล้ว | Callback / Task ที่รออยู่ใน Queue |
| ราวแขวนใบออร์เดอร์ด่วน | Microtask Queue |
| ราวแขวนใบออร์เดอร์ปกติ | Macrotask Queue |
| ผู้จัดการที่คอยยื่นใบให้เชฟ | Event Loop |

กฎเหล็ก 3 ข้อของครัวนี้:

1. **เชฟทำได้ทีละใบเท่านั้น** — ถ้าเชฟติดงานใบหนึ่งนาน ทุกอย่างค้าง (นี่คือ Blocking)
2. **ผู้จัดการจะยื่นใบใหม่ได้ก็ต่อเมื่อมือเชฟว่างสนิท** — ไม่มีการ "แทรกกลางคัน" ระหว่างที่ function กำลังรัน
3. **ใบด่วน (Microtask) ต้องเคลียร์ให้หมดก่อน ถึงจะหยิบใบปกติ (Macrotask) ใบถัดไป**

ถ้าจำกฎ 3 ข้อนี้ได้ คำถามสัมภาษณ์เรื่อง "โค้ดนี้ print อะไรก่อน" จะตอบได้เกือบทั้งหมด

และอีกหนึ่ง mental model ที่คู่กัน: **ตัวแปรใน JavaScript คือ "ป้ายชื่อ" ไม่ใช่ "กล่อง"**

- ถ้าค่าเป็น primitive → ป้ายชื่อเขียนค่านั้นไว้บนตัวป้ายเลย ก๊อปป้ายก็ได้ค่าใหม่แยกกัน
- ถ้าค่าเป็น object → ป้ายชื่อเขียนแค่ "เลขที่บ้าน" ก๊อปป้ายไปกี่ใบก็ชี้บ้านหลังเดิม

## 4. 🧠 ภาพจำ

```
🧠 ภาพจำที่ 1 — JavaScript = เชฟคนเดียว + เตาอบหลายตัว

เชฟ (Call Stack)  ทำได้ทีละงาน
เตาอบ (Web API)   ทำงานเองได้ ไม่กินแรงเชฟ
ผู้จัดการ (Event Loop) ยื่นใบใหม่ให้เชฟ "เฉพาะตอนมือว่าง"
```

```
🧠 ภาพจำที่ 2 — Microtask = คิว VIP, Macrotask = คิวธรรมดา

Macrotask 1 ใบ
      ↓
เคลียร์ Microtask ให้หมดเกลี้ยง
      ↓
Macrotask ใบถัดไป
```

```
🧠 ภาพจำที่ 3 — Value vs Reference

Primitive = ถ่ายเอกสาร      → แก้ฉบับสำเนา ต้นฉบับไม่เปลี่ยน
Object    = แชร์ Google Doc  → ใครแก้ก็เห็นกันหมด เพราะเป็นไฟล์เดียวกัน
```

```
🧠 ภาพจำที่ 4 — Closure = กระเป๋าเป้ที่ function สะพายติดตัว

function เกิดที่ไหน → หยิบของในบ้านนั้นใส่เป้
ย้ายไปอยู่ที่อื่น → ยังเปิดเป้ใช้ของเดิมได้
```

```
🧠 ภาพจำที่ 5 — Promise = ใบจองคิวร้านอาหาร

ได้ใบจอง (pending) → ยังไม่ได้อาหาร แต่มีหลักฐานว่าจะได้
เรียกคิว (fulfilled) → ได้ของ
ของหมด (rejected) → ต้องมีแผนสำรอง (.catch)
```

```
🧠 ภาพจำที่ 6 — Concurrency vs Parallelism

Concurrency = พนักงาน 1 คน สลับดูแลลูกค้า 5 โต๊ะ
Parallelism = พนักงาน 5 คน ดูแลคนละโต๊ะพร้อมกันจริง
```

## 5. How It Works

### 5.1 ภาพรวม Runtime — ชิ้นส่วนทั้งหมดอยู่ตรงไหน

```
┌─────────────────────── JAVASCRIPT RUNTIME ────────────────────────┐
│                                                                    │
│   ┌──────────── ENGINE (V8) ────────────┐                          │
│   │                                      │                          │
│   │   CALL STACK          HEAP           │                          │
│   │   ┌──────────┐      ┌──────────┐    │                          │
│   │   │ frame 3  │      │ {user}   │    │                          │
│   │   │ frame 2  │      │ [items]  │    │                          │
│   │   │ frame 1  │      │ fn()     │    │                          │
│   │   └──────────┘      └──────────┘    │                          │
│   │   ทำทีละ frame       เก็บของขนาดไม่คงที่ │                          │
│   └──────────────────────────────────────┘                          │
│              ↑                    ↓ โยนงานช้าออกไป                   │
│              │                                                      │
│              │           ┌──────────────────────────┐              │
│              │           │  WEB API (Browser)        │              │
│              │           │  หรือ libuv (Node.js)     │              │
│              │           │  - Timer                  │              │
│              │           │  - Network / fetch        │              │
│              │           │  - File I/O               │              │
│              │           │  - DOM Event              │              │
│              │           └────────────┬─────────────┘              │
│              │                        │ งานเสร็จ → ส่ง callback เข้าคิว │
│              │                        ↓                             │
│              │      ┌─────────────────────────────────────┐        │
│              │      │  MICROTASK QUEUE  (คิว VIP)          │        │
│              │      │  Promise.then / queueMicrotask       │        │
│              │      │  process.nextTick (Node)             │        │
│              │      └─────────────────────────────────────┘        │
│              │      ┌─────────────────────────────────────┐        │
│              │      │  MACROTASK QUEUE  (คิวธรรมดา)        │        │
│              │      │  setTimeout / setInterval / I/O      │        │
│              │      └─────────────────────────────────────┘        │
│              │                        ↑                             │
│              └────────────────────────┘                             │
│                     EVENT LOOP                                      │
│         "Stack ว่างหรือยัง? ถ้าว่าง หยิบงานเข้าไปให้"                  │
└────────────────────────────────────────────────────────────────────┘
```

> **ให้มองภาพนี้ว่า** "Engine คือเชฟที่ทำงานได้ทีละอย่าง งานช้าทั้งหมดถูกโยนออกไปนอกครัวให้เครื่องจักรทำแทน แล้ว Event Loop คือผู้จัดการที่คอยยื่นงานที่เสร็จแล้วกลับเข้ามาให้เชฟตอนมือว่างเท่านั้น"

### 5.2 ลำดับการทำงานของ Event Loop (แบบท่องได้)

```
[1] รัน Synchronous code ทั้งหมดจนหมด Call Stack
          ↓
[2] Call Stack ว่าง → เคลียร์ MICROTASK QUEUE จนเกลี้ยง
    (ถ้า microtask สร้าง microtask ใหม่ ก็ต้องทำต่อจนหมด)
          ↓
[3] (ใน Browser) Render / Paint หน้าจอ ถ้าถึงเวลา
          ↓
[4] หยิบ MACROTASK มา 1 งาน แล้วรันจนจบ
          ↓
[5] กลับไปข้อ [2] ใหม่
```

> **ให้มองภาพนี้ว่า** "หนึ่งรอบของ Event Loop คือ ทำงานใหญ่ 1 ชิ้น แล้วเคลียร์งานด่วนที่เกิดขึ้นทั้งหมดให้หมดเกลี้ยง ก่อนจะยอมหยิบงานใหญ่ชิ้นต่อไป"

**จุดที่คนตอบผิดบ่อยที่สุด:** Microtask ไม่ได้ทำทีละ 1 งานแบบ Macrotask — มันทำ **จนหมดคิว** และถ้าระหว่างนั้นมี microtask ใหม่เกิดขึ้น ก็ต้องทำอันนั้นด้วยในรอบเดียวกัน

### 5.3 ตัวอย่างลำดับการทำงานที่คนมักตอบผิด (ข้อสอบคลาสสิก)

```
console.log("A")

setTimeout(() => console.log("B"), 0)

Promise.resolve().then(() => console.log("C"))

console.log("D")
```

คนส่วนใหญ่ตอบ `A → B → C → D` หรือ `A → D → B → C`
**คำตอบจริงคือ `A → D → C → B`**

ไล่ทีละสเต็ป:

| สเต็ป | เกิดอะไรขึ้น | Call Stack | Microtask Q | Macrotask Q | Output |
|---|---|---|---|---|---|
| 1 | รัน `log("A")` | log | - | - | A |
| 2 | เจอ setTimeout → โยนให้ Timer API | - | - | - | A |
| 3 | Timer ครบ 0ms → ส่ง callback เข้า Macrotask | - | - | [B] | A |
| 4 | เจอ `Promise.resolve().then` → เข้า Microtask ทันที | - | [C] | [B] | A |
| 5 | รัน `log("D")` | log | [C] | [B] | A, D |
| 6 | Sync หมด Stack ว่าง → **เคลียร์ Microtask ก่อน** | - | - | [B] | A, D, C |
| 7 | ค่อยหยิบ Macrotask | - | - | - | A, D, C, B |

**ข้อสรุปที่ต้องพูดในห้องสัมภาษณ์:**
> "`setTimeout(fn, 0)` ไม่ได้แปลว่ารันทันที มันแปลว่า 'เอาไปต่อท้าย Macrotask Queue เร็วที่สุดเท่าที่ทำได้' ซึ่งยังไงก็ช้ากว่า Promise callback ที่อยู่ Microtask Queue"

### 5.4 ตัวอย่างที่ยากขึ้น — async/await ปนกับ Promise

```
async function run() {
  console.log("1")
  await null          // ← ทุกอย่างหลังบรรทัดนี้กลายเป็น microtask
  console.log("2")
}
run()
console.log("3")
```

**คำตอบ: `1 → 3 → 2`**

เหตุผลที่ต้องอธิบายให้ได้:

- โค้ดใน async function **ก่อน** `await` ตัวแรก รันแบบ **synchronous** ทันที (ไม่ได้รอรอบ Event Loop)
- คำว่า `await` แปลว่า "หยุดตรงนี้ แล้วเอาโค้ดที่เหลือไปห่อเป็น microtask"
- เพราะฉะนั้น `console.log("3")` ซึ่งเป็น sync ปกติ จึงชนะ `console.log("2")` เสมอ
- แม้ `await null` จะไม่มีอะไรให้รอเลย มันก็ยัง "เสียเวลา 1 รอบ microtask" อยู่ดี

**ประโยคทองสำหรับสัมภาษณ์:**
> "`await` ไม่ได้หยุดทั้งโปรแกรม มันหยุดเฉพาะ function ตัวนั้น แล้วคืน Call Stack ให้คนอื่นใช้ต่อ"

### 5.5 Blocking vs Non-blocking — ภาพที่เห็นความต่างชัดที่สุด

```
BLOCKING (งานหนักกิน CPU / loop ยาว)
เวลา →
[ Call Stack ] ████████████████████████  งานหนัก 5 วินาที
[ คลิกปุ่ม    ]      ✗  ✗  ✗  ✗          กดไม่ติด
[ หน้าจอ      ]      ✗ ค้างทั้งหมด        วาดใหม่ไม่ได้
```

```
NON-BLOCKING (งาน I/O เช่น fetch)
เวลา →
[ Call Stack ] █  ░░░░░░░░░░░░░░░░░  █   ว่างระหว่างรอ
[ Network API ]   ████████████████       เครือข่ายทำงานอยู่ข้างนอก
[ คลิกปุ่ม    ]    ✓  ✓  ✓  ✓            ยังกดได้ปกติ
```

> **ให้มองภาพนี้ว่า** "Blocking คือการที่เชฟยืนคนหม้อนาน 5 นาทีจนไม่มีใครสั่งอาหารได้ ส่วน Non-blocking คือเชฟกดเตาอบแล้วเดินไปรับออร์เดอร์คนอื่นต่อ"

**สิ่งที่ต้องเข้าใจให้ตรง:** `await fetch()` ไม่ได้ทำให้เกิด blocking — เพราะ Call Stack ว่างระหว่างรอ
แต่ `for` loop ที่วน 1,000 ล้านรอบ **เป็น blocking เต็มตัว** ต่อให้เขียนใน async function ก็ตาม เพราะมันครอง Call Stack จริง

### 5.6 Concurrency vs Parallelism

```
CONCURRENCY (JavaScript ทำได้)
Core 1: [A1][B1][A2][C1][B2][A3]     สลับไปมาบน core เดียว
        งาน A, B, C "คืบหน้าพร้อมกัน" ในเชิงเวลา

PARALLELISM (ต้องใช้ Worker / Cluster / หลาย core)
Core 1: [AAAAAAAAAAAA]
Core 2: [BBBBBBBBBBBB]              เดินพร้อมกันจริงในเวลาเดียวกัน
Core 3: [CCCCCCCCCCCC]
```

> **ให้มองภาพนี้ว่า** "Concurrency คือจัดการหลายงานให้เดินหน้าไปด้วยกันได้ ส่วน Parallelism คือมีหลายมือทำจริงพร้อมกัน — JavaScript ได้อย่างแรกฟรี ๆ แต่อย่างหลังต้องขอ thread เพิ่ม"

| ประเภทงาน | JavaScript จัดการได้ดีไหม | ทำไม |
|---|---|---|
| **I/O-bound** (เรียก API, อ่านไฟล์, query DB) | ดีมาก | งานจริงไปเกิดข้างนอก Stack ว่างให้คนอื่นใช้ |
| **CPU-bound** (คำนวณหนัก, เข้ารหัส, resize รูป) | แย่ | ต้องครอง Call Stack จริง → ต้องแยกไป Worker Thread / Web Worker |

### 5.7 Scope และ Scope Chain

```
GLOBAL SCOPE
  │  const appName = "shop"
  │
  ├── FUNCTION SCOPE : checkout()
  │     │  const cartId = "C-01"
  │     │
  │     └── BLOCK SCOPE : if { ... }
  │           const discount = 50
  │
  └── FUNCTION SCOPE : login()
        const userId = "U-99"
```

> **ให้มองภาพนี้ว่า** "Scope คือบ้านซ้อนบ้าน — คนในห้องมองออกไปเห็นของในบ้านใหญ่ได้ แต่คนในบ้านใหญ่มองเข้ามาในห้องไม่ได้"

ตอนหาตัวแปร JavaScript จะเดิน **จากในออกนอก** เท่านั้น (Scope Chain) และ**ไม่มีวันเดินย้อนเข้าไปข้างใน**

### 5.8 Closure — เกิดขึ้นตอนไหน

```
createCounter()  ← เกิด scope ใหม่ { count = 0 }
     ↓ return function ออกมา
createCounter() จบไปแล้ว (frame ออกจาก Stack)
     ↓
แต่ count ยังไม่ถูกลบ เพราะ function ที่ return ออกมายัง "ถืออยู่"
     ↓
เรียก counter() ทีไร → count เพิ่มจากของเดิมเสมอ
```

> **ให้มองภาพนี้ว่า** "Closure คือการที่ function สะพายเป้ที่มีของจากบ้านเกิดติดตัวไปด้วย ต่อให้บ้านเกิดถูกรื้อไปแล้วของในเป้ก็ยังอยู่"

pseudocode สั้นที่สุดที่อธิบาย closure ได้:

```
function makeCounter() {
  let count = 0                 // ตัวแปรใน scope แม่
  return () => ++count          // function ลูกยัง "จำ" count ได้
}
```

**ใช้จริงตอนไหน:** ซ่อนข้อมูลไม่ให้ข้างนอกแก้ตรง ๆ (private state), ทำ debounce / throttle, ทำ cache ในตัว, และคือกลไกเบื้องหลัง `useState` ของ React

### 5.9 Value vs Reference

```
PRIMITIVE (เก็บค่าตรง ๆ)
let a = 10
let b = a        →  a:[10]   b:[10]     คนละกล่อง
b = 20           →  a:[10]   b:[20]     a ไม่เปลี่ยน

OBJECT (เก็บที่อยู่)
let x = { n: 1 }
let y = x        →  x:[→#001]  y:[→#001]   ชี้ที่เดียวกัน
y.n = 99         →  x.n ก็กลายเป็น 99 ด้วย
```

> **ให้มองภาพนี้ว่า** "Primitive คือถ่ายเอกสารแยกฉบับ ส่วน Object คือแชร์ลิงก์ไฟล์เดียวกัน ใครแก้ก็เห็นกันหมด"

### 5.10 Error Handling — เส้นทางของ error

```
[โค้ดพัง]
    ↓
มี try/catch ครอบไหม? ──มี──→ catch จับ → log / แสดงข้อความ / retry
    ↓ ไม่มี
โยนขึ้น (bubble up) หา caller ชั้นถัดไป
    ↓
ไม่มีใครจับจนถึงบนสุด
    ↓
Browser: error หลุดออก console, UI อาจค้าง
Node.js: uncaughtException → process ตาย
```

> **ให้มองภาพนี้ว่า** "Error เหมือนลูกบอลที่เด้งขึ้นไปหาคนชั้นบนเรื่อย ๆ ถ้าไม่มีใครรับ มันจะตกทะลุออกนอกอาคาร"

**กับดักสำคัญ:** `try/catch` แบบ synchronous **จับ error ใน callback ที่รันทีหลังไม่ได้** เพราะตอน callback รัน `try` block จบไปนานแล้ว (frame ออกจาก Stack ไปแล้ว) — ต้องใช้ `.catch()` หรือ `try/catch` ที่ครอบ `await` แทน

## 6. Example — Scenario จากงานจริง

### Scenario 1: ปุ่ม Export Excel ทำให้ทั้งหน้าค้าง

**อาการ:** ผู้ใช้กดปุ่ม Export รายงาน 50,000 แถว แล้วหน้าเว็บค้างไป 8 วินาที กดอะไรไม่ได้เลย ปุ่มก็ไม่มี loading

**สาเหตุ:** โค้ดวน loop แปลงข้อมูล 50,000 แถวใน Call Stack ตรง ๆ → เป็น CPU-bound → blocking

**สิ่งที่ Junior มักตอบ:** "ใส่ `async` ให้ function สิ")
→ **ผิด** เพราะ `async` ไม่ได้ย้ายงานออกจาก Call Stack มันแค่ทำให้ function คืนค่าเป็น Promise

**ทางแก้ที่ถูก (เรียงตามลำดับที่ควรพิจารณา):**

| ทางเลือก | เหมาะเมื่อ | trade-off |
|---|---|---|
| ย้ายไป Web Worker | งานหนักจริง ต้องทำที่ frontend | เพิ่มความซับซ้อน ส่งข้อมูลข้าม thread มีต้นทุน |
| แบ่งงานเป็นก้อน (chunk) แล้วคั่นด้วย `setTimeout` | อยากได้ผลเร็ว เขียนง่าย | ช้ากว่าเดิมเล็กน้อย แต่ UI ไม่ค้าง |
| ย้ายไปทำที่ Backend แล้วส่งไฟล์กลับ | ข้อมูลใหญ่มาก / มี logic ธุรกิจ | ต้องมี endpoint ใหม่ + จัดการไฟล์ |

### Scenario 2: กด Submit สองครั้ง แล้วเกิดออร์เดอร์ซ้ำ

**อาการ:** ผู้ใช้กดปุ่มสั่งซื้อรัว ๆ 2 ครั้ง เกิดคำสั่งซื้อซ้ำในระบบ

**สาเหตุเชิง concept:** เพราะ `fetch` เป็น non-blocking — ระหว่างที่คำขอแรกยังลอยอยู่ข้างนอก Call Stack **ว่าง** ผู้ใช้จึงกดปุ่มซ้ำได้ และ event ครั้งที่สองก็เข้าคิวมาทำงานได้ตามปกติ

**ทางแก้:** ต้องมี state กันไว้เอง (`isSubmitting`) — ซึ่งจริง ๆ คือ closure ตัวหนึ่งที่จำสถานะไว้ — บวกกับฝั่ง server ต้องมี idempotency key รองรับ เพราะ frontend กันได้ไม่ 100%

**ประโยคที่ควรพูดตอนสัมภาษณ์:**
> "Non-blocking ให้ความลื่นไหลกับผู้ใช้ แต่แลกมาด้วยหน้าต่างเวลาที่ระบบยังไม่มีคำตอบ — ต้องออกแบบ UI และ backend ให้รับมือช่วงนั้นเสมอ"

### Scenario 3: ค่าใน React ไม่ยอมอัปเดต ทั้งที่แก้แล้ว

**อาการ:** `todos.push(newItem)` แล้ว `setTodos(todos)` แต่หน้าจอไม่เปลี่ยน

**สาเหตุ:** `push` เป็นการ **mutate** array เดิม → reference ยังเป็นตัวเดิม → React เปรียบเทียบด้วย reference แล้วเห็นว่า "ของเดิม" → ไม่ re-render

**ทางแก้เชิง concept:** ต้องสร้าง array ใหม่ (`[...todos, newItem]`) เพื่อให้ได้ reference ใหม่

**นี่คือจุดที่เชื่อม PART 2 → PART 3 โดยตรง:** ที่ React บังคับ immutability ไม่ใช่เรื่องความสวยงามของโค้ด แต่เพราะมันเช็คการเปลี่ยนแปลงด้วยการเทียบ reference ซึ่งเร็วกว่าการไล่เทียบทุก field มหาศาล

### Scenario 4: API ช้า 3 ตัว เรียกทีละตัว → หน้าโหลด 6 วินาที

**อาการ:** หน้า Dashboard ต้องเรียก 3 API แต่ละตัวใช้เวลา 2 วินาที รวมเป็น 6 วินาที

**สาเหตุ:** เขียน `await` เรียงกัน 3 บรรทัด → กลายเป็น **Sequential** ทั้งที่ทั้ง 3 ตัวไม่ได้ขึ้นต่อกัน

```
Sequential:   [API-A 2s][API-B 2s][API-C 2s]   = 6s
Parallel:     [API-A 2s]
              [API-B 2s]                        = 2s
              [API-C 2s]
```

> **ให้มองภาพนี้ว่า** "การใส่ await เรียงกันเหมือนเข้าคิวซื้อของ 3 ร้านทีละร้าน ทั้งที่ควรจะส่งคนไป 3 ร้านพร้อมกันแล้วมารอเจอกันที่จุดนัด"

**ทางแก้:** ยิงทั้งสามพร้อมกันแล้วค่อยรอรวม (`Promise.all`)

**trade-off ที่ต้องพูดต่อ:** `Promise.all` จะพังทั้งชุดถ้ามีตัวใดตัวหนึ่ง reject — ถ้าอยากได้ผลเท่าที่สำเร็จให้ใช้ `Promise.allSettled` แทน และถ้ายิงพร้อมกันเยอะเกินไปก็อาจโดน rate limit ของ server ต้องจำกัดจำนวนพร้อมกัน

### Scenario 5: Production ตายกลางดึกเพราะ Promise ตัวเดียว

**อาการ:** Node.js service ดับเอง log ท้ายสุดเขียนว่า `UnhandledPromiseRejection`

**สาเหตุ:** มี async function ที่ถูกเรียกแบบ "ยิงแล้วลืม" (fire and forget) ไม่มี `.catch()` พอ API ปลายทางล่ม Promise จึง reject โดยไม่มีคนรับ

**บทเรียน:** ทุก Promise ต้องมีเจ้าของเสมอ — ไม่ `await` มันก็ต้อง `.catch()` มัน และควรมี global handler (`unhandledRejection`) ไว้ log เป็นตาข่ายสุดท้าย ไม่ใช่ไว้ซ่อนปัญหา

## 7. Compare

### 7.1 Sync vs Async vs Blocking vs Non-blocking

| หัวข้อ | Synchronous | Asynchronous |
|---|---|---|
| ลำดับการทำงาน | บรรทัดถัดไปรอจนบรรทัดนี้เสร็จ | สั่งแล้วไปต่อ ผลมาทีหลัง |
| ผลต่อ Call Stack | ครองไว้จนจบ | คืน Stack ระหว่างรอ |
| ตัวอย่าง | loop, การคำนวณ, `JSON.parse` | `fetch`, `setTimeout`, อ่านไฟล์ |
| เหมาะกับ | logic ที่ต้องได้คำตอบทันที | งาน I/O ที่ใช้เวลาไม่แน่นอน |

| หัวข้อ | Blocking | Non-blocking |
|---|---|---|
| มองจากมุมไหน | มองจาก "ระบบทั้งหมดเดินต่อได้ไหม" | เช่นกัน |
| ระหว่างรอเกิดอะไร | ไม่มีใครทำงานได้เลย | คนอื่นทำงานต่อได้ |
| ตัวอย่างใน JS | `while` loop ยาว, `alert()` | `await fetch()` |

**กับดักที่คนสับสนที่สุด:**
`await` = asynchronous แต่ **อ่านเหมือน** synchronous
ส่วน CPU-heavy loop ที่อยู่ใน async function = asynchronous ในเชิง syntax แต่ **blocking จริง** ในเชิงพฤติกรรม

> จำสั้น: **Sync/Async = "ลำดับโค้ด"** / **Blocking/Non-blocking = "คนอื่นทำงานต่อได้ไหม"**

### 7.2 Callback vs Promise vs async/await

| หัวข้อ | Callback | Promise | async/await |
|---|---|---|---|
| รูปแบบ | ส่ง function เข้าไป | ได้ object กลับมา | เขียนบนลงล่าง |
| อ่านง่าย | ยากเมื่อซ้อนลึก (callback hell) | ดีขึ้น แต่ `.then` ต่อกันยาวก็อ่านยาก | อ่านง่ายที่สุด |
| จัดการ error | ต้องเช็ค `err` ทุกชั้นเอง | `.catch()` รวบได้ | `try/catch` ปกติ |
| ทำงานพร้อมกันหลายตัว | ต้องเขียนเองทั้งหมด | `Promise.all` / `allSettled` / `race` | ใช้ `Promise.all` ร่วมได้ |
| ยังเจอที่ไหน | library เก่า, Node API เดิม, event listener | ทุกที่ | โค้ดสมัยใหม่ |
| ข้อควรระวัง | nesting ลึก, เรียกซ้ำ 2 ครั้ง | ลืม return ใน `.then` | ใส่ await เรียงกันจนกลายเป็น sequential |

**สิ่งที่ต้องรู้:** `async/await` ไม่ได้ "แทนที่" Promise — มันคือ Promise ที่ถูกห่อให้อ่านง่ายขึ้น ข้างในยังเป็น Promise ทุกประการ

### 7.3 Microtask vs Macrotask

| หัวข้อ | Microtask | Macrotask |
|---|---|---|
| ใครอยู่ในคิวนี้ | `Promise.then`, `await` ต่อ, `queueMicrotask`, `process.nextTick` | `setTimeout`, `setInterval`, `setImmediate`, I/O callback, UI event |
| ทำกี่งานต่อรอบ | **ทำจนหมดคิว** | ทำทีละ 1 งาน |
| ลำดับความสำคัญ | สูงกว่าเสมอ | รองลงมา |
| อันตรายที่ต้องระวัง | ถ้าสร้างต่อเนื่องไม่จบ → Macrotask อดตาย (starvation) → UI ค้าง | หน่วงเวลาไม่แม่นยำ 100% |

### 7.4 Value vs Reference / Mutable vs Immutable

| หัวข้อ | Primitive (by value) | Object (by reference) |
|---|---|---|
| ตอน assign | คัดลอกค่า | คัดลอกที่อยู่ |
| เทียบด้วย `===` | เทียบค่าจริง | เทียบว่าเป็นตัวเดียวกันไหม |
| แก้แล้วกระทบที่อื่น | ไม่ | กระทบทุกคนที่ถืออยู่ |
| ตัวอย่างพัง | แทบไม่มี | แก้ state ใน React แล้วไม่ re-render |

| หัวข้อ | Mutable | Immutable |
|---|---|---|
| วิธีเปลี่ยนค่า | แก้ของเดิม (`push`, `splice`, `sort`) | สร้างชุดใหม่ (`[...arr]`, `map`, `filter`) |
| ข้อดี | ประหยัดหน่วยความจำ เร็วกว่าในงานใหญ่มาก ๆ | ตรวจการเปลี่ยนแปลงง่าย ย้อนกลับได้ ปลอดภัยกว่า |
| ข้อเสีย | bug แบบ "ใครไปแก้ก็ไม่รู้" | สร้าง object ใหม่บ่อย |
| ใช้เมื่อ | loop ภายใน function ที่ไม่มีใครเห็น | ทุกอย่างที่เป็น shared state โดยเฉพาะ React state |

**เตือน:** `const` ไม่ได้ทำให้ immutable — มันแค่ห้าม assign ตัวแปรใหม่ แต่ข้างใน object ยังแก้ได้หมด

### 7.5 Shallow Copy vs Deep Copy

| หัวข้อ | Shallow Copy | Deep Copy |
|---|---|---|
| คัดลอกลึกแค่ไหน | ชั้นบนสุดชั้นเดียว | ทุกชั้น |
| วิธีทั่วไป | spread `{...obj}` | `structuredClone()` หรือ library |
| ปัญหาที่เจอ | object ซ้อนชั้นในยังชี้ที่เดิม → แก้แล้วกระทบต้นฉบับ | ช้ากว่า และอาจ copy ของที่ไม่ควร copy |
| ใช้เมื่อ | state ตื้น 1-2 ชั้น (ส่วนใหญ่ของงานจริง) | ต้องตัดขาดจากต้นฉบับจริง ๆ |

### 7.6 var vs let vs const

| หัวข้อ | var | let | const |
|---|---|---|---|
| Scope | Function | Block | Block |
| Hoisting | ยกขึ้น + ได้ `undefined` | ยกขึ้นแต่ติด TDZ | ยกขึ้นแต่ติด TDZ |
| ประกาศซ้ำชื่อเดิม | ได้ | ไม่ได้ | ไม่ได้ |
| assign ใหม่ | ได้ | ได้ | ไม่ได้ |
| ควรใช้ | เลี่ยง | เมื่อค่าต้องเปลี่ยน | เป็น default |

### 7.7 Browser Runtime vs Node.js Runtime

| หัวข้อ | Browser | Node.js |
|---|---|---|
| Engine | V8 (Chrome), SpiderMonkey (Firefox) ฯลฯ | V8 |
| ส่วนที่ทำงานช้าแทน | Web API | libuv (มี thread pool ข้างใน) |
| มีอะไรพิเศษ | DOM, `window`, `localStorage`, `fetch` | File System, Process, Buffer, Stream |
| Microtask พิเศษ | ไม่มี | `process.nextTick` (มาก่อน Promise ด้วยซ้ำ) |
| เมื่อ error หลุด | log ที่ console, หน้าอาจยังใช้ได้ | process ตายได้ |
| หลักการ Event Loop | **เหมือนกัน** | **เหมือนกัน** (Node มี phase ละเอียดกว่า) |

## 8. Common Mistakes

| # | ความเข้าใจผิด | ความจริง |
|---|---|---|
| 1 | "JavaScript เป็น multi-threaded เพราะทำงานพร้อมกันได้" | JavaScript รันโค้ดด้วย thread เดียว สิ่งที่พร้อมกันคือ **สภาพแวดล้อมรอบตัว** ไม่ใช่โค้ดของเรา |
| 2 | "`setTimeout(fn, 0)` คือรันทันที" | คือ "เอาไปต่อท้าย Macrotask Queue" ซึ่งต้องรอ sync code + microtask ทั้งหมดก่อนเสมอ |
| 3 | "`setTimeout(fn, 1000)` รันตรงเป๊ะที่ 1 วินาที" | เป็นเวลา **ขั้นต่ำ** ถ้า Stack ยังไม่ว่างก็ต้องรอต่อ |
| 4 | "ใส่ `async` แล้วงานหนักจะไม่ทำให้ค้าง" | `async` ไม่ได้ย้ายงานออกจาก Call Stack — CPU-bound ยังค้างเหมือนเดิม |
| 5 | "`await` หยุดทั้งโปรแกรมรอ" | หยุดเฉพาะ async function ตัวนั้น โค้ดอื่นเดินต่อได้ |
| 6 | "Promise ทำให้เร็วขึ้น" | Promise แค่จัดระเบียบ async ไม่ได้ทำให้ network หรือ disk เร็วขึ้น |
| 7 | "`const` = ค่าเปลี่ยนไม่ได้" | ห้ามแค่ assign ตัวแปรใหม่ ข้างใน object ยังแก้ได้ |
| 8 | "spread `{...obj}` คือ deep copy" | เป็น shallow copy — object ชั้นในยังชี้ที่เดิม |
| 9 | "`arr1 === arr2` ถ้าข้างในเหมือนกันจะได้ true" | เทียบ reference ไม่ใช่เนื้อหา — สอง array ที่ข้างในเหมือนกันเป๊ะก็ยังได้ `false` |
| 10 | "`try/catch` ครอบไว้แล้วจับได้ทุก error" | จับ async error ที่รันทีหลังไม่ได้ ต้อง `await` ในนั้นหรือใช้ `.catch()` |
| 11 | "Closure คือ feature พิเศษที่ต้องตั้งใจใช้" | มันเกิดอัตโนมัติทุกครั้งที่ function ถูกสร้างใน scope อื่น |
| 12 | "Callback = asynchronous เสมอ" | callback ของ `map` / `forEach` เป็น synchronous ล้วน ๆ |
| 13 | "`Promise.all` รันเร็วขึ้นเพราะทำ parallel จริง" | มันคือ concurrency — ทุกงานถูกยิงออกไปข้างนอกพร้อมกัน แต่โค้ด JS ยังรันทีละอย่าง |
| 14 | "ถ้าไม่มี error แปลว่าโค้ด async ทำงานเสร็จแล้ว" | Promise ที่ลืม `await` อาจยังทำงานค้างอยู่หรือ reject เงียบ ๆ |
| 15 | "Memory leak ไม่เกิดใน JavaScript เพราะมี Garbage Collector" | GC เก็บเฉพาะของที่ **ไม่มีใครถืออยู่** — closure, event listener, timer ที่ลืมเคลียร์ ล้วนเป็น "คนถือ" |

## 9. Debugging

### 9.1 เจอ "หน้าเว็บค้าง / กดไม่ติด"

```
[1] เปิด DevTools → Performance → อัด 5 วินาทีช่วงที่ค้าง
        ↓
[2] ดู Main thread มีแท่งยาวสีเดียวยาวเกิน 50ms ไหม
        ↓
[3] มี → เป็น Blocking จาก CPU งานหนัก หรือ loop ยาว
    ไม่มี → ไปดู Network ว่ามีคำขอที่ไม่จบไหม
        ↓
[4] ระบุ function ที่กินเวลา → ถามว่า "อันนี้ต้องทำใน main thread จริงไหม"
        ↓
[5] ทางแก้: แบ่ง chunk / ย้ายไป Worker / ย้ายไป Backend
```

> **ให้มองภาพนี้ว่า** "หาว่าเชฟติดงานอะไรอยู่ แล้วถามว่างานนั้นย้ายออกนอกครัวได้ไหม"

### 9.2 เจอ "ลำดับการทำงานไม่เป็นอย่างที่คิด"

| ถามตัวเองตามลำดับ | ถ้าใช่แปลว่า |
|---|---|
| โค้ดนี้เป็น sync หรือ async? | ถ้า async อย่าคาดหวังว่ามันเสร็จในบรรทัดถัดไป |
| ตัวที่ผิดลำดับอยู่ใน Microtask หรือ Macrotask? | Promise จะมาก่อน setTimeout เสมอ |
| มี `await` ที่ลืมใส่ไหม? | function คืน Promise แต่เราใช้ค่านั้นเหมือนเป็นค่าจริง |
| ลืม `return` ใน `.then` ไหม? | chain ถัดไปจะได้ `undefined` |
| เขียน `await` เรียงกันทั้งที่ไม่ขึ้นต่อกันไหม? | ช้าโดยไม่จำเป็น — ควรยิงพร้อมกัน |

### 9.3 เจอ "ค่าเปลี่ยนเองโดยไม่รู้ตัว"

```
[1] ตัวแปรนี้เป็น object หรือ array ไหม → ถ้าใช่ มีโอกาสเป็นเรื่อง reference
        ↓
[2] มีใครได้รับตัวนี้ไปบ้าง (ส่งเป็น argument / เก็บใน state / ใส่ใน array)
        ↓
[3] ในทางนั้นมีการเรียก method ที่ mutate ไหม (push, splice, sort, reverse)
        ↓
[4] ทดสอบด้วยการ copy ก่อนส่งต่อ → ถ้าอาการหาย ยืนยันว่าเป็น shared reference
        ↓
[5] แก้ถาวร: บังคับ immutable ตรงจุดที่ข้อมูลถูกแชร์
```

> **ให้มองภาพนี้ว่า** "ไล่หาว่าใครบ้างที่ถือกุญแจบ้านหลังเดียวกันอยู่ แล้วคนไหนเผลอเข้าไปย้ายเฟอร์นิเจอร์"

### 9.4 เจอ "Error ไม่มีใน log แต่ระบบพัง"

| ตรวจอะไร | เพราะอะไร |
|---|---|
| มี Promise ที่ไม่มี `.catch` ไหม | reject เงียบ ๆ ไม่ขึ้น log |
| มี `catch (e) {}` ว่างเปล่าไหม | กลืน error ทิ้งโดยไม่บอกใคร |
| catch แล้ว log แค่ `e.message` ไหม | หาย stack trace → ตามหาต้นตอไม่ได้ |
| มี global handler ไหม (`unhandledrejection` / `uncaughtException`) | เป็นตาข่ายสุดท้ายก่อนเงียบหาย |
| error ข้าม async boundary ไหม | stack trace อาจขาดตอน ต้องแนบ context เอง |

### 9.5 เจอ "Memory ขึ้นเรื่อย ๆ ไม่ลง"

```
[1] DevTools → Memory → ถ่าย Heap Snapshot 2 ครั้ง ห่างกัน
        ↓
[2] เทียบว่า object ชนิดไหนเพิ่มขึ้นและไม่เคยลด
        ↓
[3] ไล่หา "ใครถืออยู่" (retainer path)
        ↓
[4] ผู้ต้องสงสัยประจำ:
    - setInterval ที่ไม่เคย clear
    - event listener ที่ไม่เคย remove
    - closure ที่ยังถือ object ใหญ่ไว้
    - array ที่เอาแต่ push ไม่เคยล้าง (เช่น cache ไม่มี TTL)
        ↓
[5] แก้ที่ "คนถือ" ไม่ใช่ที่ "ของ"
```

> **ให้มองภาพนี้ว่า** "Garbage Collector จะเก็บของก็ต่อเมื่อไม่มีใครถืออยู่ — ดังนั้นต้องตามหาคนที่ยังไม่ปล่อยมือ ไม่ใช่ตามหาของ"

## 10. Interview Questions

### 🟢 Junior

| คำถาม | สิ่งที่เขาอยากฟัง |
|---|---|
| JavaScript เป็น single-threaded หมายความว่าอะไร | รันโค้ดทีละอย่างด้วย Call Stack เดียว แต่ไม่ได้แปลว่าช้า เพราะโยนงาน I/O ออกไปข้างนอกได้ |
| Synchronous ต่างจาก Asynchronous อย่างไร | sync = บรรทัดถัดไปต้องรอ, async = สั่งแล้วไปต่อ ผลมาทีหลัง |
| Callback คืออะไร | function ที่ส่งไปให้คนอื่นถือไว้ เพื่อเรียกกลับตอนงานเสร็จ |
| Promise มีกี่สถานะ | pending / fulfilled / rejected และเปลี่ยนได้ครั้งเดียวเท่านั้น |
| `var`, `let`, `const` ต่างกันอย่างไร | scope, การ assign ใหม่, hoisting/TDZ |
| `==` กับ `===` ต่างกันอย่างไร | `==` แปลงชนิดให้ก่อน, `===` เทียบชนิดด้วย — ใช้ `===` เป็น default |
| Scope คืออะไร | ขอบเขตการมองเห็นตัวแปร มองจากในออกนอกได้ทางเดียว |

### 🟡 Mid

| คำถาม | สิ่งที่เขาอยากฟัง |
|---|---|
| อธิบาย Event Loop | ต้องพูดครบ Call Stack + Web API/libuv + 2 Queue + กฎ "microtask เคลียร์หมดก่อน macrotask ถัดไป" |
| Microtask ต่างจาก Macrotask อย่างไร | ใครอยู่คิวไหน + microtask ทำจนหมดคิว macrotask ทำทีละ 1 |
| Closure คืออะไร ใช้ทำอะไรจริง | function จำ scope ที่เกิด + ตัวอย่าง private state / debounce / useState |
| ทำไม React ถึงบังคับ immutable | เพราะเช็คการเปลี่ยนแปลงด้วย reference comparison ซึ่งเร็วกว่าเทียบทุก field |
| Blocking กับ Non-blocking ต่างจาก Sync/Async อย่างไร | sync/async คือลำดับโค้ด, blocking/non-blocking คือ "คนอื่นทำงานต่อได้ไหม" |
| `Promise.all` กับ `Promise.allSettled` ต่างกันอย่างไร | all พังทั้งชุดเมื่อมีตัวหนึ่ง reject, allSettled คืนผลทุกตัวพร้อมสถานะ |
| `try/catch` จับ error ของ async ได้ไหม | ได้ถ้าครอบ `await`, ไม่ได้ถ้าเป็น callback ที่รันทีหลัง |
| Shallow copy กับ deep copy ต่างกันอย่างไร ใช้ตอนไหน | ลึกกี่ชั้น + ปัญหา nested object + ต้นทุนของ deep copy |

### 🔴 Senior

| คำถาม | สิ่งที่เขาอยากฟัง |
|---|---|
| ถ้าต้องทำงาน CPU-heavy บน frontend จะออกแบบอย่างไร | วัดก่อน → แบ่ง chunk / Web Worker / ย้ายไป backend พร้อม trade-off แต่ละทาง |
| Concurrency กับ Parallelism ต่างกันอย่างไรใน JavaScript | JS ได้ concurrency ฟรี แต่ parallelism ต้อง Worker/Cluster + บอกว่างานแบบไหนต้องการอันไหน |
| Microtask starvation คืออะไร เกิดเมื่อไร | microtask สร้าง microtask ต่อไม่จบ → macrotask + render ไม่ได้คิว → UI ค้างทั้งที่ CPU ดูไม่ตัน |
| ออกแบบ error handling ของทั้ง app อย่างไร | แบ่ง expected vs unexpected error, จุดรวมศูนย์, ไม่กลืน error, แนบ context/trace id, มี global fallback |
| Memory leak ใน JavaScript เกิดจากอะไร ตรวจอย่างไร | อธิบาย reachability + ผู้ต้องสงสัยประจำ + วิธีอ่าน heap snapshot |
| ทำไม `async/await` ถึงไม่ใช่ตัวแทนของ Promise ทั้งหมด | await ทำให้ควบคุมงานพร้อมกันยากขึ้นถ้าใช้ไม่ระวัง — ยังต้องใช้ `Promise.all`/`race` |
| จะทำ retry ที่ปลอดภัยกับ async operation อย่างไร | ต้องมี timeout, exponential backoff, จำกัดจำนวนครั้ง, ต้อง idempotent ฝั่ง server |
| อธิบายให้ Junior ฟังว่าทำไม `setTimeout(fn, 0)` ไม่ใช่ทันที | ต้องเล่าผ่าน Event Loop โดยไม่ใช้ศัพท์ยาก — วัดความสามารถในการสอนคนอื่น |

## 11. Answer Like a Developer

### โครงการตอบ 4 ชั้น (ใช้ได้กับทุกคำถามใน chapter นี้)

```
[1] นิยามสั้น 1 ประโยค  (ภาษาคน ไม่ใช่ศัพท์)
      ↓
[2] มันแก้ปัญหาอะไร      (ทำไมถึงมีสิ่งนี้)
      ↓
[3] ตัวอย่างจากงานจริง   (เคยเจอตอนไหน)
      ↓
[4] trade-off / ข้อควรระวัง (ทำให้ดูเหมือนคนเคยเจอของจริง)
```

> **ให้มองภาพนี้ว่า** "ตอบเหมือนเล่าเรื่องให้เพื่อนฟัง ไม่ใช่ท่องนิยามจากหนังสือ"

### ตัวอย่างที่ 1 — "อธิบาย Event Loop"

**แบบท่องจำ (คะแนนต่ำ):**
> "Event Loop คือกลไกที่คอยตรวจสอบ Call Stack และ Callback Queue ครับ"

**แบบตอบเหมือน Developer:**
> "JavaScript รันโค้ดด้วย thread เดียวครับ เพราะฉะนั้นถ้ามันรอ network จริง ๆ ทุกครั้ง หน้าเว็บจะค้างตลอด
> สิ่งที่มันทำจริงคือโยนงานช้าอย่าง timer หรือ fetch ออกไปให้ Web API ข้างนอกทำ พอเสร็จแล้ว callback จะถูกส่งเข้าคิว
> Event Loop มีหน้าที่แค่คอยดูว่า Call Stack ว่างหรือยัง ถ้าว่างก็หยิบงานจากคิวเข้ามา
> จุดที่ผมเคยพลาดจริงคือ คิวมีสองอัน — Microtask ของ Promise จะถูกเคลียร์จนหมดก่อน Macrotask อย่าง setTimeout เสมอ
> ตอนนั้นผมเขียน log ไว้ทั้ง `.then` และ `setTimeout(0)` แล้วงงว่าทำไมลำดับไม่ตรง ซึ่งพอเข้าใจสองคิวนี้ก็อธิบายได้หมดครับ"

**ทำไมคำตอบนี้ได้คะแนน:** มี why → mechanism → ประสบการณ์จริง → ความละเอียดที่คนอ่านผ่าน ๆ ไม่รู้

### ตัวอย่างที่ 2 — "Closure คืออะไร"

**โครงที่ควรใช้:**

1. นิยาม: "function ที่ยังเข้าถึงตัวแปรของ scope ที่มันเกิดได้ แม้ scope นั้นจบไปแล้ว"
2. ทำไมถึงมี: "เพราะ JavaScript หาตัวแปรจากที่ function **ถูกสร้าง** ไม่ใช่ที่ function **ถูกเรียก**"
3. ใช้จริง: "ทำ private state, debounce, และเบื้องหลัง `useState` ของ React ก็คือ closure"
4. ข้อควรระวัง: "ถ้า closure ถือ object ใหญ่ไว้แล้วตัวมันเองไม่ถูกปล่อย ก็กลายเป็น memory leak ได้"

### ตัวอย่างที่ 3 — "ทำไมหน้าเว็บค้าง"

**โครงที่ควรใช้ (คำถามแนว debugging ต้องตอบเป็นกระบวนการ ไม่ใช่คำตอบเดียว):**

1. แยกก่อนว่า "ค้างเพราะ CPU" หรือ "ช้าเพราะรอ network" — สองอันนี้แก้คนละทาง
2. บอกวิธีพิสูจน์: อัด Performance profile ดู main thread
3. ถ้าเป็น CPU: อธิบายว่างานนั้นครอง Call Stack → ตัวเลือกคือแบ่ง chunk / Worker / ย้ายไป backend
4. ปิดท้ายด้วยหลักการ: "ผมจะวัดก่อนแก้เสมอ เพราะเดาผิดแล้วเสียเวลา optimize ผิดจุด"

### ประโยคที่ควรมีติดตัว

## 12. One-Minute Review

อ่านย่อหน้านี้ 1 นาทีก่อนเข้าห้อง:

**JavaScript รันด้วย thread เดียว** มี **Call Stack** ไว้ทำงานทีละชิ้น และ **Heap** ไว้เก็บ object งานที่ช้า (timer, network, file) ไม่ได้ทำใน Engine แต่ถูกโยนออกไปให้ **Web API** (browser) หรือ **libuv** (Node.js) พอเสร็จแล้ว callback จะเข้าคิว — **Microtask Queue** สำหรับ Promise และ **Macrotask Queue** สำหรับ setTimeout/I/O

**Event Loop** มีหน้าที่เดียวคือ: Stack ว่างเมื่อไร ให้เคลียร์ **Microtask จนหมดคิว** ก่อน แล้วค่อยหยิบ **Macrotask ทีละ 1 งาน** — นี่คือเหตุผลที่ `Promise.then` ชนะ `setTimeout(fn, 0)` เสมอ

**Sync/Async = ลำดับโค้ด** ส่วน **Blocking/Non-blocking = คนอื่นทำงานต่อได้ไหม** งาน **I/O-bound** JavaScript จัดการได้ดีมาก แต่ **CPU-bound** จะ block ทุกอย่าง ต้องย้ายไป Worker หรือ backend
**Concurrency** = สลับทำหลายงานบน thread เดียว (JS ได้ฟรี) **Parallelism** = ทำพร้อมกันจริงบนหลาย core (ต้องขอ thread เพิ่ม)

**Primitive คัดลอกค่า / Object คัดลอก reference** — นี่คือรากของ Mutable vs Immutable และเป็นเหตุผลที่ React บังคับให้สร้าง object ใหม่แทนการ mutate ของเดิม `const` ไม่ได้แปลว่า immutable และ spread ไม่ใช่ deep copy

**Scope** คือรั้วการมองเห็นตัวแปร มองจากในออกนอกได้ทางเดียว **Closure** คือ function ที่จำ scope ที่มันเกิดได้ ซึ่งเป็นเบื้องหลังของ private state และ `useState`

**Error Handling** ที่ดีคือไม่กลืน error, แนบ context ให้ตามต่อได้, `try/catch` ต้องครอบ `await` ไม่ใช่ครอบ callback และทุก Promise ต้องมีคนรับผิดชอบเสมอ

## 13. Memory Card

### จำ 5 อย่าง

1. **JavaScript มีเชฟคนเดียว** — Call Stack ทำงานทีละชิ้น งานช้าถูกโยนออกไปให้ Web API / libuv ทำแทน
2. **Microtask เคลียร์จนหมดก่อน Macrotask ถัดไป** — เพราะงั้น `Promise.then` ชนะ `setTimeout(0)` เสมอ
3. **Sync/Async คือลำดับโค้ด / Blocking/Non-blocking คือคนอื่นทำงานต่อได้ไหม** — `await fetch` ไม่ block แต่ loop ยาว block
4. **Object คัดลอก reference ไม่ใช่ค่า** — นี่คือเหตุผลทั้งหมดที่ React บังคับ immutable
5. **Closure = function สะพายเป้จากบ้านเกิด** — ให้พลัง (private state) และให้ปัญหา (memory leak) พร้อมกัน

### Keyword สั้น

- **Runtime** → สนามที่ให้โค้ดวิ่ง = Engine + API รอบตัว
- **Call Stack** → กองจานซ้อน ทำทีละใบ เข้าหลังออกก่อน
- **Heap** → โกดังเก็บ object
- **Event Loop** → คนเรียกคิว หยิบงานเข้าเมื่อ Stack ว่าง
- **Web API / libuv** → ลูกน้องที่ทำงานช้าแทน
- **Callback** → ฝากเบอร์ไว้ เดี๋ยวโทรกลับ
- **Promise** → ใบจองคิว pending / fulfilled / rejected
- **async/await** → Promise ที่อ่านเหมือน sync
- **Microtask** → คิว VIP ทำจนหมด
- **Macrotask** → คิวธรรมดา ทำทีละ 1
- **Blocking** → ยืนขวางประตู ทุกคนเข้าไม่ได้
- **Non-blocking** → ปล่อย Stack ว่างระหว่างรอ
- **Concurrency** → 1 คน สลับดูแล 5 โต๊ะ
- **Parallelism** → 5 คน ทำพร้อมกันจริง
- **Value** → ถ่ายเอกสาร แยกฉบับ
- **Reference** → แชร์ลิงก์ ไฟล์เดียวกัน
- **Mutable** → แก้ของเดิม
- **Immutable** → สร้างของใหม่
- **Scope** → รั้วบ้านของตัวแปร มองออกนอกได้ทางเดียว
- **Closure** → function สะพายเป้จากบ้านเกิด
- **Hoisting** → การประกาศถูกยกขึ้นบน
- **TDZ** → เขตห้ามแตะของ let/const
- **Error Handling** → อย่ากลืน error และอย่าปล่อย Promise ไร้เจ้าของ
