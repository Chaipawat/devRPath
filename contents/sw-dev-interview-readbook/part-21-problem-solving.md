## 1. Big Picture

ลองนึกภาพห้องสัมภาษณ์ที่คุ้นเคย

Interviewer ส่งโจทย์มา: "หาว่าใน list ของยอดขายรายวัน มีช่วง 7 วันติดกันช่วงไหนที่ยอดรวมสูงที่สุด"

Candidate A เงียบ 10 วินาที แล้วรีบพิมพ์ loop ซ้อน loop ทันที พอเขียนไปครึ่งทางก็เริ่มงง ลบแล้วเขียนใหม่ สุดท้ายได้คำตอบที่ถูกบ้างผิดบ้าง

Candidate B พูดออกมาว่า "ขอทวนโจทย์ก่อนนะครับ input เป็น array ของตัวเลข output เป็นผลรวมสูงสุดหรือเป็นตำแหน่งครับ? ถ้าจำนวนวันน้อยกว่า 7 ให้ทำยังไง? วิธีตรง ๆ คือรวมทุกช่วง 7 วันใหม่ทุกครั้ง แต่สังเกตว่าช่วงติดกันมันซ้อนกันเกือบทั้งหมด เลื่อนหน้าต่างไปทีละช่องแล้วบวกตัวใหม่ลบตัวเก่าได้ จะเหลือ O(n)"

Candidate B อาจยังไม่ได้เขียน code สักบรรทัด แต่ interviewer ส่วนใหญ่ **ให้คะแนน B สูงกว่า** เพราะสิ่งที่เขาวัดจริงไม่ใช่ "จำ syntax ได้ไหม" แต่คือ **"คนนี้คิดเป็นระบบไหม สื่อสารได้ไหม และเจอปัญหาใหม่แล้วจะไปต่อได้หรือเปล่า"**

**Problem Solving → การแก้ปัญหาอย่างเป็นระบบ → เปลี่ยนโจทย์ที่ยังคลุมเครือ ให้กลายเป็นขั้นตอนที่ชัด ถูกต้อง และเร็วพอ**

Chapter นี้จึงสอน **process** ไม่ใช่ syntax:

```
Understand → Input → Output → Constraints → Example → Brute Force
   → Pattern → Optimize → Complexity → Edge Cases
```

> **ให้มองภาพนี้ว่า** "เส้นทางจากโจทย์คลุมเครือไปสู่คำตอบที่มั่นใจ โดยทุกขั้นตอนจะลดความไม่รู้ลงทีละนิด ก่อนจะลงมือเขียนจริง"

ทำไมเรื่องนี้สำคัญกับ Frontend / Full-stack Developer ที่ไม่ได้เขียน algorithm ทุกวัน?

| สถานการณ์จริง | Problem Solving ที่ซ่อนอยู่ |
|---|---|
| Search box ที่ filter รายการ 10,000 ชิ้นแล้วหน้าจอกระตุก | loop ซ้อน loop = O(n²) ต้องเปลี่ยนเป็น Hash Map |
| หา "เพื่อนของเพื่อน" ใน social feature | Graph + BFS |
| Menu ซ้อนหลายชั้น / comment ตอบกลับซ้อนกัน | Tree + Recursion |
| ปุ่ม Undo / Redo | Stack |
| คิวส่ง notification / job queue | Queue |
| ตรวจว่า username ซ้ำไหม | Set / Hash Map |
| Dashboard ยอดขายสะสมรายวัน | Prefix Sum |

## 2. Keywords

| Keyword | จำสั้นๆ | ความหมาย |
|---|---|---|
| Algorithm | สูตรทำงาน | ขั้นตอนที่ชัดเจนเพื่อเปลี่ยน input เป็น output |
| Data Structure | ภาชนะเก็บข้อมูล | รูปแบบการจัดเก็บข้อมูล ที่ทำให้บางการกระทำเร็ว บางการกระทำช้า |
| Input | ของที่ได้รับ | ข้อมูลที่โจทย์ให้มา รวมถึงชนิดและขนาด |
| Output | ของที่ต้องส่ง | รูปแบบคำตอบที่ต้องคืน (ค่าเดียว / list / true-false / ตำแหน่ง) |
| Constraints | ข้อจำกัด | ขนาด n, ช่วงค่า, เวลา/หน่วยความจำ — ตัวบอกว่า O ไหนรอด |
| Edge Case | เคสขอบ | input ที่สุดโต่ง เช่น ว่าง, ตัวเดียว, ซ้ำหมด, ติดลบ |
| Brute Force | ลองทุกทาง | วิธีตรงไปตรงมาที่ถูกแน่แต่อาจช้า ใช้เป็นจุดเริ่ม |
| Pattern | ท่ามาตรฐาน | วิธีคิดซ้ำ ๆ ที่ใช้ได้กับโจทย์หลายแบบ |
| Optimize | ทำให้ดีขึ้น | ลดงานซ้ำ / ตัดงานที่ไม่จำเป็นออก |
| Big O | ต้นทุนเมื่อข้อมูลโต | อธิบายว่างานเพิ่มขึ้นเร็วแค่ไหนเมื่อ n ใหญ่ขึ้น |
| Time Complexity | ต้นทุนเวลา | จำนวนขั้นตอนโดยประมาณเทียบกับ n |
| Space Complexity | ต้นทุนหน่วยความจำ | หน่วยความจำเพิ่มเติมที่ใช้เทียบกับ n |
| Trade-off | ได้อย่างเสียอย่าง | เช่น ใช้ memory เพิ่มเพื่อแลกความเร็ว |
| Array | ช่องเรียงติดกัน | เก็บข้อมูลตามลำดับ เข้าถึงด้วย index ได้ทันที |
| String | ตัวอักษรเรียงกัน | Array ของตัวอักษร มีโจทย์เฉพาะเช่น palindrome, anagram |
| Hash Map | ตู้ล็อกเกอร์มีป้ายชื่อ | เก็บคู่ key → value ค้นหาด้วย key เฉลี่ย O(1) |
| Set | รายชื่อไม่ซ้ำ | เก็บเฉพาะค่า ไม่ซ้ำ ใช้เช็คว่า "มีหรือไม่มี" |
| Stack | กองจาน | เข้าทีหลังออกก่อน (LIFO) |
| Queue | แถวคิว | เข้าก่อนออกก่อน (FIFO) |
| Linked List | ขบวนรถไฟ | node แต่ละตัวชี้ไปตัวถัดไป แทรก/ลบง่ายถ้ารู้ตำแหน่ง |
| Tree | ผังองค์กร | โครงสร้างลำดับชั้น มี root และ child |
| Graph | แผนที่เมือง | node เชื่อมกันด้วย edge แบบใดก็ได้ อาจมีวง |
| Two Pointer | สองนิ้วชี้ | ใช้ตัวชี้สองตัวเดินบน array เพื่อลด loop ซ้อน |
| Sliding Window | หน้าต่างเลื่อน | ดูช่วงต่อเนื่อง แล้วเลื่อนขอบแทนการคำนวณใหม่ |
| Binary Search | เปิดพจนานุกรม | ตัดครึ่งพื้นที่ค้นหาทุกรอบ ต้องมีลำดับ |
| Prefix Sum | ยอดสะสม | เก็บผลรวมสะสม เพื่อตอบผลรวมช่วงใดก็ได้ใน O(1) |
| Hashing | จดไว้ในสมุด | จำสิ่งที่เคยเห็นใน Hash Map/Set เพื่อไม่ต้องย้อนหา |
| DFS | เดินลึกสุดก่อน | Depth-First Search สำรวจทางหนึ่งจนสุดแล้วค่อยย้อน |
| BFS | กระจายเป็นวง | Breadth-First Search สำรวจทีละชั้น เหมาะหาทางสั้นสุด |
| Recursion | ฟังก์ชันเรียกตัวเอง | แก้ปัญหาใหญ่ด้วยปัญหาเล็กแบบเดียวกัน ต้องมี base case |
| Base Case | จุดหยุด | เงื่อนไขที่ recursion ไม่เรียกตัวเองต่อ |
| Greedy | เลือกดีสุดตอนนี้ | ตัดสินใจทีละขั้นด้วยตัวเลือกที่ดีที่สุดเฉพาะหน้า |
| Dynamic Programming (DP) | จดคำตอบย่อย | แตกเป็นปัญหาย่อยที่ซ้ำกัน แก้ครั้งเดียวแล้วจำไว้ |
| Memoization | จำผลลัพธ์ | cache คำตอบของปัญหาย่อยใน recursion (top-down) |
| Off-by-one | พลาดไปหนึ่ง | bug จากขอบเขต index เช่น `<` กับ `<=` |
| Dry Run | เดินมือ | ไล่ algorithm ด้วยตัวอย่างเล็ก ๆ บนกระดาษทีละขั้น |

## 3. Mental Model

### 3.1 สามคำถามที่อยู่ในทุกโจทย์

ทุกโจทย์ algorithm จริง ๆ ถามแค่สามอย่าง:

```
[ข้อมูลอยู่ในรูปแบบไหน?]      → Data Structure
          ↓
[เดินผ่านข้อมูลด้วยท่าไหน?]    → Algorithm Pattern
          ↓
[ต้นทุนเท่าไรเมื่อข้อมูลโต?]   → Big O
```

> **ให้มองภาพนี้ว่า** "Data Structure คือรูปร่างของห้อง Pattern คือวิธีเดินในห้อง และ Big O คือจำนวนก้าวที่ต้องเดินเมื่อห้องใหญ่ขึ้น"

ถ้าตอบสามข้อนี้ได้ ต่อให้โจทย์ใหม่ไม่เคยเห็น ก็ยังมีจุดเริ่มคิดเสมอ

### 3.2 Process 10 ขั้น — ทำไมต้องครบทุกขั้น

| ขั้น | คำถามในหัว | ถ้าข้ามจะเกิดอะไร |
|---|---|---|
| 1. Understand | โจทย์ขอให้ทำอะไรจริง ๆ | แก้ผิดโจทย์ทั้งข้อ |
| 2. Input | ได้อะไรมา ชนิดอะไร เรียงไหม ซ้ำไหม | เลือก pattern ผิด |
| 3. Output | ต้องคืนอะไร ค่า / ตำแหน่ง / ทั้งหมด / แค่มีไหม | ทำงานเกินจำเป็น หรือคืนผิดรูป |
| 4. Constraints | n ใหญ่แค่ไหน ค่าติดลบได้ไหม | เขียน O(n²) ให้ n = 1,000,000 |
| 5. Example | ลองมือกับตัวอย่างเล็ก ๆ | ไม่เห็น pattern ที่ซ่อนอยู่ |
| 6. Brute Force | วิธีตรง ๆ ที่ถูกแน่ | ไม่มี baseline ไม่มีอะไรให้ optimize |
| 7. Pattern | โจทย์นี้หน้าตาเหมือนท่าไหน | คิดวนอยู่กับ brute force |
| 8. Optimize | งานซ้ำอยู่ตรงไหน ตัดได้ไหม | คำตอบถูกแต่ช้า |
| 9. Complexity | Time / Space เท่าไร | อธิบายความดีของคำตอบไม่ได้ |
| 10. Edge Cases | ว่าง / ตัวเดียว / ซ้ำ / ติดลบ / ใหญ่สุด | ผ่านตัวอย่าง แต่พังบน production |

**หลักสำคัญ:** ขั้น 1–5 คือ "เข้าใจปัญหา" ขั้น 6–8 คือ "หาวิธี" ขั้น 9–10 คือ "พิสูจน์ว่าวิธีนี้ดีพอ" ส่วนการเขียน code จริงอยู่ระหว่างขั้น 8 กับ 9 และเป็นส่วนที่ **ง่ายที่สุด** ถ้าขั้นก่อนหน้าชัดแล้ว

### 3.3 Big O — ภาษากลางของความเร็ว

**Big O → สัญลักษณ์บอกอัตราการโตของงาน → ใช้เปรียบเทียบว่าวิธีไหน "รอด" เมื่อข้อมูลใหญ่ขึ้น**

Big O ไม่ได้บอกว่าเร็วกี่มิลลิวินาที แต่บอกว่า **ถ้าข้อมูลเพิ่ม 10 เท่า งานเพิ่มกี่เท่า**

| Big O | ชื่อเล่น | ถ้า n เพิ่ม 10 เท่า งานเพิ่ม | ตัวอย่างสถานการณ์ |
|---|---|---|---|
| O(1) | คงที่ | เท่าเดิม | หยิบ array ด้วย index, ค้น Hash Map (เฉลี่ย) |
| O(log n) | ตัดครึ่ง | เพิ่มนิดเดียว (บวกไม่กี่ขั้น) | Binary Search, balanced tree |
| O(n) | เส้นตรง | 10 เท่า | loop รอบเดียว, หาค่ามากสุด |
| O(n log n) | เรียงของ | มากกว่า 10 เท่านิดหน่อย | การ sort ทั่วไปที่ดี |
| O(n²) | loop ซ้อน | 100 เท่า | เทียบทุกคู่ |

```
งาน
 ↑                                   O(n²)
 │                                 ╱
 │                              ╱
 │                          ╱        O(n log n)
 │                     ╱       ___───
 │                ╱   ___───            O(n)
 │           ╱___───        ______───
 │      ___──     ______───
 │ ___──______───────────────────────── O(log n)
 │━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ O(1)
 └────────────────────────────────────→ n (ขนาดข้อมูล)
```

> **ให้มองภาพนี้ว่า** "ตอนข้อมูลน้อยทุกเส้นดูใกล้กัน แต่พอข้อมูลโต เส้น O(n²) จะพุ่งหนีจนระบบค้าง ขณะที่ O(log n) แทบไม่ขยับ"

**กฎจับ Big O แบบเร็ว (ไม่ต้องคำนวณละเอียด):**

| เห็นแบบนี้ | ประมาณได้ว่า |
|---|---|
| ทำงานจำนวนครั้งคงที่ ไม่ขึ้นกับ n | O(1) |
| ตัดข้อมูลทีละครึ่ง | O(log n) |
| loop ผ่านข้อมูลครั้งเดียว (หรือหลายรอบแต่ไม่ซ้อน) | O(n) |
| sort ก่อน แล้ว loop | O(n log n) |
| loop ซ้อน loop บนข้อมูลเดียวกัน | O(n²) |
| loop นอก n ข้างในทำ binary search | O(n log n) |

**Constraints บอกคำตอบล่วงหน้า:** ถ้า n ≤ 1,000 → O(n²) มักยังรอด / ถ้า n ถึงระดับแสนหรือล้าน → ต้องหา O(n) หรือ O(n log n) / ถ้า n เล็กมาก (ราว 20) → brute force ลองทุก combination อาจรับได้ นี่คือเหตุผลที่ต้องถาม constraints ก่อน

## 4. ภาพจำ

ส่วนนี้คือ **Data Structure ทั้ง 9 ตัว** แต่ละตัวตอบ: เก่งอะไร / ไม่เก่งอะไร / ใช้เมื่อไร / ภาพจำ

### 4.1 Array

```
🧠 ภาพจำ:
Array = ตู้ล็อกเกอร์ที่มีเลขกำกับเรียงติดกัน
รู้เลข → เดินไปเปิดได้ทันที
แทรกตู้ใหม่ตรงกลาง → ต้องย้ายตู้ทั้งแถวถัดไป
index:  [0] [1] [2] [3] [4]
value:   7   3   9   1   5
```

> **ให้มองภาพนี้ว่า** "ของเรียงเป็นแถวติดกัน หยิบด้วยเลขช่องได้ทันที แต่ถ้าจะแทรกตรงกลางต้องขยับทั้งแถว"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| เข้าถึงด้วย index O(1), วน loop เร็ว, เพิ่มท้าย (เฉลี่ย) O(1) | แทรก/ลบตรงกลาง O(n), ค้นหาค่าโดยไม่เรียง O(n) | ข้อมูลมีลำดับ ต้องเข้าถึงตามตำแหน่ง, list ใน UI |

### 4.2 String

```
🧠 ภาพจำ:
String = ลูกปัดตัวอักษรร้อยเป็นสาย
อ่านทีละเม็ดได้ แต่ในหลายภาษา "แก้เม็ดกลางสาย" = ร้อยสายใหม่ทั้งเส้น
"level" → [l][e][v][e][l]
```

> **ให้มองภาพนี้ว่า** "String คือ Array ของตัวอักษร ที่หลายภาษาแก้ไขในที่ไม่ได้ (immutable) ทุกการแก้คือการสร้างสายใหม่"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| อ่านตัวอักษรตามตำแหน่ง, เทียบ prefix | ต่อ string ใน loop ซ้ำ ๆ อาจกลายเป็น O(n²) ในภาษาที่ string immutable | palindrome, anagram, นับตัวอักษร, parse ข้อความ |

**จุดสังเกต:** โจทย์ String ส่วนใหญ่แก้ด้วย Two Pointer (palindrome), Sliding Window (substring ยาวสุดไม่ซ้ำ), หรือ Hash Map (นับความถี่ตัวอักษร)

### 4.3 Hash Map

```
🧠 ภาพจำ:
Hash Map = ตู้ล็อกเกอร์ที่ติดป้ายชื่อ ไม่ใช่เลข
บอกชื่อ → เครื่องคำนวณตำแหน่งตู้ให้ → เปิดได้ทันที
"alice" ──hash──→ ตู้ 3 → { age: 25 }
"bob"   ──hash──→ ตู้ 7 → { age: 31 }
```

> **ให้มองภาพนี้ว่า** "เปลี่ยนชื่อเป็นตำแหน่งตู้ด้วยสูตร จึงไม่ต้องเดินหาทีละตู้"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| ค้น/เพิ่ม/ลบ ด้วย key เฉลี่ย O(1) | ไม่รักษาลำดับแบบเรียงค่า (ขึ้นกับภาษา), ใช้ memory เพิ่ม, worst case O(n) เมื่อ collision หนัก | นับความถี่, จำสิ่งที่เคยเห็น, group ข้อมูล, cache |

### 4.4 Set

```
🧠 ภาพจำ:
Set = รายชื่อแขกหน้างานเลี้ยง
ถามได้คำถามเดียวแต่เร็วมาก: "คนนี้อยู่ในรายชื่อไหม?"
ชื่อซ้ำ → ไม่ถูกเพิ่ม
```

> **ให้มองภาพนี้ว่า** "Set คือ Hash Map ที่สนใจแค่ key ไม่สนใจ value"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| เช็ค "มีไหม" เฉลี่ย O(1), ตัดค่าซ้ำ | เก็บข้อมูลประกอบไม่ได้ (ไม่มี value), ไม่นับจำนวน | ลบค่าซ้ำ, เช็คว่าเคยเยี่ยม node นี้หรือยัง, หา intersection |

### 4.5 Stack

```
🧠 ภาพจำ:
Stack = กองจานในร้านอาหาร
วางจานใหม่ไว้บนสุด → หยิบก็หยิบจากบนสุด
Last In, First Out (LIFO)
  push ↓   ↑ pop
      [ C ]  ← top
      [ B ]
      [ A ]
```

> **ให้มองภาพนี้ว่า** "สิ่งล่าสุดที่ใส่เข้าไป คือสิ่งแรกที่จะถูกจัดการ เหมือนงานที่ค้างซ้อนกัน"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| push/pop ด้านบน O(1) | เข้าถึงของตรงกลาง/ล่างสุด | Undo, วงเล็บจับคู่, browser back, DFS แบบไม่ใช้ recursion, call stack |

### 4.6 Queue

```
🧠 ภาพจำ:
Queue = แถวซื้อตั๋วหนัง
มาก่อนได้ก่อน First In, First Out (FIFO)
enqueue →  [ D ][ C ][ B ][ A ]  → dequeue
           ท้ายแถว          หัวแถว
```

> **ให้มองภาพนี้ว่า** "ใครมาก่อนได้รับบริการก่อน ยุติธรรมตามลำดับเวลา"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| เพิ่มท้าย / เอาออกหัว O(1) (ถ้า implement ถูก) | เข้าถึงตรงกลาง, การใช้ array ธรรมดาแล้วลบหัวอาจเป็น O(n) | BFS, job queue, task scheduling, rate limit buffer |

### 4.7 Linked List

```
🧠 ภาพจำ:
Linked List = ขบวนรถไฟ
แต่ละตู้รู้แค่ว่าตู้ถัดไปคือตู้ไหน
อยากไปตู้ที่ 5 → ต้องเดินผ่านตู้ 1, 2, 3, 4
[A] → [B] → [C] → [D] → null
```

> **ให้มองภาพนี้ว่า** "ข้อมูลไม่ได้อยู่ติดกัน แต่ละชิ้นถือเชือกผูกไปหาชิ้นถัดไป"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| แทรก/ลบ O(1) ถ้าถือ node ตำแหน่งนั้นอยู่แล้ว | เข้าถึงตัวที่ k ต้อง O(n), ใช้ memory เพิ่มสำหรับตัวชี้ | LRU cache (ร่วมกับ Hash Map), โจทย์สัมภาษณ์เรื่อง pointer (reverse, หา cycle) |

### 4.8 Tree

```
🧠 ภาพจำ:
Tree = ผังองค์กร
CEO อยู่บนสุด (root) มีลูกน้องแตกกิ่งลงมา
ทุกคนมีหัวหน้าได้คนเดียว ไม่มีวง
            [CEO]
           ╱     ╲
       [CTO]     [CFO]
       ╱   ╲         ╲
   [Dev] [QA]      [Acct]
```

> **ให้มองภาพนี้ว่า** "ข้อมูลแบบลำดับชั้น จากบนลงล่าง ที่ทุก node มีพ่อได้ตัวเดียว"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| แทนลำดับชั้น, Binary Search Tree ที่ balanced ค้นหา O(log n) | ถ้าเอียงข้างเดียว (skewed) จะกลายเป็น O(n), ซับซ้อนกว่า array | DOM, React component tree, folder, menu ซ้อน, comment thread |

### 4.9 Graph

```
🧠 ภาพจำ:
Graph = แผนที่เมืองกับถนน
เมือง = node, ถนน = edge
ถนนมีทางเดียว (directed) หรือสองทาง (undirected) ได้ อาจมีวงได้
[A] ─── [B]
 │     ╱  │
 │   ╱    │
[C] ─── [D] ─── [E]
```

> **ให้มองภาพนี้ว่า** "Tree ที่ปลดล็อกกฎทุกข้อ ใครเชื่อมกับใครก็ได้ และเดินวนกลับมาที่เดิมได้"

| เก่ง | ไม่เก่ง | ใช้เมื่อ |
|---|---|---|
| แทนความสัมพันธ์ซับซ้อน, หาเส้นทาง, หากลุ่มที่เชื่อมกัน | ต้องระวังวน (ต้องมี visited), ใช้ memory เยอะเมื่อ edge มาก | social network, dependency graph (npm, build), แผนที่, workflow |

## 5. How It Works

### 5.1 Process 10 ขั้น แบบไหลต่อเนื่อง

```
[1. Understand]   ทวนโจทย์ด้วยคำพูดตัวเอง
       ↓
[2. Input]        ชนิด? ขนาด? เรียงแล้ว? ซ้ำได้? ติดลบได้?
       ↓
[3. Output]       คืนค่าอะไร? รูปแบบไหน? มีหลายคำตอบคืนอันไหน?
       ↓
[4. Constraints]  n สูงสุดเท่าไร → Big O เป้าหมาย
       ↓
[5. Example]      ลองมือ 1 ตัวอย่างปกติ + 1 ตัวอย่างแปลก
       ↓
[6. Brute Force]  วิธีที่ถูกแน่ แม้ช้า + บอก Big O
       ↓
[7. Pattern]      โจทย์นี้หน้าตาเหมือนท่าไหน? (ดู keyword)
       ↓
[8. Optimize]     งานซ้ำอยู่ตรงไหน? ใช้ memory แลกเวลาได้ไหม?
       ↓
[9. Complexity]   Time / Space ของวิธีใหม่
       ↓
[10. Edge Cases]  ว่าง / ตัวเดียว / ซ้ำหมด / ติดลบ / ใหญ่สุด
```

> **ให้มองภาพนี้ว่า** "เครื่องกรองความคลุมเครือ ที่ทุกชั้นทำให้โจทย์ชัดขึ้นจนการเขียน code เหลือแค่การแปลภาษา"

### 5.2 จุดที่คนมักติด: จาก Brute Force ไป Optimize

หัวใจของการ optimize มีแค่ 3 คำถาม:

```
Brute Force ช้าเพราะอะไร?
       ↓
 ┌─────┼──────────────────────────┐
 ↓     ↓                          ↓
[ค้นหาซ้ำ]   [คำนวณซ้ำ]            [ดูสิ่งที่ไม่จำเป็น]
 ↓           ↓                     ↓
Hash Map/Set Prefix Sum / DP /     Two Pointer / Binary Search
             Sliding Window        / Greedy (ตัดทางทิ้ง)
```

> **ให้มองภาพนี้ว่า** "การ optimize เกือบทุกครั้งคือการหาว่า brute force ทำงานเดิมซ้ำตรงไหน แล้วเลือกเครื่องมือที่ทำให้ไม่ต้องทำซ้ำ"

### 5.3 Pattern Catalog — 10 ท่าที่ต้องรู้

ทุก pattern ด้านล่างมีครบ 4 อย่าง: **🧠 ภาพจำ / 🎯 ปัญหาแบบไหน / 📋 ตัวอย่าง (ไม่ใช้ code) / 🔎 Keyword ในโจทย์**

#### Pattern 1: Two Pointer

**Two Pointer → ตัวชี้สองตัว → เดินบนข้อมูลพร้อมกันสองตำแหน่งเพื่อลดจาก O(n²) เหลือ O(n)**

```
🧠 ภาพจำ: คนสองคนเดินเข้าหากันจากปลายสะพาน
[1] [3] [4] [6] [8] [11]
 ↑                    ↑
left                right
 → ขยับเข้าหากันตามเงื่อนไข ←
```

> **ให้มองภาพนี้ว่า** "เพราะข้อมูลเรียงแล้ว แต่ละครั้งที่ขยับนิ้ว เราตัดคู่ที่เป็นไปไม่ได้ทิ้งไปทั้งแถบ"

- 🎯 **ปัญหาแบบไหน:** หาคู่ที่รวมได้ค่าเป้าหมายใน array ที่เรียงแล้ว, เช็ค palindrome, ลบค่าซ้ำใน array ที่เรียงแล้ว, รวม list ที่เรียงสองชุด
- 📋 **ตัวอย่าง:** ราคาสินค้าเรียงจากถูกไปแพง `1, 3, 4, 6, 8, 11` ลูกค้ามีงบ 10 บาทพอดี อยากซื้อ 2 ชิ้น — ชี้ซ้ายสุด (1) กับขวาสุด (11) รวมได้ 12 เกินงบ ตัวขวาแพงไป เลื่อนขวาเข้ามาเป็น 8 → รวม 9 ขาด ตัวซ้ายถูกไป เลื่อนซ้ายเป็น 3 → รวม 11 เกิน เลื่อนขวาเป็น 6 → รวม 9 ขาด เลื่อนซ้ายเป็น 4 → รวม 10 เจอแล้ว เดินรอบเดียวไม่ต้องเทียบทุกคู่
- 🔎 **Keyword:** "เรียงแล้ว (sorted)", "คู่ (pair)", "จากสองฝั่ง", "palindrome", "in-place", "รวมสอง list"

#### Pattern 2: Sliding Window

**Sliding Window → หน้าต่างเลื่อน → ดูช่วงต่อเนื่อง โดยเลื่อนขอบเข้า-ออกแทนการคำนวณช่วงใหม่ทั้งหมด**

```
🧠 ภาพจำ: กรอบแว่นขยายเลื่อนไปบนแถวตัวเลข
[2  5  1] 8  3  7        ผลรวม = 8
 2 [5  1  8] 3  7        ผลรวม = 8 - 2 + 8 = 14
 2  5 [1  8  3] 7        ผลรวม = 14 - 5 + 3 = 12
```

> **ให้มองภาพนี้ว่า** "ช่วงที่ติดกันซ้อนทับกันเกือบทั้งหมด จึงแค่บวกตัวที่เข้าหน้าต่างและลบตัวที่ออก"

- 🎯 **ปัญหาแบบไหน:** ผลรวม/ค่าเฉลี่ยของช่วงยาว k ที่มากที่สุด, substring ที่ยาวที่สุดโดยไม่มีตัวอักษรซ้ำ, ช่วงสั้นที่สุดที่ผลรวมถึงเป้า (เมื่อค่าเป็นบวก)
- 📋 **ตัวอย่าง:** Dashboard ยอดขายรายวันต้องแสดง "7 วันติดกันที่ขายดีที่สุด" — แทนที่จะรวม 7 วันใหม่ทุกครั้ง ให้รวม 7 วันแรกครั้งเดียว แล้วทุกครั้งที่เลื่อนไปหนึ่งวัน บวกวันใหม่ ลบวันที่หลุดออก จดค่าสูงสุดไว้ ส่วนแบบ **หน้าต่างยืดหด** เช่น "ชื่อผู้ใช้ช่วงยาวสุดที่ไม่มีตัวซ้ำ" ให้ขยายขอบขวาไปเรื่อย ๆ พอเจอตัวซ้ำ ค่อยหดขอบซ้ายจนไม่ซ้ำ
- 🔎 **Keyword:** "ช่วงต่อเนื่อง (contiguous)", "subarray / substring", "k ตัวติดกัน", "ยาวที่สุด/สั้นที่สุดที่...", "ภายในช่วงเวลา"

#### Pattern 3: Binary Search

**Binary Search → ค้นหาแบบแบ่งครึ่ง → ตัดพื้นที่ค้นหาทิ้งครึ่งหนึ่งทุกรอบ ได้ O(log n)**

```
🧠 ภาพจำ: เปิดพจนานุกรมหาคำว่า "mango"
[a ........................... z]
             ↓ เปิดกลางเจอ "k" → mango อยู่หลัง
               [l .......... z]
                    ↓ เปิดกลางเจอ "r" → อยู่ก่อน
               [l ... q]
                  ↓ ... เหลือไม่กี่หน้า
```

> **ให้มองภาพนี้ว่า** "ทุกครั้งที่เปิดดูตรงกลาง เราทิ้งหนังสือครึ่งหนึ่งไปโดยไม่ต้องอ่าน"

- 🎯 **ปัญหาแบบไหน:** หาค่าใน array ที่เรียงแล้ว, หาตำแหน่งแรก/สุดท้ายที่ตรงเงื่อนไข, และ **"Binary Search on Answer"** — หาค่าน้อยที่สุด/มากที่สุดที่ยัง "ใช้ได้" เมื่อเงื่อนไขมีลักษณะ "ถ้า x ใช้ได้ ค่าที่มากกว่า x ก็ใช้ได้ด้วย"
- 📋 **ตัวอย่าง:** `git bisect` คือ binary search จริงในชีวิต developer — มี 1,000 commit รู้ว่า commit แรกดี commit ล่าสุดพัง ทดสอบ commit กลาง ถ้าดีแปลว่า bug อยู่ครึ่งหลัง ถ้าพังแปลว่าอยู่ครึ่งแรก ทำซ้ำราว 10 รอบก็เจอ commit ที่ทำพัง อีกตัวอย่าง: "server ต้องมี RAM อย่างน้อยเท่าไรถึงรับ load ได้" ลองค่ากลาง ถ้ารอดก็ลองน้อยลง ถ้าไม่รอดก็ลองมากขึ้น
- 🔎 **Keyword:** "เรียงแล้ว", "หาตำแหน่ง", "ค่าน้อยที่สุดที่...", "ค่ามากที่สุดที่...", "O(log n)", "ข้อมูลใหญ่มาก", "first / last occurrence"

#### Pattern 4: Prefix Sum

**Prefix Sum → ผลรวมสะสม → คำนวณครั้งเดียว แล้วตอบ "ผลรวมช่วง i ถึง j" ได้ทันทีด้วยการลบกัน**

```
🧠 ภาพจำ: เลขไมล์รถยนต์
วันที่:     1    2    3    4    5
วิ่ง(กม.):  10   20   5    15   30
ไมล์สะสม:  10   30   35   50   80
ระยะทางวันที่ 2 ถึง 4 = ไมล์วันที่ 4 − ไมล์วันที่ 1 = 50 − 10 = 40
```

> **ให้มองภาพนี้ว่า** "ไม่ต้องบวกระยะทางใหม่ทุกครั้ง แค่เอาเลขไมล์ปลายทางลบเลขไมล์ต้นทาง"

- 🎯 **ปัญหาแบบไหน:** ถามผลรวมช่วงหลายครั้งบน array ที่ไม่เปลี่ยน, นับจำนวน subarray ที่ผลรวมเท่ากับ k (ใช้ร่วมกับ Hash Map), หาจุดสมดุลที่ผลรวมซ้ายเท่ากับขวา
- 📋 **ตัวอย่าง:** หน้า report ให้ผู้ใช้เลือกช่วงวันที่ได้อิสระ และกดเปลี่ยนช่วงบ่อยมาก — ถ้ารวมใหม่ทุกครั้งจะเป็น O(n) ต่อคำถาม แต่ถ้าเตรียมยอดสะสมไว้ครั้งเดียว ทุกคำถามตอบได้ O(1) ด้วยการลบสองค่า (นี่คือไอเดียเดียวกับการเก็บ running total ใน database)
- 🔎 **Keyword:** "ผลรวมช่วง (range sum)", "query หลายครั้ง", "subarray sum เท่ากับ k", "ยอดสะสม", "cumulative"

#### Pattern 5: Hashing

**Hashing → จดสิ่งที่เคยเห็นไว้ในสมุด → ใช้ Hash Map / Set เปลี่ยนการค้นหา O(n) ให้เป็น O(1)**

```
🧠 ภาพจำ: พนักงานต้อนรับที่จดชื่อแขกไว้ในสมุด
แขกเข้ามา → เปิดสมุดดู → เคยมาแล้ว? → ใช่: ทักทายว่ามาอีกแล้ว
                                  → ไม่: จดชื่อลงสมุด
```

> **ให้มองภาพนี้ว่า** "แทนที่จะย้อนไปถามทุกคนที่เคยมา เราเปิดสมุดแค่ครั้งเดียว"

- 🎯 **ปัญหาแบบไหน:** หาคู่ที่รวมได้เป้าหมายใน array ที่ **ไม่เรียง** (Two Sum), หาตัวซ้ำตัวแรก, นับความถี่, จัดกลุ่ม anagram, เช็คว่าสอง list มีสมาชิกร่วมกันไหม
- 📋 **ตัวอย่าง:** ระบบตรวจ order ซ้ำ — มี order ID ไหลเข้ามาเรื่อย ๆ brute force คือเทียบกับทุก order ก่อนหน้า (O(n²)) แต่ถ้าเก็บ ID ที่เคยเห็นไว้ใน Set ทุก order ใหม่ถามแค่ "เคยเห็นไหม" O(1) รวมทั้งหมด O(n) แลกกับ memory O(n) หรือ Two Sum: เดินไปทีละตัว ถาม "ตัวคู่ที่ต้องการ (เป้าหมาย − ตัวนี้) เคยเจอไหม" ถ้าไม่เคยก็จดตัวนี้ไว้
- 🔎 **Keyword:** "เคยเจอไหม", "ซ้ำ (duplicate)", "นับความถี่", "unique", "จัดกลุ่ม (group by)", "anagram", "ไม่เรียง + ต้องหาคู่"

#### Pattern 6: DFS (Depth-First Search)

**DFS → ค้นหาลึกก่อน → เดินไปทางหนึ่งจนสุด แล้วค่อยย้อนกลับมาลองทางอื่น**

```
🧠 ภาพจำ: เดินเขาวงกตโดยเอามือแตะกำแพงไว้
        [A]
       ╱   ╲
     [B]   [C]
     ╱ ╲     ╲
   [D] [E]   [F]
ลำดับเยี่ยม: A → B → D → (ย้อน) → E → (ย้อน) → C → F
```

> **ให้มองภาพนี้ว่า** "มุ่งดิ่งลงไปจนตัน แล้วถอยทีละก้าวเพื่อลองทางแยกที่ยังไม่ได้ไป"

- 🎯 **ปัญหาแบบไหน:** สำรวจ tree ทุก node, หาว่ามีทางไปถึงปลายทางไหม, นับจำนวนเกาะ (กลุ่มที่เชื่อมกัน) ในตาราง, ตรวจว่ามีวงใน dependency, หา combination ทั้งหมด (backtracking)
- 📋 **ตัวอย่าง:** ระบบคำนวณขนาด folder ทั้งหมด — เข้า folder แรก เจอ sub-folder ก็เข้าไปอีก จนเจอแต่ไฟล์ รวมขนาดแล้วส่งค่ากลับขึ้นไปหา folder แม่ หรือ build tool ตรวจว่า module A import B, B import C, C import A → เจอวง (circular dependency)
- 🔎 **Keyword:** "ทุกเส้นทาง", "มีทางไหม", "เชื่อมกันไหม / connected", "จำนวนกลุ่ม / เกาะ", "ลึกที่สุด", "ทุก combination", "backtrack", "tree traversal"

#### Pattern 7: BFS (Breadth-First Search)

**BFS → ค้นหาแบบกว้างก่อน → สำรวจทุก node ที่ห่าง 1 ก้าว ก่อนไปที่ห่าง 2 ก้าว ใช้ Queue**

```
🧠 ภาพจำ: โยนหินลงน้ำ คลื่นกระจายเป็นวง
             [You]              ← ชั้น 0
          ╱    │    ╲
       [A]    [B]    [C]        ← ชั้น 1 (เพื่อน)
       ╱ ╲     │      ╲
     [D] [E]  [F]     [G]       ← ชั้น 2 (เพื่อนของเพื่อน)
```

> **ให้มองภาพนี้ว่า** "ขยายวงออกทีละชั้น ดังนั้นครั้งแรกที่เจอเป้าหมาย คือระยะที่ใกล้ที่สุดแน่นอน"

- 🎯 **ปัญหาแบบไหน:** ทางที่สั้นที่สุดใน graph ที่ทุก edge มีน้ำหนักเท่ากัน, จำนวนก้าวน้อยสุด, แสดง tree ทีละชั้น (level order), กระจายจากหลายจุดพร้อมกัน (เช่น ไฟลาม)
- 📋 **ตัวอย่าง:** Feature "คุณอาจรู้จัก" แบบ LinkedIn — เริ่มจากตัวเรา ใส่เพื่อนทุกคนเข้า Queue (ชั้น 1) แล้วดึงออกทีละคนมาดูเพื่อนของเขา (ชั้น 2) จด visited ไว้เพื่อไม่นับคนเดิมซ้ำ หรือเกมในแผนที่ตาราง "เดินจากจุด A ไป B ให้น้อยก้าวที่สุด"
- 🔎 **Keyword:** "ทางที่สั้นที่สุด", "น้อยก้าวที่สุด (minimum steps)", "ระดับ / ชั้น (level)", "ห่างกี่ขั้น", "ใกล้ที่สุด", "กระจายพร้อมกัน"
- ⚠️ ถ้า edge มีน้ำหนักไม่เท่ากัน (เช่น ถนนยาวไม่เท่ากัน) BFS ธรรมดาไม่พอ ต้องใช้ Dijkstra ซึ่งอยู่นอกขอบเขต Junior-Mid ส่วนใหญ่ แต่ควรรู้ว่ามีขอบเขตนี้

#### Pattern 8: Recursion

**Recursion → ฟังก์ชันที่เรียกตัวเอง → แก้ปัญหาใหญ่ด้วยการเชื่อว่า "ปัญหาเล็กกว่าแบบเดียวกันแก้ได้แล้ว"**

```
🧠 ภาพจำ: ตุ๊กตาแม่ลูกดก (Matryoshka)
[ตุ๊กตาใหญ่] → เปิด → [ตุ๊กตากลาง] → เปิด → [ตุ๊กตาเล็ก] → เปิดไม่ได้แล้ว (base case)
      ↑                    ↑                        │
      └──── ส่งคำตอบกลับ ←──┴──── ส่งคำตอบกลับ ←─────┘
```

> **ให้มองภาพนี้ว่า** "เปิดลงไปทีละชั้นจนถึงตัวเล็กสุดที่ตอบได้ทันที แล้วส่งคำตอบย้อนขึ้นมาทีละชั้น"

- 🎯 **ปัญหาแบบไหน:** โครงสร้างที่ซ้อนตัวเอง (tree, folder, JSON ซ้อน, comment ตอบกลับ), แบ่งแล้วรวม (merge sort), ลองทุกทางเลือก (backtracking)
- 📋 **ตัวอย่าง:** Render comment thread แบบ Reddit — "การแสดง comment หนึ่งอัน = แสดงข้อความตัวเอง + แสดง reply ทุกอันด้วยวิธีเดียวกัน" base case คือ comment ที่ไม่มี reply สิ่งเดียวกันคือ React component ที่ render ตัวเองซ้อน (recursive component) สำหรับ menu หลายชั้น
- 🔎 **Keyword:** "ซ้อนกัน (nested)", "tree", "ทุก sub-...", "แบ่งครึ่งแล้วรวม", "ทุก combination / permutation", "นิยามด้วยตัวเอง"
- **สองกฎเหล็ก:** (1) ต้องมี base case (2) ทุกการเรียกต้องทำให้ปัญหาเล็กลง ถ้าไม่ครบจะได้ **stack overflow**

#### Pattern 9: Greedy

**Greedy → โลภทีละขั้น → เลือกสิ่งที่ดีที่สุดเฉพาะหน้า โดยไม่ย้อนกลับมาเปลี่ยนใจ**

```
🧠 ภาพจำ: ทอนเงินด้วยเหรียญใหญ่สุดก่อน
ทอน 87 บาท (มีเหรียญ/แบงก์ 50, 20, 10, 5, 1)
50 → เหลือ 37 → 20 → เหลือ 17 → 10 → เหลือ 7 → 5 → เหลือ 2 → 1 → 1 → เสร็จ
```

> **ให้มองภาพนี้ว่า** "ทุกขั้นหยิบชิ้นที่ดีที่สุดตอนนี้ แล้วเดินหน้าต่อ ไม่คิดถึงอนาคต"

- 🎯 **ปัญหาแบบไหน:** จัดตารางประชุมให้ได้มากที่สุด (เลือกอันที่จบเร็วสุดก่อน), รวมช่วงเวลาที่ทับกัน (sort ตามเวลาเริ่มก่อน), กระโดดไปถึงปลายทางได้ไหม, ทอนเงินในระบบเหรียญมาตรฐาน
- 📋 **ตัวอย่าง:** ห้องประชุมหนึ่งห้อง มีคำขอจองหลายช่วง อยากรับได้มากที่สุด — เรียงตามเวลา **จบ** แล้วรับอันที่จบเร็วสุดที่ไม่ชนกับอันก่อนหน้า เพราะจบเร็ว = เหลือเวลาให้คนอื่นมากสุด
- 🔎 **Keyword:** "มากที่สุด / น้อยที่สุด" + มีทางเลือกเฉพาะหน้าที่ชัด, "จัดตาราง (scheduling)", "ช่วงเวลา (interval)", "เลือกได้กี่อัน", มักมาคู่กับ "sort ก่อน"
- ⚠️ **กับดัก:** Greedy ไม่ได้ถูกเสมอ เช่น ถ้าเหรียญมีแค่ 1, 3, 4 และต้องทอน 6 → Greedy เลือก 4+1+1 = 3 เหรียญ แต่คำตอบดีสุดคือ 3+3 = 2 เหรียญ เมื่อ Greedy พัง ให้นึกถึง DP

#### Pattern 10: Dynamic Programming (Concept)

**Dynamic Programming → แก้ปัญหาย่อยครั้งเดียวแล้วจดไว้ → ใช้เมื่อปัญหาใหญ่แตกเป็นปัญหาย่อยที่ "ซ้ำกัน" และคำตอบดีสุดสร้างจากคำตอบดีสุดของปัญหาย่อย**

```
🧠 ภาพจำ: ขึ้นบันได 5 ขั้น ก้าวได้ทีละ 1 หรือ 2 ขั้น มีกี่วิธี?
ขั้น:       1    2    3    4    5
จำนวนวิธี:  1    2    3    5    8
                     ↑
             วิธีถึงขั้น 3 = วิธีถึงขั้น 2 + วิธีถึงขั้น 1
```

> **ให้มองภาพนี้ว่า** "ตารางที่เติมคำตอบจากซ้ายไปขวา แต่ละช่องใช้คำตอบที่จดไว้แล้วในช่องก่อนหน้า ไม่ต้องคำนวณใหม่"

- 🎯 **ปัญหาแบบไหน:** นับจำนวนวิธี, หาค่าดีสุด (min/max) ที่ Greedy ใช้ไม่ได้, ทอนเงินด้วยเหรียญน้อยสุด (ระบบเหรียญแปลก), ลำดับย่อยที่ยาวที่สุด, เลือกของใส่กระเป๋าให้คุ้มสุด (knapsack), ความต่างระหว่างสอง string (edit distance)
- 📋 **ตัวอย่าง:** Recursion ธรรมดาของโจทย์บันไดจะคำนวณ "วิธีถึงขั้น 3" ซ้ำหลายรอบมากจนโตแบบ exponential — DP แก้ด้วยการจดคำตอบแต่ละขั้นไว้ในตาราง ขั้นละครั้ง เหลือ O(n) ในชีวิตจริง feature "Did you mean...?" ของ search box ใช้ edit distance ซึ่งเป็น DP คลาสสิก
- 🔎 **Keyword:** "มีกี่วิธี (how many ways)", "ค่าน้อยสุด/มากสุด" + ทางเลือกซ้อนกัน, "ลำดับย่อย (subsequence)", "ใช้หรือไม่ใช้ของชิ้นนี้", "Greedy ดูเหมือนจะใช้ได้แต่มีตัวอย่างค้าน"
- **สองรูปแบบ:** Top-down = recursion + memoization (จดคำตอบระหว่างทาง) / Bottom-up = เติมตารางจากปัญหาเล็กสุดขึ้นไป — ผลลัพธ์เหมือนกัน ต่างกันที่วิธีคิดและการใช้ call stack

**วิธีคิด DP แบบภาษาคน 3 ขั้น:**

1. **State:** "คำตอบในช่องนี้หมายถึงอะไร" เช่น "จำนวนวิธีถึงขั้นที่ i"
2. **Transition:** "ช่องนี้สร้างจากช่องไหน" เช่น "มาจากขั้น i−1 หรือ i−2"
3. **Base case:** "ช่องแรกสุดรู้ค่าเลย" เช่น "ขั้น 1 มี 1 วิธี"

### 5.4 Keyword → Pattern (แผนที่รวม)

```
อ่านโจทย์
    ↓
มีคำว่า...
    ├── "เรียงแล้ว"            → Binary Search หรือ Two Pointer
    ├── "ช่วงต่อเนื่อง"         → Sliding Window (หรือ Prefix Sum)
    ├── "ผลรวมช่วง ถามหลายรอบ"  → Prefix Sum
    ├── "เคยเจอไหม / นับซ้ำ"    → Hash Map / Set
    ├── "ทางที่สั้นที่สุด"        → BFS
    ├── "ทุกทาง / เชื่อมกันไหม"  → DFS
    ├── "ซ้อนกัน / tree"         → Recursion
    ├── "ล่าสุด / จับคู่วงเล็บ"   → Stack
    ├── "ตามลำดับที่มา"          → Queue
    ├── "จัดตาราง / ช่วงเวลา"    → Sort + Greedy
    └── "มีกี่วิธี / ดีที่สุด + ทางเลือกซ้อน" → DP
```

> **ให้มองภาพนี้ว่า** "keyword ในโจทย์คือป้ายบอกทาง ที่ชี้ว่าควรหยิบเครื่องมือไหนขึ้นมาลองก่อน ไม่ใช่คำตอบตายตัว"

## 6. Example

### 6.1 โจทย์: "หาคู่สินค้าที่ราคารวมเท่างบพอดี"

> ระบบโปรโมชั่น: ลูกค้ามีคูปอง 500 บาท ต้องการซื้อสินค้า 2 ชิ้นที่รวมกันได้ 500 พอดี มีสินค้าหลายพันรายการ (ราคาไม่ได้เรียง)

| ขั้น | ความคิด |
|---|---|
| Understand | หาสินค้า 2 ชิ้น (ไม่ซ้ำชิ้นเดียวกัน) ที่ราคารวม = งบ |
| Input | list ราคาจำนวนเต็ม ไม่เรียง อาจมีราคาซ้ำ |
| Output | ถาม interviewer: คืนคู่แรกที่เจอ หรือทุกคู่? คืน index หรือราคา? สมมติตกลงว่าคืน index คู่แรก |
| Constraints | n หลักพันถึงแสน → O(n²) เสี่ยง ควรเป้า O(n) หรือ O(n log n) |
| Example | `[120, 380, 250, 250, 90]` งบ 500 → (120, 380) หรือ (250, 250) |
| Brute Force | เทียบทุกคู่ → O(n²) time, O(1) space |
| Pattern | "ไม่เรียง + หาคู่ + เคยเจอไหม" → **Hashing** / หรือ sort แล้ว **Two Pointer** |
| Optimize | เดินทีละชิ้น ถามว่า "ราคาที่ขาด (500 − ราคานี้) เคยเห็นไหม" ถ้าไม่เคย จดราคานี้กับ index ลง Hash Map |
| Complexity | Hashing: O(n) time, O(n) space / Sort + Two Pointer: O(n log n) time แต่ต้องจำ index เดิมไว้ด้วย |
| Edge Cases | list ว่าง, ชิ้นเดียว, ไม่มีคู่ไหนเลย, ราคาเดียวกันสองชิ้น (250+250) ต้องไม่นับชิ้นเดียวซ้ำตัวเอง |

```
Brute Force O(n²)
       ↓  "งานซ้ำคือการค้นหาตัวคู่ซ้ำ ๆ"
Hash Map ค้นตัวคู่ O(1)
       ↓
รวม O(n) time + O(n) space
```

> **ให้มองภาพนี้ว่า** "เปลี่ยนจากการเดินถามทุกคนว่าราคาเท่าไร มาเป็นการเปิดสมุดที่จดไว้แล้ว"

**Trade-off ที่ควรพูด:** ถ้า memory จำกัดมาก การ sort + Two Pointer ใช้ memory เพิ่มน้อยกว่า (ขึ้นกับวิธี sort) แต่แลกกับเวลา O(n log n) และต้องรักษา index เดิม

### 6.2 โจทย์: "Error spike ใน 5 นาทีที่แย่ที่สุด"

> มี log จำนวน error ต่อนาทีตลอดวัน (1,440 ค่า) หา 5 นาทีติดกันที่ error รวมสูงสุด

- **Keyword ที่เห็น:** "5 นาทีติดกัน" = ช่วงต่อเนื่อง ความยาวคงที่ → **Sliding Window**
- **Brute force:** ทุกจุดเริ่ม รวม 5 ค่า → O(n × k) ถ้า k ใหญ่ขึ้นเช่น 60 นาที จะช้าลงตาม
- **Optimize:** รวม 5 นาทีแรก จากนั้นเลื่อนทีละนาที บวกนาทีใหม่ ลบนาทีที่หลุด จดค่าสูงสุด → O(n)
- **Edge cases:** log มีไม่ถึง 5 นาที, ทุกค่าเป็นศูนย์, มีหลายช่วงที่สูงเท่ากัน (คืนช่วงแรก? ถาม)
- **ต่อยอด:** ถ้าผู้ใช้เลือกช่วงเวลาเองแบบอิสระหลายครั้ง → เปลี่ยนเป็น **Prefix Sum** เพราะตอบแต่ละ query ได้ O(1)

### 6.3 โจทย์: "เพื่อนห่างกันกี่ขั้น"

> Social feature: แสดงว่าผู้ใช้ A กับผู้ใช้ B เชื่อมกันผ่านเพื่อนกี่ทอด (1st, 2nd, 3rd connection)

```
[A] → Queue: [เพื่อน A ทุกคน]         ระยะ 1
          ↓ ดึงออกทีละคน
       เพิ่มเพื่อนของเขาที่ยังไม่ visited  ระยะ 2
          ↓
       เจอ B → ตอบระยะนั้นทันที
```

> **ให้มองภาพนี้ว่า** "คลื่นที่ขยายออกจาก A ทีละวง วงแรกที่แตะ B คือระยะที่สั้นที่สุด"

- **Data Structure:** Graph (คนเป็น node, ความเป็นเพื่อนเป็น edge แบบสองทาง)
- **Pattern:** "ห่างกี่ขั้น / สั้นที่สุด" → **BFS** + **Set** สำหรับ visited
- **ทำไมไม่ใช่ DFS:** DFS อาจดิ่งลงเส้นทางยาว 6 ทอดก่อนเจอ B ทั้งที่มีทาง 2 ทอด ต้องสำรวจทั้งหมดถึงจะรู้ว่าสั้นสุด
- **Production thinking:** graph จริงมีคนหลายล้าน BFS จากทั้งสองฝั่งพร้อมกัน (bidirectional) หรือจำกัดความลึกไว้ที่ 3 ชั้น เป็นเทคนิคที่ใช้ลดงาน
- **Edge cases:** A กับ B คือคนเดียวกัน, ไม่เชื่อมกันเลย, graph มีวง (ถ้าไม่มี visited จะวนไม่จบ)

## 7. Compare

### 7.1 Array vs Linked List

| หัวข้อ | Array | Linked List |
|---|---|---|
| เข้าถึงตัวที่ i | O(1) | O(n) |
| แทรก/ลบหัว | O(n) | O(1) |
| แทรก/ลบกลาง (รู้ตำแหน่งแล้ว) | O(n) ต้องขยับ | O(1) แค่เปลี่ยนตัวชี้ |
| Memory | ติดกัน, cache-friendly | กระจาย + ตัวชี้เพิ่ม |
| ใช้จริง | เกือบทุกที่ | LRU cache, ระบบที่แทรก/ลบกลางบ่อย |

ในงานจริง Array มักเร็วกว่าในทางปฏิบัติสำหรับข้อมูลขนาดเล็ก-กลาง เพราะหน่วยความจำอยู่ติดกัน — Linked List ดีกว่าเมื่อ "ถือ node อยู่แล้วและต้องแทรก/ลบบ่อย"

### 7.2 Stack vs Queue

| หัวข้อ | Stack | Queue |
|---|---|---|
| หลักการ | LIFO — ล่าสุดออกก่อน | FIFO — มาก่อนออกก่อน |
| ภาพจำ | กองจาน | แถวคิว |
| Algorithm คู่หู | DFS | BFS |
| ใช้จริง | Undo, call stack, วงเล็บ | job queue, message queue, BFS |

### 7.3 Hash Map vs Set vs Array (ในการค้นหา)

| หัวข้อ | Array (ไม่เรียง) | Array (เรียง) | Hash Map | Set |
|---|---|---|---|---|
| หาว่ามีไหม | O(n) | O(log n) | O(1) เฉลี่ย | O(1) เฉลี่ย |
| เก็บข้อมูลประกอบ | ได้ | ได้ | ได้ (value) | ไม่ได้ |
| รักษาลำดับ | ได้ | ตามค่า | ขึ้นกับภาษา | ขึ้นกับภาษา |
| Memory เพิ่ม | ไม่ | ไม่ | O(n) | O(n) |

### 7.4 DFS vs BFS

| หัวข้อ | DFS | BFS |
|---|---|---|
| วิธีเดิน | ลึกก่อน | กว้างก่อน ทีละชั้น |
| เครื่องมือ | Stack / Recursion | Queue |
| หาทางสั้นสุด (edge เท่ากัน) | ไม่รับประกัน | รับประกัน |
| Memory | ตามความลึก | ตามความกว้างของชั้น (อาจใหญ่มาก) |
| เหมาะกับ | ทุกเส้นทาง, หาวง, backtracking, เชื่อมกันไหม | ระยะน้อยสุด, level order |

### 7.5 Two Pointer vs Sliding Window

| หัวข้อ | Two Pointer | Sliding Window |
|---|---|---|
| ตัวชี้ | มักเริ่มสองฝั่ง เดินเข้าหากัน (หรือเร็ว-ช้า) | สองขอบของช่วง เดินไปทางเดียวกัน |
| สนใจ | คู่ของค่าสองตำแหน่ง | ทุกค่าที่อยู่ "ระหว่าง" ขอบ |
| เงื่อนไขมักต้องการ | ข้อมูลเรียงแล้ว | ช่วงต่อเนื่อง |
| ตัวอย่าง | Two Sum บน sorted, palindrome | ผลรวมสูงสุด k ตัว, substring ไม่ซ้ำ |

Sliding Window จริง ๆ คือ Two Pointer รูปแบบหนึ่ง ต่างที่ "ความหมาย" ของช่องว่างระหว่างนิ้ว

### 7.6 Greedy vs Dynamic Programming

| หัวข้อ | Greedy | DP |
|---|---|---|
| วิธีคิด | เลือกดีสุดตอนนี้ ไม่ย้อน | ลองทุกทางเลือกย่อย แต่จดคำตอบไว้ |
| ความเร็ว | มักเร็วกว่า (มักแค่ sort + loop) | ช้ากว่า ใช้ memory ตามจำนวน state |
| ถูกเสมอไหม | ถูกเฉพาะเมื่อ "ทางเลือกดีสุดเฉพาะหน้า" นำไปสู่คำตอบดีสุดจริง | ถูกเมื่อนิยาม state และ transition ถูก |
| ตรวจยังไง | หาตัวอย่างค้าน (counter-example) | ตรวจว่ามีปัญหาย่อยซ้ำไหม |

## 8. Common Mistakes

| # | ความผิดพลาด | ทำไมผิด | ทำแทนแบบนี้ |
|---|---|---|---|
| 1 | รีบเขียน code ทันทีที่อ่านโจทย์จบ | ยังไม่รู้ input/output/edge case จริง แก้ผิดโจทย์ได้ | ทวนโจทย์ + ถามคำถาม 1–2 นาทีก่อนเสมอ |
| 2 | เงียบคิดคนเดียว | interviewer ไม่เห็นกระบวนการคิด ให้คะแนนไม่ได้ | คิดออกเสียง (think aloud) |
| 3 | ข้าม brute force เพราะกลัวดูไม่เก่ง | ไม่มี baseline ถ้า optimize ไม่ได้จะไม่มีคำตอบเลย | พูด brute force + Big O ก่อน แล้วค่อยปรับ |
| 4 | ไม่ถาม constraints | ไม่รู้ว่า O(n²) รอดไหม | ถามขนาด n และช่วงของค่า |
| 5 | ท่อง pattern แล้วยัดใส่ทุกโจทย์ | บางโจทย์หน้าตาคล้ายแต่เงื่อนไขต่าง เช่น Sliding Window กับค่าติดลบ | ใช้ keyword เป็น "ตัวเลือกแรกที่จะลอง" แล้วตรวจเงื่อนไข |
| 6 | ใช้ Greedy โดยไม่พิสูจน์ | Greedy ผิดได้เงียบ ๆ | ลองหาตัวอย่างค้านก่อน |
| 7 | Recursion ไม่มี base case / ไม่ทำให้ปัญหาเล็กลง | วนไม่จบ → stack overflow | เขียน base case ก่อนเป็นอย่างแรก |
| 8 | BFS/DFS บน graph แต่ลืม visited | วนไม่รู้จบเพราะ graph มีวง | ใช้ Set จด node ที่เคยเยี่ยม |
| 9 | พูดว่า Hash Map เป็น O(1) เสมอ | worst case O(n) เมื่อ collision หนัก | พูดว่า "เฉลี่ย O(1)" |
| 10 | ลืม space complexity | คำตอบเร็วแต่อาจใช้ memory เกิน | บอกทั้ง time และ space ทุกครั้ง |
| 11 | Off-by-one ใน loop / binary search | `<` กับ `<=`, mid คำนวณผิด ทำให้ loop ไม่จบ | dry run กับ array ขนาด 1 และ 2 |
| 12 | ทดสอบแค่ตัวอย่างที่โจทย์ให้ | ตัวอย่างในโจทย์มักเป็น happy path | เพิ่ม edge case เอง: ว่าง, ตัวเดียว, ซ้ำ, ติดลบ |
| 13 | คิดว่า Big O บอกเวลาจริง | Big O บอกอัตราการโต ไม่ใช่มิลลิวินาที | ใช้ Big O เทียบวิธี แล้วใช้ profiler วัดของจริง |
| 14 | ต่อ string ใน loop ใหญ่ | ในหลายภาษาเป็นการสร้าง string ใหม่ทุกรอบ | เก็บชิ้นส่วนใน list แล้วรวมครั้งเดียว (หรือใช้ builder ของภาษา) |
| 15 | Optimize ก่อนมีคำตอบที่ถูก | เร็วแต่ผิดก็ไม่มีประโยชน์ | ถูกก่อน → ชัดก่อน → เร็วทีหลัง |

## 9. Debugging

เมื่อ solution **ผิด** หรือ **ช้า** ให้ไล่ตามลำดับนี้ (ใช้ได้ทั้งตอนสัมภาษณ์และตอนงานจริง)

```
Solution มีปัญหา
       ↓
[1] ผิดหรือช้า?
       ├── ผิด ──→ [2] Dry run ด้วยตัวอย่างเล็กสุดที่พัง
       │                ↓
       │           [3] เช็คขอบเขต: index เริ่ม/จบ, < กับ <=
       │                ↓
       │           [4] เช็ค state: ตัวแปรถูก reset / update ถูกจังหวะไหม
       │                ↓
       │           [5] เช็ค edge case: ว่าง / ตัวเดียว / ซ้ำ / ติดลบ
       │
       └── ช้า ──→ [2] นับ loop ซ้อน → Big O จริงคือเท่าไร
                        ↓
                   [3] มี operation แอบแพงใน loop ไหม (ค้นใน array, ต่อ string, sort)
                        ↓
                   [4] งานซ้ำตรงไหน → Hash Map / Prefix Sum / Memoization
                        ↓
                   [5] เทียบกับ constraints อีกครั้ง
```

> **ให้มองภาพนี้ว่า** "แยกก่อนว่าปัญหาคือความถูกหรือความเร็ว เพราะสองอย่างนี้ใช้เครื่องมือตรวจคนละชุด"

### 9.1 Checklist เมื่อคำตอบ "ผิด"

| อาการ | สาเหตุที่พบบ่อย | วิธีตรวจ |
|---|---|---|
| ผิดเฉพาะตัวแรก/ตัวสุดท้าย | off-by-one | dry run array ขนาด 1, 2 |
| loop ไม่จบ | ตัวชี้ไม่ขยับในบางกรณี, binary search ไม่ตัดช่วง | เช็คว่าทุกรอบพื้นที่ค้นหาเล็กลงจริง |
| Recursion พัง (stack overflow) | ไม่มี base case / input ไม่เล็กลง | trace 3 ระดับแรกด้วยมือ |
| Graph traversal วนไม่จบ | ลืม visited | เช็คว่าจด visited "ก่อน" หรือ "หลัง" ใส่ queue ให้สม่ำเสมอ |
| นับซ้ำ / นับขาด | จด Hash Map ก่อนหรือหลังตรวจผิดจังหวะ | ไล่ตัวอย่างที่มีค่าซ้ำ เช่น 250 + 250 |
| Sliding Window ผิดเมื่อมีค่าติดลบ | สมมติฐาน "ขยายแล้วผลรวมเพิ่มเสมอ" พัง | เปลี่ยนเป็น Prefix Sum + Hash Map |
| Greedy ได้คำตอบไม่ดีสุด | greedy choice ไม่ถูกต้องสำหรับโจทย์นี้ | หาตัวอย่างค้าน แล้วพิจารณา DP |

### 9.2 เชื่อมกับ Production

อาการ "หน้า list ช้าเมื่อข้อมูลเยอะ" ใน production คือปัญหา Big O ตัวเดียวกัน:

```
ผู้ใช้บ่นว่าช้า
       ↓
Profiler ชี้ไปที่ function filter / merge ข้อมูล
       ↓
พบ loop ซ้อน: สำหรับทุก order → หา customer ใน array
       ↓
เปลี่ยน customer array เป็น Hash Map (id → customer)
       ↓
O(n × m) → O(n + m)
```

> **ให้มองภาพนี้ว่า** "bug ด้านความเร็วใน production ส่วนมากไม่ใช่เรื่องลึกลับ แต่คือ brute force ที่ไม่มีใครสังเกตตอนข้อมูลยังน้อย"

## 11. Answer Like a Developer

ไม่ใช่ประโยคท่องจำ แต่เป็น **โครงสร้าง** ที่ใช้ตอบได้ทุกโจทย์

### 11.1 โครงตอบโจทย์ Coding (ใช้ในห้องสัมภาษณ์)

```
[ทวน]      "ขอทวนนะครับ โจทย์ต้องการ..."
    ↓
[ถาม]      "input เรียงไหม ซ้ำได้ไหม n ใหญ่สุดเท่าไร คืนอะไร"
    ↓
[ตัวอย่าง]  "ขอลองกับตัวอย่างเล็ก ๆ ... และเคสแปลก ๆ ..."
    ↓
[Brute]    "วิธีตรง ๆ คือ ... ได้ O(...) "
    ↓
[สังเกต]    "งานที่ซ้ำคือ ... โจทย์มีคำว่า ... นึกถึง pattern ..."
    ↓
[Optimize] "ถ้าใช้ ... จะเหลือ O(...) แลกกับ memory O(...)"
    ↓
[ตกลง]     "ขอเขียนแบบนี้นะครับ" → เขียน
    ↓
[ทดสอบ]    dry run ตัวอย่าง + edge case ออกเสียง
    ↓
[สรุป]      Time / Space / trade-off / ถ้ามีเวลาจะปรับอะไรต่อ
```

> **ให้มองภาพนี้ว่า** "พาคนสัมภาษณ์เดินไปด้วยกันทีละขั้น ให้เขาเห็นความคิด ไม่ใช่แค่เห็นผลลัพธ์"

### 11.2 โครงตอบคำถามเชิงแนวคิด (เช่น "BFS กับ DFS ต่างกันอย่างไร")

1. **นิยามภาษาคน:** "BFS กระจายออกทีละชั้น DFS ดิ่งลึกก่อนแล้วย้อน"
2. **กลไก:** "BFS ใช้ Queue, DFS ใช้ Stack หรือ recursion"
3. **ใช้เมื่อไร:** "หาทางสั้นสุดใน graph ที่ edge เท่ากัน → BFS / สำรวจทุกทาง หาวง → DFS"
4. **Trade-off:** "BFS memory ตามความกว้าง DFS memory ตามความลึก"
5. **ตัวอย่างจริง:** "feature เพื่อนของเพื่อนใช้ BFS / ตรวจ circular dependency ใช้ DFS"

### 11.3 โครงตอบเมื่อ "คิดไม่ออก"

อย่าเงียบ ให้พูดตามลำดับนี้:

1. "ขอเริ่มจาก brute force ก่อนเพื่อให้มีคำตอบที่ถูก"
2. "ขอลองตัวอย่างเล็ก ๆ ด้วยมือ ดูว่ามี pattern อะไร"
3. "ถ้า sort ก่อนจะช่วยไหม?" / "ถ้าจดสิ่งที่เคยเห็นไว้จะช่วยไหม?"
4. "ถ้าคำตอบของข้อเล็กกว่ารู้แล้ว ช่วยข้อใหญ่ได้ไหม?" (ทางไป Recursion / DP)
5. ขอ hint อย่างมีเป้าหมาย: "ผมกำลังลังเลระหว่าง A กับ B ครับ"

## 12. One-Minute Review

- Problem Solving สอน **process** ไม่ใช่ syntax: Understand → Input → Output → Constraints → Example → Brute Force → Pattern → Optimize → Complexity → Edge Cases
- **Constraints บอก Big O เป้าหมาย:** n ใหญ่ → ต้อง O(n) หรือ O(n log n)
- **Big O:** O(1) ทันที, O(log n) ตัดครึ่ง, O(n) รอบเดียว, O(n log n) sort, O(n²) loop ซ้อน
- **Data Structure = คำตอบของคำถาม:** index → Array, key → Hash Map, มีไหม → Set, ล่าสุด → Stack, มาก่อน → Queue, แทรกกลางบ่อย → Linked List, ลำดับชั้น → Tree, เครือข่าย → Graph
- **Keyword → Pattern:** เรียงแล้ว → Binary Search / Two Pointer, ช่วงต่อเนื่อง → Sliding Window, ผลรวมช่วงหลายครั้ง → Prefix Sum, เคยเจอ/นับซ้ำ → Hashing, สั้นที่สุด → BFS, ทุกทาง/เชื่อมกันไหม → DFS, ซ้อนกัน → Recursion, ดีสุดเฉพาะหน้า → Greedy, มีกี่วิธี/ปัญหาย่อยซ้ำ → DP
- **Optimize = หางานซ้ำ:** ค้นซ้ำ → Hash, คำนวณซ้ำ → Prefix Sum/DP, ดูของไม่จำเป็น → Two Pointer/Binary Search
- **ทุกคำตอบบอก Time + Space + trade-off**
- **Debug:** แยกผิดกับช้า / dry run ตัวอย่างเล็ก / เช็คขอบเขต / เช็ค edge case
- **Think aloud** สำคัญเท่ากับคำตอบ

## 13. Memory Card

**จำ 5 อย่าง**

1. **ถูกก่อน เร็วทีหลัง** — เริ่มจาก brute force + Big O เสมอ แล้วค่อยหางานซ้ำเพื่อ optimize
2. **Constraints คือคำใบ้** — ขนาด n บอกว่า Big O ไหนรอด
3. **Data Structure เลือกจากคำถามที่ถามบ่อยที่สุด** — ถามด้วย index, key, มีไหม, ล่าสุด, มาก่อน, ลำดับชั้น, เครือข่าย
4. **Keyword ในโจทย์ชี้ Pattern** — แต่ต้องตรวจเงื่อนไขก่อนใช้เสมอ (เช่น ค่าติดลบ, greedy ผิดได้)
5. **Edge Case + Think Aloud** — ว่าง / ตัวเดียว / ซ้ำ / ติดลบ / ใหญ่สุด และพูดความคิดออกมาตลอด

**Keyword:**

- Two Pointer → สองนิ้วเดินเข้าหากันบนข้อมูลเรียง
- Sliding Window → หน้าต่างเลื่อนบนช่วงต่อเนื่อง บวกเข้า ลบออก
- Binary Search → เปิดพจนานุกรม ตัดครึ่งทุกรอบ
- Prefix Sum → เลขไมล์สะสม ปลายลบต้น
- Hashing → สมุดจดชื่อแขก "เคยเจอไหม"
- DFS → เขาวงกต ดิ่งสุดแล้วย้อน
- BFS → คลื่นน้ำ ทีละวง เจอแรกคือใกล้สุด
- Recursion → ตุ๊กตาแม่ลูกดก ต้องมีตัวเล็กสุด
- Greedy → ทอนเหรียญใหญ่ก่อน แต่ผิดได้
- DP → จดคำตอบย่อยลงตาราง ไม่คิดซ้ำ
- Big O → ถ้าข้อมูลโต 10 เท่า งานโตกี่เท่า
